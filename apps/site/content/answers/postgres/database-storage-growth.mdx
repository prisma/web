A database can grow while the number of customers stays flat. Saved documents, repeated imports, large JSON payloads, indexes and retained history all contribute. An upgrade decision is easier when you know which of those is responsible.

We make Prisma Postgres and Prisma Compute. Provider pricing and PostgreSQL documentation linked here were checked on October 22, 2026. Prisma ORM is optional.

## What should I compare before upgrading?

Check the scope of the allowance: it may apply to a database, project or account. Compare it with the provider's reported usage, the additional storage rate, other billed resources and any maximum size. A larger included allowance is useful only if the rest of the plan fits the workload.

Ask whether an upgrade changes the existing resource or requires a new database and a data copy. Verify credentials, downtime expectations, available backups and the way to return to a working state. Do this before the database is too full to accept normal application work.

On the current Prisma pricing page, Free includes 2 GB, Starter includes 10 GB and Pro includes 50 GB. Starter is a $10 monthly base with additional database storage at $2 per GB; Pro is a $49 base with additional storage at $1.50 per GB. Those are included billing amounts, not a promise of a particular database's maximum capacity. Operations and any Compute usage have their own meters.

Prisma Postgres is a straightforward fit when you want ordinary PostgreSQL access and explicit operation and storage pricing. Choose the plan using both expected data growth and query usage. A higher plan can change several rates at once.

## How do I measure and prepare the Prisma upgrade?

### 1. Confirm the database and the billed usage

In [Prisma Console](https://console.prisma.io), identify the database the app actually uses and review the workspace's current plan and usage. Include test databases when checking totals. A production database size query does not explain every resource on a workspace bill.

Keep credentials in the server's secret configuration. Prisma Postgres works with ordinary PostgreSQL clients; use the [direct connection](/docs/postgres/database/connecting-to-your-database) for administrative inspection.

### 2. Find the largest relations

With the PostgreSQL client installed, open a direct connection to the intended database. These queries inspect sizes without changing records:

~~~sql
SELECT current_database() AS database_name,
       pg_database_size(current_database()) AS database_bytes;

SELECT schemaname, relname,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 10;
~~~

The first query returns the selected database and its size in bytes. The second returns up to ten user tables with their schema names, including their indexes and related storage in the total. The names and sizes depend on your database; an empty database can return no user tables.

PostgreSQL's [size functions](https://www.postgresql.org/docs/17/functions-admin.html) describe what those totals contain. Treat SQL size as a diagnostic measurement, then reconcile it with the provider's accounting. It is not a substitute for the billing usage view.

### 3. Separate useful growth from avoidable growth

Review the largest tables with someone who knows what the records mean. Repeated imports, duplicated model responses or an unbounded event log may need a retention or deduplication rule. Customer files such as PDFs usually belong in [object storage](/compute/file-uploads-disappear-after-redeploy), with a reference in Postgres.

Keep indexes that support real queries. Removing them to save space can make the app slower. Use [query diagnostics](/postgres/managed-postgres-query-monitoring) before deciding which indexes are unnecessary.

Deleting old rows does not usually shrink the underlying file immediately. PostgreSQL's [vacuuming documentation](https://www.postgresql.org/docs/17/routine-vacuuming.html) distinguishes reusable space from returning space to the operating system. Do not treat a table rewrite as a routine cleanup button: it has locking and extra-space requirements.

### 4. Change the workspace plan and verify the database

For a directly billed workspace, open **Workspace Settings > Billing** in Console, check the **Subscription** card and review your subscription controls and [current paid pricing](/pricing) before confirming a change. The [billing guide](/docs/console/more/billing) explains the workspace scope and payment timing. If you bought through Vercel Marketplace, use **Integrations > Manage** on the Prisma integration, then **Settings > Change Plan**, following the [Vercel upgrade steps](/docs/postgres/faq#how-do-i-upgrade-my-plan-if-i-am-using-prisma-postgres-via-vercel).

Record the existing database identifier, connection target and a few known records before changing the subscription, then check them and a representative write afterwards. A newly created empty database is not a substitute for preserving the existing one. The public billing guide does not specify a maximum storage capacity or guarantee upgrade availability and credential continuity. If your launch depends on those guarantees, confirm the procedure for your database with [Prisma support](/docs/console/more/support) before it fills; do not infer them from an included-GB figure.

Keep headroom for normal writes and any planned import. Set a budget using the documented [spending controls](/compute/typescript-hosting-spending-controls); a budget is not extra capacity. Keep a [backup and restore procedure](/docs/postgres/database/backups) independent of the app release. If a capacity requirement calls for a new database, rehearse its data copy and cutover with test records before moving customer data.

## When should I choose another setup?

Choose another service when a required capacity limit, region, extension or recovery feature does not fit. Prisma Postgres has no point-in-time recovery yet (it is coming in November 2026), and automatic snapshots are on paid plans. A larger storage allowance does not change that recovery model.

For an analytical archive dominated by infrequent scans, compare a separate analytical store against keeping everything in the transactional database. Preserve the customer workflow and the records it needs rather than moving data merely to make a size graph smaller.
