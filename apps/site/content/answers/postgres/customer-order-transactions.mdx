Consider a portal that creates a customer account and its first order. If the account insert commits but the order insert fails, the application can leave behind a record that does not match the action the user requested. A transaction gives the application one decision about those related database changes.

We make Prisma Postgres and Prisma Compute. The provider and PostgreSQL documentation linked below was checked on October 18, 2026. The SQL examples use ordinary Postgres; Prisma ORM is optional.

## What should the database guarantee?

PostgreSQL's [transaction tutorial](https://www.postgresql.org/docs/17/tutorial-transactions.html) explains the all-or-nothing behavior of a transaction. Its [constraints](https://www.postgresql.org/docs/17/ddl-constraints.html) enforce rules about valid records. Use both: a foreign key can prevent an order referencing a missing customer, while a transaction groups the customer and order creation into one operation.

Decide the business boundary before writing SQL. An account may legitimately exist without an order in one application, while another workflow requires both. Group the writes that must succeed together, rather than wrapping unrelated work in a long transaction.

Also plan for a lost response after commit. The database may have saved the order even if the browser never received success. Use a stable request identifier, a suitable uniqueness constraint and application logic that returns the existing result on a retry.

## How do I test this on Prisma Postgres?

### 1. Create a development database and schema

Create a database in [Prisma Console](https://console.prisma.io) and use its [direct connection](/docs/postgres/database/connecting-to-your-database) for this setup. Run the demonstration in a fresh development database, then put your real schema in version-controlled migrations.

These fixed IDs make the example reproducible; production code should use its normal ID-generation strategy.

```sql
CREATE TABLE transaction_customer_demo (
  id integer PRIMARY KEY,
  email text NOT NULL UNIQUE
);

CREATE TABLE transaction_order_demo (
  id integer PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES transaction_customer_demo(id),
  amount_cents integer NOT NULL CHECK (amount_cents >= 0),
  request_key text NOT NULL UNIQUE
);
```

The foreign key protects the relationship and the check constraint rejects a negative amount. The request key is a demonstration of deduplication; a multi-account app should scope request identifiers and access checks to the appropriate account.

### 2. Commit both records together

```sql
BEGIN;

INSERT INTO transaction_customer_demo (id, email)
VALUES (101, 'alex@example.com');

INSERT INTO transaction_order_demo (id, customer_id, amount_cents, request_key)
VALUES (501, 101, 2500, 'checkout-demo-1');

COMMIT;

SELECT c.email, o.amount_cents
FROM transaction_customer_demo c
JOIN transaction_order_demo o ON o.customer_id = c.id
WHERE o.id = 501;
```

The result is `alex@example.com` with `2500` cents. Other sessions see the committed customer and order together. If a statement fails, application code should handle the error and roll back the transaction before reusing the connection.

### 3. Verify the rollback path

Create a customer provisionally, then try to insert an order with a negative amount. The check constraint will reject the order:

```sql
BEGIN;

INSERT INTO transaction_customer_demo (id, email)
VALUES (102, 'rollback@example.com');

INSERT INTO transaction_order_demo (id, customer_id, amount_cents, request_key)
VALUES (502, 102, -1, 'checkout-demo-2');
```

Postgres reports a violation of `transaction_order_demo_amount_cents_check`. The transaction is now aborted. On the same connection, run the following to roll it back and check both tables:

```sql
ROLLBACK;

SELECT count(*) AS remaining_customers
FROM transaction_customer_demo WHERE id = 102;

SELECT count(*) AS remaining_orders
FROM transaction_order_demo WHERE id = 502;
```

Both counts are `0`. The customer insert is rolled back, and the rejected order was never saved. Also test connection errors and retry behavior in your application's integration tests.

### 4. Use one connection for the application transaction

With `pg`, follow the [client acquisition and rollback pattern](https://node-postgres.com/features/transactions). All statements between `BEGIN` and `COMMIT` belong on the same acquired client. Ordinary app traffic can use Prisma Postgres's [pooled endpoint](/docs/postgres/database/connection-pooling); a pool does not remove the requirement to keep the transaction on one client.

Authenticate the customer and validate request values on the server. Use bound query parameters for application input. Keep network calls to external services outside the database transaction so they do not hold a connection and locks while another system responds.

For appointment reservations, the [booking app hosting guide](/postgres/booking-app-hosting) applies the same transaction discipline to claiming a slot, handling competing requests and delivering confirmations after the reservation commits.

## What else should I check before choosing a provider?

Place the app's database-calling server [near Postgres](/postgres/nodejs-database-regions) and measure representative transactions. Keep transactions short and investigate lock contention before assuming a larger database will fix a slow checkout.

Backups address recovery from committed mistakes or other incidents; they do not replace correct transaction boundaries. Prisma Postgres has plan-dependent snapshots and no point-in-time recovery yet (it is coming in November 2026). Choose another provider if its recovery capabilities, regions or extension support are required by your application.
