If a customer disappears when the server restarts, the app probably saved the record in process memory. If the record appears on one laptop but not another, it may live in browser storage. Both can be useful for a mockup, but neither gives a team a shared customer database. To find out where an app's records went and move them, see [why an app forgets new records after it restarts](/postgres/app-data-lost-after-restart).

We make Prisma Postgres and Prisma Compute. The provider documentation linked below was checked on October 17, 2026. Prisma ORM is optional: Prisma Postgres works with ordinary PostgreSQL clients.

## What does "saved permanently" mean for a prototype?

You usually need records to survive a process restart, a new app deployment and a user changing devices. A database stores those records independently of the web server. It also gives the application a central place to enforce relationships and update related records in a transaction.

That does not mean the records are guaranteed to exist forever. Someone can delete a database, application code can overwrite a field, and an account can run into plan or billing limits. Decide who owns the database account, who can change production and what recovery process you will use.

If the prototype contains personal information, add login and server-side authorization before making it public. A shared database should not mean that every user can read every customer. Develop against fictional or sanitized records, especially when an AI assistant is making schema changes.

Prisma Postgres is useful when a prototype is becoming an application: keep PostgreSQL as the durable store, keep your preferred client, and add Prisma Compute if you want to manage the app and database together. Another app host can connect to the same database through its server environment.

## How do I start saving customer details with Prisma Postgres?

### 1. Create an account-owned database

Choose one creation workflow. For a separately managed database, sign in to [Prisma Console](https://console.prisma.io), create or choose the intended project and create a Prisma Postgres database. If you use the Composer dependency workflow in step 2, let the module provision the database in your account instead; you do not need to create a second database in Console. In either workflow, choose a region near the app server and use names that distinguish development from production.

If you previously tried `npx create-db`, check whether you claimed that database. An [unclaimed database expires when its selected lifetime ends](/docs/postgres/npx-create-db), which defaults to 24 hours and can be shorter. Do not treat a temporary playground URL as the permanent home for customer records.

### 2. Connect from the server

Keep database access on the server. Choose the connection workflow that matches how you created the database; never put database credentials in browser code.

For an app on Prisma Compute, follow the [Composer database dependency guide](/docs/composer/databases): declare a `rawPostgres()` dependency for your service, provision the database in the module and wire it into the service. If that dependency is named `db`, server code reads its connection from `service.load().db.url` and passes it to the PostgreSQL client. This workflow does not require a separate `DATABASE_URL` environment variable.

For a separately managed database on Prisma Compute, or an app on Vercel or Netlify, get the [connection strings](/docs/postgres/database/connecting-to-your-database) and configure the pooled URL in the host's server environment instead. Keep the direct connection for migration and administrative workflows that need it. Use distinct databases for development, review and production. The [test-environment guide](/postgres/typescript-test-environment) explains how to keep an assistant's changes away from customer data.

### 3. Add a customer table and authenticated save endpoint

Start with fields the app actually needs: an ID, account ownership, email and creation time. Apply the table definition through a recorded migration. If the prototype has variable onboarding answers, use the [customer records and JSONB example](/postgres/customer-records-json) for a concrete schema.

Make the browser call a server endpoint. That endpoint should verify the session, validate incoming values, derive the authorized account and issue a parameterized insert. Show success only after the write succeeds. On reads, apply the same account restrictions rather than returning the entire customer table.

### 4. Check that persistence works beyond one session

Create a fictional customer through the app and note its ID. Reload the page, restart the app process and read the record again. Sign in on a second browser or device with the same authorized account and confirm it appears there too. Check that another account cannot read it.

This verifies the write/read path and shared storage, but recovery from a deletion needs its own test: rehearse restoring the data into a safe environment.

### 5. Set the recovery and cost expectations

Prisma Postgres's [backup documentation](/docs/postgres/database/backups) describes automated snapshots on Starter, Pro and Business plans. Snapshots are daily on days with database activity; a restore may omit changes made after the snapshot. The service has no point-in-time recovery yet; it is coming in November 2026.

Choose a plan based on what the business can afford to lose, and rehearse restoring into a safe environment. If you maintain manual exports, protect them as carefully as the original records. Review current [pricing and limits](/pricing) before inviting more users; an early prototype's usage is not a forecast of its production bill.

## When should I choose a different setup?

If your app must work offline, it may need local storage plus synchronization; a hosted database alone does not solve that. If required data residency or recovery features are unavailable in Prisma Postgres, choose a service that meets those requirements.

For a disposable mockup with no shared data, browser storage may be enough. Once real customers rely on saved records, give the database an accountable owner, restricted access and a tested recovery process. Hosting the app somewhere else does not remove those database responsibilities.

If the prototype already queries with the pg package, see [hosted Postgres for an existing node-postgres app](/postgres/node-postgres-hosting) for a connection probe and the configuration to check before moving data.
