An app that was fast with a few hundred test rows and slows down with real customer data has usually hit a query that reads far more rows than it returns, or a code path that sends far more queries than it needs. Find out which one before changing anything: time one slow request, split it into database time and the rest, then use `pg_stat_statements` and `EXPLAIN (ANALYZE, BUFFERS)` on the statements that take the time. Every step below works on any Postgres host that gives you a SQL connection.

We make Prisma Postgres and Prisma Compute. PostgreSQL, node-postgres, Drizzle and OpenTelemetry behavior on this page links to each project's documentation, checked on October 22, 2026. The query plans and timings come from a test on October 22, 2026: a Prisma Postgres database (PostgreSQL 17.2) in `eu-central-1`, queried from a laptop about 34 ms away. Your numbers will differ.

## Why does an app slow down when the data gets real?

Test data hides the problems that grow with row counts. The [PostgreSQL docs](https://www.postgresql.org/docs/current/using-explain.html) warn that results on a toy-sized table cannot be assumed to apply to large tables: the planner's costs aren't linear, and on a tiny table it nearly always reads the whole table whether an index exists or not. So a missing index costs almost nothing with 500 rows and a lot with 2 million.

The usual causes:

- **A filter, join or sort on a column with no index.** PostgreSQL indexes primary keys and unique constraints, but it [doesn't create an index on the referencing columns of a foreign key](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK). A query such as "orders for this customer" scans the whole `orders` table.
- **N+1 queries.** A list page that runs one query for the list and one more per row sends 201 queries for 200 rows. Each query is fast; the round trips add up.
- **Unbounded results and deep pages.** A query with no `LIMIT` returns every matching row, and the rows skipped by `OFFSET` [still have to be computed](https://www.postgresql.org/docs/current/queries-limit.html), so page 5,000 costs more than page 1.
- **Sorts and hashes that outgrow memory.** A sort can use up to [`work_mem`](https://www.postgresql.org/docs/current/runtime-config-resource.html#GUC-WORK-MEM) (4 MB by default), and a hash a multiple of it, before it writes to temporary files on disk.
- **Stale statistics.** The planner picks plans from table statistics. After a large import, they can describe the old, small table until `ANALYZE` runs.
- **Waiting for connections or locks.** Requests that wait for a free pool connection or for a lock held by another transaction are slow even when every query is fast.

## How do I check whether Postgres is the problem?

Work from the request inward: first find out how much of the slow request is SQL, then which statements, then why. Steps 2 to 4 cover slow SQL, and step 5 covers a slow request whose SQL is fast.

### 1. Split one slow request into database time and the rest

Pick one slow request and measure four numbers for it: the total request time, the time spent waiting for a database connection, the time spent running SQL, and the number of queries it sends. An APM tool or OpenTelemetry tracing gives you all four. For node-postgres, the [OpenTelemetry `pg` instrumentation](https://github.com/open-telemetry/opentelemetry-js-contrib/tree/main/packages/instrumentation-pg) records a span per query and a `pg-pool.connect` span for the time spent waiting for a pool connection.

Without tracing, your data layer's logs give you the SQL and its count. Prisma ORM [emits query events](/docs/orm/v7/prisma-client/observability-and-logging/logging#event-based-logging) that include each query's duration:

```ts
const prisma = new PrismaClient({
  adapter, // your driver adapter, for example PrismaPg
  log: [{ emit: "event", level: "query" }],
});

prisma.$on("query", (e) => {
  console.log(`${e.duration}ms ${e.query}`);
});
```

Drizzle prints each query and its parameters with [`drizzle(url, { logger: true })`](https://orm.drizzle.team/docs/goodies#logging). With node-postgres, time the `pool.query()` calls yourself, and log [`pool.waitingCount`](https://node-postgres.com/apis/pool#properties), the number of requests queued for a client because every client is checked out.

Then read the numbers:

| What you see | Where the time goes | Go to |
| --- | --- | --- |
| One or a few queries take most of the request | Query execution | Steps 2 to 4 |
| Dozens or hundreds of fast queries per request | Round trips (N+1) | Step 5 |
| Long `pg-pool.connect` spans or a growing `pool.waitingCount` | Waiting for a pool connection | Step 5 |
| Queries are fast and few, the request is still slow | App code, serialization or an external API | Not the database |

### 2. Find the statements that use the most time

[`pg_stat_statements`](https://www.postgresql.org/docs/current/pgstatstatements.html) records the count and timing of every statement shape the server runs, so it shows the queries that matter without guessing. It has to be loaded at server start through `shared_preload_libraries`, which needs a restart, and then enabled in each database. On a managed host, check that it is in the provider's extension list, then run:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       rows,
       left(query, 100) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

The `_exec_time` columns are named `total_time` and `mean_time` before PostgreSQL 13. In the test, after the app's "recent orders" screen ran for 20 customers and a dashboard looked up each order's customer one by one, the top rows were:

```text
calls | total_ms | mean_ms | rows | query
   20 |   2024.3 |  101.22 |  400 | select id, status, total_cents, created_at from orders where customer_id = $1 order by ...
  200 |      7.0 |    0.03 |  200 | select name from customers where id = $1
```

Read the columns together. A high `mean_ms` is a slow query, which steps 3 and 4 fix. A high `calls` count with a tiny `mean_ms` is a query that runs in a loop: the database spends 7 ms on it in total, but the app pays one network round trip per call, which step 5 covers. Run `SELECT pg_stat_statements_reset();` before you reproduce a slow page, so the numbers describe that page; by default only superusers can run it, unless someone grants access. Unless your role has the privileges of `pg_read_all_stats`, you see other roles' statistics but not their query text.

If your host lets you change server settings and read the server log, two more tools help. [`log_min_duration_statement`](https://www.postgresql.org/docs/current/runtime-config-logging.html#GUC-LOG-MIN-DURATION-STATEMENT) logs every statement slower than a threshold, such as `500ms`, and [`auto_explain`](https://www.postgresql.org/docs/current/auto-explain.html) logs the plan of each one. Changing either needs superuser rights or the server configuration, so on a managed host you change them through the provider's settings, if it offers them.

### 3. Read the plan with EXPLAIN (ANALYZE, BUFFERS)

Take the slowest statement, put in real parameter values, and run it with [`EXPLAIN (ANALYZE, BUFFERS)`](https://www.postgresql.org/docs/current/sql-explain.html). Run it against a database with the same data volume as production, because a plan from test data can't be trusted for real data. `ANALYZE` executes the statement, so wrap an `INSERT`, `UPDATE` or `DELETE` in `BEGIN` and `ROLLBACK`. PostgreSQL 18 includes the buffer counts with `ANALYZE` by default; on 17 and earlier, ask for `BUFFERS`.

The "recent orders" query from step 2, with 500 test orders (the plans on this page are trimmed: cost estimates and planning lines removed):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, total_cents, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

```text
Limit  (actual time=0.086..0.088 rows=10 loops=1)
  ->  Sort  (actual time=0.085..0.086 rows=10 loops=1)
        Sort Method: quicksort  Memory: 25kB
        ->  Seq Scan on orders  (actual time=0.025..0.045 rows=10 loops=1)
              Filter: (customer_id = 42)
              Rows Removed by Filter: 490
              Buffers: shared hit=5
Execution Time: 0.398 ms
```

The same query with 2 million orders:

```text
Limit  (actual time=99.932..103.985 rows=20 loops=1)
  Buffers: shared hit=16745
  ->  Gather Merge  (actual time=99.930..103.981 rows=20 loops=1)
        ->  Sort  (actual time=90.911..90.912 rows=13 loops=3)
              Sort Method: quicksort  Memory: 27kB
              ->  Parallel Seq Scan on orders  (actual time=4.678..90.781 rows=17 loops=3)
                    Filter: (customer_id = 42)
                    Rows Removed by Filter: 666817
                    Buffers: shared hit=16671
Execution Time: 104.103 ms
```

Same kind of plan, about 260 times slower: to return 20 rows, three processes (the leader and two parallel workers) read all 2 million orders and each threw away 666,817 of them. What to look for in your own plan:

- **`Seq Scan` with a large `Rows Removed by Filter`** next to few returned rows: the filter column needs an index.
- **Estimated `rows=` far from `actual ... rows=`** (shown in the cost part of each line): the statistics are stale or the data is skewed. Run `ANALYZE` on the table and compare.
- **`Sort Method: external merge  Disk: ...`**: the sort ran out of `work_mem` and wrote to disk. Sorting all 2 million orders by total wrote 43,144 kB to disk and took 1.9 seconds in the test.
- **`Buffers: ... read=`** much larger than `hit=`: the blocks came from outside PostgreSQL's buffer cache, often from disk, which grows once the data stops fitting in memory.
- **A `Nested Loop` whose inner side shows a high `loops=` count**: the inner lookup runs once per outer row, so an index on the join column matters.

### 4. Fix what the plan shows

**Add the index the query needs.** Index the filter column first and the sort column after it, so PostgreSQL can read the newest 20 orders for a customer straight from the index:

```sql
CREATE INDEX CONCURRENTLY orders_customer_id_created_at_idx
  ON orders (customer_id, created_at DESC);
```

The same query after the index:

```text
Limit  (actual time=0.253..0.292 rows=20 loops=1)
  Buffers: shared hit=18 read=3
  ->  Index Scan using orders_customer_id_created_at_idx on orders  (actual time=0.252..0.289 rows=20 loops=1)
        Index Cond: (customer_id = 42)
Execution Time: 0.362 ms
```

From 104 ms to 0.36 ms, and from 16,745 blocks to 21. [`CREATE INDEX CONCURRENTLY`](https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY) doesn't block writes while it builds, but it can't run inside a transaction, so check how your migration tool wraps statements; the [production migrations guide](/postgres/production-database-migrations) covers that. If an ORM manages your schema, declare the index there too, so the schema and the database agree: `@@index([customerId, createdAt(sort: Desc)])` in a [Prisma schema](/docs/orm/v7/prisma-schema/data-model/indexes), or [`index("...").on(...)`](https://orm.drizzle.team/docs/indexes-constraints#indexes) in a Drizzle table.

To list foreign keys whose first column has no index starting with it, run:

```sql
SELECT c.conrelid::regclass AS table_name,
       a.attname AS column_name,
       c.conname AS constraint_name
FROM pg_constraint c
JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = c.conkey[1]
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = c.conrelid AND i.indkey[0] = c.conkey[1]
  );
```

Not every foreign key needs an index. Add one where the app filters or joins on that column, or deletes rows from the table it references.

**Refresh statistics after big imports.** The autovacuum daemon [runs `ANALYZE`](https://www.postgresql.org/docs/current/routine-vacuuming.html#VACUUM-FOR-STATISTICS) once a table has changed enough, but not always before the first slow query after a bulk load. Check when each table was last analyzed, and run `ANALYZE orders;` after an import:

```sql
SELECT relname, n_live_tup, n_dead_tup, seq_scan, idx_scan, last_analyze, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_live_tup DESC
LIMIT 10;
```

A large table with a high `seq_scan` count is a good place to look for a missing index.

**Page with a cursor instead of a growing OFFSET.** Even with an index on `(created_at DESC, id DESC)`, `OFFSET 100000 LIMIT 20` read 100,020 index entries and took 18 ms in the test. Asking for the rows after the last one shown (keyset or cursor pagination) read 20 and took 0.42 ms:

```sql
SELECT id, total_cents, created_at
FROM orders
WHERE (created_at, id) < ($1, $2)  -- created_at and id of the last row on the previous page
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Prisma ORM does the same with [cursor-based pagination](/docs/orm/v7/prisma-client/queries/pagination#cursor-based-pagination).

**Return less.** Add a `LIMIT` to list queries, select the columns the page shows instead of `SELECT *`, and filter in SQL instead of in app code.

### 5. If the SQL is fast, look outside the database

**N+1 queries.** In the test, loading 200 orders and then each order's customer with its own query took 7,429 ms from the laptop. The database spent 7 ms on those 200 lookups; the rest was 200 round trips of about 34 ms each. One query with a join returned the same data in 39 ms:

```sql
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
ORDER BY o.id
LIMIT 200;
```

In Prisma ORM, load the relation in the same call with `include` or `select`, or fetch all related rows with one `in` query; the [query optimization guide](/docs/orm/v7/prisma-client/queries/advanced/query-optimization-performance#solving-the-n1-problem) shows each. In Drizzle, use a join, or a relational query with `with`, which Drizzle [sends as a single SQL statement](https://orm.drizzle.team/docs/rqb).

**Waiting for a connection.** If `pool.waitingCount` or the `pg-pool.connect` span grows under load, requests are spending their time queued for a connection. Shorten transactions, release clients, and size the pool for the number of app instances; the [too many connections guide](/postgres/too-many-connections) walks through it.

**Distance between the app and the database.** Every query pays the round trip, so a page with 20 sequential queries pays it 20 times. Put the app in the same region as the database and [measure from the deployed app](/postgres/nodejs-database-regions), not from your laptop.

**Lock waits.** A query that waits for a lock held by another transaction looks slow even though it does no work. Look at what is running and what blocks it:

```sql
SELECT pid, state, wait_event_type, wait_event,
       now() - query_start AS running_for,
       pg_blocking_pids(pid) AS blocked_by,
       left(query, 80) AS query
FROM pg_stat_activity
WHERE state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY running_for DESC;
```

A `wait_event_type` of `Lock` with a non-empty [`blocked_by`](https://www.postgresql.org/docs/current/functions-info.html#FUNCTIONS-INFO-SESSION) list means another session holds the lock, often a long transaction or a migration. Rows in `idle in transaction` hold their locks until they commit or roll back.

**The database itself is short of resources.** If the plans are good and the SQL is still slow under load, check your provider's CPU, memory and disk metrics during the slow period. That is the point where a larger instance or plan helps.

## When does this check mislead?

- **You tested with a typical customer.** One large customer can get a different plan. Run `EXPLAIN (ANALYZE, BUFFERS)` with that customer's ID.
- **Only the first request after a quiet period is slow.** That is usually cache warm-up, connection setup or an app instance starting, not the query. Compare the first and the second request.
- **Your host doesn't offer `pg_stat_statements`.** Use its query performance view instead; the [managed Postgres query monitoring guide](/postgres/managed-postgres-query-monitoring) compares a few.

## Where does Prisma Postgres fit?

[Prisma Postgres](/docs/postgres) is managed PostgreSQL 17, and the SQL in steps 2 to 5 works on it as written: all the plans and `pg_stat_statements` output on this page come from a Prisma Postgres database. `pg_stat_statements` is in its list of [supported extensions](/docs/postgres/database/postgres-extensions), and `CREATE EXTENSION` enables it. Your app keeps its Postgres client, whether that is `pg`, Drizzle, Kysely or Prisma ORM; Prisma ORM is optional.

[Query Insights](/docs/query-insights) is included on every plan, Free included, at no extra cost. It lists each query shape with its latency, executions and reads, shows the full SQL, and adds an AI-generated analysis of whether and how to optimize it, with a suggested change you can copy into your editor. It is read-only: it doesn't rewrite queries or change your schema. With Prisma ORM, the `@prisma/sqlcommenter-query-insights` package maps each SQL statement back to the Prisma call that sent it.

Prisma Postgres bills per operation, and [query duration doesn't change the price](/docs/postgres/faq#does-query-execution-time-affect-pricing-in-prisma-postgres): a 100 ms scan costs the same as a 0.4 ms index lookup. Query count does, so the N+1 pattern in step 5 costs 201 operations where the join costs one. If you also host the app, [Prisma Compute](/docs/compute) runs TypeScript apps in the same Prisma project and the same six regions as the database.

Know the limits before you rely on it:

- The docs describe Query Insights as designed mainly for development and debugging, and the ORM attribution package adds a small overhead to every query. For long retention, alerts or tracing across several services, use an APM or observability tool alongside it.
- The docs don't describe access to the server log, so use `pg_stat_statements` and Query Insights instead of `log_min_duration_statement` or `auto_explain`.
- Queries through the pooled connection are stopped after 10 minutes. Run long reports or index builds over the direct connection.
- If your database runs on another host, you don't need to move it to follow this guide; use that host's query view and the same SQL.
