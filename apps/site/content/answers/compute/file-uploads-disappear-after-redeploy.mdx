If customer uploads were there yesterday and are missing after a deploy, your app is almost certainly writing them to the server's local disk. On most hosting platforms that disk belongs to one running copy of your build, and the next deploy replaces it with a new one.

We make Prisma Compute and Prisma Postgres. Every host behavior on this page links to that host's documentation, checked on October 19, 2026. The fix works for any Node.js app, whichever framework, host or database client you use.

## Why uploaded files disappear

A deploy builds your code into an image, starts new instances from it and stops the old ones. Each new instance starts with the files from the build and nothing else, so a file your app saved at runtime, for example with multer's `diskStorage` or `fs.writeFile("./uploads/...")`, is not in it.

Hosts document this in their own words:

| Host | What happens to files your app writes at runtime |
| --- | --- |
| Fly.io | A Machine's root filesystem is ephemeral, meant for data that can be rebuilt on deploys and restarts. A Fly Volume keeps files, attached to one Machine. [Docs](https://docs.fly.io/volumes/overview) |
| Heroku | Each dyno gets a fresh copy of the latest deploy, and files it writes are discarded when it stops or restarts. Dynos restart daily. [Docs](https://devcenter.heroku.com/articles/dynos#ephemeral-filesystem), [S3 guide](https://devcenter.heroku.com/articles/s3) |
| Prisma Compute | No persistent filesystem. Files you keep go to an Object Store bucket or the database. [Docs](/docs/compute/limitations#runtime), [FAQ](/docs/compute/faq) |
| Railway | Files persist inside a mounted volume, one volume per service. Data written to the volume path at build time is not kept. [Docs](https://docs.railway.com/volumes/reference), [guide](https://docs.railway.com/volumes) |
| Render | Changes to a service's local files are lost on every redeploy or restart, unless they are on a persistent disk. [Docs](https://render.com/docs/disks) |
| Vercel | Functions have a read-only filesystem with a writable `/tmp` of up to 500 MB, for scratch space only. [Docs](https://vercel.com/docs/functions/runtimes#file-system-support) |

Two related symptoms have the same cause. If you run more than one instance, an upload saved by one instance is missing when a request lands on another. And if uploads work on your laptop but not after deploying, that is because your laptop keeps the same disk between runs and a deployed instance doesn't.

## Fix: move uploads to object storage

Object storage keeps files outside your app's instances, so deploys, restarts and extra instances no longer affect them. Use any S3-compatible service: [AWS S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html), [Cloudflare R2](https://developers.cloudflare.com/r2/api/s3/api/), [Railway Buckets](https://docs.railway.com/storage-buckets), a [Prisma Object Store bucket](/docs/storage), or the one your host recommends. Your database then keeps one row per file, so the app can list a customer's files, check who owns a file and find it in the bucket.

### 1. Create a bucket and an access key

Create a private bucket with your provider and an access key that can read and write it. Save four values as environment variables on your host, never in Git: `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`. Leave `S3_ENDPOINT` unset for AWS S3, and set `S3_REGION` to the region your provider's documentation gives for its S3 API (on AWS S3, the bucket's region).

### 2. Add a table for file references

The bucket holds the bytes. Postgres holds what your app needs to know about them:

```sql
CREATE TABLE uploads (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id text NOT NULL,
  object_key text NOT NULL UNIQUE,
  filename text NOT NULL,
  content_type text NOT NULL,
  size_bytes bigint NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

Store the object key, not a full URL. A key keeps working when you move the files to another provider or switch from public to presigned links, and a stored URL doesn't.

### 3. Write uploads to the bucket instead of the disk

Install the packages the example uses:

```sh
npm install express multer pg @aws-sdk/client-s3 @aws-sdk/s3-request-presigner
```

This Express example keeps the upload in memory with multer, writes it to the bucket, records it in Postgres and serves it back through a presigned URL. It uses ES modules, so save it as `server.mjs` or set `"type": "module"` in `package.json`. Replace the `ownerId` lines with your own authentication.

```js
import express from "express";
import multer from "multer";
import pg from "pg";
import { randomUUID } from "node:crypto";
import { S3Client, PutObjectCommand, GetObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({
  region: process.env.S3_REGION ?? "us-east-1",
  endpoint: process.env.S3_ENDPOINT, // unset for AWS S3
  credentials: {
    accessKeyId: process.env.S3_ACCESS_KEY_ID,
    secretAccessKey: process.env.S3_SECRET_ACCESS_KEY,
  },
});
const bucket = process.env.S3_BUCKET;
const db = new pg.Pool({ connectionString: process.env.DATABASE_URL });

// Memory storage instead of diskStorage, with a size limit.
const upload = multer({ storage: multer.memoryStorage(), limits: { fileSize: 10 * 1024 * 1024 } });

const app = express();

app.post("/files", upload.single("file"), async (req, res) => {
  if (!req.file) return res.status(400).send("No file uploaded");
  const ownerId = "customer-123"; // replace with the signed-in customer's id

  const key = `uploads/${ownerId}/${randomUUID()}`;
  await s3.send(
    new PutObjectCommand({
      Bucket: bucket,
      Key: key,
      Body: req.file.buffer,
      ContentType: req.file.mimetype,
    }),
  );

  const { rows } = await db.query(
    `INSERT INTO uploads (owner_id, object_key, filename, content_type, size_bytes)
     VALUES ($1, $2, $3, $4, $5) RETURNING id`,
    [ownerId, key, req.file.originalname, req.file.mimetype, req.file.size],
  );
  res.status(201).json({ id: rows[0].id });
});

app.get("/files/:id", async (req, res) => {
  if (!/^\d+$/.test(req.params.id)) return res.sendStatus(404);
  const ownerId = "customer-123"; // replace with the signed-in customer's id
  const { rows } = await db.query(
    "SELECT object_key FROM uploads WHERE id = $1 AND owner_id = $2",
    [req.params.id, ownerId],
  );
  if (rows.length === 0) return res.sendStatus(404);

  // A short-lived link the browser can use without storage credentials.
  const url = await getSignedUrl(
    s3,
    new GetObjectCommand({ Bucket: bucket, Key: rows[0].object_key }),
    { expiresIn: 300 },
  );
  res.redirect(302, url);
});

app.listen(process.env.PORT ?? 3000);
```

Generate the key yourself instead of using the customer's file name, so two files called `invoice.pdf` don't overwrite each other and nobody can write outside their own prefix. If your provider's documentation asks for path-style URLs, add `forcePathStyle: true` to the client options. If it rejects the checksum headers that recent AWS SDK versions send by default, add `requestChecksumCalculation: "WHEN_REQUIRED"`.

For large files such as videos, you can skip the app server: your app creates a presigned PUT URL and the browser uploads straight to the bucket. [AWS documents this flow](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.html), and other S3-compatible services support it to different degrees, so check yours.

### 4. Copy the files that are still on disk

Files written since the last deploy or restart exist only on the running instance. Before you deploy the fix, copy them into the bucket if your host gives you a shell on that instance or a volume to read from, then insert a row for each one. Run an S3 tool or a short script on that instance, not on a fresh one: on Heroku, for example, `heroku run` starts a new one-off dyno that doesn't have the web dyno's files. With the AWS CLI installed there and the bucket's key set as `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`:

```sh
aws s3 cp ./uploads "s3://$S3_BUCKET/uploads/" --recursive --endpoint-url "$S3_ENDPOINT"
```

Leave out `--endpoint-url` for AWS S3.

### 5. Deploy and check that files survive

Deploy, upload a test file, deploy again without changes, and open the file. If it still loads, uploads now live outside the instance. Search your code for any other runtime writes to local paths, such as generated PDFs or exported CSVs, and move them the same way.

For generated files, the [customer-report hosting guide](/compute/customer-report-hosting) connects private downloads with customer-scoped queries, report status and a durable generation workflow.

## Storing uploads with Prisma Compute and Prisma Postgres

[Prisma Compute](/docs/compute) has no persistent filesystem, so the local `uploads/` folder from the start of this page doesn't work there either. Its storage option is an Object Store bucket: S3-compatible storage that lives in the same Prisma project as your [Prisma Postgres](/docs/postgres) database, managed from the Console, the CLI or the REST API.

To run the Express example above on Compute, deploy it as a [Prisma Composer](/docs/composer) service, which is how apps deploy to Compute. Declare the service with `compute()` and two dependencies from `@prisma/composer-prisma-cloud`, `store: bucket()` and `db: rawPostgres()`, then provision both in your `module.ts`:

```ts
const store = provision(bucket({ name: "uploads" }));
const database = provision(rawPostgres({ name: "database" }));
provision(uploadsService, { deps: { store, db: database } });
```

Provisioning the bucket also mints its access key, so there are no storage credentials to copy. The server code changes in three places, following [porting an app](/docs/composer/porting-an-app) and [object storage in Composer](/docs/composer/object-storage):

```ts
import service from "./service.ts";

const { store, db: database } = service.load();

// 1. The S3 client takes the bucket's endpoint and key from the dependency.
const s3 = new S3Client({
  region: "auto", // ignored by S3-compatible endpoints, but the SDK requires one
  endpoint: store.url,
  credentials: { accessKeyId: store.accessKeyId, secretAccessKey: store.secretAccessKey },
});
const bucket = store.bucket;

// 2. The pg Pool takes the database URL from the dependency.
const db = new pg.Pool({ connectionString: database.url });

// ...the multer setup and routes stay as they are...

// 3. The port comes from the service, bound to all interfaces.
app.listen(service.port(), "0.0.0.0");
```

Your build has to produce a self-contained entry file, and `npx prisma dev module.ts` runs the app locally against a stand-in bucket and database; [porting an app](/docs/composer/porting-an-app) covers the build and the `service.ts` declaration. The `uploads` table goes in the provisioned Prisma Postgres database. To keep an existing Postgres database instead, pass its connection string as a secret [service input](/docs/composer/service-input) rather than declaring `rawPostgres()`. Prisma ORM is optional either way: the example uses the `pg` driver.

The [object storage guide](/docs/compute/object-storage) shows the other route: create the bucket and a key yourself, store the four values as environment variables, and read them with Bun's built-in S3 client (`Bun.s3`), which picks up these names without configuration:

```sh
npx prisma bucket create --name uploads
npx prisma bucket key create <bucket-id>
npx prisma project env add S3_ENDPOINT=<endpoint> --role production
npx prisma project env add S3_BUCKET=<bucketName> --role production
npx prisma project env add S3_ACCESS_KEY_ID=<accessKeyId> --role production
npx prisma project env add S3_SECRET_ACCESS_KEY=<secretAccessKey> --role production
```

`bucket key create` mints a `read_write` key unless you pass `--role read`. Its secret is shown once, so copy it right away. A deployment that only serves files can hold a `read` key, but a write with a `read` key fails with `AccessDenied`. Values resolve at deploy time, so set them before you deploy.

Things to know before you rely on it:

- **Object Store pricing and plan limits are not published yet.** The Free plan's 2 GB is Prisma Postgres database storage, which holds the `uploads` table, not the files; [pricing](/pricing) has the other plans.
- **Deleting a bucket deletes its files and keys in one step**, even when it isn't empty, and can't be undone.
- **Requests have 60 seconds to start responding.** An upload that passes through your app has to finish arriving before your handler can respond, so it has to fit in that window; see [request timeout](/docs/compute/request-timeout).

## How to prevent it, and when the fix doesn't apply

Treat every instance's disk as temporary from the start. Write uploads, generated files and anything else customers expect to find again to object storage or the database, and keep local disk for scratch files that a single request creates and deletes. A test that deploys twice and checks an uploaded file between deploys catches a regression before customers do.

Object storage is the wrong fit when your app or a tool it depends on needs a real filesystem that persists: a SQLite database file, a CMS that writes its media folder to disk, or software that expects POSIX file locking. Use a host with persistent disks or volumes for those, accept that the app runs as a single instance, and back the disk up. Prisma Compute doesn't offer persistent disks, so it is the wrong host for that kind of app. [Moving SQLite data to Postgres](/postgres/app-data-lost-after-restart) solves the database part of the problem, because the data then lives outside the instance.
