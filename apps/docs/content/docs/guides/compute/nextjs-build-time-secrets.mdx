`next build` imports your route modules and prerenders your static pages, so any code that needs a secret at import time, or a database during prerendering, runs during the build. On [Prisma Compute](/compute) the build runs in your GitHub Actions workflow or on your machine, and the variables you set with `prisma project env add` exist only in the running deployment. A build that worked on a platform that injects every variable into the build therefore stops with an error such as `Invalid environment: missing DATABASE_URL`.

This guide shows which values exist in each phase, and three code changes that let the app build without any runtime secret. Every example was run with Next.js 16.4.6 and deployed to Compute from GitHub Actions with a build that had no secrets.

The examples use the `dynamic` and `revalidate` route segment options. Next.js rejects both when `cacheComponents` is enabled in `next.config.ts`, which new `create-next-app` projects do, with `Route segment config "dynamic" is not compatible with nextConfig.cacheComponents`. The examples were tested with that option off.

## Which values exist at build time and at runtime

| Where you set the value | During `next build` | In the running app |
| --- | --- | --- |
| A project variable, set with `prisma project env add` | No | Yes, in `process.env` |
| `env:` on the workflow step that builds, or your shell | Yes | No |
| A `.env` file next to the app | Yes | Yes, because Next.js copies it into the build output |
| A `NEXT_PUBLIC_` variable | Yes, and its value is written into the client bundle | Fixed at build |

Three consequences follow from the table. A server-side secret that only request handlers use belongs in a project variable, and the build must not need it. A `NEXT_PUBLIC_` value must be present when the build runs, because changing it in the project afterwards does not change the bundle that was already built. And a deploy from your machine ships your local `.env` file with the app, because the standalone output of Next.js includes it, so keep production secrets out of that file and let the deploy workflow build from a clean checkout.

[Environment variables](/compute/environment-variables#build-time-and-runtime) describes the same split for every framework.

## 1. Skip environment validation during the build

A module that validates `process.env` when it is imported fails as soon as Next.js collects page data:

```text no-copy
Error: Failed to collect configuration for /api/checkout
  [cause]: Error: Invalid environment: missing DATABASE_URL, PAYMENT_SECRET_KEY
> Build error occurred
Error: Failed to collect page data for /api/checkout
```

Keep the validation for the running app and skip it for the build, with a variable that only the build sets:

```typescript title="lib/env.ts"
const names = ["DATABASE_URL", "PAYMENT_SECRET_KEY"] as const;

function validate() {
  const missing = names.filter((name) => !process.env[name]);
  if (missing.length > 0 && !process.env.SKIP_ENV_VALIDATION) {
    throw new Error(`Invalid environment: missing ${missing.join(", ")}`);
  }
  return Object.fromEntries(
    names.map((name) => [name, process.env[name] ?? ""]),
  ) as Record<(typeof names)[number], string>;
}

export const env = validate();
```

Libraries that validate the environment have the same switch. With [T3 Env](https://env.t3.gg/docs/customization#skipping-validation), pass `skipValidation: !!process.env.SKIP_ENV_VALIDATION` to `createEnv`.

Set the variable on the step that runs the build, and nowhere else, so that the running app still validates:

```yaml title=".github/workflows/prisma-deploy.yml (excerpt)"
      - uses: prisma/cloud-deploy-action@v1
        env:
          SKIP_ENV_VALIDATION: "1"
        with:
          build-command: npm run build
```

The action passes its step's environment to your build command. On your machine, run `SKIP_ENV_VALIDATION=1 npm run build`.

## 2. Create SDK clients on first use

With validation skipped, the next failure comes from a client that is constructed at import time with a key that is now empty:

```text no-copy
Error: Failed to collect configuration for /api/checkout
  [cause]: Error: PaymentClient: a secret key is required
```

Export a function that creates the client the first time a request needs it. Importing the file then needs no secret, and the running app still creates one client and reuses it. In the example, `payment-sdk` and `PaymentClient` are placeholders for any SDK whose constructor checks its key, such as a payment, email or storage client:

```typescript title="lib/payments.ts"
import { PaymentClient } from "payment-sdk";
import { env } from "./env";

let client: PaymentClient | undefined;

export function payments() {
  client ??= new PaymentClient(env.PAYMENT_SECRET_KEY);
  return client;
}
```

```typescript title="app/api/checkout/route.ts"
import { payments } from "@/lib/payments";

export async function POST() {
  const session = await payments().createSession();
  return Response.json(session);
}
```

A database client needs the same change only if its constructor checks the connection string. In Prisma ORM 6, `new PrismaClient()` does not: it reads `DATABASE_URL` and connects on the first query.

## 3. Decide what a prerendered page does without a database

A page that Next.js prerenders runs its queries during the build. Without a database the build stops there. The output includes these lines:

```text no-copy
Error occurred prerendering page "/".
Error [PrismaClientInitializationError]:
error: Environment variable not found: DATABASE_URL.
Export encountered an error on /page: /, exiting the build.
```

Choose one of three answers for each such page.

**Render it for each request.** Add `export const dynamic = "force-dynamic"` to the page. The build no longer runs its queries, and every request reads current data. This is the right choice for pages that are personal or change often.

**Prerender a fallback and let revalidation fill it in.** Keep `revalidate`, and return a fallback only while the build runs and has no database. Check the build phase explicitly instead of catching every error, so that a failing query in the running app still surfaces:

```tsx title="app/page.tsx"
import { PHASE_PRODUCTION_BUILD } from "next/constants";
import { prisma } from "@/lib/prisma";

export const revalidate = 60;

async function getProducts() {
  if (process.env.NEXT_PHASE === PHASE_PRODUCTION_BUILD && !process.env.DATABASE_URL) {
    return [];
  }
  return prisma.product.findMany({ orderBy: { id: "asc" } });
}

export default async function Home() {
  const products = await getProducts();
  return (
    <ul>
      {products.map((product) => (
        <li key={product.id}>{product.name}</li>
      ))}
    </ul>
  );
}
```

The build prerenders the page with an empty list. On Compute, the first request to a new deployment runs the query against the database from the project's `DATABASE_URL` and replaces the page, which is then cached for the `revalidate` period. In testing, that first response already contained the database rows.

**Give the build a database.** If the page must be complete from the first request, pass the build a connection string as a GitHub Actions secret on the same `env:` block as `SKIP_ENV_VALIDATION`. Use a read-only user where you can, and remember that the page then shows the data of that database, whichever environment the build deploys to.

## Check the result

Build with the secrets removed from your shell and with any `.env` file moved aside, the way a clean checkout in CI builds:

```bash
env -u DATABASE_URL -u PAYMENT_SECRET_KEY SKIP_ENV_VALIDATION=1 npm run build
```

**Expected result:** the build finishes and lists the prerendered route with its revalidation period and the request handlers as dynamic.

```text no-copy
Route (app)        Revalidate  Expire
┌ ○ /                      1m      1y
├ ○ /_not-found
├ ƒ /api/checkout
└ ƒ /api/health
```

Then set the runtime values on the project, for production and for previews, and deploy. `read -rs` asks for the value without showing it, and given only the variable's name, `project env add` reads the value from your environment:

```bash
read -rs PAYMENT_SECRET_KEY && export PAYMENT_SECRET_KEY # type the value, then press Enter
npx prisma project env add PAYMENT_SECRET_KEY --role production
npx prisma project env add PAYMENT_SECRET_KEY --role preview
unset PAYMENT_SECRET_KEY
```

Values are read at deploy time, so a variable you add or change applies from the next deploy. If the running app reports `Invalid environment: missing PAYMENT_SECRET_KEY`, the variable is not set for that scope, or the app was deployed before you set it.
