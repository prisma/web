## Introduction

This guide shows you how to use Prisma ORM in a NestJS API. You scaffold a project with a users controller backed by Prisma ORM, initialize the schema, query it over HTTP, and deploy the API to [Prisma Compute](/compute).

Every command below was run end to end against a live [Prisma Postgres](/postgres) database.

## Prerequisites

- [Node.js](https://nodejs.org) 22.18 or newer on the 22 line, 24.11 or newer on the 24 line, or 26 or newer (24 recommended)
- A PostgreSQL connection string, or nothing at all: `npx create-db@latest` can create a Prisma Postgres database for you

To use MongoDB instead of PostgreSQL, scaffold with `--provider mongo` and follow [Create a new app with MongoDB](/prisma-orm/quickstart/mongodb) for the database steps. A deploy does not create a MongoDB database for you: it reads your connection string from the `MONGODB_URL` environment variable.

## 1. Scaffold and enter the project

```npm
npm create prisma@latest -- my-nest-api --template nest --provider postgres --no-deploy
cd my-nest-api
```

Answer the prompts for contract authoring style, package manager, and agent skills. The scaffold generates the NestJS app with Prisma ORM wired in, installs dependencies, and emits the contract your queries are type-checked against.

Next, set the database connection for the local steps. Use your own PostgreSQL connection string, or create a Prisma Postgres database with `npx create-db@latest`, which prints a connection string and a claim URL. Claim the database with a free Prisma account if you want to keep it. Export the variable in the shell you work in; the generated scripts read the environment variable, not `.env`:

```bash
export DATABASE_URL="<your connection string>"
```

## 2. Initialize the database

```npm
npm run db:init
```

```text no-copy
✔ Applied 5 operation(s) across 1 contract space

App space
├─ Create table "Post"
├─ Create table "User"
├─ Add unique constraint on "User" (email)
├─ Create index "Post_authorId_idx_e47547ed" on "Post"
├─ Add foreign key "Post_authorId_fkey" on "Post"
└─ marker 920a87b50729a867e21706dd0fa5c3739e273a84ed89eb2f3525633b2d6ef85c
```

If `db:init` stops with `Connection terminated unexpectedly`, a database you just created is still starting; wait a few seconds and run it again. The command is safe to repeat: when there is nothing left to do, it prints `✔ Database already matches contract across 1 contract space`.

`db:init` applies your schema (`src/prisma/contract.prisma`) to the database and signs it. With TypeScript authoring (`--authoring typescript`) the schema is `src/prisma/contract.ts` and the emitted files land in `src/prisma/generated/`. Sample users are seeded automatically the first time the app queries the database.

## 3. Run and verify

```npm
npm run dev
```

The server starts on port 3000 (set `PORT` to change it). Query the API:

```bash
curl http://localhost:3000/users
```

```json no-copy
[
  { "id": "1", "email": "alice@prisma.io", "username": "alice", "name": "Alice", "createdAt": "2026-07-24T10:55:54.156Z" },
  { "id": "2", "email": "bob@prisma.io", "username": "bob", "name": "Bob", "createdAt": "2026-07-24T10:55:54.192Z" },
  { "id": "3", "email": "carol@prisma.io", "username": "carol", "name": "Carol", "createdAt": "2026-07-24T10:55:54.228Z" }

```
To run the app the way Prisma Compute runs it, with no `DATABASE_URL` to set, run `npm run dev:composer` instead. It builds the app, starts a local Prisma Postgres database, applies the committed migrations to it, and prints the app's local URL.

## Where things live

- `src/users.controller.ts`: the `GET /users` route
- `src/users.service.ts`: the service the controller calls
- `src/prisma.service.ts`: the injectable that exposes the Prisma ORM client and query helpers
- `src/prisma/users.ts`: the `listUsers` query the service runs
- `src/prisma/db.ts`: the Prisma ORM client itself

On PostgreSQL, you reach a model through the database schema it is in: `db.orm.public.User` is the `User` model in the `public` schema. The [Prisma ORM overview](/orm) explains the contract that defines your models.

## 4. Deploy to Prisma Compute

NestJS is supported on [Prisma Compute](/compute). The scaffold declares the app for [Prisma Composer](/composer) in `module.ts` and `service.ts`, so deploying is building and handing that declaration to the CLI. Sign in once (it opens a browser):

```npm
npx prisma auth login
```

Then build and deploy from the project directory:

```npm
npm run build
npx prisma deploy
```

```text no-copy
my-nest-api
├─ database   postgres-database db_abc123
└─ app        compute-service cps_abc123
              https://xyz.ewr.prisma.build
```

The deploy creates a project named after your module in your workspace, and re-running the deploy reuses it: the CLI finds the hosted state it stored on the first run and converges the project to your module. If a project with that name exists but the CLI cannot identify or verify its stored state (one left behind by a different checkout, for example), the deploy stops with `HostedStateBootstrapError`; deploy under another name with `--name <unique-name>`, or rename the module in `module.ts`. The deploy also provisions its own Prisma Postgres database on the platform, declared in `module.ts`; the `DATABASE_URL` from your local steps is not involved, and the deployed database seeds on the app's first query. Verify the live endpoint returns the seeded users:

```bash
curl https://xyz.ewr.prisma.build/users
```

For previews per Git branch and deploy on push, see [Deploy on push](/compute/deploy-on-push).

## Change the schema

The scaffold also writes a first migration to the `migrations/` directory. A deploy changes the hosted database only by applying the migrations in that directory, so every schema change needs a migration of its own. After you edit `src/prisma/contract.prisma`, for example to add a `bio String?` field to `User`, run:

```npm
npm run contract:emit
npm run migration:plan -- --name add-user-bio
npm run migrate -- --advance-ref db
```

`contract:emit` updates the files your queries are type-checked against. `migration:plan` writes the change as a new migration in `migrations/app/`, and `migrate` applies it to the database in `DATABASE_URL`. If you run the app with `npm run dev:composer` instead, you can skip `migrate`: it applies the new migration to its local database when it starts. The `--advance-ref db` flag updates `migrations/app/refs/db.json`, the file that tells the next `migration:plan` which migration your database is at. Without the flag, the next `migration:plan` starts from the older migration and plans your change a second time. [Generating a migration](/orm/migrations/generating-a-migration) explains the files `migration:plan` writes.

Commit the `migrations/` directory with your change, including `migrations/app/refs/db.json`, then deploy again with `npm run build` and `npx prisma deploy`. The deploy applies the new migration to the hosted database before it starts the new version of your app. If you skip `migration:plan`, the deploy stops with `MIGRATION_PATH_NOT_FOUND`, because no migration in `migrations/` leads to your new schema.

If `migration:plan` stops with `MIGRATION.PLAN_ORIGIN_UNKNOWN` or `MIGRATION.HASH_NOT_IN_GRAPH`, it cannot tell which migration your database is at. That happens when you have not run `db:init` in this checkout, or when you changed the database with `db:update`, which makes the database match the schema without writing a migration. Pass the name of the newest directory in `migrations/app/` that your database already has, such as the first migration's directory: `npm run migration:plan -- --from 20261120T1008_init --name add-user-bio`.

## Common gotchas

:::warning

In a long-running server, don't call `db.close()` in request handlers; the client's connection pool is shared across requests. Close it only on [process shutdown](/orm/reference/transactions-and-runtime#close).

:::

- "Using the prisma-8 skill, add GET /users/:id to the users controller that returns one user or a 404."
- "Expose GET /users/:id/posts using the Post model that ships with the starter contract."
- "Add a POST /users route that creates a user from the request body and returns it with a 201."
