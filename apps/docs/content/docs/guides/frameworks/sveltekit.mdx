## Introduction

This guide shows you how to use Prisma ORM in a SvelteKit app. You scaffold a project where a server load function queries your database, initialize the schema, see your data render, and deploy the app to [Prisma Compute](/compute).

The local steps below were run end to end against a live [Prisma Postgres](/postgres) database.

## Quick start

One command scaffolds the project with Prisma ORM wired in:

```npm
npm create prisma@latest -- my-app --template svelte --provider postgres --no-deploy
```

Answer the prompts, then export `DATABASE_URL` in your shell before running the database scripts. If you do not have a database yet, `npx create-db@latest` prints a Prisma Postgres connection string.

## Prerequisites

- [Node.js](https://nodejs.org) 22.18 or newer on the 22 line, 24.11 or newer on the 24 line, or 26 or newer (24 recommended)
- A PostgreSQL connection string, or nothing at all: `npx create-db@latest` can create a Prisma Postgres database for you

To use MongoDB instead of PostgreSQL, scaffold with `--provider mongo` and follow [Create a new app with MongoDB](/prisma-orm/quickstart/mongodb) for the database steps. A deploy does not create a MongoDB database for you. Export `MONGODB_URL` with your connection string in the shell you deploy from: the first deploy stores it on the project, and the app reads it from there.

## 1. Scaffold and enter the project

```npm
npm create prisma@latest -- my-app --template svelte --provider postgres --no-deploy
cd my-app
```

The scaffold generates the SvelteKit app with Prisma ORM wired in, installs dependencies, and emits the contract your queries are type-checked against.

Next, set the database connection: use your own PostgreSQL connection string, or create a Prisma Postgres database with `npx create-db@latest`, which prints a connection string and a claim URL. Claim the database with a free Prisma account if you want to keep it. Export the variable in the shell you work in, because the generated scripts read the environment variable, not `.env`:

```bash
export DATABASE_URL="<your connection string>"
```

## 2. Initialize the database

```npm
npm run db:init
```

```text no-copy
✔ Applied 5 operation(s) across 1 contract space

App space
├─ Create table "Post"
├─ Create table "User"
├─ Add unique constraint on "User" (email)
├─ Create index "Post_authorId_idx_e47547ed" on "Post"
├─ Add foreign key "Post_authorId_fkey" on "Post"
└─ marker 920a87b50729a867e21706dd0fa5c3739e273a84ed89eb2f3525633b2d6ef85c
```

If `db:init` stops with `Connection terminated unexpectedly`, a database you just created is still starting; wait a few seconds and run it again. The command is safe to repeat: when there is nothing left to do, it prints `✔ Database already matches contract across 1 contract space`.

`db:init` applies your schema (`src/prisma/contract.prisma`) to the database and signs it. With TypeScript authoring (`--authoring typescript`) the schema is `src/prisma/contract.ts` and the emitted files land in `src/prisma/generated/`. Sample users are seeded automatically the first time the app queries the database.

## 3. Run and verify

```npm
npm run dev
```

When you open [http://localhost:5173](http://localhost:5173), the page lists the seeded users, which the `+page.server.ts` load function reads on the server.

## Where things live

- `src/routes/+page.server.ts`: the server `load` function that fetches users
- `src/routes/+page.svelte`: the page that renders them
- `src/prisma/users.ts`: the `listUsers` query helper the load function imports
- `src/prisma/db.ts`: the Prisma ORM client behind that helper

On PostgreSQL, you reach a model through the database schema it is in: `db.orm.public.User` is the `User` model in the `public` schema. The [Prisma ORM overview](/orm) explains the contract that defines your models.

## 4. Deploy to Prisma Compute

The scaffold declares the app for [Prisma Composer](/composer), Prisma's deployment configuration, in `module.ts` and `service.ts`. It also passes SvelteKit's Node adapter (`@sveltejs/adapter-node`) to the `sveltekit()` plugin in `vite.config.ts`. Keep that adapter: `service.ts` runs the `build/index.js` server that the adapter writes. Sign in once (it opens a browser):

```npm
npx prisma auth login
```

Then build and deploy from the project directory:

```npm
npm run build
npx prisma deploy
```

The deploy prints the app's live URL; open it to see the page list the seeded users. The deploy creates a project named after your module in your workspace, and re-running the deploy reuses it. If a project with that name exists but the CLI cannot identify or verify its stored state (one left behind by a different checkout, for example), the deploy stops with `HostedStateBootstrapError`; deploy under another name with `--name <unique-name>`, or rename the module in `module.ts`. The deploy also provisions its own Prisma Postgres database, declared in `module.ts`; the `DATABASE_URL` from your local steps is not involved, and the deployed database seeds on the app's first query.

To run the app locally the way Prisma Compute runs it, with no `DATABASE_URL` to set, run `npm run dev:composer`. It builds the app, starts a local Prisma Postgres database, applies the committed migrations to it, and prints the app's local URL.

## Change the schema

The scaffold also writes a first migration to the `migrations/` directory. A deploy changes the hosted database only by applying the migrations in that directory, so every schema change needs a migration of its own.

`migration:plan` writes each new migration as a step after the migration that `migrations/app/refs/db.json` names. That file is the `db` ref, and `db:init` creates it. If you have not run `db:init` in this checkout, for example because you only use `npm run dev:composer`, point the `db` ref at the first migration once. `ls migrations/app` lists its directory, whose name ends in `_init`:

```npm
npx prisma migration ref set db <your init directory>
```

After you edit `src/prisma/contract.prisma`, for example to add a `bio String?` field to `User`, run:

```npm
npm run contract:emit
npm run migration:plan -- --name add-user-bio
```

`contract:emit` updates the files your queries are type-checked against, and `migration:plan` writes the change as a new migration in `migrations/app/`. Then apply the migration to your local database, and point the `db` ref at it so that your next `migration:plan` starts from this migration. Without the ref step, the next plan would include this change a second time.

If your development database is in `DATABASE_URL`, one command does both:

```npm
npm run migrate -- --advance-ref db
```

If you use `npm run dev:composer`, restart it: it applies new migrations when it starts. It does not update the `db` ref, so once it is running, set the ref yourself to the directory that `migration:plan` printed, such as `migrations/app/20261120T1104_add_user_bio`:

```npm
npx prisma migration ref set db <new migration directory>
```

SvelteKit builds on Vite, so the [Vite plugin](/cli/contract-emit#run-it-automatically) can run `contract:emit` for you each time you save the contract, so while the dev server runs you can skip that command. Import `prismaVitePlugin` and add it to the `plugins` array in `vite.config.ts`:

```ts title="vite.config.ts"
import adapter from "@sveltejs/adapter-node";
import { sveltekit } from "@sveltejs/kit/vite";
import { prismaVitePlugin } from "@prisma/orm-postgres/vite-plugin-contract-emit";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [prismaVitePlugin(), sveltekit({ adapter: adapter() })],
});
```

Commit the `migrations/` directory with your change, including `migrations/app/refs/db.json`, then deploy again with `npm run build` and `npx prisma deploy`. The deploy applies the new migration to the hosted database before it starts the new version of your app. If you skip `migration:plan`, the deploy stops with `MIGRATION_PATH_NOT_FOUND`, because no migration in `migrations/` leads to your new schema.

If you changed your database with `db:update`, which makes the database match the schema without writing a migration, `migration:plan` stops with `MIGRATION.HASH_NOT_IN_GRAPH`. Name the newest directory that `ls migrations/app` lists, then apply the migration as above:

```npm
npm run migration:plan -- --from <your newest migration directory> --name add-user-bio
```
