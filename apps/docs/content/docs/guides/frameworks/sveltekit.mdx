## Introduction

This guide shows you how to use Prisma ORM in a SvelteKit app. You scaffold a project where a server load function queries your database, initialize the schema, see your data render, and deploy the app to [Prisma Compute](/compute).

Every command below was run end to end against a live [Prisma Postgres](/postgres) database.

## Quick start

One command scaffolds the project with Prisma ORM wired in:

```npm
npm create prisma@latest -- my-app --template svelte --provider postgres --no-deploy
```

Answer the prompts, then export `DATABASE_URL` in your shell before running the database scripts. If you do not have a database yet, `npx create-db@latest` prints a Prisma Postgres connection string.

## Prerequisites

- [Node.js](https://nodejs.org) 22.18 or newer on the 22 line, 24.11 or newer on the 24 line, or 26 or newer (24 recommended)
- A PostgreSQL connection string, or nothing at all: `npx create-db@latest` can create a Prisma Postgres database for you

To use MongoDB instead of PostgreSQL, scaffold with `--provider mongo` and follow [Create a new app with MongoDB](/prisma-orm/quickstart/mongodb) for the database steps. Neither `npm run dev:composer` (the local run in step 3) nor a deploy creates a MongoDB database for you, so export `MONGODB_URL` with your connection string before you run either. The deployed app reads `MONGODB_URL` from your project on Prisma Compute, not from your shell, so set it there:

1. Deploy once. The first deploy creates the project, then stops and prints the command that sets the variable.
2. With `MONGODB_URL` exported, run `npx prisma project env add MONGODB_URL --project my-app --role production`. It copies the value from your shell to the project's production environment (see [`prisma project`](/cli/project)).
3. Deploy again.

A preview deploy stops the same way and prints the command with `--role preview`. To change the value later, export the new connection string and run the same command with `env update` in place of `env add`; the app gets the new value on its next deploy. If you renamed the module or deployed with `--name`, pass that name to `--project`.

## 1. Scaffold and enter the project

```npm
npm create prisma@latest -- my-app --template svelte --provider postgres --no-deploy
cd my-app
```

The scaffold generates the SvelteKit app with Prisma ORM wired in, installs dependencies, and emits the contract your queries are type-checked against.

Next, set the database connection for the local steps: use your own PostgreSQL connection string, or create a Prisma Postgres database with `npx create-db@latest`, which prints a connection string and a claim URL. Claim the database with a free Prisma account if you want to keep it. Export the variable in the shell you work in, because the generated scripts read the environment variable, not `.env`:

```bash
export DATABASE_URL="<your connection string>"
```

## 2. Initialize the database

```npm
npm run db:init
```

```text no-copy
✔ Applied 5 operation(s) across 1 contract space

App space
├─ Create table "Post"
├─ Create table "User"
├─ Add unique constraint on "User" (email)
├─ Create index "Post_authorId_idx_e47547ed" on "Post"
├─ Add foreign key "Post_authorId_fkey" on "Post"
└─ marker 920a87b50729a867e21706dd0fa5c3739e273a84ed89eb2f3525633b2d6ef85c
```

If `db:init` stops with `Connection terminated unexpectedly`, a database you just created is still starting; wait a few seconds and run it again. The command is safe to repeat: when there is nothing left to do, it prints `✔ Database already matches contract across 1 contract space`.

`db:init` applies your schema (`src/prisma/contract.prisma`) to the database and signs it. With TypeScript authoring (`--authoring typescript`) the schema is `src/prisma/contract.ts` and the emitted files land in `src/prisma/generated/`. Sample users are seeded automatically the first time the app queries the database.

## 3. Run and verify

```npm
npm run dev
```

When you open [http://localhost:5173](http://localhost:5173), the page lists the seeded users, which the `+page.server.ts` load function reads on the server.

To run the app the way Prisma Compute runs it, with no `DATABASE_URL` to set, run `npm run dev:composer` instead. It builds the app, starts a local Prisma Postgres database, applies the committed migrations to it, and prints the app's local URL.

## Where things live

- `src/routes/+page.server.ts`: the server `load` function that fetches users
- `src/routes/+page.svelte`: the page that renders them
- `src/prisma/users.ts`: the `listUsers` query helper the load function imports
- `src/prisma/db.ts`: the Prisma ORM client behind that helper

On PostgreSQL, you reach a model through the database schema it is in: `db.orm.public.User` is the `User` model in the `public` schema. The [Prisma ORM overview](/orm) explains the contract that defines your models.

## 4. Deploy to Prisma Compute

SvelteKit is supported on [Prisma Compute](/compute), and the scaffold has already set the app up for it. The app builds with `@sveltejs/adapter-node`, which writes a Node.js server to the `build/` directory. `service.ts` and `module.ts`, in the project root, describe that server and its database for [Prisma Composer](/composer), and `npx prisma deploy` reads them. Sign in once (it opens a browser):

```npm
npx prisma auth login
```

Then build and deploy from the project directory:

```npm
npm run build
npx prisma deploy
```

```text no-copy
my-app
├─ database   postgres-database db_abc123
└─ app        compute-service cps_abc123
              https://xyz.ewr.prisma.build
```

The first deploy creates a project in your workspace named after your module, which is the first argument to `module()` in `module.ts` (`my-app` here). The project gets its own Prisma Postgres database, declared in `module.ts`. The deploy does not use the `DATABASE_URL` from your local steps, and the deployed database seeds on the app's first query. Running `npx prisma deploy` again updates that same project.

The deploy finds the project by that name, so a deploy from any app whose module has the same name, such as two apps both scaffolded as `my-app`, goes to that same project. Give each app its own name in `module.ts`. If a project with that name exists but the CLI cannot identify or verify its stored state (one deployed by an older version of Composer, for example), the deploy stops with `HostedStateBootstrapError`: rename the module in `module.ts`, or deploy under another name with `--name <unique-name>` and pass the same `--name` on every later deploy.

Open the URL to verify the live app: the page lists the seeded users. For the first few seconds after the first deploy, the URL can answer `There is no service on this URL`; wait a moment and load it again. To check from the command line, fetch the page and look for the seeded email addresses:

```bash
curl -s https://xyz.ewr.prisma.build | grep -o '[a-z]*@prisma.io' | sort -u
```

```text no-copy
alice@prisma.io
bob@prisma.io
carol@prisma.io
```

For previews per Git branch and deploy on push, see [Deploy on push](/compute/deploy-on-push).

## Change the schema

The scaffold also writes a first migration to the `migrations/` directory. A deploy changes the hosted database only by applying the migrations in that directory, and so does `npm run dev:composer` for its local database, so every schema change needs a migration of its own.

`migration:plan` writes each new migration as a step after the migration that `migrations/app/refs/db.json` names. That file is the `db` ref, and `db:init` creates it. If you have not run `db:init` in this checkout, for example because you only use `npm run dev:composer`, point the `db` ref at the first migration once. Pass the directory name only, without `migrations/app/` in front: `ls migrations/app` lists it, and its name ends in `_init`, such as `20261120T1011_init`. A path such as `migrations/app/20261120T1011_init` fails with `MIGRATION.REF_NOT_FOUND`.

```npm
npx prisma migration ref set db <your init directory>
```

After you edit `src/prisma/contract.prisma`, for example to add a `bio String?` field to `User`, run:

```npm
npm run contract:emit
npm run migration:plan -- --name add-user-bio
```

`contract:emit` updates the files your queries are type-checked against, and `migration:plan` writes the change as a new migration in `migrations/app/`. Then apply the migration to your local database, and point the `db` ref at it so that your next `migration:plan` starts from this migration. Without the ref step, the next plan would include this change a second time.

If your development database is in `DATABASE_URL`, one command does both:

```npm
npm run migrate
```

If you use `npm run dev:composer`, restart it: it applies new migrations when it starts. It does not update the `db` ref, so once it is running, set the ref yourself. Pass the last part of the path that `migration:plan` printed on its `app space:` line: for `migrations/app/20261120T1124_add_user_bio`, that is `npx prisma migration ref set db 20261120T1124_add_user_bio`.

```npm
npx prisma migration ref set db <new migration directory>
```

SvelteKit builds on Vite, so the [Vite plugin](/cli/contract-emit#run-it-automatically) can run `contract:emit` for you each time you save the contract, so while the dev server runs you can skip that command. Import `prismaVitePlugin` and add it to the `plugins` array in `vite.config.ts`:

```ts title="vite.config.ts"
import adapter from "@sveltejs/adapter-node";
import { sveltekit } from "@sveltejs/kit/vite";
import { prismaVitePlugin } from "@prisma/orm-postgres/vite-plugin-contract-emit";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [prismaVitePlugin(), sveltekit({ adapter: adapter() })],
});
```

Commit the `migrations/` directory with your change, including `migrations/app/refs/db.json`, then deploy again with `npm run build` and `npx prisma deploy`. The deploy applies the new migration to the hosted database before it starts the new version of your app. If you skip `migration:plan`, the deploy stops with `MIGRATION_PATH_NOT_FOUND`, because no migration in `migrations/` leads to your new schema.

If you changed your database with `db:update`, which makes the database match the schema without writing a migration, `migration:plan` stops with `MIGRATION.HASH_NOT_IN_GRAPH`. Pass the newest migration with `--from`: it is the first migration name in the graph that `npx prisma migration list` prints, such as `20261120T1124_add_user_bio`. Then apply the migration as above:

```npm
npm run migration:plan -- --from <your newest migration directory> --name add-user-bio
```
