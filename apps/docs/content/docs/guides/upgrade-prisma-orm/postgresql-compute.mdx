This guide takes an Express, Fastify, Hono or other Node.js server that runs Prisma ORM 6 or 7 on PostgreSQL and moves it to Prisma 8 in one pass, then deploys it on [Prisma Compute](/compute). You keep your `schema.prisma`, your database and its data. At the end, Prisma 8 owns your migrations, every query runs through the Prisma 8 client, and a push to GitHub deploys the app with its own Prisma Postgres database.

A Prisma ORM 6 app does not need to upgrade to Prisma ORM 7 first: Prisma 8 reads a Prisma ORM 6 schema as it is. If you want to keep Prisma ORM 7 running beside Prisma 8 and move one route at a time instead, follow [Prisma ORM 7 to 8 (PostgreSQL)](/guides/upgrade-prisma-orm/postgresql). That guide does not cover Prisma Compute.

The examples follow a small feedback board: Express 4, EJS views, Prisma ORM 6.19, compiled with `tsc` and run with `node`. Its models are `Board`, `Post`, `Vote` and `Comment`, with a `PostStatus` enum. Map the names to your own app.

## Two ways to upgrade

Follow the steps below yourself, or have your coding agent follow them with the `prisma-postgres-upgrade` [skill](/ai/tools/skills):

```npm
npx skills add prisma/skills --skill prisma-postgres-upgrade
```

Then ask your agent from the project root:

<AgentPrompt>

```text
Upgrade this app from Prisma ORM 6 to Prisma 8 and set it up to deploy on Prisma Compute.
```

</AgentPrompt>

The agent runs your project's type check, build and tests before and after the upgrade, and stops for what only you can do: connecting the repository in the Console, providing environment variable values, and pushing.

## Prerequisites

- **Node.js 24.11 or newer.** Prisma 8 itself runs on Node.js 22.18 or newer too (see [Supported versions](/orm/supported-versions)), but `prisma dev`, which runs the app locally the way Prisma Compute runs it in step 6, needs Node.js 24.11 or newer. The deploy workflow uses Node.js 24.
- **A working Prisma ORM 6 or 7 app on PostgreSQL**, and a database it has migrated. Start the app and load a page that queries the database before you change anything, so you have something to compare with.
- **TypeScript 5.9 or newer**, with `"strict": true`.
- **The app in a GitHub repository**, with a committed lockfile, and a [Prisma Console](https://console.prisma.io) workspace you can connect it to.

## 1. Install Prisma 8

### 1.1. Replace the Prisma CLI

Remove the Prisma ORM 6 or 7 CLI and install the Prisma 8 CLI and its PostgreSQL runtime at the versions the Console's Compute setup installs:

```npm
npm uninstall prisma
npm install --save-dev --save-exact prisma@8.0.0-rc.27
npm install --save-exact @prisma/orm-postgres@8.0.0-rc.20
```

`prisma` is the Prisma 8 CLI, and `@prisma/orm-postgres` is the PostgreSQL runtime your code imports. The two packages have separate version numbers.

Install these exact versions, not `@latest`. The setup pull request the Console opens in step 6 adds Prisma Composer, the part of Prisma Compute that deploys your app, and keeps whatever `prisma` and `@prisma/orm-postgres` versions your `package.json` already declares. Today the latest pair on npm does not work with the Composer version the setup installs, so a deploy fails. When the Console moves to newer versions, its setup pull request lists the ones it uses; install those instead.

Leave `@prisma/client`, a driver adapter such as `@prisma/adapter-pg`, and the generated client in place for now. Step 7 removes them.

:::note[Your old client after a fresh install]

From here on, `prisma` is the Prisma 8 CLI and nothing regenerates your old client, so this guide rewrites every query in one pass. To move a Prisma ORM 7 app gradually instead, keep its CLI as `prisma7` with `@prisma/prisma7` and follow the [side-by-side guide](/guides/upgrade-prisma-orm/postgresql). Prisma ORM 6 has no equivalent.

The client you already generated keeps working on your machine while you rewrite queries in step 5. A fresh install, such as a CI run or a new clone, has none, and a Prisma ORM 6 app then fails with `@prisma/client did not initialize yet`. Rewrite every query before you push this work to a branch that CI builds.

:::

### 1.2. Remove `prisma generate` from your scripts

The Prisma 8 CLI has no `generate` command. `npx prisma generate` now fails with `CLI.UNKNOWN_COMMAND` and exit code `2`, so any script that runs it, such as `build` or `postinstall`, fails too. Remove it, along with the Prisma ORM 6 or 7 migration and seed scripts. Step 3 sets up the Prisma 8 migration command:

```json title="package.json (excerpt)"
{
  "scripts": {
    "build": "prisma generate && tsc", // [!code --]
    "build": "tsc", // [!code ++]
    "postinstall": "prisma generate", // [!code --]
    "db:migrate": "prisma migrate dev", // [!code --]
    "db:deploy": "prisma migrate deploy", // [!code --]
    "db:seed": "prisma db seed", // [!code --]
    "db:migrate": "prisma db migrate" // [!code ++]
  },
  "prisma": { "seed": "tsx prisma/seed.ts" } // [!code --]
}
```

Prisma 8 has no seed command. To seed, write a script that imports the client from step 5 and calls `.create(...)`, and run it with `tsx`.

**Check:** `npx prisma --version` prints `8.0.0-rc.27`.

## 2. Create the contract from your schema

Prisma 8 describes your models as a [contract](/orm/contract-authoring/the-data-contract). It can read your existing `schema.prisma` as that contract, so you keep editing the file you have.

### 2.1. Write `prisma.config.ts`

Create `prisma.config.ts` in the project root. In a Prisma ORM 7 app, replace the `prisma.config.ts` you have, because Prisma 8 reads only its own config format under that name:

```typescript title="prisma.config.ts"
import "dotenv/config";
import { definePrismaConfig } from "prisma/config";
import { defineConfig, prisma7Schema } from "@prisma/orm-postgres/config";

export default definePrismaConfig({
  orm: defineConfig({
    contract: prisma7Schema("prisma/schema.prisma"),
    output: "src/prisma",
    db: {
      connection: process.env["DATABASE_URL"],
    },
  }),
});
```

`prisma7Schema(...)` reads a Prisma ORM 7 schema, and it reads a Prisma ORM 6 schema unchanged too: the `generator client { provider = "prisma-client-js" }` block and `url = env("DATABASE_URL")` in the datasource stay as they are, and Prisma 8 ignores them. `output: "src/prisma"` writes the emitted contract inside `src/`, where `tsc` compiles it and the Compute setup in step 6 expects it.

[Use a Prisma ORM 7 schema](/cli/configuration#use-a-prisma-orm-7-schema) lists how each date and time type reads, and the parts of a schema Prisma 8 cannot read, such as `view` blocks. If your schema uses PostgreSQL extensions such as `pgvector` or `citext`, that section also shows the packs to add to the config.

If you use a coding agent, install the [agent skills](/cli/skills) that ship inside the Prisma 8 packages, matched to their versions:

```npm
npx prisma skills sync
```

It needs the Prisma 8 `prisma.config.ts`: with a Prisma ORM 7 config still in place, it fails with `CLI.CONFIG_UNREADABLE`. Run it again after step 6, which adds Composer and its skill.

### 2.2. Emit the contract

```npm
npx prisma contract emit
```

**Expected result:** `Emitted contract.json and contract.d.ts`, and the two files in `src/prisma/`. `contract.json` is what the Prisma 8 client and the deploy read at runtime, and `contract.d.ts` holds its types. Commit both, and run `contract emit` again after every change to `schema.prisma`.

If `contract emit` fails, its error names the line in `schema.prisma` and the edit to make.

### 2.3. Sign the existing database

Your database already has every table the contract describes. Record that in the database:

```npm
npx prisma db sign
```

[`db sign`](/cli/db-sign) checks that the tables match the contract, then writes a marker in the database that names the contract it matches. It does not change your tables. It also writes a snapshot of the contract under `migrations/snapshots/` and a ref named `db` in `migrations/app/refs/db.json`, which step 3 plans from.

**Expected result:** the command prints `Database signed` and `Advanced ref "db"`. If you keep using other existing databases, such as a staging database, run `db sign` once against each of them with `DATABASE_URL` pointing at it; a database the Compute deploy creates in step 6 does not need it.

## 3. Hand migrations to Prisma 8

From here on, Prisma 8 plans and applies schema changes, and you stop running `prisma migrate`. Prisma 8 keeps reading `prisma/schema.prisma`, so you go on editing the same file.

### 3.1. Plan the baseline migration

```npm
npx prisma migration plan --name init
```

**Expected result:** `Planned baseline (12 operation(s)) + 0 operation(s)`, with your own number of operations, and a folder `migrations/app/<timestamp>_baseline`. The baseline creates every table, index and foreign key in the contract, so a new, empty database ends up with your schema. Your existing database skips it, because its marker already names that contract:

```npm
npx prisma db migrate
```

**Expected result:** the command prints `(no operations)`, while the Compute deploy runs the same command against the new database it creates and applies the baseline there.

### 3.2. Retire `prisma/migrations`

Prisma 8 does not read the `prisma/migrations` folder, and the baseline already describes the schema those migrations built. Delete the folder, including `migration_lock.toml`:

```bash
rm -r prisma/migrations
```

Keep `prisma/schema.prisma`: it is still your contract. Prisma ORM 6 and 7 recorded applied migrations in a `_prisma_migrations` table, which stays in the database. Prisma 8 leaves it out of `db verify` and `contract infer`, and you can drop it whenever you like.

From now on, a schema change is: edit `prisma/schema.prisma`, then run

```npm
npx prisma contract emit
npx prisma migration plan --name <change>
npx prisma db migrate --advance-ref db
```

`--advance-ref db` points `migrations/app/refs/db.json` at the new contract, so the next `migration plan` starts from it. [How migrations work](/orm/migrations/how-migrations-work) covers the full loop.

## 4. Point TypeScript at the Prisma 8 client

Every Prisma 8 package is published as ES modules, and your code imports the emitted `contract.json`. An app that compiles with `tsc` and runs the output with `node` can stay CommonJS. Set `module` and `moduleResolution` to `nodenext`, and turn on `resolveJsonModule`:

```json title="tsconfig.json (excerpt)"
{
  "compilerOptions": {
    "module": "commonjs", // [!code --]
    "module": "nodenext", // [!code ++]
    "moduleResolution": "nodenext", // [!code ++]
    "resolveJsonModule": true, // [!code ++]
    "outDir": "dist",
    "rootDir": "src",
    "strict": true
  },
  "include": ["src"]
}
```

Keep `package.json` without `"type": "module"`, and your relative imports stay as they are, without extensions. Keep `include` limited to `src` as well, so `tsc` does not compile `prisma.config.ts` into `dist/`. If your app runs through `tsx` or a bundler, or `package.json` has `"type": "module"`, [Set up tsconfig.json](/guides/upgrade-prisma-orm/postgresql#26-set-up-tsconfigjson-for-the-prisma-orm-8-client) gives the settings for each case.

## 5. Rewrite your queries

### 5.1. Create the Prisma 8 client

Replace the file that creates `PrismaClient`. For now the client reads `DATABASE_URL`, so you can run the app against your local database while you rewrite queries. Step 6 changes it for Prisma Compute.

```typescript title="src/db.ts" tab="Prisma 8"
import "dotenv/config";
import postgres from "@prisma/orm-postgres/runtime";
import { contractFromJson } from "@prisma/orm-postgres/static";
import type { Contract } from "./prisma/contract.d";
import contractJson from "./prisma/contract.json";

export const db = postgres({
  contract: contractFromJson<Contract>(contractJson),
  url: process.env["DATABASE_URL"]!,
});
```

```typescript title="src/db.ts" tab="Prisma ORM 6"
import { PrismaClient } from "@prisma/client";

export const prisma = new PrismaClient();
```

```typescript title="src/db.ts" tab="Prisma ORM 7"
import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient } from "../generated/prisma/client";

const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL! });

export const prisma = new PrismaClient({ adapter });
```

In a file that compiles as an ES module, write the JSON import as `import contractJson from "./prisma/contract.json" with { type: "json" };`.

### 5.2. Rewrite each query

A Prisma 8 query starts from `db.orm.public.<Model>`, where `public` is the PostgreSQL schema your tables are in, and chains calls instead of taking one options object. The last call, such as `.all()`, `.first()` or `.create(...)`, says what you get back. The calls in Prisma ORM 6 and 7 are the same, so one rewrite covers both:

```typescript title="src/server.ts (excerpt)" tab="Prisma 8"
import { db } from "./db";

// findMany with a relation count and orderBy
const boards = await db.orm.public.Board.include("posts", (posts) => posts.count())
  .orderBy((b) => b.createdAt.asc())
  .all();
// boards[0].posts is a number

// findMany with where, two counts, and ordering by a relation count
const posts = await db.orm.public.Post.where({ boardId: board.id })
  .include("votes", (votes) => votes.count())
  .include("comments", (comments) => comments.count())
  .orderBy([(p) => p.votes.count().desc(), (p) => p.createdAt.desc()])
  .all();

// findUnique by primary key, with relations
const post = await db.orm.public.Post.whereUnique({ id })
  .include("board")
  .include("comments", (comments) => comments.orderBy((c) => c.createdAt.asc()))
  .include("votes", (votes) => votes.count())
  .first();

// findUnique by a @unique field, and by a compound @@unique
const bySlug = await db.orm.public.Board.where({ slug }).first();
const vote = await db.orm.public.Vote.where({ postId, voterId }).first();

// create with a nested create
const created = await db.orm.public.Post.create({
  boardId: board.id,
  title,
  body,
  author,
  votes: (v) => v.create([{ voterId }]),
});

// deleteMany, returning the number of deleted rows
const deleted = await db.orm.public.Vote.where({ postId, voterId }).deleteAndCount();

// count
const { total } = await db.orm.public.Post.where({ boardId: board.id }).aggregate((agg) => ({
  total: agg.count(),
}));

// $queryRaw
await db.query(db.raw.sql`SELECT 1 AS ok`.returnsRow({ ok: "pg/int4@1" }).build());

// enum values
const STATUSES = db.nativeEnums.public.PostStatus.values;
```

```typescript title="src/server.ts (excerpt)" tab="Prisma ORM 6 and 7"
import { PostStatus } from "@prisma/client";
import { prisma } from "./db";

const boards = await prisma.board.findMany({
  orderBy: { createdAt: "asc" },
  include: { _count: { select: { posts: true } } },
});
// boards[0]._count.posts is a number

const posts = await prisma.post.findMany({
  where: { boardId: board.id },
  include: { _count: { select: { votes: true, comments: true } } },
  orderBy: [{ votes: { _count: "desc" } }, { createdAt: "desc" }],
});

const post = await prisma.post.findUnique({
  where: { id },
  include: {
    board: true,
    comments: { orderBy: { createdAt: "asc" } },
    _count: { select: { votes: true } },
  },
});

const bySlug = await prisma.board.findUnique({ where: { slug } });
const vote = await prisma.vote.findUnique({
  where: { postId_voterId: { postId, voterId } },
});

const created = await prisma.post.create({
  data: { boardId: board.id, title, body, author, votes: { create: { voterId } } },
});

const deleted = (await prisma.vote.deleteMany({ where: { postId, voterId } })).count;

const total = await prisma.post.count({ where: { boardId: board.id } });

await prisma.$queryRaw`SELECT 1`;

const STATUSES = Object.values(PostStatus);
```

Four differences catch most rewrites:

- **A count lands on the relation's own key.** `include("votes", (votes) => votes.count())` puts the number in `post.votes`, where Prisma ORM 6 and 7 put it in `post._count.votes`. Update the views or response code that read `_count`.
- **`whereUnique` takes only the primary key here.** A schema read through `prisma7Schema(...)` keeps each `@unique` and `@@unique` as the unique index Prisma ORM 6 and 7 created, and `whereUnique` accepts only a primary key or a unique constraint. Look rows up by those fields with `.where({ ... }).first()`, which runs the same query.
- **Enums come from the client.** An `enum` in a Prisma ORM 6 or 7 schema is a PostgreSQL enum type, so its values are in `db.nativeEnums.public.<Enum>.values`. Fields of that type still read and write the same strings.
- **At `@prisma/orm-postgres@8.0.0-rc.20`, a `DateTime` field reads as a string**, such as `"2026-11-06 09:10:48.497"`: the stored UTC time, without an offset. Code that calls a `Date` method on it, such as `post.createdAt.toISOString()` in a template, fails. Use the string, or convert it with `new Date(value.replace(" ", "T") + "Z")`. Later releases read the field as a `Date` again, so check this when you upgrade. In the same release, a `@default(now())` field you leave out of `.create(...)` gets its value from the database's `now()`, which for a `timestamp` column is the database's local time. Prisma ORM 6 and 7 sent the UTC time instead, so if `SHOW timezone` on your database prints anything other than `UTC`, new rows are off by that offset.

The [ORM client reference](/orm/reference/orm-client) has every method, and [Coming from Prisma ORM 7](/orm/coming-from-prisma-orm-7#queries) maps the rest of the Prisma ORM 6 and 7 query API, including what has no Prisma 8 form yet, such as `increment` in an update.

### 5.3. Run the app locally

```npm
npm run build
npm start
```

Load the same pages as before you started, and try each write. **Expected result:** the pages show the same data as on Prisma ORM 6 or 7, and `npx tsc --noEmit` passes with no file importing `@prisma/client` or the generated client.

## 6. Deploy on Prisma Compute

On Prisma Compute, the app does not read `DATABASE_URL`. The deploy creates a Prisma Postgres database for each branch, applies `migrations/app/` to it, and hands the app a client connected to it. `DATABASE_URL` is a reserved variable that holds the placeholder `-`, so an app that keeps reading it deploys and then fails every query with `P1001` and `host: "base"`.

### 6.1. Connect the repository in the Console

Commit and push your work, then in the [Console](https://console.prisma.io) create a project and connect the repository to it. [GitHub](/compute/github) describes the connection.

The Console opens a pull request, **Set up Prisma Cloud deploys**, on a branch named `prisma-cloud/setup`. It adds:

- `.github/workflows/prisma-deploy.yml`, which deploys every push: the default branch to production, and every other branch to its own preview.
- `module.mjs`, which declares the app and its Prisma Postgres database for [Prisma Composer](/composer).
- `service.mjs`, which declares your server as a service with `deps: { db: postgres(dataContract(contractJson)) }`, the database it needs.
- A `composer` section in `prisma.config.ts`, and the Composer packages in `package.json`.

Because the workflow runs on every push, the setup branch deploys as a preview. Make the changes below on that branch, and merge the pull request only after its preview works: merging deploys production.

### 6.2. Move the service declaration into your build

A Compute service runs the files your build produces, here `dist/`, and nothing outside them. Your server code imports the service declaration to get its database, so the declaration has to be part of the build. Check out the setup branch, then move `service.mjs` into `src/` as a TypeScript ES module:

```bash
git switch prisma-cloud/setup
git rm service.mjs
```

```typescript title="src/service.mts"
import node from "@prisma/composer/node";
import { compute } from "@prisma/composer-prisma-cloud";
import { postgres, dataContract } from "@prisma/composer-prisma-cloud/orm";
import type { Contract } from "./prisma/contract.js";
import contractJson from "./prisma/contract.json" with { type: "json" };

export default compute({
  name: "feedback-board",
  deps: { db: postgres(dataContract<Contract>(contractJson)) },
  build: node({ module: import.meta.url, dir: ".", entry: "server.js", dependencies: "external" }),
});
```

Keep the `name` the setup wrote. `tsc` compiles this file to `dist/service.mjs`, so `dir: "."` is `dist/` and `entry` is the file in it that starts your server, the one `npm start` runs. Check it: the setup guesses the entry from your repository and can get it wrong. `dependencies: "external"` ships the packages in `node_modules` that the entry imports, because `tsc` does not bundle them. `dataContract<Contract>(...)` gives the client the types from `contract.d.ts`.

In `module.mjs`, import the compiled service instead of the deleted file:

```javascript title="module.mjs"
import feedbackBoardService from "./service.mjs"; // [!code --]
import feedbackBoardService from "./dist/service.mjs"; // [!code ++]
```

The deploy workflow runs `npm run build` before it reads `module.mjs`, so `dist/service.mjs` exists by then.

### 6.3. Take the client from the service

Change `src/db.ts` to use the client Composer connects to the branch's database:

```typescript title="src/db.ts"
import service from "./service.mjs";

export const db = service.load().db.client;
```

`service.load().db` also has `url`, the raw connection string, for a library that needs one. `db.client` has the same type as the client from step 5, so the rest of your code does not change. `src/db.ts` stays CommonJS and loads the ES module through `require`, which Node.js 22.12 and newer support.

Outside a Composer run, `service.load()` throws `missing required config param "url"`. To run the app locally from now on, run it under `prisma dev`, which starts a local Prisma Postgres, applies `migrations/app/` to it, and runs the service the way Compute does:

```npm
npm run build
npx prisma dev module.mjs
```

**Expected result:** `dev: ready` and the service's local URL, such as `feedbackboard: http://localhost:3000`. The local database starts empty.

### 6.4. Ship files the server reads at runtime

Only `dist/` reaches Compute, so if your server reads other files at runtime, such as EJS views in `views/` or static files in `public/`, copy them into `dist/` in the build, and read them from next to the compiled code:

```json title="package.json (excerpt)"
{
  "scripts": {
    "build": "tsc", // [!code --]
    "build": "tsc && cp -R views public dist/" // [!code ++]
  }
}
```

```typescript title="src/server.ts (excerpt)"
app.set("views", path.join(__dirname, "..", "views")); // [!code --]
app.set("views", path.join(__dirname, "views")); // [!code ++]
app.use(express.static(path.join(__dirname, "..", "public"))); // [!code --]
app.use(express.static(path.join(__dirname, "public"))); // [!code ++]
```

Without this, the app starts and every page it renders fails with `Failed to lookup view`.

### 6.5. Set your other environment variables

Every variable your app reads other than the database and `PORT`, which Compute sets, goes into the project. Set each one for production and for previews, reading the value from your shell so it stays out of your shell history:

```bash
SESSION_SECRET=<production value> npx prisma project env add SESSION_SECRET --role production
SESSION_SECRET=<preview value> npx prisma project env add SESSION_SECRET --role preview
```

Run these from a directory linked to the project, or add `--project <id-or-name>`. The values reach `process.env` when the service deploys, so set them before you push, and redeploy after you change one. [Environment variables](/compute/environment-variables) covers scopes and branch overrides. `prisma dev` does not pass your shell's variables to the service, so a variable your app requires at startup needs a local default or a [service input](/composer/service-input), which reads the same value on Compute and locally.

### 6.6. Push and check the preview

```bash
git add -A
git commit -m "Deploy on Prisma Compute"
git push
```

The push runs the deploy workflow for the setup branch. Find the preview's URL:

```npm
npx prisma service list --branch prisma-cloud/setup
```

**Expected result:** the request you used as a health check succeeds against that URL, for example `curl https://<preview-url>/healthz` returns `{"ok":true}`, and pages that read and write the database work. The preview database starts empty: it has your schema from `migrations/app/`, and no data.

When the preview works, merge the pull request. The merge deploys production the same way, with its own database.

## 7. Remove Prisma ORM 6 or 7

When no file imports `@prisma/client` or the generated client, remove them and the driver adapter:

```npm
npm uninstall @prisma/client @prisma/adapter-pg
```

Then delete the generated Prisma ORM 7 client folder, such as `generated/prisma`, and any seed script that still imports `@prisma/client`. A Prisma ORM 6 client lives in `node_modules/.prisma` and goes with the next clean install.

**Check:** `npm run build` passes, and `npx prisma db verify` reports that the database matches the contract.
