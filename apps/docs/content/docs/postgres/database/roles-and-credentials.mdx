Each connection string you generate for a Prisma Postgres database carries a username and password for a Postgres role that Prisma manages. This page explains what that role can do, how it affects row-level security, and how to manage the credentials. To get a connection string in the first place, see [Connecting to your database](/postgres/database/connecting-to-your-database).

## The role a connection string uses

A connection string generated in the [Prisma Console](https://console.prisma.io) logs in as a restricted superuser. It has superuser-level access for application work: creating schemas, tables, and indexes, reading and writing all data, and enabling [supported extensions](/postgres/database/postgres-extensions).

The restriction covers role and platform management. A Console connection string cannot:

- create roles: `CREATE ROLE` fails with `restricted superuser cannot create roles` (SQLSTATE `42501`)
- alter roles, including its own: `ALTER ROLE` fails with `restricted superuser cannot alter roles`
- install extensions outside the supported list
- change server configuration or reach the machine the database runs on

To see which role you are connected as, run:

```sql
SELECT current_user;
```

## Custom, read-only, and app-only roles

Console has no option to choose a role when you generate a connection string, so every connection string has the same access. There is no read-only connection string and no connection string limited to data changes (DML) only.

You can't create your own roles today. Prisma manages the database roles, and a connection string can't create or alter roles. Support for managing your own roles is planned, but there's no date yet.

If you need a least-privilege setup today, keep migrations and admin tools on a separate connection string from your application so you can rotate each one on its own, and keep both strings in server-side secrets.

## Row-level security

Postgres superusers bypass row-level security (RLS) policies. Because a Console connection string logs in as a restricted superuser, RLS policies do not restrict queries made with it.

Switching to another role inside a session, for example with `SET ROLE` or `set_config('role', ...)`, is not a supported way to enforce RLS on Prisma Postgres. Don't rely on it as a security boundary.

## TLS

Every connection must use TLS. Connection strings include `sslmode=require`, and connections without TLS are refused. Your client must also send the hostname during the TLS handshake (Server Name Indication, SNI), because Prisma Postgres uses it to route the connection to your database. Standard Postgres drivers do this when you connect by hostname. See [Connection pooling](/postgres/database/connection-pooling#networking).

Your connection's TLS session ends at Prisma Postgres's connection endpoint, which then routes the connection to your database inside Prisma's infrastructure. Traffic on that route is encrypted whenever it travels between machines. The only unencrypted step is between processes on the same machine, so your data never crosses a network unencrypted.

## Create, rotate, and delete credentials

Each connection string you generate holds a credential: a password for the same Prisma-managed user. [Connecting to your database](/postgres/database/connecting-to-your-database) covers how to [get your connection strings](/postgres/database/connecting-to-your-database#get-your-connection-strings) and how to [rotate or delete a credential](/postgres/database/connecting-to-your-database#rotate-or-delete-a-credential) from Console, the CLI, or the REST API, including credentials Vercel created.

The password is shown only once, when you generate the connection string. Console keeps only the connection string's name and the last four characters, so neither you nor Prisma support can look up a lost password later. If you lose it, generate a new connection string and delete the old one.

To be sure an old password no longer works, don't rely on a rotate. Create a new credential, switch your application to it and redeploy, and then delete the old credential. Rotating keeps the same connection and tries to remove the old password on a best-effort basis, so the old password can keep working.

## Common questions

### Can I create a read-only user for backups or reporting?

Not from Console: every connection string has the same restricted-superuser access. Run `pg_dump` with your existing direct connection string, or rely on the platform's [backups](/postgres/database/backups). See the note under [Custom, read-only, and app-only roles](#custom-read-only-and-app-only-roles).

### Why does `CREATE ROLE` or `ALTER ROLE` fail with a permission error?

The connection string logs in as a restricted superuser, which cannot create or alter roles. Prisma manages the database roles for you.

### Why are my row-level security policies ignored?

Row-level security isn't supported on Prisma Postgres. Console connection strings log in as a restricted superuser, and superusers bypass RLS. Enforce access rules in your application instead. See [Row-level security](#row-level-security).

### I lost my database password. Can you send it to me?

No. The password is shown only once, and Prisma keeps only the last four characters. Generate a new connection string in Console and delete the old one.

### My new connection string is rejected with an authentication error. What do I do?

A new connection string works as soon as Console shows it; there's no delay. Check that you copied the whole string, including the password, and that the connection string hasn't been deleted in Console. If you've lost the password, generate a new connection string.

### How do I make sure an old credential no longer works?

Create a new credential, move your application to it, and then delete the old credential. Rotating revokes the old password on a best-effort basis only, so deleting the old credential is the reliable way. See [Replace a leaked password](/postgres/database/connecting-to-your-database#replace-a-leaked-password).
