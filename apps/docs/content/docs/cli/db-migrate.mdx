`db migrate` applies pending on-disk migrations to advance the database. It walks every contract space and applies migrations in canonical order: extensions alphabetically, then the app. It applies only the migrations that exist on disk and never generates new operations.

Prisma ORM keeps one migration history for your own models, called the `app` space, in `migrations/app/`, and one for each [extension package](/orm/extensions/using-extensions) that ships its own migrations, such as pgvector. Each of these histories is a [contract space](/orm/migrations/the-migration-graph#terms-used-on-this-page).

Use it from a controlled deployment step after reviewing migration packages.

## Usage

```npm
npx prisma db migrate --db "$DATABASE_URL"
```

## Options

| Option | What it does |
| --- | --- |
| `--db <url>` | Connects to the database. |
| `--to <contract>` | Applies migrations up to a target contract state. Accepts a [contract reference](/cli/migration-ref#contract-reference-forms): a hash, a hash prefix, a [ref name](#contract-references), a migration directory name, [`<dir>^`](#contract-references), [`@contract`](#contract-references), [`@db`](#contract-references), or [`@empty`](#contract-references). |
| `--advance-ref <name>` | Advances the named [ref](/cli/migration-ref) to the post-apply marker after success. |
| `--show` | Previews the migration route without applying (read-only). |
| `--from <contract>` | Use it with `--show`, where it sets the starting state for the preview. Accepts a [contract reference](/cli/migration-ref#contract-reference-forms): a hash, a hash prefix, a [ref name](#contract-references), a migration directory name, [`<dir>^`](#contract-references), [`@contract`](#contract-references), [`@db`](#contract-references), or [`@empty`](#contract-references). |
| `--config <path>` | Read this config file instead of `./prisma.config.ts`. |
| `--json` | Prints a machine-readable result. |

### Contract references [#contract-references]

A ref name is a name you gave a contract state with [`migration ref set`](/cli/migration-ref), such as `prod`. `<dir>^` is a migration directory name followed by `^`, and it names the contract state before that migration, while the directory name alone names the state after it. [Contract references each command accepts](/cli/migration-ref#contract-reference-forms) lists the forms for every command.

`@contract` names the contract in `contract.json`, which `contract emit` writes. The database stores a marker, a row that says which contract state it matches. `@db` names that state, or the empty database when the database has no marker. `@empty` names the empty database, before any migration.

## Recommended flow

```npm
npx prisma migration status --db "$DATABASE_URL"
npx prisma db migrate --db "$DATABASE_URL"
npx prisma migration status --db "$DATABASE_URL"
npx prisma db verify --db "$DATABASE_URL"
```

Run `migration status` before and after applying migrations to see what changed.

## Previewing the route

`--show` prints the route `db migrate` would take without touching the database:

```npm
npx prisma db migrate --show
npx prisma db migrate --show --from @contract --to production
```

## Applying to a target

If your project uses named [refs](/cli/migration-ref), apply up to a target ref:

```npm
npx prisma db migrate --db "$DATABASE_URL" --to production
```

Manage refs with [`migration ref`](/cli/migration-ref).

## When the marker is outside your migrations

Before it runs anything, `db migrate` checks that the database's marker names a contract state that one of your migrations starts or ends at, in every contract space. When it does not, the command fails with `MIGRATION.MARKER_MISMATCH` and changes nothing. The error's `why` says what moved the database there, such as a migration that is no longer on disk or a `db update`. Its next actions give two ways back, and neither resets the database: `db update` for a database whose migration history does not need to be kept, or new migrations for a database that changes only through migrations, such as production. [Drift](/orm/migrations/rollbacks-and-recovery#drift-when-the-database-isnt-where-migrations-left-it) walks through both.

## When no migration reaches the target

When no sequence of the migrations on disk leads from the state the database is in to the target, `db migrate` fails with `MIGRATION.PATH_UNREACHABLE` and changes nothing. The target is the contract that [`contract emit`](/cli/contract-emit) last wrote, or the state that `--to` names. Three cases cause it most often, and each has its own fix. The first two print the same error: if you did not pass `--to`, read the first case, and if you did, read the second. A less common cause is two migrations that start from the same state, so that the history has two branches. [The automatic baseline](/cli/migration-plan#the-automatic-baseline) says how `migration plan` can write the second branch, and [A worked example](/orm/migrations/the-migration-graph#a-worked-example) shows how to join two branches.

### You changed the contract and did not plan a migration

You edited the contract, ran `contract emit`, and then ran `db migrate`. The target is your new contract, and no migration ends at it yet. The error gives the state the database is in as a hash, and it calls a migration an edge. These are its first lines:

```text
✘ [MIGRATION.PATH_UNREACHABLE] Current contract has no planned migration path
  why: No migration edge connects the current state "<current hash>" to the target "<target hash>" in contract space "app".
→ Plan the missing edge: prisma migration plan --from <current hash> --to <target hash> --name <slug>
→ Apply it: prisma db migrate --to <target hash>
```

Do not run the commands as the error prints them. Its [`migration plan`](/cli/migration-plan) command fails with `MIGRATION.REF_NOT_FOUND`, because `--to` only accepts a contract that a migration already produces, and its `db migrate --to` command fails with `MIGRATION.PATH_UNREACHABLE` again until the migration is planned. Run `migration plan` without `--to`, with the current hash from the error and a name for the migration, then apply the result. The first seven characters of the hash are enough:

```npm
npx prisma migration plan --from <current hash> --name add-phone
npx prisma db migrate --db "$DATABASE_URL"
```

Without `--to`, `migration plan` plans up to the contract you just emitted.

### You passed `--to` with an earlier migration

`db migrate` cannot run a migration backwards. To take the database back, you plan a new migration that undoes the later ones. The error is the same as above. Here the two commands it suggests work as printed, because a migration already produces each of the two states. Put `npx` in front of each:

```npm
npx prisma migration plan --from <current hash> --to <target hash> --name undo-phone
npx prisma db migrate --to <target hash> --db "$DATABASE_URL"
```

The new migration usually drops columns or tables, and the data in them. `migration plan` asks you to confirm each drop. In a script it stops instead, and names the flag to pass to `migration plan`, such as `--delete User.phone`. It writes the migration to a new directory under `migrations/app/`, so read the `migration.ts` there before you apply it.

After you go back, your emitted contract is still the later one. A plain `db migrate` then applies the later migrations again, so keep passing `--to <target hash>` until you have changed the contract to match and run `contract emit`. [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) covers going back in more detail.

### The project has no migrations yet

When `migrations/app/` holds no migration, the error reads `No on-disk migrations for contract space "app"`, and on a new, empty database the fix is to plan the first migration and apply it:

```npm
npx prisma migration plan --name init
npx prisma db migrate --db "$DATABASE_URL"
```

If the database already has your tables, do not apply that first migration, because it creates every table from nothing. Sign the database first, then plan and apply. `db migrate` skips the first migration on a signed database:

```npm
npx prisma db sign --db "$DATABASE_URL"
npx prisma migration plan --name init
npx prisma db migrate --db "$DATABASE_URL"
```

[`db sign`](/cli/db-sign) records in the database which contract it matches. `db migrate` applies only the migrations after the first one to a database signed this way, as [The automatic baseline](/cli/migration-plan#the-automatic-baseline) explains. So here it reports `Already up to date`, while on a new, empty database the same migration creates the tables.

`db sign` only signs a database whose tables match your contract. If they differ, it lists the differences, exits with code `4`, and signs nothing, so change the contract or the database until they match and sign again. To start from the database's side, [`contract infer`](/cli/contract-infer) writes a starter contract from it. [When to use `db sign`](/cli/db-sign#when-to-use-it) says when signing is the right step.

### In a script

With `--json`, the `error` object of the result has a `meta` object that holds `kind`, `spaceId`, `fromHash`, and `targetHash`. `kind` is `neverPlanned` when the project has no migrations, and then there is no `fromHash`. In every other case it is `pathUnreachable`, so a script cannot tell those causes apart from `kind`. It can tell them apart by whether it passed `--to`. `spaceId` is `app` for your own contract.

## When an apply fails [#when-an-apply-fails]

Each operation checks the database before and after it runs, as [How migrations work](/orm/migrations/how-migrations-work#every-operation-checks-itself) explains. When a check fails, `db migrate` stops and its `why` says which check failed and, when the check names one object, what the database already has or lacks:

```text
✘ [MIGRATION.PRECHECK_FAILED] Operation table.user failed during precheck: ensure table "user" does not exist
  why: Before operation table.user runs, it checks: ensure table "user" does not exist. That check failed: the database already has table "user". The failed apply changed nothing.
```

Some checks name no object, such as a check about data or a check in a migration planned before `8.0.0-rc.20`. For those, `why` says only "That check failed on this database."

The `why` ends by saying whether the database changed. On PostgreSQL and SQLite a failed apply is rolled back, so it says "The failed apply changed nothing." MongoDB has no transaction around a migration, so once an operation has written anything it says "The operations that ran before the failure stay applied." Before `8.0.0-rc.20`, `db migrate` said a failed apply on MongoDB changed nothing even when earlier operations stayed applied. When the apply stopped in an extension's [contract space](/cli/migration-status#contract-spaces) rather than your own, the `why` also names it, ending with `The apply stopped in contract space "<id>".`, and `meta.failingSpace` holds its id. After you fix the cause, run `db migrate` again: it skips the migrations that were applied and finishes the rest.

With `--json`, the error's `meta` holds the same facts:

```json
{
  "failedCheck": {
    "operationId": "table.user",
    "phase": "precheck",
    "description": "ensure table \"user\" does not exist",
    "expectation": { "expects": "absent", "object": "table \"user\"" }
  },
  "failingSpace": "app",
  "databaseUnchanged": true
}
```

`databaseUnchanged` is `true` when the database is exactly as it was before the apply, and `false` when changes stay. When the schema check after the last operation fails, `meta.schemaIssues` lists the differences, in the shape [`db verify`](/cli/db-verify#schema-differences-in-json-output) describes.

`nextActions` lists each way to fix the failure as its own entry. A script reads its `kind`:

- `run-command`: running this command alone fixes the failure, such as `prisma db sign` for a database that already matches the contract.
- `edit-file`: a person edits a file first, such as the contract source or a migration's `migration.ts`.
- `user-choice`: a person decides, because the step changes data or chooses between plans.

## Data lines

Without `--json`, standard output gets one line per applied migration, with these fields separated by tabs: `space`, `name`, `from`, `to`, and the number of operations run. With `--show`, it gets one line per migration that will run, with `space`, `name`, `from`, and `to`; there is no operation count before the run. `from` is empty for a migration that starts from the empty database. [Global flags](/cli/global-flags#data-lines-of-prisma-orm-commands) lists the rules data lines follow.

```bash
npx prisma db migrate --show | cut -f2
```
