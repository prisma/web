`dev` brings a [Prisma Composer](/composer) application up entirely on this machine. It takes an `<entry>` argument: the module whose default export is the application root, typically `module.ts`. The command runs credential-free against local emulators, programs on your machine that stand in for Prisma Compute, Prisma Postgres, and buckets. It watches the built output and restarts a service when its build changes. See [Local development](/composer/local-development).

Like [`deploy`](/cli/deploy), `dev` runs your *built* output, so build first.

## Usage

```npm
npx prisma dev module.ts
npx prisma dev module.ts --fresh
npx prisma dev module.ts --detach
npx prisma dev url gateway
npx prisma dev stop
```

## Commands

| Command | Description |
| --- | --- |
| `dev <entry>` | Run the app on this machine and watch it for changes until you press `Ctrl-C` |
| `dev url <address>` | Print where a service, database, or bucket of the app answers locally |
| `dev stop` | Stop the app that `prisma dev` last ran from this directory |

`dev url`, `dev stop`, and `--detach` are available from the `prisma` release after `8.0.0-rc.23`. On `8.0.0-rc.23` and earlier, `prisma dev url` and `prisma dev stop` are not commands. Check your version with `npx prisma --version`.

## Flags

| Flag | Description |
| --- | --- |
| `--name <name>` | Run the app under this name instead of the name its root module declares. A different name gets its own local services, databases, and buckets |
| `--fresh` | Before starting, delete this app's local services, databases, and buckets, with their data. Other apps run from the same directory keep theirs |
| `--detach` | Return once every service answers, and leave the app running without watching for changes. `prisma dev stop` stops it. Use it in scripts, agents, and CI |

`dev` needs no credentials or environment variables; local runs never talk to the platform.

When `dev` ends, by `Ctrl-C` or a failure, it stops the app's service processes and local Postgres servers. The emulators themselves keep running. Their data and ports are kept, so the next `dev` in this directory starts with the same ports and data.

With `--detach`, `dev` prints the same `ready` line and service URLs as a foreground run, then exits with code `0` and leaves the app running. It does not pick up rebuilds: run `prisma dev module.ts --detach` again after a build, or run `prisma dev module.ts` in the foreground, which takes over the running app and watches it. If a detached start fails before every service answers, `dev` stops the whole app and exits non-zero. `--detach` combines with `--fresh` and `--name`.

## dev url

`dev url <address>` prints the local URL of one node of the app that `prisma dev` runs from the current directory. A node is a service, database, or bucket in the app, and its address is its name in the app, with dots for a nested node, such as `catalog.database`.

```npm
npx prisma dev url gateway
```

```text no-copy
✔ The service gateway is running at http://localhost:3001
```

| Node | What `dev url` prints |
| --- | --- |
| Service | `http://localhost:<port>` |
| Database | Its connection string, with its local credentials |
| Bucket | Its S3 endpoint followed by `/<bucket>` |

That line is for you to read. When standard output is a pipe or a file, or `$(...)` captures it, `dev url` writes the URL alone, so a script can use it directly. Check the exit status before using it, so a failure does not run the next command with an empty URL:

```bash
url=$(npx prisma dev url gateway) && curl "$url"
```

Run it from the directory you ran `prisma dev` in, while the app runs. It starts nothing: it reads what the last `prisma dev` in this directory recorded. With `--json`, it prints `{ address, kind, url, state }` instead.

`dev url` prints a URL only for a node that is running, so something is listening at the URL it prints. Otherwise it fails with one of these codes:

| Code | Meaning |
| --- | --- |
| `DEV.NOT_STARTED_HERE` | `prisma dev` never ran in this directory |
| `DEV.ADDRESS_UNKNOWN` | The app has no node at that address. The message lists the addresses it has |
| `DEV.EMULATOR_UNREACHABLE` | The emulator that runs the node is not running. Run `prisma dev` again, which starts it |
| `DEV.NOT_RUNNING` | The node exists but is not running. Usually it was stopped, by `prisma dev stop`, by `prisma dev` ending, or by running another app in this directory. A service that keeps crashing is reported this way too, with the path of its log |

## dev stop

`dev stop` stops the app that `prisma dev` last ran from the current directory: its service processes and local database servers, as `Ctrl-C` does in a foreground `prisma dev`.

```npm
npx prisma dev stop
```

Use it to stop an app started with `--detach`, or when `prisma dev` was killed without a chance to stop the app. It lists the services and databases it stopped. When nothing of the app was running, it prints `Nothing of <app> was running.` and still exits with code `0`. Data and ports are kept, so the next `prisma dev` starts with the same ports and data. The emulators themselves keep running, because apps in other directories may use them.

## Global flags

The Prisma CLI's [global flags](/cli/global-flags) also apply: `--format`, `--json`, `--log-level`, `--verbose`, `--quiet`, `--yes`, `--confirm`, `--interactive`, `--color`, and `--config`.

To tail the running application's merged logs, use the `log` operation of the [control API](/cli/deploy#the-control-api); the unified CLI has no `log` command. To see every local emulator and what runs on it, use [`emulator list`](/cli/emulator).
