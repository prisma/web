`migration plan` compares the emitted contract with a starting contract and writes a new migration directory with the operations that turn one into the other.

The starting contract is whatever `--from` names, or the [ref](/cli/migration-ref) named `db` when `--from` is absent.

With neither, what happens depends on the migrations already on disk:

- **`migrations/app/` is empty.** The plan starts from an empty database and contains the full `CREATE` operations for the whole contract. This is the first migration in a new project. The command says so under its summary (`No db ref set — planning from an empty database`), and `--json` output carries `fromDefaulted: true`, so a plan that recreates a database you already have is easy to spot. If a database already exists, run `db init`, `db update`, or `db sign` first.
- **Migrations already exist.** The command refuses with `MIGRATION.PLAN_ORIGIN_UNKNOWN` rather than write a migration that creates every table from nothing, which no existing database could apply. The error names three ways out: `migration ref set db <contract>` to point the ref at the state your database is at, `--from <ref>` to name the starting state for this one plan, or `--from @empty` when you do mean to plan from an empty database. To find the state your database is at, run `npx prisma migration status`, which prints its hash next to the `@db` label, and pass that hash, or the directory name of the migration that ends at it, as `<contract>`.

Keep the `db` ref current and you never see the refusal. [`db init`](/cli/db-init) and [`db update`](/cli/db-update) update it for you when you run them without `--db`; with `--db` you have to add `--advance-ref db`. [`db sign`](/cli/db-sign) updates it whenever it signs, `--db` or not, unless you pass `--no-advance-ref`. [`db migrate`](/cli/db-migrate) updates it when you run it without `--db` and outside CI, or when you pass `--advance-ref db`.

### The automatic baseline

Say `migrations/app/` has no migrations yet, the `db` ref is set, and `migrations/snapshots/` holds a copy of the contract the ref points at. `db init`, `db update`, and `db sign` save that copy when they point the `db` ref at a state, so after one of them this is where you are. Then `migration plan` writes a baseline: a migration from an empty database to the ref's contract. If your emitted contract has changed since then, the same run also writes a second migration with those changes. Expect one or two new directories in `git status`.

`db migrate` never applies the baseline to a database that already records which contract it matches, such as one you ran `db sign` on. It applies only the migrations after the contract that database records.

The baseline only creates things, because it is planned from an empty database, so it never removes data. The second migration can remove data, and `migration plan` asks about it before it writes either one, as [Renames and data loss](#renames-and-data-loss) describes.

If a migration already starts from the contract the `db` ref points at, `migration plan` writes a second migration that starts from the same contract, so the [migration history](/orm/migrations/the-migration-graph) splits into two branches. This happens, for example, after `db migrate --db <url>` or `db migrate` in CI, which apply migrations but leave the `db` ref where it was. `migration plan` still writes the migration and prints a warning. A database that has already run the existing migration then has no migration leading to your new contract, so `db migrate` on that database fails with `MIGRATION.PATH_UNREACHABLE`. To build on what that database has applied instead, delete the directory this run wrote and plan again with `--from` set to the state the database is at. `npx prisma migration status` prints that state's hash next to the `@db` label.

The command is offline, so it does not need a database connection.

## Usage

```npm
npx prisma migration plan --name add_users_table
```

## Options

| Option | What it does |
| --- | --- |
| `--name <slug>` | Sets the migration directory name suffix. |
| `--from <contract>` | Uses a specific starting contract state instead of the `db` ref. Accepts a [contract reference](/cli/migration-ref#contract-reference-forms): a hash, a hash prefix, a [ref name](#contract-references), a migration directory name, [`<dir>^`](#contract-references), or [`@empty`](#contract-references). `@db` is not accepted here, because `migration plan` is offline and cannot read a database. `@contract` is not accepted either. |
| `--to <contract>` | Sets the destination contract state. Defaults to the emitted contract. Accepts the same forms as `--from`, except `@empty`, which is refused as a destination. |
| `--rename <old>:<new>` | Renames a namespace, a model or a field and keeps its rows, instead of dropping and creating it, or moves a model to another namespace. On PostgreSQL and SQLite, also renames an enum value in the rows that hold it, as in `--rename Status.ARCHIVED:Status.RETIRED`, a field of a value object, as in `--rename GeoPoint.lat:GeoPoint.latitude`, and a variant. Repeatable. See [Renames and data loss](#renames-and-data-loss). |
| `--delete <subject>` | Lets the migration lose the data of a model, a field, a table no model stores, every model of a namespace the contract removed, or, on PostgreSQL and SQLite, an enum value the contract removed, a field of a value object, or the rows of a variant. For a type change, accepts the database's own cast. Repeatable. |
| `--convert <Model.field>` | For a type change that can lose values, writes an `alterColumnType` whose conversion you fill in. On PostgreSQL and SQLite, `--convert <Variant>` rewrites the stored discriminator value of a variant whose value changed. Repeatable. See [Type changes and required fields](#type-changes-and-required-fields). |
| `--backfill <Model.field>` | For a new required field or a field made required, writes a backfill step you fill in, instead of a temporary value. On PostgreSQL and SQLite, also takes a field of a value object, as in `--backfill GeoPoint.country`. Repeatable. See [Type changes and required fields](#type-changes-and-required-fields). |
| `--config <path>` | Read this config file instead of `./prisma.config.ts`. |
| `--json` | Prints a machine-readable result. |

### Contract references [#contract-references]

A ref name is a name you gave a contract state with [`migration ref set`](/cli/migration-ref), such as `prod`. `<dir>^` is a migration directory name followed by `^`, and it names the contract state before that migration, while the directory name alone names the state after it. `@empty` names the empty database, before any migration. [Contract references each command accepts](/cli/migration-ref#contract-reference-forms) lists the forms for every command.

## Renames and data loss [#renames-and-data-loss]

When the migration would lose data, because it drops a model, a field, a table or a collection, or changes a field's type in a way that can change values, `migration plan` asks you what to do before it writes anything. Answer each question on the command line:

- `--delete <subject>` lets the data go. A subject is `Model`, `Model.field`, or, for data no model stores, its storage name.
- `--rename <old>:<new>` keeps the data. The migration renames the table or column, and the constraints and indexes named after it, instead of dropping and creating it. Each side is `Model`, `namespace.Model`, `Model.field` or `namespace.Model.field`, and a field's model is named as the new contract names it: `--rename Profile:User --rename User.name:User.fullName`. A rename on the command line is planned from the start, so the drop it replaces is never asked about.
- `--convert <Model.field>` answers a type change that can lose values: the migration gets a `placeholder(...)` call that you replace with your own conversion code.

```npm
npx prisma migration plan --name rename_full_name --rename User.name:User.fullName
```

In a terminal, the command asks the questions you did not answer with a flag. With `--yes`, in a CI job, or with `--no-interactive`, where it cannot ask, it fails with `CLI.CONSENT_REQUIRED` instead. The error lists each question, and its next actions give the flags to add. `--rename` is offered only for a model or field the new contract no longer has, so a field whose type changes is answered with `--convert` or `--delete`. `--confirm` answers none of these questions.

Dropping an index, a unique or foreign-key constraint, a check, a default or a native enum type, and setting `NOT NULL`, lose no data, so the command asks nothing about them.

### A changed stored name [#a-changed-stored-name]

On PostgreSQL and SQLite, a model, field or enum member that keeps its name in the contract is the same object, even when what it is stored as changes. When only its `@@map`, its `@map`, or the value an enum member stores changes, the migration renames the table or column, with the constraints and indexes named after it, or replaces the stored value in the rows, and asks nothing. A table or column is renamed only when its control policy is `managed` in both contracts. A `--delete` for such a change fails with `CLI.CONSENT_UNUSED`, because nothing asks about it.

To start with an empty table under the new name instead, make two changes, each planned and applied before the next: remove the model and answer `--delete`, then add it back with its new `@@map`.

Swaps, chains and takeovers are refused with `MIGRATION.PLANNING_FAILED`: two models or fields that trade tables or columns, one that moves to a name another frees, one that takes the storage of one the change removes, and enum members that trade stored values. Make the change in two steps through a name nothing uses, such as `prisma_swap_users`, planned and applied one after the other.

MySQL and MongoDB plan these changes as before. Before `8.0.0-rc.25`, a changed `@@map` was planned as dropping the table and creating an empty one, and asked for `--delete`.

On PostgreSQL, a changed `onDelete` or `onUpdate` on a relation is planned as dropping the foreign key and adding it back with the new actions. A changed or removed primary key is planned the same way, and because PostgreSQL does not drop a primary key while a foreign key points at it, the migration first drops every foreign key that points at the old key, then adds back each one the new contract still declares. A foreign key the new contract leaves out stays dropped. When such a foreign key is on a table the migration must not change, such as a table whose model has an [`@@control(...)`](/orm/contract-authoring/psl-syntax#control-policy) value other than `managed`, or a table in a schema the contract no longer declares, the command refuses and names that foreign key. Before `8.0.0-rc.20`, both changes failed with `MIGRATION.PLANNING_FAILED`.

On PostgreSQL, a namespace is renamed, moved or removed with the same flags. `--rename billing:finance` renames the schema, and everything in it stays in it. `--rename public.Invoice:billing.Invoice` moves the model's table to another schema with its rows, constraints, indexes and policies, and creates the schema first when the database does not have it. Namespace renames run before the other renames, whatever order you give them in. `public` and a schema another contract space declares are not renamed.

A namespace is a PostgreSQL schema that your contract declares with a `namespace` block. When you remove that block, the command asks about each model in the namespace, as it asks about any removed model. Answer with the flag that matches what you meant:

- If you renamed the namespace, answer with `--rename billing:finance`. Nothing is dropped.
- To keep one model's data, move it to a namespace the contract keeps, as in `--rename billing.Invoice:public.Invoice`.
- To drop the namespace, answer with `--delete billing`. The migration drops each of its tables and then the schema.

`migration plan` does not read the database, so it cannot see a table, view or function in that schema that no contract declares. If the schema holds one, `db migrate` fails before it drops the schema, and the error names the object. Drop or move it yourself, then run `db migrate` again.

The command leaves alone a schema that no contract declared, such as Supabase's `auth`, and a namespace that only another contract space declares. Before `8.0.0-rc.20`, the command did not ask about a removed namespace and left its tables in place.

On PostgreSQL and SQLite, removing a member from an `enum` block is asked about too, because rows may hold its value. The command asks once for each value, however many columns hold it:

- If you renamed the member, answer with `--rename Status.ARCHIVED:Status.RETIRED`. The migration changes the stored value in every column and list that holds it.
- To let the value go, answer with `--delete Status.ARCHIVED`. Optional columns that hold it are set to `NULL`, and lists lose it. A required column cannot take `NULL`, so while any of its rows hold the value, the apply fails with `MIGRATION.PRECHECK_FAILED` before it changes anything. The error counts those rows and says how to keep them.

A member you rename while keeping its stored value, such as `RETIRED = "archived"` in place of `ARCHIVED = "archived"`, changes no rows, so nothing is asked. A member that keeps its name but stores a new value is [a changed stored name](#a-changed-stored-name): the migration replaces the value in the rows and asks nothing. Two members that swap their stored values are refused; make the swap in two migrations through a value nothing uses. [Stored enum values](/orm/reference/migration-api#stored-enum-values) in the migration API reference shows the calls a migration uses.

Native PostgreSQL enums (`pg.enum(...)`) are not affected. Before `8.0.0-rc.21`, PostgreSQL failed at apply when a row held the removed value, and SQLite planned nothing.

On PostgreSQL and SQLite, a field of a [value object](/orm/contract-authoring/psl-syntax#value-objects) is asked about too when the contract renames it, removes it, or makes it required. Name the field through its value object, such as `GeoPoint.lat`, not through a model. Each statement acts on every column that holds the value object, including lists of it and value objects nested in another:

- `--rename GeoPoint.lat:GeoPoint.latitude` renames the key in every stored object.
- `--delete GeoPoint.lng` removes the key from every stored object.
- An enum value inside a value object is asked about as the enum value. `--rename Status.ARCHIVED:Status.RETIRED` rewrites it wherever it is stored, and `--delete Status.DRAFT` sets an optional field that holds it to JSON `null` and takes it out of a list.
- `--backfill GeoPoint.country` fills a field that becomes required. The migration gets a `fillStoredKey` step whose value is `placeholder('GeoPoint.country:value')`. Replace the placeholder with one JSON value, then run `node migration.ts`. `db migrate` refuses the migration while the placeholder is left. Without `--backfill`, the command refuses and names the flag.

A [variant](/orm/contract-authoring/psl-syntax#base-models-and-variants) whose discriminator value changes, or that the contract removes, is asked about as a model:

- `--convert Bug` rewrites the old value to the new one in the base table's discriminator column.
- `--rename Bug:Defect` of a variant whose value also changed rewrites the value in the same way.
- `--delete Bug` deletes the rows that hold the old value, then drops a removed variant's own table or the columns only it used.

On MongoDB, changes inside documents are asked about too, since `8.0.0-rc.25`:

- A field that a value object or an embedded model loses: `--rename Address.street:Address.line1` if you renamed it, or `--delete Address.street` to remove the key from every stored object.
- A stored value that an enum loses: `--rename Status.ARCHIVED:Status.RETIRED` to keep the documents under another member, or `--delete Status.ARCHIVED` to unset it in optional fields and take it out of lists. Where a required field holds it, the apply stops with `MIGRATION.PRECHECK_FAILED`, counts the documents, and says how to keep them.
- A variant whose discriminator value changes: `--convert Bug` to rewrite the value, or `--delete Bug` to delete its documents.
- A variant the contract removes: `--rename Bug:Issue` if you renamed it, or `--delete Bug` to delete its documents.
- A new required field inside a value object or an embedded model gets a temporary value in the objects that lack it. To write your own value, pass `--backfill Address.zip` and replace the placeholder in the migration with an aggregation expression, such as `{ $literal: 'unknown' }`.

A plan in which one operation writes a field, key or value that another operation of the same plan reads, such as two renames that trade names, is refused with advice to make the change in two migrations, because MongoDB applies operations one at a time.

On MongoDB, a field type change that can lose values is asked about, as on SQL, and it has two answers. `--delete User.age` casts the stored values with `$convert` and stops on a value it cannot cast. `--convert User.age` writes a data transform that holds `placeholder('User.age:update')`, which you replace with your own update document or aggregation pipeline; [MongoDB operations](/orm/reference/migration-api#mongodb-operations) shows the planned transform. A change such as `String` to `Boolean`, which `$convert` would get wrong, offers `--convert` only. A cast that keeps every value, such as `Int` to `BigInt`, is planned with nothing asked.

A new required field on MongoDB is filled with a temporary value in the documents that lack it: `""` for a `String`, `0` for a number, and `false` for a `Boolean`. A field of another type, such as a `DateTime`, has no temporary value, so plan it with `--backfill`. Without `--backfill`, `migration plan` writes no fill for such a field and prints no warning, and `db migrate` stops at the validator change with `MIGRATION.PRECHECK_FAILED`, naming the `--backfill` flag. To set your own value instead, pass `--backfill User.plan`, which writes a data transform for it. A new required field that a unique index covers gets no temporary value, so plan it with `--backfill`. A change to a collection's validator checks the documents before it applies; see [how migrations work](/orm/migrations/how-migrations-work#the-same-model-for-sql-and-mongodb). This paragraph and the one before it apply since `8.0.0-rc.24`.

On MongoDB, a model rename renames its collection and keeps its documents, indexes and validator, and a field rename renames the field in every document that holds it. Removing a field from a model removes it from every document that holds it, so the command asks about it as it asks about a dropped collection: answer with `--delete User.nickname` or `--rename User.nickname:User.<new name>`. The planner refuses a rename of the field stored as `_id`, of a field whose stored name contains `.` or starts with `$`, of a time-series collection, and of a variant whose discriminator value changes, and says what to do instead.

On MongoDB, `--rename` and `--delete` name fields by their names in the schema, not by the names they are stored under. For a field `id ObjectId @id @map("_id")`, write `--rename User.id:User.userId`, not `User._id`.

The first MongoDB migration you plan after upgrading from a release before `8.0.0-rc.19` is the exception. The [upgrade instructions](https://github.com/prisma/orm/blob/v8.0.0-rc.19/skills/prisma-8/upgrading/app/upgrades/8.0.0-rc.18-to-8.0.0-rc.19/) include a script that rewrites the copies of your old contract under `migrations/`, and those copies name each field by its stored name. That first migration starts from such a copy, so in it you name the old field by its stored name and the new field by its schema name. For a field that was `name String @map("display_name")` and is now `title String`, write `--rename User.display_name:User.title`. From the next migration on, use schema names only.

## Type changes and required fields [#type-changes-and-required-fields]

On PostgreSQL and SQLite, a type change that can lose values, such as `String` to `Int` or a longer `varchar` to a shorter one, is a question like a drop. Answer it with one of these flags:

- `--convert <Model.field>` writes an `alterColumnType` with `using: placeholder('<Model.field>:convert')`. Replace the placeholder with the conversion as SQL over the column, such as `using: '"age"::integer'`, then run `node migration.ts`. On SQLite the slot is the column's copy expression in `recreateTable`, such as `copyExpressions: { age: 'CAST("age" AS INTEGER)' }`.
- `--delete <Model.field>` lets the database's own cast run. It may cut or round values, and a value it cannot cast fails the apply.

A new required field on a table with rows gets a temporary value in the existing rows, such as `''` for text or `0` for a number, and the command's output names it. An optional field made required is tightened directly, so the apply fails while any row holds `NULL`, with a message that counts those rows. To fill the rows yourself, pass `--backfill <Model.field>`: the migration gets a `dataTransform` step with `check` and `run` placeholders to fill in, as [Editing a migration](/orm/migrations/editing-a-migration) shows. A new unique, primary-key or foreign-key field has no temporary value, so use `--backfill` when the table has rows.

```npm
npx prisma migration plan --name age_to_int --convert User.age --backfill User.displayName
```

## When nothing in the database changes [#no-database-change]

If the storage part of the contract did not change, `migration plan` writes nothing and prints `✔ No changes detected`; with `--json`, the result's `summary` is `No changes detected between contracts`. That is not an error, and there is nothing to do. If the storage part changed but the database needs no change, `migration plan` writes a migration with no operations and names what changed:

```text
⚠ Planned 0 operation(s). The storage the contract describes changed, but the database needs no operation for it, so the migration has none. What changed: table "public.user".
```

This happens after a Prisma upgrade that changes how `contract.json` records values, after you change how a field's values are written in `contract.json` while its database type stays the same, or after you change a control policy. Apply the migration with `prisma db migrate` as usual, so each database records the new contract. If you manage the database with `db init` or `db update` instead of migrations, run [`prisma db sign`](/cli/db-sign) on each database.

The one case that fails is a first migration with no operations, from a contract that describes nothing to create: `migration plan` stops with `MIGRATION.PLANNING_FAILED`. If the database needs something the contract does not describe, write it by hand in a migration from [`prisma migration new`](/cli/migration-new).

If you expected the database to change, report it with the output of `prisma migration plan --json`.

## Recommended flow

```npm
npx prisma contract emit
npx prisma migration plan --name add_users_table
npx prisma migration show <migration-dir>
```

`<migration-dir>` is the new migration's directory name, such as `20260707T1006_add_user_phone`, which `migration plan` prints. Review the migration before you apply it with [`db migrate`](/cli/db-migrate).

## Planning a rollback

`<dir>^` names the contract state before the migration in `<dir>`, so with `--from <migration-dir>` and `--to "<migration-dir>^"` you plan a migration from the state after that migration back to the state before it. [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) shows the whole rollback:

```npm
npx prisma migration plan --from <migration-dir> --to "<migration-dir>^" --name rollback
```

## Data lines

Without `--json`, standard output gets one line per directory the command wrote, each once: the [automatic baseline](#the-automatic-baseline) first when the command wrote one, then the new migration, then any migration it wrote for an extension's contract space. [Global flags](/cli/global-flags#data-lines-of-prisma-orm-commands) lists the rules data lines follow.

## When to use migration plan

Use `migration plan` when your team wants database changes reviewed in version control. For local prototypes where review is not needed, [`db update`](/cli/db-update) is usually faster.

If the generated migration is not the migration you want, use [`migration new`](/cli/migration-new) and author the migration manually.
