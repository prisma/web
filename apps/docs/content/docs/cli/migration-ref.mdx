A ref is a name, such as `staging` or `production`, for the contract state an environment should match. The contract is your schema as [`contract emit`](/cli/contract-emit) writes it to `contract.json`, and each version of it has a hash. Use refs when an environment should be migrated to a state you choose instead of to your latest migration. Other commands then take the name in place of a contract hash: [`db migrate --to production`](/cli/db-migrate), [`db update --to production`](/cli/db-update), or [`db sign production`](/cli/db-sign).

A ref can point only at a contract that one of your migrations produces, so plan a migration for a change before you point a ref at it. Each ref is a file in your migrations folder, by default `migrations/app/refs/<name>.json`, so commit it with your migrations. The `migration ref` commands change only these files and never connect to a database.

## The db ref

The `db` ref records the contract state you expect your local database to match. When you run [`migration plan`](/cli/migration-plan) without `--from`, it plans from the `db` ref, so as long as the ref is up to date, each plan contains only your latest change.

These commands update the `db` ref for you:

- [`db init`](/cli/db-init) and [`db update`](/cli/db-update) update it when they take the connection from `prisma.config.ts`. When you pass `--db`, they update it only if you also pass `--advance-ref db`.
- [`db sign`](/cli/db-sign) updates it after it succeeds, with or without `--db`. Pass `--no-advance-ref` to stop it.
- [`db migrate`](/cli/db-migrate) updates it only when you pass `--advance-ref db`. Without that flag it never changes the file, so a deploy or CI run leaves your repository unchanged. In CI, run `db init` and `db update` with `--db` for the same reason.

You can also set it yourself with `migration ref set db <contract>`.

## Usage

```npm
npx prisma migration ref set production 4cb4256
npx prisma migration ref list
npx prisma migration ref delete production
```

## Subcommands

| Subcommand | What it does |
| --- | --- |
| `set <name> <contract>` | Points a ref at a contract, and replaces its target without asking if the ref already exists. The contract is a [contract reference](/orm/migrations/the-migration-graph#contract-reference-forms): a hash or the start of one, another ref name, a migration directory name, or `<dir>^` for the state before that migration. |
| `list` | Lists every ref with the contract hash it points at. |
| `delete <name>` | Deletes a ref. The contract it pointed at is untouched. |

## Ref names

A ref name is made of parts separated by forward slashes. Each part uses lowercase letters, digits, and hyphens, and starts and ends with a letter or digit. So `staging`, `prod-2`, and `staging/eu` are valid, and `Prod`, `prod_2`, `release.1`, `x-`, and `a//b` are refused.

## When a subcommand refuses

A refused subcommand changes nothing and exits with code `2`. The error code is printed in square brackets on standard error, and with `--json`, standard output gets one line whose `envelope.error.code` holds it:

| You ran | Error code | What to do |
| --- | --- | --- |
| `set` or `delete` with a name that breaks the rules above | [`MIGRATION.INVALID_REF_NAME`](/orm/reference/error-reference#MIGRATION.INVALID_REF_NAME) | Choose a name that follows the rules. |
| `set` with a contract reference that matches nothing | [`MIGRATION.REF_NOT_FOUND`](/orm/reference/error-reference#MIGRATION.REF_NOT_FOUND) | Check the hash, or the names in `migration ref list`. |
| `set` with a hash that no migration produces, such as the hash of a change you have not planned yet | [`MIGRATION.HASH_NOT_IN_GRAPH`](/orm/reference/error-reference#MIGRATION.HASH_NOT_IN_GRAPH) | Run [`migration plan`](/cli/migration-plan) first, or pass the name of an existing migration. |
| `set` with `@db`, which means the live database | [`MIGRATION.HASH_NOT_IN_GRAPH`](/orm/reference/error-reference#MIGRATION.HASH_NOT_IN_GRAPH) | Pass a hash or a migration directory name, because `migration ref` never reads the database. |
| `set` with `@empty`, or with `<dir>^` for your first migration, which both mean an empty database | [`MIGRATION.REF_SET_EMPTY_SENTINEL`](/orm/reference/error-reference#MIGRATION.REF_SET_EMPTY_SENTINEL) | Point the ref at a migration. |
| `delete` with a ref that does not exist | [`MIGRATION.UNKNOWN_REF`](/orm/reference/error-reference#MIGRATION.UNKNOWN_REF) | Check the names in `migration ref list`. |

To delete a ref only if it exists, check the list first. Reading the list into a variable makes the script stop if `list` itself fails:

```bash
set -e
refs=$(npx prisma migration ref list)
if printf '%s\n' "$refs" | cut -f1 | grep -qx staging; then
  npx prisma migration ref delete staging
fi
```

## Data lines

Without `--json`, the subcommands print these data lines on standard output:

- `list`: one line per ref, with three fields separated by tabs: `name`, `hash`, and `invariants`. `invariants` lists the ids of the data operations that migrating to the ref must run, separated by commas, and is empty when there are none.
- `set`: one line, the contract hash the ref now points at.
- `delete`: nothing. It exits with code `0` when it deleted the ref.

```bash
npx prisma migration ref list | cut -f1
```

[Global flags](/cli/global-flags#data-lines-of-prisma-orm-commands) lists the rules data lines follow.

## Example workflow

```npm
npx prisma migration ref set production 20260101T1000_add_user
npx prisma migration status --db "$DATABASE_URL" --to production
npx prisma db migrate --db "$DATABASE_URL" --to production
```

If you pass `--advance-ref <name>` to a command that changes the database, that command also points the ref at the state it applied, once it succeeds.
