Prisma Composer is a TypeScript framework for defining applications composed of multiple services and resources.

You declare each service and its dependencies in TypeScript. Dependencies can include other services, [Prisma Postgres](/postgres) databases, scheduled jobs, object storage, and secrets. Composer uses those declarations to provision the services on [Prisma Compute](/compute), the databases on Prisma Postgres, and the authenticated connections between them when you deploy.

Composer is one way to deploy to Prisma Compute, not a requirement. A single service deploys to Compute directly; see [Deployments](/compute/deployments) for the other paths.

:::info[Early Access]

Prisma Composer is in [Early Access](/console/more/feature-maturity#early-access). APIs and commands can change between releases. The Composer commands ship inside the [Prisma CLI](/composer/cli-reference): run them with `npx prisma@next composer <command>`.

:::

## What a Composer application is

An application is a tree of services and resources. Services call each other through typed contracts; each service declares its own resources, such as a database. Step through how the pieces relate:

## A minimal example

A service is declared as data. This declaration says the `storefront` service calls the catalog service's API and is built as a Next.js app:

```ts title="src/storefront/service.ts"
import nextjs from '@prisma/composer/nextjs';
import { rpc } from '@prisma/composer/service-rpc';
import { compute } from '@prisma/composer-prisma-cloud';
import { catalogContract } from '../catalog/contract.ts';

export default compute({
  name: 'storefront',
  deps: { catalog: rpc(catalogContract) },
  build: nextjs({ module: import.meta.url, appDir: '..' }),
});
```

`deps.catalog` declares a dependency on the catalog contract. The contract determines which methods the client exposes and their TypeScript types.

At runtime, the service receives that client from `service.load()`. Calling a contract method is an ordinary async function call:

```ts title="src/storefront/data.ts"
import service from './service.ts';

const { catalog } = service.load();
const { products } = await catalog.listProducts({});
```

The root module is the application. It provisions each service and wires every dependency to the service or resource that provides it:

```ts title="module.ts"
import { module } from '@prisma/composer';
import catalogModule from './src/catalog/module.ts';
import ordersModule from './src/orders/module.ts';
import storefrontService from './src/storefront/service.ts';

export default module('store', ({ provision }) => {
  const catalog = provision(catalogModule);
  const orders = provision(ordersModule, { deps: { catalog: catalog.rpc } });
  provision(storefrontService, { deps: { catalog: catalog.rpc, orders: orders.rpc } });
});
```

TypeScript checks the wiring: a dependency bound to a producer with a different contract, a missing RPC handler, or a config value of the wrong shape is a compile error, not a failed deploy.

`npx prisma@next composer deploy module.ts` loads the root module, compares it with the deploy state stored for that environment, and creates or updates the services on Prisma Compute and the databases on Prisma Postgres. Re-running a deploy applies only the difference:

## Core concepts

- **App**: the complete deployable application, defined by the root module. Deployed as one Prisma [project](/compute#the-model).
- **Service**: a running application component, declared with `compute()`. Deployed as one Prisma Compute service.
- **Resource**: something a service depends on that is not a service: a Prisma Postgres database, a bucket, or a secret.
- **Contract**: the typed interface through which services communicate, written as [Standard Schema](https://standardschema.dev) definitions.
- **Module**: a reusable unit that provisions services and resources behind a typed boundary, such as a service packaged with its own database.
- **Dependency**: a contract or resource a service declares in `deps` and receives from `service.load()`.

[Apps and Modules](/composer/apps-and-modules) covers each in depth.

## Design principles

- **Dependencies are injected, not discovered.** Application code does not read `process.env` or hardcode URLs. Every dependency arrives typed through `service.load()`, so any environment, whether production, an isolated stage, or a test, is the same code with different injected values.
- **Builds are yours.** Composer never bundles or transforms your code. You build with your own bundler; the deploy assembles what you built.

## Use Composer with an AI coding agent

Composer's declaration-based API works well with coding agents because mistakes fail the TypeScript compile instead of a deploy. Before your agent writes Composer code, install the Composer skill so it works from the real API instead of guessing:

```npm
npx skills add prisma/composer
```

The skill documents the full authoring API, the CLI commands, and the first-party Modules for scheduled jobs, object storage, and event streams. Review the generated declarations like any other TypeScript: `npx tsc --noEmit` checks the wiring before you deploy.
