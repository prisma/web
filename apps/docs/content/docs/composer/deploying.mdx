`deploy` loads your entry file (the one whose default export is the root module, named by `entry` in the `composer` section of `prisma.config.ts`) and stands the whole app up on [Prisma Compute](/compute) and [Prisma Postgres](/postgres). You choose the target **environment**, such as `production`, `staging`, or `pr-42`, on the command line rather than in your code. Tearing an environment down is the `destroy` operation of the [control API](#driving-deploys-from-code).

| You want to... | Run |
| --- | --- |
| Deploy to production | `npx prisma deploy` |
| Deploy another environment | `npx prisma deploy --environment <name>` |
| Deploy under a different app name | `npx prisma deploy --name demo-42` |

## Credentials

On your machine, `deploy` uses the session stored by `auth login`, the same sign-in every other CLI command uses:

```npm
npx prisma auth login
```

In CI or any headless environment, use a service token instead. Set two environment variables:

- `PRISMA_SERVICE_TOKEN`: create a service token for your workspace in the [Prisma Console](https://console.prisma.io).
- `PRISMA_WORKSPACE_ID`: in the workspace's settings.

A fresh checkout with those two variables set deploys successfully once the app's project exists. The very first deploy creates that project, and a new project needs a region: set it in the deploy config or in the environment, as described in the [`deploy` reference](/cli/deploy). Once the project exists it keeps its region, and later deploys, other environments included, inherit it. The CLI finds or creates everything else. Keep the values out of the repo (an `.env` you source at deploy time, or CI secrets). When `PRISMA_SERVICE_TOKEN` is set it takes priority over any stored session.

## Build first

`deploy` does not build for you. It assembles what your build produced:

```npm
npm run build
npx prisma deploy
```

Deploy state records what is already provisioned, so a re-deploy applies the difference instead of recreating everything. The platform stores this state with the environment it describes, scoped to that environment's branch inside the app's project. It is not stored on your machine, so your laptop and CI see the same state. Concurrent deploys of the same environment take turns through a lease on that state. While one deploy holds the lease, a second deploy fails immediately with a message naming the holder. If a deploy crashes, its lease expires after about a minute, and the next deploy takes over.

## Environments

Deploying with no `--environment` targets **production**, exactly as `--environment production` does. In platform terms, the app is a project (named after your root module), and production is the project's default branch. The name is looked up in your workspace: a project this module deployed before is reused, and redeploying converges it. A project with the same name whose hosted state the CLI cannot identify or verify (one created outside this module's deploys, for example) stops the command with `HostedStateBootstrapError`. Use `--name` to deploy under a different name, or rename the module.

`--environment <name>` with any other name deploys a complete, isolated copy of the app as a [preview branch](/compute/branching) of that same project: its own services, its own databases, its own configuration. The only thing an environment shares with production is the code. Composer's *environment* and Compute's *preview branch* are the same object seen from two tools, which is why the environment's variables are the branch's [environment variables](/compute/environment-variables):

```npm
npx prisma deploy                        # production
npx prisma deploy --environment staging  # a persistent staging environment
npx prisma deploy --environment pr-42    # one environment per PR
```

Re-deploying any environment is safe to run more than once: it updates the resources in place. An environment name must be a valid git ref name; an invalid name fails with `DEPLOY.ENVIRONMENT_INVALID` rather than being renamed. A name that is the default branch's own name, such as `main`, is refused, because it would be production under a second name.

`--stage` was renamed to `--environment` in Composer 0.36. `--stage` now fails with `CLI.COMMAND_MOVED`, naming the new flag.

## Make a service public

A service is reachable from the internet through a **public URL** you declare with `publicUrl()`. The service exposes an HTTP interface with `rawHttpContract`, and the public URL points at it. Provision it where the hostname is decided, usually in the root module:

```ts title="module.ts"
import { module, resolve } from '@prisma/composer';
import { publicUrl } from '@prisma/composer-prisma-cloud';
import webService from './src/web/service.ts';

export default module('shop', ({ environment, provision }) => {
  const web = provision(webService);
  const url = resolve([environment.name], ([name]) =>
    name === 'production' ? 'shop.com' : publicUrl.prismaBuild());
  provision(publicUrl({ id: 'site', url, target: web.http }));
});
```

`publicUrl()` takes three parameters:

- `id`: the public URL's provision ID, so this one's address is `shop.site`. Changing it destroys the public URL and creates a new one.
- `target`: the raw HTTP interface the service exposes, here `web.http`, declared as `expose: { http: rawHttpContract }` with `rawHttpContract` from `@prisma/composer/http`. An RPC interface fails the type check.
- `url`: which hostname serves the service. It is required. `publicUrl.prismaBuild()` serves the service at the `prisma.build` hostname the platform gives every service. `publicUrl.hostname('shop.com')`, or the bare string `'shop.com'`, attaches that hostname to the service as a custom domain. `url` can be a value from `resolve()`, so each environment can get its own hostname.

Before the deploy can attach a named hostname, two DNS records must be published: a TXT record at `_prisma-verification.<hostname>` with your workspace's verification value, and a CNAME record that points the hostname at the platform. Without them the deploy fails with the platform's error, such as `domain-ownership-required`. In Composer 0.37, a named hostname works only in production; use `publicUrl.prismaBuild()` in every other environment.

`prisma dev` ignores named hostnames and serves every service on its local URL. Today the platform still gives every service a `prisma.build` hostname, so a service with no public URL is reachable there too; declare a public URL for each service the internet should reach, so your code does not change when that hostname becomes opt-in.

## What a deploy prints

A deploy ends by printing what it made, in your own terms: the names you authored, what each one became on the platform, and the public URLs:

```text no-copy
storefront-auth
├─ auth
│  └─ api   compute-service cps_abc123
│           https://xyz.ewr.prisma.build
├─ db       postgres-database db_def456
└─ web      compute-service cps_ghi789
            https://uvw.ewr.prisma.build
```

The tree is your module structure: `storefront-auth.auth.api` is the `api` service inside the `auth` Module. Under each name is the platform resource it became and its ID, the thing to search for in the Console when you need it.

URLs appear for publicly reachable endpoints. That is why a Compute service prints one and a database does not: a database has a connection string, not a public endpoint. Secrets are left out entirely, so a node whose only output is a keypair prints no resource line. A node that deployed but published nothing reportable still appears in the tree, marked `(no entities reported)`.

## Removing resources

Your module is the source of truth for what exists. To remove a resource, delete its provision from the code and deploy again: the deploy compares the declaration against the environment's deploy state and deletes whatever is no longer declared, alongside any creates and updates the same deploy needs.

```text no-copy
Plan: 3 to update, 4 to delete, 1 to noop
[web2-deploy] deleted
[COMPOSER_WEB2_PORT-var] deleted
[COMPOSER_WEB2_ORIGIN-var] deleted
[web2-svc] deleted
```

A removed service takes its deployment and its wiring with it, and the resources that remain are untouched: a two-service app whose second service is deleted from the module keeps serving from the first without interruption.

Two things a deploy never removes:

1. **The last service.** An app is at least one service; a module that provisions nothing fails with `ASSEMBLE.SERVICE_MISSING` before anything runs, so you cannot empty an environment by emptying the module.
2. **The project and its branches.** Those are the containers an environment deploys into: created if absent on deploy, and never deleted by one. Tearing down a whole environment is the [`destroy` operation](#destroying); deleting an entire project is [`project delete`](/cli/project), which asks you to repeat the project id with `--confirm <project-id>` because it destroys the project's databases too.

## Destroying

The unified CLI has no `destroy` command. Tear an environment down with the `destroy` operation from `@prisma/composer/control` (see [Driving deploys from code](#driving-deploys-from-code)). It requires an explicit `environment`, even for production, which is `environment: 'production'`. There is no default, so a teardown always names what it destroys; a call without one fails with `DEPLOY.ENVIRONMENT_REQUIRED`. Unlike the CLI, the control API does not read the session stored by `auth login`. Export `PRISMA_SERVICE_TOKEN` and `PRISMA_WORKSPACE_ID` (see [Credentials](#credentials)) before running the script, or it stops with `environment variable PRISMA_WORKSPACE_ID is required`:

```ts title="destroy-staging.ts"
import { fileURLToPath } from 'node:url';
import { destroy } from '@prisma/composer/control';
import prismaConfig from './prisma.config.ts';

const result = await destroy({
  environment: 'staging', // or 'production'
  config: {
    value: prismaConfig.composer,
    file: fileURLToPath(new URL('./prisma.config.ts', import.meta.url)),
  },
});
if (!result.ok) throw new Error(`${result.failure.code}: ${result.failure.message}`);
```

Run it from the directory you deploy from, for example with `node destroy-staging.ts` on Node.js 22.18 or newer, which runs `.ts` files directly.

If you deployed under a different name with `--name`, pass the same `name` here so the operation finds the right project.

Destroying any environment other than production removes its resources, then deletes its branch along with the environment's deploy state. Destroying production removes the resources and, if the project is empty afterwards, deletes the project too, so empty projects do not pile up in your workspace. A project still holding another environment's resources stays in place. Tearing down an environment that was never deployed fails with "nothing deployed". It does not provision one first.

## CI

On GitHub, connect the repository and add [prisma/cloud-deploy-action](https://github.com/prisma/cloud-deploy-action) to a workflow instead of scripting the deploy yourself. The action derives the target from the branch: the default branch deploys production, and every other branch deploys an environment named after it. Connected repositories authenticate through GitHub's OIDC tokens, without a stored secret. [Deploy on push](/compute/deploy-on-push) walks through the setup.

Any other CI runs the same commands as your machine: set the two credential variables as CI secrets, build, and deploy. The per-PR environment pattern:

```npm
npx prisma deploy --environment "pr-$PR_NUMBER"    # on push
```

When the PR closes, tear the environment down with the `destroy` operation from a small script, passing `environment: 'pr-42'` for PR 42.

Two more steps apply if your app binds input fields with `envSecret` or `envParam` (see [Service input](/composer/service-input)):

- **`envSecret`:** when an environment does not have a secret's platform variable yet, the deploy copies the value from your app secrets (by default the deploying shell), and later deploys use the platform copy. So CI must export a secret on every deploy where the environment lacks it: for every secret on a new environment's first deploy, such as a new `pr-42`, and for a secret you add to the app later. If a name is absent from both the platform and the app secrets, the deploy fails early and names the missing variable. Keep secrets in CI's secret store, not in committed files.
- **`envParam` and a root module's `input`:** the deploy reads them from the shell, or from the `config` list in `prisma.config.ts`, on every deploy, so CI must export them every time, or you commit them in a `.env.<environment>` file and list `dotenv()` in `prisma.config.ts` (see [Values from outside the code](/composer/service-input#values-from-outside-the-code)).

## When prisma.config.ts fails on an effect version conflict

The deploy engine Composer drives needs the exact `effect` version `@prisma/composer` pins. The extensions in your `composer` section import that engine, so when your installed tree gives it a different `effect`, evaluating `prisma.config.ts` fails before any command runs:

```text no-copy
CLI.CONFIG_UNREADABLE  /path/to/prisma.config.ts could not be evaluated:
Cannot find module '.../node_modules/effect/dist/unstable/http/FetchHttpClient.js'
```

The message after the colon is the module error from inside the engine, and it varies with the versions involved: a missing `effect` module, or an `effect` export that is not a function. The command exits with code 2. Commands that do not read the config, such as `prisma --version`, still run.

This happens when your app, or another dependency of it, pins a different `effect` than `@prisma/composer` does and your package manager hoists that copy where the deploy engine resolves it. A plain Composer app never hits it: `@prisma/composer` and `@prisma/composer-prisma-cloud` pin every `effect`-family package the engine would otherwise float, so a fresh install resolves a single `effect`. The fix is to use the same `effect` as Composer: match your own `effect` dependency to `@prisma/composer`'s exact pin (see its `dependencies.effect`), or, when a dependency you cannot change pins another version, force Composer's with your package manager's override setting and reinstall. Each one takes the version in `@prisma/composer`'s `dependencies.effect`.

npm reads `overrides` in `package.json`:

```json title="package.json"
"overrides": {
  "effect": "<the version in @prisma/composer's dependencies.effect>"
}
```

pnpm 11 and later read `overrides` in `pnpm-workspace.yaml` and ignore the `"pnpm"` field of `package.json`:

```yaml title="pnpm-workspace.yaml"
overrides:
  effect: "<the version in @prisma/composer's dependencies.effect>"
```

pnpm 10 and earlier read `overrides` under `"pnpm"` in `package.json`:

```json title="package.json"
"pnpm": {
  "overrides": {
    "effect": "<the version in @prisma/composer's dependencies.effect>"
  }
}
```

Yarn reads `resolutions` in `package.json`:

```json title="package.json"
"resolutions": {
  "effect": "<the version in @prisma/composer's dependencies.effect>"
}
```

The setting only takes effect when the tree is rebuilt, and it goes stale when you upgrade `@prisma/composer`, so update it with each upgrade.

## When a deploy stops on a missing connection value

A dependency's connection declares the values it needs, by name, and the node on the other end has to supply them. When one does not, the deploy stops and names the edge rather than standing the app up:

```text no-copy
Connection input "auth.db" declares param "url", but its producer "db" did not
supply it — the producer's outputs carry [host].
```

Fix it at whichever end is wrong: add the name to the outputs the producer returns, or mark the param `optional` on the connection if absent is a valid value (the consumer then reads `undefined`). Do not make the param optional just to route around the error: that reinstates a silent `undefined`. You will only meet this error if you authored the connection or an extension on one side of the wire. Every block that ships with the framework supplies what it declares.

## Production behavior

Behavior you will run into once the app is deployed, and what to do about it:

- **Compute scales to zero, and idle database connections get closed.** A long-lived client that treats a dropped connection as fatal will crash-loop through 502s. Keep the pool small and reconnect-friendly, turn off named prepared statements so a reconnect against the local `prisma dev` database does not fail with `prepared statement "..." already exists`, and do not let an async error kill the process:

  ```ts
  const sql = new SQL({ url: db.url, max: 1, idleTimeout: 10, prepare: false });
  process.on('uncaughtException', (err) => console.error('uncaughtException', err));
  process.on('unhandledRejection', (err) => console.error('unhandledRejection', err));
  ```

- **Bind `0.0.0.0`, not loopback.** Compute routes external HTTP to the VM; a `localhost` listener is unreachable from outside.
- **A deployed `/rpc/<method>` returns `401` to you.** Calls are [authenticated for you](/composer/services-and-contracts#calls-are-authenticated-for-you), and your `curl` is not one of the services the app connected. Reach it through a consumer instead.
- **Calls into a sleeping service can get `ECONNRESET`** while it cold-starts. Retry them; the generated RPC client already does.
- **The `cron` scheduler stays awake on purpose.** It holds Compute's keep-awake guard for its whole lifetime, so it never scales to zero: one warm instance per app is the cost of the clock. Every other service, the runner included, sleeps as usual.
- **The `COMPOSER_*` variables in your project belong to the deploy.** Config, secret pointers, and service keys all land there, and every deploy rewrites them. An edit made by hand does not survive the next deploy.
- **Streaming responses stream, but the first bytes have a 60-second deadline.** Compute's ingress forwards your response as your service sends it; it does not hold it back until the response completes. What it bounds is the wait for the response to start: send nothing for 60 seconds and the client gets `504 Gateway Time-out` and the request is cancelled. Send the first bytes early, keep data flowing rather than letting a started stream sit idle, and have a long-lived client reconnect instead of holding one connection open. See [Request timeout](/compute/request-timeout).
- **Next.js pages that call `service.load()` need `export const dynamic = 'force-dynamic'`.** The runtime environment does not exist at build time, and Next.js will not re-read it for prerendered routes.

## Driving deploys from code

Everything the CLI does is also callable in-process, from `@prisma/composer/control`: typed `deploy`, `destroy`, `dev`, and `log` operations that return structured results instead of printing and exiting. The operations and their result shapes are documented in [the control API](/cli/deploy#the-control-api) on the `deploy` command reference.
