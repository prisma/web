Use [Alchemy](https://alchemy.run/) and its [`@alchemy.run/prisma`](https://github.com/alchemy-run/alchemy/tree/main/packages/prisma) package to create Prisma Postgres databases and deploy applications to Prisma Compute from one `alchemy.run.ts` file.

[Alchemy Prisma docs](https://alchemy.run/prisma/) · [Package source](https://github.com/alchemy-run/alchemy/tree/main/packages/prisma) · [Examples](https://github.com/alchemy-run/alchemy/tree/main/examples) · [npm](https://www.npmjs.com/package/@alchemy.run/prisma)

:::note

The Prisma resources moved out of the `alchemy` package into `@alchemy.run/prisma`. If your stack imports from `alchemy/Prisma`, install `@alchemy.run/prisma` and import from it instead. The resource names are unchanged.

:::

## Deploy Postgres and Compute

### 1. Install and authenticate

Alchemy runs on Node.js 24.11.1 or later, or on Bun. Install Alchemy, the Prisma package, and Effect:

```npm title="Terminal"
npm install alchemy @alchemy.run/prisma effect @effect/platform-node
printf '\n.alchemy/\n' >> .gitignore
```

Keep the versions of `effect` and the `@effect/*` packages aligned with the version Alchemy depends on.

Create a Prisma [service token](/rest-api/authentication#service-tokens) in your workspace settings, then add Prisma to your local Alchemy profile:

```npm title="Terminal"
npx alchemy profile edit --add Prisma
```

Paste the token when prompted. Alchemy stores it under `~/.alchemy/credentials/<profile>/`.

In CI (when `CI=true`), Alchemy skips profiles and reads the token from the environment instead. Set `PRISMA_SERVICE_TOKEN` (or `PRISMA_API_TOKEN`):

```bash title="Terminal"
export PRISMA_SERVICE_TOKEN="<your-service-token>"
```

`alchemy dev` runs everything locally and does not need a Prisma token.

### 2. Create the stack

```ts title="alchemy.run.ts"
import * as Prisma from "@alchemy.run/prisma";
import * as Alchemy from "alchemy";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "MyApp",
  {
    providers: Prisma.providers(),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const project = yield* Prisma.Project("Project", {
      createDatabase: false,
      region: "us-east-1",
    });

    const postgres = yield* Prisma.Postgres("Postgres", {
      project,
      region: "us-east-1",
    });

    const connection = yield* Prisma.Connection("Connection", {
      database: postgres,
    });

    const app = yield* Prisma.Compute("App", {
      project,
      build: "auto",
      env: {
        DATABASE_URL: connection.databaseUrl,
      },
    });

    return { url: app.url };
  }),
);
```

`Prisma.Postgres` is an alias for `Prisma.Database`. `connection.databaseUrl` is the pooled connection string, which is the right choice for application traffic. `connection.directConnectionString` is the direct one, for migrations and other tooling.

`build: "auto"` builds the application in the current directory (or in `path`) and detects Next.js, Nuxt, Astro, NestJS, TanStack Start, Vite, and Bun applications, in that order. Each framework must produce deployable server output:

- **Next.js**: set `output: "standalone"` in `next.config`.
- **Nuxt**: keep the default `node-server` Nitro preset.
- **Astro**: install `@astrojs/node` and use `adapter: node({ mode: "standalone" })`.
- **TanStack Start**: add the Nitro plugin to `vite.config` with its default node preset.
- **Vite**: the `dist` output is served as a single-page app.
- **Bun**: set `entrypoint` on the resource or `main` in `package.json`.

To force one strategy, pass `build: { type: "auto", framework: "nextjs" }`. To run your own build, pass `build: { command, outdir, entrypoint }`. To upload a directory that is already built, pass `build: false`. Set `port` if your server listens on a port other than the framework's default.

### 3. Deploy and verify

```npm title="Terminal"
npx alchemy deploy
curl "<url-from-stack-output>"
```

Alchemy shows the plan, creates the project, database, connection, and Compute deployment, and prints the stack output. Copy the printed `url` into the `curl` command.

Run `alchemy deploy` again after changing your application or infrastructure. Alchemy only updates what changed.

Without `--stage`, `alchemy deploy` deploys to `$ALCHEMY_STAGE` or, when that is unset, to a stage named `live_<your-username>`. Pass `--stage` to choose one, for example `npx alchemy deploy --stage production`.

## Default or explicit database

The stack above sets `createDatabase: false` and declares its database explicitly, so the database and connection are separate resources you can reference.

Alternatively, let the project create its default database:

```ts title="Default database"
const project = yield* Prisma.Project("Project", {
  region: "us-east-1",
});

const app = yield* Prisma.Compute("App", {
  project,
  build: "auto",
});
```

:::warning

Prisma injects the default database's `DATABASE_URL` into the application. Do not set `DATABASE_URL` in `env` when you use the default database. Alchemy rejects keys that Prisma manages.

:::

## Schema migrations

Alchemy does not migrate your schema unless you add migration resources to the stack. For Prisma ORM 8, `Prisma.Contract` runs `prisma contract emit` (and plans a migration when the contract has changed), and `Prisma.Migrate` applies pending migrations to the database:

```ts title="alchemy.run.ts"
const contract = yield* Prisma.Contract("Contract");

const migrate = yield* Prisma.Migrate("Migrate", {
  url: connection.directConnectionString,
  contract,
});
```

`Prisma.Contract` reads `./prisma.config.ts` and the `./migrations` directory by default. Set `config` and `migrationsDir` if yours live elsewhere. Applying migrations is idempotent. Removing either resource from the stack leaves your database, emitted contract, and migrations untouched.

Alchemy orders resources by the outputs they reference. To make sure migrations finish before Compute builds a new deployment, reference an output of `migrate` from the Compute resource, for example in the build environment:

```ts title="alchemy.run.ts"
const app = yield* Prisma.Compute("App", {
  project,
  build: {
    type: "auto",
    env: { SCHEMA_MARKER: migrate.markerHash },
  },
  env: {
    DATABASE_URL: connection.databaseUrl,
  },
});
```

If you migrate another way, run your migrations against `connection.directConnectionString` before you deploy the application. See [Migrations](/orm/migrations/how-migrations-work) for how Prisma ORM plans and applies them.

## Local development

Configure the local app process alongside the database:

```ts title="alchemy.run.ts"
const postgres = yield* Prisma.Postgres("Postgres", {
  project,
  dev: {
    persistenceMode: "stateful",
    migrate: "npm run db:setup",
  },
});

const connection = yield* Prisma.Connection("Connection", {
  database: postgres,
});

const app = yield* Prisma.Compute("App", {
  project,
  build: "auto",
  env: {
    DATABASE_URL: connection.databaseUrl,
  },
  dev: {
    command: "npm run dev",
    port: 3000,
  },
});
```

```npm title="Terminal"
npx alchemy dev
```

`alchemy dev` starts a local Prisma Postgres server with `@prisma/dev`, runs the `dev.migrate` command once the database is ready, and then starts your app with the configured `dev.command`. The connection returns local connection strings, so the app reads the same `DATABASE_URL` locally and in production. Use `dev.env` on `Prisma.Compute` for values that apply only locally.

## Production options

Set an application directory, a health check, and old-deployment cleanup when needed:

```ts title="alchemy.run.ts"
const app = yield* Prisma.Compute("App", {
  project,
  path: "./apps/web",
  build: "auto",
  env: {
    DATABASE_URL: connection.databaseUrl,
  },
  healthCheck: {
    path: "/api/health",
  },
  destroyOldDeployment: true,
});

const domain = yield* Prisma.CustomDomain("Domain", {
  app,
  hostname: "app.example.com",
});

return {
  url: app.url,
  dnsRecords: domain.dnsRecords,
};
```

- `healthCheck` makes Alchemy request the path on the new deployment before promoting it and on the stable URL afterward. Any `2xx` response counts as healthy unless you set `statusCodes`.
- `destroyOldDeployment` deletes the previous deployment after the new one is promoted.
- `env` values are stored in Alchemy state. Wrap secrets in `Redacted.make(...)` from `effect/Redacted`.

Prisma checks the domain's `CNAME` record when the custom domain is created. Before deploying, point `app.example.com` at your app's regional endpoint, `switchboard.<region>.prisma.build`. The returned `dnsRecords` list the records Prisma expects. Certificate provisioning continues after the deploy, so check the domain's `status` before you send production traffic to it.

The package also exports `Prisma.Website` constructors, such as `Prisma.Website.Nextjs`, for framework sites. See the [examples](https://github.com/alchemy-run/alchemy/tree/main/examples) whose names start with `prisma-website-`.

## CI and cleanup

```npm title="CI"
npx alchemy deploy --stage "pr-${PR_NUMBER}" --yes
npx alchemy destroy --stage "pr-${PR_NUMBER}" --yes
```

Use a unique preview stage for each pull request and destroy that same stage when it closes. Cleanup must never target your production stage.

Replace `Alchemy.localState()` with a shared [Alchemy state store](https://alchemy.run/state-store/) before deploying from CI or as a team. Local state is only suitable when one machine owns the stack. State can contain database credentials, so never commit `.alchemy/`.

`alchemy destroy` deletes the stack's Compute apps and then the Prisma project, including its databases.
