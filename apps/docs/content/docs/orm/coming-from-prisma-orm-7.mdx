If you know Prisma ORM 7, this page tells you what each thing you already use is called in Prisma ORM 8. It is a lookup table, not a tutorial: one table each for the schema, the command-line tool, and the query API, and a final list of what is not available yet.

To move a running application, follow [Migrate from Prisma ORM 7 to 8](/guides/upgrade-prisma-orm/postgresql) instead. It runs both versions side by side against the same database and moves one part of the app at a time. To decide whether to move at all, see [Release status](/prisma-orm/release-status).

All examples use PostgreSQL.

## Before you start

Install the two packages and let `orm init` set the project up. It writes `prisma.config.ts`, a starter `src/prisma/contract.prisma`, and `src/prisma/db.ts`, and installs `dotenv`:

```npm
npm install --save-dev prisma
npm install @prisma/orm-postgres
npx prisma orm init
```

Every query example on this page imports `db` from that `src/prisma/db.ts`; the file is shown under [Queries](#queries).

Two things to know first:

- The starter contract `orm init` writes is a placeholder. For an existing database, generate your contract from it with `npx prisma contract infer`, then check the result against the schema table below. For a schema you want to convert by hand, the same table is the mapping.
- In a project that still runs Prisma ORM 7, do not install `prisma` at version 8 on its own: it replaces the version 7 command-line tool. [Release status](/prisma-orm/release-status) shows how to install both.

## Schema

`schema.prisma` is now `src/prisma/contract.prisma`. It is the same file, renamed: you still describe your models in it. (In Prisma ORM 8 docs, "schema" means the live database structure. See [Core concepts](/orm/core-concepts).)

The biggest visible change is that database types are written as the type itself. Where Prisma ORM 7 wrote `String @db.VarChar(255)`, Prisma ORM 8 writes `VarChar(255)`.

| Prisma ORM 7 | Prisma ORM 8 | Notes |
| --- | --- | --- |
| `schema.prisma` | `contract.prisma` | |
| (nothing) | `// use prisma-next` as the first line | `orm init` writes it; keep it, because your editor's Prisma extension ignores contract files without it. Not a typo |
| `generator client { ... }` | removed | `prisma contract emit` writes two files next to your contract, `contract.json` and `contract.d.ts`. Commit both |
| `datasource db { ... }` | the `orm` section of `prisma.config.ts` | the connection string and file paths live in the config file, not the schema. Example below |
| `String @db.Text` | `String` | `String` is already stored as `text`. The error message for a removed `@db.*` attribute may suggest `Text`; there is no `Text` type, `String` is the answer |
| `String @db.VarChar(255)` | `VarChar(255)` | |
| `Decimal @db.Decimal(10, 2)` | `Numeric(10, 2)` | plain `Decimal` still exists when you do not need a precision and scale |
| `String @db.Uuid` | `Uuid` | |
| `DateTime` | `DateTime` | same name, but values come back as `Temporal.Instant` objects instead of JavaScript `Date`. See the note below the table |
| `DateTime @updatedAt` | `updatedAt temporal.updatedAt()` | set on create and on every update. `temporal.` is built into the schema language; there is nothing to import |
| `DateTime @default(now())` | `DateTime @default(now())`, or `createdAt temporal.createdAt()` | both work |
| `String @default(cuid())` | `String @default(cuid(2))` | plain `cuid()` is rejected; the error message tells you to use `cuid(2)` |
| `Json` | `Jsonb` | use `Jsonb`. It is what a Prisma ORM 7 `Json` column was; in Prisma ORM 8 the name `Json` means the older `json` type |
| `enum Role { ADMIN USER }`, in a new database | `enum Role { ADMIN USER }` | same syntax; the column is stored as text now, not as a PostgreSQL enum type. You can give members explicit values (`ADMIN = "admin"`) |
| `enum Role { ADMIN USER }`, in an existing Prisma ORM 7 database | `native_enum Role { ... }`, used in a field as `pg.enum(Role)` | your database already has a PostgreSQL enum type for it; `native_enum` keeps it. `pg.` is built into the schema language, like `temporal.` |
| `String[]` | `String[]` | unchanged on PostgreSQL. The list filters (`has`, `hasEvery`, `hasSome`, `isEmpty`) are not available yet; see below |
| implicit many-to-many (`Post[]` on `Tag` and `Tag[]` on `Post`, with no model for the join table) | the same two list fields, plus a model for the join table | you write the join table as a model yourself; example below. `.include("tags")` gives you `post.tags` as a `Tag[]`; writes with `connect` and `disconnect` work; `set` does not (see [Not available yet](#not-available-yet)) |
| `@id`, `@unique`, `@default`, `@relation`, `@map`, `@@map`, `@@index`, `@@id`, `@@unique` | unchanged | |

:::note[DateTime values and Node.js versions]

A `DateTime` column is read as a `Temporal.Instant`, not a JavaScript `Date`. Node.js 26 and later have `Temporal` built in (Homebrew's build of Node.js 26 does not; run `node -p "typeof Temporal"` to check). On Node.js 25 and earlier, which includes the supported 22 and 24 lines, this applies to every `DateTime` column: install `temporal-polyfill` and add `import "temporal-polyfill/full/global"` at the top of `src/prisma/db.ts`, or declare the column as `TimestamptzString` to read and write it as text. Nothing changes in the database either way.

:::

A many-to-many relation keeps the two list fields and adds a model for the join table:

```prisma title="src/prisma/contract.prisma"
model Post {
  id   Int    @id @default(autoincrement())
  tags Tag[]
}

model Tag {
  id    Int    @id @default(autoincrement())
  posts Post[]
}

model PostTag {
  postId Int
  tagId  Int
  post   Post @relation(fields: [postId], references: [id])
  tag    Tag  @relation(fields: [tagId], references: [id])

  @@id([postId, tagId])
}
```

That is complete as written. You do not add a `PostTag[]` field to `Post` or `Tag`: Prisma ORM 8 finds the join table from its two foreign keys.

The config file replaces the `generator` and `datasource` blocks. This one is for PostgreSQL:

```ts title="prisma.config.ts"
import { definePrismaConfig } from "prisma/config";
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.prisma",
    db: {
      connection: process.env.DATABASE_URL!,
    },
  }),
});
```

The `orm` section takes `contract` (the path to your contract) and `db` (the connection), and optionally `output` (where `contract.json` and `contract.d.ts` are written; next to the contract by default), `extensions` (database extensions such as pgvector), and `migrations` (where migration files are kept; `migrations/` by default). There is no `provider` setting: for MongoDB you import `ormConfig` from `@prisma/orm-mongo/config` instead. You can also write the contract in TypeScript instead of the schema language by pointing `contract` at a `.ts` file; this page shows the schema language.

## Commands

The Prisma ORM 8 command-line tool groups commands by what they act on: `contract` for your contract file, `db` for the database you are connected to, and `migration` for the migration files in your repository.

| Prisma ORM 7 | Prisma ORM 8 | Notes |
| --- | --- | --- |
| `prisma generate` | `prisma contract emit` | run it after every change to the contract. It writes `contract.json` and `contract.d.ts`; commit both |
| `prisma migrate dev` | `prisma db update` while you are iterating, or `prisma migration plan` followed by `prisma db migrate` when you want a migration file | `db update` changes the database to match your contract directly. `migration plan` writes a folder under `migrations/app/` with a `migration.ts` you can read, edit, and commit; `db migrate` applies it. See [Generating a migration](/orm/migrations/generating-a-migration) |
| `prisma migrate deploy` | `prisma db migrate` | applies the migration files in your repository |
| `prisma db push` | `prisma db init` the first time, on an empty database; `prisma db update` after that | `db init` creates the tables; `db update` changes existing tables to match the contract. See [`db update`](/cli/db-update) |
| `prisma db pull` | `prisma contract infer` | writes a first draft of a contract from an existing database |
| `prisma migrate diff` | `prisma migration plan --from <migration directory>`, and `--to <migration directory>` to diff two migrations | a migration directory is a folder under `migrations/app/`, for example `migrations/app/20260911T1030_add_bio`. The difference is written as a migration file rather than printed. Without `--to`, the target is your current contract. To check whether the database matches your contract without writing anything, use `prisma db verify` |
| `prisma migrate resolve --applied` | see [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) | for a migration that failed half way |
| `prisma migrate resolve` for a database that already matches your schema | `prisma db sign`, then `prisma migration ref set db <migration directory>` | `db sign` records in the database that it matches your contract. The second command sets the `db` ref, a marker in your repository that says which migration the database is at, so the next `prisma migration plan` continues from it |
| `prisma db seed` | none | there is no seed command. Write a script that imports `db` from `src/prisma/db.ts` and calls `.create(...)`, and run it the way you run any TypeScript file, for example `npx tsx src/prisma/seed.ts` |
| `prisma studio` | none in the Prisma ORM 8 tool | run Studio from the Prisma ORM 7 tool with a connection string: `npx prisma@7 studio --url "$DATABASE_URL"`. Run it from a directory outside your project, because the version 7 tool would otherwise try to read your version 8 `prisma.config.ts` and fail. See [Studio with Prisma ORM](/studio/prisma-next) |
| `prisma format` | `prisma contract format` | |
| `prisma validate` | none | `prisma contract emit` fails if the contract is invalid, and `prisma db verify` checks it against the database |

Day to day, the loop that replaces `prisma migrate dev` is: edit the contract, run `prisma contract emit`, then `prisma db update` to apply the change to your development database. When you want a migration file to commit, run `prisma migration plan` instead of `db update`, then `prisma db migrate` to apply it.

New commands with no Prisma ORM 7 counterpart, the four you will meet first:

- `prisma orm init` sets up Prisma ORM 8 in an existing project: config file, starter contract, and `db.ts`. Run it first (see [Before you start](#before-you-start)).
- `prisma db init` creates the tables for your contract in an empty database. (`db update` is for a database that already has tables.)
- `prisma db verify` checks whether the database still matches your contract.
- `prisma db sign` records in the database that it matches your contract.

The rest are in the [CLI reference](/cli).

## Queries

Instead of a generated `PrismaClient`, you create the client yourself in one file, `src/prisma/db.ts`, from the two files `prisma contract emit` wrote:

```ts title="src/prisma/db.ts"
import "dotenv/config";
import postgres from "@prisma/orm-postgres/runtime";
import type { Contract } from "./contract.d";
import contractJson from "./contract.json" with { type: "json" };

export const db = postgres<Contract>({
  contractJson,
  url: process.env.DATABASE_URL!,
});
```

`prisma orm init` writes this file for you. Every example below imports `db` from it.

On `db`: `db.orm` holds your models. `db.raw.sql` builds a raw SQL query and `db.runtime().query()` runs it. `db.transaction` runs several queries in one transaction. To add middleware, add a `middleware: [...]` key to the `postgres({ ... })` call above.

A query is a chain of calls that ends with the call that runs it (`.all()`, `.first()`, `.create(...)`, and so on), instead of one method with one big options object.

| Prisma ORM 7 | Prisma ORM 8 |
| --- | --- |
| `new PrismaClient()` | `db`, from `src/prisma/db.ts` above |
| `prisma.user` | `db.orm.public.User` (`public` is the PostgreSQL schema; unless you set one up, every table is in `public`) |
| `findMany({ where })` | `.where(...).all()` |
| `findFirst({ where })` | `.where(...).first()`. Returns `null` when nothing matches. `.first({ id: 1 })` is a shortcut for `.where({ id: 1 }).first()` |
| `findUnique({ where })` | `.where(...).first()`, and check for `null` |
| `where: { id: 1, active: true }` | `.where({ id: 1, active: true })`; for comparisons, `.where((u) => u.age.gt(18))` |
| `select: { id: true, email: true }` | `.select("id", "email")` |
| `include: { posts: true, where: ... }` | `.include("posts")`, or `.include("posts", (posts) => posts.where({ published: true }))` to filter or sort the related records |
| `where: { name: { contains: "ali" } }` | `.where((u) => u.name.like("%ali%"))`; see [Not available yet](#not-available-yet) for `startsWith` and case-insensitive matching |
| `orderBy: { createdAt: "desc" }` | `.orderBy((u) => u.createdAt.desc())` |
| `take` / `skip` | `.limit(n)` / `.offset(n)` |
| `distinct: ["country"]` | `.distinct("country")` |
| `create({ data: { ... } })` | `.create({ ... })`, without the `data` wrapper |
| `create({ data: { ..., posts: { create: [...] } } })` | `.create({ ..., posts: (p) => p.create([...]) })`; `connect` works the same way |
| `createMany({ data: [...] })` | `.createAll([...])` to get the rows back, or `.createAndCount([...])` to get a count |
| `update({ where, data })` | `.where(...).update({ ... })` |
| `updateMany({ where, data })` | `.where(...).updateAll({ ... })` for the rows, or `.updateAndCount({ ... })` for a count |
| `delete({ where })` | `.where(...).delete()` |
| `deleteMany({ where })` | `.where(...).deleteAll()` for the rows, or `.deleteAndCount()` for a count |
| `upsert({ where, create, update })` | `.upsert({ create: { email: "a@b.c", name: "A" }, update: { name: "A" }, conflictOn: { email: "a@b.c" } })`. `conflictOn` is the unique field to match on. Leave it out to match on the primary key |
| `count({ where })` | `.where(...).aggregate((agg) => ({ total: agg.count() }))`, which returns one object, `{ total: 5 }` |
| `aggregate({ _sum, _avg })` | `.aggregate((agg) => ({ total: agg.sum("views"), average: agg.avg("views") }))` |
| `groupBy({ by, _count })` | `.groupBy("userId").aggregate((agg) => ({ count: agg.count() }))` |
| `$transaction(async (tx) => ...)` | `db.transaction(async (tx) => ...)`; inside, query through `tx.orm` instead of `db.orm` |
| `$queryRaw` | see the raw SQL example below |
| `$executeRaw` | see the raw SQL example below |
| `$connect()` | `db.connect()`. You rarely need it: the client connects on the first query |
| `$disconnect()` | `db.close()` |

On MongoDB the accessor uses the collection name and has no schema part: `db.orm.users`.

### Find with a filter

```ts title="Prisma ORM 7"
const users = await prisma.user.findMany({
  where: { active: true },
  select: { id: true, email: true },
  orderBy: { createdAt: "desc" },
  take: 10,
});
```

```ts title="Prisma ORM 8"
import { db } from "./prisma/db";

const users = await db.orm.public.User
  .where({ active: true })
  .select("id", "email")
  .orderBy((u) => u.createdAt.desc())
  .limit(10)
  .all();
```

### Create a record

```ts title="Prisma ORM 7"
const user = await prisma.user.create({
  data: { email: "alice@prisma.io", name: "Alice" },
});
```

```ts title="Prisma ORM 8"
const user = await db.orm.public.User.create({
  email: "alice@prisma.io",
  name: "Alice",
});
```

### Raw SQL

```ts title="Prisma ORM 7"
const rows = await prisma.$queryRaw`SELECT id, email FROM "user" WHERE active = true`;
await prisma.$executeRaw`UPDATE "user" SET active = false WHERE id = ${id}`;
```

```ts title="Prisma ORM 8"
// Build the query with db.raw.sql, run it with db.runtime().query().
// A query that returns rows must say what type each column is.
const select = db.raw.sql`SELECT id, email FROM "user" WHERE active = true`
  .returnsRow({ id: "pg/int4@1", email: "pg/text@1" })
  .build();
const rows = await db.runtime().query(select);

// A statement that changes rows: ask for the count.
const update = db.raw.sql`UPDATE "user" SET active = false WHERE id = ${id}`
  .affectedCount()
  .build();
await db.runtime().execute(update);
```

The rule: every raw query that returns rows needs `.returnsRow(...)` with a type per column. For a column that exists in your contract, reuse its type instead of spelling one out: `returnsRow({ id: user.columns.id, email: user.columns.email })` where `const user = db.sql.public.user`. Spell out a type such as `pg/int4@1` (always `@1` today) only for a computed column; [Raw queries](/orm/reference/raw-queries) lists them.

### Transaction

```ts title="Prisma ORM 7"
const [user, post] = await prisma.$transaction([
  prisma.user.create({ data: { email: "jane@prisma.io" } }),
  prisma.post.create({ data: { title: "Hello" } }),
]);
```

```ts title="Prisma ORM 8"
const result = await db.transaction(async (tx) => {
  const user = await tx.orm.public.User.create({ email: "jane@prisma.io" });
  const post = await tx.orm.public.Post.create({ title: "Hello", authorId: user.id });
  return { user, post };
});
```

## Not available yet

Prisma ORM 7 features that have no direct form in Prisma ORM 8 today, with what to do instead.

| Prisma ORM 7 feature | Status | What to do instead |
| --- | --- | --- |
| `createMany({ skipDuplicates: true })` | available in a different form | `.upsert({ create, update: {}, conflictOn })` one row at a time skips rows that already exist. There is no batch form |
| `{ increment: n }` / `{ decrement: n }` in an update | not available | write the arithmetic as raw SQL (see the example above), or read the value and write it back inside `db.transaction(...)` |
| `findUniqueOrThrow` / `findFirstOrThrow` | not available on the query | the usual form is `.first()` and a `null` check. If you want the throw, `.where({ id }).all().firstOrThrow()` throws `RUNTIME.NO_ROWS` when nothing matches; it fetches every matching row first, so only with a unique `where` |
| `mode: "insensitive"` | available in a different form | on PostgreSQL, `.ilike("%alice%")` on a text field. You write the `%` wildcards yourself |
| `contains` / `startsWith` / `endsWith` | available in a different form | `.like("alice%")` with `%` wildcards |
| filtering inside JSON (`path`, `string_contains`, `array_contains`) | not available | a `Jsonb` field can only be compared as a whole (`eq`, `neq`, `in`, `notIn`) or checked for null. Write the query as raw SQL (see the example above) |
| `$transaction([...])` with an array of queries | available in a different form | `db.transaction(async (tx) => ...)`; the queries inside run one after another |
| `Prisma.UserGetPayload<...>` and the generated model types | one named type today; more in the next release | query results are typed as you write them (`.select("id", "email")` gives `{ id, email }`). What is missing is a way to name such a type for reuse: today `DefaultModelRow<Contract, "User">` from `contract.d.ts` names a full row; named types for `select` and `include` results come in the release after rc.9 |
| implicit many-to-many relations | available in a different form | write the join table as a model; see the example under [Schema](#schema) |
| `@@map` on an `enum` | not available | an `enum` cannot be renamed in the database. If you need a real PostgreSQL enum type with a specific name, declare it with `native_enum`, which does accept `@@map` |
| `$use` middleware | available in a different form | pass `middleware: [...]` when you create the client in `db.ts`. Your function receives each query before it runs and can log it, change it, or block it; there is no `params.model` or `params.action`. [How middleware works](/orm/middleware/how-middleware-works) shows the function's shape |
| `$extends` (computed fields, custom model methods, query wrapping) | not available | compute derived values in your own code after the query, and put custom model methods in your own functions. (Prisma ORM 8 has something also called extensions, which add database types such as pgvector; it is not a replacement for `$extends`.) |

Also not available today:

- Nested writes other than create and connect: `connectOrCreate`, nested `update`, `updateMany`, `upsert`, `delete`, `deleteMany`, and `set` on a relation. Change the related rows through their own model instead, for example `db.orm.public.Post.where({ authorId }).updateAll({ ... })`, inside `db.transaction(...)` if it must be atomic.
- The list filters `has`, `hasEvery`, `hasSome`, and `isEmpty` on `String[]` and other list fields (the fields themselves work).
- Transaction options: `isolationLevel`, `timeout`, `maxWait`, and transactions inside transactions.
- `omit`, `relationLoadStrategy`, `Prisma.skip`, and the automatic batching of `findUnique` calls.
- The `P2002` / `P2025` style error codes. Errors carry a `code` such as `RUNTIME.NO_ROWS` instead, and a database error such as a unique-constraint violation carries the PostgreSQL code in `error.sqlState` (`23505` for a unique violation), so catch it with `if (error instanceof Error && "sqlState" in error && error.sqlState === "23505")`. See the [error reference](/orm/reference/error-reference).
- `Prisma.sql`, `Prisma.join`, `Prisma.raw`, `Prisma.empty`, and TypedSQL. Use `db.raw.sql` (example above); [Raw queries](/orm/reference/raw-queries) covers building a query from pieces.
- Soft delete, declarative validations, lifecycle hooks on models, and read replicas. For soft delete, add a nullable `deletedAt` field and filter on it. Validate in your application code. Use middleware for hooks. For read replicas, create one client per database.
