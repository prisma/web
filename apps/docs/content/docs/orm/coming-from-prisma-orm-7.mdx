If you know Prisma ORM 7, this page tells you what each thing you already use is called in Prisma ORM 8. It is a lookup table, not a tutorial: one table each for the schema, the command-line tool, and the query API, and a final list of what is not available yet.

To move a running application, follow [Migrate from Prisma ORM 7 to 8](/guides/upgrade-prisma-orm/postgresql) instead. It runs both versions side by side against the same database and moves one part of the app at a time. To decide whether to move at all, see [Release status](/prisma-orm/release-status).

All examples use PostgreSQL.

## Schema

Your `schema.prisma` becomes `contract.prisma`. The file is now called a contract because it describes the agreement between your code and the database; "schema" is reserved for what the database actually has. See [Core concepts](/orm/core-concepts).

The biggest visible change is that database types are written as the type itself. Where Prisma ORM 7 wrote `String @db.VarChar(255)`, Prisma ORM 8 writes `VarChar(255)`.

| Prisma ORM 7 | Prisma ORM 8 | Notes |
| --- | --- | --- |
| `schema.prisma` | `contract.prisma` | |
| (nothing) | `// use prisma-next` as the first line | marks the file as a Prisma ORM 8 contract so your editor's Prisma extension knows how to treat it |
| `generator client { ... }` | removed | nothing is generated into `node_modules`. Instead, `prisma contract emit` writes two files next to your contract, `contract.json` and `contract.d.ts`, and you commit both |
| `datasource db { ... }` | the `orm` section of `prisma.config.ts` | the connection string and file paths live in the config file, not the schema. Example below |
| `String @db.Text` | `String` | `String` is already stored as `text`. If an error message suggests writing `Text`, ignore it: there is no `Text` type, `String` is the answer |
| `String @db.VarChar(255)` | `VarChar(255)` | |
| `Decimal @db.Decimal(10, 2)` | `Numeric(10, 2)` | plain `Decimal` still exists when you do not need a precision and scale |
| `String @db.Uuid` | `Uuid` | |
| `DateTime` | `DateTime` | same name. Values are read as `Temporal.Instant` objects, not JavaScript `Date`. Node.js 26 and later have `Temporal` built in (except Homebrew's build of Node.js 26). On Node.js 25 and earlier, add `import "temporal-polyfill/full/global"` before your first query, or use `TimestamptzString` to read and write the value as text |
| `DateTime @updatedAt` | `updatedAt temporal.updatedAt()` | set on create and on every update |
| `DateTime @default(now())` | `DateTime @default(now())`, or `createdAt temporal.createdAt()` | both work |
| `String @default(cuid())` | `String @default(cuid(2))` | plain `cuid()` is rejected; the error message tells you to use `cuid(2)` |
| `Json` | `Jsonb` | in Prisma ORM 7, `Json` was stored as `jsonb`. In Prisma ORM 8, `Jsonb` means `jsonb` and `Json` means the older `json` type. You almost always want `Jsonb` |
| `enum Role { ADMIN USER }` | `enum Role { ADMIN USER }` | unchanged. Stored as text with a check constraint. You can give members explicit values (`ADMIN = "admin"`) if you want |
| an enum stored as a PostgreSQL enum type | `native_enum Role { ... }`, used in a field as `pg.enum(Role)` | a real PostgreSQL enum type is declared with its own keyword |
| `String[]` | `String[]` | unchanged on PostgreSQL. The list filters (`has`, `hasEvery`, `hasSome`, `isEmpty`) are not available yet; see below |
| implicit many-to-many (`Post[]` on `Tag` and `Tag[]` on `Post`, with no model for the join table) | a model for the join table, with both foreign keys and `@@id([postId, tagId])` | you write the join table as a model yourself. The `Post[]` and `Tag[]` fields stay, and queries go through them as before |
| `@id`, `@unique`, `@default`, `@relation`, `@map`, `@@map`, `@@index`, `@@id`, `@@unique` | unchanged | |

The config file replaces the `generator` and `datasource` blocks:

```ts title="prisma.config.ts"
import { definePrismaConfig } from "prisma/config";
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.prisma",
    db: {
      connection: process.env.DATABASE_URL!,
    },
  }),
});
```

The `orm` section takes `contract` (the path to your contract; a `.ts` path means you write the contract in TypeScript instead of Prisma schema language), `db`, and optionally `output` (where the two emitted files go; next to the contract by default), `extensions`, and `migrations`. There is no `provider` setting; the database is chosen by the package you import the config from.

## Commands

The Prisma ORM 8 command-line tool groups commands by what they act on: `contract` for your contract file, `db` for the database you are connected to, and `migration` for the migration files in your repository.

| Prisma ORM 7 | Prisma ORM 8 | Notes |
| --- | --- | --- |
| `prisma generate` | `prisma contract emit` | run it after every change to the contract. It writes `contract.json` and `contract.d.ts`; commit both |
| `prisma migrate dev` | `prisma db update` while you are iterating, or `prisma migration plan` followed by `prisma db migrate` when you want a migration file | `db update` changes the database to match your contract directly. `migration plan` writes a migration file you can read and commit; `db migrate` applies it |
| `prisma migrate deploy` | `prisma db migrate` | applies the migration files in your repository |
| `prisma db push` | `prisma db update` | same job. See [`db update`](/cli/db-update) |
| `prisma db pull` | `prisma contract infer` | writes a first draft of a contract from an existing database |
| `prisma migrate diff` | `prisma migration plan --from <contract>` | the difference is written as a migration file rather than printed. To check whether the database matches your contract without writing anything, use `prisma db verify` |
| `prisma migrate resolve` | `prisma db sign`, then `prisma migration ref set db <hash>` | `db sign` records that the database matches your contract. The second command records where the next migration should start from |
| `prisma db seed` | none | there is no seed command. Write a script and run it yourself |
| `prisma studio` | none in the Prisma ORM 8 tool | run Studio from the Prisma ORM 7 tool with a connection string: `npx prisma@7 studio --url "$DATABASE_URL"`, from a directory outside your project. See [Studio with Prisma ORM](/studio/prisma-next) |
| `prisma format` | `prisma contract format` | |
| `prisma validate` | none | `prisma contract emit` fails if the contract is invalid, and `prisma db verify` checks it against the database |

New commands with no Prisma ORM 7 counterpart: `prisma orm init`, `prisma db init`, `prisma db sign`, `prisma db verify`, `prisma db schema`, and the `prisma migration` group (`new`, `check`, `graph`, `list`, `log`, `show`, `status`, and `ref list|set|delete`).

## Queries

Two things change at once. The client is created from your contract when the app starts, instead of being generated ahead of time. And a query is a chain of calls that ends with the call that runs it (`.all()`, `.first()`, `.create(...)`, and so on), instead of one method with one big options object.

| Prisma ORM 7 | Prisma ORM 8 |
| --- | --- |
| `new PrismaClient()` | `postgres<Contract>({ contractJson, url })` in `src/prisma/db.ts`, exported as `db` |
| `prisma.user` | `db.orm.public.User` (`public` is the PostgreSQL schema the table is in) |
| `findMany({ where })` | `.where(...).all()` |
| `findFirst({ where })` | `.where(...).first()`, or `.first({ ... })` |
| `findUnique({ where })` | `.where(...).first()` |
| `where: { id: 1, active: true }` | `.where({ id: 1, active: true })`; for comparisons, `.where((u) => u.age.gt(18))` |
| `select: { id: true, email: true }` | `.select("id", "email")` |
| `include: { posts: true }` | `.include("posts")`; a second argument lets you filter or sort the related records |
| `orderBy: { createdAt: "desc" }` | `.orderBy((u) => u.createdAt.desc())` |
| `take` / `skip` | `.limit(n)` / `.offset(n)` |
| `distinct: ["country"]` | `.distinct("country")` |
| `create({ data: { ... } })` | `.create({ ... })`, without the `data` wrapper |
| `createMany({ data: [...] })` | `.createAll([...])` to get the rows back, or `.createAndCount([...])` to get a count |
| `update({ where, data })` | `.where(...).update({ ... })` |
| `updateMany({ where, data })` | `.where(...).updateAll({ ... })` for the rows, or `.updateAndCount({ ... })` for a count |
| `delete({ where })` | `.where(...).delete()` |
| `deleteMany({ where })` | `.where(...).deleteAll()` for the rows, or `.deleteAndCount()` for a count |
| `upsert({ where, create, update })` | `.upsert({ create, update, conflictOn })`, where `conflictOn` names the unique field to match on, for example `conflictOn: { email: "a@b.c" }`. Leave it out to match on the primary key |
| `count({ where })` | `.where(...).aggregate((agg) => ({ total: agg.count() }))` |
| `aggregate({ _sum, _avg })` | `.aggregate((agg) => ({ total: agg.sum("views"), average: agg.avg("views") }))` |
| `groupBy({ by, _count })` | `.groupBy("userId").aggregate((agg) => ({ count: agg.count() }))` |
| `$transaction(async (tx) => ...)` | `db.transaction(async (tx) => ...)`; inside, query through `tx.orm` instead of `db.orm` |
| `$queryRaw` | ``db.raw.sql`...`.returnsRow(spec).build()``, then `db.runtime().query(plan)`. See [Raw queries](/orm/reference/raw-queries) |
| `$executeRaw` | ``db.raw.sql`...`.affectedCount().build()``, then `db.runtime().execute(plan)` |
| `$connect()` | `db.connect()`. You rarely need it: the client connects on the first query |
| `$disconnect()` | `db.close()` |

On MongoDB the accessor uses the collection name and has no schema part: `db.orm.users`.

### Find with a filter

```ts title="Prisma ORM 7"
const users = await prisma.user.findMany({
  where: { active: true },
  select: { id: true, email: true },
  orderBy: { createdAt: "desc" },
  take: 10,
});
```

```ts title="Prisma ORM 8"
import { db } from "./prisma/db";

const users = await db.orm.public.User
  .where({ active: true })
  .select("id", "email")
  .orderBy((u) => u.createdAt.desc())
  .limit(10)
  .all();
```

### Create a record

```ts title="Prisma ORM 7"
const user = await prisma.user.create({
  data: { email: "alice@prisma.io", name: "Alice" },
});
```

```ts title="Prisma ORM 8"
const user = await db.orm.public.User.create({
  email: "alice@prisma.io",
  name: "Alice",
});
```

### Transaction

```ts title="Prisma ORM 7"
const [user, post] = await prisma.$transaction([
  prisma.user.create({ data: { email: "jane@prisma.io" } }),
  prisma.post.create({ data: { title: "Hello" } }),
]);
```

```ts title="Prisma ORM 8"
const result = await db.transaction(async (tx) => {
  const user = await tx.orm.public.User.create({ email: "jane@prisma.io" });
  const post = await tx.orm.public.Post.create({ title: "Hello", authorId: user.id });
  return { user, post };
});
```

## Not available yet

Prisma ORM 7 features that have no direct form in Prisma ORM 8 today, with what to do instead.

| Prisma ORM 7 feature | Status | What to do instead |
| --- | --- | --- |
| `createMany({ skipDuplicates: true })` | not available | `.upsert({ create, update: {}, conflictOn })` one row at a time skips rows that already exist. There is no batch form |
| `{ increment: n }` / `{ decrement: n }` in an update | not available | write the arithmetic as raw SQL with `db.raw.sql`, or read the value and write it back inside `db.transaction(...)` |
| `findUniqueOrThrow` / `findFirstOrThrow` | available in a different form | `.all().firstOrThrow()` throws when nothing matches. It loads every matching row first, so narrow the query with `.where(...)` |
| `mode: "insensitive"` | available in a different form | on PostgreSQL, `.ilike("%alice%")` on a text field. You write the `%` wildcards yourself |
| `contains` / `startsWith` / `endsWith` | not available | `.like("alice%")` with `%` wildcards |
| filtering inside JSON (`path`, `string_contains`, `array_contains`) | not available | a `Jsonb` field can only be compared as a whole (`eq`, `neq`, `in`, `notIn`) or checked for null. Write the query as raw SQL with `db.raw.sql` |
| `$transaction([...])` with an array of queries | not available | `db.transaction(async (tx) => ...)`; the queries inside run one after another |
| `Prisma.UserGetPayload<...>` and the generated model types | coming in the next release after rc.9 | `contract.d.ts` will export a `Models` namespace, `Scalars<Model>` for a row without relations, `Shape<Model, Spec>` for the shape a given `select` or `include` returns, and `ResultType<Query>` for a query's result. On rc.9, `DefaultModelRow<Contract, "User">` gives you the full row |
| implicit many-to-many relations | not available | write the join table as a model, with both foreign keys and `@@id([aId, bId])`. The `Post[]` and `Tag[]` fields stay |
| `@@map` on an `enum` | not available | an `enum` cannot be renamed in the database. If you need a real PostgreSQL enum type with a specific name, declare it with `native_enum`, which does accept `@@map` |
| `$use` middleware | available in a different form | middleware is passed when you create the client, as `middleware: [...]`. It sees queries after they are built, not per model method. See [How middleware works](/orm/middleware/how-middleware-works) |
| `$extends` | not available | extensions add database types and operators to your contract rather than wrapping the client. See [Using extensions](/orm/extensions/using-extensions) |

Also not available today:

- Nested writes other than create and connect: `connectOrCreate`, nested `update`, `updateMany`, `upsert`, `delete`, `deleteMany`, and `set` on a relation.
- The list filters `has`, `hasEvery`, `hasSome`, and `isEmpty` on `String[]` and other list fields (the fields themselves work).
- Transaction options: `isolationLevel`, `timeout`, `maxWait`, and transactions inside transactions.
- `omit`, `relationLoadStrategy`, `Prisma.skip`, and the automatic batching of `findUnique` calls.
- The `P2002` / `P2025` style error codes. Errors carry a code such as `RUNTIME.NO_ROWS` instead. See the [error reference](/orm/reference/error-reference).
- `Prisma.sql`, `Prisma.join`, `Prisma.raw`, `Prisma.empty`, and TypedSQL. A `db.raw.sql` query that returns rows can be used inside another raw query, which covers most of what those did.
- Soft delete, declarative validations, lifecycle hooks on models, and read replicas. For soft delete, add a nullable `deletedAt` field and filter on it. Validate in your application code. Use middleware for hooks. For read replicas, create one client per database.
