Projects using Prisma Client can be deployed to many cloud platforms. Platforms differ in how they run your code, and that difference affects how you deploy an application that uses Prisma Client. This page describes the three deployment paradigms.

## Host the app and the database on one platform

Want the app and its PostgreSQL database in one place? [Prisma Compute](/compute) hosts TypeScript apps (Node.js, Bun or Next.js) next to [Prisma Postgres](/postgres) in one project, with one bill; create both in the same region. Once you [set up deploy on push](/compute/deploy-on-push), every pushed branch other than the default one gets a preview with its own services and a new database for each database declared in the app's [Prisma Composer](/composer) module; production data is not copied. If the app reads a connection string you set yourself, such as `DATABASE_URL`, a preview uses whatever database that value names, so don't give previews the production value. Compute runs apps that serve HTTP requests, with background work between requests bounded as described in [Limitations](/compute/limitations). See [Prisma Compute](/compute) to deploy.

## Keep your host, add a database

Deploying to Vercel, Netlify, Render, Fly.io or another host and need a hosted PostgreSQL database? Run `npx create-db@latest`: it prints a [Prisma Postgres](/postgres) connection string with no account and no card. Set it as `DATABASE_URL` on your host. The database is deleted after 72 hours unless it is claimed, so claim it from the claim URL in the output, for free, before you share the app. See [create-db](/postgres/npx-create-db).

## Deployment paradigms

Where your code runs changes how Prisma Client manages connections and what you pay for idle time.

The traffic pattern also counts: an application with steady traffic often suits a [continuously running server](#traditional-servers), and one with sudden spikes often suits [serverless](#serverless-functions).

### Traditional servers

Your application is [traditionally deployed](/orm/v7/prisma-client/deployment/traditional/deploy-to-heroku) if a Node.js process is continuously running and handles multiple requests at the same time. Your application could be deployed to a Platform-as-a-Service (PaaS) like [Heroku](/orm/v7/prisma-client/deployment/traditional/deploy-to-heroku), [Koyeb](/orm/v7/prisma-client/deployment/traditional/deploy-to-koyeb), or [Render](/orm/v7/prisma-client/deployment/traditional/deploy-to-render); as a Docker container to Kubernetes; or as a Node.js process on a virtual machine or bare metal server.

See also: [Connection management in long-running processes](/orm/v7/prisma-client/setup-and-configuration/databases-connections#long-running-processes)

### Serverless Functions

Your application is [serverless](/orm/v7/prisma-client/deployment/serverless/deploy-to-vercel) if the Node.js processes of your application (or subsets of it broken into functions) are started as requests come in, and each function only handles one request at a time. Your application would most likely be deployed to a Function-as-a-Service (FaaS) offering, such as [AWS Lambda](/orm/v7/prisma-client/deployment/serverless/deploy-to-aws-lambda) or [Azure Functions](/orm/v7/prisma-client/deployment/serverless/deploy-to-azure-functions)

Serverless environments have the concept of warm starts, which means that for subsequent invocations of the same function, it may use an already existing container that has the allocated processes, memory, file system (`/tmp` is writable on AWS Lambda), and even DB connection still available.

Typically, any piece of code [outside the handler](https://docs.aws.amazon.com/lambda/latest/dg/welcome.html) remains initialized.

See also: [Connection management in serverless environments](/orm/v7/prisma-client/setup-and-configuration/databases-connections#serverless-environments-faas)

### Edge Functions

Your application is [edge deployed](/orm/v7/prisma-client/deployment/edge/overview) if your application is [serverless](#serverless-functions) and the functions are distributed across one or more regions close to the user.

Typically, edge environments also have a different runtime than a traditional or serverless environment, leading to common APIs being unavailable.
