Prisma ORM 8 replaces `schema.prisma` with [a contract](/orm/contract-authoring/the-data-contract). You can write your contract in two forms. One is a `.prisma` file written in PSL, short for Prisma Schema Language. The other is TypeScript, in `src/prisma/contract.ts`, built with the `defineContract` builder. [`npx prisma contract emit`](/cli/contract-emit) writes `contract.json` and `contract.d.ts` beside the source, and both forms produce those same two files.

## When to choose TypeScript over PSL

[PSL](/orm/contract-authoring/psl-syntax) is the preferred way to write the contract. Both forms produce the same two files, so you give up nothing by staying with PSL. Use the TypeScript builder for the cases PSL does not cover. Reach for it when:

- model definitions must be split, composed, or reused across ordinary TypeScript modules or packages
- you want to build models in a loop from data you already keep in TypeScript, such as one model per entry in a list of table names

If neither applies, write PSL. It is more compact, and it is what [`contract infer`](/cli/contract-infer) writes.

## Point the config at the contract file

The config's `contract` path names the one file Prisma ORM reads. A `.ts` extension selects TypeScript authoring:

```typescript title="prisma.config.ts" tab="PostgreSQL"
import { definePrismaConfig } from "prisma/config";
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.ts",
  }),
});
```

```typescript title="prisma.config.ts" tab="MongoDB"
import { definePrismaConfig } from "prisma/config";
import { defineConfig as ormConfig } from "@prisma/orm-mongo/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.ts",
  }),
});
```

## A complete contract

The builder comes from your database's package: `@prisma/orm-postgres/contract-builder` for PostgreSQL, `@prisma/orm-mongo/contract-builder` for MongoDB.

Export the contract under the name `contract`, as below, or as the file's default export. `prisma contract emit` looks for those two names and nothing else.

```typescript title="src/prisma/contract.ts" tab="PostgreSQL"
import pgvector from "@prisma/orm-extension-pgvector/pack";
import { defineContract, enumType, member, rel } from "@prisma/orm-postgres/contract-builder";

const pgText = { codecId: "pg/text@1", nativeType: "text" } as const;

const Priority = enumType(
  "Priority",
  pgText,
  member("Low", "low"),
  member("High", "high"),
  member("Urgent", "urgent"),
);

export const contract = defineContract(
  {
    extensions: { pgvector },
  },
  ({ field, model, type }) => {
    const types = {
      Embedding1536: type.pgvector.Vector(1536),
    } as const;

    const User = model("User", {
      fields: {
        id: field.id.uuidv4String(),
        email: field.text(),
        createdAt: field.temporal.createdAt(),
        updatedAt: field.temporal.updatedAt(),
        address: field.json().optional(),
      },
    });

    const Post = model("Post", {
      fields: {
        id: field.id.uuidv4String(),
        title: field.text(),
        userId: field.uuidString(),
        priority: field.namedType(Priority).default(Priority.members.Low),
        createdAt: field.temporal.createdAt(),
        updatedAt: field.temporal.updatedAt(),
        embedding: field.namedType(types.Embedding1536).optional(),
      },
    });

    return {
      enums: { Priority },
      types,
      models: {
        User: User.relations({
          posts: rel.hasMany(Post, { by: "userId" }),
        }).sql({
          table: "user",
        }),
        Post: Post.relations({
          user: rel.belongsTo(User, { from: "userId", to: "id" }),
        }).sql(({ cols, constraints }) => ({
          table: "post",
          foreignKeys: [
            constraints.foreignKey(cols.userId, User.refs.id, {
              name: "post_userId_fkey",
            }),
          ],
        })),
      },
    };
  },
);
```

```typescript title="src/prisma/contract.ts" tab="MongoDB"
import { defineContract, field, model, rel } from "@prisma/orm-mongo/contract-builder";

const User = model("User", {
  collection: "users",
  fields: {
    _id: field.objectId(),
    name: field.string(),
    email: field.string(),
    bio: field.string().optional(),
  },
  relations: {
    posts: rel.hasMany("Post", { from: "_id", to: "authorId" }),
  },
});

const Post = model("Post", {
  collection: "posts",
  fields: {
    _id: field.objectId(),
    authorId: field.objectId(),
    title: field.string(),
    publishedAt: field.date().optional(),
  },
  relations: {
    author: rel.belongsTo(User, { from: "authorId", to: User.ref("_id") }),
  },
});

export const contract = defineContract({
  models: {
    User,
    Post,
  },
});
```

Run `npx prisma contract emit` after any change to refresh the two files.

## How `defineContract` works

You never pass the name of your database. It comes from the package you import.

On PostgreSQL, `defineContract` takes an options object and then a function. The options object lists the extension packs you use. The function returns the contract's content: `models`, plus `enums` and `types` if you have them. Its one argument gives you `field`, `model`, `rel`, and `type`. Those four come from the argument, not from imports. `type.pgvector` exists in the example only because `pgvector` is listed in `extensions`.

On MongoDB, `defineContract` takes a single object holding `models`, and you import `field`, `model`, and `rel` from the package instead. The MongoDB builder differs from the PostgreSQL one in four more ways. Every model declares an `_id` field built with `field.objectId()`, and that field is the primary key, so you never mark it with `.id()`. The scalar helpers are `field.objectId()`, `field.string()`, `field.int32()`, `field.double()`, `field.bool()`, and `field.date()`. The collection name and the relations are inline options on the model rather than chained calls. Relations name the field on each side, as in `rel.hasMany("Post", { from: "_id", to: "authorId" })`, and a field on another model is written `User.ref("_id")`.

The rest of this page uses the PostgreSQL builder.

## Fields

`field` has a helper for each column type. On PostgreSQL:

| Column | Helper |
| --- | --- |
| text | `field.text()` |
| integer | `field.int()` |
| big integer | `field.bigint()` |
| float | `field.float()` |
| decimal | `field.decimal()` |
| boolean | `field.boolean()` |
| date and time | `field.dateTime()` |
| bytes | `field.bytes()` |
| JSON | `field.json()` |
| UUID stored as text | `field.uuidString()` |
| UUID stored in a `uuid` column | `field.uuidNative()` |

There is no helper for a date without a time, or a time without a date. Extension packs add more helpers of their own.

For a primary key whose value your app generates, use `field.id.uuidv4String()`, `field.id.uuidv7String()`, `field.id.ulid()`, `field.id.nanoid()`, `field.id.cuid2()`, or `field.id.ksuid()`. Each one marks the field as the primary key for you. `field.id.uuidv4Native()` and `field.id.uuidv7Native()` do the same in a `uuid` column.

`field.temporal.createdAt()` fills the column with `now()` when the row is created. `field.temporal.updatedAt()` fills it on every create and every update.

`field.namedType(x)` takes an enum or a type from an extension pack.

Every field builder supports chained modifiers:

- `.optional()` makes the field nullable.
- `.default(value)` sets a literal default. `.defaultSql(expression)` sets a default the database computes, and the argument is a SQL expression as a string: `.defaultSql("now()")`.
- `.unique()` adds a unique constraint. `.id()` marks the primary key.
- `.column("column_name")` sets the column name in the database when it differs from the field name.

## Enums

`enumType` declares an enum, the type its values are stored as, and its members:

```typescript
const Priority = enumType(
  "Priority",
  { codecId: "pg/text@1", nativeType: "text" } as const,
  member("Low", "low"),
  member("High", "high"),
);
```

The second argument says how each member is stored. `codecId` is the type id, which is the PostgreSQL type plus a version, always `@1` today. [Raw queries](/orm/reference/raw-queries#binding-a-bare-value-with-param) shows more type ids. `nativeType` is the column type in the database. `as const` keeps both strings as literal types so the builder can check them.

Each `member(name, storedValue)` pairs the TypeScript-visible name with the value stored in the column. Fields reference the enum with `field.namedType(Priority)`, and defaults reference a member as `Priority.members.Low`. Include the enum in the returned `enums` map so it reaches the two files.

The TypeScript builder has no helper for a real PostgreSQL `enum` type. Members are stored in whatever column type you name here, `text` above. To get a PostgreSQL `enum` type, write the contract in PSL and use a `native_enum` block.

## Relations

Relations are declared on the model builder with `.relations(...)` and the `rel` helpers, as the full example above shows.

`rel.hasMany(Model, { by })` names the foreign key field on the other model. `rel.hasOne(Model, { by })` is the same with at most one row on the other side. `rel.belongsTo(Model, { from, to })` maps the local foreign key field to the field it points at.

`rel.manyToMany(Model, { through, from, to })` goes through a join table. You declare the model for the join table yourself and pass it as `through`. `from` and `to` name the two foreign key fields on that model:

```typescript
User.relations({
  teams: rel.manyToMany(Team, { through: Membership, from: "userId", to: "teamId" }),
});
```

`rel.belongsTo` on its own does not create a foreign key constraint in the database. Ask for one in either of two places. Chain `.sql({ fk: { name: "post_userId_fkey" } })` on the relation, or list `constraints.foreignKey(...)` in the model's `.sql({ foreignKeys: [...] })`, as the full example above does. Both forms take `name`, `onDelete`, and `onUpdate`.

`rel.hasMany`, `rel.hasOne`, `rel.belongsTo`, and `rel.manyToMany` also accept the model name as a string. Pass the model object, as above, and a typo is a compile error. Pass a string and the typo is reported when `prisma contract emit` builds the contract.

## Storage mapping

`.sql(...)` maps a model to its table. The object form covers the common case: `User.sql({ table: "user" })`.

`.relations(...)`, `.attributes(...)`, and `.sql(...)` are independent. A model with no relations calls `.sql({ table })` straight after `model(...)`.

The callback form gives you the model's columns as `cols` and the constraint builders as `constraints`. Use it for indexes and for foreign keys with explicit names:

```typescript
Post.relations({ ... }).sql(({ cols, constraints }) => ({
  table: "post",
  foreignKeys: [
    constraints.foreignKey(cols.userId, User.refs.id, { name: "post_userId_fkey" }),
  ],
  indexes: [
    constraints.index([cols.userId]),
    constraints.index([cols.userId, cols.createdAt], { name: "post_user_created_idx" }),
  ],
}));
```

`constraints.index` takes one column for a plain index and a list for a multi-column index. Add `{ unique: true }` to make it a unique index.

`Model.refs` provides typed references to another model's fields, so `User.refs.id` is checked against the actual `User` definition.

A primary key made of two fields is a model attribute rather than storage mapping. Chain `.attributes(...)` and build it from the field references:

```typescript
Membership.attributes(({ fields, constraints }) => ({
  id: constraints.id([fields.userId, fields.teamId]),
}));
```

`constraints.unique([fields.userId, fields.teamId])` in the same block makes a unique constraint across two fields. For a key made of one field, `.id()` on the field is enough, and the `field.id.*` helpers already do it.

## Extension types

Declare packs in `defineContract`'s options and the `type` helper exposes their constructors. The full example above imports `pgvector` from `@prisma/orm-extension-pgvector/pack`, lists it in `extensions`, builds `type.pgvector.Vector(1536)` in the returned `types` map, and uses it on a field with `field.namedType(types.Embedding1536)`.

Add the same pack to `prisma.config.ts`. It goes inside `ormConfig({ ... })`, beside `contract`, and the config imports the pack's `/control` export while the contract file imports its `/pack` export:

```typescript title="prisma.config.ts"
import { definePrismaConfig } from "prisma/config";
import pgvector from "@prisma/orm-extension-pgvector/control";
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.ts",
    extensions: [pgvector],
  }),
});
```

## Keep the contract file free of changing values [#keep-the-contract-file-pure]

The contract file describes structure. Three rules keep it usable:

- Do not read `process.env`, the current time, or random values into the contract. `prisma contract emit` writes the contract to JSON in a fixed key order and hashes it. A contract that changes per machine or per run breaks that hash and the checks that rely on it.
- Keep field values plain: strings, numbers, booleans, and the builder's own objects. Functions, class instances, and `Date` objects do not serialize.
- Keep the file free of side effects. `prisma contract emit` imports the file and reads its `default` or `contract` export, and nothing else. It runs the file, but it does not type-check it. Type errors show in your editor and when you run `tsc`.

Configuration that legitimately varies per environment, such as the database URL, belongs in `prisma.config.ts`, not in the contract.

## Parity with PSL

TypeScript and [PSL](/orm/contract-authoring/psl-syntax) authoring produce the same `contract.json` and `contract.d.ts` for an equivalent contract. You can move between the two forms without changing anything downstream. A project names exactly one contract file in its config.

No command converts a `.prisma` contract into TypeScript. To move an existing project, write the TypeScript file by hand, point `contract` in `prisma.config.ts` at it, and delete the `.prisma` file so the two can never disagree.
