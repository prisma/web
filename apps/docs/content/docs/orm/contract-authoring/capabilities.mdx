Your [contract](/orm/contract-authoring/the-data-contract), the `contract.prisma` file that replaced `schema.prisma`, describes your data. Not every database supports every feature: one setup can run lateral joins and `RETURNING` clauses, and another cannot. [`npx prisma contract emit`](/cli/contract-emit) writes `contract.json` and `contract.d.ts` beside your contract. The `capabilities` section of `contract.json` lists the database features your setup supports, and you never edit it. Prisma ORM reads that list before it uses one of those features. A feature your setup lacks fails right away, with an error that names the key for the missing feature, instead of reaching the database and failing there.

## Where the `capabilities` section comes from [#where-capabilities-come-from]

Three things each say which features they support: your database, your database package, and any extension packages listed in `prisma.config.ts`. Your database package is `@prisma/orm-postgres`, `@prisma/orm-sqlite`, or `@prisma/orm-mongo`, and you choose it by the import in `prisma.config.ts`. `npx prisma contract emit` collects all of those answers into `contract.json`, in groups:

```json title="src/prisma/contract.json (excerpt)"
{
  "capabilities": {
    "postgres": {
      "distinctOn": true,
      "pgvector.cosine": true
    },
    "sql": {
      "lateral": true,
      "scalarList": true
    }
  }
}
```

A key is written group first. The `pgvector.cosine` key under `postgres` is written `postgres.pgvector.cosine`. Keys under `sql` are shared across SQL databases, and keys under `postgres` belong to PostgreSQL only. Extension packages add keys of their own, and `pgvector.cosine` above comes from the pgvector package. Install it with `npm install @prisma/orm-extension-pgvector`, add these two lines to `prisma.config.ts`, and run `npx prisma contract emit` again:

```diff title="prisma.config.ts"
+ import pgvector from "@prisma/orm-extension-pgvector/control";

  orm: ormConfig({
    contract: "./src/prisma/contract.prisma",
+   extensions: [pgvector],
  }),
```

## What the `capabilities` section controls [#what-capabilities-gate]

Two errors tell you that a feature is missing. Both arrive before any SQL reaches the database.

**When the contract is built.** If your contract uses a feature your database cannot store, `npx prisma contract emit` fails. SQLite has no `scalarList` key, so a list field such as `tags String[]` fails on SQLite:

```text
Field "User.tags" is a scalar list, but target "sqlite" does not support
scalar lists (the adapter does not report the "scalarList" capability).
Remove the list or author it against a target that supports scalar lists.
```

In that message, "target" and "adapter" both mean your database package, which is `@prisma/orm-sqlite` here. Do one of the two: remove the list field, or switch to a database that supports list fields. To switch to PostgreSQL, change the import in `prisma.config.ts` from `@prisma/orm-sqlite/config` to `@prisma/orm-postgres/config`.

**When you call a query-builder method.** A method that needs a feature throws an error with code `ORM.CAPABILITY_MISSING`. The message names the method and the key:

```text
distinctOn() requires capability postgres.distinctOn
lateralJoin() requires capability sql.lateral
```

That message means the method is not available on the database you are connected to. Rewrite the query without it, or move to a database that supports the feature. If the key comes from an extension package, install that package, list it in `prisma.config.ts`, and run `npx prisma contract emit` again. The call throws as soon as you make it, so a test that calls it catches it.

Your own code can read the same list. `db` is the client you create once in `src/prisma/db.ts`, and it exposes the list as `db.contract.capabilities`. A whole group can be absent, so write `db.contract.capabilities.sql?.lateral`, which is `true` when lateral joins are available.

## Example keys [#example-capabilities]

A few of the keys your database, your database package, and the built-in extension packages supply:

| Key | What it covers |
| --- | --- |
| `sql.lateral` | Lateral joins (`lateralJoin()`) |
| `sql.returning` | `RETURNING` clauses on writes |
| `sql.scalarList` | List fields such as `tags String[]` |
| `postgres.distinctOn` | `DISTINCT ON` queries (`distinctOn()`) |
| `postgres.pgvector.cosine` | Cosine distance from the pgvector package |

PostgreSQL has all three `sql` keys above, and SQLite has none of them. This table is a sample, not the full list. Open `src/prisma/contract.json` in your project to see every key your setup supports.

The methods that need these keys exist only on the SQL query builder, and MongoDB does not have one, so nothing on MongoDB reads the `capabilities` section. The [ORM reference](/orm/reference) lists the methods each database has.

## The `capabilities` section and `prisma db verify` [#capabilities-and-verification]

The keys say what your installed software supports. They are recorded when you run `npx prisma contract emit`, not read from the live database, so the same contract behaves the same way in every environment. Checking the live database is a separate job. [`db verify`](/cli/db-verify) compares the database against your contract. Extension packages are the main source of keys beyond the built-in ones, and [using extensions](/orm/extensions/using-extensions) shows the full path from install to first query.
