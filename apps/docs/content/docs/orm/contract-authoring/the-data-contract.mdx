Every Prisma ORM project has one description of its data: the models, their fields, and how they map to database tables. That description is the data contract, the `contract.prisma` file that replaced `schema.prisma`.

For example, a blog's contract declares a `User` and a `Post`, the fields each carries, and how they relate. You author it in PSL, the Prisma schema language:

```prisma title="prisma/contract.prisma"
// use prisma-8

model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}

model Post {
  id     Int    @id @default(autoincrement())
  title  String
  userId Int

  user User @relation(fields: [userId], references: [id])
}
```

The first line of every `.prisma` contract is `// use prisma-8`. It marks the file as a Prisma ORM 8 contract rather than a Prisma ORM 7 schema. The Prisma language server only offers diagnostics, completion, and formatting on files that carry it. Completion covers field, model, and block attribute names and their argument keys, taken from the installed target and extensions. Contracts written before `8.0.0-rc.10` start with `// use prisma-next`. The language server still accepts that line and replaces it when you format the file.

`prisma contract emit` turns this source into two machine-readable files, and the rest of the toolchain works against them. Your queries are type-checked against the contract, migrations are planned as changes to it, and `prisma db verify` checks a live database against it.

Think of it as a `package-lock.json` for your data: an exact, versioned record of what your application expects from its database.

:::note[Contract vs. schema]

In Prisma ORM, the **contract** is what you write in your code, and the **schema** is your database's actual structure. Some tools use these words the other way around, so keep the distinction in mind: you author a contract, and Prisma ORM checks that the database's schema satisfies it.

:::

## Why a contract

Prisma ORM 7 compiles your schema into generated client code. The description of your data is in there, but only the generated client can read it.

Prisma ORM keeps that description in the open. Your contract source compiles to two plain files. `contract.json` describes your models, how they are stored, and which database features the contract needs. `contract.d.ts` holds the TypeScript types derived from it. The same source always produces the same two files, so you can read them in a code review, hash them, and hand them to tools and coding agents.

The contract also identifies the exact version of the schema it describes. `prisma contract emit` computes hashes over its contents. When you run [`prisma db sign`](/cli/db-sign), Prisma ORM records which contract the database matches in a small table it creates in the database. The client reads that record before its first query and logs a warning if the record does not match the contract the client holds. To fail instead of warn, for example in a deploy check, run [`prisma db verify`](/cli/db-verify).

## How it works

A Prisma ORM project declares one contract source in `prisma.config.ts`:

```typescript title="prisma.config.ts"
import { definePrismaConfig } from "prisma/config";
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./prisma/contract.prisma",
  }),
});
```

The source is either a Prisma schema file (`contract.prisma`) or a TypeScript file (`contract.ts`). The file extension selects the authoring mode. Both modes describe the same things: models with fields and relations, the tables and columns they map to, named types, enums, and any extension-provided types.

Run `prisma contract emit` after every change to the contract. It writes `contract.json` and `contract.d.ts` beside the source:

```npm
npx prisma contract emit
```

From there, the rest of the toolchain takes over:

- The query APIs load `contract.d.ts` to give you typed models, fields, and results.
- `db` reads `contract.json` and compares its hashes with the record `prisma db sign` wrote in the database.
- The migration tooling compares two contracts to plan schema changes, and [`prisma db verify`](/cli/db-verify) checks a live database against the current contract.

## Two authoring modes, one `contract.json` [#two-authoring-modes-one-artifact]

**[PSL](/orm/contract-authoring/psl-syntax)** is the usual way to write the contract. It is a compact language for describing data. It is what `npm create prisma@latest` scaffolds, and what [`prisma contract infer`](/cli/contract-infer) writes when you start from an existing database.

For the cases PSL does not cover, define models with the **[TypeScript builder](/orm/contract-authoring/typescript-schema-builder)** instead. Reach for it when model definitions must be composed, generated, or shared as ordinary TypeScript modules.

Both modes produce the same contract. For an equivalent schema they write the same `contract.json`, so migrations, database checks, and the query APIs behave the same no matter which mode you write. You give up nothing by staying with PSL. A project has exactly one contract file, the one named by `contract` in the config. Keep the other form out of the project, or treat it as a generated reference, so the two can never disagree.

## What the contract contains

The contract describes structure, not data:

- models, fields, and relations, plus how they map to tables and columns
- storage details: primary keys, unique constraints, indexes, and foreign keys
- named types, enums, and `type` blocks, each a structured value stored inside its parent row with no table of its own
- the types and database features that extension packs add, such as pgvector's `Vector`
- hashes that identify this exact version of the schema

It contains no rows, no credentials, and no connection details, so committing the source, `contract.json`, and `contract.d.ts` to version control is safe and expected.

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent; in an existing project, run `npx prisma skills sync`. The `prisma-8` skill covers the contract. Ask your agent to:

- "Using the prisma-8 skill, explain what our contract.json currently declares."
- "Add an Invoice model to the contract and run prisma contract emit."
- "Check whether our database still satisfies the contract."
