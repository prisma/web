Every Prisma ORM project has one description of its data: the models, their fields, and how they map to database tables. That description is the data contract, the `contract.prisma` file that replaced `schema.prisma`.

For example, a blog's contract declares a `User` and a `Post`, the fields each one has, and how they relate. You author it in PSL, the Prisma Schema Language, the same language as `schema.prisma`:

```prisma title="src/prisma/contract.prisma"
// use prisma-8

model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}

model Post {
  id     Int    @id @default(autoincrement())
  title  String
  userId Int
  user   User   @relation(fields: [userId], references: [id])
}
```

Start every `.prisma` contract with `// use prisma-8`. Your editor's Prisma support only works on files that have that line. A `contract.ts` file needs no header line.

`prisma contract emit` turns this file into two files that the rest of the toolchain reads: `contract.json` and `contract.d.ts`. Your queries are type-checked against the contract, migrations are planned as changes to it, and `prisma db verify` checks a live database against it. Think of it as a `package-lock.json` for your data: an exact, versioned record of what your application expects from its database.

If you already have a Prisma ORM 7 `schema.prisma`, [Coming from Prisma ORM 7](/orm/coming-from-prisma-orm-7) lists what changed and the [PostgreSQL upgrade guide](/guides/upgrade-prisma-orm/postgresql) walks through converting the file.

:::note[Contract vs. schema]

In Prisma ORM, the **contract** is what you write in your code, and the **schema** is your database's actual structure. Some tools use these words the other way around. The language you write the contract in keeps the older name: it is PSL, the Prisma Schema Language, the same language as `schema.prisma`.

:::

## Why a contract

Your contract compiles to two plain files you can open and read. `contract.json` describes your models, how they are stored, and [which database features they need](/orm/contract-authoring/capabilities). `contract.d.ts` holds the TypeScript types derived from it. The same source always produces the same two files, so you can read them in a code review and hand them to tools and coding agents. In Prisma ORM 7 the same description existed, but only the generated client could read it.

`prisma contract emit` also writes a hash of the contract into `contract.json`. When you apply a contract change to the database, the command that applies it records that hash in a small table it creates in your database. Before its first query, `db` compares the two and logs a warning if they differ. To fail instead of warn, for example in a deploy check, run [`prisma db verify`](/cli/db-verify).

## How it works

A Prisma ORM project declares one contract file in `prisma.config.ts`:

```typescript title="prisma.config.ts"
import { definePrismaConfig } from "prisma/config";
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.prisma",
  }),
});
```

`definePrismaConfig` holds the whole config. `ormConfig` comes from your database package and holds the settings for that database: `@prisma/orm-postgres` for PostgreSQL, `@prisma/orm-sqlite` for SQLite, and `@prisma/orm-mongo` for MongoDB. The examples here use PostgreSQL. To start a new project, run `npm create prisma@latest -- my-app`. To add Prisma ORM to a project you already have, run `prisma orm init`. Either one writes `prisma.config.ts`, the contract file, and `src/prisma/db.ts`, and installs the database package.

The contract file is either a PSL file (`contract.prisma`) or a TypeScript file (`contract.ts`). The file extension selects the authoring mode, so to author in TypeScript you point `contract` at `./src/prisma/contract.ts`. Both modes describe the same things: models with fields and relations, the tables and columns they map to, named types, enums, and any types that [extension packages](/orm/contract-authoring/psl-syntax#extension-types) add. Extension packages are npm packages that add field types and database features, such as pgvector, a PostgreSQL extension for vector columns.

After every change to the contract, run these three commands:

```npm
npx prisma contract emit
npx prisma migration plan
npx prisma db migrate
```

`prisma contract emit` writes `contract.json` and `contract.d.ts` beside the source. [`prisma migration plan`](/orm/migrations/generating-a-migration) works out what the database needs and writes a migration. [`prisma db migrate`](/orm/migrations/applying-a-migration) applies it and records the new hash for you, so there is no separate signing step. Run [`prisma db sign`](/cli/db-sign) only when the database already matches the contract and nothing needs applying, for example after `prisma contract infer`.

`db` is the client you create once in `src/prisma/db.ts`, and `prisma orm init` writes that file for you. From a file directly inside `src/`, import it with `import { db } from "./prisma/db"` and query a model: `await db.orm.public.User.all()` returns every user row. `db.orm` holds your models by model name. `public` is the PostgreSQL schema, the namespace your tables are in, which is `public` unless you set one. [Reading data](/orm/fundamentals/reading-data) covers queries.

## Two authoring modes, one `contract.json` [#two-authoring-modes-one-artifact]

**[PSL](/orm/contract-authoring/psl-syntax)** is the usual way to write the contract. It is a compact language for describing data. It is what `npm create prisma@latest` scaffolds, and what [`prisma contract infer`](/cli/contract-infer) writes when you start from an existing database. That command reads the live database and writes a `contract.prisma` from what it finds.

Define models with the **[TypeScript builder](/orm/contract-authoring/typescript-schema-builder)** instead when you want to build them with code. Reach for it when model definitions must be composed, generated, or shared as ordinary TypeScript modules. That page shows what a `contract.ts` file looks like.

Both modes produce the same contract. For the same models they write the same `contract.json`, so migrations, database checks, and `db` behave the same no matter which mode you write. A project has exactly one contract file, the one named by `contract` in the config. Do not keep both a `contract.prisma` and a `contract.ts`. If you had both, they could describe different things.

## What the contract contains

The contract describes structure, not data:

- models, fields, and relations, plus how they map to tables and columns
- how the data is stored: primary keys, unique constraints, indexes, and foreign keys
- [named types](/orm/contract-authoring/psl-syntax#named-types), which are reusable aliases for a type and its storage details, and enums
- [`type` blocks](/orm/contract-authoring/psl-syntax#value-objects), each a structured value stored inside its parent row with no table of its own. On PostgreSQL each one is stored in a single `jsonb` column.
- the types and database features that extension packages add, such as pgvector's `Vector` type
- a hash of the contract, which the database check compares against

It contains no rows, no credentials, and no connection details, so committing the source, `contract.json`, and `contract.d.ts` to version control is safe and expected.

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. The `prisma-8` skill covers the contract. Ask your agent to:

- "Using the prisma-8 skill, explain what our contract.json currently declares."
- "Add an Invoice model to the contract and run prisma contract emit."
- "Check whether our database still satisfies the contract."
