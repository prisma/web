[`prisma contract emit`](/cli/contract-emit) writes `contract.json` and `contract.d.ts` beside the source by default:

| File | Contents | Read by |
| --- | --- | --- |
| `contract.json` | The machine-readable contract: models, how they are stored, which database features they need, and the hashes | `db`, the migration tooling, the database checks, and anything else that needs to read your schema |
| `contract.d.ts` | TypeScript declarations derived from the contract | The query APIs and your application code, for typed models and results |

Both files are generated. Do not edit them. Change the [PSL](/orm/contract-authoring/psl-syntax) or [TypeScript](/orm/contract-authoring/typescript-schema-builder) source and run `prisma contract emit` again. Each file starts with a notice that says exactly this.

## The same source always produces the same two files [#deterministic-emission]

Run `prisma contract emit` on the same source on any machine and you get byte-identical files. Keys are written in a fixed key order and values in a normalized form, which is what lets you read the files in a code review and hash them.

That is also why the contract source must not read the environment, the clock, or random values. A source that did would produce different files each run, and every hash below would stop meaning anything. The [TypeScript authoring page](/orm/contract-authoring/typescript-schema-builder#keep-the-contract-file-pure) lists the rules.

## The content hashes

`prisma contract emit` computes a hash over each of these parts of the contract:

| Hash | Covers | Changes when |
| --- | --- | --- |
| `storageHash` | The storage layout: tables, columns, primary keys, uniques, indexes, foreign keys, and the value sets behind enums | A table, column, key, constraint, or index changes |
| `executionHash` | The defaults Prisma ORM applies before a write, such as `@default(uuid())` | A generated default changes |
| `profileHash` | The database this contract targets, and its family | The contract targets a different database |

The hashes are how Prisma ORM connects the contract to a live database. [`prisma db sign`](/cli/db-sign) checks that the database satisfies the contract, then records `storageHash` and `profileHash` in a small table it creates in the database. [`prisma db verify`](/cli/db-verify) compares the contract you hold against that record and against the live schema, and fails when they disagree. `db` makes the same comparison before its first query, but it logs a warning and carries on.

## Inside `contract.json`

The contract separates what your application models from how it is stored. The `domain` section describes models, fields, and relations; the `storage` section describes tables, columns, keys, and indexes. On MongoDB it describes collections and indexes instead. Each model's own `storage` block joins the two. Everything is grouped by namespace. On PostgreSQL the namespace is the schema, `public` unless you set one.

An abridged `contract.json` for a `User` and `Post` schema:

```json title="prisma/contract.json (abridged)"
{
  "schemaVersion": "1",
  "targetFamily": "sql",
  "target": "postgres",
  "profileHash": "…",
  "roots": {
    "post": { "model": "Post", "namespace": "public" },
    "user": { "model": "User", "namespace": "public" }
  },
  "domain": {
    "namespaces": {
      "public": {
        "models": {
          "User": {
            "fields": {
              "email": { "nullable": false, "type": { "codecId": "pg/text@1", "kind": "scalar" } },
              "id": { "nullable": false, "type": { "codecId": "pg/uuid@1", "kind": "scalar" } }
            },
            "relations": {
              "posts": {
                "cardinality": "1:N",
                "on": { "localFields": ["id"], "targetFields": ["userId"] },
                "to": { "model": "Post", "namespace": "public" }
              }
            },
            "storage": {
              "fields": { "email": { "column": "email" }, "id": { "column": "id" } },
              "namespaceId": "public",
              "table": "user"
            }
          }
        }
      }
    }
  },
  "storage": {
    "namespaces": {
      "public": {
        "entries": {
          "table": {
            "user": {
              "columns": {
                "email": { "codecId": "pg/text@1", "nativeType": "text", "nullable": false },
                "id": { "codecId": "pg/uuid@1", "nativeType": "uuid", "nullable": false }
              },
              "primaryKey": { "columns": ["id"] }
            }
          }
        }
      }
    },
    "storageHash": "…"
  },
  "execution": { "executionHash": "…" },
  "capabilities": { "postgres": { "returning": true } },
  "extensions": {}
}
```

The sections, top to bottom:

- **`schemaVersion`, `targetFamily`, `target`**: the contract format version and the database this contract targets.
- **`roots`**: each table name mapped to the model stored in it. The SQL query builder is keyed by those table names, as in `db.sql.public.user`, and the model name is what `db.orm.public.User` uses.
- **`domain`**: the application's view. Each scalar field records whether it is nullable and its type id, such as `pg/text@1`, the PostgreSQL type plus a version, always `@1` today. Relations record how many records are on each side and the fields they join on. The model's `storage` block maps fields to columns.
- **`storage`**: the database's view. Tables with their columns, each with a native type and a type id, plus primary keys, uniques, indexes, foreign keys, check constraints, and the value sets behind enums. This is the section the migration tooling compares between versions and `prisma db verify` checks the live schema against.
- **`execution`**: the defaults Prisma ORM applies before a write, such as `@default(uuid())`. These are not column defaults in the database.
- **`capabilities`** and **`extensions`**: which database features this contract can use, collected from the adapter for your database and any extension packs when you run `prisma contract emit`. The query APIs check these before building a query that needs one. See [which database features the contract needs](/orm/contract-authoring/capabilities).

## Inside `contract.d.ts`

The declarations file gives the type system the same information. It exports the contract type, branded hash types matching `contract.json`, and input/output types for every model:

```typescript title="prisma/contract.d.ts (excerpt)"
export type StorageHash =
  StorageHashBase<"9f49f8f9e51a9cc016f1ec2098ebae9406521a3cc2cf00207adc795078333d8b">;
export type ProfileHash =
  ProfileHashBase<"9c8aa3114e84ed3b7ea2bd57526d9c2e1bf7c5292be694e9d3801f566fda7ccb">;

export type AddressOutput = {
  readonly street: CodecTypes["pg/text@1"]["output"];
  readonly city: CodecTypes["pg/text@1"]["output"];
  readonly zip: CodecTypes["pg/text@1"]["output"] | null;
  readonly country: CodecTypes["pg/text@1"]["output"];
};
```

Because the hashes are literal types, a client built against one version of the contract will not type-check against another version's files. TypeScript catches a mismatched contract before `prisma db verify` has to.

## How the application consumes the artifacts

`db` is built from both files: `contract.json` as the value, `contract.d.ts` as the type. `prisma orm init` writes `src/prisma/db.ts` for you.

```typescript title="src/prisma/db.ts"
import postgres from "@prisma/orm-postgres/runtime";
import type { Contract } from "./contract.d";
import contractJson from "./contract.json" with { type: "json" };

export const db = postgres<Contract>({
  contractJson,
});
```

Before its first query, `db` reads the record `prisma db sign` wrote in the database and compares it with the contract's hashes. If they do not match, it logs a warning and runs the query anyway. Run `prisma db verify` when you need the check to fail instead.

## Version control

Commit `contract.json` and `contract.d.ts` alongside the source. They hold structure only, no data and no credentials. Committing them lets teammates, CI, and deploys read the contract without running `prisma contract emit` first. Run `prisma contract emit` after every source change so the two files never trail the source. A CI job can enforce this by running the command and failing if the working tree changes.
