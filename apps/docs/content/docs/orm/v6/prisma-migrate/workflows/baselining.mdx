Baselining is the process of initializing a migration history for a database that:

- ✔ Existed before you started using Prisma Migrate
- ✔ Contains data that must be maintained (like production), which means that the database cannot be reset

Baselining tells Prisma Migrate to assume that one or more migrations have **already been applied**. This prevents generated migrations from failing when they try to create tables and fields that already exist.

> **Note**: We assume it is acceptable to reset and seed development databases.

Baselining is part of [adding Prisma Migrate to a project with an existing database](/orm/v6/prisma-migrate/getting-started#adding-prisma-migrate-to-an-existing-project).

:::warning

This guide **does not apply for MongoDB**.<br />
Instead of `migrate deploy`, [`db push`](/orm/v6/prisma-migrate/workflows/prototyping-your-schema) is used for [MongoDB](/orm/v6/overview/databases/mongodb).

:::

## Why you need to baseline

When you add Prisma Migrate to an existing project, your initial migration contains all the SQL required to recreate the state of the database **before you started using Prisma Migrate**:

An arrow labelled 'represented by' connects the database features list to a box that represents a migration. The existing databases's features are represented by a single migration.](/img/v6/orm/prisma-migrate/workflows/existing-database.png)

:::tip

You can edit the initial migration to include schema elements that cannot be represented in the Prisma schema - such as stored procedures or triggers.

:::

You need this initial migration to create and reset **development environments**:

![The image shows a migration history with three migrations. Each migration is represented by a file icon and a name, and all migrations are surrounded by a box labelled 'migration history'. The first migration has an additional label: "State of database before Prisma Migrate", and the two remaining migrations are labelled "Generated as part of the Prisma Migrate workflow". An arrow labelled "prisma migrate dev" connects the migration history box to a database labelled "new development database", signifying that all three migrations are applied to the development database - none are skipped.](/img/v6/orm/prisma-migrate/workflows/new-dev-db.png)

However, when you `prisma migrate deploy` your migrations to databases that already exist and _cannot_ be reset - such as production - you **do not want to include the initial migrations**.

The target database already contains the tables and columns created by the initial migration, and attempting to create these elements again will most likely result in an error.

![A migration history represented by three migration files (file icon and name), surrounded by a box labelled 'migration history'. The first migration is marked 'do not apply', and the second two migrations are marked 'apply'. An arrow labelled with the command 'prisma migrate deploy' points from the migration history to a database labelled 'production'.](/img/v6/orm/prisma-migrate/workflows/deploy-db.png)

Baselining solves this problem by telling Prisma Migrate to pretend that the initial migration(s) **have already been applied**.

## Baselining a database

To create a baseline migration:

1. If you have a `prisma/migrations` folder, delete, move, rename, or archive this folder.

1. Run the following command to create a `migrations` directory inside with your preferred name. This example will use `0_init` for the migration name:

   ```bash
   mkdir -p prisma/migrations/0_init
   ```

   :::info

   Then `0_` is important because Prisma Migrate applies migrations in a [lexicographic order](https://en.wikipedia.org/wiki/Lexicographic_order). You can use a different value such as the current timestamp.

   :::

1. Generate a migration and save it to a file using `prisma migrate diff`

   ```bash no-lines
   npx prisma migrate diff \
   --from-empty \
   --to-schema-datamodel prisma/schema.prisma \
   --script --output prisma/migrations/0_init/migration.sql
   ```

1. Run the `prisma migrate resolve` command for each migration that should be ignored:

   ```npm
   npx prisma migrate resolve --applied 0_init
   ```

This command adds the target migration to the `_prisma_migrations` table and marks it as applied. When you run `prisma migrate deploy` to apply new migrations, Prisma Migrate:

1. Skips all migrations marked as 'applied', including the baseline migration
1. Applies any new migrations that come _after_ the baseline migration

## Baselining a migration history that is behind your schema [#migration-history-behind-schema]

A migration history falls behind when tables or columns reach the database without a migration, for example through [`prisma db push`](/orm/v6/prisma-migrate/workflows/prototyping-your-schema) or SQL that someone ran by hand. The database and the Prisma schema still agree with each other, so the application works, but the `prisma/migrations` folder can no longer recreate the database.

You notice this when you move to a new database or create a new environment. `prisma migrate deploy` applies only the migrations in the folder to the empty database, reports `All migrations have been successfully applied.`, and leaves every table that never had a migration missing. `prisma migrate status` does not warn you either, because it compares the folder with the `_prisma_migrations` table and not with the tables in the database, so it prints `Database schema is up to date!` for a database in this state.

### Detect the drift

Compare the Prisma schema with the existing database first. This comparison does not need a shadow database, and with `--exit-code` the command exits with `0` when the two match, `2` when they differ and `1` on an error:

```bash
npx prisma migrate diff \
  --from-schema-datamodel prisma/schema.prisma \
  --to-schema-datasource prisma/schema.prisma \
  --exit-code
```

The command should print `No difference detected.`. If it lists differences, the schema and the database disagree, and you need to settle that before you continue, for example by updating the schema from the database with [`prisma db pull`](/orm/v6/reference/prisma-cli-reference#db-pull).

Then compare the migration history with the Prisma schema. Prisma Migrate replays the migrations in a [shadow database](/orm/v6/prisma-migrate/understanding-prisma-migrate/shadow-database) to find out what they produce, so this comparison needs one. Any empty database of the same type that you can throw away works, and for PostgreSQL that includes a second Prisma Postgres database. Set its connection string as the `SHADOW_DATABASE_URL` environment variable and pass it with `--shadow-database-url`:

```bash
npx prisma migrate diff \
  --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url "$SHADOW_DATABASE_URL" \
  --exit-code
```

Exit code `2` means the history is behind, and the output lists what the migrations do not create:

```text no-copy
[+] Added tables
  - Product
  - Order
  - OrderItem
  - AuditLog
```

### Add a catch-up migration

Write the missing SQL into a new migration. Give the folder a name that sorts after your latest migration, such as the current UTC time in the `YYYYMMDDHHMMSS` format followed by a short label. `--output` creates the folder and writes the file, so do not create the folder yourself first, because an empty migration folder makes the command fail with error `P3015`:

```bash
npx prisma migrate diff \
  --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url "$SHADOW_DATABASE_URL" \
  --script \
  --output prisma/migrations/20261125150000_catch_up/migration.sql
```

Review the SQL in the new file, and then run the history comparison from the previous step again. It should now print `No difference detected.` and exit with `0`.

Every database that already contains these tables must skip the new migration. With `DATABASE_URL` pointing at the existing database, mark the migration as applied:

```npm
npx prisma migrate resolve --applied 20261125150000_catch_up
```

If you copy the database to its new home with `pg_dump` and `pg_restore`, the copy includes the `_prisma_migrations` table, so resolve the migration once, either on the source before the dump or on the copy after the restore.

A new, empty database needs no special handling from here on. Point `DATABASE_URL` at it and deploy, and Prisma Migrate applies the whole history, including the catch-up migration:

```npm
npx prisma migrate deploy
```

### Verify the result

Run the first comparison against each database, the existing one and any new one:

```bash
npx prisma migrate diff \
  --from-schema-datamodel prisma/schema.prisma \
  --to-schema-datasource prisma/schema.prisma \
  --exit-code
```

`No difference detected.` and exit code `0` on every database mean that the schema, the migration history and the databases agree. You can then delete the shadow database.

## Write the SQL file with `--output` on Windows [#windows-powershell-encoding]

Pass `--output <file>` to `prisma migrate diff` and do not redirect its output with `>`. The option writes UTF-8 without a byte order mark (BOM) in every shell, while redirection leaves the encoding to the shell. According to [Microsoft's documentation](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1), `>` in Windows PowerShell 5.1 creates a UTF-16LE file with a BOM and `Out-File -Encoding utf8` creates a UTF-8 file with a BOM, and only PowerShell 6 and later default to UTF-8 without one.

PostgreSQL rejects a SQL file that starts with a BOM. `prisma db execute --file` stops with `ERROR: syntax error at or near ""`, where the quoted character is the invisible BOM, and `prisma migrate deploy` reports the same message under error `P3018` with database error code `42601`. A UTF-16 file fails in `prisma migrate deploy` with `string contains embedded null`. `psql` skips a UTF-8 BOM, so the same file can work in `psql` and fail in the Prisma CLI.

To repair a migration whose file has the wrong encoding, delete its folder and generate the file again with `--output`. If `prisma migrate deploy` already failed on that migration, the database records it as failed and later deploys stop with error `P3009`, so mark it as rolled back and deploy again, with the name of your migration in place of `0_init`:

```npm
npx prisma migrate resolve --rolled-back 0_init
```

```npm
npx prisma migrate deploy
```
