The `lints` middleware catches queries that are almost certainly a mistake before they reach your database. A `DELETE` with no `WHERE` clause removes every row in the table, which is rarely what anyone meant to write, so `lints` looks at the structure of each query first and either blocks it or logs a warning.

You turn it on by adding it to the `middleware` list when you create your `db` client. The default rules are useful as they are, so there is nothing to configure to get started:

```ts title="src/prisma/db.ts"
import postgres from '@prisma/orm-postgres/runtime';
import { lints } from '@prisma/orm-postgres/family-runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [lints()],
});
```

This is the `src/prisma/db.ts` that `create-prisma` generates, with the `middleware` option added. If you set your project up by hand, [The data contract](/orm/contract-authoring/the-data-contract) covers where `contract.json` and `contract.d.ts` come from.

`lints` works on any SQL database rather than on one database product, so a PostgreSQL client is where you register it, and a MongoDB client refuses it. There is nothing extra to install, because `@prisma/orm-postgres/family-runtime` is part of the `@prisma/orm-postgres` package you already have. If you register other middleware alongside it, Prisma ORM runs them in the order you list them in the array, which [How middleware works](/orm/middleware/how-middleware-works) covers.

## The rules

The checks happen inside your application, before the query reaches the database driver, so a query that a rule blocks never touches your database at all. Queries that return rows and writes that only report a count are both checked.

When you build a query with the ORM API or the SQL query builder, Prisma ORM knows how the query is put together, so each rule can read the parts of the query directly: whether it has a `WHERE` clause, whether it has a `LIMIT`, which columns it asks for. Raw SQL that you wrote yourself is checked a different way, described under [Raw SQL](#raw-sql).

Every rule has a severity, which is `warn` or `error` and nothing else. A rule set to `error` throws, and the query is blocked before it reaches the database. A rule set to `warn` builds a record for the logger and lets the query run. There is no third value that switches a rule off, so the quietest you can make a rule is `warn`.

| Rule | Code | Default severity | Fires when |
| --- | --- | --- | --- |
| DELETE without WHERE | `LINT.DELETE_WITHOUT_WHERE` | `error` | A `DELETE` has no `WHERE` clause |
| UPDATE without WHERE | `LINT.UPDATE_WITHOUT_WHERE` | `error` | An `UPDATE` has no `WHERE` clause |
| No LIMIT | `LINT.NO_LIMIT` | `warn` | A `SELECT` has no `LIMIT` clause |
| SELECT star | `LINT.SELECT_STAR` | `warn` | A query selects all columns instead of naming them |

The rules are named after the SQL they are about, and you write your queries in the ORM API, so here is which of your own calls sets off which rule.

`LINT.NO_LIMIT` fires on a `SELECT` with no `LIMIT`, which in the ORM API means every `.all()` you call without a `.limit(...)` earlier in the chain. `.first(...)` never sets it off, because it adds `LIMIT 1` for you. If your app is full of `.all()` calls, this is the rule you will see most, and registering `lints` will produce a warning for nearly every read you make.

`LINT.SELECT_STAR` fires when a query asks for all the columns rather than naming the ones it wants, which in the ORM API means any query where you never called `.select(...)`. So `await db.orm.public.User.limit(50).all()` sets it off, and `await db.orm.public.User.select('id', 'email').limit(50).all()` does not.

`LINT.DELETE_WITHOUT_WHERE` and `LINT.UPDATE_WITHOUT_WHERE` cannot come from the ORM API, because `deleteAll()` and `updateAll()` are typed to need a `.where(...)` before them and TypeScript rejects the call when there is none. Where they do fire is the [SQL query builder](/orm/reference/sql-query-builder), which lets you call `delete()` or `update()` and build the query without a `where()`.

When a `warn` rule fires, Prisma ORM builds a record holding the code of the rule, a message, and the table the query touched, and hands that record to the client's logger:

```text title="Lint warning"
warn {
  code: 'LINT.NO_LIMIT',
  message: 'Unbounded SELECT may return large result sets',
  details: { table: 'user' }
}
```

:::note

You cannot yet give the `postgres(...)` client a logger of your own, so nothing prints that record and you will not see it anywhere. The rules you set to `error` are the ones you can act on today, because a blocked query is something you notice. Treat the `warn` rules as something to plan for rather than something you will read, until the client accepts a logger.

:::

## What a blocked query looks like

A rule set to `error` throws before the database sees anything, so the call you were awaiting rejects. What it rejects with is an ordinary `Error` object that carries a `code` property, along with `category`, `severity`, and a `details` object saying what the rule found. You catch it the way you catch any other error and read `code` off it:

```ts
try {
  const plan = db.sql.public.user.delete().build();
  await db.runtime().execute(plan);
} catch (error) {
  if ((error as { code?: string }).code === 'LINT.DELETE_WITHOUT_WHERE') {
    // add a where() clause, or use the backfill client described below
  }
  throw error;
}
```

Those four properties hold this for a `DELETE` with no `WHERE` on the `user` table:

```text title="Blocked DELETE" no-copy
{
  code: 'LINT.DELETE_WITHOUT_WHERE',
  category: 'LINT',
  severity: 'error',
  message: 'DELETE without WHERE clause blocks execution to prevent accidental full-table deletion',
  details: { table: 'user' }
}
```

## Configure severities

When a default does not suit your project, `severities` lets you make any rule stricter or gentler. You name only the rules you want to change, and every rule you leave out keeps the default from the table. In a service where every list endpoint has to paginate, for example, you can make a `SELECT` without a `LIMIT` fail rather than warn, and fail a query that names no columns as well:

```ts title="src/prisma/db.ts"
lints({
  severities: {
    noLimit: 'error',
    selectStar: 'error',
  },
});
```

The key for a rule is its name in camel case, so the four rules in the table are `deleteWithoutWhere`, `updateWithoutWhere`, `noLimit`, and `selectStar`. There is a fifth key, `readOnlyMutation`, which applies only to the [raw SQL](#raw-sql) check below. Each key takes `'warn'` or `'error'`.

## Raw SQL

A whole statement you wrote yourself with [`db.raw.sql`](/orm/reference/raw-queries) is SQL text rather than a query Prisma ORM assembled, so there are no parts for a rule to read and the four rules above are skipped for it. `lints` reads the SQL text instead, every time a raw statement runs, and it looks for three things there: a `select *`, a missing `LIMIT`, and a statement that changes data inside a query marked as read-only, which it reports as an error whose `code` is `LINT.READ_ONLY_MUTATION`.

Those text checks start from their own defaults, which are not the defaults in the table above. In raw SQL a `select *` is an `error` rather than a warning, so `select * from "user"` is blocked outright, while a missing `LIMIT` is still a warning and changing data in a read-only query is an `error`. Anything you set in `severities` applies to these findings too.

`fallbackWhenAstMissing` decides what `lints` does with a query whose structure it cannot read at all. Every query the ORM API and the SQL query builder produce carries that structure with it, and a raw statement always gets the text checks above whatever you set here, so in ordinary use this option changes nothing and the default is the one you want:

```ts title="src/prisma/db.ts"
lints({ fallbackWhenAstMissing: 'raw' }); // default: read the SQL text instead
lints({ fallbackWhenAstMissing: 'skip' }); // run no checks at all
```

Reading SQL as text is guesswork, and it can get a query wrong that a structural check would have read correctly, so treat a lint finding on raw SQL as a reason to go and look at the query yourself rather than as a verdict.

## Common gotchas

:::warning

Sometimes you do mean to change every row, in a backfill script for example. `LINT.DELETE_WITHOUT_WHERE` and `LINT.UPDATE_WITHOUT_WHERE` are `error` by default, so `lints` blocks that write, and no severity switches the rule off. A script like that needs one of the two ways through below.

:::

The first way is to write a `WHERE` clause that is true for every row, which states the intent in the query itself. On a table whose primary key is `id`, comparing that column to `null` with `fns.ne` gives you `id IS NOT NULL`, which every row matches:

```ts
const plan = db.sql.public.user
  .delete()
  .where((f, fns) => fns.ne(f.id, null))
  .build();
await db.runtime().execute(plan);
```

The second way is to build that script its own `db` client with the rule set to `warn`:

```ts title="scripts/backfill/db.ts"
import postgres from '@prisma/orm-postgres/runtime';
import { lints } from '@prisma/orm-postgres/family-runtime';
import type { Contract } from '../../src/prisma/contract.d';
import contractJson from '../../src/prisma/contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [lints({ severities: { deleteWithoutWhere: 'warn' } })],
});
```

Keep that client inside the script and import your usual `db` everywhere else, because setting the rule to `warn` for your whole application gives up the protection everywhere.
