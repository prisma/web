The `lints` middleware catches queries that are almost certainly a mistake before they reach your database. A `DELETE` with no `WHERE` clause removes every row in the table, which is rarely what anyone meant to write, so `lints` looks at the structure of each query first and either blocks it or logs a warning.

You turn it on by adding it to the `middleware` list when you create your `db` client. The default rules are useful as they are, so there is nothing to configure to get started:

```ts title="src/prisma/db.ts"
import postgres from '@prisma/orm-postgres/runtime';
import { lints } from '@prisma/orm-postgres/family-runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [lints()],
});
```

`lints` works with SQL databases in general rather than with one database product, which is what `familyId: 'sql'` in its definition says, so you can register it on a PostgreSQL `db` client. There is nothing extra to install: it comes from `@prisma/orm-postgres/family-runtime`, which is part of the `@prisma/orm-postgres` package.

## The rules

The checks happen inside your application, before the query reaches the database driver, so a query that a rule blocks never touches your database at all. When you build a query with the ORM client or the SQL query builder, Prisma ORM keeps a structured description of it, its AST, and each rule reads that description rather than the SQL text. Raw SQL that you wrote yourself is checked a different way, described under [Raw SQL](#raw-sql).

`lints` registers the same check under both `beforeQuery` and `beforeExecute`, the two points where Prisma ORM calls middleware before running something, so queries that return rows and writes that return nothing are both covered.

Every rule has a severity, which decides what `lints` does when the rule fires. A rule set to `error` throws, and the query is blocked before it reaches the database. A rule set to `warn` writes to the log and lets the query run.

| Rule | Code | Default severity | Fires when |
| --- | --- | --- | --- |
| DELETE without WHERE | `LINT.DELETE_WITHOUT_WHERE` | `error` | A `DELETE` has no `WHERE` clause |
| UPDATE without WHERE | `LINT.UPDATE_WITHOUT_WHERE` | `error` | An `UPDATE` has no `WHERE` clause |
| No LIMIT | `LINT.NO_LIMIT` | `warn` | A `SELECT` has no `LIMIT` clause |
| SELECT star | `LINT.SELECT_STAR` | `warn` | A query selects all columns instead of naming them |

When a `warn` rule fires, Prisma ORM writes a record to its log with the code of the rule, a message, and the table the query touched:

```text title="Lint warning"
warn {
  code: 'LINT.NO_LIMIT',
  message: 'Unbounded SELECT may return large result sets',
  details: { table: 'user' }
}
```

:::note

You cannot yet give the `postgres(...)` client a logger of your own, so nothing prints these warnings and you will not see them anywhere. The rules you set to `error` are the ones you can act on today, because a blocked query is something you notice. Treat the `warn` rules as something to plan for rather than something you will read, until the client accepts a logger.

:::

## Configure severities

When a default does not suit your project, `severities` lets you make any rule stricter or gentler. In a service where every list endpoint has to paginate, for example, you can make a `SELECT` without a `LIMIT` fail rather than warn:

```ts title="src/prisma/db.ts"
lints({
  severities: {
    noLimit: 'error',
    selectStar: 'warn',
  },
});
```

The keys you can set are `deleteWithoutWhere`, `updateWithoutWhere`, `noLimit`, and `selectStar`, one for each rule, plus `readOnlyMutation` for the [raw SQL](#raw-sql) check on queries you marked as read-only.

## Raw SQL

When you build a query with the ORM client or the SQL query builder, Prisma ORM knows how the query is put together, so the rules can look at its parts directly.

A whole statement you wrote yourself with [`db.raw.sql`](/orm/reference/raw-queries) is different. Prisma ORM still records it, under the kind `raw-query`, but Prisma ORM did not build the query, so there is no structure for a rule to inspect and the structural rules are skipped. `lints` reads the SQL text instead, and it always does so for a raw statement: it looks for `select *`, for a missing `LIMIT`, and for a statement that changes data inside a query you marked as read-only, which it reports as an error whose `code` is `LINT.READ_ONLY_MUTATION`. These text checks come with their own defaults, which are not the same as the ones in the table. In raw SQL, `select *` is an `error` rather than a warning, a missing `LIMIT` is still a warning, and changing data in a read-only query is an `error`. Anything you set in `severities` applies to raw SQL findings too.

`fallbackWhenAstMissing` decides what happens with a query where `plan.ast` is missing entirely, which is not the same thing as a raw statement: a `raw-query` is recorded with its own kind and always gets the text checks, so this option never applies to one.

```ts title="src/prisma/db.ts"
lints({ fallbackWhenAstMissing: 'raw' }); // default: heuristic checks on the SQL text
lints({ fallbackWhenAstMissing: 'skip' }); // skip linting for plans with no AST
```

Reading SQL as text is guesswork, and it can get a query wrong that a structural check would have read correctly, so treat a lint finding on raw SQL as a reason to go and look at the query yourself rather than as a verdict.

## Common gotchas

:::warning

Sometimes you do mean to change every row, in a backfill script for example. `LINT.DELETE_WITHOUT_WHERE` and `LINT.UPDATE_WITHOUT_WHERE` are `error` by default, so `lints` blocks that write. For a one-off script you have two ways through: write a `WHERE` clause that is true for every row, which states the intent in the query itself, or create that script's `db` client with the rule set to `warn`. Keep that change inside the script, because setting the rule to `warn` for your whole application gives up the protection everywhere.

:::
