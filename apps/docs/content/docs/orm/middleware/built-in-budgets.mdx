The `budgets` middleware stops one careless query from reading far more of your data, or taking far more time, than you meant to give it. You give it a row limit and a time limit, and it checks every query you send against both. It checks the row limit twice, first by estimating how many rows the query could return before the query runs, and then by counting the rows as the database sends them back, because an estimate made from the query text alone can be too optimistic. It checks the time limit once the query has finished, so the time limit tells you a query was slow rather than stopping it.

Before you register it, know that `budgets` rejects any `SELECT` that has no `LIMIT` on it, however few rows the table holds. On the ORM API that is every `.all()` call with no `.limit(...)` in front of it, so those calls start throwing the moment you add `budgets` to your client and you should expect to add limits across your app. A `.first(...)` call is fine, because it asks the database for one row.

Register it where you create your client, with the row and time limits you want to enforce:

```ts title="src/prisma/db.ts"
import postgres from '@prisma/orm-postgres/runtime';
import { budgets } from '@prisma/orm-postgres/family-runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [
    budgets({
      maxRows: 10_000,
      defaultTableRows: 10_000,
      tableRows: { user: 10_000, post: 10_000 },
      maxLatencyMs: 1_000,
    }),
  ],
});
```

This is the `src/prisma/db.ts` that `create-prisma` generates, with the `middleware` option added. If you set your project up by hand, [The data contract](/orm/contract-authoring/the-data-contract) covers where `contract.json` and `contract.d.ts` come from.

`maxRows`, `defaultTableRows`, and `maxLatencyMs` are written out at their default values above, so that the example shows you where each one goes. Choose your own from what a single query in your app has any business doing, because `maxRows` and `maxLatencyMs` are the ceilings you want a mistake to hit. The numbers in `tableRows` are different: they are your own estimate of how many rows each table really holds, so a `post` table with two million rows in it is written `tableRows: { post: 2_000_000 }`.

`budgets` works with SQL databases only, so you register it on a PostgreSQL client and a MongoDB client refuses it. You import it from `@prisma/orm-postgres/family-runtime`, which arrives with `@prisma/orm-postgres`, so there is nothing extra to install.

## Options

Every option is optional, and the default in the table applies when you leave one out.

| Option | Type | Default | What it controls |
| --- | --- | --- | --- |
| `maxRows` | `number` | `10_000` | The most rows one query may produce |
| `defaultTableRows` | `number` | `10_000` | How many rows to assume a table has when it is not listed in `tableRows` |
| `tableRows` | `Record<string, number>` | `{}` | How many rows to assume each table has, keyed by table name |
| `maxLatencyMs` | `number` | `1_000` | The longest one query may take, in milliseconds |
| `severities.rowCount` | `'warn' \| 'error'` | `'error'` | Whether going over the row budget throws or only logs a warning |
| `severities.latency` | `'warn' \| 'error'` | `'warn'` | Whether going over the time budget throws or only logs a warning |

The two `severities` entries are the one option with a nested shape, and you write them together in a single object: `budgets({ maxRows: 10_000, severities: { rowCount: 'warn', latency: 'error' } })`.

Setting them changes nothing on PostgreSQL, though, because when you create your client with `postgres(...)` a budget violation always throws. The `severities` options only take effect on a client that runs in permissive mode, and `postgres(...)` does not offer that, so read both severity rows above as `'error'` and expect an error every time either budget is exceeded. That applies to the time budget too: a query that runs longer than `maxLatencyMs` throws an error whose `code` is `BUDGET.TIME_EXCEEDED`, even though the table gives `severities.latency` a default of `'warn'`.

## How it enforces the budget

`budgets` looks at every query you send three times, from the moment you send it to the moment it finishes:

1. **Before the query runs**, `budgets` reads the query and works out how many rows it could return. A `SELECT` with no `LIMIT` on it is over budget on its own, whatever `maxRows` says, unless the query can only ever produce a single row, which is the case for an aggregate such as a count with no `GROUP BY`. When the query does have a limit, `budgets` compares that limit against the size you gave for the table it reads, in `tableRows` or in `defaultTableRows` when the table is not listed, and takes the smaller of the two as its estimate. The query is over budget when that estimate is above `maxRows`. Either way you get an error whose `code` is `BUDGET.ROWS_EXCEEDED` before the database is asked to do anything.
2. **While the rows come back**, `budgets` counts the rows the database really returns, so a query that got past the estimate is still caught. As soon as that count passes `maxRows` it throws an error whose `code` is `BUDGET.ROWS_EXCEEDED` and stops reading the rest of the rows.
3. **After the query finishes**, `budgets` compares how long the query took against `maxLatencyMs` and reports an error whose `code` is `BUDGET.TIME_EXCEEDED` when it ran too long. The database has already done the work by the time this check runs, so it cannot save the slow query. It is there to make slow queries loud instead of invisible.

## What you see when a budget trips

When `budgets` blocks a query, the call you were awaiting rejects with an ordinary `Error` that has a `code` property saying which budget was exceeded and a `details` property with the numbers it measured. If you do not catch it, a `SELECT` with no `LIMIT` and `maxRows` at `10_000` prints this, where "unbounded" in the message is the error's own word for a query with no `LIMIT`:

```text title="Row budget error" no-copy
Error [RuntimeError]: Unbounded SELECT query exceeds budget
    ... {
  code: 'BUDGET.ROWS_EXCEEDED',
  category: 'BUDGET',
  severity: 'error',
  details: { source: 'ast', estimatedRows: 10000, maxRows: 10000 }
}
```

The `source` field is how you tell which of the two row checks stopped the query: `'ast'` means the check before the query ran, and `'observed'` means the database really did return that many rows. `estimatedRows` is there only when the estimate was at or above `maxRows`, so a query with no `LIMIT` against a table you said was small is rejected with the two fields `{ source: 'ast', maxRows: 10000 }` and no `estimatedRows` at all.

When a slow query blocks, the error gives you both numbers, the time the query took and the time you allowed:

```text title="Latency budget error" no-copy
Error [RuntimeError]: Query latency exceeds budget
    ... {
  code: 'BUDGET.TIME_EXCEEDED',
  category: 'BUDGET',
  severity: 'error',
  details: { latencyMs: 1501, maxLatencyMs: 1000 }
}
```

Both errors are plain `Error` objects, so you catch them the way you catch anything else and read the `code` to tell which budget was exceeded:

```ts
try {
  await db.orm.public.User.select('id').all();
} catch (error) {
  if ((error as { code?: string }).code === 'BUDGET.ROWS_EXCEEDED') {
    // add a limit, or raise the budget
  }
  throw error;
}
```

Most of the time the fix is to give the query a limit, with [`limit(...)` on the ORM API](/orm/fundamentals/reading-data#sort-and-paginate) or `.limit(...)` on the SQL query builder. When the query is right and the budget is too low, raise `maxRows`, but that raises it for every query on that client, because `budgets` is an option of the client and no query can opt out of it. So for a job that genuinely has to read millions of rows, such as a nightly export, build a second client from the same contract with `budgets` left out of its `middleware` array and run the job against that client.

## Common gotchas

:::warning

The check that runs before your query never asks the database how big your tables are. It only knows the numbers you gave it in `tableRows` and `defaultTableRows`, so when your real tables are much larger than those numbers, a query can get past that first check and then fail part way through reading rows, once the rows the database returns pass `maxRows`. What matters about each number is which side of `maxRows` it falls on, so with `maxRows` at `10_000`, a table you listed at 5,000 rows that really holds 8,000 changes nothing, while one you listed at 5,000 that really holds 5 million changes everything. Revisit `tableRows` when a table you query grows ten times larger.

:::
