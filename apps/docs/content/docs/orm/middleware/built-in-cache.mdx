The cache middleware keeps the rows a read returned in memory, so when your app runs that same read again it gets the stored rows back instead of going to the database. Nothing is cached unless you ask for it: you mark a query with a TTL, meaning how long its stored rows stay usable, and every query you do not mark runs against the database exactly as it did before.

Reach for it when the same read runs over and over and you can live with an answer that is a little out of date, such as a dashboard, a lookup table, feature flags, navigation data, or a search result that is expensive to run.

Install the package and register the middleware:

```npm title="Terminal"
npm install @prisma/orm-extension-middleware-cache
```

```ts title="src/prisma/db.ts"
import { createCacheMiddleware } from '@prisma/orm-extension-middleware-cache';
import postgres from '@prisma/orm-postgres/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [createCacheMiddleware({ maxEntries: 1_000 })],
});
```

The cache takes part only in queries that return rows, and it does that with the hooks `interceptQuery`, `onRow`, and `afterQuery`, all of which Prisma ORM calls around a query that returns rows. If you register other middleware that can answer a query themselves from `interceptQuery`, put the cache before them in the `middleware` array when you want the cached rows to be the answer.

That is also why a read you send through `runtime.execute(plan)` is never cached and never comes back to you as rows. `execute` is the call for statements that change data, and it reports how many rows they affected instead of returning them.

The cache does not care which database you are on. `budgets` and `lints` run on PostgreSQL only, but the cache runs on MongoDB as well.

## Opt a query in

You tell Prisma ORM that a read may be cached by attaching `cacheAnnotation` to it with a `ttl`, the number of milliseconds its rows stay usable. When you build the query with the SQL query builder, chain `.annotate(...)` onto the query you are building:

```ts title="src/prisma/get-users-cached.ts"
import { cacheAnnotation } from '@prisma/orm-extension-middleware-cache';
import { db } from './db';

export async function getUsersCached() {
  const plan = db.sql.public.user
    .select('id', 'email')
    .annotate(cacheAnnotation({ ttl: 60_000 }))
    .limit(10)
    .build();

  return db.runtime().query(plan);
}
```

When you use the ORM API instead, the annotation goes through the query's meta callback:

```ts title="src/prisma/get-user-cached.ts"
import { cacheAnnotation } from '@prisma/orm-extension-middleware-cache';
import { db } from './db';

export async function getUserCached(id: number) {
  return db.orm.public.User.first({ id }, (meta) =>
    meta.annotate(cacheAnnotation({ ttl: 60_000 })),
  );
}
```

The first call goes to the database as usual, and the cache keeps the rows it got back, exactly as they came. If the same query with the same parameter values runs again before the `ttl` has run out, Prisma ORM answers it from those stored rows and never calls the database driver.

You can set the following fields on the annotation:

| Field | Type | What it does |
| --- | --- | --- |
| `ttl` | `number` | How long the stored rows stay usable, in milliseconds. Leave it out and the annotation does nothing, so the query is not cached |
| `skip` | `boolean` | Set it to `true` to send this one call to the database even though a `ttl` is set, which is how you force a refresh |
| `key` | `string` | Your own string to store the rows under, used as you wrote it, instead of the key the cache works out |

Because `cacheAnnotation` declares itself read-only with `applicableTo: ['read']`, putting it on a write such as `create`, `update`, or `delete` is rejected by TypeScript as you write the code and throws when the query runs, so you cannot cache a write by accident.

## How keys and hits work

The cache has to tell one of your reads apart from another, and unless you give it a `key` it works that out from the query itself. It hashes the statement as Prisma ORM finally turned it into SQL, together with the parameter values bound to that statement and the storage hash of your contract. So the same read with a different parameter value is stored separately, and a read is answered from the cache only when both the statement and its parameters match what was stored. Running a migration changes your contract's storage hash, which means everything cached before that migration can no longer answer queries against the new database schema.

A read answered from the cache is still visible to the rest of your middleware. Their `beforeQuery` hooks have already run by the time the cache is asked, the database driver and `onRow` are both skipped because no rows are arriving, and `afterQuery` then runs on every middleware with `result.source` set to `'middleware'` rather than `'driver'`, so your logging and metrics keep recording cached reads.

When you run a read inside a transaction, or on a connection you checked out yourself, it always goes to the database and the cache stays out of it. Code that holds a transaction or a connection expects to read back what it has just written, and that is what the cache leaves intact.

## Options

These are the options you pass to `createCacheMiddleware`:

| Option | Type | Default | What it controls |
| --- | --- | --- | --- |
| `maxEntries` | `number` | `1000` | How many entries the built-in in-memory store holds before it drops the ones it has gone longest without using. Read only when you leave `store` out |
| `store` | `CacheStore` | in-memory LRU | Your own place to keep cached rows, for example one backed by Redis |
| `clock` | `() => number` | `Date.now` | Where the cache reads the current time when it records `storedAt` on an entry it has committed. Working out when a `ttl` has run out is the store's job |

## Common gotchas

:::warning

The built-in store holds the rows in the memory of one process, so if you run two instances of your app each one keeps its own copy, and every deploy starts them empty again. That suits reads you run often and can afford to have slightly out of date, and it makes a poor source of truth. If you want your instances to share one cache, write a `store` against infrastructure they can all reach.

:::
