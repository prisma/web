## Introduction

A custom middleware is a plain object with a `name` and the hook functions you choose to implement, so there is no base class to extend and no registration API beyond the `middleware` array you already know from [How middleware works](/orm/middleware/how-middleware-works).

The middleware you build from scratch below is a query logger that prints every query with its row count and how long it took. You create one file, register it in one place, run a query, and see the output.

## Prerequisites

- A Prisma ORM project with a working `src/prisma/db.ts`. The [PostgreSQL quickstart](/prisma-orm/quickstart/postgresql) sets one up in a few minutes:

```npm
npm create prisma@latest -- --provider postgres
cd my-app
npm run db:init
```

## 1. Create the middleware

Create a new file next to your database setup. The logger needs only one hook: Prisma ORM calls `afterQuery` once after every query that returns rows, and gives it the outcome of that query, which is where the row count and the timing come from:

```ts title="src/prisma/query-logger.ts"
import type { SqlMiddleware } from "@prisma/orm-postgres/family-runtime";

export function queryLogger(): SqlMiddleware {
  return {
    name: "query-logger",
    familyId: "sql",

    async afterQuery(plan, result) {
      console.log(
        `[query-logger] ${result.rowCount} rows in ${Math.round(result.latencyMs)}ms · ${plan.sql}`,
      );
    },
  };
}
```

Queries that return rows are only one of the two paths a query can take through your middleware. Statements that go through `runtime.execute(plan)` report how many rows they affected instead of returning any, so they never reach `afterQuery` and end at `afterExecute` instead. To have the logger cover those as well, add a second hook that reads `result.stats.affectedRows`, which is the count that path reports:

```ts title="src/prisma/query-logger.ts (excerpt)"
    async afterExecute(plan, result) {
      const affected = result.completed ? result.stats.affectedRows : 0;
      console.log(
        `[query-logger] ${affected} affected in ${Math.round(result.latencyMs)}ms · ${plan.sql}`,
      );
    },
```

When you type the object as `SqlMiddleware`, TypeScript works out the parameter types of every hook for you, so you rarely have to import the argument types yourself. `familyId: "sql"` declares that this middleware is meant for SQL databases, and [step 5](#5-know-which-family-to-declare) covers when you need to set it.

## 2. Register it

You register a middleware by adding it to the `middleware` array where you create your client. This is the complete file after the change:

```ts title="src/prisma/db.ts"
import postgres from '@prisma/orm-postgres/runtime';
import { queryLogger } from './query-logger';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [queryLogger()],
});
```

That one line is all the setup there is, and every query on this client now passes through the logger, whether you wrote it with the ORM API or with the SQL query builder.

## 3. Run a query and see the output

To see the logger work, put a small script in `src/index.ts` that writes a row and then reads some back:

```ts title="src/index.ts"
import { db } from "./prisma/db";

await db.orm.public.User.create({
  email: `mia+${Date.now()}@prisma.io`,
  name: "Mia",
});

const users = await db.orm.public.User.select("id", "email").limit(5).all();
console.log(`fetched ${users.length} users`);

await db.close();
```

Run it:

```bash
npm run dev
```

The logger reports both queries, and prints the SQL that actually ran:

```text no-copy
[query-logger] 1 rows in 18ms · INSERT INTO "public"."user" ("email", "name", "updatedAt") VALUES ($1, $2, $3) RETURNING "user"."createdAt", "user"."email", "user"."id", "user"."name", "user"."updatedAt", "user"."username"
[query-logger] 1 rows in 17ms · SELECT "user"."id" AS "id", "user"."email" AS "email" FROM "public"."user" LIMIT 5
fetched 1 users
```

The `dev` script watches `src/index.ts` and keeps running after the output appears, so stop it with Ctrl+C when you are done. If you see the query result but no `[query-logger]` lines, then the query ran on a client that does not have the middleware registered, so check that your script imports `db` from the file you edited in step 2.

## 4. Add an option

Middleware you write for real work usually takes options, so give the logger a threshold in milliseconds and it reports only the queries that took longer than that:

```ts title="src/prisma/query-logger.ts"
import type { SqlMiddleware } from "@prisma/orm-postgres/family-runtime";

export interface QueryLoggerOptions {
  /** Only log queries slower than this many milliseconds. Default: 0, log everything. */
  readonly thresholdMs?: number;
}

export function queryLogger(options?: QueryLoggerOptions): SqlMiddleware {
  const thresholdMs = options?.thresholdMs ?? 0;

  return {
    name: "query-logger",
    familyId: "sql",

    async afterQuery(plan, result) {
      if (result.latencyMs < thresholdMs) return;
      console.log(
        `[query-logger] ${result.rowCount} rows in ${Math.round(result.latencyMs)}ms · ${plan.sql}`,
      );
    },
  };
}
```

Register it with a threshold:

```ts title="src/prisma/db.ts"
middleware: [queryLogger({ thresholdMs: 250 })],
```

Run the script again and the logger goes quiet, because both queries finish in under 250ms. Drop the threshold back to see them again.

Prisma ORM runs hooks in the order you registered them, and if one middleware throws, the ones after it never run. So register your logger before any middleware that can throw, such as `budgets`, and the queries you most want to see still get logged.

## 5. Know which family to declare

Prisma ORM sorts the databases it supports into two groups, which it calls families: `sql` is PostgreSQL and SQLite, and `mongo` is MongoDB. Set `familyId: 'sql'` when your middleware reads or writes something only a SQL database has, such as `plan.sql` in the logger above. If your middleware is then registered on a MongoDB client, Prisma ORM refuses it the first time that client is used, with an error whose `code` is `RUNTIME.MIDDLEWARE_FAMILY_MISMATCH`, rather than letting it fail later inside your hook.

Leave `familyId` out only when your middleware would work against either group, which means it uses hooks that both groups have, every hook except `beforeCompile`, and reads only the result fields that PostgreSQL and MongoDB both give it. A middleware written that way runs on PostgreSQL and on MongoDB, which is how the built-in [cache](/orm/middleware/built-in-cache) works.

You now have a working middleware that takes options. The other hooks, and the context object each of them receives, are what you reach for as your middleware grows.

## The hooks

`afterQuery` is one hook among several, and it belongs to only one of the two paths a query can take: a query that returns rows runs through one set of hooks, a write that returns no rows runs through another, and `beforeCompile` is the only hook on both paths. Implement whichever of them you need:

| Hook | Path | Runs | Use it to |
| --- | --- | --- | --- |
| `beforeCompile(draft, ctx)` | both | Before Prisma ORM turns the query into SQL | Rewrite the query, for example add a tenant filter |
| `beforeQuery(plan, ctx, params?)` | row query | Before the database driver runs it, once `plan.sql` is written out | Validate, throw to block, or adjust parameter values |
| `interceptQuery(plan, ctx)` | row query | Just before the database driver runs it | Return `{ rows }` to answer the query yourself |
| `onRow(row, plan, ctx)` | row query | Once per row | Count or sample rows, or throw to stop the query |
| `afterQuery(plan, result, ctx)` | row query | After the query finishes | Log `result.rowCount`, `result.latencyMs`, `result.completed`, `result.source` |
| `beforeExecute(plan, ctx, params?)` | write | Before the database driver runs it, once `plan.sql` is written out | Validate, throw to block, or adjust parameter values |
| `interceptExecute(plan, ctx)` | write | Just before the database driver runs it | Return `{ stats }` to answer the statement yourself |
| `afterExecute(plan, result, ctx)` | write | After the statement finishes | Log `result.stats.affectedRows`, `result.latencyMs`, `result.completed`, `result.source` |

There is no general-purpose `intercept` hook, and nothing falls back from one path to the other, so a middleware that wants to cover both registers the same function under both names. That is how `lints` and `budgets` apply to reads and writes alike.

[How middleware works](/orm/middleware/how-middleware-works#the-two-lifecycles) walks through the order with an animation. `beforeCompile` and `interceptQuery` are worth a closer look, because they change the query instead of only watching it.

### Rewrite queries with beforeCompile

`beforeCompile` is where you change a query before it runs. It receives the query as a typed syntax tree, before Prisma ORM turns that tree into SQL, so returning a new draft from it rewrites the query. The middleware below adds a condition to every `SELECT` on the `user` table:

```ts title="src/prisma/scope-user-selects.ts"
import type { SqlMiddleware } from '@prisma/orm-postgres/family-runtime';
import { AndExpr, type BinaryExpr } from '@prisma/orm-postgres/relational-core/ast';

export function scopeUserSelects(predicate: BinaryExpr): SqlMiddleware {
  return {
    name: 'scope-user-selects',
    familyId: 'sql',

    async beforeCompile(draft) {
      if (draft.ast.kind !== 'select') return undefined;
      if (draft.ast.from?.kind !== 'table-source') return undefined;
      if (draft.ast.from.name !== 'user') return undefined;
      const where = draft.ast.where ? AndExpr.of([draft.ast.where, predicate]) : predicate;
      return { ...draft, ast: draft.ast.withWhere(where) };
    },
  };
}
```

When you have nothing to change, return `undefined` and the query goes through unchanged. The draft one middleware returns is what the next middleware sees, so several rewrites stack up in the order you registered them.

### Answer queries with interceptQuery

`interceptQuery` lets your middleware answer a query itself, because when you return `{ rows }` from it, the database driver never runs. Caches, test fixtures, rate limiters, and circuit breakers all work this way. The rows you return are raw row objects, which Prisma ORM reads into values exactly as it would rows from the database, and `afterQuery` reports `source: 'middleware'`, so your logging can still tell which queries were answered without a trip to the database. For writes, `interceptExecute` does the same job and returns `{ stats }`. The [cache middleware](/orm/middleware/built-in-cache) is the implementation to copy from.

## The context object

Every hook receives a context object as its last argument, called `ctx`, which tells the hook what it needs to know about the query it is running inside:

| Field | What it gives you |
| --- | --- |
| `ctx.planExecutionId` | The same unique ID in every hook that runs for one query, so you can tie your observations together |
| `ctx.now()` | The clock Prisma ORM itself reads. Prefer it over `Date.now()` so that tests can control time |
| `ctx.scope` | `'runtime'`, `'connection'`, or `'transaction'`, so you can skip the work in a scope you should not touch |
| `ctx.mode` | `'strict'` or `'permissive'`, so you can throw in strict mode and warn otherwise |
| `ctx.contentHash(plan)` | A digest of the statement and its parameters that is the same every time for the same query, which makes it a cache key |
| `ctx.contract` | Your contract, for when a hook needs to know what your database schema looks like |
| `ctx.log` | `info`, `warn`, and `error` functions that send what you log to Prisma ORM's own logger |

On PostgreSQL, `ctx.mode` is always `'strict'`, because `postgres(...)` never passes a mode along and only `mongo(...)` takes one. The `postgres(...)` client also has no way yet to attach somewhere for logs to go, so what you send to `ctx.log` is not printed anywhere by default. For output you can see today, log directly to your own logger, the way the query logger above uses `console.log`.

## Common gotchas

:::warning

- If you throw from `afterQuery` after a query has succeeded, the call fails even though the database has already done the work, so keep that for cases where failing loudly is the point, the way the [budgets](/orm/middleware/built-in-budgets) latency check does.
- `afterQuery` and `afterExecute` also run when the database driver fails, and they get `result.completed` set to `false`. A failed write has no `result.stats`, so read it only when `result.completed` is true. Anything you throw while handling a failure is discarded, so that it cannot hide the error the driver reported.

:::
