## Introduction

A middleware you write yourself is a plain object: a `name`, plus the hook functions you want Prisma ORM to call around your queries. There is no base class to extend and no registration call, because you register a middleware by putting it in the `middleware` array where you create your client.

If you used `$use` in Prisma ORM 7, the `middleware` array is its replacement. There is no `next()`: you pick the hook that runs at the moment you care about. [Coming from Prisma ORM 7](/orm/coming-from-prisma-orm-7#not-available-yet) lists what changed.

The steps that follow build a query logger that prints every query with its row count and how long it took. You create one file, register it in one place, run a query, and see the output.

## Prerequisites

- A Prisma ORM project with a working `src/prisma/db.ts`, the file where the client is created, because that is where middleware is registered. If you already have a project, you can use the `db.ts` you have. The [PostgreSQL quickstart](/prisma-orm/quickstart/postgresql) sets a new one up in a few minutes:

```npm
npm create prisma@latest -- --provider postgres
cd my-app
npm run db:init
```

## 1. Create the middleware

Create a new file next to your database setup. The logger needs one hook, `afterQuery`, which Prisma ORM calls once after every query that returns rows. Its second argument is called `result`, and that is where the numbers come from: `result.rowCount` is how many rows came back, and `result.latencyMs` is how long the query took in milliseconds.

```ts title="src/prisma/query-logger.ts"
import type { SqlMiddleware } from "@prisma/orm-postgres/family-runtime";

export function queryLogger(): SqlMiddleware {
  return {
    name: "query-logger",
    familyId: "sql",

    async afterQuery(plan, result) {
      console.log(
        `[query-logger] ${result.rowCount} rows in ${Math.round(result.latencyMs)}ms · ${plan.sql}`,
      );
    },
  };
}
```

The first argument, `plan`, is the built query: the statement, its parameters, and some metadata, as a plain object, before it runs. `plan.sql` is the SQL text Prisma ORM sent to the database, which is what the logger prints.

The `SqlMiddleware` type comes from `@prisma/orm-postgres/family-runtime`, the part of the package that holds the middleware types together with the built-in `lints` and `budgets` middleware. Typing the object you return as `SqlMiddleware` is what gives `plan` and `result` their types in your editor, so you rarely have to import the argument types yourself. The other field, `familyId: "sql"`, says this middleware is written for SQL databases, and [step 5](#5-know-which-family-to-declare) covers when you need to set it.

Queries that return rows are one of the two routes a query can take through your middleware, and the other route is for calls that give you back a count instead of rows. Those calls never reach `afterQuery` and end at `afterExecute` instead. On the ORM API the counting calls are `createAndCount`, `updateAndCount`, and `deleteAndCount`, and with the SQL query builder they are whatever you hand to `db.runtime().execute(plan)`. Everything else, `create`, `update`, `delete`, `updateAll`, and `deleteAll` included, returns rows, because the SQL Prisma ORM writes for them ends in `RETURNING`.

To have the logger cover the counting calls as well, add a second hook inside the same returned object, next to `afterQuery`:

```ts title="src/prisma/query-logger.ts (excerpt)"
    async afterExecute(plan, result) {
      const affected = result.completed ? result.stats.affectedRows : 0;
      console.log(
        `[query-logger] ${affected} affected in ${Math.round(result.latencyMs)}ms · ${plan.sql}`,
      );
    },
```

`result.stats.affectedRows` is how many rows that statement changed. It is there only when the statement finished, which is what `result.completed` tells you, so read the count through the check above rather than on its own.

## 2. Register it

You register a middleware by adding it to the `middleware` array where you create your client. This is the complete file after the change:

```ts title="src/prisma/db.ts"
import postgres from '@prisma/orm-postgres/runtime';
import { queryLogger } from './query-logger';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [queryLogger()],
});
```

This is the `src/prisma/db.ts` that `create-prisma` generates, with the `middleware` option added. If you set your project up by hand, [The data contract](/orm/contract-authoring/the-data-contract) covers where `contract.json` and `contract.d.ts` come from.

That one line is all the setup there is, and every query on this client now passes through the logger, whether you wrote it with the ORM API (`db.orm.public.User...`) or with the SQL query builder, the lower-level API where you build the query yourself and run it on `db.runtime()`.

## 3. Run a query and see the output

To see the logger work, put a small script in `src/index.ts` that writes a row and then reads some back:

```ts title="src/index.ts"
import { db } from "./prisma/db";

await db.orm.public.User.create({
  email: `mia+${Date.now()}@prisma.io`,
  name: "Mia",
});

const users = await db.orm.public.User.select("id", "email").limit(5).all();
console.log(`fetched ${users.length} users`);

await db.close();
```

In a project from the quickstart, the `dev` script is `tsx watch src/index.ts`, so running it runs your script and then keeps watching the file:

```bash
npm run dev
```

The logger reports both queries, and prints the SQL that actually ran:

```text no-copy
[query-logger] 1 rows in 18ms · INSERT INTO "public"."user" ("email", "name", "updatedAt") VALUES ($1, $2, $3) RETURNING "user"."createdAt", "user"."email", "user"."id", "user"."name", "user"."updatedAt", "user"."username"
[query-logger] 1 rows in 17ms · SELECT "user"."id" AS "id", "user"."email" AS "email" FROM "public"."user" LIMIT 5
fetched 1 users
```

Both lines came through `afterQuery`, the `create` included: `create` is a write, but its SQL ends in `RETURNING`, so it returns the row it inserted and takes the row route like any read.

The `dev` script keeps running after the output appears, so stop it with Ctrl+C when you are done. If you see the query result but no `[query-logger]` lines, then the query ran on a client that does not have the middleware registered, so check that your script imports `db` from the file you edited in step 2.

## 4. Add an option

Middleware you write for real work usually takes options, so give the logger a threshold in milliseconds and it reports only the queries that took longer than that. The file below shows `afterQuery` on its own to keep the change easy to see. If you added `afterExecute` in step 1, keep it where it is:

```ts title="src/prisma/query-logger.ts"
import type { SqlMiddleware } from "@prisma/orm-postgres/family-runtime";

export interface QueryLoggerOptions {
  /** Only log queries slower than this many milliseconds. Default: 0, log everything. */
  readonly thresholdMs?: number;
}

export function queryLogger(options?: QueryLoggerOptions): SqlMiddleware {
  const thresholdMs = options?.thresholdMs ?? 0;

  return {
    name: "query-logger",
    familyId: "sql",

    async afterQuery(plan, result) {
      if (result.latencyMs < thresholdMs) return;
      console.log(
        `[query-logger] ${result.rowCount} rows in ${Math.round(result.latencyMs)}ms · ${plan.sql}`,
      );
    },
  };
}
```

Register it with a threshold:

```ts title="src/prisma/db.ts"
middleware: [queryLogger({ thresholdMs: 250 })],
```

Run the script again and the logger goes quiet, because both queries finish in under 250ms. Drop the threshold back to see them again.

Prisma ORM calls your hooks in the order you listed the middleware in the array, and it waits for each hook to finish before the query moves on, so a slow `afterQuery` delays the `await` in your own code. If one middleware throws, the ones after it never run, so register your logger before any middleware that can throw, such as [budgets](/orm/middleware/built-in-budgets), and the queries you most want to see still get logged.

## 5. Know which family to declare

Prisma ORM sorts databases into two groups it calls families, SQL and MongoDB, and `familyId: 'sql'` on a middleware means it works with SQL databases only. Set it when your middleware reads or writes something only a SQL database has, such as `plan.sql` in the logger above.

If a middleware that declares `familyId: 'sql'` is registered on a MongoDB client, that client throws the first time it needs to talk to the database, before it sends any query. The error's `code` is `RUNTIME.MIDDLEWARE_FAMILY_MISMATCH` and the message names the middleware, so you find out at the first query you run rather than from a failure inside your hook much later.

Leave `familyId` out when your middleware stays away from everything specific to one kind of database: use any hook except `beforeCompile`, which only SQL databases have, and read the `result` fields your hook is handed (`rowCount`, `latencyMs`, `completed`, `source`, and `stats.affectedRows`) rather than `plan.sql` or `plan.ast`, which a SQL query has and a MongoDB query does not. A middleware written that way runs on PostgreSQL and on MongoDB, which is how the built-in [cache](/orm/middleware/built-in-cache) works.

You now have a working middleware that takes options. The other hooks, and the context object each of them receives, are what you reach for as your middleware grows.

## The hooks

Which hooks Prisma ORM calls depends on what your call gives back. A call that returns rows runs one set of hooks, a call that returns only a count runs a shorter set, and `beforeCompile` is the only hook that runs on both. Implement whichever of them you need:

| Hook | Route | Runs | Use it to |
| --- | --- | --- | --- |
| `beforeCompile(draft, ctx)` | both | Before Prisma ORM turns the query into SQL text | Rewrite the query, for example add a tenant filter |
| `beforeQuery(plan, ctx, params?)` | returns rows | After the SQL text has been built, before the database driver runs it | Validate, throw to block, or change parameter values |
| `interceptQuery(plan, ctx)` | returns rows | Just before the database driver runs it | Return `{ rows }` to answer the query yourself |
| `onRow(row, plan, ctx)` | returns rows | Once per row | Count or sample rows, or throw to stop the query |
| `afterQuery(plan, result, ctx)` | returns rows | After the query finishes | Log `result.rowCount`, `result.latencyMs`, `result.completed`, `result.source` |
| `beforeExecute(plan, ctx, params?)` | returns a count | After the SQL text has been built, before the database driver runs it | Validate, throw to block, or change parameter values |
| `interceptExecute(plan, ctx)` | returns a count | Just before the database driver runs it | Return `{ stats }` to answer the statement yourself |
| `afterExecute(plan, result, ctx)` | returns a count | After the statement finishes | Log `result.stats.affectedRows`, `result.latencyMs`, `result.completed`, `result.source` |

`result.source` is `'driver'` when the database answered the query and `'middleware'` when a middleware answered it instead. Throwing from `onRow` fails the call with your error, and the rows still to come are not passed on to your code.

A hook you implement on one route is never called for a call that took the other, so a middleware that needs to cover both implements a hook on each. `lints` and `budgets` do this by assigning the same function to `beforeQuery` and `beforeExecute`, which works because those two hooks take the same arguments and return nothing. The intercept hooks cannot be shared that way, because `interceptQuery` returns `{ rows }` and `interceptExecute` returns `{ stats }`.

[How middleware works](/orm/middleware/how-middleware-works#the-two-lifecycles) walks through the order with an animation. `beforeCompile` and `interceptQuery` are worth a closer look, because they change the query instead of only watching it.

### Rewrite queries with beforeCompile

`beforeCompile` is where you change a query before it runs. It gives you the query as a tree of typed objects, one object per part of the statement, and it runs before Prisma ORM turns that tree into SQL text, so a changed tree changes the SQL that reaches the database. Its argument is called a draft because the SQL text does not exist yet: a draft has `ast`, the tree, and `meta`, the metadata Prisma ORM keeps about the query. You return a copy of the draft with a new `ast`, or `undefined` when there is nothing to change.

The middleware below adds a condition to every `SELECT` on the `user` table:

```ts title="src/prisma/scope-user-selects.ts"
import type { SqlMiddleware } from '@prisma/orm-postgres/family-runtime';
import { AndExpr, type BinaryExpr } from '@prisma/orm-postgres/relational-core/ast';

export function scopeUserSelects(predicate: BinaryExpr): SqlMiddleware {
  return {
    name: 'scope-user-selects',
    familyId: 'sql',

    async beforeCompile(draft) {
      if (draft.ast.kind !== 'select') return undefined;
      if (draft.ast.from?.kind !== 'table-source') return undefined;
      if (draft.ast.from.name !== 'user') return undefined;
      const where = draft.ast.where ? AndExpr.of([draft.ast.where, predicate]) : predicate;
      return { ...draft, ast: draft.ast.withWhere(where) };
    },
  };
}
```

The name it checks, `'user'`, is the table name in your database rather than the model name in your contract, because by this point the query is expressed in tables and columns.

The condition itself is an object you build from the same classes, and you pass it in when you register the middleware:

```ts title="src/prisma/db.ts"
import postgres from '@prisma/orm-postgres/runtime';
import { BinaryExpr, ColumnRef, ParamRef } from '@prisma/orm-postgres/relational-core/ast';
import { scopeUserSelects } from './scope-user-selects';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

const onlyMia = BinaryExpr.eq(
  ColumnRef.of('user', 'name'),
  ParamRef.of('Mia', { codec: { codecId: 'pg/text@1' } }),
);

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [scopeUserSelects(onlyMia)],
});
```

Every `SELECT` on `user` now runs with `WHERE "user"."name" = $1` added, and a query that already had a `WHERE` clause keeps it, joined to yours with `AND`. Swap `name` for whatever column holds your tenant to get the tenant filter.

Put values through `ParamRef.of` rather than `LiteralExpr.of`: a `ParamRef` becomes a bound parameter such as `$1`, while a literal is written into the SQL text itself, which is how untrusted input turns into SQL injection. A `ParamRef` you build by hand has to say how the value is stored, with `codec: { codecId: ... }`, because the query builder is not there to fill it in for you. `pg/text@1` is the id for a `text` column, and without it the query fails with an error whose `code` is `RUNTIME.PARAM_REF_MISSING_CODEC`. `BinaryExpr` has one method per comparison (`eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `like`, `in`, `notIn`), and `AndExpr.of` and `OrExpr.of` combine conditions. They all come from `@prisma/orm-postgres/relational-core/ast`, so your editor lists them once you import from there.

The draft one middleware returns is what the next middleware sees, so several rewrites stack up in the order you registered them.

### Answer queries with interceptQuery

`interceptQuery` lets your middleware answer a query itself: return `{ rows }` from it and the database driver never runs. Caches, test fixtures, and circuit breakers all work this way.

The rows you return are raw row objects, keyed by the column aliases in the SQL, exactly as the driver would hand them over before Prisma ORM converts the values. That is the same shape `onRow` receives, so the way to see what a row looks like for a query of yours is to log it from `onRow` first:

```ts
async onRow(row) {
  console.log(row);
},
```

For the `SELECT` in step 3, whose SQL is `SELECT "user"."id" AS "id", "user"."email" AS "email" FROM "public"."user" LIMIT 5`, a row object has an `id` key and an `email` key. Returning objects of that shape from `interceptQuery` gives your caller the same typed result it would have got from the database:

```ts
async interceptQuery(plan) {
  if (!plan.sql.includes('FROM "public"."user"')) return undefined;
  return { rows: [{ id: 1, email: 'mia@prisma.io' }] };
},
```

Return `undefined` and the query carries on to the database as usual. When several middleware implement `interceptQuery`, the first one in the array that returns rows answers the query and the rest are not called at all. `afterQuery` still runs either way, with `result.source` set to `'middleware'`, so your logging can tell which queries were answered without a trip to the database. For the counting route, `interceptExecute` does the same job and returns `{ stats }`, for example `{ stats: { affectedRows: 0 } }`. The [cache middleware](/orm/middleware/built-in-cache) is the implementation to copy from.

## The context object

Every hook receives a context object called `ctx`, which tells the hook what it needs to know about the query it is running inside. It comes after the plan, and after the result in `afterQuery` and `afterExecute`. A hook may declare fewer arguments than the full signature shows, which is why `afterQuery(plan, result)` in the logger above compiles without naming `ctx` at all.

| Field | What it gives you |
| --- | --- |
| `ctx.planExecutionId` | The same unique ID in every hook that runs for one query |
| `ctx.now()` | The current time in milliseconds, from a clock your tests can control |
| `ctx.scope` | Where the query is running: `'runtime'`, `'connection'`, or `'transaction'` |
| `ctx.mode` | `'strict'` or `'permissive'`. On PostgreSQL it is always `'strict'`, because `postgres(...)` has no way to set it |
| `ctx.contentHash(plan)` | A string that is the same for every query with the same statement and parameters |
| `ctx.contract` | Your contract, for when a hook needs to know what your database looks like |
| `ctx.log` | `info`, `warn`, and `error` functions that send what you log to Prisma ORM's own logger |

`ctx.planExecutionId` is how you match a line your `beforeQuery` logged to the line your `afterQuery` logged for the same query. `ctx.scope` is `'runtime'` for a query you sent on `db` directly, `'transaction'` inside `db.transaction(...)`, and `'connection'` on a connection you checked out yourself, which is how the cache knows to leave queries inside a transaction alone. `ctx.contentHash(plan)` returns a promise, so `await` it, and the string it gives back can be used directly as a cache key.

`ctx.log` has nowhere to send anything on PostgreSQL today, because `postgres(...)` takes no option for attaching a log handler, so nothing you pass to it is printed. Use your own logger for output you can see, the way the query logger above uses `console.log`.

`beforeQuery` and `beforeExecute` take one more argument after `ctx`, called `params`, which lets you read and replace the bound parameter values before they are sent to the database. Leave it out of your parameter list when you do not need it.

## Common gotchas

:::warning

- If you throw from `afterQuery` after a query has succeeded, the call fails even though the database has already done the work, so keep that for cases where failing loudly is the point, the way the [budgets](/orm/middleware/built-in-budgets) latency check does.
- `afterQuery` and `afterExecute` also run when the database driver fails, and they get `result.completed` set to `false`. A failed write has no `result.stats`, so read it only when `result.completed` is true.
- If your hook throws while it is handling a failure like that, Prisma ORM discards your error and your caller still sees the failure the driver reported.

:::
