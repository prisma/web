Middleware lets you run your own code around every query your app sends through Prisma ORM.

For example, you can log every query with its latency, block a `DELETE` that has no `WHERE` clause before it reaches the database, or serve a repeated read from memory instead of running it again. You write the policy once, register it once, and every query follows it, with no call sites to update.

A middleware is a plain object with a name and one or more hooks, and a hook is a function that Prisma ORM calls at a fixed moment around a query. You register the whole object once, in the `middleware` option of your client setup:

```ts title="src/prisma/db.ts"
import { createCacheMiddleware } from '@prisma/orm-extension-middleware-cache';
import postgres from '@prisma/orm-postgres/runtime';
import { budgets, lints } from '@prisma/orm-postgres/family-runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [
    createCacheMiddleware({ maxEntries: 1_000 }),
    lints(),
    budgets({ maxRows: 10_000, maxLatencyMs: 1_000 }),
  ],
});
```

Every query goes through that list, whether you wrote it with the ORM API or with the SQL query builder, because both kinds of query are sent by the same `db` object. If your database is MongoDB, pass the same `middleware` option to `mongo(...)` from `@prisma/orm-mongo/runtime`.

Your app talks to the database, and your middleware is in between, so it can let a query through, block it, or answer it itself:

## When your hooks run [#the-two-lifecycles]

You write only the hooks you care about, and Prisma ORM skips the ones you leave out. Which hooks it calls depends on what kind of query you ran, because a query that returns rows and a statement that only reports how many rows it changed take different routes through the library.

**A row query** is anything that returns rows, whether you wrote it with the ORM API or ran it with `runtime.query(plan)`. Its hooks run in this order:

`beforeCompile` → `beforeQuery` → `interceptQuery` → `onRow` (once per row) → `afterQuery`

**A non-returning write** is a statement you run through `runtime.execute(plan)`, which reports how many rows it affected rather than returning them. It runs a shorter sequence:

`beforeCompile` → `beforeExecute` → `interceptExecute` → `afterExecute`

There is no general `intercept` hook that covers both routes, and no fallback from one to the other, so a middleware that needs to act on both registers the same function under both names. `lints` and `budgets` both do exactly that.

<ConceptAnimation name="middleware-lifecycle" />

At each step Prisma ORM calls that hook on every middleware you registered, in the order you listed them in the `middleware` array.

### beforeCompile: rewrite the query

Reach for `beforeCompile` when you want to change what a query asks for rather than only look at it. It runs on both routes, early enough that the query is still a tree of typed objects and has not been turned into SQL text yet, so you can return a changed copy and Prisma ORM will use that instead, for example to add a tenant filter to every `SELECT`. Because it works on that tree of SQL objects, the hook exists on SQL databases only.

### beforeQuery and beforeExecute: validate or block

These two hooks are where you inspect a query and refuse it. `beforeQuery` runs on the row-query route and `beforeExecute` on the write route, both after the SQL text has been rendered and before anything reaches the database. Your hook receives the query itself, so you can read the SQL text in `plan.sql` and the same query as objects in `plan.ast`. Throwing from the hook blocks the query:

```ts
async beforeQuery(plan) {
  if (isForbidden(plan)) throw new Error("blocked by policy");
}
```

This is where `lints` stops a `DELETE` without `WHERE`, and where `budgets` rejects a query that would read too many rows. Both middleware register the same function under both names, so the check applies to reads and writes alike. Either hook can also adjust parameter values before they are encoded for the driver.

### interceptQuery and interceptExecute: answer without the database

These hooks let you answer a query yourself, so the database never sees it. They are the last thing to run before the driver takes over: return `{ rows }` from `interceptQuery`, or `{ stats }` from `interceptExecute`, and that is what your caller gets back, but return nothing and the operation carries on to the driver as usual. This is how the cache serves repeated reads. Anything you checked in `beforeQuery` has already run by the time either hook is called.

### onRow: watch rows arrive

`onRow` lets you see each row as your own code receives it. It runs once per row on the row-query route, as rows are handed to your loop, so you can count them, sample them, or throw to abort part way through. `budgets` uses it to stop a query once it has returned more rows than its `maxRows` budget allows. It does not run on the write route, and it does not run for rows that an `interceptQuery` hook answered.

### afterQuery and afterExecute: observe the finished operation

These two hooks are for recording what happened once the work is over. Prisma ORM calls them once at the end of the operation, whether it succeeded or failed.

On the row-query route, `afterQuery` receives `result.rowCount`, `result.completed`, `result.latencyMs`, and `result.source`, which is `'driver'` for a normal query and `'middleware'` when an `interceptQuery` answered it, so you can tell where the rows came from.

On the write route, `afterExecute` receives `result.completed`, `result.latencyMs`, and `result.source`, and on a completed run the number of rows it changed in `result.stats.affectedRows`. There is no `rowCount` here, because the statement never returned rows.

Timing, logging, and latency budgets all belong in these two hooks.

The order you list middleware in is the order Prisma ORM calls them at every hook, so if one middleware rewrites the query in `beforeCompile`, the next middleware sees the rewritten version. That order also decides who answers a query: when several middleware implement `interceptQuery`, the first one that returns rows is the one that wins, and the same holds for `interceptExecute`.

## What ships built in

`@prisma/orm-postgres` already contains [lints](/orm/middleware/built-in-lints), which blocks risky query shapes, and [budgets](/orm/middleware/built-in-budgets), which caps row counts and reports slow queries, so you can register either one without installing anything else. Middleware that ships as its own package is an extension like any other, and the [extension directory](https://www.prisma.io/extensions) lists those, including middleware written by the community:

| Name | What it adds | Package | Databases | By |
| --- | --- | --- | --- | --- |
| [Cache middleware](https://www.prisma.io/extensions/middleware-cache) | Serve repeated reads from an in-memory or pluggable cache, opted in per query. | `@prisma/orm-extension-middleware-cache` | PostgreSQL, MongoDB | Prisma |
{/* extensions-catalog:end */}

If none of them do what you need, the [authoring guide](/orm/middleware/authoring-custom-middleware) builds a working query logger step by step. Once your own middleware is on npm, [submit it to the directory](https://www.prisma.io/extensions/submit) so other Prisma ORM users can find it.

## Which databases a middleware runs on

A middleware cannot always work on every database, so each one declares which kind of database it was written for. Prisma ORM sorts databases into two groups it calls families: the SQL family, which is PostgreSQL and the other SQL databases, and the document family, which is MongoDB. A middleware that inspects SQL text or the tree of SQL objects behind a query only makes sense on SQL databases, so it says so with `familyId: 'sql'`.

- `budgets` and `lints` declare `familyId: 'sql'`. They register on PostgreSQL and are rejected on MongoDB.
- The cache declares no `familyId`. It works only on the parts of a query that are the same on both kinds of database, so it runs on PostgreSQL and on MongoDB.

Prisma ORM makes this check the first time your client needs to talk to the database, so a middleware registered against a database it was not written for fails there with an error whose `code` is `RUNTIME.MIDDLEWARE_FAMILY_MISMATCH`, before it ever sends a query.

## When a middleware or the driver throws

When your hook throws from `beforeCompile`, `beforeQuery`, `beforeExecute`, `interceptQuery`, `interceptExecute`, or `onRow`, the whole operation fails: your caller gets the error you threw, and the database work stops.

When the driver is the thing that fails, Prisma ORM still calls `afterQuery` on every middleware, or `afterExecute` on the write route, with `result.completed` set to `false`, so your logging sees failed queries as well as successful ones. If one of those hooks throws while it is handling a failure, that error is discarded, so what the caller sees is still the original failure.
