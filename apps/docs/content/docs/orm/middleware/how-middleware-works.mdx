Middleware lets you run your own code around every query your app sends through Prisma ORM.

For example, you can log every query with its latency, block a `DELETE` that has no `WHERE` clause before it reaches the database, or serve a repeated read from memory instead of running it again. You write the policy once, register it once, and every query follows it, with no call sites to update.

If you used `$use` in Prisma ORM 7, the `middleware` array is its replacement. There is no `next()`: you pick the hook that runs at the moment you care about. [Coming from Prisma ORM 7](/orm/coming-from-prisma-orm-7#not-available-yet) lists what changed.

A middleware is a plain object with a name and one or more hooks, and a hook is a function that Prisma ORM calls at a fixed moment around a query. You register the whole object once, in the `middleware` option of your client setup:

```ts title="src/prisma/db.ts"
import { createCacheMiddleware } from '@prisma/orm-extension-middleware-cache';
import postgres from '@prisma/orm-postgres/runtime';
import { budgets, lints } from '@prisma/orm-postgres/family-runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  middleware: [
    createCacheMiddleware({ maxEntries: 1_000 }),
    lints(),
    budgets({ maxRows: 10_000, maxLatencyMs: 1_000 }),
  ],
});
```

This is the `src/prisma/db.ts` that `create-prisma` generates, with the `middleware` option added. If you set your project up by hand, [The data contract](/orm/contract-authoring/the-data-contract) covers where `contract.json` and `contract.d.ts` come from. The client itself, `postgres(...)`, comes from `@prisma/orm-postgres/runtime`, while `lints` and `budgets` come from `@prisma/orm-postgres/family-runtime`, which is also where the `SqlMiddleware` type is when you write your own.

Writing your own middleware means writing that same kind of object. Here is a complete one that prints every query it sees:

```ts title="src/prisma/query-logger.ts"
import type { SqlMiddleware } from '@prisma/orm-postgres/family-runtime';

export function queryLogger(): SqlMiddleware {
  return {
    name: 'query-logger',
    familyId: 'sql',

    async afterQuery(plan, result) {
      console.log(`${result.rowCount} rows in ${Math.round(result.latencyMs)}ms · ${plan.sql}`);
    },
  };
}
```

Add `queryLogger()` to the `middleware` array in `src/prisma/db.ts`, alongside the built-in middleware or on its own, and every query on that client runs through it. The [authoring guide](/orm/middleware/authoring-custom-middleware) builds this logger step by step, with the options and the other hooks.

Every query goes through that list, whether you wrote it with the ORM API (`db.orm.public.User...`) or with the SQL query builder, the lower-level API where you build the query yourself and run it on `db.runtime()`. Both kinds of query are sent by the same `db` object, so both see the same middleware. If your database is MongoDB, pass the same `middleware` option to `mongo(...)` from `@prisma/orm-mongo/runtime`.

Your app talks to the database, and your middleware is in between, so it can let a query through, block it before the database sees it, or answer it itself and return rows the database never produced:

## When your hooks run [#the-two-lifecycles]

You write only the hooks you care about, and Prisma ORM skips the ones you leave out. Which hooks it calls depends on what your query gives back: if the query returns rows, one set of hooks runs, and if it only reports how many rows it changed, a shorter set runs instead.

**A row query** is anything that returns rows. On the ORM API that is nearly every call, `create`, `update`, and `delete` included, because the SQL Prisma ORM writes for them ends in `RETURNING`. It is also what you get from `db.runtime().query(plan)`, where a plan is the built query: the statement, its parameters, and some metadata, as a plain object, before it runs. A row query calls your hooks in this order:

`beforeCompile` → `beforeQuery` → `interceptQuery` → `onRow` (once per row) → `afterQuery`

**A non-returning write** is a statement that reports how many rows it affected rather than returning them. On the ORM API those are `createAndCount`, `updateAndCount`, and `deleteAndCount`, and with the SQL query builder it is whatever you hand to `db.runtime().execute(plan)`. These run a shorter sequence:

`beforeCompile` → `beforeExecute` → `interceptExecute` → `afterExecute`

If your middleware needs to act on reads and writes both, register the same function twice, once under each name, because nothing falls back from one set of hooks to the other. `lints` and `budgets` both do exactly that.

<ConceptAnimation name="middleware-lifecycle" />

At each step Prisma ORM calls that hook on every middleware you registered, in the order you listed them in the `middleware` array, and it waits for each one to finish before the query moves on. A hook can be `async`, so a slow `afterQuery` delays the `await` in your own code.

### beforeCompile: rewrite the query

Reach for `beforeCompile` when you want to change what a query asks for rather than only look at it. It runs before the query becomes SQL text, on both kinds of query, and it gives you the query as a tree of typed objects, one object per part of the statement. Return a changed copy of that tree and Prisma ORM runs your version instead, which is how you add a tenant filter to every `SELECT` without editing a single call site. Return nothing and the query goes through as written. [Rewrite queries with beforeCompile](/orm/middleware/authoring-custom-middleware#rewrite-queries-with-beforecompile) has a working tenant filter to copy. `beforeCompile` is not available on MongoDB, because the tree it works on is made of SQL objects.

### beforeQuery and beforeExecute: validate or block

These two hooks are where you inspect a query and refuse it. `beforeQuery` runs on a row query and `beforeExecute` on a non-returning write, both after the SQL text has been written out and before anything reaches the database. Your hook receives the built query, so you can read the SQL text in `plan.sql` and read the same query as objects in `plan.ast`, which is the same tree of typed objects `beforeCompile` works on. Throwing from the hook blocks the query, and returning normally lets it carry on to the database:

```ts
async beforeQuery(plan) {
  if (isForbidden(plan)) throw new Error("blocked by policy");
}
```

This is where `lints` stops a `DELETE` without `WHERE`, and where `budgets` rejects a query that would read too many rows. Both middleware register the same function under both names, so the check applies to reads and writes alike.

Either hook can also change the values the query sends, and it does that through a third argument, `params`, which you declare as `beforeQuery(plan, ctx, params)` when you want it. Call `params.entries()` to walk the values the query carries and `params.replaceValue(ref, newValue)` to swap one of them for another, and what you put there is what the database receives. Write the hook as `beforeQuery(plan)` instead and nothing about the values changes.

### interceptQuery and interceptExecute: answer without the database

These hooks let you answer a query yourself, so the database never sees it. They are the last thing to run before the database driver takes over: return `{ rows }` from `interceptQuery`, or `{ stats }` from `interceptExecute`, and that is what your caller gets back, but return nothing and the query carries on to the driver as usual. The rows you return are raw row objects, keyed by the column aliases in the SQL, exactly as the driver would return them before Prisma ORM converts the values, which is the same shape `onRow` below hands you. This is how the cache serves repeated reads. Anything you checked in `beforeQuery` has already run by the time either hook is called.

### onRow: watch rows arrive

`onRow` lets you see each row of a result on its way to your code. Prisma ORM calls it once for every row as it reads the result, before your `.all()` or `.first()` call returns, so you can count rows, sample them, or throw to stop the query part way through. `budgets` uses it to stop a query once it has returned more rows than its `maxRows` budget allows. It does not run on a non-returning write, and it does not run for rows that an `interceptQuery` hook answered.

### afterQuery and afterExecute: observe the finished operation

These two hooks are for recording what happened once the work is over. Prisma ORM calls them once at the end of the operation, whether it succeeded or failed.

After a row query, `afterQuery` receives `result.rowCount`, `result.completed`, `result.latencyMs`, and `result.source`, which is `'driver'` for a normal query and `'middleware'` when an `interceptQuery` answered it, so you can tell where the rows came from.

After a non-returning write, `afterExecute` receives `result.completed`, `result.latencyMs`, and `result.source`, and on a completed run the number of rows it changed in `result.stats.affectedRows`. There is no `result.rowCount` on this one.

Timing, logging, and latency budgets all belong in these two hooks.

The order you list middleware in is the order Prisma ORM calls them at every hook, so if one middleware rewrites the query in `beforeCompile`, the next middleware sees the rewritten version. The after-hooks follow that same order rather than unwinding in reverse, so the middleware at index 0 is the first to log. Order also decides who answers a query: when several middleware implement `interceptQuery`, the first one that returns rows wins and the rest are not called at all, and the same holds for `interceptExecute`.

## What ships built in

`@prisma/orm-postgres` already contains [lints](/orm/middleware/built-in-lints), which blocks risky query shapes, and [budgets](/orm/middleware/built-in-budgets), which caps row counts and reports slow queries, so you can register either one without installing anything else. Middleware that ships as its own package is an extension like any other, and the [extension directory](https://www.prisma.io/extensions) lists those, including middleware written by the community:

{/* extensions-catalog:start tag=middleware source=official */}
| Name | What it adds | Package | Databases | By |
| --- | --- | --- | --- | --- |
| [Cache middleware](https://www.prisma.io/extensions/middleware-cache) | Serve repeated reads from an in-memory or pluggable cache, opted in per query. | `@prisma/orm-extension-middleware-cache` | PostgreSQL, MongoDB | Prisma |
{/* extensions-catalog:end */}

Nothing is cached until you say so on a query, which you do by attaching `cacheAnnotation({ ttl: 60_000 })` to that one read, where `ttl` is how many milliseconds its rows stay usable. [Opt a query in](/orm/middleware/built-in-cache#opt-a-query-in) shows the call for the ORM API and for the SQL query builder.

If none of them do what you need, the [authoring guide](/orm/middleware/authoring-custom-middleware) builds a working query logger step by step. Once your own middleware is on npm, [submit it to the directory](https://www.prisma.io/extensions/submit) so other Prisma ORM users can find it.

## Which databases a middleware runs on

A middleware cannot always work on every database, so each one declares which kind of database it was written for. Prisma ORM sorts databases into two groups it calls families, SQL and MongoDB, and `familyId: 'sql'` on a middleware means it works with SQL databases only. That key goes next to `name` in the middleware object, the way `queryLogger` sets it.

- `budgets` and `lints` declare `familyId: 'sql'`. They register on PostgreSQL and are rejected on MongoDB.
- The cache declares no `familyId`. It works only on the parts of a query that are the same on both kinds of database, so it runs on PostgreSQL and on MongoDB.

If you register a middleware against a database it was not written for, the first time your client needs to talk to that database it fails with an error whose `code` is `RUNTIME.MIDDLEWARE_FAMILY_MISMATCH`, and no query of yours has run by then.

## When a middleware or the driver throws

When your hook throws from `beforeCompile`, `beforeQuery`, `beforeExecute`, `interceptQuery`, `interceptExecute`, or `onRow`, the whole operation fails: your caller gets the error you threw, and the database work stops.

When the database driver is the thing that fails, Prisma ORM still calls `afterQuery` on every middleware, or `afterExecute` after a non-returning write, with `result.completed` set to `false`, so your logging sees failed queries as well as successful ones. A throw from `afterQuery` or `afterExecute` while it is handling a failure cannot hide the real error: your caller still gets the failure the driver reported.
