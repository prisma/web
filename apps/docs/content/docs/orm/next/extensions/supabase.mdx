The Supabase extension teaches Prisma 8 what Supabase owns in your database. It ships a complete external contract of the `auth` and `storage` schemas and the three platform roles, so your application contract can declare a real foreign key into `auth.users` and Row Level Security policies that Prisma migrates like any other schema object. At runtime, a role-bound client executes every query as the Supabase role your request represents: `authenticated`, `anon`, or `service_role`.

By the end of this guide you will have a `Note` model owned by a Supabase Auth user, four RLS policies declared in your Prisma schema and applied by a Prisma migration, and a verified check that users can only reach their own rows.

## Feature status

The Supabase extension is part of Prisma 8, available in Early Access. The extension supports contract references to `auth.*` and `storage.*` tables, RLS policy authoring in PSL and TypeScript, role-bound query execution with JWT verification, and a `service_role`-only admin root for reading Supabase-internal tables. Realtime, Storage uploads, PostgREST interop, and edge runtimes are not covered; keep using `supabase-js` for those subsystems.

## Prerequisites

- Node.js 24 or later
- A Supabase project on a current platform version
- Your project's session pooler connection string (Dashboard > Connect > Session pooler), project URL, and database password

Use the session pooler on port 5432 or the direct IPv6 connection. The transaction pooler on port 6543 does not work because role binding relies on session-scoped `set_config`.

## 1. Initialize a Prisma 8 project

Scaffold the config, schema, and runtime files. This installs the `@prisma/orm-postgres` facade and emits your first contract.

```bash
npx prisma-next@0.17.0 init --yes --target postgres --authoring psl
```

You now have `prisma-next.config.ts`, a starter schema at `src/prisma/contract.prisma`, and a `.env.example`. If your `package.json` declares `"type": "commonjs"`, change it to `"module"`; the scaffolded runtime file uses ESM import attributes.

## 2. Install the Supabase extension

```bash
npm install @prisma/orm-extension-supabase@0.17.0
```

Prisma 8 installs as the `prisma-next` CLI plus exactly one database facade per app. This guide was tested with `prisma-next@0.17.0`, `@prisma/orm-postgres@0.17.0`, and `@prisma/orm-extension-supabase@0.17.0`.

## 3. Configure the connection

Set `DATABASE_URL` in `.env` to the session pooler string:

```bash title=".env"
DATABASE_URL="postgresql://postgres.YOUR_PROJECT_REF:YOUR_DB_PASSWORD@aws-0-YOUR_REGION.pooler.supabase.com:5432/postgres"
SUPABASE_URL="https://YOUR_PROJECT_REF.supabase.co"
```

If connections to `db.YOUR_PROJECT_REF.supabase.co` fail with a DNS error, your network has no IPv6 route; the pooler host works over IPv4.

## 4. Register the extension

Compose the Supabase pack into your config so the extension's contract joins yours at emit time:

```ts title="prisma-next.config.ts"
import 'dotenv/config';
import supabasePack from '@prisma/orm-extension-supabase/pack';
import { defineConfig } from '@prisma/orm-postgres/config';

export default defineConfig({
  contract: './src/prisma/contract.prisma',
  extensions: [supabasePack],
  migrations: {
    dir: 'migrations',
  },
  db: {
    connection: process.env['DATABASE_URL']!,
  },
});
```

The extension's contract is external: Prisma knows the exact shape of `auth.users` and its neighbors but never generates DDL for them.

## 5. Reference auth.users and declare RLS

Replace the starter schema. The `supabase:` prefix on the relation type names the extension's contract space; `@@rls` enables Row Level Security; the `policy_*` blocks declare named policies with the same `USING` and `WITH CHECK` predicates you would write in SQL.

```prisma title="src/prisma/contract.prisma"
namespace public {
  model Note {
    id        Uuid        @id @default(uuid())
    title     String
    body      String?
    userId    Uuid
    user      supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
    createdAt Timestamptz @default(now())

    @@map("note")
    @@rls
  }

  policy_select note_owner_read {
    target = Note
    roles  = [authenticated]
    using  = "\"userId\"::uuid = auth.uid()"
  }

  policy_insert note_owner_create {
    target    = Note
    roles     = [authenticated]
    withCheck = "\"userId\"::uuid = auth.uid()"
  }

  policy_update note_owner_update {
    target    = Note
    roles     = [authenticated]
    using     = "\"userId\"::uuid = auth.uid()"
    withCheck = "\"userId\"::uuid = auth.uid()"
  }

  policy_delete note_owner_delete {
    target = Note
    roles  = [authenticated]
    using  = "\"userId\"::uuid = auth.uid()"
  }
}
```

Two things to know about the relation. The referencing column must match the target's native type, so `userId` is `Uuid` because `auth.users.id` is `uuid`; Prisma does not coerce. And the relation is declared but not navigable: it exists for the constraint and the cascade, and including `user` in a query is a compile-time error.

There is no `anon` policy on purpose. With RLS enabled and no matching policy, the `anon` role sees zero rows.

## 6. Apply the changes

Emit the contract, plan the migration, and apply it:

```bash
npx prisma-next contract emit
npx prisma-next migration plan --name init
npx prisma-next migrate
```

`migration plan` writes the migration and, on first run, pins the Supabase extension's contract under `migrations/supabase/`; commit that directory, it is what lets CI and production apply and verify without loading the extension package. `migrate` then applies 9 operations for this schema: the table, the foreign key to `auth.users`, `ENABLE ROW LEVEL SECURITY`, and four `CREATE POLICY` statements.

If `migrate` or `db init` fails with `MIGRATION.CONTRACT_SPACE_LAYOUT_VIOLATION` and `declaredButUnmigrated: supabase`, you skipped `migration plan`; run it once and retry.

Verify the constraint landed:

```sql
select conname, pg_get_constraintdef(oid)
from pg_constraint
where conrelid = 'public.note'::regclass and contype = 'f';
```

```js no-copy
note_userId_fkey | FOREIGN KEY ("userId") REFERENCES auth.users(id) ON DELETE CASCADE
```

## 7. Create the client

The `supabase()` factory returns a client with no top-level query surface. You choose a role for every query, which is what keeps the connection's login role from silently bypassing RLS.

```ts title="src/prisma/db.ts"
import { type SupabaseDb, supabase } from '@prisma/orm-extension-supabase/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

let instance: Promise<SupabaseDb<Contract>> | undefined;

export function getDb(): Promise<SupabaseDb<Contract>> {
  instance ??= supabase<Contract>({
    contractJson,
    url: process.env['DATABASE_URL']!,
    jwksUrl: `${process.env['SUPABASE_URL']!}/auth/v1/.well-known/jwks.json`,
  });
  return instance;
}
```

Configure exactly one key source. Current Supabase projects sign JWTs with asymmetric keys, so `jwksUrl` is the right choice. `jwtSecret` exists for legacy HS256 projects only; your project printing a `JWT_SECRET` does not mean it uses it. Setting both or neither throws `SUPABASE.CONFIG_INVALID`.

## 8. Query as a user, as anon, and as service_role

Bind a role, then query. `asUser` verifies the JWT before touching a connection and rejects bad tokens with a structured `SUPABASE.JWT_INVALID` error.

```ts
const db = await getDb();

// A signed-in user: RLS scopes every query to the token's auth.uid().
const userDb = await db.asUser(jwt);
const mine = await userDb.orm.public.Note.select('id', 'title').all().toArray();

// Anonymous: sees only what anon policies allow (here, nothing).
const publicRows = await db.asAnon().orm.public.Note.select('id').all().toArray();

// service_role: bypasses RLS. Admin surfaces only.
const all = await db.asServiceRole().orm.public.Note.select('id', 'userId').all().toArray();
```

Writes go through the same bindings. Creating a note as the signed-in user succeeds only when `userId` matches the token's `auth.uid()`:

```ts
const note = await userDb.orm.public.Note.select('id', 'title', 'userId').create({
  title: 'my note',
  body: null,
  userId, // must equal auth.uid() or the WITH CHECK policy rejects it
});
```

## 9. Test allowed and denied access

Sign up two users through your project's auth endpoint, then check both directions. The tested example ships this as a 15-test vitest suite; the core assertions:

```ts
// Each user sees exactly their own rows.
const aliceRows = await (await db.asUser(alice.token)).orm.public.Note.select('title', 'userId').all().toArray();
// [{ title: 'alice note', userId: alice.id }]

// Cross-user updates affect zero rows.
const count = await (await db.asUser(alice.token)).orm.public.Note
  .where({ userId: bob.id })
  .updateAndCount({ title: 'should-not-change' });
// 0

// Forging ownership is rejected by WITH CHECK.
await (await db.asUser(alice.token)).orm.public.Note.select('id')
  .create({ title: 'forged', body: null, userId: bob.id });
// throws: new row violates row-level security policy

// Anonymous requests see nothing.
await db.asAnon().orm.public.Note.select('id').all().toArray();
// []
```

Keep `service_role` out of your RLS assertions: it bypasses RLS by design, so a test that reads through `asServiceRole()` can never prove a policy works.

## 10. Deploy to Prisma Compute

[Prisma Compute](https://www.prisma.io/compute) (public beta) is serverless TypeScript hosting that runs your app next to your database. Install the config SDK, then add a committed config:

```bash
npm install @prisma/compute-sdk
```

```ts title="prisma.compute.ts"
import { defineComputeConfig } from '@prisma/compute-sdk/config';

export default defineComputeConfig({
  app: {
    name: 'prisma8-supabase-rls',
    framework: 'hono',
    httpPort: 8080,
    env: '.env',
  },
});
```

Then deploy:

```bash
npx @prisma/cli app deploy --create-project prisma8-supabase-rls
```

The CLI builds locally, uploads, and prints a live URL. Environment values from `.env` are configured through the deploy per the config's `env` field and never land in your repository. Because enforcement lives in Postgres, the deployed app preserves the exact RLS behavior you tested locally; re-run your curl checks against the live URL to confirm.

## Reading auth.users for admin work

App queries cannot reach `auth.*` tables, on any role. For admin reads, `asServiceRole()` exposes the extension's own query surface as a secondary root:

```ts
const admin = db.asServiceRole();
const users = await admin.supabase
  .execute(admin.supabase.sql.auth.users.select('id', 'email').build())
  .toArray();
```

On a hosted project, run a one-time grant first, because Supabase gives `service_role` no table privileges on `auth.*` over a direct connection:

```sql
GRANT USAGE ON SCHEMA auth TO service_role;
GRANT SELECT ON TABLE auth.users TO service_role;
```

For creating users, password resets, and other lifecycle operations, use the Supabase Auth Admin API rather than direct SQL.

## Troubleshooting

- `MIGRATION.CONTRACT_SPACE_LAYOUT_VIOLATION` (`declaredButUnmigrated: supabase`): run `npx prisma-next migration plan --name <slug>` once; it materializes the extension's pinned contract under `migrations/`.
- `SUPABASE.CONFIG_INVALID`: set exactly one of `jwksUrl` or `jwtSecret`.
- `SUPABASE.JWT_INVALID` with an algorithm mismatch in `meta.reason`: you passed an ES256 token to a `jwtSecret` client or vice versa; switch the key source.
- Connection timeouts or DNS failures: use the session pooler host, not `db.<ref>.supabase.co`, on IPv4 networks.
- `db verify` reports missing `storage.iceberg_namespaces` / `storage.iceberg_tables` on a current hosted project: known issue, the extension's storage contract lags the hosted platform. Migrations and runtime behavior are unaffected; use `npx prisma-next db verify --marker-only` until the updated extension ships.

## Known limitations

- Cross-space relations are constraints, not navigable relations; `include` across them is a compile-time error.
- No transaction spans your tables and `auth.*` tables.
- Node.js and Bun only; the runtime needs a Postgres driver, so edge runtimes are not supported.
- Policy predicates are strings; Prisma names, migrates, and introspects policies but does not type-check predicate contents.
- Triggers and functions (for example, create-a-profile-on-signup) are not contract objects; author them as raw SQL migration operations.
