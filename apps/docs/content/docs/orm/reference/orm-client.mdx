The ORM client gives you model-level methods for reading and writing data across PostgreSQL and MongoDB. This page documents every method, its availability on each database, and the behavior that differs between the two.

Each method says which databases it works on. Where a method behaves differently on one of them, the Remarks say how. Where TypeScript rejects something the database itself would accept, the Remarks say that too.

For task-oriented walkthroughs, see the Fundamentals guides: [Reading data](/orm/fundamentals/reading-data), [Writing data](/orm/fundamentals/writing-data), [Relations and joins](/orm/fundamentals/relations-and-joins), and [Transactions](/orm/fundamentals/transactions).

## Example schema

All examples on this page run against the schema below. Every example is copied from a test suite that runs against a live database. The grouped-aggregate examples use a separate `Customer` / `Order` schema, shown under [Grouped aggregates](#grouped-aggregates).

You write this schema in your contract, the `contract.prisma` file that replaced `schema.prisma`. After every change to it, run `npx prisma contract emit`. That command writes `contract.json` and `contract.d.ts`, the two files the examples below import.

Some parts of the schema the examples rely on:

- `@@map("user")` sets the table or collection name. Without it, the table name is the model name with a lowercase first letter.
- `Uuid` is the type for a PostgreSQL `uuid` column. `@default(uuid())` fills the id in when you insert a row.
- `@@type("pg/text@1")` on an `enum` block stores the enum as a text column, with a check constraint that allows only the declared values. This page calls that a text-backed enum.
- A `native_enum` block is the other kind. It creates a real PostgreSQL enum type with `CREATE TYPE ... AS ENUM`. This page calls that a native enum. The two sort differently; see [`orderBy()`](#orderby).
- An enum member's stored value is the string after `=`, or the member name when there is no `=`. That string is what you pass to `.eq()`. So `Urgent = "urgent"` is matched by `.eq('urgent')`, and a bare `admin` member is matched by `.eq('admin')`.
- `@@base(Task, "bug")` makes `Bug` a variant of `Task`: a model stored together with the model it is based on. `@@discriminator(type)` names the column that says which variant a row is. `variant('Bug')` narrows a collection to that variant, and the name you pass is the model name, not the string in `@@base`.
- `PostTag` is required. A many-to-many needs the model for the join table, and a pair of list fields with no such model is rejected. See [Relations and joins](/orm/fundamentals/relations-and-joins#many-to-many).
- `Embedding1536` comes from the pgvector extension. See [PostgreSQL](#postgresql) for the extra line it needs when you create the client.

## Setting up the client

Create a client with `postgres(...)` or `mongo(...)`, then read and write your models through `db.orm`. The two databases have different entry points, and they name the models differently.

### PostgreSQL

Create a PostgreSQL client with `postgres(...)`. `db.orm` holds your models by model name, grouped by database schema: `db.orm.public.User`, `db.orm.public.Post`. `public` is the PostgreSQL schema your tables are in unless you put them in another one.

```typescript
import postgres from '@prisma/orm-postgres/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

const db = postgres<Contract>({ contractJson, url: process.env.DATABASE_URL });

const users = await db.orm.public.User.all();
```

If your contract uses a type from an extension package, pass that package to `extensions` when you create the client. The example schema's `Embedding1536` type comes from pgvector, so it needs this:

```typescript
import pgvector from '@prisma/orm-extension-pgvector/runtime';

const db = postgres<Contract>({
  contractJson,
  url: process.env.DATABASE_URL,
  extensions: [pgvector],
});
```

To give a model your own methods on top of the built-in ones, subclass `Collection` and register the subclass with the `orm(...)` function instead of calling `postgres(...)`. [Custom `Collection` subclass](#custom-collection-subclass) has the code.

### MongoDB

Create a MongoDB client with `mongo(...)`. `db.orm` holds your models by collection name, with no schema in between: `db.orm.users`, `db.orm.posts`, not `db.orm.User`. The collection name is the one you set with `@@map`, or the model name with a lowercase first letter when you did not set one.

```typescript
import mongo from '@prisma/orm-mongo/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

const db = mongo<Contract>({ contractJson, url: process.env.MONGODB_URL, dbName: 'app' });

const users = await db.orm.users.all();
```

:::note[The two databases name models differently]
On PostgreSQL you write the model name under its schema: `db.orm.public.User`. On MongoDB you write the collection name with nothing in front of it: `db.orm.users`. The examples below follow each database's own form.
:::

## Query-building methods

These methods narrow a query. Each returns a collection you can chain more methods on. You run the query with a [read method](#read-terminals) such as `all()` or `first()`. MongoDB supports fewer of them than PostgreSQL, and each method's Remarks say which databases it works on.

Some examples import a filter helper you can use on its own. On PostgreSQL those come from `@prisma/orm-postgres/orm-client`, on MongoDB from `@prisma/orm-mongo/query-ast/execution`. See [Filter conditions and operators](#filter-conditions-and-operators).

The examples below use these ids, which stand for rows the test suite inserted first:

```typescript
const aliceId = '00000000-0000-4000-8000-000000000001';
const carolId = '00000000-0000-4000-8000-000000000003';
const postId = '00000000-0000-4000-8000-000000000010';
const acmeId = '00000000-0000-4000-8000-000000000020';
const emptyCustomerId = '00000000-0000-4000-8000-000000000021';
```

### `where()`

Restrict a query to rows matching a filter.

#### Remarks

- Available for PostgreSQL and MongoDB, but the accepted filter shapes differ.
- On PostgreSQL, `where()` takes either a callback that calls an operator on a column (`u.email.eq(...)`) or an object of field-and-value pairs that must match exactly.
- On MongoDB, `where()` takes either an object of field-and-value pairs that must match exactly or a `MongoFieldFilter`. The object form can only test for equality. For anything else, such as greater-than, use `MongoFieldFilter` (see [MongoFieldFilter](#mongofieldfilter)).
- Calling `where()` more than once on the same query requires a row to match all of the filters.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `filter` | Callback `(fields) => Expression`, shorthand object, or (MongoDB) a `MongoFieldFilter` | Yes | The condition rows must satisfy. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection` | `db.orm.public.User.where(...)` | A collection narrowed by the filter. Chain more methods on it, then run it with a read or write method. |

#### Examples

##### Callback form with a column operator (PostgreSQL)

```typescript
const admins = await db.orm.public.User.where((u) => u.kind.eq('admin')).all();
```

##### Shorthand object form

```typescript tab="PostgreSQL"
const bob = await db.orm.public.User.where({ email: 'bob@example.com' }).first();
```

```typescript tab="MongoDB"
const authors = await db.orm.users.where({ role: 'author' }).all();
```

##### Chaining `where()` calls (ANDed)

```typescript
const carolUrgentPosts = await db.orm.public.Post.where({ userId: carolId })
  .where((p) => p.priority.eq('urgent'))
  .all();
```

##### `MongoFieldFilter` expression (MongoDB)

```typescript
import { MongoFieldFilter } from '@prisma/orm-mongo/query-ast/execution';

const alice = await db.orm.users.where(MongoFieldFilter.eq('email', 'alice@example.com')).first();

const recentPosts = await db.orm.posts
  .where(MongoFieldFilter.gte('createdAt', new Date('2024-01-02T00:00:00.000Z')))
  .all();
```

For a task-oriented guide to filtering, see [Reading data](/orm/fundamentals/reading-data#filter-records).

### `select()`

Project a row down to a subset of scalar fields.

#### Remarks

- Available for PostgreSQL and MongoDB.
- On PostgreSQL, `select()` narrows the returned row shape at the type level: fields you didn't select are absent from the result type.
- On MongoDB, `select()` changes what the database returns but not the TypeScript type. Only the fields you named come back, while the type still lists every field on the model.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `...fields` | Field names (`string`) | Yes | One or more scalar field names to keep. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection` | `db.orm.public.User.select('id', 'email')` | A collection projected to the named fields. |

#### Examples

##### Project to a subset of fields

```typescript tab="PostgreSQL"
const summaries = await db.orm.public.User.select('id', 'email').orderBy((u) => u.email.asc()).all();
// summaries[0] is { id, email } — no displayName
```

```typescript tab="MongoDB"
const summaries = await db.orm.users.select('name', 'email').all();
```

### `include()`

Eagerly load a relation onto the returned rows.

#### Remarks

- Available for PostgreSQL and MongoDB, with differences noted below.
- On PostgreSQL, `include(relationName, refineFn?)` loads both to-one and to-many relations. The optional callback receives the related rows as a collection, so you can filter, order, limit, and aggregate them. See [Refinements, aggregates, and combine](#refinements-aggregates-and-combine).
- On MongoDB, `include(relationName)` loads a relation that is stored as a reference. It takes the relation name and nothing else: there is no callback.
- On MongoDB, the `_id` of a loaded related document comes back as a driver `ObjectId`, not as the hex string you get for a top-level `_id`. Wrap it in `String(...)` before you compare it.
- On MongoDB, a second argument to `include()` is ignored rather than rejected, and the relation loads unfiltered.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `relationName` | `string` | Yes | The relation to load. |
| `refineFn` | `(relation: Collection) => Collection \| aggregate` | No | PostgreSQL only. Narrows the loaded relation, or reduces it to one value. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection` | `db.orm.public.User.include('posts')` | A collection whose rows carry the loaded relation. |

#### Examples

##### To-one relation (PostgreSQL)

```typescript
const posts = await db.orm.public.Post.include('user').where({ id: postId }).all();
// posts[0].user is the related User
```

##### To-many relation (PostgreSQL)

```typescript
const users = await db.orm.public.User.include('posts').where({ id: aliceId }).all();
// users[0].posts is an array of the user's posts
```

##### Reference relation (MongoDB)

```typescript
const posts = await db.orm.posts.include('author').where({ title: 'Hello world' }).all();
// posts[0].author._id is an ObjectId; compare it as String(posts[0].author._id)
```

For a task-oriented guide to loading related records, see [Relations and joins](/orm/fundamentals/relations-and-joins).

### Refinements, aggregates, and combine

On PostgreSQL, the callback you pass to `include()` receives the related rows as a collection. You can filter, order, and paginate them. You can also reduce them to a single value, or use `combine()` to return several results at once.

#### Remarks

- PostgreSQL only. On MongoDB, `include()` takes no callback, and `count`, `sum`, `avg`, `min`, `max`, and `combine` do not exist on a collection at all. Calling one throws a `TypeError`.
- On PostgreSQL, those six are only callable **inside** an `include()` callback. Called anywhere else, they throw an `Error`.
- `sum()` and `avg()` take a numeric column: an integer, a floating-point number, or a decimal. They also take an interval or a time-of-day column. They do not take a date or a timestamp, and calling them on one is a compile error that names the operation the database has no version of.
- `min()` and `max()` take more: numeric and text columns, dates, times, timestamps, intervals, IP addresses, and text arrays. They do not take a boolean, a `uuid`, binary data, a bit string, or JSON.
- `count()` takes no argument and returns a `number`. `countBigInt()` returns a `bigint` instead, for a count too large for a JavaScript `number`.
- `sum()` over an integer column returns a `number`. Past ±(2^53 − 1) a `number` cannot hold the total, and reading it throws an error whose `code` is `RUNTIME.DECODE_FAILED`. Use `sumBigInt(field)` for totals that large; it returns a `bigint`.
- `avg()` over an integer column returns a `number`, which rounds. `avgDecimal(field)` returns the exact average instead.
- When a to-many relation has no rows, `sum()` and `avg()` come back as `null`, not `0`.
- `combine(shape)` takes an object whose keys you choose. Each value is either the relation with more methods chained on it, which comes back as an array of rows, or an aggregate such as `posts.count()`, which comes back as that single value. Each value must start from the collection the callback was given, which is why the example below writes `posts` inside its own callback.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `filter` / `orderBy` / `limit` / `offset` | Chained on the nested collection | No | Refine which related rows load. |
| `count()` | Aggregate, no arguments | No | Reduces the relation to a row count. |
| `sum(field)` / `avg(field)` | Aggregate over a numeric field | No | Reduces the relation to one number. |
| `min(field)` / `max(field)` | Aggregate over a sortable field | No | Reduces the relation to its smallest or largest value, in the column's own type. |
| `combine(shape)` | Object of named collections and aggregates | No | Returns several results under one relation key. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| The narrowed relation, a single value, or an object of both | `include('posts', (p) => p.count())` | The relation key on each row holds the callback's result instead of the related rows. |

#### Examples

##### Filter, order, and limit within a relation (PostgreSQL)

```typescript
const users = await db.orm.public.User.include('posts', (posts) =>
  posts
    .where((p) => p.priority.eq('low'))
    .orderBy((p) => p.createdAt.desc())
    .limit(1),
)
  .where({ id: aliceId })
  .all();
```

##### Reduce a relation to a count (PostgreSQL)

```typescript
const users = await db.orm.public.User.include('posts', (posts) => posts.count())
  .where({ id: aliceId })
  .all();
// users[0].posts is the number 2
```

##### `sum()` / `avg()` over a numeric relation (PostgreSQL)

This example uses the `Customer` and `Order` models, which are in the separate schema shown under [Grouped aggregates](#grouped-aggregates).

```typescript
const customers = await db.orm.public.Customer.include('orders', (orders) => orders.sum('amount'))
  .where({ id: acmeId })
  .all();
// customers[0].orders is 1500

const avgCustomers = await db.orm.public.Customer.include('orders', (orders) => orders.avg('amount'))
  .where({ id: acmeId })
  .all();
// avgCustomers[0].orders is 300
```

A customer with no orders reduces to `null`:

```typescript
const rows = await db.orm.public.Customer.include('orders', (orders) => orders.sum('amount'))
  .where({ id: emptyCustomerId })
  .all();
// rows[0].orders is null
```

##### `combine()` multiple sub-views (PostgreSQL)

```typescript
const users = await db.orm.public.User.include('posts', (posts) =>
  posts.combine({
    recent: posts.orderBy((p) => p.createdAt.desc()).limit(1),
    total: posts.count(),
  }),
)
  .where({ id: aliceId })
  .all();
// users[0].posts.total is 2; users[0].posts.recent is a one-element array
```

:::note[`min()` and `max()` over a date column]
`min('createdAt')` over a `DateTime` column compiles, and it returns a `Temporal.Instant` (the standard JavaScript date and time object; Node.js 26 has it built in, earlier versions need `temporal-polyfill`). `sum('createdAt')` and `avg('createdAt')` do not compile, because PostgreSQL has no `SUM` or `AVG` over a date or a timestamp. The TypeScript error names the operation that is missing for that column.
:::

### `orderBy()`

Sort the result set.

#### Remarks

- Available for PostgreSQL and MongoDB, with different argument shapes.
- On PostgreSQL, `orderBy()` takes a callback that returns `.asc()` or `.desc()` on one column. Pass an array of such callbacks to sort by more than one column.
- On MongoDB, `orderBy()` takes an object instead: `{ field: 1 }` sorts ascending and `{ field: -1 }` sorts descending.
- On PostgreSQL, a native enum column sorts in the order its members are declared, not alphabetically. A `native_enum Priority` declared `Low`, `High`, `Urgent` sorts in that order under `.asc()`. A text-backed enum sorts by its stored text instead, so `'high'` comes before `'low'` and `'urgent'`. To sort a text-backed enum by meaning, store numbers rather than words, or write your own ranking expression.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `sort` | Callback `(fields) => f.field.asc() \| .desc()`, an array of such callbacks (PostgreSQL), or a `{ field: 1 \| -1 }` object (MongoDB) | Yes | The sort key(s) and direction(s). |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection` | `db.orm.public.Post.orderBy(...)` | A collection with an ordering applied. |

#### Examples

##### Ascending and descending

```typescript tab="PostgreSQL"
const newestFirst = await db.orm.public.Post.where({ userId: aliceId })
  .orderBy((p) => p.createdAt.desc())
  .all();
```

```typescript tab="MongoDB"
const newestFirst = await db.orm.posts.orderBy({ createdAt: -1 }).all();
```

##### Multiple sort keys (PostgreSQL)

```typescript
const byPriorityThenDate = await db.orm.public.Post.orderBy([
  (p) => p.priority.asc(),
  (p) => p.createdAt.asc(),
]).all();
// Priority is text-backed here, so it sorts as 'high', 'low', 'urgent'
```

### `cursor()`

Resume pagination from a known position.

#### Remarks

- PostgreSQL only. MongoDB's collection has no `cursor()`; calling it throws `TypeError`.
- Always call `orderBy()` before `cursor()`. TypeScript rejects the call if you do not, but nothing checks at runtime. If you get past the type system, the cursor value is ignored and you get every row back, with no error.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `values` | Object of the `orderBy()` key(s) and their values | Yes | The position to resume after. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection` | `db.orm.public.Post.cursor({ createdAt })` | A collection resuming after the cursor position. |

#### Examples

##### Resume pagination (PostgreSQL)

```typescript
const page1 = await db.orm.public.Post.orderBy((p) => p.createdAt.asc()).limit(2).all();
const last = page1[page1.length - 1];

const page2 = await db.orm.public.Post.orderBy((p) => p.createdAt.asc())
  .cursor({ createdAt: last.createdAt })
  .limit(2)
  .all();
```

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `...fields` | Field names (`string`) | Yes | The fields to deduplicate on. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection` | `db.orm.public.Post.distinct('priority')` | A collection with duplicate rows removed on the named fields. |

#### Examples

##### Deduplicate on a field (PostgreSQL)


### `distinctOn()`

Keep the first row per key according to `orderBy()`.

#### Remarks

- PostgreSQL only. MongoDB's collection has no `distinctOn()`; calling it throws `TypeError`.
- Call `orderBy()` first, so that "the first row per key" means something. As with `cursor()`, TypeScript checks this and the runtime does not.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `...fields` | Field names (`string`) | Yes | The key field(s) to keep the first row of. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection` | `db.orm.public.Post.distinctOn('userId')` | A collection keeping one row per key. |

#### Examples

##### First row per key (PostgreSQL)

```typescript
const latestPerUser = await db.orm.public.Post.orderBy([(p) => p.userId.asc(), (p) => p.createdAt.desc()])
  .distinctOn('userId')
  .all();
```

### `variant()`

Narrow a model to one of the variants declared with `@@base`.

#### Remarks

- Available for PostgreSQL and MongoDB.
- Pass the variant's model name, such as `'Bug'`, not the string in its `@@base` attribute.
- On PostgreSQL, a variant's own fields are in a second table alongside the base model's table. That changes how some writes behave; see [`createAndCount()`](#createandcount) and [`upsert()`](#upsert).
- On MongoDB, every variant is a document in the one collection, told apart by the field named in `@@discriminator`.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `variantName` | `string` | Yes | The model name of the variant. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Collection`, narrowed to the variant | `db.orm.public.Task.variant('Bug')` | A collection holding only rows of that variant. |

#### Examples

##### Narrow to a variant

```typescript tab="PostgreSQL"
const bugs = await db.orm.public.Task.variant('Bug').all();
```

```typescript tab="MongoDB"
const tutorials = await db.orm.posts.variant('Tutorial').all();
```

## Read methods [#read-terminals]

A read method runs the query and gives you the rows. `all()` and `first()` are available on both databases. `aggregate()` and `groupBy()` are PostgreSQL only and are documented under [Grouped aggregates](#grouped-aggregates).

There is no `count()` method on either database. On PostgreSQL, count with `aggregate((a) => ({ n: a.count() }))`. On MongoDB, count with the pipeline builder. Both are shown under [Count records](/orm/fundamentals/reading-data#count-records).

For a task-oriented walkthrough, see [Reading data](/orm/fundamentals/reading-data).

### `all()`

Resolve the query to every matching row.

#### Remarks

- Available for PostgreSQL and MongoDB.
- `all()` returns an [`AsyncIterableResult`](#asynciterableresult): you can `await` it to collect an array, or use `for await` to stream rows one at a time.
- `await`ing a result you have already `await`ed is safe. You get the same array back, and the query does not run again.
- Each result can be used one way only. Awaiting it and then looping it with `for await`, or the reverse, throws an error whose `code` is `RUNTIME.ITERATOR_CONSUMED`. See [Single consumption and mode switching](#single-consumption-and-mode-switching).

#### Options

`all()` takes no arguments.

#### Return type

| Return type | Example | Description |
|---|---|---|
| `AsyncIterableResult<Row>` | `await db.orm.public.User.all()` | Awaitable to `Row[]`, or iterable with `for await` for streaming. |

#### Examples

##### Await to collect an array

```typescript tab="PostgreSQL"
const users = await db.orm.public.User.all();
```

```typescript tab="MongoDB"
const users = await db.orm.users.all();
```

##### Stream rows one at a time

```typescript tab="PostgreSQL"
for await (const user of db.orm.public.User.orderBy((u) => u.email.asc()).all()) {
  console.log(user.email);
}
```

```typescript tab="MongoDB"
for await (const post of db.orm.posts.orderBy({ createdAt: 1 }).all()) {
  console.log(post.title);
}
```

For Prisma ORM 7 users, `findMany` maps onto `all()`:

```diff
- const users = await prisma.user.findMany({ where: { kind: 'admin' } });
+ const users = await db.orm.public.User.where({ kind: 'admin' }).all();
```

### `first()`

Resolve the query to the first matching row, or `null` if none matches.

#### Remarks

- Available for PostgreSQL and MongoDB.
- On PostgreSQL, `first()` accepts an inline filter: a shorthand object or a callback (`first((p) => p.priority.eq('urgent'))`).
- On PostgreSQL, an inline filter is added to any earlier `where()` call. Both have to match.
- On MongoDB, `first()` takes no filter argument. Filter with `where(...)` first, then call `first()`.
- Returns `null` when no row matches.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `filter` | Shorthand object or callback (PostgreSQL only) | No | An inline filter applied before resolving. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Row \| null` | `await db.orm.public.User.first(...)` | The first matching row, or `null`. |

#### Examples

##### Match by an inline filter (PostgreSQL)

```typescript
const alice = await db.orm.public.User.first({ email: 'alice@example.com' });
const urgentPost = await db.orm.public.Post.first((p) => p.priority.eq('urgent'));
```

##### Match with a prior `where()` (MongoDB)

```typescript
const bob = await db.orm.users.where({ name: 'Bob' }).first();
```

##### No match returns `null`

```typescript tab="PostgreSQL"
const nobody = await db.orm.public.User.first({ email: 'nobody@example.com' });
// null
```

```typescript tab="MongoDB"
const nobody = await db.orm.users.where({ email: 'nobody@example.com' }).first();
// null
```

For Prisma ORM 7 users, `findUnique` and `findFirst` map onto `first()`:

```diff
- const alice = await prisma.user.findUnique({ where: { email } });
+ const alice = await db.orm.public.User.first({ email });
```

### Custom `Collection` subclass

On PostgreSQL you can subclass `Collection` to attach domain methods, and register the subclass when you create the client.

#### Remarks

- PostgreSQL only. The MongoDB ORM has no equivalent collection-subclassing mechanism.
- To register a subclass, build the client with the `orm(...)` function and pass a `collections` object. The client's own `.orm` cannot do this: `postgres(...)` has no `collections` option, so `db.orm` always uses the plain `Collection`.
- A method that returns `this.variant('Bug')` gives back a collection narrowed to the `Bug` model. It is chainable, so you finish it with `all()`, `first()`, or any other method.

#### Examples

##### Register a subclass with a domain method (PostgreSQL)

```typescript
import postgres from '@prisma/orm-postgres/runtime';
import { Collection, orm } from '@prisma/orm-postgres/orm-client';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

class TaskCollection extends Collection<Contract, 'Task'> {
  bugs() {
    return this.variant('Bug');
  }
  features() {
    return this.variant('Feature');
  }
}

const client = postgres<Contract>({ contractJson, url: process.env.DATABASE_URL });
const runtime = await client.connect();

// orm() takes a `collections` option; the client's own `.orm` does not.
const db = orm({
  runtime,
  // client.context carries the contract, which orm() needs to build collections.
  context: client.context,
  collections: { Task: TaskCollection },
}).public; // .public is the PostgreSQL schema

const bugs = await db.Task.bugs().all();
const features = await db.Task.features().all();
```

## Write methods [#mutation-terminals]

A write method changes the database. `create`, `createAll`, `createAndCount`, `update`, `updateAll`, `updateAndCount`, `delete`, `deleteAll`, `deleteAndCount`, and `upsert` are available on both databases. The differences between the two are listed under each method.

For a task-oriented walkthrough, see [Writing data](/orm/fundamentals/writing-data). For grouping several writes into one unit, see [Transactions](/orm/fundamentals/transactions).

:::warning[Filter before you update or delete]
Always call `where()` before an update or a delete. On MongoDB you get an error if you forget, with the message `updateAll() requires a .where() filter. Call .where() before .updateAll()`. On PostgreSQL you do not: `update()` and `delete()` change one arbitrary row, and `updateAll()` and `deleteAll()` change every row. TypeScript does refuse to compile `update()` and `delete()` without a `where()`, but nothing checks at run time.
:::

The examples below use `aliceId`, `bobId`, `carolId`, `postId`, `tagId`, `tutorialId`, and `userId` for the ids of rows that already exist. Substitute your own.

### `create()`

Insert a single row and return it.

#### Remarks

- Available for PostgreSQL and MongoDB.
- On PostgreSQL, leave out any field your contract gives a default, including the id. Nullable fields can be left out too. Every other field is required.
- On MongoDB, `_id` is the only field you can leave out. Give every other field a value, and write `null` for a field you want empty.
- On MongoDB, `create()` returns the values you passed plus the `_id` the server assigned. It does not read the stored document back. On PostgreSQL the returned row comes from the database.
- On PostgreSQL, `create()` can create or link related rows in the same transaction. Nest `create()` on the side that does not hold the foreign key, and `connect()` on the side that does.
- Nested `create()` and `connect()` are not available on MongoDB.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `data` | Object of field values | Yes | The row to insert. |

On PostgreSQL, `data` can also carry a `create` or `connect` callback for a related row, as shown below.

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Row` | `await db.orm.public.Tag.create(...)` | The inserted row. |

#### Examples

##### Insert a single row

```typescript tab="PostgreSQL"
const tag = await db.orm.public.Tag.create({ label: 'typescript-2' });
```

```typescript tab="MongoDB"
const user = await db.orm.users.create({
  name: 'Carol',
  email: 'carol@example.com',
  bio: null,
  role: 'reader',
  address: null,
});
// user._id is the server-assigned id
```

##### Nested `create()` on the side without the foreign key (PostgreSQL) [#nested-create-on-a-child-owned-relation-postgresql]

```typescript
const author = await db.orm.public.User.create({
  id: '00000000-0000-0000-0000-000000000099',
  email: 'dana@example.com',
  displayName: 'Dana',
  kind: 'user',
  posts: (posts) =>
    posts.create([{ id: '10000000-0000-0000-0000-000000000099', title: 'Dana post one' }]),
});
```

##### Nested `connect()` on the side with the foreign key (PostgreSQL) [#nested-connect-on-a-parent-owned-relation-postgresql]

```typescript
const post = await db.orm.public.Post.create({
  id: '10000000-0000-0000-0000-000000000098',
  title: 'Connected to Bob',
  user: (user) => user.connect({ id: bobId }),
```


### `update()`

Update the matched row and return it, or `null` if none matches.

#### Remarks

- Available for PostgreSQL and MongoDB. Requires a prior `where()` (see the warning at the top of this section).
- On MongoDB, `update()` takes a data object or a callback that returns field operations, such as `(t) => [t.duration.inc(5)]`. See [Field update operations](#field-update-operations).
- On PostgreSQL, `update()` takes a data object only. Passing a function is a mistake that returns `null`; pass an object.
- On PostgreSQL, `update()` can also relink related rows. `connect()` points the foreign key at a different row, and `disconnect()` removes a many-to-many link without deleting either row.
- On MongoDB, `update()` changes one document in a single database operation.
- Returns `null` when no row matches. On PostgreSQL it also returns `null` when you passed a function instead of an object.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `data` | Data object, or (MongoDB) a field-operations callback | Yes | The changes to apply. On PostgreSQL, relation mutators (`connect`, `disconnect`) may be included. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Row \| null` | `await db.orm.public.User.where(...).update(...)` | The updated row, or `null` if none matched. |

#### Examples

##### Update with a data object

```typescript tab="PostgreSQL"
const updated = await db.orm.public.User.where({ id: bobId }).update({ displayName: 'Bob Updated' });
```

```typescript tab="MongoDB"
const updated = await db.orm.users.where({ _id: bobId }).update({ bio: 'Now with a bio' });
```

##### Field-operations callback (MongoDB)

```typescript
const updated = await db.orm.posts
  .variant('Tutorial')
  .where({ _id: tutorialId })
  .update((t) => [t.duration.inc(5), t.content.set('Updated content')]);
```

##### Nested `connect()` relinks a foreign key (PostgreSQL)

```typescript
const relinked = await db.orm.public.Post.where({ id: postId }).update({
  user: (user) => user.connect({ id: carolId }),
});
```

##### Nested `disconnect()` unlinks a many-to-many row (PostgreSQL)

```typescript
const updated = await db.orm.public.Post.where({ id: postId })
  .select('id', 'title')
  .include('tags', (tag) => tag.select('id', 'label').orderBy((t) => t.label.asc()))
  .update({
    tags: (tag) => tag.disconnect([{ id: tagId }]),
  });
// only the join-table row is removed; the Tag row itself still exists
```

For Prisma ORM 7 users, `update()` moves the filter into `where()` and drops the `data` wrapper:

```diff

+ const updated = await db.orm.public.User.where({ id: bobId }).update({ displayName: 'Bob Updated' });
```

### `updateAll()`

Update every matching row and collect the results.

#### Remarks

- Available for PostgreSQL and MongoDB. Call `where()` first: MongoDB enforces this at runtime; PostgreSQL does not (see the section warning above: without a filter these affect every row).
- On PostgreSQL, `updateAll()` runs as one statement, so every matching row changes together.
- On MongoDB, `updateAll()` is not one operation. It collects the matching ids, updates, then reads those documents back. A document someone else changes in between can come back with their values, and a document that starts matching only after the first step is updated but not returned.
- Prisma ORM has no `db.transaction()` on MongoDB, so there is no way to avoid this from the client. If it matters, run the writes yourself in a MongoDB driver session. See [Transactions on MongoDB](/orm/fundamentals/transactions#transactions-on-mongodb).

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `data` | Data object, or (MongoDB) a field-operations callback | Yes | The changes to apply to every matched row. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `AsyncIterableResult<Row>` | `await db.orm.public.Post.where(...).updateAll(...)` | The updated rows. |

#### Examples

##### Update all matching rows

```typescript tab="PostgreSQL"
const updated = await db.orm.public.Post.where({ userId: aliceId }).updateAll({ priority: 'urgent' });
```

```typescript tab="MongoDB"
const updated = await db.orm.users.where({ role: 'author' }).updateAll({ role: 'admin' });
// see the remark above: this is not one operation
```

### `upsert()`

Insert a row if none matches, otherwise update the existing row.

#### Remarks

- On MongoDB, call `where()` first; the filter decides which document is updated.
- On PostgreSQL, `where()` is not used. `conflictOn` decides which row counts as already existing.
- `conflictOn` takes one unique column with a value, such as `conflictOn: { label: 'typescript' }`. Only the column name is read: it names the unique constraint the database checks. The value is required by the type but is not used, so it does not have to match the value in `create`.
- Leave `conflictOn` out to use the primary key instead.
- On MongoDB, the `update` side takes a data object or a field-operations callback. If a field appears in both `create` and `update`, the `update` value is used, even when the row is inserted.
- On PostgreSQL, `upsert()` does not work on a multi-table inheritance variant, the same restriction as [`createAndCount()`](#createandcount). It throws an error whose `code` is `ORM.OPERATION_UNSUPPORTED`, with the message `upsert() is not supported for MTI variant "Tutorial" on model "Post". Use createAll() instead.`
- On MongoDB, the `_id` on the returned row comes back as the driver's `ObjectId`, not a hex string. Compare it as text: `String(user._id) === String(bobId)`.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `create` | Data object | Yes | The row to insert if none matches. |
| `update` | Data object, or (MongoDB) a field-operations callback | Yes | The changes to apply if a row matches. |
| `conflictOn` | Object with one unique column and a value (PostgreSQL) | No | Names the unique constraint that decides insert or update. Omit to use the primary key. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `Row` | `await db.orm.public.Tag.upsert(...)` | The inserted or updated row. |

#### Examples

##### Insert or update (PostgreSQL)

```typescript
// Insert: no existing row has label 'brand-new', so the create side is used.
const inserted = await db.orm.public.Tag.upsert({
  create: { id: '30000000-0000-0000-0000-000000000099', label: 'brand-new' },
  update: { label: 'brand-new-updated' },
  conflictOn: { label: 'brand-new' },
});

// Update: a row with label 'typescript' already exists, so the update runs against it.
const updated = await db.orm.public.Tag.upsert({
  create: { id: '30000000-0000-0000-0000-000000000098', label: 'typescript' },
  update: { label: 'typescript-renamed' },
  conflictOn: { label: 'typescript' },
});
```

##### Insert or update (MongoDB)

```typescript
const user = await db.orm.users.where({ email: 'newperson@example.com' }).upsert({
  create: {
    name: 'New Person',
    email: 'newperson@example.com',
    bio: null,
    role: 'reader',
    address: null,
  },
  update: { bio: 'set on upsert' },
});
// on insert, an `update` value replaces the `create` value for the same field
```

##### Field-operations callback on the update side (MongoDB)

```typescript
const post = await db.orm.posts
  .variant('Tutorial')
  .where({ _id: tutorialId })
  .upsert({
    create: {
      title: 'Should not be used',
      content: 'unused',
      authorId: bobId,
      createdAt: new Date('2024-01-01T00:00:00.000Z'),
      difficulty: 'beginner',
      duration: 0,
    },
    update: (t) => [t.duration.inc(1)],
  });
```

For Prisma ORM 7 users, `upsert()` replaces the `where` argument with `conflictOn` (PostgreSQL):

```diff
- const tag = await prisma.tag.upsert({
-   where: { label: 'typescript' },
-   update: { label: 'typescript-renamed' },
-   create: { label: 'typescript' },
- });
+ const tag = await db.orm.public.Tag.upsert({
+   update: { label: 'typescript-renamed' },
+   create: { label: 'typescript' },
+   conflictOn: { label: 'typescript' },
+ });
```

## Grouped aggregates

PostgreSQL supports aggregation over a result set, both flat (`aggregate()`) and grouped (`groupBy().aggregate()`), with `having()` to filter groups. MongoDB has neither method: `aggregate()` and `groupBy()` do not exist on a MongoDB collection, and calling them throws a `TypeError`. Use the pipeline builder for MongoDB aggregation instead, described in [MongoDB: Pipeline builder](/orm/fundamentals/advanced-queries#mongodb-pipeline-builder).

The examples below use a separate `Customer` / `Order` schema, where `Order.amount` is a numeric column:

<details>

<summary>Expand for the aggregate example schema</summary>

```prisma
model Customer {
  id      Uuid   @id @default(uuid())
  name    String
  segment String

  orders Order[]

  @@map("customer")
}

model Order {
  id         Uuid     @id @default(uuid())
  customerId Uuid
  channel    String
  amount     Int
  quantity   Int
  placedAt   DateTime @default(now())

  customer Customer @relation(fields: [customerId], references: [id])

  @@map("order")
}
```

</details>

### `aggregate()`

Compute aggregates over the current result set.

#### Remarks

- PostgreSQL only. Calling `aggregate()` on a Mongo collection throws `TypeError`.
- `count()` counts rows. It takes no argument and always resolves to a number (`0` over an empty set).
- `count(field)` counts the rows where that field is not null.
- `sum()` and `avg()` resolve to `null`, not `0`, over an empty result set. This is standard SQL: aggregating zero rows with `SUM`/`AVG` yields `NULL`. Their TypeScript return type is `number | null` for this reason.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `selector` | Callback `(agg) => ({ alias: agg.sum('amount') })` | Yes | The aggregates to compute, keyed by output alias. |

The selector's `agg` gives you `count()`, `count(field)`, `sum(field)`, `avg(field)`, `min(field)`, and `max(field)`.

#### Return type

| Return type | Example | Description |
|---|---|---|
| Object of aggregate results | `{ total: 10 }` | One object with the requested aliases. `sum`/`avg` are `number \| null`. |

#### Examples

##### Count (PostgreSQL)

```typescript
const stats = await db.orm.public.Order.aggregate((agg) => ({ total: agg.count() }));
// { total: 10 }
```

##### Count the rows where a field is set (PostgreSQL)

```typescript
const stats = await db.orm.public.Order.aggregate((agg) => ({ withQuantity: agg.count('quantity') }));
// { withQuantity: 8 }
```

##### Sum and average (PostgreSQL)

```typescript
const stats = await db.orm.public.Order.where({
  customerId: '20000000-0000-0000-0000-000000000001',
}).aggregate((agg) => ({
  totalAmount: agg.sum('amount'),
  avgAmount: agg.avg('amount'),
}));
// { totalAmount: 1500, avgAmount: 300 }
```

##### Min and max (PostgreSQL)

```typescript
const stats = await db.orm.public.Order.aggregate((agg) => ({
  cheapest: agg.min('amount'),
  priciest: agg.max('amount'),
}));
// { cheapest: 10, priciest: 500 }
```

##### `null` over an empty set (PostgreSQL)

```typescript
const stats = await db.orm.public.Order.where((o) => o.amount.gt(999_999)).aggregate((agg) => ({
  total: agg.sum('amount'),
  average: agg.avg('amount'),
  count: agg.count(),
}));
// { total: null, average: null, count: 0 }
```

For Prisma ORM 7 users, `aggregate()` takes a selector callback instead of `_sum`/`_avg` keys:

```diff
- const stats = await prisma.order.aggregate({ _sum: { amount: true }, _avg: { amount: true } });
+ const stats = await db.orm.public.Order.aggregate((agg) => ({ total: agg.sum('amount'), average: agg.avg('amount') }));
```

### `groupBy()`

Group rows by one or more fields, then aggregate per group.

#### Remarks

- PostgreSQL only. Calling `groupBy()` on a Mongo collection throws `TypeError`.
- Pass field names as separate arguments: `groupBy('customerId', 'channel')`.
- `groupBy(...)` returns a `GroupedCollection`. Call `.aggregate(...)` on it to get one row per group, carrying both the grouping fields and the aggregate aliases.
- A `where(...)` before `groupBy(...)` filters the rows that get grouped.
- `orderBy(...)` on a grouped collection sorts the groups by a grouping field. You cannot sort them by an aggregate value here. For that, use the SQL query builder, described in [Advanced queries](/orm/fundamentals/advanced-queries).
- `limit(n)` and `offset(n)` page the groups, and both require an `orderBy(...)` before them. Without one they are a TypeScript error.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `...fields` | One or more field names (`string`) | Yes | The fields to group by. |

#### Return type

| Return type | Example | Description |
|---|---|---|
| `GroupedCollection` | `db.orm.public.Order.groupBy('customerId')` | A grouped collection, resolved via `aggregate()`. |

#### Examples

##### Group and aggregate (PostgreSQL)

```typescript
const perCustomer = await db.orm.public.Order.groupBy('customerId').aggregate((agg) => ({
  orderCount: agg.count(),
  totalAmount: agg.sum('amount'),
}));
// one row per customer, each { customerId, orderCount, totalAmount }
```

##### Group by two fields (PostgreSQL)

```typescript
const perCustomerAndChannel = await db.orm.public.Order.groupBy('customerId', 'channel').aggregate(
  (agg) => ({ totalAmount: agg.sum('amount') }),
);
// one row per customer and channel, each { customerId, channel, totalAmount }
```

##### Filter rows, then group (PostgreSQL)

```typescript
const perCustomer = await db.orm.public.Order.where((o) => o.amount.gte(100))
  .groupBy('customerId')
  .having((h) => h.count().gt(1))
  .aggregate((agg) => ({ totalAmount: agg.sum('amount') }));
```

##### Sort and page the groups (PostgreSQL)

```typescript
const firstTwoChannels = await db.orm.public.Order.groupBy('channel')
  .orderBy((group) => group.channel.desc())
  .limit(2)
  .aggregate((agg) => ({ orderCount: agg.count() }));
```

For Prisma ORM 7 users, `groupBy()` chains into `aggregate()` instead of taking a `by` array with aggregate keys:

```diff
- const perCustomer = await prisma.order.groupBy({ by: ['customerId'], _sum: { amount: true } });
+ const perCustomer = await db.orm.public.Order.groupBy('customerId').aggregate((agg) => ({ totalAmount: agg.sum('amount') }));
```

### `having()`

Filter groups by an aggregate comparison.

#### Remarks

- PostgreSQL only. Chained on a `GroupedCollection` between `groupBy()` and `aggregate()`.
- The `having()` callback gives you `count()`, `sum(field)`, `avg(field)`, `min(field)`, and `max(field)`. Each of those returns an object with `eq`, `neq`, `gt`, `lt`, `gte`, and `lte`.
- You cannot refer to an alias from `aggregate()` here. Write the aggregate out again in `having()`.

#### Options

| Name | Type | Required | Description |
|---|---|---|---|
| `predicate` | Callback `(h) => h.<aggregate>(<field>).<comparison>(<value>)` | Yes | The group-level condition. |

The angle-bracket names above are placeholders. A real call is `h.sum('amount').gt(1000)`.

#### Return type

| Return type | Example | Description |
|---|---|---|
| `GroupedCollection` | `db.orm.public.Order.groupBy('customerId').having(...)` | A grouped collection filtered by the aggregate predicate. |

#### Examples

##### Filter groups by a sum (PostgreSQL)

```typescript
const bigSpenders = await db.orm.public.Order.groupBy('customerId')
  .having((h) => h.sum('amount').gt(1000))
  .aggregate((agg) => ({ totalAmount: agg.sum('amount') }));
```

##### Filter groups by row count (PostgreSQL)

```typescript
const groupsWithAtLeastFive = await db.orm.public.Order.groupBy('customerId')
  .having((h) => h.count().gte(5))
  .aggregate((agg) => ({ orderCount: agg.count() }));
```

## Filter conditions and operators

Filters build the condition inside `where()`, and inside relation filters. PostgreSQL and MongoDB have different filter APIs.

- **PostgreSQL** uses column-level comparison methods (`u.email.eq(...)`) inside a callback, plus standalone combinator functions imported from `@prisma/orm-postgres/orm-client`.
- **MongoDB** uses static factories on `MongoFieldFilter` imported from `@prisma/orm-mongo/query-ast/execution`, plus `.and()`/`.not()` instance methods and the standalone `MongoOrExpr.of(...)`.

### Scalar comparisons (PostgreSQL)

Column-level comparison methods on a field.

#### Remarks

- PostgreSQL. Which methods a field has depends on its type: `eq`/`neq`/`in`/`notIn` on any field that can be compared for equality; `gt`/`lt`/`gte`/`lte` on any field that can be ordered; `like` and `ilike` on text fields; `isNull`/`isNotNull` on every field.
- `like()` matches a SQL pattern case-sensitively. `ilike()` matches the same pattern case-insensitively.
- `in([])` matches no rows. `notIn([])` matches every row.

#### Options

| Method | Type | Description |
|---|---|---|
| `eq(value)` / `neq(value)` | Exact value | Equality / inequality. |
| `gt(value)` / `lt(value)` / `gte(value)` / `lte(value)` | Ordered value | Ordered comparisons. |
| `like(pattern)` / `ilike(pattern)` | SQL `LIKE` pattern | Case-sensitive / case-insensitive pattern match. |
| `in(values)` / `notIn(values)` | Array of values | Membership / exclusion. |
| `isNull()` / `isNotNull()` | No argument | NULL checks. |

#### Examples

##### Equality and inequality (PostgreSQL)

```typescript
const alice = await db.orm.public.User.where((u) => u.email.eq('alice@example.com')).first();
const notAlice = await db.orm.public.User.where((u) => u.email.neq('alice@example.com')).all();
```

##### Ordered comparisons (PostgreSQL)

```typescript
const after = await db.orm.public.Post.where((p) => p.createdAt.gt(new Date('2024-01-02T10:00:00.000Z'))).all();
const inclusive = await db.orm.public.Post.where((p) => p.createdAt.gte(new Date('2024-01-02T10:00:00.000Z'))).all();
```

##### Pattern matching (PostgreSQL)

```typescript
const matches = await db.orm.public.User.where((u) => u.email.like('%@example.com')).all(); // case-sensitive
const caseInsensitive = await db.orm.public.User.where((u) => u.email.ilike('%@EXAMPLE.COM')).all();
```

##### Membership and NULL checks (PostgreSQL)

```typescript
const lowOrHigh = await db.orm.public.Post.where((p) => p.priority.in(['low', 'high'])).all();
const notLowOrHigh = await db.orm.public.Post.where((p) => p.priority.notIn(['low', 'high'])).all();
const withoutEmbedding = await db.orm.public.Post.where((p) => p.embedding.isNull()).all();
```

### Combinators

Combine or negate predicates.

#### Remarks

- On PostgreSQL, `and`, `or`, `not`, and `all` are **standalone functions** imported from `@prisma/orm-postgres/orm-client`. You import them; they are not methods on a field.
- On PostgreSQL, `all()` takes no arguments and returns a condition that is always true. Use it where the code has to pass a condition but you do not want to filter anything, such as a branch of your own helper. This `all()` is not the `.all()` you call at the end of a chain to run the query.
- On MongoDB, `.and(other)` and `.not()` are **instance methods** on every filter expression, including `MongoFieldFilter`, `MongoOrExpr`, and `MongoAndExpr`. There is **no `.or()` instance method**. To OR filters, build `MongoOrExpr.of([...])`.
- On MongoDB, an AND of two ORs is `MongoOrExpr.of([...]).and(MongoOrExpr.of([...]))`.

#### Examples

##### `and` / `or` / `not` (PostgreSQL)

```typescript
import { and, or, not } from '@prisma/orm-postgres/orm-client';

const both = await db.orm.public.Post.where((p) =>
  and(p.priority.eq('low'), p.userId.eq('00000000-0000-0000-0000-000000000003')),
).all();
const either = await db.orm.public.Post.where((p) => or(p.priority.eq('urgent'), p.priority.eq('high'))).all();
const negated = await db.orm.public.Post.where((p) => not(p.priority.eq('low'))).all();
```

##### `all` (PostgreSQL)

```typescript
import { all } from '@prisma/orm-postgres/orm-client';

const everyPost = await db.orm.public.Post.where(() => all()).all();
```

##### `and` / `or` / `not` (MongoDB)

```typescript
import { MongoFieldFilter, MongoOrExpr } from '@prisma/orm-mongo/query-ast/execution';

const both = await db.orm.users
  .where(MongoFieldFilter.eq('role', 'author').and(MongoFieldFilter.eq('name', 'Alice')))
  .all();
const either = await db.orm.users
  .where(MongoOrExpr.of([MongoFieldFilter.eq('name', 'Alice'), MongoFieldFilter.eq('name', 'Bob')]))
  .all();
const negated = await db.orm.users.where(MongoFieldFilter.eq('name', 'Alice').not()).all();
```

##### AND of two ORs (MongoDB)

```typescript
const authorsNamedAliceOrBob = await db.orm.users
  .where(
    MongoOrExpr.of([MongoFieldFilter.eq('name', 'Alice'), MongoFieldFilter.eq('name', 'Bob')]).and(
      MongoOrExpr.of([MongoFieldFilter.eq('role', 'author'), MongoFieldFilter.eq('role', 'editor')]),
    ),
  )
  .all();
```

:::note[No `.or()` instance method or `$nor` on MongoDB]
MongoDB filter expressions have `.and(...)` and `.not()`, but no `.or(...)`. Use `MongoOrExpr.of([...])` instead. There is no `$nor` combinator in the library.
:::

### Relation filters (PostgreSQL)

Filter parents by their related rows.

#### Remarks

- PostgreSQL. `some()`, `every()`, and `none()` are methods on a to-many relation, and they compile to SQL `EXISTS` subqueries.
- Each of the three takes either a callback or a plain object of equality matches: `u.posts.some((p) => p.priority.eq('urgent'))` and `u.posts.some({ priority: 'urgent' })` mean the same thing.
- `some()` with no argument matches parents with at least one related row.
- A user with no posts matches `every()`.
- `not(u.posts.some(...))` and `u.posts.none(...)` match the same rows. Prefer `none(...)`.
- A to-one relation is filtered the same way, from the side that holds the foreign key: `p.user.some(...)`.

#### Examples

##### `some` / `every` / `none` (PostgreSQL)

```typescript
const withUrgentPost = await db.orm.public.User.where((u) => u.posts.some((p) => p.priority.eq('urgent'))).all();
const withAnyTag = await db.orm.public.Tag.where((t) => t.posts.some()).all();
const allLowPriority = await db.orm.public.User.where((u) => u.posts.every((p) => p.priority.eq('low'))).all();
const noUrgentPost = await db.orm.public.User.where((u) => u.posts.none((p) => p.priority.eq('urgent'))).all();
```

##### To-one relation predicate (PostgreSQL)

```typescript
const postsByAlice = await db.orm.public.Post.where((p) => p.user.some({ email: 'alice@example.com' })).all();
```

### Shorthand object filter

A plain object of equality matches, ANDed together.

#### Remarks

- Available for PostgreSQL and MongoDB.
- Multiple keys are combined with implicit AND.
- A key set to `null` becomes an IS NULL check. A key set to `undefined` is skipped.
- A field whose type cannot be compared for equality throws an error whose `code` is `ORM.FILTER_UNSUPPORTED`. Filter that field with a comparison method instead.

#### Examples

##### Shorthand object

```typescript tab="PostgreSQL"
const row = await db.orm.public.Post.where({
  userId: '00000000-0000-0000-0000-000000000001',
  priority: 'high',
}).first();
```

```typescript tab="MongoDB"
const alice = await db.orm.users.where({ name: 'Alice', role: 'author' }).first();
```

### `MongoFieldFilter`

Static factories that build MongoDB filter expressions.

#### Remarks

- MongoDB. Imported from `@prisma/orm-mongo/query-ast/execution`.
- Exactly eleven factories exist: `of`, `eq`, `neq`, `gt`, `lt`, `gte`, `lte`, `in`, `nin`, `isNull`, `isNotNull`. There is no `ne`; use `neq`.
- `of(field, operator, value)` takes a raw MongoDB operator string, for any operator the other ten factories do not cover.
- `isNull` / `isNotNull` are shorthand for equals-null and not-equals-null, not a `$exists` check.
- For `$exists`, import `MongoExistsExpr` from the same module and call `MongoExistsExpr.exists(field)` or `MongoExistsExpr.notExists(field)`.
- The factories `exists`, `regex`, `elemMatch`, `all`, and `size` do **not** exist on `MongoFieldFilter`, and the library has no regex, `elemMatch`, `$all`, or `$size` support anywhere.

#### Options

| Method | Type | Description |
|---|---|---|
| `of(field, operator, value)` | Field + MongoDB operator string + value | Any operator, written out, such as `'$gt'`. |
| `eq(field, value)` / `neq(field, value)` | Field + value | Equality / inequality. |
| `gt` / `lt` / `gte` / `lte` `(field, value)` | Field + ordered value | Ordered comparisons. |
| `in(field, values)` / `nin(field, values)` | Field + array | Membership / exclusion. |
| `isNull(field)` / `isNotNull(field)` | Field | Null / not-null (equals-null semantics). |

#### Examples

##### Comparison factories (MongoDB)

```typescript
import { MongoFieldFilter } from '@prisma/orm-mongo/query-ast/execution';

const alice = await db.orm.users.where(MongoFieldFilter.eq('name', 'Alice')).first();
const notAlice = await db.orm.users.where(MongoFieldFilter.neq('name', 'Alice')).all();
const strictlyAfter = await db.orm.posts
  .where(MongoFieldFilter.gt('createdAt', new Date('2024-01-01T10:00:00.000Z')))
  .all();
```

##### Membership and null checks (MongoDB)

```typescript
const articlesOrTutorials = await db.orm.posts
  .where(MongoFieldFilter.in('kind', ['article', 'tutorial']))
  .all();
const notArticles = await db.orm.posts.where(MongoFieldFilter.nin('kind', ['article'])).all();
const noBio = await db.orm.users.where(MongoFieldFilter.isNull('bio')).all();
const hasBio = await db.orm.users.where(MongoFieldFilter.isNotNull('bio')).all();
```

##### An operator written out, and `$exists` (MongoDB)

```typescript
import { MongoExistsExpr, MongoFieldFilter } from '@prisma/orm-mongo/query-ast/execution';

const older = await db.orm.users.where(MongoFieldFilter.of('age', '$gt', 30)).all();
const withBioField = await db.orm.users.where(MongoExistsExpr.exists('bio')).all();
```

### Dot-notation into an embedded object (MongoDB)

Filter into a field of an embedded value object using a dot path.

#### Remarks

- MongoDB. This works at runtime, but the TypeScript types do not know nested paths, so the object form needs a cast. Prefer `MongoFieldFilter.eq`, which takes a bare `string` path and needs no cast.
- `MongoWhereFilter` is typed against the model's own top-level field names. `{ 'address.city': ... }` is therefore a compile error without a cast.

#### Examples

##### Dot-notation path (MongoDB)

```typescript
import { MongoFieldFilter } from '@prisma/orm-mongo/query-ast/execution';

const usersInSf = await db.orm.users.where(MongoFieldFilter.eq('address.city', 'San Francisco')).all();
```

The object form works at runtime too, with a cast:

```typescript
const usersInSf = await db.orm.users
  .where({ 'address.city': 'San Francisco' } as unknown as Record<string, unknown>)
  .all();
```
## Field update operations

On MongoDB, `update()`, `updateAndCount()`, and `upsert()` accept a callback in place of a data object. The callback receives one argument, written `u` or `t` below, with one property per field: `u.bio`, `t.duration`. Call an operation on that property, such as `u.bio.set('Hello')`. Each call returns an update instruction; collect them in the array you return. PostgreSQL's `update()` has no callback form (see [`update()`](#update)).

All three methods require `.where()`. `update()` returns the updated document, or `null` when nothing matched. `updateAndCount()` returns the number of documents it changed.

### Available operations (MongoDB)

#### Remarks

- MongoDB only.
- `set()`, `unset()`, `inc()`, and `mul()` are available and verified.
  - `set(value)` assigns a field.
  - `unset()` removes a field.
  - `inc(n)` increments a numeric field. Applied to a missing field, it sets the field to `n`.
  - `mul(n)` multiplies a numeric field. Applied to a missing field, MongoDB sets it to `0` regardless of the multiplier.
- The callback argument is typed against the collection's base model, even after `variant(...)`. TypeScript only knows the base model's fields, so `t.duration.inc(10)` is a type error even though it runs correctly. Put `// @ts-expect-error` on that line to accept it.

#### Examples

These examples use the MongoDB accessors from [Setting up the client](#setting-up-the-client).
##### `set()` (MongoDB)

Return as many operations as you want. They are applied together, in one write.

```typescript
const updated = await db.orm.users
  .where({ _id: '6650f1c2a1b2c3d4e5f60002' })
  .update((u) => [u.bio.set('Set via field op'), u.name.set('Bob R.')]);
```

##### `inc()` and `mul()` (MongoDB)

`duration` is declared on `Tutorial`, not on the base `Post` model, so each line that touches it needs `// @ts-expect-error`.

```typescript
const incremented = await db.orm.posts
  .variant('Tutorial')
  .where({ _id: '6650f1c2a1b2c3d4e5f60003' })
  // @ts-expect-error duration is a Tutorial field, not a Post field
  .update((t) => [t.duration.inc(10)]);

const multiplied = await db.orm.posts
  .variant('Tutorial')
  .where({ _id: '6650f1c2a1b2c3d4e5f60003' })
  // @ts-expect-error duration is a Tutorial field, not a Post field
  .update((t) => [t.duration.mul(3)]);
```

##### `unset()` (MongoDB)

`updateAndCount()` takes the callback in the same place. `upsert()` takes it as its `update` key, beside `create`: `upsert({ create: { ... }, update: (u) => [u.bio.unset()] })`.

```typescript
const updated = await db.orm.users.where({ _id: '6650f1c2a1b2c3d4e5f60001' }).update((u) => [u.bio.unset()]);
const changed = await db.orm.users.where({ _id: '6650f1c2a1b2c3d4e5f60002' }).updateAndCount((u) => [u.bio.unset()]);
```

### Operations that do not exist (MongoDB)

#### Remarks

- MongoDB. `min()`, `max()`, `rename()`, and `currentDate()` have **no accessor method at all**.

:::warning[No `min`, `max`, `rename`, or `currentDate` field operations]
The callback argument implements `set`, `unset`, `inc`, `mul`, `push`, `pull`, `addToSet`, and `pop` only. `min`, `max`, `rename`, and `currentDate` are absent from the API. A missing or misspelled operation is not a compile error: `u.bio.rename` is `undefined`, and you only get a `TypeError` when you call it. Do not use `min()`, `max()`, `rename()`, or `currentDate()`.
:::

### Array operations (MongoDB, unverified)

#### Remarks

- MongoDB. `push()`, `pull()`, `addToSet()`, and `pop()` exist on the callback argument and compile. They are not tested; try them on a real array field before relying on them.
- Applied to a field that is not an array, MongoDB rejects the write with a server-level error (`The field '...' must be an array but is of type ...`), not a library error. An array field is declared with `[]` in your contract, as in `tags String[]`.

```typescript
const updated = await db.orm.posts.where({ _id: '6650f1c2a1b2c3d4e5f60003' }).update((p) => [
  p.tags.push('mongodb'), // appends one element
  p.tags.addToSet('mongodb'), // appends it only if it is not already there
  p.tags.pull('draft'), // removes every element equal to the argument
  p.tags.pop(1), // removes the last element; pop(-1) removes the first
]);
```

## Result types

### `AsyncIterableResult`

The methods `all()` / `createAll()` / `updateAll()` / `deleteAll()` return an `AsyncIterableResult`. You can use it two ways:

- `await` the result (or call `.toArray()`) to get every row in one array.
- Loop over it with `for await ... of` to take rows one at a time.

If you need the type by name, import it from `@prisma/orm-postgres/components/runtime` on PostgreSQL, or from `@prisma/orm-mongo/components/runtime` on MongoDB.

#### Single consumption and mode switching

Each result is read once, one way:

- Re-`await`ing (or calling `.toArray()` on) a result you already awaited is **safe**. It returns the same array.
- Switching from one way to the other throws an error whose `code` is `RUNTIME.ITERATOR_CONSUMED` (message: `already been consumed`). Awaiting a result and then looping it with `for await`, or the reverse, is what throws.

The example below uses the PostgreSQL accessor; on MongoDB the same methods are on `db.orm.users` (see [Setting up the client](#setting-up-the-client)).

```typescript
const result = db.orm.public.User.all();
const first = await result;
const again = await result.toArray(); // safe: same array

try {
  for await (const user of result) {
  }
} catch (error) {
  if (error instanceof Error && 'code' in error && error.code === 'RUNTIME.ITERATOR_CONSUMED') {
    // the result was already read as an array
  }
}
```

PostgreSQL and MongoDB behave the same here. The error message and the rule are identical.

### Aggregate result shapes

- `aggregate((agg) => ({ ... }))` resolves to a **single object** keyed by your aliases. `db.orm.public.Order.aggregate((agg) => ({ total: agg.count() }))` resolves to `{ total: 10 }`.
- `groupBy(...).aggregate((agg) => ({ ... }))` resolves to an **array**, one object per group. Each object carries the group key field or fields plus your aliases. `db.orm.public.Order.groupBy('customerId').aggregate((agg) => ({ orderCount: agg.count(), totalAmount: agg.sum('amount') }))` resolves to `[{ customerId, orderCount, totalAmount }, ...]`.
- `count()` is always a `number` (`0` over an empty set). `sum()` and `avg()` are `number | null`: they resolve to `null`, not `0`, over an empty result set.
