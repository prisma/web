"Rollback" refers to two different situations, which Prisma ORM treats differently:

- **The migration applied, but the change was wrong.** You need to move the database *back* to an earlier state. This is a **rollback**, and in Prisma ORM it's one more migration.
- **The migration failed partway.** You need to get *unstuck*. This is **recovery**, and it usually means fixing the cause and re-running, because re-running is safe.

## Rollback: a migration like any other

There is no `migrate down` command and no separate "down migration" files. A rollback is a new migration in your [migration history](/orm/migrations/the-migration-graph) that changes the database back to an earlier state. If you know git, this is `git revert`, not `git reset`: nothing is deleted from history.

<ConceptAnimation name="migration-rollback" />

Suppose you applied `20260707T1008_add_display_name` in production and need to undo it. Your contract is the `contract.prisma` file that replaced `schema.prisma`. A contract state is one version of your contract, named by a hash computed from the contract. [`npx prisma migration plan`](/orm/migrations/generating-a-migration) writes a migration from one contract state to another, so use it to write the rollback. In the command, a directory name means the state after that migration, and the same name followed by `^` means the state before it:

```npm
npx prisma migration plan \
  --from 20260707T1008_add_display_name \
  --to "20260707T1008_add_display_name^" \
  --name rollback_display_name
```

```text
✔ Planned 1 operation(s)

migrations/app/20260707T1010_rollback_display_name
└─ ⚠ Drop column "displayName" from "user"

⚠ This migration contains destructive operations that may cause data loss.

from:       e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1010_rollback_display_name

ℹ DDL preview

ALTER TABLE "public"."user" DROP COLUMN "displayName";
```

Review the new migration before you apply it, because `db migrate` runs destructive operations without asking. Open its `migration.ts`, and run `npx prisma migration show 20260707T1010_rollback_display_name` to see its SQL. Then finish the rollback in this order:

1. **Save the data, if you need it.** Dropping the column deletes its data for good. To copy the column into a table that already exists, add a [`rawSql` operation](/orm/migrations/editing-a-migration#escape-hatch-raw-sql) that runs an `INSERT ... SELECT`, and put it before the `dropColumn` call in this migration's `migration.ts`. Then recompile the migration by running `node migrations/app/20260707T1010_rollback_display_name/migration.ts` from your project's root directory. This rewrites `ops.json`, which holds the operations `db migrate` runs.
2. **Revert the change in your contract.** Remove `displayName` from `contract.prisma`, then run `npx prisma contract emit`, which replaces `prisma generate` and rewrites `contract.json`. Step 4 needs this, because `db migrate` moves the database to the contract state in that file.
3. **Commit the migration and the contract together.** Commit the new migration's directory, `contract.prisma`, `contract.json`, and `contract.d.ts`. A rollback adds no directory under `migrations/snapshots/`, because it ends at a contract state that already has one.
4. **Apply the rollback.** In CI and production, run `npx prisma db migrate`, which replaces [`migrate deploy`](/orm/coming-from-prisma-orm-7). In development, run `npx prisma db migrate --advance-ref db` instead. The flag updates the [`db` ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from), a file in `migrations/app/refs/` that names the contract state you last applied in development. By default, `migration plan` starts from that state, so without the flag your next migration repeats changes you already applied.

After step 4, `npx prisma db verify` passes. `db migrate` runs neither migration on a database that never applied `add_display_name`, such as a staging database you had not deployed it to. It takes the shortest path to the contract state, and that path skips both.

To undo several migrations, write one migration with `npx prisma migration plan --from <newest-migration-dir> --to "<oldest-migration-to-undo>^" --name rollback_changes`, then follow the same four steps. In step 2, restore `contract.prisma` from a commit made before you added the oldest migration you undo, for example with `git checkout <commit> -- src/prisma/contract.prisma`, and run `npx prisma contract emit`.

### One planning caveat after a rollback

After a rollback, the next `migration plan` fails with an error whose `code` is `MIGRATION.NO_TARGET`, even if you applied the rollback with `--advance-ref db`. When `migration plan` starts from the `db` ref, it first looks for the contract state your history ends at. The rollback leads back to the state `add_display_name` started from, so your history has no end state. Pass `--from` once, with the rollback's directory name, and `migration plan` skips that lookup:

```npm
npx prisma migration plan --from 20260707T1010_rollback_display_name --name add_nickname
```

Once this migration exists, `migration plan` no longer fails this way.

## Recovery: when a migration fails partway

A failed `db migrate` run stops at the failing operation and reports it:

```text
✘ [MIGRATION.RUNNER_FAILED] Operation alterNullability.setNotNull.user.nickname failed during precheck: ensure no NULL values in "nickname"
  why: Migration runner failed
  docs: https://docs.prisma.io/docs/orm/v8/reference/error-reference/MIGRATION.RUNNER_FAILED
```

On PostgreSQL, one `db migrate` run is one transaction, so a failed run leaves nothing to clean up. On MongoDB, a `db migrate` run is not wrapped in a transaction, so operations that finished before the failure stay in the database. [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) explains what a re-run does there. Prisma ORM 8 does not support MySQL, and [SQLite support](/orm/supported-databases) is experimental.

1. **Read which check failed.** The error names the operation and the [check](/orm/migrations/how-migrations-work#every-operation-checks-itself) that failed. A precheck runs before its operation. Here the precheck found rows with `NULL` in `nickname`, so the run stopped before it set `NOT NULL`.
2. **Fix the cause, then run `npx prisma db migrate` again.** There is no `migrate resolve` step. In development, add `--advance-ref db` as before. Sometimes the cause is the environment, such as a PostgreSQL extension the server lacks, or missing permissions. Sometimes it's the migration itself. Here you'd edit the migration to [fill in `nickname` for existing rows](/orm/migrations/editing-a-migration#worked-example-making-a-column-required) before the `setNotNull`. Then recompile it with `node migrations/app/<dir>/migration.ts` from your project's root directory, and apply again.

Sometimes a migration applies in development and then fails in production. Say your development database had no `NULL`s in `nickname`, but production does. In production, the precheck stops the run before the `ALTER` runs.

### Drift: when the database isn't where migrations left it

Drift means the database changed without a migration. The [marker](/orm/migrations/the-migration-graph#terms-used-on-this-page) is the record in the database of which contract state it currently matches. It is not the `db` ref file. Drift shows up in one of two ways:

- **The marker is at a contract state that no migration ends at.** [`npx prisma db update`](/cli/db-update), which makes a database match your contract without a migration, can cause this. The next `db migrate` then fails with an error whose `code` is `MIGRATION.MARKER_MISMATCH`, before it runs any operation. To fix it, run `npx prisma migration plan --from <newest-migration-dir> --name <name>` before you change the contract again. The new migration ends at the state `db update` applied, so on that database the next `db migrate` has nothing to run.
- **Only tables or columns changed**, for example with a hand-run `ALTER`. The marker does not move, so `db migrate` still runs. It skips an operation whose change is already in the database. It fails if an operation's check fails, or if something your contract describes is missing or different after the operations run.

To see which contract state the database is at, run two commands that only read it. They connect to the database in `db.connection` in `prisma.config.ts`, or to the URL you pass with `--db`, such as `--db "$PRODUCTION_DATABASE_URL"`:

- **[`npx prisma migration status`](/cli/migration-status)** shows the marker's contract state and labels it `@db`, which is not the `db` ref.
- **[`npx prisma db verify`](/cli/db-verify)** checks the marker and the tables against your contract. With `--schema-only`, it checks only the tables. It lists each difference it finds under `Schema issues`.

A change made by hand has two fixes:

- **Undo it.** Change the tables back by hand until `npx prisma db verify --schema-only --strict` passes. The marker never moved, so you need nothing else.
- **Keep it.** Add the change to your contract, run `npx prisma contract emit`, then plan and apply a migration as usual. On that database, `db migrate` skips the change you already made.

Use [`npx prisma db sign`](/cli/db-sign) for a database whose tables match your contract and that has no marker. It does not fix either kind of drift. For a database that Prisma ORM 7 migrated, follow [step 4 of the upgrade guide](/guides/upgrade-prisma-orm/postgresql#4-transfer-migration-ownership).

:::note[What's early]

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8), instruction files for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Plan a rollback for the last migration and show me its destructive operations before I decide."
- "This db migrate run failed. Read the error, fix the migration, and re-run it."
- "Check whether staging has drifted from the contract and explain the differences."
