"Rollback" covers two situations, which Prisma ORM treats differently:

- **The migration applied, but the change was wrong.** That is a **rollback**, and in Prisma ORM it is one more migration.
- **The migration failed partway.** That is **recovery**: fix the cause and run it again, because re-running is safe.

## Rollback: a migration like any other

There is no `migrate down` command and no "down migration" files. A rollback is a new migration in your [migration history](/orm/migrations/the-migration-graph) that changes the database back to an earlier state. If you know git, this is `git revert`, not `git reset`: nothing is deleted from history.

<ConceptAnimation name="migration-rollback" />

Suppose you applied `20260707T1008_add_display_name` in production and need to undo it. A contract state is one version of your contract, the `contract.prisma` file that replaced `schema.prisma`, named by its hash. [`npx prisma migration plan`](/orm/migrations/generating-a-migration) writes a migration from one contract state to another. A directory name means the state after that migration, and `^` after the name means the state before it:

```npm
npx prisma migration plan \
  --from 20260707T1008_add_display_name \
  --to "20260707T1008_add_display_name^" \
  --name rollback_display_name
```

```text
✔ Planned 1 operation(s)

migrations/app/20260707T1010_rollback_display_name
└─ ⚠ Drop column "displayName" from "user"

⚠ This migration contains destructive operations that may cause data loss.

from:       e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1010_rollback_display_name

ℹ DDL preview

ALTER TABLE "public"."user" DROP COLUMN "displayName";
```

Review the migration before applying it: `db migrate` runs destructive operations without asking. Open its `migration.ts` and run `npx prisma migration show 20260707T1010_rollback_display_name` to see its SQL. Then finish in order:

1. **Save the data, if you need it.** Dropping the column deletes its data for good. To copy it into a table that already exists, add a [`rawSql` operation](/orm/migrations/editing-a-migration#escape-hatch-raw-sql) running an `INSERT ... SELECT` before the `dropColumn` call in `migration.ts`. Then recompile: run `node migrations/app/20260707T1010_rollback_display_name/migration.ts` from your project root, which rewrites `ops.json`, the file holding the operations `db migrate` runs.
2. **Revert the change in your contract.** Remove `displayName` from your contract file, then run `npx prisma contract emit`, which replaces `prisma generate` and rewrites `contract.json`. Step 4 needs this: `db migrate` applies migrations until the database matches the state in `contract.json`.
3. **Commit the migration and the contract together.** That means the new migration's directory, your contract file, `contract.json`, and `contract.d.ts`. A rollback adds no directory under `migrations/snapshots/`, because it ends at a contract state that already has one.
4. **Apply the rollback.** In CI and production, run `npx prisma db migrate`, which replaces [`migrate deploy`](/orm/coming-from-prisma-orm-7). In development, run `npx prisma db migrate --advance-ref db`. The [`db` ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) is a file in `migrations/app/refs/` naming the contract state you last applied in development, and the flag points it at the state you just applied. `migration plan` starts from it by default, so without the flag your next migration repeats changes you already applied.

After step 4, `npx prisma db verify` passes. `db migrate` runs the fewest migrations that end at the contract state, so it runs neither migration on a database that never applied `add_display_name`.

To undo several migrations, plan one with `npx prisma migration plan --from <newest-migration-dir> --to "<oldest-migration-to-undo>^" --name rollback_changes`, then follow the same four steps. In step 2, restore your contract file from a commit made before the oldest migration you undo, for example with `git checkout <commit> -- src/prisma/contract.prisma`.

### One planning caveat after a rollback

After a rollback, the next `migration plan` fails with an error whose `code` is `MIGRATION.NO_TARGET`, even if you applied the rollback with `--advance-ref db`. Starting from the `db` ref, `migration plan` first looks for the contract state your history ends at, meaning one no migration starts from. The rollback ends at the state `add_display_name` starts from, so there is none. Pass `--from` with the rollback's directory name to skip that lookup:

```npm
npx prisma migration plan --from 20260707T1010_rollback_display_name --name add_nickname
```

Once this migration exists, `migration plan` no longer fails this way.

## Recovery: when a migration fails partway

A failed `db migrate` run stops at the failing operation and reports it:

```text
✘ [MIGRATION.RUNNER_FAILED] Operation alterNullability.setNotNull.user.nickname failed during precheck: ensure no NULL values in "nickname"
  why: Migration runner failed
  docs: https://docs.prisma.io/docs/orm/v8/reference/error-reference/MIGRATION.RUNNER_FAILED
```

On PostgreSQL, one `db migrate` run is one transaction, so a failed run leaves nothing to clean up. On MongoDB, a run is not one transaction, so operations that finished before the failure stay in the database. [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) covers re-runs there.

1. **Read which check failed.** The error names the operation and the [check](/orm/migrations/how-migrations-work#every-operation-checks-itself) that failed. A precheck runs before its operation. Here it found rows with `NULL` in `nickname`, so the run stopped before setting `NOT NULL`.
2. **Fix the cause, then run `npx prisma db migrate` again.** There is no `migrate resolve` step. In development, add `--advance-ref db`. The cause may be the environment, such as a PostgreSQL extension the server lacks or missing permissions. It may be the migration itself, which can pass in development and fail in production, where the data differs. Here you would edit the migration to [fill in `nickname` for existing rows](/orm/migrations/editing-a-migration#worked-example-making-a-column-required) before the `setNotNull`, recompile as in the rollback's step 1, and apply again.

### Drift: when the database changed without a migration [#drift-when-the-database-isnt-where-migrations-left-it]

The [marker](/orm/migrations/the-migration-graph#terms-used-on-this-page) is the record in the database of which contract state it matches. Drift shows up in two ways:

- **The marker records a contract state that no migration ends at.** [`npx prisma db update`](/cli/db-update), which makes a database match your contract without a migration, can cause this. The next `db migrate` fails with an error whose `code` is `MIGRATION.MARKER_MISMATCH` before it runs any operation. To fix it, run `npx prisma migration plan --from <newest-migration-dir> --name <name>` before you change the contract again. That migration ends at the state `db update` applied, so the next `db migrate` there has nothing to run.
- **Only tables or columns changed**, for example with a hand-run `ALTER`. The marker still records the last contract state applied, so `db migrate` still runs. It skips an operation whose change is already in the database, and fails if an operation's check fails or if your contract describes something missing or different after the operations run.

To see which contract state a database matches, run two read-only commands. Both connect to `db.connection` in `prisma.config.ts`, or to the URL you pass with `--db`:

- **[`npx prisma migration status`](/cli/migration-status)** shows the marker's contract state, labeled `@db`, which is not the `db` ref.
- **[`npx prisma db verify`](/cli/db-verify)** checks the marker and the tables against your contract. With `--schema-only`, it checks only the tables. It lists each difference under `Schema issues`.

A change made by hand has two fixes:

- **Undo it.** Change the tables back by hand until `npx prisma db verify --schema-only --strict` passes. The marker never changed, so you need nothing else.
- **Keep it.** Add the change to your contract, run `npx prisma contract emit`, then plan and apply a migration as usual. `db migrate` skips the change you already made there.

Use [`npx prisma db sign`](/cli/db-sign) for a database that has no marker but whose tables match your contract. It fixes neither kind of drift. For a database that Prisma ORM 7 migrated, follow [step 4 of the upgrade guide](/guides/upgrade-prisma-orm/postgresql#4-transfer-migration-ownership).

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8), instruction files for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Plan a rollback for the last migration and show me its destructive operations."
- "This db migrate run failed. Read the error, fix the migration, and re-run it."
- "Check whether staging has drifted from the contract and explain the differences."
