"Rollback" refers to two different situations, which Prisma ORM treats differently:

- **The migration applied, but the change was wrong.** You need to move the database *back* to an earlier state. This is a **rollback**, and in Prisma ORM it's one more migration.
- **The migration failed partway.** You need to get *unstuck*. This is **recovery**, and it usually means fixing the cause and re-running, because re-running is safe.

## Rollback: a migration like any other

There is no `migrate down` command and no separate "down migration" files. Your [migration history](/orm/migrations/the-migration-graph) already describes the database as it was before the change, so a rollback is a new migration that changes the database back to that state. If you know git, this is `git revert`, not `git reset`: nothing is deleted from history. The database's [ledger](/orm/migrations/the-migration-graph#terms-used-on-this-page), its own list of every migration applied to it, lists both the change and the rollback.

Suppose `20260707T1008_add_display_name` shipped and needs to come back out. Write the reverse migration with [`npx prisma migration plan`](/orm/migrations/generating-a-migration). The migration it writes moves the database between two contract states. A contract state is one version of your contract, the `contract.prisma` file that replaced `schema.prisma`. In the command, the directory name means the state after that migration, and `<dir>^` means the state before it:

```npm
npx prisma migration plan \
  --from 20260707T1008_add_display_name \
  --to 20260707T1008_add_display_name^ \
  --name rollback_display_name
```

```text
✔ Planned 1 operation(s)

migrations/app/20260707T1010_rollback_display_name
└─ ⚠ Drop column "displayName" from "user"

⚠ This migration contains destructive operations that may cause data loss.

ℹ DDL preview

ALTER TABLE "public"."user" DROP COLUMN "displayName";
```

Review the new migration before you apply it. Open its `migration.ts`, and run `npx prisma migration show 20260707T1010_rollback_display_name` to see its SQL. Then finish the rollback in this order:

1. **Save the data, if you need it.** A rollback does not bring data back, so dropping the column discards whatever the original migration and your app wrote into it. To copy the column into another table before the `DROP`, edit this migration's `migration.ts` as [Editing a migration](/orm/migrations/editing-a-migration) shows. Then run `node migrations/app/20260707T1010_rollback_display_name/migration.ts` from your project's root directory to recompile it. Recompiling rewrites `ops.json`, the file that `db migrate` runs.
2. **Revert the change in your contract.** Remove `displayName` from `contract.prisma`, then run `npx prisma contract emit`. It replaces `prisma generate` and writes `contract.json` and `contract.d.ts`.
3. **Commit the migration and the contract together.** Commit the new directory's `migration.ts`, `ops.json`, and `migration.json`, the `migrations/snapshots/<hash>/` directories that `migration.ts` imports, and `contract.prisma`, `contract.json`, and `contract.d.ts`.
4. **Apply the rollback.** In CI and production, run `npx prisma db migrate`, which replaces [`migrate deploy`](/orm/coming-from-prisma-orm-7). With no `--to`, it moves the database to the contract state in `contract.json`, so it applies the rollback. In development, run `npx prisma db migrate --advance-ref db`. The flag also moves the [`db` ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from), a saved name for the contract state that `migration plan` starts from, to the state the run applied.

After step 4, `npx prisma db verify` passes. `npx prisma migration graph` shows the round trip, with the original migration marked `↑` and the rollback marked `↓`. `ops` counts each migration's operations, the single steps such as dropping a column:

```text
○   e6b5c28
│↑  20260707T1008_add_display_name       925198f → e6b5c28  3 ops
│↓  20260707T1010_rollback_display_name  e6b5c28 → 925198f  1 ops
○   925198f  @contract
│↑  20260707T1006_add_user_phone         705b1a6 → 925198f  1 ops
○   705b1a6
│↑  20260707T1005_init                         ∅ → 705b1a6  2 ops
○   ∅
```

`migration graph` reads only your files and never connects to the database. It marks your contract with `@contract`, but it never shows where the database is. To see that, run `npx prisma migration status`, which marks the database's contract state with `@db`.

To undo several migrations, you don't need to retrace every step. Write one migration with `npx prisma migration plan --from <newest-migration-dir> --to <oldest-migration-to-undo>^ --name rollback_changes`. Revert your contract to its version from before the oldest migration you undo, for example with `git show <commit>:<contract path> > <contract path>`. Then run `npx prisma contract emit` and apply the migration once.

### One planning caveat after a rollback

After a rollback, every contract state in your migration history has a migration leading out of it, so the history has no newest state. The next `migration plan` then fails with an error whose `code` is `MIGRATION.NO_TARGET`, even when the `db` ref is set. "Target" in that name means the newest state, not `--to`. Pass `--from` once, with the rollback's directory name:

```npm
npx prisma migration plan --from 20260707T1010_rollback_display_name --name add_nickname
```

Once this migration exists, the history has a newest state again, and `migration plan` no longer fails this way.

## Recovery: when a migration fails partway

A failed `db migrate` run stops at the failing operation and reports it:

```text
✘ [MIGRATION.RUNNER_FAILED] Operation alterNullability.setNotNull.user.nickname failed during precheck: ensure no NULL values in "nickname"
  why: Migration runner failed
  docs: https://docs.prisma.io/docs/orm/v8/reference/error-reference/MIGRATION.RUNNER_FAILED
```

On PostgreSQL, a failed run leaves nothing to clean up, because one `db migrate` run is one transaction. MongoDB has no transaction, and [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) explains what a re-run does there. Prisma ORM 8 supports PostgreSQL and MongoDB, and SQLite is experimental, as [Supported databases](/orm/supported-databases) lists.

1. **Read which check failed.** The error names the operation and the [check](/orm/migrations/how-migrations-work#every-operation-checks-itself) that failed. Here, rows with `NULL` in `nickname` still exist, so the precheck stopped the run before it set `NOT NULL`.
2. **Fix the cause, then run `npx prisma db migrate` again.** In development, add `--advance-ref db` as before. Sometimes the cause is the environment, such as a PostgreSQL extension the server lacks, or missing permissions. Sometimes it's the migration itself. Here you'd [edit the migration](/orm/migrations/editing-a-migration) to fill in `nickname` for existing rows before the `setNotNull`. Then recompile it with `node migrations/app/<dir>/migration.ts` from your project's root directory, and apply again.

Sometimes a migration applies in development and then fails in production. Say your development database had no `NULL`s in `nickname`, but production does. In production, the precheck stops the run with an error that names the check, before the `ALTER` runs. After you edit and recompile the migration, `db migrate` has nothing to run in development, because that database is already at the state the migration ends at.

### Drift: when the database isn't where migrations left it

Drift means the database changed without a migration. The [marker](/orm/migrations/the-migration-graph#terms-used-on-this-page) is the record in the database of the last contract state applied to it. Drift shows up in one of two ways:

- **The marker is at a contract state that is not in your migration history.** `npx prisma db update` can cause this. It makes a development database match your contract and writes a marker for that contract state, even when no migration ends there. The next `db migrate` then fails with an error whose `code` is `MIGRATION.MARKER_MISMATCH`, before it runs any operation. To fix it, keep the contract that `db update` applied, and write a migration that ends at its state: run `npx prisma migration plan --from <newest-migration-dir> --name <name>`.
- **Only tables or columns changed**, for example with a hand-run `ALTER`. The marker does not move, so `db migrate` still runs. An operation that conflicts with the manual change can fail.

To find out where the database is, run two commands that only read it. They connect to the database in `db.connection` in `prisma.config.ts`, or to the URL you pass with `--db`:

- **[`npx prisma migration status`](/cli/migration-status)** shows which contract state the marker is at, marked `@db`.
- **[`npx prisma db verify`](/cli/db-verify)** checks the marker and the tables against your contract. With `--schema-only`, it checks only the tables.

To fix drift in production, change the tables back by hand, or with a migration if `db migrate` still runs. When `npx prisma db verify --schema-only` passes, run [`npx prisma db sign`](/cli/db-sign). It checks the tables against your contract again, then writes the marker for that contract. For a new environment with no migration history, [`npx prisma db init`](/cli/db-init) changes the database: it creates what your contract declares and the database lacks. For a database that Prisma ORM 7 migrated, run `npx prisma db sign`, as the [PostgreSQL upgrade guide](/guides/upgrade-prisma-orm/postgresql) shows.

:::note[What's early]

Reverse planning (`--to <dir>^`), destructive-operation warnings, safe re-runs, and the ledger all work today. Not built yet: a way to try a migration on a temporary copy of the database before it runs for real. After a rollback, `migration plan` needs an explicit `--from`. For drift that these commands don't cover, you fix the database by hand. For unusual situations, ask in `#prisma-next` on [Discord](https://pris.ly/discord).

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8), instruction files for your coding agent. In an existing project, run `npx prisma skills sync`, and then you can ask your agent to:

- "Plan a rollback for the last migration and show me its destructive operations before I decide."
- "This db migrate run failed. Read the error, fix the migration, and re-run it."
- "Check whether staging has drifted from the contract and explain the differences."
