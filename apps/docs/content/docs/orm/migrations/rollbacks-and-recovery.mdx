"Rollback" refers to two different situations, which Prisma ORM treats differently:

- **The migration applied, but the change was wrong.** You need to move the database *back* to an earlier state. This is a **rollback**, and in Prisma ORM it's one more migration.
- **The migration failed partway.** You need to get *unstuck*. This is **recovery**, and it usually means fixing the cause and re-running, because re-running is safe.

## Rollback: a migration like any other

There is no `migrate down` command and no separate "down migration" files. The state you want to return to is already in your [migration history](/orm/migrations/the-migration-graph), so rolling back means planning a new migration that ends at it. If you know git, this is `git revert`, not `git reset`. History only ever grows, and the ledger, the database's own list of every migration applied to it, keeps the full round trip.

<ConceptAnimation name="migration-rollback" />

Suppose `20260707T1008_add_display_name` shipped and needs to come back out. Plan the reverse migration. `<dir>^` means "the state before that migration":

```npm
npx prisma migration plan \
  --from 20260707T1008_add_display_name \
  --to 20260707T1008_add_display_name^ \
  --name rollback_display_name
```

```text
✔ Planned 1 operation(s)

migrations/app/20260707T1010_rollback_display_name
└─ Drop column "displayName" from "user"

⚠ This migration contains destructive operations that may cause data loss.

from:       e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
to:         705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
app space:  migrations/app/20260707T1010_rollback_display_name

DDL preview

ALTER TABLE "public"."user" DROP COLUMN "displayName";
```

The planner compares the two contract states, writes the operations that undo the change, and flags the destructive ones. This is a real migration: review it, edit it (for example, to archive the column's data into another table before the `DROP`), and commit it. Then apply it like any other migration:

```npm
npx prisma db migrate --to 20260707T1008_add_display_name^
```

One loose end remains after the database moves back. Your contract, the `contract.prisma` file that replaced `schema.prisma`, still contains the change, so `db verify` reports that the database does not match it until you revert the contract and run `npx prisma contract emit`. Roll back the contract in the same commit as the rollback migration and the two stay in step.

Afterwards, `npx prisma migration graph` shows the round trip, with the forward migration marked `↑` and the rollback marked `↓`:

```text
○   e6b5c28  @contract
│↑  20260707T1008_add_display_name       705b1a6 → e6b5c28  3 ops
│↓  20260707T1010_rollback_display_name  e6b5c28 → 705b1a6  1 ops
○   705b1a6
│↑  20260707T1005_init                         ∅ → 705b1a6  2 ops
○   ∅
```

The database's marker, the record in the database of which contract state it currently matches, is back at `705b1a6`. The ledger records both the apply and the rollback. Nothing is rewritten or deleted.

Keep two details in mind:

- **A rollback does not bring data back.** Dropping the column discards whatever the forward migration and the app wrote into it. If that data matters, edit the rollback migration to save it somewhere first.
- **You don't need to retrace every step.** A rollback migration can go from the current contract state straight to any earlier one: one planned migration, one apply, even if you're rolling back three changes.

### One planning caveat after a rollback

A rollback creates a cycle in your migration history (`A → B → A`), so `migration plan` can no longer work out the latest state on its own. The next time you run `migration plan`, pass `--from` a migration directory name or a hash, the short identifier computed from a contract. Otherwise it fails with an error whose `code` is `MIGRATION.NO_TARGET` and lists the reachable states.

## Recovery: when a migration fails partway

A failed `db migrate` run stops at the failing operation and reports it:

```text
✖ Operation alterNullability.setNotNull.user.nickname failed during precheck: ensure no NULL values in "nickname" (MIGRATION.RUNNER_FAILED)
  Why: Migration runner failed
  Fix: Fix the issue and re-run `prisma db migrate --to <contract>` — previously applied migrations are preserved.
```

What to do:

1. **Read which check failed.** The error names the operation and the precheck or postcheck that failed, in plain language. Here, rows with `NULL` still exist, so setting `NOT NULL` would fail.
2. **Nothing to clean up.** On PostgreSQL a failed run is rolled back completely, so there is no half-applied migration to untangle by hand.
3. **Fix the cause, then re-run `db migrate`.** Sometimes the cause is the environment, such as a missing extension or permissions. Sometimes it's the migration itself: here you'd [edit the migration](/orm/migrations/editing-a-migration) to add a backfill before the `setNotNull`, recompile it by running `node migration.ts`, and apply again. Re-running is safe, as [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) explains.

The precheck also protects you when a migration works in development but would fail in production. Your development database had no `NULL`s, but production does, so the precheck stops the production run *before* the destructive `ALTER` touches anything. The error names the failed check instead of reporting a constraint violation partway through a statement.

### Drift: when the database isn't where migrations left it

If someone changed the database outside of migrations, for example with a hand-run `ALTER` or a restore from an old backup, two things can happen. If the change also moved the marker to a contract state your migration history doesn't contain, `db migrate` fails before running any operation. If the marker is intact and only the database's tables or columns changed, `db migrate` still runs. Each operation's postcheck decides whether its work is already done, so a hand-applied change that satisfies it is skipped, and one that doesn't can make that operation fail. Either way, start by finding out where the database really is. Your options, in order of preference:

- **`db verify`** checks whether the database still matches your contract, and fails with a precise error when it doesn't.
- **In development**, `db update` changes the database to match your contract directly, without going through your migrations. It writes no migration files, so your migration history has no record of the change.
- **For a database with no migration history**, such as a fresh environment or an existing database you are moving to Prisma ORM, `db init` creates what your contract declares and the database lacks, then writes the marker.

:::note[What's early]

Reverse planning (`--to <dir>^`), destructive-operation warnings, safe re-runs, and the ledger all work today. Not built yet: a rehearsal mode that runs a migration against a shadow copy of the database first. After a rollback, `migration plan` needs an explicit `--from`, and recovering from drift beyond `db verify`, `db update`, and `db init` is manual. For unusual situations, ask in `#prisma-next` on [Discord](https://pris.ly/discord).

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Plan a rollback for the last migration and show me its destructive operations before I decide."
- "This db migrate run failed. Read the error, fix the migration, and re-run it."
- "Check whether staging has drifted from the contract and explain the differences."
