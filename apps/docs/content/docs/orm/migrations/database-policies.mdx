Database policies are rules stored in a database about how Prisma ORM may change it. Use them to protect a database such as production from a command run by mistake: for example, a production database can record that it changes only through reviewed migrations, and that no change may drop data. Every Prisma ORM command that changes the database reads its policies first, and refuses to do what they forbid.

A database can record two policies:

- The [change policy](#change-policy) says which commands may change the database.
- The [data protection policy](#data-protection-policy) says whether a change may lose data, or change who can read or write it.

A database that records no policy works as it did before policies existed: every command may change it, and losing data or changing access needs your consent. Policies are in Prisma ORM since `8.0.0-rc.25`. To give a database its policies, you write them in a ref, a file under `migrations/app/refs/` that names the version of your contract an environment should match, and then apply that ref to the database, as [Set a database's policies](#declare-policies-in-a-ref) shows.

## Change policy

The change policy lists the ways the database may be changed:

| Value | Commands it allows |
| --- | --- |
| `migrate` | [`db migrate`](/cli/db-migrate), which runs the migrations you planned |
| `reconcile` | [`db update`](/cli/db-update) and [`db sign`](/cli/db-sign), which change or sign the database to match a contract with no migration |

A command the policy does not allow fails with [`MIGRATION.CHANGE_POLICY_FORBIDS`](/orm/reference/error-reference#MIGRATION.CHANGE_POLICY_FORBIDS) before it changes anything. A production database usually records `["migrate"]`, so that `db update` cannot change it by accident. To change such a database, plan the change with [`migration plan`](/cli/migration-plan) and apply it with `db migrate`.

## Data protection policy

The data protection policy has two settings, and each takes one of three values:

| Setting | What it covers | Values |
| --- | --- | --- |
| `dataLoss` | An operation that loses data, such as dropping a table or a column, or a type change that can change values | `data-loss-forbidden`, `data-loss-with-consent`, `data-loss-permitted` |
| `accessWidening` | An operation that changes who can read or write data | `access-widening-forbidden`, `access-widening-with-consent`, `access-widening-permitted` |

On PostgreSQL, two operations count as changing access: disabling row-level security, and dropping a row-level security policy. On SQLite, MySQL, MariaDB and MongoDB, no operation counts, so `access-widening-forbidden` refuses nothing there. For access changes, only the operations Prisma ORM plans are checked: a row-level security change you write as raw SQL in a migration is not.

### `with-consent`

`with-consent` is the default, and is how the commands behave when the database records no policy. `db update` asks before it loses data or changes access, and `migration plan` asks before it writes a migration that loses data.

### `forbidden`

When a setting is `forbidden`, `db update` and `db migrate` refuse such an operation before anything runs, with [`MIGRATION.DATA_PROTECTION_FORBIDS`](/orm/reference/error-reference#MIGRATION.DATA_PROTECTION_FORBIDS). No answer permits it: not `--delete`, not `--allow`, and not an answer typed in the terminal. The error says how to plan the change again without losing data, which depends on what you changed:

- If you renamed a model or a field, say so with `--rename`, as [Renames and data loss](/cli/migration-plan#renames-and-data-loss) shows. A rename loses no data, so the policy allows it.
- If you changed a field's type, plan the change with `migration plan --convert`, so that the migration converts the stored values.
- Otherwise, keep the model or field in the contract.

When the refused operation is in a migration that an extension package ships, do not edit or delete that migration. The extension's author, or the owner of the database, has to resolve it.

### `permitted`

When a setting is `permitted`, `db update` asks nothing about such an operation. Where it would have asked whether to keep or lose data, it loses the data, as if you had answered with `--delete`.

## Set a database's policies [#declare-policies-in-a-ref]

You declare the policies a database should have in a [ref](/cli/migration-ref), the file that names the contract state an environment should match, and then apply that ref to the database.

### 1. Declare the policies in a ref

Add a `policies` key to the ref's file. Every key inside it is optional, and a key you leave out declares nothing:

```json title="migrations/app/refs/production.json"
{
  "hash": "4b1c…e09a",
  "invariants": [],
  "policies": {
    "change": ["migrate"],
    "dataProtection": {
      "dataLoss": "data-loss-forbidden",
      "accessWidening": "access-widening-forbidden"
    }
  }
}
```

The commands that rewrite a ref file keep its `policies` key.

### 2. Apply the ref to the database [#apply-a-refs-policies-to-a-database]

`db migrate --to <ref>` and `db update --to <ref>` compare the ref's policies with the database's before they run anything. When they differ, the command fails with [`MIGRATION.POLICY_MISMATCH`](/orm/reference/error-reference#MIGRATION.POLICY_MISMATCH), and the error names each setting with both values. If the ref is wrong, correct it. If the owner of the database means to change its policies, pass `--permit-policy-change`:

```npm
npx prisma db migrate --to production --permit-policy-change --db "$DATABASE_URL"
```

With `--permit-policy-change`, the run is checked against the ref's policies, and writes them into the database when it succeeds. A failed run leaves the old policies in place, and a run with no pending migration writes only the policies. The flag needs `--to` with a ref name. A deploy pipeline can pass the flag on every run, because with a ref that declares no policies, the flag changes nothing.

Treat `--permit-policy-change` as consent from whoever owns the database, in the same way as `--delete`. Do not add it, or loosen a ref's `policies`, to get a refused command past a policy.

`migration plan --to <ref>` checks the ref's policies too: it refuses to write a migration that the ref's data protection policy forbids.
