This tutorial turns a change to your contract, the `contract.prisma` file that replaced `schema.prisma`, into a migration you review before it runs. To create a project first, see the [quickstart](/prisma-orm/quickstart/postgresql).

After you edit the contract, run `npx prisma contract emit`. It replaces `prisma generate`, and writes `contract.json` and `contract.d.ts` next to `contract.prisma`. Then `npx prisma migration plan` writes a new migration from `contract.json` without applying it. It never connects to a database, so you can plan in CI or a sandbox with no credentials. By default it starts from the `db` [ref](/orm/migrations/the-migration-graph#terms-used-on-this-page), a file in `migrations/app/refs/` naming the contract version you last applied in development.

## Your first migration

Say your contract has a single model:

```prisma title="contract.prisma"
model User {
  id    Int     @id
  email String
  name  String?

  @@map("user")
}
```

Run both commands. With `--name init`, the new directory is named `<timestamp>_init`:

```npm
npx prisma contract emit
npx prisma migration plan --name init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        init

✔ Planned 2 operation(s)
ℹ No db ref set — planning from an empty database. Run db init, db update, or db sign if a database already exists.

migrations/app/20260707T1005_init
├─ Create schema "public"
└─ Create table "user"

from:       (baseline)
to:         705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
app space:  migrations/app/20260707T1005_init

ℹ DDL preview

CREATE SCHEMA IF NOT EXISTS "public";
CREATE TABLE "public"."user" (
  "email" text NOT NULL,
  "id" int4 NOT NULL,
  "name" text,
  PRIMARY KEY ("id")
);
```

Four things to note:

- **`Planned 2 operation(s)`** counts the migration's steps, listed under its directory. The DDL preview is the SQL they run.
- **`to:`** is your contract's hash. Each version of your contract is a contract state, named by its hash.
- **`from: (baseline)`** marks a baseline migration, a first migration from an empty database to a contract state. What Prisma ORM 7 called baselining, marking an existing database as already migrated, is `npx prisma db sign` in Prisma ORM 8.
- **`app space:`** is the new migration's directory. `migrations/app/` holds your app's migrations, and each [Prisma ORM extension package](/orm/extensions/using-extensions) that ships migrations has its own. `migrations/` is in the directory you run commands from, normally the project root.

The `No db ref set` line means the project has no `db` ref, so `migration plan` started from an empty database. With an existing database, what to do first depends on what it holds:

- A database that Prisma ORM 7 migrated needs the steps in the [upgrade guide](/guides/upgrade-prisma-orm/postgresql#4-transfer-migration-ownership).
- An empty database needs nothing: `npx prisma db migrate` creates the tables, though not the database itself.
- A database whose tables all match your contract needs [`npx prisma db sign`](/cli/db-sign), then [The automatic baseline](#the-automatic-baseline). It checks the tables against your contract, then writes the [marker](/orm/migrations/the-migration-graph#terms-used-on-this-page), the record in the database of which contract state it matches.
- A database with only some of your tables needs [`npx prisma db init`](/cli/db-init). It adds only what is missing, and stops if matching your contract needs a change that could lose data, such as dropping a column.
- A development or preview database that should match your contract without migration files needs [`npx prisma db update`](/cli/db-update). Unlike `db init`, it makes changes that could lose data, after asking you to type the database name.

Each migration directory holds three files and no SQL file: `migration.ts`, which you read and sometimes edit, plus `ops.json` and `migration.json`, which `db migrate` reads. Commit all three, along with `contract.prisma`, `contract.json`, `contract.d.ts`, and any new directories under `migrations/snapshots/`, saved copies of your contract. `migration.ts` lists the change as method calls:

```ts title="migrations/app/20260707T1005_init/migration.ts"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract';
import endContract from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract.json' with { type: 'json' };
import { Migration, MigrationCLI, col, primaryKey } from '@prisma/orm-postgres/migration';

export default class M extends Migration<never, End> {
  override readonly endContractJson = endContract;

  override get operations() {
    return [
      this.createSchema({ schema: 'public' }),
      this.createTable({
        schema: 'public',
        table: 'user',
        columns: [
          col('email', 'text', { notNull: true, codecRef: { codecId: 'pg/text@1' } }),
          col('id', 'int4', { notNull: true, codecRef: { codecId: 'pg/int4@1' } }),
          col('name', 'text', { codecRef: { codecId: 'pg/text@1' } }),
        ],
        constraints: [primaryKey(['id'])],
      }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The `operations` list is the change. A change like this one needs no edit, and you never edit `ops.json` by hand. [Editing a migration](/orm/migrations/editing-a-migration) covers editing and recompiling `migration.ts` to add a data backfill, reorder operations, or run raw SQL.

## The second migration: planning a delta

Apply the first migration to your development database with `npx prisma db migrate --advance-ref db`. It connects to [`db.connection`](/orm/contract-authoring/the-data-contract) in `prisma.config.ts`, or to a connection string passed with `--db`. `--advance-ref db` points the `db` ref at the state you just applied, so the next `migration plan` starts from there.

Now add an optional `phone String?` field to `User`, and run both commands again:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_user_phone

✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

To start from a different contract state, pass `--from`, as in `--from 20260707T1005_init`. A migration directory name means the state after that migration. The [`migration plan` reference](/cli/migration-plan#options) lists every form it accepts.

### The db ref: skipping --from

For every change after your first migration, repeat these five steps. They replace Prisma ORM 7's `migrate dev` when you want migration files, as the [command table](/orm/coming-from-prisma-orm-7#commands) shows:

1. Edit your contract.
2. Run `npx prisma contract emit`. Skip it and `migration plan` reads the old `contract.json`, so it prints `No changes detected` or plans without your latest edit.
3. Run `npx prisma migration plan --name <name>`.
4. Review it with `npx prisma migration show <dir>`, where `<dir>` is the directory name. After editing `migration.ts`, [recompile it](/orm/migrations/editing-a-migration): run `node migrations/app/<dir>/migration.ts` from your project root, which rewrites `ops.json` and `migration.json`.
5. Apply it: `npx prisma db migrate --advance-ref db` in development, `npx prisma db migrate` in CI and production.

Plan a second migration before applying the first with `--advance-ref db`, and the `db` ref still points at the older contract state, so the second migration repeats the first one's changes. Delete the repeated migration's directory, run [`npx prisma migration ref set db <dir>`](/cli/migration-ref) with the name of the directory it repeated, then plan again. To discard any migration that has not run on a database, delete its directory. Its `migrations/snapshots/` directory can stay.

`npx prisma db sign`, `db init`, and `db update` also point the `db` ref at the new state after they change the database in `prisma.config.ts`. `db sign` updates it even with the `--db` flag, so add `--no-advance-ref` when you sign another database.

When you leave off `--from`, `migration plan` does one of four things:

| Migrations in `migrations/app/` | `db` ref | What `migration plan` does |
| --- | --- | --- |
| None | None | Plans from an empty database |
| None | Exists | Writes a baseline migration, then your change |
| Some | Exists | Plans from the state the `db` ref points at |
| Some | None | Stops with an error |

In the last case, the error prints three commands: one sets the `db` ref, one passes `--from`, and one passes `--from @empty`.

### The automatic baseline

`db sign` and `db update` leave you in the table's second row: `migrations/app/` is empty, and the `db` ref points at a contract state. Run `migration plan` before `db migrate`. It writes a baseline migration to that state, plus a second migration if `contract.json` changed since. `db migrate` fails on that database until one migration's `to:` hash matches the marker, and it never runs the baseline there, because the marker already records that state. [Baselines](/orm/migrations/the-migration-graph#baselines) has the full rule.

If a deployed database, such as production, matches an older version of your contract than your development database, plan the baseline from that older version, because the automatic baseline would end at your development database's state:

1. Change your contract back to the deployed version, for example with `git show <commit>:<contract path> > <contract path>`.
2. Run `npx prisma contract emit`.
3. Run `npx prisma migration plan --name baseline --from @empty`.
4. Run `npx prisma db sign --db "$PRODUCTION_DATABASE_URL" --no-advance-ref` against the deployed database. It writes the marker there, and `--no-advance-ref` leaves your `db` ref alone.
5. Restore your current contract and run `npx prisma contract emit` again.
6. Plan the change with `npx prisma migration plan --name <name> --from <baseline dir>`, the baseline's directory name.

None of these steps changes your `db` ref.

## When the planner needs your input

Add a **required** field with no default to an existing table, and `migration plan` writes the `ADD COLUMN` and the `SET NOT NULL`. Only you know what the existing rows should contain, so it leaves that to you as a **placeholder**. To see one, apply `add_user_phone`, then add a required `displayName String` field to `User` and run both commands again:

```npm
npx prisma contract emit
npx prisma migration plan --name add_display_name
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_display_name

⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

from:       925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
to:         e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
app space:  migrations/app/20260707T1008_add_display_name
```

The new `migration.ts` has a `dataTransform` step, which updates existing rows, between the `ADD COLUMN` and `SET NOT NULL`. Its two `placeholder(...)` calls mark where your queries go: one finds rows that still need a `displayName`, and one fills it in. Write both with the [SQL query builder](/orm/reference/sql-query-builder), as [Editing a migration](/orm/migrations/editing-a-migration) shows. Then recompile it. The output calls that step self-emit. `migration plan` leaves `ops.json` empty when it writes placeholders, so `db migrate` fails and changes nothing until you recompile.

## Reviewing what you planned

Three commands check the migration before anything runs, and none connects to a database:

```npm
# One migration in detail: operations, metadata, DDL preview
npx prisma migration show 20260707T1006_add_user_phone
# The whole migration history, with your new migration in place
npx prisma migration graph
# Integrity check: hashes match, no files missing, every migration starts from empty or where another ends, refs point at known states
npx prisma migration check
```

In CI, run `npx prisma migration check` and read its exit code. `0` means every check passed. `4` means an integrity failure, such as a missing file or an `ops.json` someone edited by hand. `2` means it could not find a migration you named. It never reads `migration.ts`, so it cannot tell whether you recompiled after your last edit. To confirm, stage the migration with `git add` and recompile it. If `git status` then shows no unstaged change to `ops.json` or `migration.json`, they were up to date. This does not work for a backfill on a model with an [`updatedAt` column](/orm/migrations/editing-a-migration#worked-example-making-a-column-required).

:::note[What's early]

Planning covers tables, columns, indexes, constraints, and the backfill placeholder shown above. Column renames are not detected yet: renaming an optional field plans as **drop column + add column**, and `migration plan` prints a data-loss warning. `db migrate` runs destructive operations without asking, so read `migration show <dir>` first. To rename a column and keep its data, edit `migration.ts`, replace the pair with a [`rawSql` operation](/orm/migrations/editing-a-migration#escape-hatch-raw-sql) that runs `ALTER TABLE ... RENAME COLUMN`, and recompile. Unlike Prisma ORM 7's `migrate dev`, `migration plan` never asks you questions.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. The skills are instruction files your agent reads, so you can ask it to:

- "Add a required `displayName` field to User, emit the contract, and plan the migration."
- "Plan a migration named `add-orders-table` and show me its DDL preview before I commit it."
- "Run `migration check` and explain any integrity failures."
