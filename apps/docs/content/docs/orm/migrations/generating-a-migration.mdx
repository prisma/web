This tutorial takes a change to your contract, the `contract.prisma` file that replaced `schema.prisma`, from your editor to a migration on disk that you review before it runs. After every change to the contract, run `npx prisma contract emit`, which replaces `prisma generate` and writes `contract.json` and `contract.d.ts` next to `contract.prisma`. `npx prisma migration plan` finds that `contract.json` through `prisma.config.ts` and writes a new migration from it without applying anything. It never connects to a database, so you can plan in CI or in a sandbox with no credentials. Once your first migration exists, every later change follows the [five steps under The db ref](#the-db-ref-skipping---from). To create a project first, follow the [quickstart](/prisma-orm/quickstart/postgresql).

## Your first migration

Say your contract has a single model:

```prisma title="contract.prisma"
model User {
  id    Int     @id
  email String
  name  String?

  @@map("user")
}
```

Run both commands. With `--name init`, the new directory is named `<timestamp>_init`, and without `--name` its name ends in `_migration`:

```npm
npx prisma contract emit
npx prisma migration plan --name init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        init

✔ Planned 2 operation(s)
ℹ No db ref set — planning from an empty database. Run db init, db update, or db sign if a database already exists.

migrations/app/20260707T1005_init
├─ Create schema "public"
└─ Create table "user"

from:       (baseline)
to:         705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
app space:  migrations/app/20260707T1005_init

ℹ DDL preview

CREATE SCHEMA IF NOT EXISTS "public";
CREATE TABLE "public"."user" (
  "email" text NOT NULL,
  "id" int4 NOT NULL,
  "name" text,
  PRIMARY KEY ("id")
);
```

Four things to note:

- **`Planned 2 operation(s)`** counts the migration's steps, which are listed under its directory. The DDL preview is the SQL those steps will run, and nothing has run against a database yet.
- **`to:`** is your contract's hash. Each version of your contract is a contract state, named by its hash.
- **`from: (baseline)`** means the migration starts from an empty database, the same state that `--from @empty` names. A baseline migration is a first migration from an empty database to a contract state. What Prisma ORM 7 called baselining, marking an existing database as already migrated, is `npx prisma db sign` in Prisma ORM 8.
- **`app space:`** is the new migration's directory. `migrations/app/` holds your app's migrations, and Prisma ORM looks for `migrations/` in the directory you run the command from. To use another directory, set `migrations.dir` in `prisma.config.ts` to the directory that should hold `app/` and `snapshots/`.

The `No db ref set` line means the project has no `db` ref yet. A [ref](/orm/migrations/the-migration-graph#terms-used-on-this-page) is a name for a contract state, stored as a file in `migrations/app/refs/`. If you already have a database, what to run depends on what it holds:

- An empty database needs nothing, because `npx prisma db migrate` creates the tables.
- A database whose tables all match your contract needs [`npx prisma db sign`](/cli/db-sign). It checks the tables against your contract, then saves a record in the database, called the [marker](/orm/migrations/the-migration-graph#terms-used-on-this-page), that says which contract state the database matches.
- A database that has only some of your tables needs [`npx prisma db init`](/cli/db-init). It adds what is missing and keeps what is already there, but it stops if matching your contract would need a destructive change.
- A development database that should match your contract without a migration needs [`npx prisma db update`](/cli/db-update).
- A database that Prisma ORM 7 migrated needs the steps in the [upgrade guide](/guides/upgrade-prisma-orm/postgresql).

Each migration directory holds three files and no SQL file. `ops.json` lists the operations that `npx prisma db migrate` runs, and `migration.json` records the hashes of the contract states the migration goes from and to. `migration.ts` imports saved copies of your contract from `migrations/snapshots/`. Commit the migration directory, any new directories under `migrations/snapshots/`, and `contract.prisma`, `contract.json`, and `contract.d.ts`. Open `migration.ts`, which lists the change as method calls:

```ts title="migrations/app/20260707T1005_init/migration.ts"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract';
import endContract from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract.json' with { type: 'json' };
import { Migration, MigrationCLI, col, primaryKey } from '@prisma/orm-postgres/migration';

export default class M extends Migration<never, End> {
  override readonly endContractJson = endContract;

  override get operations() {
    return [
      this.createSchema({ schema: 'public' }),
      this.createTable({
        schema: 'public',
        table: 'user',
        columns: [
          col('email', 'text', { notNull: true, codecRef: { codecId: 'pg/text@1' } }),
          col('id', 'int4', { notNull: true, codecRef: { codecId: 'pg/int4@1' } }),
          col('name', 'text', { codecRef: { codecId: 'pg/text@1' } }),
        ],
        constraints: [primaryKey(['id'])],
      }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The `operations` list is the change, and for a simple change you don't edit this file. You also leave the rest as `migration plan` wrote it: the imports load the saved contract, `never` means the migration starts from an empty database, each `codecId` is the column's PostgreSQL type plus a version, and `MigrationCLI.run` lets `node` run the file. When you need a data backfill, a different operation order, or raw SQL, see [Editing a migration](/orm/migrations/editing-a-migration).

## The second migration: planning a delta

Apply the first migration to your development database with `npx prisma db migrate --advance-ref db`. It connects to [`db.connection`](/orm/contract-authoring/the-data-contract) in `prisma.config.ts`, such as `db: { connection: process.env["DATABASE_URL"]! }`, unless you pass a connection string with `--db`. `--advance-ref db` saves the contract state it applied in the `db` ref, so the next `migration plan` starts from there. [Applying a migration](/orm/migrations/applying-a-migration) covers this step in detail.

Now add an optional `phone String?` field to `User`, and run both commands again to plan a migration with only that change:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_user_phone

✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

To start from a different contract state, pass `--from`, for example `npx prisma migration plan --name <name> --from 20260707T1005_init`. `--from` takes a contract state in any of these forms:

- A migration directory name, as in that example, means the state after that migration.
- `<dir>^` means the state before that migration.
- A contract hash can be given in full, or as its first 6 or more characters when they match only one hash.
- A ref name, such as the `db` ref, means the state that ref points at.
- `@empty` means an empty database.

### The db ref: skipping --from

If the **`db` ref** exists, `migration plan` starts from the contract state it points at, so you don't pass `--from`. The `db` ref is a file in `migrations/app/refs/`, not a record in the database, so it can point at a different contract state than your database's marker. For every change after your first migration, repeat these five steps, which replace Prisma ORM 7's `migrate dev` when you want migration files, as the [command table](/orm/coming-from-prisma-orm-7#commands) shows:

1. Edit your contract.
2. Run `npx prisma contract emit`. If you skip it, `migration plan` reads the old `contract.json`, so it prints `No changes detected` or plans without your latest edit.
3. Run `npx prisma migration plan --name <name>`.
4. Review the migration with `npx prisma migration show <dir>`. If you edit `migration.ts`, [recompile it](/orm/migrations/editing-a-migration) from your project's root directory with `node migrations/app/<dir>/migration.ts`, which rewrites `ops.json` and `migration.json` without connecting to a database. The Prisma ORM CLI needs Node.js 22.18 or later, and those versions run `migration.ts` directly.
5. Apply it. In development, run `npx prisma db migrate --advance-ref db`. In CI and production, run `npx prisma db migrate`.

If you leave off `--advance-ref db` in development, the `db` ref stays at the older contract state. The next `migration plan` then plans from that state to your contract, so the new migration repeats the changes of the migration you already planned. To fix it, delete the repeated migration's directory, run `npx prisma migration ref set db <dir>` with the directory name of the last migration you applied, and plan again.

Other commands move the `db` ref too:

- `npx prisma db init` and `npx prisma db update` move it after a successful run. With `--dry-run` they never move it, and with `--db` they move it only if you add `--advance-ref db`.
- `npx prisma db sign` moves it even with `--db`, because you usually sign a database that way. Add `--no-advance-ref` to leave it alone.
- [`npx prisma migration ref set db <dir>`](/cli/migration-ref) points it at the state after the migration you name.

When you leave off `--from`, `migration plan` does one of four things:

| Migrations in `migrations/app/` | `db` ref | What `migration plan` does |
| --- | --- | --- |
| None | None | Plans from an empty database |
| None | Exists | Writes a baseline migration, then your change |
| Some | Exists | Plans from the state the `db` ref points at |
| Some | None | Stops with an error |

In the last case, planning from an empty database would write a migration that recreates everything your existing migrations already create. The error prints three commands you can run instead: one sets the `db` ref, one passes `--from`, and one passes `--from @empty` to plan from an empty database on purpose.

### The automatic baseline

The second row of the table is the usual state after you run `npx prisma db sign` on a database that already has tables, or after a few `db update` runs: `migrations/app/` is empty, and the `db` ref points at a contract state. The next `migration plan` writes a baseline migration from an empty database to that state. When `contract.json` differs from that state, it also writes a second migration with the change, so expect one or two new directories in `git status`. Plan before you run `npx prisma db migrate`, because `db migrate` refuses a signed database until a migration in your history ends at its contract state.

`db migrate` applies only the migrations after a database's marker, so the baseline never runs on a database that has a marker. For a database that has tables but no marker, run `npx prisma db sign` rather than `db migrate`, because `db sign` checks the tables against your contract before it writes the marker. The migration graph page has the full rule under [Baselines](/orm/migrations/the-migration-graph#baselines).

Write the baseline migration by hand when a deployed database, such as production, does not have changes that your development database already has. The automatic baseline ends at the `db` ref's state, which includes those changes, so it would not match the deployed database:

1. Change your contract back to the deployed state. With Git, that could be `git show <commit>:<contract path> > <contract path>`.
2. Run `npx prisma contract emit`.
3. Run `npx prisma migration plan --name baseline --from @empty`.
4. Run `npx prisma db sign --db "$PRODUCTION_DATABASE_URL" --no-advance-ref` against the deployed database. It writes the marker there, and `--no-advance-ref` leaves your `db` ref alone.
5. Restore your current contract and run `npx prisma contract emit` again.
6. Plan the change with `npx prisma migration plan --name <name> --from <baseline dir>`, using the baseline's directory name.

## When the planner needs your input

Some changes can't be planned from the contract change alone. Add a **required** field with no default to an existing table, and `migration plan` can write the `ADD COLUMN` and the `SET NOT NULL`, but only you know what the existing rows should contain. Rather than guessing, it leaves that decision as a **placeholder**. To see one, apply `add_user_phone` with `npx prisma db migrate --advance-ref db`. Then add a required `displayName String` field to `User`, and run both commands again:

```npm
npx prisma contract emit
npx prisma migration plan --name add_display_name
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_display_name

⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

from:       925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
to:         e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
app space:  migrations/app/20260707T1008_add_display_name
```

The new `migration.ts` has a `dataTransform` step, which updates existing rows, between the `ADD COLUMN` and `SET NOT NULL` steps. Its two `placeholder(...)` calls mark where your queries go: one finds rows that still need a `displayName`, and one fills it in. You write both in TypeScript with the query builder, as [Editing a migration](/orm/migrations/editing-a-migration) shows. Then recompile from your project's root directory with `node migrations/app/20260707T1008_add_display_name/migration.ts`. The output's `node migration.ts` means this same step, and the root directory matters because that is where it finds `prisma.config.ts`. If you run `npx prisma db migrate` before you recompile, it fails and changes nothing, because `ops.json` is still empty.

## Reviewing what you planned

Three commands check the migration before anything runs, and none of them connects to a database:

```npm
# One migration in detail: operations, metadata, DDL preview
npx prisma migration show 20260707T1006_add_user_phone
# The whole migration history, with your new migration in place
npx prisma migration graph
# Integrity check: hashes match, no files missing, every migration starts from empty or where another ends, refs point at known states
npx prisma migration check
```

In CI, run `npx prisma migration check` as a step and read its exit code. `0` means every check passed. `4` means it found an integrity failure, such as a missing file or an `ops.json` that someone edited by hand. `2` means it could not find a migration you named, as in `npx prisma migration check 20260707T1006_add_user_phone`. It does not read `migration.ts`, so it cannot tell whether you recompiled after your last edit.

:::note[What's early]

Planning covers tables, columns, indexes, constraints, and the backfill placeholder shown above. Column renames are not detected yet: renaming a field plans as **drop column + add column**, and `migration plan` prints a data-loss warning. `db migrate` runs destructive operations without asking, so read `npx prisma migration show <dir>` in review to catch one before it runs. To rename a column and keep its data, edit `migration.ts`, replace the pair with a [`rawSql` operation](/orm/migrations/editing-a-migration#escape-hatch-raw-sql) that runs `ALTER TABLE ... RENAME COLUMN`, and recompile. Unlike Prisma ORM 7's `migrate dev`, `migration plan` never asks you questions, so you make any changes in `migration.ts`.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. The skills are instruction files your agent reads, so you can ask it to:

- "Add a required `displayName` field to User, emit the contract, and plan the migration."
- "Plan a migration named `add-orders-table` and show me its DDL preview before I commit it."
- "Run `migration check` and explain any integrity failures."
