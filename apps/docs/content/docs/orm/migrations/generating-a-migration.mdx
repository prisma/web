This tutorial takes a change to your contract, the `contract.prisma` file that replaced `schema.prisma`, from your editor to a planned migration on disk. Planning is **fully offline**: `migration plan` reads your emitted contract and your existing migrations, and it never connects to a database. This means you can plan on a plane, in CI, or in a sandbox with no credentials. Start from an existing project, or create one with `npm create prisma@latest -- my-app`.

## Your first migration

Say your contract has a single model:

```prisma title="contract.prisma"
model User {
  id    Int     @id
  email String
  name  String?

  @@map("user")
}
```

Emit the contract with `npx prisma contract emit`, which you run after every change to the contract, then plan. `--name` sets the readable part of the directory name, and without it the name ends in `_migration`:

```npm
npx prisma contract emit
npx prisma migration plan --name init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        init

✔ Planned 2 operation(s)
ℹ No db ref set — planning from an empty database. Run db init, db update, or db sign if a database already exists.

migrations/app/20260707T1005_init
├─ Create schema "public"
└─ Create table "user"

from:       (baseline)
to:         705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
app space:  migrations/app/20260707T1005_init

ℹ DDL preview

CREATE SCHEMA IF NOT EXISTS "public";
CREATE TABLE "public"."user" (
  "email" text NOT NULL,
  "id" int4 NOT NULL,
  "name" text,
  PRIMARY KEY ("id")
);

→ Review migrations/app/20260707T1005_init
→ Apply the migration: prisma db migrate
```

Four things to note:

- **The DDL preview** is the SQL the migration runs, shown before anything exists but files.
- **`from: (baseline)`** means this migration starts from an empty database. It is the first migration in your [migration history](/orm/migrations/the-migration-graph).
- **`to:` is your contract's hash**, a short identifier computed from the contract. The migration builds a database that matches exactly the contract you emitted.
- **`app space`** is your app's contract space, a separate migration history: one for your app, and one for each database extension that ships its own migrations. See [extension spaces](/orm/migrations/applying-a-migration#extension-spaces).

The migration directory holds `migration.ts`, the operations in `ops.json`, and the metadata in `migration.json`. The contract snapshots that `migration.ts` imports are stored once per migrations directory, under `migrations/snapshots/<contract hash>/`:

```text
migrations/
├── app/
│   └── 20260707T1005_init/
│       ├── migration.ts
│       ├── ops.json
│       └── migration.json
└── snapshots/
    └── 705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/
        ├── contract.json
        └── contract.d.ts
```

Open `migration.ts`. It is a description of the change, so it reads like one:

```ts title="migrations/app/20260707T1005_init/migration.ts"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract';
import endContract from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract.json' with {
  type: 'json',
};
import { Migration, MigrationCLI, col, primaryKey } from '@prisma/orm-postgres/migration';

export default class M extends Migration<never, End> {
  override readonly endContractJson = endContract;

  override get operations() {
    return [
      this.createSchema({ schema: 'public' }),
      this.createTable({
        schema: 'public',
        table: 'user',
        columns: [
          col('email', 'text', { notNull: true, codecRef: { codecId: 'pg/text@1' } }),
          col('id', 'int4', { notNull: true, codecRef: { codecId: 'pg/int4@1' } }),
          col('name', 'text', { codecRef: { codecId: 'pg/text@1' } }),
        ],
        constraints: [primaryKey(['id'])],
      }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The `col(...)` calls mirror your contract fields. The planner fills in each `codecRef`, which records how that column's values are stored and read. For a simple change you don't need to touch this file. When you need a data backfill, a different operation order, or raw SQL, see [Editing a migration](/orm/migrations/editing-a-migration).

## The second migration: planning a delta

Apply the first migration as shown in [Applying a migration](/orm/migrations/applying-a-migration). Then add an optional `phone String?` field to `User`, emit, and plan again. This time, tell the planner where to start from, so it plans only the change rather than the whole database:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone --from 20260707T1005_init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  from:        20260707T1005_init
│  name:        add_user_phone

✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;

→ Review migrations/app/20260707T1006_add_user_phone
→ Apply the migration: prisma db migrate
```

`--from` accepts a migration directory name, as here, a contract hash or a prefix that matches only one hash, a ref name, `<dir>^` for the state *before* that migration, or `@empty` for an empty database.

### The db ref: skipping --from

You don't have to pass `--from` every time. If a [ref](/orm/migrations/the-migration-graph#name-important-states-with-refs) named **`db`** exists, planning starts from the contract state it points at. A ref is a name for a contract state, stored as a file in `migrations/app/refs/`. Four things move the `db` ref forward:

- `db init` and `db update` advance it after a successful run without `--dry-run`, but only when you leave `--db` off and the connection comes from `prisma.config.ts`. With `--db`, they leave it alone unless you also pass `--advance-ref db`.
- `db sign` advances it after a successful signature, with or without `--db`. That is why the first plan after you adopt an existing database starts from that database's contract, not from empty. Pass `--no-advance-ref` to sign without moving it.
- `db migrate --advance-ref db` advances it after the migrations are applied. Plain `db migrate` never advances a ref.
- `migration ref set db <contract>` sets it by hand.

```npm
npx prisma db update                                        # advances db on its own
npx prisma db update --db "$DATABASE_URL" --advance-ref db  # with --db, ask for it
npx prisma db sign --db "$DATABASE_URL"                     # advances db on its own
npx prisma db migrate --advance-ref db
npx prisma migration plan --name next_change                # starts from the db ref automatically
```

:::warning[Without `--from` or a `db` ref, planning stops]

If there is no `db` ref, you omit `--from`, and migrations already exist in `migrations/app/`, `migration plan` stops and fails with an error whose `code` is `MIGRATION.PLAN_ORIGIN_UNKNOWN`. Planning from an empty database there would write a migration that recreates everything your existing migrations already create. The error names three ways forward: set the `db` ref with `migration ref set db <contract>` or `db update`, pass `--from <contract>`, or pass `--from @empty` to plan from an empty database on purpose.

Only when `migrations/app/` has no migrations yet does the command still plan from an empty database on its own: that is the first migration in a new project, described above. It then prints `No db ref set — planning from an empty database` under its summary, with a reminder to run `db init`, `db update`, or `db sign` if a database already exists.

:::

### The automatic baseline

Sometimes `migrations/app/` has no migrations yet, but the `db` ref already points at a contract state whose snapshot is stored under `migrations/snapshots/`. That is the usual state after a few `db update` runs. One `migration plan` run then writes a baseline migration from an empty database to the ref's contract state and, when your emitted contract differs from it, a second migration with the change. Expect one or two new directories in `git status`.

The baseline never runs against a database that already has a marker, the record in the database of which contract state it currently matches: `db migrate` starts from the marker and applies only the migrations after it. The baseline exists so the ref's contract state is in your migration history and the change has somewhere to attach. The rule is under [Baselines](/orm/migrations/the-migration-graph#baselines).

To create a baseline by hand for a deployed database you must not touch, change the contract back to the deployed state, run `contract emit` and `migration plan --name baseline --from @empty`, then restore your current contract, emit it again, and plan the change with `--from` set to the baseline directory.

## When the planner needs your input

Some changes can't be planned from the contract change alone. Add a **required** field with no default to an existing table, and the planner can write the `ADD COLUMN` and the `SET NOT NULL`, but only you know what the existing rows should contain. Rather than guessing, it leaves that decision as a **placeholder**:

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_display_name

⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

from:       925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
to:         4b8e2f6a1c9d3e7f5a0b2c4d6e8f1a3b5c7d9e0f2a4b6c8d0e1f3a5b7c9d1e2f
app space:  migrations/app/20260707T1008_add_display_name

→ Replace each placeholder(...) call in migrations/app/20260707T1008_add_display_name/migration.ts with your query
→ Run it to self-emit ops.json and attest the package: node "migrations/app/20260707T1008_add_display_name/migration.ts"
```

The generated migration puts a `dataTransform` between the `ADD COLUMN` and `SET NOT NULL` steps, with `placeholder(...)` where your backfill query goes. Filling it in is explained in [Editing a migration](/orm/migrations/editing-a-migration).

## Reviewing what you planned

Three offline commands let you check the migration before anything runs:

```npm
# One migration in detail: operations, metadata, DDL preview
npx prisma migration show 20260707T1006_add_user_phone
# The whole migration history, with your new migration in place
npx prisma migration graph
# Integrity check: hashes match, files complete, no unreachable migrations or dangling refs
npx prisma migration check
```

In CI, read the exit code of `migration check`: `0` means every check passed, `2` means it could not find the migration or `--space` you named, and `4` means it found an integrity failure, for example a hand-edit to `ops.json` without re-running `migration.ts`.

:::note[What's early]

Planning covers tables, columns, indexes, constraints, and the backfill placeholder shown above. Column renames are not detected yet: renaming a field plans as **drop column + add column**, flagged destructive with a data-loss warning. For a true rename, edit the migration and replace the pair with a `rawSql` operation that runs `ALTER TABLE ... RENAME COLUMN`. There is also no interactive mode: the planner writes its best answer and leaves changes to you in `migration.ts`.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Add a required `displayName` field to User, emit the contract, and plan the migration."
- "Plan a migration named `add-orders-table` and show me its DDL preview before I commit it."
- "Run `migration check` and explain any integrity failures."
