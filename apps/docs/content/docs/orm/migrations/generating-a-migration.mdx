This tutorial takes a change to your contract, the `contract.prisma` file that replaced `schema.prisma`, from your editor to a migration on disk that you review before it runs. After every change to the contract, run `npx prisma contract emit`, which replaces `prisma generate`. It writes `contract.json` and `contract.d.ts`, and in this tutorial they go to `src/prisma/`. `npx prisma migration plan` reads that `contract.json` and your existing migrations. It never connects to a database, so you can plan in CI or in a sandbox with no credentials. To create a project first, follow the [quickstart](/prisma-orm/quickstart/postgresql).

## Your first migration

Say your contract has a single model:

```prisma title="contract.prisma"
model User {
  id    Int     @id
  email String
  name  String?

  @@map("user")
}
```

Emit the contract, then plan. With `--name init`, the new directory is named `<timestamp>_init`, and without `--name` its name ends in `_migration`:

```npm
npx prisma contract emit
npx prisma migration plan --name init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        init

✔ Planned 2 operation(s)
ℹ No db ref set — planning from an empty database. Run db init, db update, or db sign if a database already exists.

migrations/app/20260707T1005_init
├─ Create schema "public"
└─ Create table "user"

from:       (baseline)
to:         705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
app space:  migrations/app/20260707T1005_init

ℹ DDL preview

CREATE SCHEMA IF NOT EXISTS "public";
CREATE TABLE "public"."user" (
  "email" text NOT NULL,
  "id" int4 NOT NULL,
  "name" text,
  PRIMARY KEY ("id")
);
```

Four things to note:

- **The DDL preview** is the SQL the migration will run. Nothing has run against a database yet.
- **`(baseline)`** in `migration plan` output means the migration starts from an empty database. A baseline migration is a first migration from an empty database to a contract state. What Prisma ORM 7 called baselining (marking an existing database as already migrated) is `npx prisma db sign` in Prisma ORM 8.
- **`to:` is your contract's hash**, an identifier computed from the contract. Each version of your contract, called a contract state, has its own hash.
- **`app space:`** is the new migration's directory, inside `migrations/app/`. The `migrations/` directory is found in the directory you run the command from, unless you set `migrations.dir` in `prisma.config.ts`.

The `No db ref set` line means the project has no `db` ref yet. A [ref](/orm/migrations/the-migration-graph#terms-used-on-this-page) is a name for a contract state, stored as a file in `migrations/app/refs/`. If you already have a database, what to run depends on what it holds:

- An empty database needs nothing, because `npx prisma db migrate` creates the tables.
- A database whose tables match your contract needs [`npx prisma db sign`](/cli/db-sign). It checks the tables against your contract, then writes the marker, the record in the database of which contract state it currently matches.
- [`npx prisma db init`](/cli/db-init) adds missing tables and keeps compatible ones. It stops if a change would be destructive.
- A database that Prisma ORM 7 migrated needs the steps in the [upgrade guide](/guides/upgrade-prisma-orm/postgresql).

Each migration directory holds `migration.ts`, `ops.json`, and `migration.json`, and there is no SQL file. You edit only `migration.ts`, and only when a migration needs a change. Commit all three files, the `migrations/snapshots/<hash>/` directories that `migration.ts` imports, and `contract.json` and `contract.d.ts`. Open `migration.ts`, which lists the change as method calls:

```ts title="migrations/app/20260707T1005_init/migration.ts"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract';
import endContract from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract.json' with { type: 'json' };
import { Migration, MigrationCLI, col, primaryKey } from '@prisma/orm-postgres/migration';

export default class M extends Migration<never, End> {
  override readonly endContractJson = endContract;

  override get operations() {
    return [
      this.createSchema({ schema: 'public' }),
      this.createTable({
        schema: 'public',
        table: 'user',
        columns: [
          col('email', 'text', { notNull: true, codecRef: { codecId: 'pg/text@1' } }),
          col('id', 'int4', { notNull: true, codecRef: { codecId: 'pg/int4@1' } }),
          col('name', 'text', { codecRef: { codecId: 'pg/text@1' } }),
        ],
        constraints: [primaryKey(['id'])],
      }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The `operations` list is the change, and for a simple change you don't edit this file. When you need a data backfill, a different operation order, or raw SQL, see [Editing a migration](/orm/migrations/editing-a-migration).

## The second migration: planning a delta

Apply the first migration to your development database with `npx prisma db migrate --advance-ref db`. It connects with the connection string you pass with `--db`, or otherwise with [`db.connection`](/orm/contract-authoring/the-data-contract) in `prisma.config.ts`. `--advance-ref db` then sets the `db` ref to the contract state it applied, and the next `migration plan` starts from there. [Applying a migration](/orm/migrations/applying-a-migration) covers this step in detail. Now add an optional `phone String?` field to `User`, then emit and plan again, with no `--from`:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_user_phone

✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

To start from a different contract state, pass `--from`, for example `npx prisma migration plan --name <name> --from 20260707T1005_init`. `--from` takes a contract state in any of these forms:

- A migration directory name, as in that example, means the state after that migration.
- `<dir>^` means the state before that migration.
- A contract hash can be given in full, or as its first 6 or more characters when they match only one hash.
- A ref name, such as `db`, means the state that ref points at.
- `@empty` means an empty database.

### The db ref: skipping --from

If a ref named **`db`** exists, `migration plan` starts from the contract state it points at, so you don't pass `--from`. The `db` ref is a file in `migrations/app/refs/`, and the marker is a record in the database: `migration plan` reads the ref, and `db migrate` reads the marker. This everyday loop replaces Prisma ORM 7's `migrate dev` when you want migration files, as the [command table](/orm/coming-from-prisma-orm-7#commands) shows:

1. Edit your contract.
2. Run `npx prisma contract emit`. If you skip it, `migration plan` reads the old `contract.json`, so it prints `No changes detected` or plans without your latest edit.
3. Run `npx prisma migration plan --name <name>`, with no `--from`.
4. Review the migration with `npx prisma migration show <dir>`. If you edit `migration.ts`, recompile it from your project's root directory with `node migrations/app/<dir>/migration.ts`.
5. Apply it. In development, run `npx prisma db migrate --advance-ref db`, which moves the `db` ref to the state it applied. In CI and production, run `npx prisma db migrate`.

If you leave off `--advance-ref db` in development, the `db` ref stays at the older contract state. The next `migration plan` then plans from that state to your contract, so the new migration repeats the changes of the migration you already planned.

These commands move the `db` ref:

- `npx prisma db init` and `npx prisma db update` move it after a successful run. They leave it alone with `--dry-run`, and also when you pass `--db`, unless you add `--advance-ref db`.
- `npx prisma db sign` moves it after it signs the database, with or without `--db`. To leave it alone, add `--no-advance-ref`.
- `npx prisma db migrate` moves it only when you pass `--advance-ref db`, after the migrations are applied.
- `npx prisma migration ref set db <contract>` sets it by hand, where `<contract>` is a hash, a ref name, a migration directory name, or `<dir>^`, as in the `--from` list.

To start using migrations with a database that already has tables, sign it first with `npx prisma db sign`, which moves the `db` ref to that database's contract state. With no migrations on disk yet, the next `migration plan` writes a baseline migration from empty to that state, plus a migration with your change. The baseline never runs on the signed database, because its marker is already at that state.

When you leave off `--from`, `migration plan` does one of four things:

| Migrations in `migrations/app/` | `db` ref | What `migration plan` does |
| --- | --- | --- |
| None | None | Plans from an empty database |
| None | Exists | Writes a baseline migration, then your change |
| Some | Exists | Plans from the state the `db` ref points at |
| Some | None | Stops with an error |

In the last case, planning from an empty database would write a migration that recreates everything your existing migrations already create. The error prints three commands you can run instead: one sets the `db` ref, one passes `--from`, and one passes `--from @empty` to plan from an empty database on purpose.

### The automatic baseline

The second row of the table is the usual state after `db sign` or a few `db update` runs: `migrations/app/` is empty, and the `db` ref points at a contract state. One `migration plan` run then writes a baseline migration from an empty database to the ref's state. When your emitted contract differs from that state, it also writes a second migration with the change. Expect one or two new directories in `git status`.

`db migrate` applies only the migrations after a database's marker, so the baseline never runs on a database that has a marker. On a database with tables and no marker, `db migrate` starts from your first migration. It skips each operation whose work already exists, such as creating a table that is already there, and then writes a marker. To adopt such a database, run `npx prisma db sign` instead, because it checks the tables against your contract before it writes the marker. The migration graph page has the full rule under [Baselines](/orm/migrations/the-migration-graph#baselines).

Create a baseline by hand when your `db` ref is already ahead of a deployed database. The automatic baseline goes to the `db` ref's state, so it would not describe that database:

1. Change your contract back to the deployed state. With Git, that could be `git show <commit>:<contract path> > <contract path>`.
2. Run `npx prisma contract emit`.
3. Run `npx prisma migration plan --name baseline --from @empty`.
4. Run `npx prisma db sign --db "$DATABASE_URL" --no-advance-ref` against the deployed database. It writes the marker, so `db migrate` never runs the baseline there, and `--no-advance-ref` leaves your `db` ref alone.
5. Restore your current contract and run `npx prisma contract emit` again.
6. Plan the change with `npx prisma migration plan --name <name> --from <baseline dir>`, using the baseline's directory name.

## When the planner needs your input

Some changes can't be planned from the contract change alone. Add a **required** field with no default to an existing table, and the planner can write the `ADD COLUMN` and the `SET NOT NULL`, but only you know what the existing rows should contain. Rather than guessing, it leaves that decision as a **placeholder**. To see one, apply `add_user_phone` with `npx prisma db migrate --advance-ref db`. Then add a required `displayName String` field to `User`, and emit and plan:

```npm
npx prisma contract emit
npx prisma migration plan --name add_display_name
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_display_name

⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

from:       925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
to:         e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
app space:  migrations/app/20260707T1008_add_display_name
```

The generated migration puts a `dataTransform` step between the `ADD COLUMN` and `SET NOT NULL` steps, with `placeholder(...)` where your query that fills `displayName` for existing rows goes. "Self-emit" in the output means recompiling. After you fill in the placeholder, recompile from your project's root directory with `node migrations/app/20260707T1008_add_display_name/migration.ts`. If you run `npx prisma db migrate` before that, it fails because the `displayName` column is still missing, and it changes nothing. [Editing a migration](/orm/migrations/editing-a-migration) explains how to fill it in.

## Reviewing what you planned

Three offline commands let you check the migration before anything runs:

```npm
# One migration in detail: operations, metadata, DDL preview
npx prisma migration show 20260707T1006_add_user_phone
# The whole migration history, with your new migration in place
npx prisma migration graph
# Integrity check: hashes match, no files missing, every migration starts from empty or where another ends, refs point at known states
npx prisma migration check
```

In CI, run `npx prisma migration check` as a step and read its exit code. `0` means every check passed. `4` means it found an integrity failure, such as a missing file or an `ops.json` that someone edited by hand. `2` means it could not find a migration you named, as in `npx prisma migration check 20260707T1006_add_user_phone`.

:::note[What's early]

Planning covers tables, columns, indexes, constraints, and the backfill placeholder shown above. Column renames are not detected yet: renaming a field plans as **drop column + add column**, and `migration plan` prints a data-loss warning. `db migrate` runs destructive operations without asking, so read `npx prisma migration show <dir>` in review to catch one before it runs. For a true rename, edit `migration.ts`, replace the pair with a [`rawSql` operation](/orm/migrations/editing-a-migration#escape-hatch-raw-sql) that runs `ALTER TABLE ... RENAME COLUMN`, and recompile. There is also no interactive mode: the planner writes its best answer and leaves changes to you in `migration.ts`.

:::
