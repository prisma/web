This tutorial takes a change to your contract, the `contract.prisma` file that replaced `schema.prisma`, from your editor to a migration on disk that you review before it runs. To create a project first, follow the [quickstart](/prisma-orm/quickstart/postgresql).

After you edit the contract, run `npx prisma contract emit`. It does the job `prisma generate` used to do, and writes `contract.json` and `contract.d.ts` next to `contract.prisma`. Then `npx prisma migration plan` writes a new migration from `contract.json` without applying it. It never connects to a database, so you can plan in CI or in a sandbox with no credentials. By default it starts from the `db` [ref](/orm/migrations/the-migration-graph#terms-used-on-this-page), a file in `migrations/app/refs/` that names the version of your contract you last applied in development. Once your first migration exists, every later change follows the [five steps below](#the-db-ref-skipping---from).

## Your first migration

Say your contract has a single model:

```prisma title="contract.prisma"
model User {
  id    Int     @id
  email String
  name  String?

  @@map("user")
}
```

Run both commands. With `--name init`, the new directory is named `<timestamp>_init`:

```npm
npx prisma contract emit
npx prisma migration plan --name init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        init

✔ Planned 2 operation(s)
ℹ No db ref set — planning from an empty database. Run db init, db update, or db sign if a database already exists.

migrations/app/20260707T1005_init
├─ Create schema "public"
└─ Create table "user"

from:       (baseline)
to:         705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
app space:  migrations/app/20260707T1005_init

ℹ DDL preview

CREATE SCHEMA IF NOT EXISTS "public";
CREATE TABLE "public"."user" (
  "email" text NOT NULL,
  "id" int4 NOT NULL,
  "name" text,
  PRIMARY KEY ("id")
);
```

Four things to note:

- **`Planned 2 operation(s)`** counts the migration's steps, which are listed under its directory. The DDL preview is the SQL those steps will run.
- **`to:`** is your contract's hash. Each version of your contract is a contract state, named by its hash.
- **`from: (baseline)`** means the migration starts from an empty database. A baseline migration is a first migration from an empty database to a contract state. What Prisma ORM 7 called baselining, marking an existing database as already migrated, is `npx prisma db sign` in Prisma ORM 8.
- **`app space:`** is the new migration's directory. `migrations/app/` holds your app's migrations, and each [Prisma ORM extension package](/orm/extensions/using-extensions) that ships migrations has its own directory. `migrations/` sits in the directory you run commands from, normally the project root.

The `No db ref set` line means the project has no `db` ref yet, so `migration plan` started from an empty database. If you already have a database, what to run depends on what it holds:

- A database that Prisma ORM 7 migrated needs the steps in the [upgrade guide](/guides/upgrade-prisma-orm/postgresql#4-transfer-migration-ownership).
- An empty database needs nothing, because `npx prisma db migrate` creates the tables. It does not create the database itself.
- A database whose tables all match your contract needs [`npx prisma db sign`](/cli/db-sign), then the steps in [The automatic baseline](#the-automatic-baseline). `db sign` checks the tables against your contract, then saves a record in the database, called the [marker](/orm/migrations/the-migration-graph#terms-used-on-this-page), that says which contract state the database matches.
- A database that has only some of your tables needs [`npx prisma db init`](/cli/db-init). It only adds what is missing, and it stops if matching your contract would need a change that could lose data, such as dropping a column.
- A local development or preview database that should match your contract without migration files needs [`npx prisma db update`](/cli/db-update). Unlike `db init`, it also makes changes that could lose data, but it first asks you to type the database name.

Each migration directory holds three files and no SQL file: `migration.ts`, which you read and sometimes edit, and `ops.json` and `migration.json`, which `npx prisma db migrate` reads. Commit the migration directory and any new directories under `migrations/snapshots/`, which hold saved copies of your contract. Commit `contract.prisma`, `contract.json`, and `contract.d.ts` too. Open `migration.ts`, which lists the change as method calls:

```ts title="migrations/app/20260707T1005_init/migration.ts"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract';
import endContract from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract.json' with { type: 'json' };
import { Migration, MigrationCLI, col, primaryKey } from '@prisma/orm-postgres/migration';

export default class M extends Migration<never, End> {
  override readonly endContractJson = endContract;

  override get operations() {
    return [
      this.createSchema({ schema: 'public' }),
      this.createTable({
        schema: 'public',
        table: 'user',
        columns: [
          col('email', 'text', { notNull: true, codecRef: { codecId: 'pg/text@1' } }),
          col('id', 'int4', { notNull: true, codecRef: { codecId: 'pg/int4@1' } }),
          col('name', 'text', { codecRef: { codecId: 'pg/text@1' } }),
        ],
        constraints: [primaryKey(['id'])],
      }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The `operations` list is the change. For a change like this one you edit nothing, and you never edit `ops.json` by hand. To add a data backfill, change the order of operations, or run raw SQL, you edit `migration.ts` and recompile it, as [Editing a migration](/orm/migrations/editing-a-migration) shows.

## The second migration: planning a delta

Apply the first migration to your development database with `npx prisma db migrate --advance-ref db`. It connects to the database in [`db.connection`](/orm/contract-authoring/the-data-contract) in `prisma.config.ts`, or to a connection string you pass with the `--db` flag. `--advance-ref db` points the `db` ref at the contract state it applied, so the next `migration plan` starts from there.

Now add an optional `phone String?` field to `User`, and run both commands again to plan a migration with only that change:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_user_phone

✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

To start from a different contract state, pass `--from`, as in `npx prisma migration plan --name <name> --from 20260707T1005_init`, where a migration directory name means the state after that migration. The [`migration plan` reference](/cli/migration-plan#options) lists every form `--from` accepts.

### The db ref: skipping --from

When the `db` ref exists, `migration plan` starts from it, so you don't pass `--from`. For every change after your first migration, repeat these five steps. They replace Prisma ORM 7's `migrate dev` when you want migration files, as the [command table](/orm/coming-from-prisma-orm-7#commands) shows:

1. Edit your contract.
2. Run `npx prisma contract emit`. If you skip it, `migration plan` reads the old `contract.json`, so it prints `No changes detected` or plans without your latest edit.
3. Run `npx prisma migration plan --name <name>`.
4. Review the migration with `npx prisma migration show <dir>`, where `<dir>` is its directory name, such as `20260707T1006_add_user_phone`. If you edit `migration.ts`, [recompile it](/orm/migrations/editing-a-migration) by running `node migrations/app/<dir>/migration.ts` from your project root, which rewrites `ops.json` and `migration.json`.
5. Apply it. In development, run `npx prisma db migrate --advance-ref db`. In CI and production, run `npx prisma db migrate`.

If you plan again before you apply with `--advance-ref db`, the `db` ref still points at the older contract state. The new migration then repeats the changes of the migration you planned before it. To fix it, delete the repeated migration's directory. Then run [`npx prisma migration ref set db <dir>`](/cli/migration-ref) with the directory name of the migration it repeated, such as `20260707T1006_add_user_phone`, and plan again. To throw away any migration that has not run on a database, delete its directory. Its directory under `migrations/snapshots/` can stay.

`npx prisma db sign`, `db init`, and `db update` also move the `db` ref after they change the database in `prisma.config.ts`. `db sign` moves it with the `--db` flag too, so add `--no-advance-ref` when you sign another database. The [`migration ref`](/cli/migration-ref) page lists when each command moves it.

When you leave off `--from`, `migration plan` does one of four things:

| Migrations in `migrations/app/` | `db` ref | What `migration plan` does |
| --- | --- | --- |
| None | None | Plans from an empty database |
| None | Exists | Writes a baseline migration, then your change |
| Some | Exists | Plans from the state the `db` ref points at |
| Some | None | Stops with an error |

In the last case, the error prints three commands to choose from: one sets the `db` ref, one passes `--from`, and one passes `--from @empty`.

### The automatic baseline

The second row of the table is what you have after `npx prisma db sign` on a database that already has tables, or after `npx prisma db update`: `migrations/app/` is empty, and the `db` ref points at a contract state. Run `npx prisma migration plan` next, before `npx prisma db migrate`. It writes a baseline migration from an empty database to that state, and a second migration if `contract.json` has changed since. `db migrate` fails on that database until one migration's `to:` hash matches the database's marker, and it never runs the baseline there, because the marker is already at that state. The migration graph page has the full rule under [Baselines](/orm/migrations/the-migration-graph#baselines).

If a deployed database, such as production, is behind your development database, plan the baseline from the deployed version of your contract, because the automatic baseline would end at your development database's state:

1. Change your contract back to the version you last deployed, for example with `git show <commit>:<contract path> > <contract path>`.
2. Run `npx prisma contract emit`.
3. Run `npx prisma migration plan --name baseline --from @empty`.
4. Run `npx prisma db sign --db "$PRODUCTION_DATABASE_URL" --no-advance-ref` against the deployed database. It writes the marker there, and `--no-advance-ref` leaves your `db` ref alone.
5. Restore your current contract and run `npx prisma contract emit` again.
6. Plan the change with `npx prisma migration plan --name <name> --from <baseline dir>`, using the baseline's directory name.

None of these steps moves your `db` ref.

## When the planner needs your input

Add a **required** field with no default to an existing table, and `migration plan` can write the `ADD COLUMN` and the `SET NOT NULL`, but only you know what the existing rows should contain. It leaves that decision to you as a **placeholder**. To see one, apply `add_user_phone` with `npx prisma db migrate --advance-ref db`. Then add a required `displayName String` field to `User`, and run both commands again:

```npm
npx prisma contract emit
npx prisma migration plan --name add_display_name
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_display_name

⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

from:       925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
to:         e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
app space:  migrations/app/20260707T1008_add_display_name
```

The new `migration.ts` has a `dataTransform` step, which updates existing rows, between the `ADD COLUMN` and `SET NOT NULL` steps. Its two `placeholder(...)` calls mark where your queries go: one finds rows that still need a `displayName`, and one fills it in. You write both in TypeScript with the [SQL query builder](/orm/reference/sql-query-builder), as [Editing a migration](/orm/migrations/editing-a-migration) shows. Then recompile, the step the output calls self-emit. Run `node migrations/app/20260707T1008_add_display_name/migration.ts` from your project root. `migration plan` leaves `ops.json` empty when it writes placeholders, so until you recompile, `npx prisma db migrate` fails and changes nothing.

## Reviewing what you planned

Three commands check the migration before anything runs, and none of them connects to a database:

```npm
# One migration in detail: operations, metadata, DDL preview
npx prisma migration show 20260707T1006_add_user_phone
# The whole migration history, with your new migration in place
npx prisma migration graph
# Integrity check: hashes match, no files missing, every migration starts from empty or where another ends, refs point at known states
npx prisma migration check
```

In CI, run `npx prisma migration check` and read its exit code. `0` means every check passed. `4` means it found an integrity failure, such as a missing file or an `ops.json` that someone edited by hand. `2` means it could not find a migration you named. It never reads `migration.ts`, so it cannot tell whether you recompiled after your last edit. To confirm that, stage the migration with `git add`, then run `node migrations/app/<dir>/migration.ts` again from your project root. If `git status` shows no unstaged change to `ops.json` or `migration.json`, they were already up to date. That does not work for a backfill on a model with an [`updatedAt` column](/orm/migrations/editing-a-migration#worked-example-making-a-column-required).

:::note[What's early]

Planning covers tables, columns, indexes, constraints, and the backfill placeholder shown above. Column renames are not detected yet: renaming an optional field plans as **drop column + add column**, and `migration plan` prints a data-loss warning. `db migrate` runs destructive operations without asking, so read `npx prisma migration show <dir>` before you apply. To rename a column and keep its data, edit `migration.ts`, replace the pair with a [`rawSql` operation](/orm/migrations/editing-a-migration#escape-hatch-raw-sql) that runs `ALTER TABLE ... RENAME COLUMN`, and recompile. Unlike Prisma ORM 7's `migrate dev`, `migration plan` never asks you questions.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. The skills are instruction files your agent reads, so you can ask it to:

- "Add a required `displayName` field to User, emit the contract, and plan the migration."
- "Plan a migration named `add-orders-table` and show me its DDL preview before I commit it."
- "Run `migration check` and explain any integrity failures."
