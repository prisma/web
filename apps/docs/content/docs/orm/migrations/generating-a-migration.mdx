This tutorial takes a change to your contract, the `contract.prisma` file that replaced `schema.prisma`, from your editor to a migration on disk that you review before it runs. After every change to the contract, you run `npx prisma contract emit`. It writes `contract.json`, with `contract.d.ts` beside it, to the contract output path from `prisma.config.ts`, which is `src/prisma/contract.json` in this tutorial. `migration plan` reads that `contract.json` and your existing migrations. It never connects to a database, so you can plan on a plane, in CI, or in a sandbox with no credentials. Start from an existing project, or create one with `npm create prisma@latest -- my-app`.

## Your first migration

Say your contract has a single model:

```prisma title="contract.prisma"
model User {
  id    Int     @id
  email String
  name  String?

  @@map("user")
}
```

Emit the contract, then plan. With `--name init`, the new directory is named `<timestamp>_init`, and without `--name` its name ends in `_migration`:

```npm
npx prisma contract emit
npx prisma migration plan --name init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        init

✔ Planned 2 operation(s)
ℹ No db ref set — planning from an empty database. Run db init, db update, or db sign if a database already exists.

migrations/app/20260707T1005_init
├─ Create schema "public"
└─ Create table "user"

from:       (baseline)
to:         705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
app space:  migrations/app/20260707T1005_init

ℹ DDL preview

CREATE SCHEMA IF NOT EXISTS "public";
CREATE TABLE "public"."user" (
  "email" text NOT NULL,
  "id" int4 NOT NULL,
  "name" text,
  PRIMARY KEY ("id")
);
```

Four things to note:

- **The DDL preview** is the SQL the migration will run. Nothing has run against a database yet.
- **`from: (baseline)`** means the migration starts from an empty database, so it is the first migration in your [migration history](/orm/migrations/the-migration-graph). It is not the same as baselining an existing database, which is covered in [The automatic baseline](#the-automatic-baseline).
- **`to:` is your contract's hash**, a 64-character identifier computed from the contract. Each version of your contract, called a contract state, has its own hash. The migration builds a database that matches exactly the contract you emitted.
- **`app space:`** is the new migration's directory. Your app's migrations go in `migrations/app/`. A Prisma ORM extension package that ships its own migrations gets its own directory next to it, as described in [Extension spaces](/orm/migrations/applying-a-migration#extension-spaces).

The `No db ref set` line appears because the project has no `db` ref yet, which [The db ref](#the-db-ref-skipping---from) explains. If you already have a database, run one of these commands first. Each of them writes the marker, the record in the database of which contract state it currently matches.

- [`npx prisma db init`](/cli/db-init) adds what your contract declares and the database does not have yet. It leaves compatible tables alone and stops if a change would be destructive.
- [`npx prisma db update`](/cli/db-update) makes a development database match your contract, without writing any migration files.
- [`npx prisma db sign`](/cli/db-sign) is for a database that already matches your contract. It checks that the database matches, then writes the marker without changing any table.

Each migration directory holds `migration.ts`, the operations in `ops.json`, and the metadata in `migration.json`. There is no SQL file, because `db migrate` runs the operations in `ops.json`. `migration.ts` imports a copy of the contract from `migrations/snapshots/<contract hash>/`, and there is one `snapshots/` directory for the whole `migrations/` directory.

Open `migration.ts`. It is a description of the change, so it reads like one:

```ts title="migrations/app/20260707T1005_init/migration.ts"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract';
import endContract from '../../snapshots/705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5/contract.json' with { type: 'json' };
import { Migration, MigrationCLI, col, primaryKey } from '@prisma/orm-postgres/migration';

export default class M extends Migration<never, End> {
  override readonly endContractJson = endContract;

  override get operations() {
    return [
      this.createSchema({ schema: 'public' }),
      this.createTable({
        schema: 'public',
        table: 'user',
        columns: [
          col('email', 'text', { notNull: true, codecRef: { codecId: 'pg/text@1' } }),
          col('id', 'int4', { notNull: true, codecRef: { codecId: 'pg/int4@1' } }),
          col('name', 'text', { codecRef: { codecId: 'pg/text@1' } }),
        ],
        constraints: [primaryKey(['id'])],
      }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The `col(...)` calls mirror your contract fields, and you can ignore `codecRef`. For a simple change you don't need to touch this file. When you need a data backfill, a different operation order, or raw SQL, see [Editing a migration](/orm/migrations/editing-a-migration).

## The second migration: planning a delta

Apply the first migration with `npx prisma db migrate`. It connects with `--db` if you pass it, and otherwise with the connection in `prisma.config.ts`. [Applying a migration](/orm/migrations/applying-a-migration) covers this step in detail. Then add an optional `phone String?` field to `User`, emit, and plan again. This time `migration plan` needs a starting point. Planning is offline, so it does not know what your database holds, and it does not start from the newest migration on disk either. It starts from the contract state you pass with `--from`, or from the `db` ref described below. Plain `db migrate` does not set the `db` ref, so pass the first migration's directory name:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone --from 20260707T1005_init
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  from:        20260707T1005_init
│  name:        add_user_phone

✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

`--from` takes a contract state in any of the forms below. A [ref](/orm/migrations/the-migration-graph#name-important-states-with-refs) is a name for a contract state, stored as a file in `migrations/app/refs/`.

- A migration directory name, as here, means the state after that migration.
- `<dir>^` means the state before that migration.
- A contract hash can be given in full, or as its first 6 or more characters when they match only one hash.
- A ref name, such as `db`, means the state that ref points at.
- `@empty` means an empty database.

### The db ref: skipping --from

You don't have to pass `--from` every time. If a ref named **`db`** exists, `migration plan` starts from the contract state it points at. In development you keep the `db` ref at the state of your database, so your everyday loop is:

1. Edit your contract.
2. Run `npx prisma contract emit`, which writes `contract.json` and `contract.d.ts`.
3. Run `npx prisma migration plan --name <name>`, with no `--from`.
4. Review the migration. If you edit `migration.ts`, recompile it from your project's root directory with `node migrations/app/<dir>/migration.ts`.
5. Apply it. In development, run `npx prisma db migrate --advance-ref db`, which moves the `db` ref to the state it applied. In CI and production, run `npx prisma db migrate`.

If you leave off `--advance-ref db` in development, the `db` ref stays at the older contract state, and the next `migration plan` starts from there.

These commands move the `db` ref:

- `npx prisma db init` and `npx prisma db update` move it after a successful run. With `--dry-run`, they leave it alone.
- Both also leave it alone when you pass `--db`. To move it anyway, add `--advance-ref db`.
- `npx prisma db sign` moves it after it signs the database, with or without `--db`. To leave it alone, add `--no-advance-ref`.
- `npx prisma db migrate` moves it only when you pass `--advance-ref db`, after the migrations are applied.
- `npx prisma migration ref set db <contract>` sets it by hand, where `<contract>` is a hash, a ref name, a migration directory name, or `<dir>^`, as in the `--from` list.

Signing checks that a database already matches your contract, then writes the marker. So when you start using migrations with a database that already has tables, sign it first, and your first `migration plan` starts from that database's contract state instead of from empty.

When you leave off `--from`, `migration plan` does one of four things:

| Migrations in `migrations/app/` | `db` ref | What `migration plan` does |
| --- | --- | --- |
| None | None | Plans from an empty database |
| None | Exists | Writes a baseline migration, then your change |
| Some | Exists | Plans from the state the `db` ref points at |
| Some | None | Stops with an error |

In the last case, planning from an empty database would write a migration that recreates everything your existing migrations already create. The error prints three commands you can run instead: one sets the `db` ref, one passes `--from`, and one passes `--from @empty` to plan from an empty database on purpose.

### The automatic baseline

The second row of the table is the usual state after a few `db update` runs: `migrations/app/` is empty, and the `db` ref points at a contract state whose snapshot is stored under `migrations/snapshots/`. One `migration plan` run then writes a baseline migration from an empty database to the ref's state. When your emitted contract differs from that state, it also writes a second migration with the change. Expect one or two new directories in `git status`.

`db migrate` starts from a database's marker and applies only the migrations after it, so the baseline never runs against a database that has a marker. On a database with no marker, it starts from an empty database, so the baseline would run there. The migration graph page covers this under [Baselines](/orm/migrations/the-migration-graph#baselines).

To create a baseline by hand, for example for a deployed database that you cannot let `db migrate` run `CREATE TABLE` against:

1. Change your contract back to the deployed state. With Git, that could be `git show <commit>:<contract path> > <contract path>`.
2. Run `npx prisma contract emit`.
3. Run `npx prisma migration plan --name baseline --from @empty`.
4. Run `npx prisma db sign --db "$DATABASE_URL" --no-advance-ref` against the deployed database. It writes the marker, so `db migrate` never runs the baseline there, and `--no-advance-ref` leaves your `db` ref alone.
5. Restore your current contract and run `npx prisma contract emit` again.
6. Plan the change with `npx prisma migration plan --name <name> --from <baseline dir>`, using the baseline's directory name.

## When the planner needs your input

Some changes can't be planned from the contract change alone. Add a **required** field with no default to an existing table, and the planner can write the `ADD COLUMN` and the `SET NOT NULL`, but only you know what the existing rows should contain. Rather than guessing, it leaves that decision as a **placeholder**. To see one, follow the everyday loop. Apply `add_user_phone` with `npx prisma db migrate --advance-ref db`, so the `db` ref moves to its state. Then add a required `displayName String` field to `User`, and emit and plan with no `--from`:

```npm
npx prisma contract emit
npx prisma migration plan --name add_display_name
```

```text
│  contract:    src/prisma/contract.json
│  migrations:  migrations/app
│  name:        add_display_name

⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

from:       925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
to:         e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
app space:  migrations/app/20260707T1008_add_display_name
```

The generated migration puts a `dataTransform` step between the `ADD COLUMN` and `SET NOT NULL` steps, with `placeholder(...)` where your backfill query goes. "Self-emit" in the output means that running `migration.ts` writes `ops.json` and records a new `migrationHash` in `migration.json`. After you fill in the placeholder, run it from your project's root directory with `node migrations/app/20260707T1008_add_display_name/migration.ts`. [Editing a migration](/orm/migrations/editing-a-migration) explains how to fill it in.

## Reviewing what you planned

Three offline commands let you check the migration before anything runs:

```npm
# One migration in detail: operations, metadata, DDL preview
npx prisma migration show 20260707T1006_add_user_phone
# The whole migration history, with your new migration in place
npx prisma migration graph
# Integrity check: hashes match, no files missing, migrations connect, refs point at known states
npx prisma migration check
```

In CI, read the exit code of `migration check`. `0` means every check passed. `2` means it could not find the migration you named, or the directory under `migrations/` that you named with `--space`, such as `app`. `4` means it found an integrity failure, for example a hand-edit to `ops.json` without recompiling `migration.ts`.

:::note[What's early]

Planning covers tables, columns, indexes, constraints, and the backfill placeholder shown above. Column renames are not detected yet: renaming a field plans as **drop column + add column**, flagged destructive with a data-loss warning. For a true rename, edit `migration.ts`, replace the pair with a [`rawSql` operation](/orm/migrations/editing-a-migration#escape-hatch-raw-sql) that runs `ALTER TABLE ... RENAME COLUMN`, and recompile. There is also no interactive mode: the planner writes its best answer and leaves changes to you in `migration.ts`.

:::

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:
