A migration is how Prisma ORM changes your database when your contract changes. Your contract is the `contract.prisma` file that replaced `schema.prisma`, and `prisma contract emit` compiles it into `contract.json`. A migration changes the database itself: its tables, columns, and indexes. For example, if you add a field to a model, something has to run `ALTER TABLE` against every database that serves your app: your laptop, staging, production. Migrations are that something, recorded as files in your repo so any change is reviewable, repeatable, and versioned with your code.

The workflow is a loop that you run many times a day during development:

<ConceptAnimation name="migration-loop" />

1. **Change your contract**: edit `contract.prisma`, then run `prisma contract emit`, which writes `contract.json`. The other commands read that file.
2. **Plan a migration**: `migration plan` compares the new contract with the previous contract state and writes a migration directory under `migrations/app/`.
3. **Review it**: read the generated TypeScript and the DDL preview. Edit the migration if the change needs a data step, then run the file again to recompile it.
4. **Apply it**: `db migrate` runs the pending migrations against your database.

In a project with a database connection configured (the [quickstart](/prisma-orm/quickstart/postgresql) sets one up), the whole loop is three commands. Add an optional `phone String?` field to a model in `contract.prisma`, then:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone
npx prisma db migrate --advance-ref db
```

In development, add `--advance-ref db` so the next `migration plan` starts from what you just applied, as [The db ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) explains.

`migration plan` prepares the SQL for the migration, but doesn't run it:

```text
✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

and `db migrate` applies the migration to your database and confirms what it applied:

```text
✔ Applied 1 migration(s) (1 operation(s)) across 1 contract space(s)
```

A contract space is a separate migration history: one for your app, and one for each database extension that ships its own migrations. If you see the `✔ Applied` line, you've run the entire workflow.

## What a migration contains

A migration is a directory under `migrations/app/`, named with a timestamp and a slug:

```text
migrations/
├── app/
│   └── 20260707T1006_add_user_phone/
│       ├── migration.ts     # the file you edit
│       ├── ops.json         # the file Prisma runs
│       └── migration.json   # where this migration fits in history
└── snapshots/
    └── <contract hash>/
        ├── contract.json    # snapshot of one contract state
        └── contract.d.ts    # types for that snapshot; they type-check migration.ts
```

Contract snapshots are kept in `migrations/snapshots/`, one directory per contract hash. A migration imports the contract states it moves between from there, so a contract state shared by several migrations is stored once. A baseline migration starts from nothing, so it imports only its end contract.

Three files matter day to day, and each has one job:

| File | Purpose |
| --- | --- |
| `migration.ts` | The file you edit. It describes the changes to tables, columns, and data as TypeScript calls. |
| `ops.json` | The file Prisma runs. It contains the compiled migration operations as JSON. |
| `migration.json` | The file Prisma uses to track where this migration fits in history. |

### migration.ts: the file you edit

`migration.ts` is the authoring file and contains the migration steps as ordinary TypeScript:

```ts
this.addColumn(...)
this.createTable(...)
this.dataTransform(...)
```

Because it is TypeScript that imports its contract snapshots from `migrations/snapshots/`, your editor catches type mistakes before the migration touches a database.

When you want to review or change what the migration does, use this file. For more information, see [Editing a migration](/orm/migrations/editing-a-migration).

### ops.json: the file Prisma runs

`ops.json` is the compiled form of the migration. `migration plan` writes it for you, and after you edit `migration.ts` you run `node migration.ts` to write it again, as [Editing a migration](/orm/migrations/editing-a-migration) explains. The migration runner runs only this file.

That means production never executes `migration.ts`: it reads the compiled operations, so no migration TypeScript runs with production credentials.

```text
migration.ts  ->  ops.json
you edit          Prisma runs
```

The two files are committed side by side and work like `package.json` and `package-lock.json`:

```text
package.json  ->  package-lock.json
what you ask for  exact resolved result

migration.ts  ->  ops.json
what you author   exact operations to run
```

### migration.json: its place in history [#migrationjson-the-history-marker]

`migration.json` records where this migration fits in your migration history. Each contract state is named by its hash, a short identifier computed from the contract. The same contract always produces the same hash. A migration records:

- the contract hash it starts `from`
- the contract hash it moves `to`
- when it was created
- its own hash, so a hand-edit to `migration.json` or `ops.json` is detected

```json title="migrations/app/20260707T1006_add_user_phone/migration.json"
{
  "from": "705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5",
  "to": "925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72",
  "providedInvariants": [],
  "createdAt": "2026-07-07T10:06:55.937Z",
  "migrationHash": "4b57fa2141c8ad94476d5de66c451468fd6c864210481ad00ac89b259491fbcf"
}
```

Read `from` and `to` like a Git commit range: the contract state before, and the contract state after. These hashes link migrations into a [migration history](/orm/migrations/the-migration-graph) that can branch, instead of a numbered list. If your migrations form a straight line, you can ignore the branching entirely. `providedInvariants` lists the `invariantId` values that the migration's operations declare, such as a data transform's, and is empty for most app migrations.

Together, the three files make a migration both editable and safe to run:

```text
migration.ts     you author the change
ops.json         Prisma runs the compiled operations
migration.json   Prisma tracks the migration in history
```

## Every operation checks itself

Inside `ops.json`, each operation runs in three parts, in order:

1. **Precheck**: confirms the database is in the expected state before the change runs.
2. **Execute**: the statements that make the change.
3. **Postcheck**: confirms the change worked after it runs.

Each operation also has a class, which drives the data-loss warnings you see in CLI output:

- **Additive**: safe to apply, like adding a column.
- **Widening**: relaxes a constraint or widens a type.
- **Destructive**: can lose data, like dropping a column.
- **Data**: changes rows, not structure.

```json title="One operation from ops.json"
{
  "id": "column.public.user.phone",
  "label": "Add column \"phone\" to \"user\"",
  "operationClass": "additive",
  "target": { "id": "postgres", "details": { "schema": "public", "objectType": "column", "name": "phone", "table": "user" } },
  "precheck": [
    {
      "description": "ensure column \"phone\" is missing",
      "sql": "SELECT NOT EXISTS (SELECT 1 AS \"one\" FROM \"information_schema\".\"columns\" WHERE (\"table_schema\" = $1 AND \"table_name\" = $2 AND \"column_name\" = $3)) AS \"result\"",
      "params": ["public", "user", "phone"]
    }
  ],
  "execute": [
    {
      "description": "add column \"phone\"",
      "sql": "ALTER TABLE \"public\".\"user\" ADD COLUMN \"phone\" text"
    }
  ],
  "postcheck": [
    {
      "description": "verify column \"phone\" exists",
      "sql": "SELECT EXISTS (SELECT 1 AS \"one\" FROM \"information_schema\".\"columns\" WHERE (\"table_schema\" = $1 AND \"table_name\" = $2 AND \"column_name\" = $3)) AS \"result\"",
      "params": ["public", "user", "phone"]
    }
  ]
}
```

This structure is what makes Prisma ORM migrations safe in the situations where classic SQL migrations hurt:

- **A migration fails.** On PostgreSQL the whole run rolls back, and re-running skips any operation whose postcheck already holds, as [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) explains.
- **The database isn't in the state you assumed.** The precheck catches it before the change runs, and the error names the exact operation and the exact check that failed, not a generic SQL error halfway through.
- **Someone (or an agent) wrote the migration for you.** The intent (`migration.ts`), the exact SQL (`ops.json`), and the verification for every step are all in the diff, so review is straightforward.

## The commands

These commands are part of the [Prisma ORM CLI](/cli), and you run them with `npx prisma <command>`. The planning and inspection commands work offline, because they read files, not your database:

| Command                   | What it does                                                            |
| ------------------------- | ----------------------------------------------------------------------- |
| `migration plan`          | [Generate a migration](/orm/migrations/generating-a-migration) from your contract changes |
| `migration new`           | Scaffold an empty migration for [manual authoring](/orm/migrations/editing-a-migration#starting-from-a-blank-migration) |
| `migration show <target>` | Print one migration's operations, DDL preview, and metadata            |
| `migration list`          | List every on-disk migration                                            |
| `migration graph`         | Draw the [migration graph](/orm/migrations/the-migration-graph)   |
| `migration check`         | Verify migration files and graph integrity (useful in CI)               |

Three commands talk to a database:

| Command            | What it does                                                                 |
| ------------------ | ---------------------------------------------------------------------------- |
| `db migrate`          | [Apply pending migrations](/orm/migrations/applying-a-migration)        |
| `migration status` | Show where the database is in the graph and which migrations are pending     |
| `migration log`    | Show the history of migrations the database has actually applied             |

Note that applying is `db migrate`, not `migration apply`: `migration ...` commands manage the on-disk migration directories, while `db migrate` moves a database.

## The same model for SQL and MongoDB

Everything above applies to both PostgreSQL and MongoDB. On PostgreSQL, operations compile to SQL DDL, and the applied state is tracked in a **marker**, the record in the database of which contract state it currently matches. On MongoDB, operations create collections, indexes, and JSON Schema validators, and the marker is kept in a `_prisma_migrations` collection. The commands, the file layout, the migration history, and the precheck/execute/postcheck structure are the same.

:::note[Migrations are early]

Migrations are one of the newest parts of Prisma ORM. The core loop (plan, edit, apply, roll back) works today and is exercised in the Prisma ORM test suite. Some things classic migration tools grew over years are not built yet: there is no squash command and no shadow-database dry run. Baselines do exist, both the automatic one and the explicit `--from @empty` retrofit. See [the migration graph](/orm/migrations/the-migration-graph#baselines).

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Add a `phone` field to the User model and plan a migration for it."
- "Show me the pending migrations and what SQL they will run."
- "Explain what the ops.json in the latest migration does."
