A migration is how Prisma ORM changes your database when your contract changes. Your contract is the `contract.prisma` file that replaced `schema.prisma`, and `npx prisma orm init` puts it in `src/prisma/`. After you edit it, run `npx prisma contract emit`, which replaces `prisma generate`. It writes two files next to `contract.prisma`: `contract.json`, which the migration commands read, and `contract.d.ts`, which your client's types come from.

Prisma ORM 8 supports PostgreSQL and MongoDB, and SQLite is experimental. It does not support MySQL, as [Supported databases](/orm/supported-databases) lists.

You run this loop many times a day during development:

<ConceptAnimation name="migration-loop" />

1. **Change your contract**: edit `contract.prisma`, then run `npx prisma contract emit`.
2. **Plan a migration**: `migration plan` compares your new contract with an earlier contract state and writes a migration directory under `migrations/app/`. A contract state is one version of your contract, named by its hash, an identifier computed from the contract. By default, the earlier state is the one named by the `db` ref, a file in `migrations/app/refs/` that names the contract state you last applied in development.
3. **Review it**: run `npx prisma migration show <dir>`, where `<dir>` is the migration's directory name, to see the operations and SQL that `db migrate` will run. If you also need to change rows, such as filling a new column, edit `migration.ts` as [Editing a migration](/orm/migrations/editing-a-migration) shows. Then recompile it: run `node migrations/app/<dir>/migration.ts` from your project root, which rewrites `ops.json` and `migration.json` without connecting to a database. The Prisma ORM CLI needs Node.js 22.18 or later, and those versions run `migration.ts` directly.
4. **Apply it**: `db migrate` reads the database's marker, the record in the database of which contract state it currently matches. Then it runs the migrations that lead from that state to your current contract. In development, add `--advance-ref db`, which points the `db` ref at the state you just applied, so the next `migration plan` starts from there.

In a project with a database connection, which the [quickstart](/prisma-orm/quickstart/postgresql) sets up, add an optional `phone String?` field to the `User` model in `contract.prisma`, then run:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone
npx prisma migration show 20260707T1006_add_user_phone
npx prisma db migrate --advance-ref db
```

`migration plan` prepares the SQL for the migration, but doesn't run it:

```text
✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

The `User` model's table is `"user"`, and a `UserProfile` model's table is `"userProfile"`, because the table name is the model name with a lowercase first letter unless the model sets `@@map`. A database that Prisma ORM 7 created has a `"User"` table instead. Before you plan a migration for such a database, follow [the upgrade guide](/guides/upgrade-prisma-orm/postgresql#24-edit-the-inferred-contract), which maps those names with `@@map`.

The `app space:` line shows where the migration was written. A contract space is a separate migration history. Your app's is `migrations/app/`, and each [Prisma ORM extension package](/orm/migrations/applying-a-migration#extension-spaces) that ships migrations, such as pgvector support, gets its own directory under `migrations/`.

`db migrate` applies the migration to your database and confirms what it applied:

```text
✔ Applied 1 migration(s) (1 operation(s)) across 1 contract space(s)
```

`migration plan` reads only files, never your database. It starts from the contract state that the `db` ref names, and that ref is the file `migrations/app/refs/db.json`. With no migrations and no `db` ref yet, the first `migration plan` starts as if the database were empty. To start somewhere else, pass `--from`, such as `--from 20260707T1006_add_user_phone` for the state after that migration. The [`migration plan` reference](/cli/migration-plan#options) lists the other forms.

If you apply without `--advance-ref db`, or plan twice before you apply, the next `migration plan` starts from the older state again. The migration it writes then repeats the changes of the one you already planned, and [The db ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) shows how to remove it.

`db migrate` connects with `db.connection` in [`prisma.config.ts`](/orm/contract-authoring/the-data-contract), such as `db: { connection: process.env["DATABASE_URL"]! }`, unless you pass a URL with the `--db` flag. In CI and production, run plain `npx prisma db migrate`.

## What a migration contains

A migration is a directory under `migrations/app/`, named with a timestamp and the `--name` you passed. `migrations/` is in the directory you run commands from, normally your project root:

```text
migrations/
├── app/
│   └── 20260707T1006_add_user_phone/
│       ├── migration.ts     # the change, as TypeScript
│       ├── ops.json         # the operations, as JSON
│       └── migration.json   # where this migration fits in history
└── snapshots/
    └── <contract hash>/
        ├── contract.json    # snapshot of one contract state
        └── contract.d.ts    # types for that snapshot; they type-check migration.ts
```

Each directory under `migrations/snapshots/` holds the `contract.json` and `contract.d.ts` of one contract state, and its name is that state's hash.

After `migration plan`, commit the new migration directory and any new directories it added under `migrations/snapshots/`. Also commit `contract.prisma`, `contract.json`, and `contract.d.ts`.

### migration.ts: the file you edit

`migration plan` writes `migration.ts` as a TypeScript class with one call per step, such as `this.addColumn(...)` for a new column. To change what the migration does, edit this file, as [Editing a migration](/orm/migrations/editing-a-migration) explains.

### ops.json: the file Prisma runs

`migration plan` writes `ops.json`, which holds the migration's operations as JSON. `db migrate` runs `ops.json` and never runs `migration.ts`. If you edit `migration.ts` and don't recompile it, `db migrate` runs the old `ops.json`, and neither `db migrate` nor `migration check` warns you, as [Editing a migration](/orm/migrations/editing-a-migration) explains.

### migration.json: its place in history [#migrationjson-the-history-marker]

`migration.json` records where this migration fits in your migration history:

- the contract hash it starts `from`
- the contract hash it ends at, `to`
- when it was created
- its own hash, `migrationHash`, which lets `npx prisma migration check` catch a hand edit to `ops.json` or `migration.json`

Do not edit `migration.json` or `ops.json` by hand. Edit `migration.ts` and recompile it instead, which rewrites both files.

Read `from` and `to` like a Git commit range: the contract state before, and the contract state after. Your [migration history](/orm/migrations/the-migration-graph) branches when two people plan migrations from the same contract state on separate Git branches. [A worked example](/orm/migrations/the-migration-graph#a-worked-example) shows the two migrations to plan after the Git merge, one for the databases on each branch.

## Every operation checks itself

Inside `ops.json`, each operation has three parts, shown here for the `phone` column:

- **Precheck**: confirms the database is in the state the change expects, here that `"user"` has no `phone` column.
- **Execute**: the statements that make the change, here `ALTER TABLE "public"."user" ADD COLUMN "phone" text`.
- **Postcheck**: confirms the change is in the database, here that the `phone` column exists. Not every operation has one, and an operation without one is never skipped.

`db migrate` runs the postcheck before the change as well as after it. If the postcheck already passes before the change, the change is already in the database, so the operation is skipped. Otherwise `db migrate` runs the precheck, the statements, and the postcheck, in that order, and stops the run if either check fails. After the operations, `db migrate` checks the database against the contract before it moves the marker. So if `"user"` already had a `phone` column of another type, the postcheck skips the operation, but this last check fails the run.

Each operation also has a class, which you choose yourself when you write a raw SQL operation:

- **Additive**: adds something new, like a column.
- **Widening**: loosens a constraint or lets a type accept more values, like dropping `NOT NULL` from a column.
- **Destructive**: removes or changes something that exists, like dropping a column, and can lose data.
- **Data**: changes rows, not structure.

Only destructive operations get a warning, `This migration contains destructive operations that may cause data loss.` `migration plan` prints it when it writes the migration. `npx prisma migration show <dir>` prints it for any migration on disk. `db migrate` runs destructive operations without asking and prints the warning again after applying them.

The checks help in two situations:

- **A migration fails.** On PostgreSQL, one `db migrate` run is one transaction, so a failure leaves the database as it was before the run. On MongoDB, a `db migrate` run is not wrapped in a transaction, so operations that finished before a failure stay in the database. [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) covers recovery.
- **The database isn't in the state you assumed.** The precheck stops the run before the change runs. For example, a precheck stops a migration that sets `NOT NULL` on a column that still holds `NULL` values. The error names the operation and the check that failed. To fix it, edit `migration.ts` to fill those rows first, recompile it, and run `npx prisma db migrate` again, as [Recovery](/orm/migrations/rollbacks-and-recovery#recovery-when-a-migration-fails-partway) shows.

## The commands

The migration commands are part of the [Prisma ORM CLI](/cli), and you run them with `npx prisma <command>`. The commands in this table read only files in your project, so they work without a database connection:

| Command                   | What it does                                                            |
| ------------------------- | ----------------------------------------------------------------------- |
| [`migration plan`](/cli/migration-plan) | [Generate a migration](/orm/migrations/generating-a-migration) from your contract changes |
| [`migration new`](/cli/migration-new) | Write an empty migration for a [data-only or hand-written change](/orm/migrations/editing-a-migration#starting-from-a-blank-migration) |
| [`migration show <target>`](/cli/migration-show) | Print one migration's operations, DDL preview, and metadata            |
| `migration list`          | List every on-disk migration                                            |
| `migration graph`         | Draw your [migration history](/orm/migrations/the-migration-graph) as a graph |
| `migration check`         | Check that each migration's `migrationHash` still matches its files and no files are missing, for example in CI |

For `migration show`, `<target>` is a migration's directory name, its path under `migrations/app/`, or the first 6 or more characters of its `migrationHash`.

The commands in this table connect to a database:

| Command            | What it does                                                                 |
| ------------------ | ---------------------------------------------------------------------------- |
| [`db migrate`](/cli/db-migrate) | [Apply pending migrations](/orm/migrations/applying-a-migration)        |
| [`migration status`](/cli/migration-status) | Show where the database is in your migration history and which migrations are pending |
| `migration log`    | Show the history of migrations the database has actually applied             |

If you used Prisma ORM 7, these commands replace its migrate commands:

- `migrate dev` becomes `migration plan`, then `db migrate --advance-ref db`, when you want migration files. When you only want a development database to match the contract, it becomes `db update`, which changes the database directly, writes no migration files, and can move the `db` ref, as [The db ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) lists.
- `migrate deploy` becomes `db migrate`.
- `migrate reset` has no equivalent. Drop and recreate the database with your database tools. Then run `npx prisma db migrate --advance-ref db` to run your migrations again, or `npx prisma db init` to create what your contract declares without running them.
- `migrate diff` becomes `migration show <dir>`, which prints one migration, or `db update --dry-run`, which shows the operations that would make a database match the contract.
- What Prisma ORM 7 called baselining, marking an existing database as already migrated, is [`npx prisma db sign`](/cli/db-sign), which checks that the tables match your contract before it writes the marker. For a database that Prisma ORM 7 migrated, follow [Prisma ORM 7 to 8 (PostgreSQL)](/guides/upgrade-prisma-orm/postgresql#4-transfer-migration-ownership).

[Coming from Prisma ORM 7](/orm/coming-from-prisma-orm-7#commands) has the full table, including `migrate resolve`.

## The same model for SQL and MongoDB

The commands, the file layout, the migration history, and each operation's precheck and postcheck work the same way on PostgreSQL and MongoDB. On PostgreSQL, operations run SQL statements such as `ALTER TABLE`. On MongoDB, operations create collections, indexes, and JSON Schema validators.

Each database keeps a [marker and a ledger](/orm/migrations/the-migration-graph#terms-used-on-this-page). The marker records the one contract state the database matches now, and `db migrate` updates it after applying migrations. The ledger is the database's own list of every migration applied to it, and `migration log` reads that list.

:::note[Migrations are early]

Migrations are one of the newest parts of Prisma ORM. Planning, editing, applying, and [rolling back](/orm/migrations/rollbacks-and-recovery) work today. There is no squash command and no shadow-database dry run yet.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8), instruction files for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Add a `phone` field to the User model and plan a migration for it."
- "Show me the pending migrations and what SQL they will run."
- "Explain what the ops.json in the latest migration does."
