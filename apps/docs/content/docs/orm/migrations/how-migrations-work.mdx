A migration is how Prisma ORM changes your database when your contract changes. Your contract is the `contract.prisma` file that replaced `schema.prisma`. After you edit it, run `npx prisma contract emit`, which replaces `prisma generate`. It writes `contract.json`, which the migration commands read, and `contract.d.ts`, which your client's types come from.

A migration changes the database itself: its tables, columns, and indexes. For example, if you add a field to a model, something has to run `ALTER TABLE` against every database that serves your app: your laptop, staging, production. Migrations are that something, recorded as files in your repo so any change is reviewable, repeatable, and versioned with your code. Prisma ORM 8 supports PostgreSQL and MongoDB, and SQLite is experimental, as [Supported databases](/orm/supported-databases) lists.

The workflow is a loop that you run many times a day during development:

<ConceptAnimation name="migration-loop" />

1. **Change your contract**: edit `contract.prisma`, then run `npx prisma contract emit`.
2. **Plan a migration**: `migration plan` compares your new contract with an earlier contract state and writes a migration directory under `migrations/app/`. A contract state is one version of your contract, named by its hash.
3. **Review it**: read the generated `migration.ts`, and read the DDL preview in the `migration plan` output, which shows the SQL the migration will run. If the change needs a data step, such as filling a new column, edit `migration.ts`. Then recompile it: run `node migrations/app/<dir>/migration.ts` from your project root, which rewrites `ops.json`.
4. **Apply it**: `db migrate` runs the pending migrations against your database.

In a project with a database connection, which the [quickstart](/prisma-orm/quickstart/postgresql) sets up, the whole loop is three commands. Add an optional `phone String?` field to the `User` model in `contract.prisma`, then run:

```npm
npx prisma contract emit
npx prisma migration plan --name add_user_phone
npx prisma db migrate --advance-ref db
```

`migration plan` does not read your database, so by default it starts from the contract state that the `db` ref names. A ref is a name for a contract state, and the `db` ref is stored in the file `migrations/app/refs/db.json`. To start somewhere else, pass `--from` with a hash, a ref name, a migration directory name, `<dir>^` for the state before that migration, or `@empty` for an empty database, as [The db ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) explains.

In development, add `--advance-ref db` to `db migrate`, which moves the `db` ref to the contract state you just applied. If you leave the flag off, the next `migration plan` starts from the older state again, and the migration it writes repeats the changes of the migration you already planned. In CI and production, run plain `npx prisma db migrate`. It connects with `db.connection` in `prisma.config.ts`, or with a connection URL that you pass as `--db <url>`.

`migration plan` prepares the SQL for the migration, but doesn't run it:

```text
✔ Planned 1 operation(s)

migrations/app/20260707T1006_add_user_phone
└─ Add column "phone" to "user"

from:       705b1a62f26f0913caa4bfe3f8b7cb491a1b94bd47fc43471d8711bc480bcbb5
to:         925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
app space:  migrations/app/20260707T1006_add_user_phone

ℹ DDL preview

ALTER TABLE "public"."user" ADD COLUMN "phone" text;
```

The `User` model's table is `"user"`, because the table name is the model name with a lowercase first letter unless the model sets `@@map`. A database that Prisma ORM 7 created has a `"User"` table instead, and [the upgrade guide](/guides/upgrade-prisma-orm/postgresql#24-edit-the-inferred-contract) covers mapping those names with `@@map`. `db migrate` applies the migration to your database and confirms what it applied:

```text
✔ Applied 1 migration(s) (1 operation(s)) across 1 contract space(s)
```

If you see the `✔ Applied` line, you've run the entire workflow. A contract space is a separate migration history, and `migrations/app/` holds your app's, which the `app space:` line in the `migration plan` output points into. A Prisma ORM extension package is an npm package that adds database features, such as `@prisma/orm-extension-pgvector` for pgvector. One that ships its own migrations gets its own contract space in `migrations/<extension>/`, as [Extension spaces](/orm/migrations/applying-a-migration#extension-spaces) explains.

## What a migration contains

A migration is a directory under `migrations/app/`, named with a timestamp and a slug:

```text
migrations/
├── app/
│   └── 20260707T1006_add_user_phone/
│       ├── migration.ts     # the change, as TypeScript
│       ├── ops.json         # the operations, as JSON
│       └── migration.json   # where this migration fits in history
└── snapshots/
    └── <contract hash>/
        ├── contract.json    # snapshot of one contract state
        └── contract.d.ts    # types for that snapshot; they type-check migration.ts
```

`migrations/snapshots/` holds one directory per contract state, named by its [hash](#migrationjson-the-history-marker). Each `migration.ts` imports its start and end contracts from there. A baseline migration is a first migration from an empty database to a contract state, so it imports only its end contract, as [Baselines](/orm/migrations/the-migration-graph#baselines) explains.

Commit `migration.ts`, `ops.json`, `migration.json`, and the `migrations/snapshots/` directories that each `migration.ts` imports. Also commit `contract.json` and `contract.d.ts`.

### migration.ts: the file you edit

`migration.ts` describes the migration in ordinary TypeScript. Each step is a call to one of the methods on the migration class that `migration.ts` defines:

```ts
this.addColumn(...)
this.createTable(...)
this.dataTransform(...)
```

Because it imports its contract snapshots, your editor catches type mistakes before the migration touches a database. To review or change what the migration does, read or edit this file, as [Editing a migration](/orm/migrations/editing-a-migration) explains.

### ops.json: the file Prisma runs

`migration plan` writes `ops.json`, which holds the migration's operations as JSON. `db migrate` never runs `migration.ts`. Neither `db migrate` nor `migration check` compares `ops.json` with `migration.ts`, so recompile after every edit to `migration.ts`, as [Editing a migration](/orm/migrations/editing-a-migration) explains.

### migration.json: its place in history [#migrationjson-the-history-marker]

`migration.json` records where this migration fits in your migration history. Each contract state is named by its hash, an identifier computed from the contract, and the same contract always produces the same hash. Where a command takes a hash, you can pass its first 6 or more characters, as long as they match only one hash. A migration records:

- the contract hash it starts `from`
- the contract hash it moves `to`
- when it was created
- its own hash, `migrationHash`, so `npx prisma migration check` fails if someone edits `migration.json` or `ops.json` by hand

Do not edit `migration.json` or `ops.json` by hand. Edit `migration.ts` and recompile it instead, which rewrites both files.

Read `from` and `to` like a Git commit range: the contract state before, and the contract state after. These hashes link migrations into a [migration history](/orm/migrations/the-migration-graph) that can branch instead of forming a numbered list. It branches when two people plan migrations from the same contract state on separate Git branches. After both branches merge, plan one migration from the end of each branch to the merged contract, as [the worked example](/orm/migrations/the-migration-graph#a-worked-example) shows. `npx prisma migration graph` draws your migration history, so you can see whether it branches.

## Every operation checks itself

Inside `ops.json`, each operation has three parts:

1. **Precheck**: confirms the database is in the expected state before the change runs.
2. **Execute**: the statements that make the change.
3. **Postcheck**: confirms the change worked after it runs.

`db migrate` runs the postcheck first, and if it already passes, the change is already in the database, so the operation is skipped. Otherwise `db migrate` runs the precheck, the change, and the postcheck, in that order.

Each operation also has a class:

- **Additive**: adds something new, like a column.
- **Widening**: loosens a constraint or lets a type accept more values, like dropping `NOT NULL` from a column.
- **Destructive**: removes or changes something that exists, like dropping a column, and can lose data.
- **Data**: changes rows, not structure.

Only destructive operations get a warning. `migration plan` and `migration show` print `This migration contains destructive operations that may cause data loss.` before anything runs. `db migrate` runs destructive operations without asking and prints the warning again after applying them. To catch one before it runs, read the output of `npx prisma migration show <dir>` when you review a migration.

```json title="One operation from ops.json"
{
  "id": "column.public.user.phone",
  "label": "Add column \"phone\" to \"user\"",
  "operationClass": "additive",
  "target": { "id": "postgres", "details": { "schema": "public", "objectType": "column", "name": "phone", "table": "user" } },
  "precheck": [
    {
      "description": "ensure column \"phone\" is missing",
      "sql": "SELECT NOT EXISTS (SELECT 1 AS \"one\" FROM \"information_schema\".\"columns\" WHERE (\"table_schema\" = $1 AND \"table_name\" = $2 AND \"column_name\" = $3)) AS \"result\"",
      "params": ["public", "user", "phone"]
    }
  ],
  "execute": [
    {
      "description": "add column \"phone\"",
      "sql": "ALTER TABLE \"public\".\"user\" ADD COLUMN \"phone\" text"
    }
  ],
  "postcheck": [
    {
      "description": "verify column \"phone\" exists",
      "sql": "SELECT EXISTS (SELECT 1 AS \"one\" FROM \"information_schema\".\"columns\" WHERE (\"table_schema\" = $1 AND \"table_name\" = $2 AND \"column_name\" = $3)) AS \"result\"",
      "params": ["public", "user", "phone"]
    }
  ]
}
```

The checks help in three situations:

- **A migration fails.** On PostgreSQL, one `db migrate` run is one transaction, so a failure undoes the whole run and running it again starts from the same place. On MongoDB, a run uses no transaction, so the operations that finished before a failure stay in the database. On both databases, a change that is already there, such as one made by hand or left by a failed MongoDB run, is skipped because its postcheck passes. [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) covers recovery.
- **The database isn't in the state you assumed.** The precheck stops the run before the change, for example when a migration sets `NOT NULL` on a column that still has `NULL` values, and the error names the operation and the check that failed. Fix the cause, for example by editing the migration to fill those rows first, then run `npx prisma db migrate` again, as [Recovery](/orm/migrations/rollbacks-and-recovery#recovery-when-a-migration-fails-partway) shows.
- **Someone else or a coding agent wrote the migration.** The intent in `migration.ts`, the SQL in `ops.json`, and the checks for every step are all in the diff for you to review.

## The commands

These commands are part of the [Prisma ORM CLI](/cli), and you run them with `npx prisma <command>`. The planning and inspection commands work offline, because they read files, not your database:

| Command                   | What it does                                                            |
| ------------------------- | ----------------------------------------------------------------------- |
| `migration plan`          | [Generate a migration](/orm/migrations/generating-a-migration) from your contract changes |
| `migration new`           | Write an empty migration for a [data-only or hand-written change](/orm/migrations/editing-a-migration#starting-from-a-blank-migration) |
| `migration show <target>` | Print one migration's operations, DDL preview, and metadata            |
| `migration list`          | List every on-disk migration                                            |
| `migration graph`         | Draw your [migration history](/orm/migrations/the-migration-graph) as a graph |
| `migration check`         | Check that migration hashes match and no files are missing, for example in CI |

For `migration show`, `<target>` is a migration's directory name, its path under `migrations/app/`, or the first 6 or more characters of its `migrationHash`.

Three commands connect to a database:

| Command            | What it does                                                                 |
| ------------------ | ---------------------------------------------------------------------------- |
| `db migrate`          | [Apply pending migrations](/orm/migrations/applying-a-migration)        |
| `migration status` | Show where the database is in your migration history and which migrations are pending |
| `migration log`    | Show the history of migrations the database has actually applied             |

If you used Prisma ORM 7, these commands replace its migrate commands:

- `migrate dev` becomes `migration plan`, then `db migrate --advance-ref db`, when you want migration files. It becomes `db update` when you only want a development database to match the contract.
- `migrate deploy` becomes `db migrate`.
- `migrate reset` has no equivalent. Drop and recreate the database with your database tools, then run `npx prisma db init`.
- `migrate diff` becomes `migration show <dir>` or `db update --dry-run`.
- What Prisma ORM 7 called baselining, marking an existing database as already migrated, is `npx prisma db sign`. For a database that Prisma ORM 7 migrated, follow [Prisma ORM 7 to 8 (PostgreSQL)](/guides/upgrade-prisma-orm/postgresql).

[Coming from Prisma ORM 7](/orm/coming-from-prisma-orm-7#commands) has the full table, including `migrate resolve`.

## The same model for SQL and MongoDB

The commands, the file layout, the migration history, and the three checks on every operation are the same on PostgreSQL and MongoDB. On PostgreSQL, operations run SQL statements such as `ALTER TABLE`. On MongoDB, operations create collections, indexes, and JSON Schema validators.

Each database keeps a [**marker**](/orm/migrations/the-migration-graph#terms-used-on-this-page), the record in the database of which contract state it currently matches. After applying, `db migrate --advance-ref db` sets the `db` ref to that same contract state. Each database also keeps a ledger, its own list of every migration applied to it, and `migration log` reads that list.

:::note[Migrations are early]

Migrations are one of the newest parts of Prisma ORM. Planning, editing, applying, [rolling back](/orm/migrations/rollbacks-and-recovery), and [baseline migrations](/orm/migrations/the-migration-graph#baselines) work today. There is no squash command and no shadow-database dry run yet.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Add a `phone` field to the User model and plan a migration for it."
- "Show me the pending migrations and what SQL they will run."
- "Explain what the ops.json in the latest migration does."
