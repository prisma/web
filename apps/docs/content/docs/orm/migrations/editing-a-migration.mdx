Each migration is a TypeScript file, `migration.ts`, that calls methods such as `this.addColumn(...)`. `npx prisma migration plan` writes a first draft, but some decisions need you: what to put in existing rows when a column becomes required, which order to run two steps in, and how to write a statement that has no method. The SQL that runs is in `ops.json`, and `npx prisma db migrate`, which replaces [`prisma migrate deploy`](/orm/coming-from-prisma-orm-7), runs only that file. So you never edit `ops.json` by hand: you edit `migration.ts` and recompile it, which writes `ops.json` again.

After any edit, recompile from your project's root directory:

```bash
node migrations/app/20260707T1008_add_display_name/migration.ts
```

```text
Wrote ops.json + migration.json to /path/to/my-app/migrations/app/20260707T1008_add_display_name
```

Each migration is a directory under `migrations/app/`, the folder that holds your app's migrations. Run the command from the project root, because inside the migration directory it fails with an error whose `code` is `CONFIG.FILE_NOT_FOUND`. If someone hand-edits `ops.json` after you recompile, `npx prisma migration check` fails. It does not read `migration.ts`, so it cannot tell when you edit `migration.ts` and forget to recompile. Commit `migration.ts`, `ops.json`, `migration.json`, the `migrations/snapshots/<hash>/` directories that `migration.ts` imports, and your `contract.json` and `contract.d.ts`, all together.

An edit reaches only the databases that have not applied the migration yet, because `npx prisma db migrate` does not compare the migrations a database already applied with the files on disk. To change a database that already applied a migration, plan a new migration.

## Worked example: making a column required

You add a required `displayName` field to `User` in your contract, the `contract.prisma` file that replaced `schema.prisma`. The `user` table already has rows, and those rows have no `displayName`. Run `npx prisma contract emit`, which replaces `prisma generate` and writes `contract.json` and `contract.d.ts`. Then plan the migration as [Generating a migration](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) describes:

```npm
npx prisma migration plan --name add_display_name
```

```text
⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

app space:  migrations/app/20260707T1008_add_display_name
```

The `app space` line is the new migration's directory. Running `node migration.ts` to self-emit means recompiling: the file writes its own `ops.json`, and you run it from the project root as shown above. `migration plan` writes the three steps this change needs and leaves the backfill query to you. `this.addColumn(...)` adds the column as nullable, `this.dataTransform(...)` holds the backfill, and `this.setNotNull(...)` makes the column required. The table name `user` is the model name with a lowercase first letter:

```ts title="migration.ts (as planned)"
override get operations() {
  return [
    this.addColumn({
      schema: 'public',
      table: 'user',
      column: col('displayName', 'text', { codecRef: { codecId: 'pg/text@1' } }),
    }),
    this.dataTransform(endContract, 'backfill-user-displayName', {
      check: () => placeholder('backfill-user-displayName:check'),
      run: () => placeholder('backfill-user-displayName:run'),
    }),
    this.setNotNull({ schema: 'public', table: 'user', column: 'displayName' }),
  ];
}
```

A `dataTransform` takes two callbacks. `check` finds rows that still need the backfill, so it must be a query that returns rows, and any row it returns means work remains. A typical `check` is `select('id').where(<rows not yet fixed>).limit(1)`. `run` makes the change. Write both with the `sql` query builder, a typed builder that gets its types from a snapshot, not a template string of raw SQL. In each `where`, `f` holds the table's columns and `fns` holds functions such as `eq`. A snapshot is a saved copy of your contract in `migrations/snapshots/<hash>/`, named by the contract's 64-character hash. This migration imports two: the start contract, from before the migration, and the end contract, from after it.

```ts title="migration.ts (filled in)"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract';
import endContractJson from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract.json' with { type: 'json' };
import type { Contract as Start } from '../../snapshots/925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72/contract';
import startContractJson from '../../snapshots/925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72/contract.json' with { type: 'json' };
import { Migration, MigrationCLI, col } from '@prisma/orm-postgres/migration';
import postgresAdapter from '@prisma/orm-postgres/adapter/runtime';
import { sql } from '@prisma/orm-postgres/builder/runtime';
import { createExecutionContext, createSqlExecutionStack } from '@prisma/orm-postgres/family-runtime';
import postgresTarget, { PostgresContractSerializer } from '@prisma/orm-postgres/target/runtime';

const endContract = new PostgresContractSerializer().deserializeContract<End>(endContractJson);
const stack = createSqlExecutionStack({ target: postgresTarget, adapter: postgresAdapter });

const db = sql<End>({
  context: createExecutionContext({ contract: endContract, stack }),
  rawCodecInferer: stack.adapter.rawCodecInferer,
});

export default class M extends Migration<Start, End> {
  override readonly endContractJson = endContractJson;
  override readonly startContractJson = startContractJson;

  override get operations() {
    return [
      this.addColumn({
        schema: 'public',
        table: 'user',
        column: col('displayName', 'text', { codecRef: { codecId: 'pg/text@1' } }),
      }),
      this.dataTransform(endContract, 'backfill-user-displayName', {
        check: () =>
          db.public.user
            .select('id')
            .where((f, fns) => fns.eq(f.displayName, null))
            .limit(1),
        run: () =>
          db.public.user
            .update({ displayName: 'Anonymous' })
            .where((f, fns) => fns.eq(f.displayName, null)),
      }),
      this.setNotNull({ schema: 'public', table: 'user', column: 'displayName' }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The planned file differs from the filled-in file in three places:

1. The planned `import { Migration, MigrationCLI, col, placeholder } from '@prisma/orm-postgres/migration'` loses `placeholder`. Below it, add the four other `@prisma/orm-postgres` imports and the `endContract`, `stack`, and `db` statements, copied as they are.
2. The planned snapshot imports `import endContract from ...` and `import startContract from ...` become `endContractJson` and `startContractJson`, in the imports and in the two class fields. The rename frees the name `endContract` for the contract that the new `endContract` statement builds from that JSON.
3. The two `placeholder(...)` calls become your `check` and `run` queries. Keep the rest of each operation as `migration plan` wrote it, including each `codecRef`, whose `codecId` is the PostgreSQL type plus a version.

Recompile with `node migrations/app/20260707T1008_add_display_name/migration.ts` from the project root, then review what the backfill became in `ops.json`, because that file is what runs. If no rows need the backfill when `npx prisma db migrate` runs, the operation is skipped:

```json title="ops.json (the compiled dataTransform)"
{
  "id": "data_migration.backfill-user-displayName",
  "label": "Data transform: backfill-user-displayName",
  "operationClass": "data",
  "target": { "id": "postgres" },
  "precheck": [
    {
      "description": "Check backfill-user-displayName has work to do",
      "sql": "SELECT EXISTS (SELECT \"id\" AS \"id\" FROM \"public\".\"user\" WHERE \"displayName\" IS NULL LIMIT 1) AS ok",
      "params": []
    }
  ],
  "execute": [
    {
      "description": "Run backfill-user-displayName",
      "sql": "UPDATE \"public\".\"user\" SET \"displayName\" = $1 WHERE \"displayName\" IS NULL",
      "params": ["Anonymous"]
    }
  ],
  "postcheck": [
    {
      "description": "Verify backfill-user-displayName resolved all violations",
      "sql": "SELECT NOT EXISTS (SELECT \"id\" AS \"id\" FROM \"public\".\"user\" WHERE \"displayName\" IS NULL LIMIT 1) AS ok",
      "params": []
    }
  ]
}
```

A column declared as `temporal.updatedAtString()` gets the current time whenever a row is created or updated. `updatedAt` in the starter contract that `npx prisma orm init` writes is one. If the model has such a column, the backfill's `update` sets it too, with a time fixed when you recompile. Each recompile writes a new time into `ops.json` but leaves the `migrationHash` in `migration.json` the same, so `npx prisma migration check` fails with an error whose `code` is `MIGRATION.CHECK_HASH_MISMATCH`, even right after a recompile. To avoid this, write an intermediate contract that is your contract with the column changed to `updatedAt TimestamptzString`, as the next section shows, and build `db` from it. The backfill then leaves `updatedAt` unchanged.

## When a backfill reads a column the migration removes

Suppose the next migration replaces the boolean `isAdmin` on `User` with a required text column, `role`. The backfill has to read `isAdmin` to decide each row's `role`. The end contract has no `isAdmin`, and the start contract has no `role`. If you build `db` from the end contract, TypeScript rejects `f.isAdmin`. If you run `node migration.ts` anyway, it stops with an error that does not name the column, and it writes nothing.

Instead, build `db` from a third contract that describes the database while the backfill runs. Copy your whole contract into the migration directory as `intermediate.prisma`. In its `User` model, add `isAdmin` back and make `role` optional, because `role` is still empty while the backfill runs. Leave the other models and fields as they are. If `User` has an `updatedAt temporal.updatedAtString()` column, change it to `updatedAt TimestamptzString` in this file.

```prisma title="intermediate.prisma (User, other fields left out)"
model User {
  id          Int     @id
  displayName String
  isAdmin     Boolean
  role        String?
}
```

In the same migration directory, add `intermediate.config.ts`. It is a second config file, in addition to your project's `prisma.config.ts`, and it names `intermediate.prisma` as the contract. It needs no database connection:

```ts title="intermediate.config.ts"
import { definePrismaConfig } from 'prisma/config';
import { defineConfig as ormConfig } from '@prisma/orm-postgres/config';
export default definePrismaConfig({ orm: ormConfig({ contract: './intermediate.prisma' }) });
```

Then run `cd migrations/app/20260708T0900_replace_is_admin && npx prisma contract emit --config intermediate.config.ts`, and go back to the project root before you recompile. The output mentions `contract.json`, but the command writes `intermediate.json` and `intermediate.d.ts` next to `intermediate.prisma`. Commit all four `intermediate.*` files with the migration. `migration.ts` imports the `.json` and `.d.ts` files, and you need the other two to run `npx prisma contract emit` again.

```text title="migrations/app/20260708T0900_replace_is_admin/"
├── intermediate.config.ts
├── intermediate.d.ts
├── intermediate.json
├── intermediate.prisma
├── migration.json
├── migration.ts
└── ops.json
```

Start from the `migration.ts` of the `displayName` example. Replace its `endContract` and `db` statements with the first block below, and replace its `operations` getter with the second. Pass the same contract to `dataTransform` that you build `db` from, because if the two differ, `node migration.ts` fails with an error whose `code` is `MIGRATION.DATA_TRANSFORM_CONTRACT_MISMATCH`. The `run` callbacks run in the order you list them, so the second one sets `member` only on rows the first left empty. `migration plan` puts `dropColumn` for `isAdmin` first, so move it after the backfill, as shown:

```ts title="migration.ts (in place of the endContract and db statements)"
import type { Contract as Mid } from './intermediate';
import midContractJson from './intermediate.json' with { type: 'json' };
const midContract = new PostgresContractSerializer().deserializeContract<Mid>(midContractJson);
const db = sql<Mid>({ context: createExecutionContext({ contract: midContract, stack }), rawCodecInferer: stack.adapter.rawCodecInferer });
```

```ts title="migration.ts (the operations getter)"
override get operations() {
  return [
    this.addColumn({ schema: 'public', table: 'user', column: col('role', 'text', { codecRef: { codecId: 'pg/text@1' } }) }),
    this.dataTransform(midContract, 'backfill-user-role', {
      check: () => db.public.user.select('id').where((f, fns) => fns.eq(f.role, null)).limit(1),
      run: [
        () => db.public.user.update({ role: 'admin' }).where((f, fns) => fns.eq(f.isAdmin, true)),
        () => db.public.user.update({ role: 'member' }).where((f, fns) => fns.eq(f.role, null)),
      ],
    }),
    this.setNotNull({ schema: 'public', table: 'user', column: 'role' }),
    this.dropColumn({ schema: 'public', table: 'user', column: 'isAdmin' }),
  ];
}
```

Build `db` from the end contract if the backfill uses only columns that still exist after the migration. If it reads a column the migration drops or renames, build `db` from an intermediate contract, or split the change into two migrations instead. To split it, add `role` to your contract as optional, then plan the migration and fill in its backfill with `db` built from its end contract. Then remove `isAdmin`, make `role` required, and plan again. Both ways work. Splitting needs no intermediate files, but it adds one more [contract state](/orm/migrations/the-migration-graph#terms-used-on-this-page), a version of your contract in the migration history.

## Raw SQL [#escape-hatch-raw-sql]

For a statement that has no method, such as `COMMENT ON`, import `rawSql` from `@prisma/orm-postgres/migration` and put the call inside the `operations` array. Set `operationClass` to `additive`, `widening`, `destructive`, or `data`, as [How migrations work](/orm/migrations/how-migrations-work#every-operation-checks-itself) describes, and note that `destructive` makes the CLI mark the operation with a data-loss warning. The `id` can be any string, and Prisma ORM does not check that it is unique. On PostgreSQL, one `npx prisma db migrate` run is [one transaction](/orm/migrations/applying-a-migration#when-something-goes-wrong), so `rawSql` does not support a statement that cannot run inside a transaction, such as `CREATE INDEX CONCURRENTLY`. Give the operation a precheck and a postcheck if you can. This example enables the `pgcrypto` PostgreSQL extension:

```ts
rawSql({
  id: 'extension.pgcrypto',
  label: 'Enable extension "pgcrypto"',
  operationClass: 'additive',
  target: { id: 'postgres' },
  precheck: [
    { description: 'not yet enabled', sql: "SELECT NOT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'pgcrypto')" },
  ],
  execute: [{ description: 'enable it', sql: 'CREATE EXTENSION IF NOT EXISTS pgcrypto' }],
  postcheck: [
    { description: 'now enabled', sql: "SELECT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'pgcrypto')" },
  ],
}),
```

Each check is a query that must return a row whose first column is true, and the column's name does not matter. An empty `precheck` lets the operation run, and an empty `postcheck` means the operation is never skipped as already done. [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) explains when that matters. If you write the same `rawSql` twice, move it into a function.

## The same pattern on MongoDB

On MongoDB, import `dataTransform` from `@prisma/orm-mongo/target/migration`. Its `check` is an object whose `source` is a callback that returns the query, and `dataTransform` compiles to a precheck, a `run` step, and a postcheck. A `check` can use the query builder, but an update in `run` cannot use it yet. Build updates from command classes such as `RawUpdateManyCommand`, and other hand-built queries from classes such as `AggregateCommand`. Both are imported from `@prisma/orm-mongo/query-ast/execution`. In this excerpt, `setValidation` comes first because the same migration adds a `status` field, so the collection's validator must be updated to match the end contract:

```ts title="migration.ts (MongoDB, excerpt)"
import { dataTransform, setValidation } from '@prisma/orm-mongo/target/migration';

override get operations() {
  const storageHash = this.endContract.storage.storageHash;
  const productsValidator = this.endContract.collection.products.validator;
  return [
    setValidation('products', productsValidator.jsonSchema, {
      validationLevel: productsValidator.validationLevel,
      validationAction: productsValidator.validationAction,
    }),
    dataTransform('backfill-product-status', {
      check: { source: () => existingProductsWithoutStatus(storageHash) },
      run: () => backfillRun(storageHash),
    }),
  ];
}
```

`existingProductsWithoutStatus` and `backfillRun` are helper functions that return the two queries. They take the end contract's hash because a query's type requires it in `meta`. Both are defined in the full migration in the Prisma ORM repo's [retail-store example](https://github.com/prisma/orm/blob/main/examples/retail-store/migrations/app/20260513T0508_backfill_product_status/migration.ts).

## Starting from a blank migration

Sometimes you want a data-only migration, or you'd rather write the whole thing by hand. `npx prisma migration new` writes a migration directory with an empty `ops.json`, a `migration.json`, and a `migration.ts`. `migration.json` records the contract hashes the migration goes `from` and `to`. The `migration.ts` has the snapshot imports, the class, and an empty `operations` array, but no `db` setup, so copy the setup from the `displayName` example. For a data-only migration, run:

```npm
npx prisma migration new --name backfill_scores --from <hash>
```

Without `--from`, the new migration starts at the end contract of your latest migration and ends at your current contract, so if your contract has not changed since then, the command fails with an error whose `code` is `MIGRATION.NO_CHANGES`. For `<hash>`, use the `to` value in your latest migration's `migration.json`, or the start of that hash as `npx prisma migration graph` prints it, such as `866ab88`. Until you add an operation to the new migration and recompile it, `npx prisma migration check` and `npx prisma migration plan` both fail. Write your operations in the generated `migration.ts`, then recompile it from the project root with `node migrations/app/<dir>/migration.ts`.

## Editing checklist

1. Edit `migration.ts`, never `ops.json`.
2. Recompile from the project root: `node migrations/app/<dir>/migration.ts`.
3. Review the diff of `ops.json`, because that's what will run.
4. Verify: `npx prisma migration check`. It prints `✔ All checks passed` when nothing is wrong.
5. Commit `migration.ts`, `ops.json`, `migration.json`, the `migrations/snapshots/<hash>/` directories that `migration.ts` imports, and your `contract.json` and `contract.d.ts`. If the migration has `intermediate.*` files, commit those too.

:::note[What's early]

Hand-written MongoDB data transforms cannot use the query builder for updates. Nothing checks that `ops.json` still matches `migration.ts`, so recompile after every edit.

:::
