Your app's migrations are directories in `migrations/app/`. Each has a TypeScript file, `migration.ts`, that calls methods such as `this.addColumn(...)`. `npx prisma migration plan` writes a first draft, but some decisions need you: what to put in existing rows, which order to run steps in, and how to write a statement that has no method.

`npx prisma db migrate`, which replaces [`prisma migrate deploy`](/orm/coming-from-prisma-orm-7), runs the SQL in each migration's `ops.json`. Hand-editing `ops.json` makes `npx prisma migration check` fail and `npx prisma db migrate` refuse to run. Edit `migration.ts` instead, then recompile it with Node.js from your project root, which rewrites `ops.json` and `migration.json` without connecting to a database:

```bash
node migrations/app/20260707T1008_add_display_name/migration.ts
```

```text
Wrote ops.json + migration.json to /path/to/my-app/migrations/app/20260707T1008_add_display_name
```

The Prisma ORM CLI needs Node.js 22.18 or later, and those versions run `migration.ts` directly. Inside the migration directory the command fails with an error whose `code` is `CONFIG.FILE_NOT_FOUND`.

`migration.json` records the contract state the migration starts `from`, the state it ends at, `to`, and a hash of the migration. `npx prisma migration check` recomputes that hash from `ops.json` and `migration.json` and compares it with the stored one, never reading `migration.ts`.

An edit affects only databases that have not applied the migration. To change one that has, plan a new migration. To test an edit on a development database that already applied it, drop and recreate that database with your own tools, because Prisma ORM 8 has no replacement for `prisma migrate reset`. Then run `npx prisma db migrate --advance-ref db`, which points the [`db` ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) at the state you just applied. That ref names the contract state you last applied in development, in a file under `migrations/app/refs/`.

## Worked example: making a column required

You add a required `displayName` field to `User` in your contract, the `contract.prisma` file that replaced `schema.prisma`. Existing rows in the `user` table have no `displayName`. Run `npx prisma contract emit`, which replaces `prisma generate` and writes `contract.json` and `contract.d.ts`. Then plan the migration as [Generating a migration](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) describes:

```npm
npx prisma migration plan --name add_display_name
```

```text
⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

from:       925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72
to:         e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63
app space:  migrations/app/20260707T1008_add_display_name
```

In the output, `self-emit` means recompiling, and `app space` shows the new migration's directory. `migration plan` writes three steps: `addColumn` adds the column as nullable, `dataTransform` holds the backfill you write, and `setNotNull` makes the column required. The table name `user` is the model name with a lowercase first letter, unless the model sets `@@map`:

```ts title="migration.ts (as planned)"
override get operations() {
  return [
    this.addColumn({
      schema: 'public',
      table: 'user',
      column: col('displayName', 'text', { codecRef: { codecId: 'pg/text@1' } }),
    }),
    this.dataTransform(endContract, 'backfill-user-displayName', {
      check: () => placeholder('backfill-user-displayName:check'),
      run: () => placeholder('backfill-user-displayName:run'),
    }),
    this.setNotNull({ schema: 'public', table: 'user', column: 'displayName' }),
  ];
}
```

A `dataTransform` takes two callbacks, and each returns a query built with the [`sql` query builder](/orm/reference/sql-query-builder), not a SQL string. `check` returns rows that still need the backfill, and `run` changes them. In each `where`, `f` holds the table's columns, `fns` holds [functions](/orm/reference/sql-query-builder#expressions-and-functions) such as `eq`, so `fns.eq(f.displayName, null)` becomes `IS NULL`. To set a column from another column, pass [`update()`](/orm/reference/sql-query-builder#update) a callback: `update((f) => ({ displayName: f.email }))`. A snapshot is a copy of your contract that `migration plan` saves in `migrations/snapshots/<hash>/`. This migration imports the snapshot from before it and the one from after it.

```ts title="migration.ts (filled in)"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract';
import endContractJson from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract.json' with { type: 'json' };
import type { Contract as Start } from '../../snapshots/925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72/contract';
import startContractJson from '../../snapshots/925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72/contract.json' with { type: 'json' };
import { Migration, MigrationCLI, col } from '@prisma/orm-postgres/migration';
import postgresAdapter from '@prisma/orm-postgres/adapter/runtime';
import { sql } from '@prisma/orm-postgres/builder/runtime';
import { createExecutionContext, createSqlExecutionStack } from '@prisma/orm-postgres/family-runtime';
import postgresTarget, { PostgresContractSerializer } from '@prisma/orm-postgres/target/runtime';

const endContract = new PostgresContractSerializer().deserializeContract<End>(endContractJson);
const stack = createSqlExecutionStack({ target: postgresTarget, adapter: postgresAdapter });

const db = sql<End>({
  context: createExecutionContext({ contract: endContract, stack }),
  rawCodecInferer: stack.adapter.rawCodecInferer,
});

export default class M extends Migration<Start, End> {
  override readonly endContractJson = endContractJson;
  override readonly startContractJson = startContractJson;

  override get operations() {
    return [
      this.addColumn({
        schema: 'public',
        table: 'user',
        column: col('displayName', 'text', { codecRef: { codecId: 'pg/text@1' } }),
      }),
      this.dataTransform(endContract, 'backfill-user-displayName', {
        check: () =>
          db.public.user
            .select('id')
            .where((f, fns) => fns.eq(f.displayName, null))
            .limit(1),
        run: () =>
          db.public.user
            .update({ displayName: 'Anonymous' })
            .where((f, fns) => fns.eq(f.displayName, null)),
      }),
      this.setNotNull({ schema: 'public', table: 'user', column: 'displayName' }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

The planned file differs in three ways. Its migration import also has `placeholder`, and it lacks the four other `@prisma/orm-postgres` imports and the `endContract`, `stack`, and `db` statements, which build queries and never connect to a database. Its snapshot `contract.json` imports are named `endContract` and `startContract`, renamed here to `endContractJson` and `startContractJson` so that `endContract` names the deserialized contract. Its `placeholder(...)` calls become your `check` and `run` queries, and the rest of each operation, such as `codecRef`, stays as `migration plan` wrote it.

Recompile. While a `placeholder(...)` call is left, recompiling fails with an error whose `code` is `MIGRATION.UNFILLED_PLACEHOLDER`, and `npx prisma db migrate` fails because `ops.json` is still empty. Then check that the compiled `UPDATE` in `ops.json` sets the value you meant on the rows you meant:

```json title="ops.json (the compiled dataTransform)"
{
  "id": "data_migration.backfill-user-displayName",
  "label": "Data transform: backfill-user-displayName",
  "operationClass": "data",
  "target": { "id": "postgres" },
  "precheck": [
    {
      "description": "Check backfill-user-displayName has work to do",
      "sql": "SELECT EXISTS (SELECT \"id\" AS \"id\" FROM \"public\".\"user\" WHERE \"displayName\" IS NULL LIMIT 1) AS ok",
      "params": []
    }
  ],
  "execute": [
    {
      "description": "Run backfill-user-displayName",
      "sql": "UPDATE \"public\".\"user\" SET \"displayName\" = $1 WHERE \"displayName\" IS NULL",
      "params": ["Anonymous"]
    }
  ],
  "postcheck": [
    {
      "description": "Verify backfill-user-displayName resolved all violations",
      "sql": "SELECT NOT EXISTS (SELECT \"id\" AS \"id\" FROM \"public\".\"user\" WHERE \"displayName\" IS NULL LIMIT 1) AS ok",
      "params": []
    }
  ]
}
```

A column declared as `temporal.updatedAtString()` gets the current time whenever a row is created or updated, like `@updatedAt` in Prisma ORM 7. This example's `User` has none, but the starter contract from `npx prisma orm init` has one, `updatedAt`. On such a model the backfill's `update` also sets `updatedAt`, so `npx prisma migration check` fails right after every recompile with an error whose `code` is `MIGRATION.CHECK_HASH_MISMATCH`, and `npx prisma db migrate` refuses to run.

To fix it, build `db` from an intermediate contract and pass that contract to `dataTransform`, as the next section shows. In that contract, make `displayName` optional and declare `updatedAt` as `TimestamptzString`, which Prisma ORM does not set for you.

## When a backfill reads a column the migration removes

Suppose the next migration replaces the boolean `isAdmin` on `User` with a required text column, `role`. Change your contract, run `npx prisma contract emit`, and plan the migration as in the `displayName` example. The backfill reads `isAdmin` to decide each row's `role`, but the end contract has no `isAdmin` and the start contract has no `role`. Build `db` from the end contract and TypeScript rejects `f.isAdmin`, so recompiling fails with an error that does not name the column.

Instead, build `db` from an intermediate contract that describes the database while the backfill runs. Copy your whole contract into the migration directory as `intermediate.prisma`, and in its `User` model add `isAdmin` back and make `role` optional, because no row has a `role` yet.

```prisma title="intermediate.prisma (User, other fields left out)"
model User {
  id          Int     @id
  displayName String
  isAdmin     Boolean
  role        String?
}
```

In the same migration directory, add `intermediate.config.ts`, a second config file that names `intermediate.prisma` as the contract and needs no database connection:

```ts title="intermediate.config.ts"
import { definePrismaConfig } from 'prisma/config';
import { defineConfig as ormConfig } from '@prisma/orm-postgres/config';
export default definePrismaConfig({ orm: ormConfig({ contract: './intermediate.prisma' }) });
```

Emit the intermediate contract from inside the migration directory, because `intermediate.config.ts` reads its paths from the directory you run the command in. Commit all four `intermediate.*` files with the migration.

```bash
cd migrations/app/20260708T0900_replace_is_admin
npx prisma contract emit --config intermediate.config.ts
cd ../../..
```

```text title="migrations/app/20260708T0900_replace_is_admin/"
├── intermediate.config.ts
├── intermediate.d.ts
├── intermediate.json
├── intermediate.prisma
├── migration.json
├── migration.ts
└── ops.json
```

Now edit this migration's own planned `migration.ts`, not a copy of the `displayName` file, whose snapshot imports point at other contracts. The listing below builds `db` from the intermediate contract and passes that same contract to `dataTransform`. Pass a different one and `node migration.ts` fails with an error whose `code` is `MIGRATION.DATA_TRANSFORM_CONTRACT_MISMATCH`. The planned `dropColumn` for `isAdmin` now runs after the backfill, and the two `run` callbacks run in order, so the second sets `member` only on rows the first left empty.

```ts title="migration.ts (filled in)"
#!/usr/bin/env -S node
import type { Contract as End } from '../../snapshots/<end hash>/contract';
import endContractJson from '../../snapshots/<end hash>/contract.json' with { type: 'json' };
import type { Contract as Start } from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract';
import startContractJson from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract.json' with { type: 'json' };
import type { Contract as Mid } from './intermediate';
import midContractJson from './intermediate.json' with { type: 'json' };
import { Migration, MigrationCLI, col } from '@prisma/orm-postgres/migration';
import postgresAdapter from '@prisma/orm-postgres/adapter/runtime';
import { sql } from '@prisma/orm-postgres/builder/runtime';
import { createExecutionContext, createSqlExecutionStack } from '@prisma/orm-postgres/family-runtime';
import postgresTarget, { PostgresContractSerializer } from '@prisma/orm-postgres/target/runtime';

const stack = createSqlExecutionStack({ target: postgresTarget, adapter: postgresAdapter });
const midContract = new PostgresContractSerializer().deserializeContract<Mid>(midContractJson);

const db = sql<Mid>({
  context: createExecutionContext({ contract: midContract, stack }),
  rawCodecInferer: stack.adapter.rawCodecInferer,
});

export default class M extends Migration<Start, End> {
  override readonly endContractJson = endContractJson;
  override readonly startContractJson = startContractJson;

  override get operations() {
    return [
      this.addColumn({ schema: 'public', table: 'user', column: col('role', 'text', { codecRef: { codecId: 'pg/text@1' } }) }),
      this.dataTransform(midContract, 'backfill-user-role', {
        check: () => db.public.user.select('id').where((f, fns) => fns.eq(f.role, null)).limit(1),
        run: [
          () => db.public.user.update({ role: 'admin' }).where((f, fns) => fns.eq(f.isAdmin, true)),
          () => db.public.user.update({ role: 'member' }).where((f, fns) => fns.eq(f.role, null)),
        ],
      }),
      this.setNotNull({ schema: 'public', table: 'user', column: 'role' }),
      this.dropColumn({ schema: 'public', table: 'user', column: 'isAdmin' }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

Instead of an intermediate contract, you can split the change into two migrations. First add `role` to your contract as optional and plan. In that migration, add a `dataTransform` that sets `role` from `isAdmin`, with `db` built from its end contract. Then remove `isAdmin`, make `role` required, and plan again. That plan writes a `handle-nulls-user-role` placeholder, which you fill in for rows where `role` is still empty. Splitting needs no `intermediate.*` files, unless `User` has a `temporal.updatedAtString()` column.

## Raw SQL [#escape-hatch-raw-sql]

For a statement that has no method, such as `COMMENT ON`, import `rawSql` from `@prisma/orm-postgres/migration` and add the call to the `operations` array. Set `operationClass` to one of the [four classes](/orm/migrations/how-migrations-work#every-operation-checks-itself): `additive`, `widening`, `destructive`, or `data`. `npx prisma db migrate` runs all four, and adds a data-loss warning for `destructive`. Give each operation its own `id`, because error messages name it and Prisma ORM does not check that it is unique. The CLI prints the `label`. One `npx prisma db migrate` run on PostgreSQL is [one transaction](/orm/migrations/applying-a-migration#when-something-goes-wrong), so `rawSql` cannot run `CREATE INDEX CONCURRENTLY` or anything else that must run outside a transaction. Use `this.createIndex`, a plain `CREATE INDEX` that blocks writes while it builds. The example below is only an illustration: it enables the `pgcrypto` PostgreSQL extension, which you would do with `this.installExtension`:

```ts
rawSql({
  id: 'extension.pgcrypto',
  label: 'Enable extension "pgcrypto"',
  operationClass: 'additive',
  target: { id: 'postgres' },
  precheck: [
    { description: 'not yet enabled', sql: "SELECT NOT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'pgcrypto')" },
  ],
  execute: [{ description: 'enable it', sql: 'CREATE EXTENSION IF NOT EXISTS pgcrypto' }],
  postcheck: [
    { description: 'now enabled', sql: "SELECT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'pgcrypto')" },
  ],
}),
```

Give each operation a precheck and postcheck if you can. Each check is a query whose first row must have `true` in its first column. `npx prisma db migrate` runs the postcheck twice. Before the operation, a passing postcheck means the change is already there, so the operation is skipped. Otherwise the precheck runs, and if it is not true the run stops. After the operation, a failing postcheck stops the run. An empty `precheck` lets the operation run. An empty `postcheck` never passes before the operation, so that operation runs on every `npx prisma db migrate` that applies its migration.

## The same pattern on MongoDB

On MongoDB, import `dataTransform` from `@prisma/orm-mongo/target/migration`. Its `check` is an object whose `source` is a callback that returns the query. The example below needs no `db` statements. It builds the `check` query with `AggregateCommand` and the `run` update with `RawUpdateManyCommand`, both from `@prisma/orm-mongo/query-ast/execution`. `new RawUpdateManyCommand('products', { status: { $exists: false } }, { $set: { status: 'active' } })` takes the collection name, a filter, and an update. The helpers `existingProductsWithoutStatus` and `backfillRun` return those two queries. Each takes the end contract's `storageHash`, because every MongoDB query records the hash of the contract it was built for. `setValidation` is here only because this migration also adds fields to `products`, which the collection's validator must include. Both helpers are in the full [retail-store example](https://github.com/prisma/orm/blob/main/examples/retail-store/migrations/app/20260513T0508_backfill_product_status/migration.ts):

```ts title="migration.ts (MongoDB, excerpt)"
import { dataTransform, setValidation } from '@prisma/orm-mongo/target/migration';

override get operations() {
  const storageHash = this.endContract.storage.storageHash;
  const productsValidator = this.endContract.collection.products.validator;
  return [
    setValidation('products', productsValidator.jsonSchema, {
      validationLevel: productsValidator.validationLevel,
      validationAction: productsValidator.validationAction,
    }),
    dataTransform('backfill-product-status', {
      check: { source: () => existingProductsWithoutStatus(storageHash) },
      run: () => backfillRun(storageHash),
    }),
  ];
}
```

## Starting from a blank migration

For a data-only migration, or one you write by hand, run `npx prisma migration new`. It writes an empty `ops.json`, a `migration.json`, and a `migration.ts` with the snapshot imports, the class, and an empty `operations` array. It has no `placeholder` import to remove. Add the `@prisma/orm-postgres` imports and the `endContract`, `stack`, and `db` statements from the filled-in `displayName` listing.

A data-only migration starts and ends at your current contract state, so pass `--from` with your contract's hash, which `npx prisma migration graph` marks `@contract`. The [`migration new` reference](/cli/migration-new) lists its options:

```npm
npx prisma migration new --name backfill_scores --from <hash>
```

Write your operations in the new `migration.ts` and recompile it. Until you do, `npx prisma migration check` and `npx prisma migration plan` both fail.

## Editing checklist

1. Edit `migration.ts`, never `ops.json`, then recompile it.
2. Review the diff of `ops.json`, the file that runs.
3. Run `npx prisma migration check`, which prints `✔ All checks passed` when nothing is wrong.
4. Commit `migration.ts`, `ops.json`, `migration.json`, the `migrations/snapshots/<hash>/` directories that `migration.ts` imports, and your `contract.json` and `contract.d.ts`. If the migration has `intermediate.*` files, commit those too.

:::note[What's early]

Hand-written MongoDB data transforms cannot use the query builder for updates. No command notices a `migration.ts` edit that you did not recompile, so recompile after every edit.

:::
