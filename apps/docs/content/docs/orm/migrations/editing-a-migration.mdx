The planner writes a good first draft, but many migrations require the input of a human (or agent) for key decisions: what to put in existing rows when a column becomes required, which order to run two steps in, one statement the planner has no factory for. In Prisma ORM you make those changes by editing `migration.ts` (ordinary TypeScript with autocomplete and type checking) and recompiling it. You never hand-edit SQL files or `ops.json`.

The rule that makes this safe:

> **You edit `migration.ts`, and running it regenerates `ops.json`. The runner only ever executes `ops.json`.**

After any edit, recompile from your project's root directory:

```bash
node migrations/app/20260707T1008_add_display_name/migration.ts
```

```text
Wrote ops.json + migration.json to /path/to/my-app/migrations/app/20260707T1008_add_display_name
```

Recompiling also records a new `migrationHash` in `migration.json`, computed from `migration.json` and `ops.json`. If someone hand-edits `ops.json` afterwards, `migration check` fails with a hash mismatch. `migration.ts` is not part of that hash, so `migration check` cannot tell when someone edits `migration.ts` and forgets to recompile. Commit `migration.ts` and `ops.json` together.

## Worked example: making a column required

This is the classic case: `User` gets a required `displayName`, but the table already has rows and those rows have no `displayName`. Plan it:

```npm
npx prisma migration plan --name add_display_name
```

```text
⚠ Planned migration with placeholder(s) — edit migration.ts then run `node migration.ts` to self-emit

Replace each placeholder(...) call in migrations/app/20260707T1008_add_display_name/migration.ts with your query
```

The planner writes the three steps this change needs (add the column as nullable, backfill it, then make it required) and leaves the backfill query to you:

```ts title="migration.ts (as planned)"
override get operations() {
  return [
    this.addColumn({
      schema: 'public',
      table: 'user',
      column: col('displayName', 'text', { codecRef: { codecId: 'pg/text@1' } }),
    }),
    this.dataTransform(endContract, 'backfill-user-displayName', {
      check: () => placeholder('backfill-user-displayName:check'),
      run: () => placeholder('backfill-user-displayName:run'),
    }),
    this.setNotNull({ schema: 'public', table: 'user', column: 'displayName' }),
  ];
}
```

A `dataTransform` takes two closures. `check` asks "are there rows that still need this?", so it must be a row-returning query where *any row* means work remains. The conventional shape is `select('id').where(<violation>).limit(1)`. `run` performs the change. Fill them with the typed SQL query builder, built from the snapshot of your contract (the `contract.prisma` file that replaced `schema.prisma`) that the migration imports from `migrations/snapshots/`:

```ts title="migration.ts (filled in)"
import type { Contract as End } from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract';
import endContractJson from '../../snapshots/e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63/contract.json' with {
  type: 'json',
};
import type { Contract as Start } from '../../snapshots/925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72/contract';
import startContractJson from '../../snapshots/925198f3cc272c5fd19c24ac02f251661775ddac21cdac4e634bbc0dda8b2d72/contract.json' with {
  type: 'json',
};
import { Migration, MigrationCLI, col } from '@prisma/orm-postgres/migration';
import postgresAdapter from '@prisma/orm-postgres/adapter/runtime';
import { sql } from '@prisma/orm-postgres/builder/runtime';
import { createExecutionContext, createSqlExecutionStack } from '@prisma/orm-postgres/family-runtime';
import postgresTarget, { PostgresContractSerializer } from '@prisma/orm-postgres/target/runtime';

const endContract = new PostgresContractSerializer().deserializeContract(endContractJson);
const stack = createSqlExecutionStack({ target: postgresTarget, adapter: postgresAdapter });

const db = sql<End>({
  context: createExecutionContext({ contract: endContract, stack }),
  rawCodecInferer: stack.adapter.rawCodecInferer,
});

export default class M extends Migration<Start, End> {
  override readonly endContractJson = endContractJson;
  override readonly startContractJson = startContractJson;

  override get operations() {
    return [
      this.addColumn({
        schema: 'public',
        table: 'user',
        column: col('displayName', 'text', { codecRef: { codecId: 'pg/text@1' } }),
      }),
      this.dataTransform(endContract, 'backfill-user-displayName', {
        check: () =>
          db.public.user
            .select('id')
            .where((f, fns) => fns.eq(f.displayName, null))
            .limit(1),
        run: () =>
          db.public.user
            .update({ displayName: 'Anonymous' })
            .where((f, fns) => fns.eq(f.displayName, null)),
      }),
      this.setNotNull({ schema: 'public', table: 'user', column: 'displayName' }),
    ];
  }
}

MigrationCLI.run(import.meta.url, M);
```

`sql()` needs both a `context` and the adapter's `rawCodecInferer`. `rawCodecInferer` is what works out how to convert a bare JavaScript value you interpolate into a raw SQL fragment. It is a required field, so a call without it does not type-check. Keeping the execution stack in its own `const` lets you pass `stack.adapter.rawCodecInferer`, the same value the Prisma ORM client passes.

Two details matter here:

- **The types come from the migration's end-contract snapshot** (`migrations/snapshots/<contract hash>/contract`), not your app's current contract. You're type-checking against the database *as it will exist when this step runs*. That's why the builder accepts `displayName` even though the column doesn't exist yet, and why a migration written months ago keeps compiling after your contract changes.
- **The query is ordinary TypeScript.** You can import shared constants, and typos in column names fail the type check instead of failing in production.

Recompile with `node migration.ts` and inspect what the backfill became:

```json title="ops.json (the compiled dataTransform)"
{
  "id": "data_migration.backfill-user-displayName",
  "label": "Data transform: backfill-user-displayName",
  "operationClass": "data",
  "target": { "id": "postgres" },
  "precheck": [
    {
      "description": "Check backfill-user-displayName has work to do",
      "sql": "SELECT EXISTS (SELECT \"id\" AS \"id\" FROM \"public\".\"user\" WHERE \"displayName\" IS NULL LIMIT 1) AS ok",
      "params": []
    }
  ],
  "execute": [
    {
      "description": "Run backfill-user-displayName",
      "sql": "UPDATE \"public\".\"user\" SET \"displayName\" = $1 WHERE \"displayName\" IS NULL",
      "params": ["Anonymous"]
    }
  ],
  "postcheck": [
    {
      "description": "Verify backfill-user-displayName resolved all violations",
      "sql": "SELECT NOT EXISTS (SELECT \"id\" AS \"id\" FROM \"public\".\"user\" WHERE \"displayName\" IS NULL LIMIT 1) AS ok",
      "params": []
    }
  ]
}
```

Your `check` closure became both the [precheck](/orm/migrations/how-migrations-work#every-operation-checks-itself) (`EXISTS`: is there work?) and the postcheck (`NOT EXISTS`: is it done?). Your `run` became a parameterized `UPDATE`. `"Anonymous"` is sent in `params` and bound by the database driver, so it is never written into the SQL text. The reviewer reading your PR sees intent in `migration.ts` and the exact statements in `ops.json`, side by side.

## When a backfill reads a column the migration removes

Suppose the next migration replaces the boolean `isAdmin` on `User` with a required text column, `role`. The backfill has to read `isAdmin` to decide each row's `role`. The end contract has no `isAdmin`. The start contract has no `role`. If you build `db` from the end contract, TypeScript rejects `f.isAdmin`. If you run `node migration.ts` anyway, it stops with an error before it writes `ops.json`.

Instead, describe `User` as it is while the backfill runs, in a contract of its own. Copy your contract into the migration directory as `intermediate.prisma`, and give `User` both columns. `role` is optional here because it is still empty:

```prisma title="intermediate.prisma (the User model)"
model User {
  id          Int     @id
  displayName String
  isAdmin     Boolean
  role        String?
}
```

`npx prisma contract emit` reads only the contract file that a config file names. Add a second config file, `intermediate.config.ts`, next to `intermediate.prisma`. Run `npx prisma contract emit --config intermediate.config.ts` from the migration directory, because paths in a config file are relative to where you run the command. It writes `intermediate.json` and `intermediate.d.ts` next to `intermediate.prisma`.

```ts title="intermediate.config.ts"
import { definePrismaConfig } from 'prisma/config';
import { defineConfig as ormConfig } from '@prisma/orm-postgres/config';
export default definePrismaConfig({ orm: ormConfig({ contract: './intermediate.prisma' }) });
```

```text title="migrations/app/20260708T0900_replace_is_admin/"
├── intermediate.config.ts
├── intermediate.d.ts
├── intermediate.json
├── intermediate.prisma
├── migration.json
├── migration.ts
└── ops.json
```

In `migration.ts`, import the intermediate contract and build `db` from it. Pass the same contract to `dataTransform`. If the two differ, `node migration.ts` fails with an error whose `code` is `MIGRATION.DATA_TRANSFORM_CONTRACT_MISMATCH`. These lines replace `endContract`, `db`, and the `operations` getter in the example above:

```ts title="migration.ts (what changes)"
import type { Contract as Mid } from './intermediate';
import midContractJson from './intermediate.json' with { type: 'json' };
const midContract = new PostgresContractSerializer().deserializeContract(midContractJson);
const db = sql<Mid>({
  context: createExecutionContext({ contract: midContract, stack }),
  rawCodecInferer: stack.adapter.rawCodecInferer,
});
override get operations() {
  return [
    this.addColumn({ schema: 'public', table: 'user', column: col('role', 'text', { codecRef: { codecId: 'pg/text@1' } }) }),
    this.dataTransform(midContract, 'backfill-user-role', {
      check: () => db.public.user.select('id').where((f, fns) => fns.eq(f.role, null)).limit(1),
      run: [
        () => db.public.user.update({ role: 'admin' }).where((f, fns) => fns.eq(f.isAdmin, true)),
        () => db.public.user.update({ role: 'member' }).where((f, fns) => fns.eq(f.role, null)),
      ],
    }),
    this.setNotNull({ schema: 'public', table: 'user', column: 'role' }),
    this.dropColumn({ schema: 'public', table: 'user', column: 'isAdmin' }),
  ];
}
```

Type a transform against the end contract when it writes only columns the end contract has and reads only columns it keeps. Use an intermediate contract when it reads a column the migration removes or renames. The alternative is two migrations: the first adds and backfills `role`, and the second drops `isAdmin`. That costs an extra contract state, which exists only so the backfill can be written.

If `User` has a column that sets itself on every update, such as `updatedAt temporal.updatedAtString()` in the model `npx prisma orm init` writes, the backfill's `update` sets that column too. The value is the time you ran `node migration.ts`, so every row gets that time, and each recompile writes a new one into `ops.json`. In `intermediate.prisma`, declare the column as a plain `TimestamptzString`, and the backfill leaves it unchanged.

## Raw SQL [#escape-hatch-raw-sql]

For a statement the operation factories don't cover (such as `CREATE INDEX CONCURRENTLY` or a vendor-specific statement), use `rawSql` from `@prisma/orm-postgres/migration`, and give it a precheck and a postcheck if you can:

```ts
rawSql({
  id: 'extension.pgcrypto',
  label: 'Enable extension "pgcrypto"',
  operationClass: 'additive',
  target: { id: 'postgres' },
  precheck: [
    { description: 'not yet enabled', sql: "SELECT NOT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'pgcrypto')" },
  ],
  execute: [{ description: 'enable it', sql: 'CREATE EXTENSION IF NOT EXISTS pgcrypto' }],
  postcheck: [
    { description: 'now enabled', sql: "SELECT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'pgcrypto')" },
  ],
}),
```

The `precheck` and `postcheck` arrays can be empty, but the runner skips an operation only when its postchecks already pass, and stops when a precheck fails. See [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) for what that means on a failed run. If you write the same `rawSql` twice, move it into a function.

## The same pattern on MongoDB

On MongoDB, you import `dataTransform` from `@prisma/orm-mongo/target/migration`, and `check` puts its query in `{ source }`. It compiles to a precheck, a `run` step, and a postcheck. Hand-written MongoDB transforms build their queries from command objects such as `AggregateCommand` and `RawUpdateManyCommand`, not the typed query builder, because the runner cannot read the builder's update commands back from `ops.json`:

```ts title="migration.ts (MongoDB, excerpt)"
import { dataTransform, setValidation } from '@prisma/orm-mongo/target/migration';

override get operations() {
  const storageHash = this.endContract.storage.storageHash;
  const productsValidator = this.endContract.collection.products.validator;
  return [
    setValidation('products', productsValidator.jsonSchema, {
      validationLevel: productsValidator.validationLevel,
      validationAction: productsValidator.validationAction,
    }),
    dataTransform('backfill-product-status', {
      check: { source: () => existingProductsWithoutStatus(storageHash) },
      run: () => backfillRun(storageHash),
    }),
  ];
}
```

The full working migration, including the two functions that build its queries, is in the Prisma ORM repo's [retail-store example](https://github.com/prisma/orm/blob/main/examples/retail-store/migrations/app/20260513T0508_backfill_product_status/migration.ts).

## Starting from a blank migration

Sometimes you want a data-only migration, or you'd rather write the whole thing by hand. `migration new` writes a migration directory with a `migration.ts` that has no operations, an empty `ops.json`, and a `migration.json` that already has a `migrationHash`:

```npm
npx prisma migration new --name backfill_scores
```

If your contract has not changed since the last migration, that command fails with an error whose `code` is `MIGRATION.NO_CHANGES`. For a data-only migration, pass the `to` hash from your latest migration's `migration.json`: `npx prisma migration new --name backfill_scores --from <hash>`. Then write your operations in the generated `migration.ts` and recompile it the same way: `node migration.ts`.

## Editing checklist

1. Edit `migration.ts`, never `ops.json`.
2. Recompile: `node <migration-dir>/migration.ts`.
3. Review the diff of `ops.json`, because that's what will run.
4. Verify: `npx prisma migration check`.
5. Commit `migration.ts`, `ops.json`, and `migration.json` together.

:::note[What's early]

Hand-written MongoDB data transforms cannot use the typed query builder for updates, because the runner cannot read those commands back from `ops.json`. Nothing checks that `ops.json` still matches `migration.ts`, so recompile after every edit.

:::
