To apply your migrations to a database, run `npx prisma db migrate`. It is the Prisma ORM 8 command that replaces `prisma migrate deploy`:

```npm
npx prisma db migrate
```

A database that Prisma ORM migrates holds a **marker**, the record in the database of which contract state it currently matches. On PostgreSQL, the marker is a row in the `prisma_contract.marker` table. A contract state is one version of your contract, the `contract.prisma` file that replaced `schema.prisma`. `db migrate` reads the marker, then applies each migration between that state and the contract you last emitted. You emit the contract with `npx prisma contract emit`, which writes `contract.json` and `contract.d.ts` and which you run after every change to the contract. The `npx prisma migration status` and `npx prisma migration log` commands read the database but never change it.

By default, the connection comes from `db.connection` in `prisma.config.ts`. Pass `--db` to override it:

```npm
npx prisma db migrate --db $DATABASE_URL
```

A successful run reports what it applied and the marker it left behind:

```text
✔ Applied 1 migration(s) (3 operation(s)) across 1 contract space(s)

App space
├─ Add column "displayName" to "user"
├─ Data transform: backfill-user-displayName
├─ ⚠ Set NOT NULL on "user"."displayName"
└─ marker e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63

⚠ This migration contains destructive operations that may cause data loss.
```

`App space` is your app's contract space. A contract space is a separate migration history: one for your app, and one for each database extension that ships its own migrations. See [Extension spaces](#extension-spaces). A `⚠` in front of an operation marks it as destructive.

## Check before, preview, then apply

On a shared database, run these three commands in order:

```npm
# 1. Where is the database, what's pending?
npx prisma migration status --db $DATABASE_URL

# 2. Which migrations would run?
npx prisma db migrate --show --db $DATABASE_URL

# 3. Run it.
npx prisma db migrate --db $DATABASE_URL
```

`migration status` draws your migration history and marks each migration as applied or pending:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  1 ops  ⧗ pending
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6  2 ops  ✓ applied
○   ∅
```

Each `○` line is a contract state, shown by the first 7 characters of its hash. A hash is an identifier computed from the contract, 64 hexadecimal characters long. Commands accept any prefix of 6 or more characters that matches one hash. The labels on the right say what points at each state:

- `@contract` is the contract you last emitted.
- `@db` is where the database's marker is.
- `(db)` is the [ref](/orm/migrations/the-migration-graph#name-important-states-with-refs) named `db`. A ref is a name for a contract state, stored as a file in `migrations/app/refs/`. It is tracked separately from `@db`, so the two can be on different states. They match here, as they do after `npx prisma db migrate --advance-ref db`, which moves the `db` ref to the state it applied.

When migrations are pending, `migration status` also suggests a `db migrate --to` command with the first 12 characters of the target hash. Step 3 leaves out `--to` because plain `db migrate` targets the contract you last emitted, which is the same state here.

`db migrate --show` changes nothing. It draws the same history, marks each migration it would apply with `will run`, and lists those migrations in the order they run:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  ↑ will run
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6
○   ∅

ℹ The following 1 migration will run:

  20260707T1006_add_user_phone  705b1a6 → 925198f
```

`--show` lists migrations, not SQL. To see a migration's operations, whether any is destructive, and the SQL for its table changes, run `npx prisma migration show 20260707T1006_add_user_phone` with that migration's directory name. [Reviewing what you planned](/orm/migrations/generating-a-migration#reviewing-what-you-planned) shows its output.

After applying, `npx prisma migration log --db $DATABASE_URL` prints the **ledger**, the database's own list of every migration applied to it. On PostgreSQL, the ledger is the `prisma_contract.ledger` table. The marker says where the database is now, and the ledger says how it got there:

```text
Applied at                  Migration                     Change             Ops
2026-07-07 10:05:32 +00:00  20260707T1005_init            ∅ → 705b1a6        2 ops
2026-07-07 10:09:55 +00:00  20260707T1006_add_user_phone  705b1a6 → 925198f  1 ops
```

## Choosing a target

With no `--to`, `db migrate` moves the database to the contract you last emitted. To aim somewhere else, name the target with `--to`:

```npm
npx prisma db migrate --to prod --db $DATABASE_URL
```

`--to` accepts a hash or a prefix of one, a ref name such as `prod`, a migration directory name, or `<dir>^` for the state before that migration. You create a ref such as `prod` with `npx prisma migration ref set`, as shown in [Name important states with refs](/orm/migrations/the-migration-graph#name-important-states-with-refs). To go back to an earlier state, you first plan a rollback migration, as described in [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery). The [`db migrate` reference](/cli/db-migrate#options) lists the other options.

## When something goes wrong

When an operation fails, `db migrate` stops and prints what failed and why:

```text
✘ [MIGRATION.RUNNER_FAILED] Operation pgvector.install-vector-extension failed during execution: create extension "vector"
  why: extension "vector" is not available
  docs: https://docs.prisma.io/docs/orm/v8/reference/error-reference/MIGRATION.RUNNER_FAILED
```

In this example, the database server does not have the `vector` extension available. Make it available on the server, then run the same `db migrate` command again. Prisma ORM 8 supports PostgreSQL and MongoDB, and SQLite is experimental, as listed in [Supported databases](/orm/supported-databases). Four things make a failure easy to recover from:

- **On PostgreSQL, a failed run leaves nothing behind.** The whole `db migrate` run, across every contract space, is one transaction. When an operation fails, everything from that run is rolled back and the database is where it was before you started. Migrations applied in *earlier* runs stay applied.
- **The error is specific.** It names the operation, the step that failed, and that step's description, which is usually enough to find the cause. Every operation has three steps: [precheck, execute, and postcheck](/orm/migrations/how-migrations-work#every-operation-checks-itself).
- **Re-running is safe.** An operation whose work is already done, by an earlier run or by hand, is skipped instead of failing. On MongoDB there is no transaction, so this skipping is what lets a partly applied run finish when you re-run it. See [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) for how to recover from a failure.
- **An unknown database state stops the run.** If the database's marker is not a contract state in your migration history, for example because another tool migrated the database, the run fails with an error whose `code` is `MIGRATION.MARKER_MISMATCH` and no operation runs. Run `npx prisma db verify` to check the database against your contract, then follow the steps in [Drift](/orm/migrations/rollbacks-and-recovery#drift-when-the-database-isnt-where-migrations-left-it). To start using `db migrate` on a database that Prisma ORM 7 migrated, follow the [upgrade guide](/guides/upgrade-prisma-orm/postgresql).

## Development vs. production

You run the same `db migrate` command everywhere. In development, you apply changes you just planned yourself. In CI and production, you apply migrations that were already planned and reviewed.

**In development**, emit the contract, plan a migration, review it, and apply it with `--advance-ref db`:

```npm
npx prisma contract emit
npx prisma migration plan --name my_change
# Review the new migration directory before you apply it.
npx prisma db migrate --advance-ref db
```

If you edit `migration.ts` during review, run `node migrations/app/<dir>/migration.ts` to recompile it before you apply or commit, as described in [Editing a migration](/orm/migrations/editing-a-migration). `--advance-ref db` moves the `db` ref to the state you just applied, so the next `migration plan` starts from there. Without it, the `db` ref stays at the older state, and the next `migration plan` starts from that older state. The full loop is on [Generating a migration](/orm/migrations/generating-a-migration#the-db-ref-skipping---from).

**In CI and production**, migrations arrive through your repository, already planned, reviewed, and merged. Commit `migration.ts`, `ops.json`, `migration.json`, and the `migrations/snapshots/<hash>/` directories that `migration.ts` imports. `migration.json` records where the migration fits in your history. Before deploying, run `npx prisma migration check`, which fails if someone edited `ops.json` or `migration.json` by hand. It does not read `migration.ts`, so it cannot tell whether you recompiled after your last edit. Its exit codes are on [Generating a migration](/orm/migrations/generating-a-migration#reviewing-what-you-planned). The deploy step is:

```npm
npx prisma migration check                        # files and history intact, no database needed
npx prisma db migrate --show --db $DATABASE_URL   # log what's about to run
npx prisma db migrate --db $DATABASE_URL
```

`db migrate` runs only `ops.json`, so no TypeScript runs when you apply. That includes the `backfill-user-displayName` data transform above, whose queries were turned into SQL in `ops.json` when you ran `migration.ts`.

On PostgreSQL, two `db migrate` runs against the same database wait for each other instead of interleaving. On MongoDB, if another `db migrate` run moves the marker while yours is running, yours fails with `Marker was modified by another process during migration execution.` The operations your run executed stay applied, but your run does not move the marker or write to the ledger. Run `npx prisma migration status` to see where the database is now, then run `npx prisma db migrate` again. Operations whose work is already done are skipped.

## Extension spaces

If your project uses a [Prisma ORM extension package](/orm/extensions/using-extensions), such as pgvector support, you'll see more than one contract space in the output. An extension package ships its own migrations, for example one that runs `CREATE EXTENSION IF NOT EXISTS vector`. `npx prisma migration plan` copies them into `migrations/<extension>/`, next to your app's `migrations/app/`. One `db migrate` run applies them all, extensions first and then your app, and reports each space separately:

```text
✔ Applied 2 migration(s) (20 operation(s)) across 2 contract space(s)

Extension space: pgvector
├─ Enable extension "vector"
└─ marker 3d2c56a2944685bd21b05bc8a8d73164397df51c014201902932fbe7e80ff1b8

App space
├─ Create table "user"
└─ ...
```

:::note[What's early]

Applying, targeting, previewing, refs, the ledger, and applying several contract spaces in one run all work today. Not built yet: a rehearsal that applies migrations to a throwaway copy of the database first, and a check at apply time that `ops.json` still matches `migration.ts`. Until then, `db migrate` runs against the real database, so preview with `--show`, rehearse on a staging database, and run `migration check` in CI to catch a hand-edited `ops.json`.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Check migration status against staging and apply whatever is pending."
- "List what `db migrate --to prod` would run, then run `migration show` on each migration and summarize the destructive operations."
- "Apply the pending migrations and advance the `db` ref."
