To apply your migrations to a database, run `npx prisma db migrate`. It replaces Prisma ORM 7's `prisma migrate deploy`, as the [command table](/orm/coming-from-prisma-orm-7#commands) shows. It works on the [supported databases](/orm/supported-databases), PostgreSQL and MongoDB, with SQLite still experimental.

```npm
npx prisma db migrate
```

Your contract, the `contract.prisma` file that replaced `schema.prisma`, describes your models. After every change to it, run `npx prisma contract emit`, which replaces `prisma generate`. Each version of your contract is a **contract state**, named by a hash computed from the contract. The database stores a [**marker**](/orm/migrations/the-migration-graph#terms-used-on-this-page), the record of which contract state it currently matches. `db migrate` reads the marker, then applies each migration between that state and the contract you last emitted.

Commands that connect to a database use `db.connection` in `prisma.config.ts`, for example `db: { connection: process.env["DATABASE_URL"]! }`, as shown in [The data contract](/orm/contract-authoring/the-data-contract). The `--db` flag is optional. Pass it to connect to a different database instead, such as production with `--db "$PRODUCTION_DATABASE_URL"`.

A **contract space** is one migration history. Your app has one, and so does each [Prisma ORM extension package](#extension-spaces) that ships its own migrations. A successful run reports, for each contract space, what it applied and the marker it left behind:

```text
✔ Applied 1 migration(s) (3 operation(s)) across 1 contract space(s)

App space
├─ Add column "displayName" to "user"
├─ Data transform: backfill-user-displayName
├─ ⚠ Set NOT NULL on "user"."displayName"
└─ marker e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63

⚠ This migration contains destructive operations that may cause data loss.
```

Each `├─` line under `App space` is an operation, one step of one of your app's migrations. A data transform is an operation that changes existing rows, here filling in `displayName`. A `⚠` marks a [destructive](/orm/migrations/how-migrations-work#every-operation-checks-itself) operation, one that removes or changes something that already exists. Setting `NOT NULL` on an existing column counts, so it gets the data-loss warning even though it deletes no rows. `db migrate` runs destructive operations without asking. To catch them before they run, review the migration with `npx prisma migration show` and its directory name, which prints the same warning.

## Check before, preview, then apply

Before you apply migrations to staging or production, run these three commands in order:

```npm
# 1. Are the migration files and history intact? Needs no database.
npx prisma migration check

# 2. Which migrations would run?
npx prisma db migrate --show --db "$PRODUCTION_DATABASE_URL"

# 3. Run them.
npx prisma db migrate --db "$PRODUCTION_DATABASE_URL"
```

To see which contract state a database is at, and which migrations are still pending, run `npx prisma migration status`. It reads the database but never changes it. It draws your migration history and marks each migration as applied or pending:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  1 ops  ⧗ pending
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6  2 ops  ✓ applied
○   ∅
```

Read it from the bottom up. `∅` is an empty database, each `○` line is a contract state shown by the first 7 characters of its hash, and each `│↑` line is a migration from the state below it to the state above it. Commands accept any prefix of 6 or more characters that matches one hash. The labels on the right say what points at each state:

- `@contract` is the contract you last emitted.
- `@db` is the contract state that the marker in the connected database records.
- `(db)` is the [ref](/orm/migrations/the-migration-graph#name-important-states-with-refs) named `db`, a name for a contract state stored as a file in `migrations/app/refs/`. `npx prisma db migrate --advance-ref db` moves it to the state it applied, as [Development vs. production](#development-vs-production) shows. So `@db` and `(db)` can point at different states, for example when you check a production database that you apply without that flag.

When migrations are pending, `migration status` also prints a `db migrate --to <hash>` command to run. Here that hash is the `@contract` state, which plain `npx prisma db migrate` also targets, so the three steps above leave out `--to`.

`db migrate --show` changes nothing. It draws the same history, marks each migration it would apply with `will run`, and lists those migrations in the order they run:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  ↑ will run
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6
○   ∅

ℹ The following 1 migration will run:

  20260707T1006_add_user_phone  705b1a6 → 925198f
```

`--show` lists migrations, not SQL. To see a migration's operations, whether any is destructive, and the SQL for its table changes, run `npx prisma migration show 20260707T1006_add_user_phone` with that migration's directory name. [Reviewing what you planned](/orm/migrations/generating-a-migration#reviewing-what-you-planned) shows its output.

After applying, `npx prisma migration log --db "$PRODUCTION_DATABASE_URL"` prints the **ledger**, the database's own list of every migration applied to it. Like `migration status`, it never changes the database:

```text
Applied at                  Migration                     Change             Ops
2026-07-07 10:05:32 +00:00  20260707T1005_init            ∅ → 705b1a6        2 ops
2026-07-07 10:09:55 +00:00  20260707T1006_add_user_phone  705b1a6 → 925198f  1 ops
```

## Choosing a target

With no `--to`, `db migrate` moves the database to the contract you last emitted. To stop at a different contract state, name it with `--to`. Here `prod` is a ref, so the command applies migrations up to the state that `prod` names, not up to your latest contract:

```npm
npx prisma db migrate --to prod --db "$PRODUCTION_DATABASE_URL"
```

`--to` accepts any of these:

- A hash, or a prefix of one.
- A ref name, such as `prod`.
- A migration directory name. The target is the state that migration ends at.
- `<dir>^`, a migration directory name with `^` added. The target is the state that migration starts from.

`npx prisma migration ref set prod 20260707T1006_add_user_phone` points `prod` at the state after that migration, as [Name important states with refs](/orm/migrations/the-migration-graph#name-important-states-with-refs) shows. To go back to an earlier state, first plan a rollback migration, as described in [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery). If no migrations lead from the database's current state to the one you name, the run fails with an error whose `code` is `MIGRATION.PATH_UNREACHABLE`. The [`db migrate` reference](/cli/db-migrate#options) lists the other options.

## When something goes wrong

When an operation fails, `db migrate` stops and prints what failed and why:

```text
✘ [MIGRATION.RUNNER_FAILED] Operation pgvector.install-vector-extension failed during execution: create extension "vector"
  why: extension "vector" is not available
  docs: https://docs.prisma.io/docs/orm/v8/reference/error-reference/MIGRATION.RUNNER_FAILED
```

Here, an operation from the pgvector [extension package](#extension-spaces) failed because the `vector` PostgreSQL extension is not available on the database server. Install it on the server, or enable it in your database host's settings, then run the same `db migrate` command again. Three things make a failure easy to recover from:

- **On PostgreSQL, a failed run leaves nothing behind.** The whole `db migrate` run, across every contract space, is one transaction. When an operation fails, everything from that run is rolled back and the database is where it was before you started. Migrations applied in *earlier* runs stay applied.
- **The error is specific.** It names the operation, the step that failed, and why. That step is either the SQL statement or one of the [checks that run before and after it](/orm/migrations/how-migrations-work#every-operation-checks-itself).
- **Re-running is safe.** `db migrate` skips each operation whose change is already in the database, whether an earlier run made it or you made it by hand. On MongoDB, a `db migrate` run is not wrapped in a transaction, so operations that finished before a failure stay in the database, and a re-run skips them and continues. [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) covers other ways to recover.

`db migrate` also refuses to start when the database's marker points at a contract state that none of your migrations starts or ends at. It fails with an error whose `code` is `MIGRATION.MARKER_MISMATCH`, and no operation runs. `npx prisma db update`, which makes a development database match your contract without a migration, can leave the marker at such a state. To fix that, write a migration that ends there with `npx prisma migration plan --from <newest-migration-dir> --name <name>`, as [Drift](/orm/migrations/rollbacks-and-recovery#drift-when-the-database-isnt-where-migrations-left-it) shows. Changing tables by hand does not move the marker, so it does not cause this error.

A database that Prisma ORM 7 migrated has no marker. To adopt it, make your contract match its tables, then run `npx prisma db sign`, which checks the tables against your contract and then writes the marker. If no migration ends at the signed state yet, `db migrate` fails with the same `MIGRATION.MARKER_MISMATCH` error. Run `npx prisma migration plan --name baseline` next, which writes a baseline migration that ends at that state. So the order is `db sign`, then `migration plan`, then `db migrate`, and the [upgrade guide](/guides/upgrade-prisma-orm/postgresql) shows each step.

## Development vs. production

You run the same `db migrate` command everywhere. In development, you apply changes you just planned yourself. In CI and production, you apply migrations that were already planned and reviewed.

**In development**, emit the contract, plan a migration, review it, and apply it with `--advance-ref db`:

```npm
npx prisma contract emit
npx prisma migration plan --name my_change
# Review the new migration directory before you apply it.
npx prisma db migrate --advance-ref db
```

`migration plan` writes `migration.ts`, the TypeScript file you review and can edit, and `ops.json`, the operations `db migrate` runs. If you edit `migration.ts`, recompile it by running `node migrations/app/<dir>/migration.ts`, which rewrites `ops.json` from your edit, as described in [Editing a migration](/orm/migrations/editing-a-migration). The Prisma ORM CLI needs Node.js 22.18 or later, and those versions run `migration.ts` directly. `--advance-ref db` moves the `db` ref to the state you just applied, so the next `migration plan` plans from that state to your contract. Without it, the next migration repeats the changes of the one you already applied. If you forgot the flag, run `npx prisma migration ref set db <dir>` with the directory name of the migration you applied. The full loop is on [Generating a migration](/orm/migrations/generating-a-migration#the-db-ref-skipping---from).

**In CI and production**, migrations arrive through your repository, already planned, reviewed, and merged. With each migration, commit its directory, any new directories under `migrations/snapshots/`, and `contract.prisma`, `contract.json`, and `contract.d.ts`. Deploy with the three commands in [Check before, preview, then apply](#check-before-preview-then-apply). `migration check` fails if someone edited `ops.json` or [`migration.json`](/orm/migrations/how-migrations-work#migrationjson-the-history-marker) by hand, but it does not catch a `migration.ts` that you edited without recompiling. Its exit codes are on [Generating a migration](/orm/migrations/generating-a-migration#reviewing-what-you-planned). A data transform such as `backfill-user-displayName` still runs when you apply, because recompiling turned its queries into SQL in `ops.json`.

On PostgreSQL, when two `db migrate` runs start against the same database, one waits for the other to finish. On MongoDB, if another `db migrate` run moves the marker while yours is running, yours fails with `Marker was modified by another process during migration execution.` Run `npx prisma migration status` to see which contract state the database is at now, then run `npx prisma db migrate` again.

## Extension spaces

If your project uses a [Prisma ORM extension package](/orm/extensions/using-extensions), such as pgvector support, you'll see more than one contract space in the output. The package ships its own migrations, for example one that installs the `vector` PostgreSQL extension. `migration plan` copies them into `migrations/<space>/`, such as `migrations/pgvector/`, and `db migrate` fails without that directory, so commit it. One `db migrate` run applies every space, extension packages first and then your app, and reports each space separately. `--to` applies only to your app, and each extension space always moves to the newest state its package ships:

```text
✔ Applied 2 migration(s) (20 operation(s)) across 2 contract space(s)

Extension space: pgvector
├─ Enable extension "vector"
└─ marker 3d2c56a2944685bd21b05bc8a8d73164397df51c014201902932fbe7e80ff1b8

App space
├─ Create table "user"
└─ ...
```

:::note[What's early]

Applying, targeting, previewing, refs, the ledger, and applying several contract spaces in one run all work today. Not built yet: a rehearsal that applies migrations to a throwaway copy of the database first, and a check at apply time that `ops.json` still matches `migration.ts`. Until then, `db migrate` runs against the real database, so preview with `--show`, rehearse on a staging database, and run `migration check` in CI to catch a hand-edited `ops.json`.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Check migration status against staging and apply whatever is pending."
- "List what `db migrate --to prod` would run, then run `migration show` on each migration and summarize the destructive operations."
- "Apply the pending migrations and advance the `db` ref."
