Applying is the one step that changes a database, and it is a single command:

```npm
npx prisma db migrate
```

The command is `db migrate`, not `migration apply`, because the `migration ...` commands never change a database. `db migrate` reads the database's **marker**, the record in the database of which contract state it currently matches. A contract state is one version of your contract, the `contract.prisma` file that replaced `schema.prisma`. `db migrate` then finds a path through your [migration history](/orm/migrations/the-migration-graph) to the target and applies each migration on that path, running every operation's [precheck, execute, and postcheck](/orm/migrations/how-migrations-work#every-operation-checks-itself) steps.

By default, the connection comes from `db.connection` in `prisma.config.ts`. Pass `--db` to override it:

```npm
npx prisma db migrate --db $DATABASE_URL
```

A successful run reports what it applied and the marker it left behind:

```text
✔ Applied 1 migration(s) (3 operation(s)) across 1 contract space(s)

App space
  ├─ Add column "displayName" to "user"
  ├─ Data transform: backfill-user-displayName
  ├─ Set NOT NULL on "user"."displayName"
  └─ marker e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63

⚠ This migration contains destructive operations that may cause data loss.

Next: prisma migration status
```

`App space` is your app's contract space. A contract space is a separate migration history: one for your app, and one for each database extension that ships its own migrations. See [Extension spaces](#extension-spaces).

## Check before, preview, then apply

When working on shared databases, it helps to always follow these three steps:

```npm
# 1. Where is the database, what's pending?
npx prisma migration status --db $DATABASE_URL

# 2. What exactly would run?
npx prisma db migrate --show --db $DATABASE_URL

# 3. Run it.
npx prisma db migrate --db $DATABASE_URL
```

`migration status` draws your migration history and marks each migration as applied or pending:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  1 ops  ⧗ pending
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6  2 ops  ✓ applied
○   ∅

1 pending — run `prisma db migrate --to 925198f3cc27`
```

Read the labels on the right. `@db` is the database's marker, and `@contract` is your contract as of the last `npx prisma contract emit`. `(db)` is the [ref](/orm/migrations/the-migration-graph#name-important-states-with-refs) named `db`, which points at the same contract state. A ref is a name for a contract state, stored as a file in `migrations/app/refs/`.

`db migrate --show` is a read-only preview. It draws your migration history, marks each migration on the path with `will run`, and lists those migrations in the order they run:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  ↑ will run
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6
○   ∅

The following 1 migration will run:
  20260707T1006_add_user_phone  705b1a6 → 925198f
```

After applying, `migration log` prints the **ledger**, the database's own list of every migration applied to it:

```text
 Applied at                   Migration                      Change                Ops
──────────────────────────── ────────────────────────────── ─────────────────── ───────
 2026-07-07 10:05:32 +00:00   20260707T1005_init             ∅ → 705b1a6         2 ops
 2026-07-07 10:09:55 +00:00   20260707T1006_add_user_phone   705b1a6 → 925198f   1 ops
```

## Choosing a target

With no `--to`, `db migrate` moves the database to your contract as of the last `npx prisma contract emit`. To aim somewhere else, name the target with `--to`:

```npm
npx prisma db migrate --to prod --db $DATABASE_URL
```

`db migrate` always moves toward one target, so a branched migration history does not stop it. When more than one path leads to the target, it picks one, and `db migrate --show` prints the path it will take. The [`db migrate` reference](/cli/db-migrate#options) lists its other options.

## When something goes wrong

When an operation fails, the runner stops and prints what failed, why, and how to fix it:

```text
✖ Operation pgvector.install-vector-extension failed during execution: create extension "vector" (MIGRATION.RUNNER_FAILED)
  Why: extension "vector" is not available
  Fix: Fix the issue and re-run `prisma db migrate --to <contract>` — previously applied migrations are preserved.
```

Four things make a failure easy to recover from:

- **On PostgreSQL, a failed run leaves nothing behind.** The whole `db migrate` run, across every contract space, is one transaction. When an operation fails, everything from that run is rolled back and the database is where it was before you started. Migrations applied in *earlier* runs are untouched, which is what "previously applied migrations are preserved" means.
- **The error is specific.** It names the operation, the step that failed (precheck, execute, or postcheck), and that step's description, which is usually enough to find the cause.
- **Re-running is safe.** Before it runs an operation, the runner evaluates the operation's postcheck and skips the operation if the postcheck already holds. An operation whose work is already done, by an earlier run or by hand, is skipped instead of failing. On MongoDB the runner uses no transaction, so this check is what lets a partly applied run finish when you re-run it. See [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) for how to recover from a failure.
- **An unknown database state stops the run.** Before it runs any operation, `db migrate` checks that the database's marker is a contract state in your migration history. If it is not, for example because another tool migrated the database, the run fails with an error whose `code` is `MIGRATION.MARKER_MISMATCH` and no operation runs.

## Development vs. production

The commands are the same everywhere: what changes is where the files come from and who runs them.

**In development**, you plan, edit, and apply immediately. Add `--advance-ref db` so the next [`migration plan`](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) starts from what you just applied:

```npm
npx prisma migration plan --name my_change && npx prisma db migrate --advance-ref db
```

**In CI and production**, migrations arrive via your repo, already planned, reviewed, and merged. That's why the [editing rule](/orm/migrations/editing-a-migration) matters: commit `migration.ts` and `ops.json` together. Run `migration check` before deployment to catch an `ops.json` or `migration.json` that was edited by hand. It does not read `migration.ts`, so it cannot tell whether you ran `node migration.ts` after your last edit. See [Generating a migration](/orm/migrations/generating-a-migration#reviewing-what-you-planned) for its exit codes. The deploy step is:

```npm
npx prisma migration check          # files intact, graph well-formed (offline)
npx prisma db migrate --show --db $DATABASE_URL   # log what's about to run
npx prisma db migrate --db $DATABASE_URL
```

The runner executes only `ops.json`, which is plain data. Your `migration.ts` files, and any TypeScript they import, are never executed with production credentials.

On PostgreSQL, concurrent deploys are safe: the whole run is one transaction that holds an advisory lock, so two `db migrate` runs take turns instead of interleaving. On MongoDB there is no transaction. After a contract space's operations run, the runner checks the database against the contract and then moves the marker with a compare-and-swap. If another run moved the marker first, this run fails with `Marker was modified by another process during migration execution.`

## Extension spaces

If your project uses [database extensions](/orm/extensions/using-extensions), such as pgvector, you'll see more than one contract space in the output. Extensions ship their own migrations, for example one that runs `CREATE EXTENSION IF NOT EXISTS vector`. They are stored in `migrations/<extension>/`, next to your app's `migrations/app/`. One `db migrate` run applies them all, extensions first and then your app, and reports each space separately:

```text
✔ Applied 2 migration(s) (20 operation(s)) across 2 contract space(s)

Extension space: pgvector
  ├─ Enable extension "vector"
  └─ marker 3d2c56a2944685bd21b05bc8a8d73164397df51c014201902932fbe7e80ff1b8

App space
  ├─ Create table "user"
  └─ ...
```

:::note[What's early]

Apply, targeting, preview, refs, the ledger, and multi-space runs all work today. Not built yet: a shadow-database rehearsal, and an apply-time check that `ops.json` still matches `migration.ts`. Until then, `db migrate` runs against the real target, so preview with `--show`, rehearse on a staging database, and run `migration check` in CI to catch a hand-edited `ops.json`.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Check migration status against staging and apply whatever is pending."
- "Preview what `db migrate --to prod` would run and summarize the destructive operations."
- "Apply the pending migrations and advance the `db` ref."
