To apply your migrations to a database, run `npx prisma db migrate`. It replaces Prisma ORM 7's `prisma migrate deploy`, as the [command table](/orm/coming-from-prisma-orm-7#commands) shows. It works on the [supported databases](/orm/supported-databases), PostgreSQL and MongoDB, with SQLite still experimental.

```npm
npx prisma db migrate
```

Your contract, the `contract.prisma` file that replaced `schema.prisma`, describes your models. After every change to it, run `npx prisma contract emit`, which replaces `prisma generate`. A **contract state** is one version of your contract, named by its hash. A database that Prisma ORM migrates holds a **marker**, the record in the database of which contract state it currently matches. `db migrate` reads the marker, then applies each migration between that state and the contract you last emitted.

The connection comes from `db.connection` in `prisma.config.ts`, for example `db: { connection: process.env["DATABASE_URL"]! }`, as shown in [The data contract](/orm/contract-authoring/the-data-contract). Pass `--db` to override it:

```npm
npx prisma db migrate --db $DATABASE_URL
```

A successful run reports what it applied and the marker it left behind:

```text
✔ Applied 1 migration(s) (3 operation(s)) across 1 contract space(s)

App space
├─ Add column "displayName" to "user"
├─ Data transform: backfill-user-displayName
├─ ⚠ Set NOT NULL on "user"."displayName"
└─ marker e6b5c2849eca8d24ff1e8e88ab2a4234db8e74c497c035cb7ce42e814f31cd63

⚠ This migration contains destructive operations that may cause data loss.
```

Each `├─` line is an operation, one step of a migration. A data transform is an operation that changes existing rows, here filling in `displayName`. `App space` is your app's contract space, a separate migration history. A Prisma ORM extension package that ships its own migrations gets a space of its own, as [Extension spaces](#extension-spaces) shows. A `⚠` marks a [destructive](/orm/migrations/how-migrations-work#every-operation-checks-itself) operation. `db migrate` runs destructive operations without asking, so catch them during review with `npx prisma migration show <dir>`, which prints the same warning before anything runs.

## Check before, preview, then apply

Before you apply migrations to staging or production, run these three commands in order:

```npm
# 1. Which contract state is the database at, and what's pending?
npx prisma migration status --db $DATABASE_URL

# 2. Which migrations would run?
npx prisma db migrate --show --db $DATABASE_URL

# 3. Run it.
npx prisma db migrate --db $DATABASE_URL
```

`migration status` reads the database but never changes it. It draws your migration history and marks each migration as applied or pending:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  1 ops  ⧗ pending
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6  2 ops  ✓ applied
○   ∅
```

Read it from the bottom up. `∅` is an empty database, each `○` line is a contract state shown by the first 7 characters of its hash, and each `│↑` line is a migration from the state below it to the state above it. Commands accept any prefix of 6 or more characters that matches one hash. The labels on the right say what points at each state:

- `@contract` is the contract you last emitted.
- `@db` is the contract state that the marker in the connected database records.
- `(db)` is the [ref](/orm/migrations/the-migration-graph#name-important-states-with-refs) named `db`. A ref is a name for a contract state, stored as a file next to your migrations. `npx prisma db migrate --advance-ref db` sets the `db` ref to the state it applied, and `migration plan` with no `--from` starts from that state. `@db` comes from the database and `(db)` comes from a file, so the two can point at different states.

When migrations are pending, `migration status` also suggests a `db migrate --to <hash>` command. That hash is the `@contract` state, unless you passed `--to` to `migration status`, in which case it is that target. Step 3 leaves out `--to` because plain `db migrate` also targets `@contract`.

`db migrate --show` changes nothing. It draws the same history, marks each migration it would apply with `will run`, and lists those migrations in the order they run:

```text
○   925198f  @contract
│↑  20260707T1006_add_user_phone  705b1a6 → 925198f  ↑ will run
○   705b1a6  @db (db)
│↑  20260707T1005_init                  ∅ → 705b1a6
○   ∅

ℹ The following 1 migration will run:

  20260707T1006_add_user_phone  705b1a6 → 925198f
```

`--show` lists migrations, not SQL. To see a migration's operations, whether any is destructive, and the SQL for its table changes, run `npx prisma migration show 20260707T1006_add_user_phone` with that migration's directory name. [Reviewing what you planned](/orm/migrations/generating-a-migration#reviewing-what-you-planned) shows its output.

After applying, `npx prisma migration log --db $DATABASE_URL` prints the **ledger**, the database's own list of every migration applied to it. Like `migration status`, it never changes the database. The marker records which contract state the database is at now, and the ledger records how it got there:

```text
Applied at                  Migration                     Change             Ops
2026-07-07 10:05:32 +00:00  20260707T1005_init            ∅ → 705b1a6        2 ops
2026-07-07 10:09:55 +00:00  20260707T1006_add_user_phone  705b1a6 → 925198f  1 ops
```

## Choosing a target

With no `--to`, `db migrate` moves the database to the contract you last emitted. To aim somewhere else, name the target with `--to`:

```npm
npx prisma db migrate --to prod --db $DATABASE_URL
```

`--to` accepts a hash or a prefix of one, a ref name such as `prod`, a migration directory name for the state after that migration, or `<dir>^` for the state before it. You point a ref such as `prod` at a state with `npx prisma migration ref set`, as shown in [Name important states with refs](/orm/migrations/the-migration-graph#name-important-states-with-refs). To go back to an earlier state, first plan a rollback migration, as described in [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery). If no migrations lead from the database's current state to the one you name, the run fails with an error whose `code` is `MIGRATION.PATH_UNREACHABLE`. The [`db migrate` reference](/cli/db-migrate#options) lists the other options.

## When something goes wrong

When an operation fails, `db migrate` stops and prints what failed and why:

```text
✘ [MIGRATION.RUNNER_FAILED] Operation pgvector.install-vector-extension failed during execution: create extension "vector"
  why: extension "vector" is not available
  docs: https://docs.prisma.io/docs/orm/v8/reference/error-reference/MIGRATION.RUNNER_FAILED
```

In this example, the database server does not have the `vector` PostgreSQL extension available. Make it available on the server, then run the same `db migrate` command again. Four things make a failure easy to recover from:

- **On PostgreSQL, a failed run leaves nothing behind.** The whole `db migrate` run, across every contract space, is one transaction. When an operation fails, everything from that run is rolled back and the database is where it was before you started. Migrations applied in *earlier* runs stay applied.
- **The error is specific.** It names the operation, the check or statement that failed, and why, which is usually enough to find the cause.
- **Re-running is safe.** Before each operation, `db migrate` checks whether its work is already done, by an earlier run or by hand, and skips the operation if it is. On MongoDB there is no transaction, so this skipping is what lets a partly applied run finish when you re-run it. See [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) for how to recover from a failure.
- **An unknown database state stops the run.** If the marker records a contract state that no migration in your history produces, the run fails with an error whose `code` is `MIGRATION.MARKER_MISMATCH` and no operation runs. This happens after `npx prisma db update`, which writes the marker for your contract without a migration. Changing tables by hand does not move the marker. Run `npx prisma db verify` to check the database against your contract, then follow the steps in [Drift](/orm/migrations/rollbacks-and-recovery#drift-when-the-database-isnt-where-migrations-left-it).

A database that Prisma ORM 7 migrated has your tables and a `_prisma_migrations` table, but no marker. `db migrate` treats it as an empty database, so it starts from your first migration and skips each operation whose work is already done, such as creating a table that exists. Give the database a marker first instead: once your contract matches its tables, run `npx prisma db sign`, as the [upgrade guide](/guides/upgrade-prisma-orm/postgresql) shows.

## Development vs. production

You run the same `db migrate` command everywhere. In development, you apply changes you just planned yourself. In CI and production, you apply migrations that were already planned and reviewed.

**In development**, emit the contract, plan a migration, review it, and apply it with `--advance-ref db`:

```npm
npx prisma contract emit
npx prisma migration plan --name my_change
# Review the new migration directory before you apply it.
npx prisma db migrate --advance-ref db
```

`migration plan` writes `migration.ts`, the TypeScript file you review and can edit, and `ops.json`, the operations `db migrate` runs. If you edit `migration.ts`, run `node migrations/app/<dir>/migration.ts` to recompile it, which rewrites `ops.json` from your edit, as described in [Editing a migration](/orm/migrations/editing-a-migration). `--advance-ref db` moves the `db` ref to the state you just applied, so the next `migration plan` starts from there. Without it, the next `migration plan` starts from the older state, and the new migration repeats the changes of the one you already applied. The full loop is on [Generating a migration](/orm/migrations/generating-a-migration#the-db-ref-skipping---from).

**In CI and production**, migrations arrive through your repository, already planned, reviewed, and merged. Commit `migration.ts`, `ops.json`, `migration.json`, the `migrations/snapshots/<hash>/` directories named in the imports at the top of `migration.ts`, and the `contract.json` and `contract.d.ts` files that `contract emit` writes. Before deploying, run `npx prisma migration check`, which fails if someone edited `ops.json` or `migration.json` by hand. It does not read `migration.ts`, so it cannot tell whether you recompiled after your last edit. Its exit codes are on [Generating a migration](/orm/migrations/generating-a-migration#reviewing-what-you-planned). `db migrate` runs only `ops.json`, so no TypeScript runs when you apply, not even the `backfill-user-displayName` data transform. The deploy step is:

```npm
npx prisma migration check                        # files and history intact, no database needed
npx prisma db migrate --show --db $DATABASE_URL   # log what's about to run
npx prisma db migrate --db $DATABASE_URL
```

On PostgreSQL, two `db migrate` runs against the same database wait for each other instead of interleaving. On MongoDB, if another `db migrate` run moves the marker while yours is running, yours fails with `Marker was modified by another process during migration execution.` The operations your run executed stay applied, but your run does not move the marker. Run `npx prisma migration status` to see which contract state the database is at now, then run `npx prisma db migrate` again, which skips operations whose work is already done.

## Extension spaces

If your project uses a [Prisma ORM extension package](/orm/extensions/using-extensions), such as pgvector support, you'll see more than one contract space in the output. The package ships its own migrations, for example one that installs the `vector` PostgreSQL extension. One `db migrate` run applies them all, extension packages first and then your app, and reports each space separately:

```text
✔ Applied 2 migration(s) (20 operation(s)) across 2 contract space(s)

Extension space: pgvector
├─ Enable extension "vector"
└─ marker 3d2c56a2944685bd21b05bc8a8d73164397df51c014201902932fbe7e80ff1b8

App space
├─ Create table "user"
└─ ...
```

:::note[What's early]

Applying, targeting, previewing, refs, the ledger, and applying several contract spaces in one run all work today. Not built yet: a rehearsal that applies migrations to a throwaway copy of the database first, and a check at apply time that `ops.json` still matches `migration.ts`. Until then, `db migrate` runs against the real database, so preview with `--show`, rehearse on a staging database, and run `migration check` in CI to catch a hand-edited `ops.json`.

:::

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Check migration status against staging and apply whatever is pending."
- "List what `db migrate --to prod` would run, then run `migration show` on each migration and summarize the destructive operations."
- "Apply the pending migrations and advance the `db` ref."
