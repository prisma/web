Say you are Alice. On your branch you add a `phone` field to your contract, the `contract.prisma` file that replaced `schema.prisma`. Your teammate Bob adds an `avatar` field on his branch, and both branches merge the same afternoon. Now your laptop, Bob's laptop, staging, and production each have a slightly different version of the database. Something has to bring them all to the merged state, without losing work or running the same change twice.

Prisma ORM 7 keeps migrations as timestamped SQL directories in one folder and applies them once each, in timestamp order. When two branches each add a migration, their timestamps interleave, and that breaks the "run once, in order" rule. Prisma ORM 8 avoids this with a different approach: the migration graph.

## When this matters

You can build a whole app without thinking about the graph. You need to understand it when any of these happen:

- Two people, or two AI agents, change the contract on separate branches and merge.
- You need to roll a database back to an earlier contract state and then forward again.
- A database is behind and has to catch up through several changes, for example after a fresh clone or on a long-lived staging database.
- You want the repo to record which contract state an environment should be at, so reviewers can see it.

## The short version

Each migration records two versions of your contract, called contract states: the one it starts from and the one it ends at. A branch, a merge, or a rollback is one more migration between two contract states.

:::tip[You probably need only these five commands]

After you change the contract, run `npx prisma contract emit`, then create a migration with `npx prisma migration plan --name <name>`, as [Generating a migration](/orm/migrations/generating-a-migration) explains. In development, apply it with `npx prisma db migrate --advance-ref db`. To see the graph, run `npx prisma migration graph`. To check where a database is and what `db migrate` would run next, run `npx prisma migration status`.

:::

## Terms [#terms-used-on-this-page]

| Term | Meaning |
| --- | --- |
| **Contract** | Your contract, the `contract.prisma` file that replaced `schema.prisma`, compiled to `contract.json`. |
| **Contract state** | One version of your contract, named by its hash. |
| **Hash** | An identifier computed from the contract. The graph output shows its first seven characters, like `789dd79`. |
| **Node** | A contract state that a migration starts or ends at. |
| **Edge** | A migration. It moves the database from one node (`from`) to another (`to`). |
| **Marker** | The record in the database of which contract state it currently matches. |
| **Ledger** | The database's own list of every migration applied to it. |
| **Ref** | A name for a contract state, like `prod`, stored as a file in `migrations/app/refs/`. |
| **Contract space** | A separate migration history. Your app's is `migrations/app/`, and each [Prisma ORM extension package](/orm/extensions/using-extensions) that ships migrations, such as pgvector support, has its own. |

## How it works

After every change to the contract, you run `npx prisma contract emit`, which replaces `prisma generate`. It writes `contract.json` and `contract.d.ts`, and you commit both. `contract.json` includes the contract's hash, and the same contract always produces the same hash.

Each migration is a directory in `migrations/app/`. There is no `migration.sql` file. The SQL a migration runs is in its `ops.json`, as [What a migration contains](/orm/migrations/how-migrations-work#what-a-migration-contains) shows. Its `migration.json` records the hash the migration starts `from` and the hash it moves the database `to`. Those two hashes link migrations together, and the timestamp in the directory name is only for people to read.

A database with a **marker** is at one contract state, the one its marker holds. A database with no marker counts as empty, so `db migrate` starts it from the first migration.

## A worked example

Here is the situation from the top of the page as a graph. Alice adds `phone`, Bob adds `avatar`, and both branches merge:

```npm
npx prisma migration graph
```

```text
○     f9a41d7  (prod)
│─╮
│↑│   20260303T1000_merge_alice      93be6c2 → f9a41d7  1 ops
│ │↑  20260303T1100_merge_bob        7e3fa7f → f9a41d7  1 ops
○ │   93be6c2
│↑│   20260302T1000_alice_add_phone  789dd79 → 93be6c2  1 ops
│ ○   7e3fa7f
│ │↑  20260302T1100_bob_add_avatar   789dd79 → 7e3fa7f  1 ops
│─╯
○     789dd79
│↑    20260301T1000_init                   ∅ → 789dd79  1 ops
○     ∅

1 space(s), 5 contract(s), 5 migration(s)
```

Read it from the bottom up. From an empty database (`∅`), `init` produces contract state `789dd79`. Alice and Bob both start from `789dd79`: her migration produces `93be6c2`, and his produces `7e3fa7f`. `1 ops` is the number of operations, the steps listed in the migration's `ops.json`. This is a diamond: one start, two parallel branches, and one shared end at `f9a41d7`, which the `prod` ref points at.

Alice and Bob each planned their branch migration on their own branch. After the branches merge, someone emits the merged contract with `npx prisma contract emit`. Until a migration leads to it, `npx prisma migration status` reports no migration path to the contract, and `npx prisma db migrate` fails with an error whose `code` is `MIGRATION.PATH_UNREACHABLE`. So that person plans one merge migration from the end of each branch:

```npm
npx prisma migration plan --name merge_alice --from 20260302T1000_alice_add_phone
npx prisma migration plan --name merge_bob --from 20260302T1100_bob_add_avatar
```

`merge_alice` adds Bob's `avatar` to a database that already has `phone`, and `merge_bob` adds `phone` to one that already has `avatar`. Both end at `f9a41d7`, because both are planned toward the same merged contract, and no directories were renamed to make the timestamps line up. A migration directory name as `--from` means the state after that migration. `migration plan --from` also accepts a hash or a prefix of one, a ref name, `<dir>^` for the state before a migration, or `@empty`.

## What happens when you run db migrate

`npx prisma db migrate` starts at the database's marker and runs the migrations on the path to its target. The target is the contract state that `--to` names, such as the `prod` ref. Without `--to`, the target is `contract.json`, the contract you last emitted. The marker moves to the target only after every migration on the path has run. If an operation finds the database in a state it does not expect, the run stops before that operation and names the check that failed. On PostgreSQL the whole run is one transaction, so a failed run leaves the database and its marker where they were. [When something goes wrong](/orm/migrations/applying-a-migration#when-something-goes-wrong) explains how to re-run, and [Recovery](/orm/migrations/rollbacks-and-recovery#recovery-when-a-migration-fails-partway) explains what to do next.

When more than one path leads to the target, `db migrate` takes the one with the fewest migrations. Both paths here have two, so it takes Alice's, because `alice_add_phone` has an earlier `createdAt` in its `migration.json` than `bob_add_avatar`. Preview the path with `npx prisma db migrate --show`.

If no chain of migrations leads from the marker to the target, the run fails with an error whose `code` is `MIGRATION.PATH_UNREACHABLE`. Plan the missing migration with `npx prisma migration plan --from <hash> --name <name>`, using the marker's hash, or check that `--to` names the state you meant.

## Inspecting the graph

Five read-only commands, each answering a different question:

| Question you have | Command | Needs a database? |
| --- | --- | --- |
| What does the whole graph look like? | `npx prisma migration graph` | No |
| Which migration directories exist on disk? | `npx prisma migration list` | No |
| Was a migration file edited by hand, or does a ref name a missing state? | `npx prisma migration check` | No |
| Where is my database, and what would `db migrate` run next? | `npx prisma migration status` | Yes |
| What has actually been applied, and when? | `npx prisma migration log` | Yes |

`migration log` reads the **ledger**. A rollback appears there as one more applied migration, so no history is ever deleted. Run `migration check` in CI before you deploy, and see [Reviewing what you planned](/orm/migrations/generating-a-migration#reviewing-what-you-planned) for its exit codes.

### Try it on real fixtures

The Prisma ORM repository has example graphs you can draw, including the diamond above. You need Git, Node.js 24 or later, and pnpm, which `corepack enable` sets up:

```bash
git clone https://github.com/prisma/orm && cd orm
pnpm install --frozen-lockfile && pnpm build
cd examples/prisma-8-demo
pnpm exec prisma migration graph --config ./fixtures/diamond/prisma.config.ts --legend
```

`--legend` adds a key that explains the symbols. The other examples are in `examples/prisma-8-demo/fixtures/`.

## Name important states with refs

Hashes are long and hard to remember, so name the states that matter. A **ref** is a name for a contract state, stored as a small file in `migrations/app/refs/`. You create and move refs yourself with `npx prisma migration ref set`, and you commit a ref such as `prod` like any other change:

```npm
npx prisma migration ref set prod f9a41d7
npx prisma migration ref list
npx prisma db migrate --to prod
```

`ref set` takes a full hash or a prefix of at least six characters that matches only one hash. Because the `prod` ref is committed, reviewers can see in a pull request where production should be.

Plain `npx prisma db migrate` moves the database to `contract.json`, which you commit with each contract change. `npx prisma db migrate --to prod` moves it to the state the `prod` ref names instead. Both change the database that `prisma.config.ts` connects to, or the one you pass with `--db`. To move `prod` forward, run `npx prisma migration ref set prod <hash>` and commit the ref file. [Development vs. production](/orm/migrations/applying-a-migration#development-vs-production) shows the CI deploy step.

`migration plan` never connects to a database, so it starts from the `db` ref instead of from a marker. In development, apply with `npx prisma db migrate --advance-ref db`, which sets the `db` ref to the database's contract state after it applies. If you leave the flag off, the `db` ref stays at the older state. Your next `migration plan` then starts from there, and the new migration repeats the changes of the migration you already planned. [The db ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) explains the rest.

Three reserved tokens, names that start with `@`, stand for a contract state without a ref:

- `@contract`: the contract you most recently emitted.
- `@db`: the contract state that the connected database's marker holds. It is not the `db` ref.
- `@empty`: the empty database, before any migration.

`db migrate` takes `--from` only with `--show`, which previews a run without changing anything, and there `--from` accepts all three tokens. For example, `npx prisma db migrate --show --from @contract --to prod` prints the path from your emitted contract to the `prod` ref. Of the three, `npx prisma migration plan --from` accepts only `@empty`, to plan from an empty database.

## What the graph gives you

### Parallel work without ordering conflicts

Alice and Bob each planned a migration from `789dd79` on their own branches. In a timestamp-ordered system, whoever merges second inherits a broken history. Here both migrations stay in the graph, the merge migrations join them, and every environment finds its own path to the merged state.

### History you can trust

Each migration records the contract state it starts `from`, so it does not run against a database at a different state. If the marker is not a state in your migration history, for example because `npx prisma db update` wrote a marker for a contract that no migration produced, the run stops before any operation runs. [Drift](/orm/migrations/rollbacks-and-recovery#drift-when-the-database-isnt-where-migrations-left-it) explains what to do next. This check reads only the marker, so to compare the tables with your contract, run `npx prisma db verify`.

### Rollback as a normal move

A migration can go backwards, from a later contract state to an earlier one. Rolling back is not a special mode: you plan one more migration whose `to` is an earlier state. [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) shows the commands.

### More than one shape of history

A straight line of migrations, branches that split from one contract state, and branches that join again all work with the same commands.

## Baselines

"Baseline" means three things:

- `(baseline)` in `migration plan` output means the migration starts from an empty database.
- A baseline migration is a first migration from an empty database to a contract state.
- What Prisma ORM 7 called baselining, marking an existing database as already migrated, is `npx prisma db sign` in Prisma ORM 8.

To start a migration history for a database that already has tables, run [`npx prisma db sign`](/cli/db-sign) first. It checks that the tables match your emitted contract, then writes the marker and points the `db` ref at that contract state. It also saves a copy of that contract under `migrations/snapshots/`. If the tables do not match, it writes nothing. Then run `npx prisma migration plan --name <name>`. With no migrations in `migrations/app/` yet, it writes a baseline migration to the `db` ref's state, plus a second migration with any contract change you made after signing. The baseline never runs on the signed database, because its marker is already at that state. [The automatic baseline](/orm/migrations/generating-a-migration#the-automatic-baseline) shows the commands, including how to write a baseline by hand for a deployed database. For a database that Prisma ORM 7 migrated, see [Prisma ORM 7 to 8 (PostgreSQL)](/guides/upgrade-prisma-orm/postgresql).

## Database-specific details

The graph and the commands are the same on every database Prisma ORM 8 supports: PostgreSQL and MongoDB, with SQLite experimental, as [Supported databases](/orm/supported-databases) lists. What differs is where the marker and ledger are stored.

- **PostgreSQL**: the marker is the `prisma_contract.marker` table and the ledger is the `prisma_contract.ledger` table.
- **MongoDB**: the marker and ledger are documents in a `_prisma_migrations` collection.

## Release-candidate limitations

The graph, path selection in `db migrate`, refs, the marker, and the ledger all work now. These are not built yet:

- **No squash.** You cannot yet collapse a long chain of migrations into one, including into a single baseline after the fact.
- **No split.** You cannot yet break one large migration into smaller ones after the fact.
- **`migration new` needs `--from` when there is more than one branch tip, a contract state that no migration starts from.** `npx prisma migration new` writes an empty migration for a change you write yourself, such as a data update, starting from the end of your migration history. After Alice's and Bob's branches merge but before the merge migrations exist, `93be6c2` and `7e3fa7f` are both branch tips, so `migration new` fails with an error whose `code` is `MIGRATION.AMBIGUOUS_TARGET`. Pass a prefix of the hash to start from, for example `npx prisma migration new --name backfill --from 93be6c2`. Unlike `migration plan`, its `--from` accepts only a hash prefix.

## Common tasks

| Task | Command |
| --- | --- |
| Create a migration after you change the contract | `npx prisma migration plan --name <name>` |
| Apply migrations to your development database | `npx prisma db migrate --advance-ref db` |
| See the whole graph | `npx prisma migration graph` |
| Check where a database is | `npx prisma migration status` |
| Move a database to a named state | `npx prisma db migrate --to prod` |
| Name a contract state `prod` | `npx prisma migration ref set prod <hash>` |
| List the refs you have named | `npx prisma migration ref list` |
| Plan a rollback of the migration in `<dir>` | `npx prisma migration plan --from <dir> --to <dir>^ --name <name>` |
| Apply a rollback migration you planned | `npx prisma db migrate --to <earlier-ref-or-hash>` |
| Check migration files and refs before you deploy | `npx prisma migration check` |

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Draw the migration graph for this project and explain the branches."
- "Which contract state is the `prod` ref pointing at, and is the database there yet?"
- "Two feature branches both added migrations. Draw the graph and plan the merge migrations they need."
