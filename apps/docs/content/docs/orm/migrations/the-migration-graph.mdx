Consider this situation: on your branch you add a `phone` field to your contract, the `contract.prisma` file that replaced `schema.prisma`. A teammate adds an `avatar` field on theirs, and both branches merge the same afternoon. Now your laptop, your teammate's laptop, staging, and production each have a slightly different version of the database. Something has to bring them all to the merged state, without losing work or running the same change twice.

Classic migration tools make this a complicated and time-consuming process. Migrations are kept in a single folder and run just once, in timestamp order. When multiple branches each add a migration, the timestamps interleave. This breaks the "run once in order" assumption, and someone has to spend an afternoon renaming files to force a clean line. Prisma ORM avoids this with a different approach: the migration graph.

## When this matters

You can build a whole app without thinking about the graph. However, the moment that any of the following occur and more than one line of history exists, it becomes vital:

- Two people (or two AI agents) change the contract on separate branches and merge.
- You need to roll a database back to an earlier contract state and then forward again.
- A database is behind (a fresh clone, a long-lived staging box) and has to catch up through several changes.
- You want to point an environment at an exact contract state and prove in review that it is there.

## The short version

Prisma ORM does not treat migrations as one timestamp-ordered list. Each migration records the contract state it starts from and the contract state it produces, and those links form a graph. A database moves through the graph by following migrations from its current contract state to wherever you tell it to go. Because every migration is anchored to real contract states rather than to its position in a folder, branches, merges, and rollbacks are all just paths through the same graph.

:::tip[You probably just need three commands]

Usually you won't ever touch the graph directly. To see it, run `migration graph`. To check where a database is and what is pending, run `migration status`. To move a database to a specific state, run `db migrate --to <ref>`.

:::

## Terms [#terms-used-on-this-page]

| Term | Meaning |
| --- | --- |
| **Contract** | Your contract, the `contract.prisma` file that replaced `schema.prisma`, compiled to `contract.json`. |
| **Contract state** | One version of your contract, named by its hash. |
| **Hash** | A short identifier computed from the contract, like `789dd79…`, the way a Git commit hash names an exact state of your files. |
| **Node** | A contract state in the graph, identified by its hash. |
| **Edge** | A migration. It moves the database from one node (`from`) to another (`to`). |
| **Marker** | The record in the database of which contract state it currently matches. |
| **Ref** | A name for a contract state, like `prod`, stored as a file in `migrations/app/refs/`. |

## How it works

Every time you run `prisma contract emit` after a change to the contract, it writes `contract.json` with the contract's hash. The same contract always produces the same hash. Those hashes are the **nodes** of the graph.

A migration is an **edge**: it records the contract hash it starts `from` and the hash it moves the database `to`. Nothing about a migration's place in history comes from its file name: the timestamps in directory names are for humans, and the `from` and `to` hashes inside each `migration.json` are what link migrations together.

<ConceptAnimation name="migration-graph" />

A database is always at exactly one node: its **marker** holds the hash of the contract state it currently matches. Applying a migration means walking one edge and moving the marker.

## A worked example

Here is the Alice-and-Bob situation as an actual graph. Alice adds `phone`, Bob adds `avatar`, and both branches merge:

```npm
npx prisma migration graph
```

```text
○     f9a41d7  (prod)
│─╮
│↑│   20260303T1000_merge_alice      93be6c2 → f9a41d7  1 ops
│ │↑  20260303T1100_merge_bob        7e3fa7f → f9a41d7  1 ops
○ │   93be6c2
│↑│   20260302T1000_alice_add_phone  789dd79 → 93be6c2  1 ops
│ ○   7e3fa7f
│ │↑  20260302T1100_bob_add_avatar   789dd79 → 7e3fa7f  1 ops
│─╯
○     789dd79
│↑    20260301T1000_init                   ∅ → 789dd79  1 ops
○     ∅

1 space(s), 5 contract(s), 5 migration(s)
```

Read it bottom-up. From an empty database (`∅`), `init` produces contract state `789dd79`. Alice and Bob both branch from `789dd79`: her migration produces `93be6c2`, his produces `7e3fa7f`. Each branch then has a merge migration into the combined state `f9a41d7`, which the `prod` ref points at. This is a diamond: one start, two parallel branches, one shared end.

The payoff is in the `from → to` column and the two merge edges. A database that follows Alice's branch is at `93be6c2` and reaches `f9a41d7` through `merge_alice`, while a database that follows Bob's is at `7e3fa7f` and takes `merge_bob`. Neither developer needed to know about the other's migration, and no files were renamed to make the timestamps line up.

The summary line counts contract spaces: a separate migration history for your app, and one for each [database extension](/orm/migrations/applying-a-migration#extension-spaces) that ships its own migrations.

## What happens when you run db migrate

When you run `db migrate`, the runner walks the graph for you:

1. It reads the database's **marker** to find which node the database is on now.
2. It resolves your target: the state `--to` names, such as the `prod` ref, or the contract you last emitted if you did not pass `--to`.
3. It finds a path of edges from the marker to the target.
4. It applies each edge in order, then moves the marker to the target.
5. If an operation's precheck fails, it stops before that operation runs and names the operation and the check that failed.

`db migrate` never has to choose between branch tips, because its target is always one contract state. If no chain of migrations leads from the marker to the target, it stops with an error whose `code` is `MIGRATION.PATH_UNREACHABLE`.

## Inspecting the graph

Four read-only commands, each answering a different question:

| Question you have | Command | Needs a database? |
| --- | --- | --- |
| What does the whole graph look like? | `migration graph` | No |
| Which migration directories exist on disk? | `migration list` | No |
| Where is my database, and what is pending? | `migration status` | Yes |
| What has actually been applied, and when? | `migration log` | Yes |

`migration log` reads the **ledger**, the database's own list of every migration applied to it. The runner adds to the ledger on every apply, so even a rollback shows up as history rather than as deleted history.

### Try it on real fixtures

The Prisma ORM repo ships example graphs (a diamond, a wide fan-out, converging branches, rollback chains) as ready-to-render fixtures:

```bash
git clone https://github.com/prisma/orm
cd orm && pnpm install && pnpm -w build && pnpm install
cd examples/prisma-8-demo
pnpm exec prisma migration graph --config ./fixtures/showcase/prisma.config.ts --legend
```

Swap `showcase` for `diamond`, `wide-fan`, `converging-branches`, `multi-branch`, `long-spine`, or `skip-rollback` to explore each shape.

## Name important states with refs

Raw hashes are awkward to type and impossible to remember, so name the states that matter. A **ref** is a name for a contract state, stored as a small file in `migrations/app/refs/` and committed to your repo:

```npm
npx prisma migration ref set prod f9a41d7
npx prisma migration ref list
npx prisma db migrate --to prod
```

Because refs are committed, "where production should be" is a reviewable fact in a pull request instead of tribal knowledge in someone's terminal history.

In development, add `--advance-ref db` to `db migrate` so the next `migration plan` starts from what you just applied, as [The db ref](/orm/migrations/generating-a-migration#the-db-ref-skipping---from) explains.

Three reserved tokens name a contract state without setting up a ref:

- `@contract`: the contract you most recently emitted.
- `@db`: the contract state that the connected database's marker holds.
- `@empty`: the empty database, before any migration.

Only `db migrate --show` accepts `@contract` and `@db`. `@empty` also works in `migration plan --from`.

## What the graph gives you

### Parallel work without ordering conflicts

Alice and Bob each planned a migration from `789dd79` on their own branches. In a timestamp-ordered system, whoever merges second inherits a broken history, but here both edges are in the graph and every environment finds its own path to the merged state. This matters even more when the "two developers" are two AI agents planning migrations concurrently, since neither has to know anything at all about the other.

### History you can trust

Because each edge declares its `from` state, a migration will not run against a database at a different contract state. If the marker does not match, the run stops before any operation runs, with an error that names the mismatch.

### Rollback as a normal move

An edge can point backwards, from a later contract state to an earlier one. Rolling back is not a special mode: it is planning one more migration, the destination of which is a previous state. See [Rollbacks and recovery](/orm/migrations/rollbacks-and-recovery) for more information.

### More than one shape of history

The graph accommodates whatever your workflow produces: long linear spines, wide fan-outs where many branches leave one node, diamonds that converge again, and fast-forward edges that jump several states in one hop.

## Baselines

A database that already exists can become the graph's starting node without replaying anything. When the graph is empty and the `db` ref names a contract whose snapshot is stored under `migrations/snapshots/`, one `migration plan` run writes two migrations: a baseline from nothing to the ref's contract, and the delta from there to your emitted contract.

For a deployed database you must not touch, `--from @empty` is the explicit retrofit: bring the contract back to the deployed state, emit, plan the baseline, then restore the current contract and plan the delta from it.

A baseline is never replayed against a database that already has a marker: the runner starts at the marker and applies only the edges past it.

## Database-specific details

The graph works the same on every database: same nodes, same edges, same commands. What differs is how the marker and ledger are stored.

- **PostgreSQL**: the marker is in a `prisma_contract.marker` table, and each apply runs inside a transaction that takes an advisory lock, so two runners cannot move the same database at once.
- **MongoDB**: the marker and ledger are documents in a `_prisma_migrations` collection. The marker is updated with a compare-and-swap, so an apply fails if another process changed the marker while it ran.

## Release-candidate limitations

The graph, pathfinding, refs, and the marker and ledger all work now. However, some features that you might expect have not yet been built:

- **No squash.** You cannot yet collapse a long chain of migrations into one, including into a single baseline after the fact. The chain stays as-is.
- **No split.** You cannot yet break one large migration into smaller ones after the fact.
- **Branch tips need an explicit start.** When the graph has more than one branch tip, `migration new` cannot pick its starting state and fails with an error whose `code` is `MIGRATION.AMBIGUOUS_TARGET`. Pass `--from` instead.

The graph has been designed with these in mind, but the commands have not shipped yet.

## Common tasks

| Task | Command |
| --- | --- |
| See the whole graph | `migration graph` |
| Check where a database is | `migration status` |
| Move a database to a named state | `db migrate --to prod` |
| Name a contract state `prod` | `migration ref set prod <hash>` |
| List the refs you have named | `migration ref list` |
| Apply a rollback migration you planned | `db migrate --to <earlier-ref-or-hash>` |
| Verify migration files and graph integrity | `migration check` |

## Prompt your coding agent

Projects created with `npm create prisma@latest` include the [Prisma ORM skills](/ai/tools/skills#available-skills-for-prisma-8) for your coding agent. In an existing project, run `npx prisma skills sync`. Ask your agent to:

- "Draw the migration graph for this project and explain the branches."
- "Which contract state is the `prod` ref pointing at, and is the database there yet?"
- "Two feature branches both added migrations. Check whether they conflict."
