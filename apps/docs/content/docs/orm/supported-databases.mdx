Prisma ORM 8 ships one library per database, and installing the one that matches yours brings the config, the client, contract authoring, and migrations with it. Today there are two you can build on, an experimental third, and an early preview of a fourth.

| Database | Status | Library | Install |
| --- | --- | --- | --- |
| PostgreSQL, including Prisma Postgres | Release candidate | `@prisma/orm-postgres` | `npm install @prisma/orm-postgres` |
| MongoDB | Early access | `@prisma/orm-mongo` | `npm install @prisma/orm-mongo` |
| MySQL | Early preview, migrations, reads and writes | `@prisma/orm-mysql` | `npm install @prisma/orm-mysql` |
| MariaDB | Coming soon | | |
| SQLite | Experimental | `@prisma/orm-sqlite` | `npm install @prisma/orm-sqlite` |
| Microsoft SQL Server | Coming soon | | |
| CockroachDB | Coming soon | | |

`npm create prisma@latest -- my-app` asks which database you use and installs the right library for you. See [Create a new app with PostgreSQL](/prisma-orm/quickstart/postgresql) or [Create a new app with MongoDB](/prisma-orm/quickstart/mongodb).

## What the labels mean

**Release candidate.** Install it and build with it today. Until the final release, some details of the API may still change, so code you write now may need small edits later. Each release candidate fixes bugs found in the last one. [Release status](/orm/release-status) has the dates and what `npm install` gives you.

**Early access.** The library works and you can build with it, but some of what the PostgreSQL library does is not there yet. The table below and the reference pages say what works on MongoDB, and [what is not available yet](/orm/coming-from-prisma-orm-7#not-available-yet) lists the gaps. Report what you hit on [GitHub](https://github.com/prisma/orm/issues).

**Experimental.** SQLite is published as an experimental package, [`@prisma/orm-sqlite`](https://www.prisma.io/extensions/sqlite), without a quickstart yet. `db.transaction(...)` works the same way as on PostgreSQL. The date and time types `DateTime`, `Date`, `Time` and `Duration` work as on PostgreSQL, with `as:` choosing what your code reads, such as `DateTime(as: string)` or `Date(as: temporal)`, and SQLite stores every one of them as text. A duration is stored as written, so a filter on `PT60M` does not match a row written as `PT1H`, and a `Duration` field cannot be ordered. Write durations in one form if you filter on them. A field read `as: temporal` needs a global `Temporal` in your app, such as `import 'temporal-polyfill/full/global'`, or reading it fails with [`RUNTIME.TEMPORAL_UNAVAILABLE`](/orm/reference/error-reference#RUNTIME.TEMPORAL_UNAVAILABLE). `db verify` reads a column default of `date('now')` as the current date, so it matches only a field written `Date @default(now())`. `@prisma/orm-sqlite` declares `temporal-polyfill` as a peer dependency, which npm, pnpm and bun install for you. With Yarn, or with pnpm when its `autoInstallPeers` setting is `false`, add `temporal-polyfill` to your dependencies, or the `prisma` commands fail because they cannot find it.

**Early preview.** MySQL is published as `@prisma/orm-mysql` so you can try it. Your app can read from and write to MySQL with the ORM and the SQL builder, including nested and ordered includes, through `mysql({ contract, url })` from `@prisma/orm-mysql/runtime` and `contractFromJson` from `@prisma/orm-mysql/static`, and can run raw SQL and `db.transaction(...)`. ORM `create`, `update`, `upsert` and `delete` return the rows they wrote, as on PostgreSQL. MySQL has no `RETURNING`, so the ORM writes the rows and then reads them back by their key in the same transaction. Every session runs at READ COMMITTED, so when binary logging is on it must be row-based (`binlog_format = ROW`, MySQL 8.4's default); with statement-based logging, MySQL refuses every ORM write with error 1665. The contract must list every unique index of a table the ORM upserts into. MySQL's `ON DUPLICATE KEY UPDATE` fires on any unique index, not only the one `conflictOn` names. A collision on an index the contract does not list makes `upsert` fail with `ORM.MUTATION_ROW_MISSING`, or update the row that index matched and return the `conflictOn` row unchanged. `npx prisma db verify --strict` reports unique indexes the contract does not list. `delete` reads the row first and then deletes it. Row locks such as `FOR UPDATE`, `LATERAL` joins, `RETURNING`, and skipping rows that collide with a unique constraint are refused with a message that they are not supported on MySQL yet. The `mariadb` package that runs each statement writes its values into the statement with its own escaping, so Prisma's code never puts a value into SQL. A value stays inside its quotes only while your raw SQL keeps to the [driver's environment requirements](https://github.com/prisma/orm/blob/v8.0.0-rc.23/packages/3-targets/mysql/3-driver/README.md#environment-requirements). Raw SQL must not add `NO_BACKSLASH_ESCAPES` or `ANSI_QUOTES` to `sql_mode`, or change `character_set_client` or `character_set_results` from utf8mb4. It must also keep `NO_AUTO_VALUE_ON_ZERO` in `sql_mode`, or an ORM `create` that writes 0 to an auto-increment key fails with `ORM.MUTATION_ROW_MISSING`. Put a space after a value in raw SQL when a quote, `#`, `/*` or `--` follows it. `DateTime`, `Date`, `Time` and `Duration` work as on PostgreSQL, and `storage:` chooses the column, such as `DateTime(storage: timestamp)`. A `DateTime` field refuses to write a value outside its column's range, with `RUNTIME.ENCODE_FAILED`. It drops the digits of a second that its column does not hold, so a column without fractions of a second stores a value without its milliseconds. A `datetime` column holds the years 1000 to 9999, and a `timestamp` column holds 1970-01-01T00:00:01Z to 2038-01-19T03:14:07.999999Z. A duration is stored as written, so a filter on `PT60M` does not match a row written as `PT1H`. A field read `as: temporal` needs a global `Temporal` in your app, as on SQLite. `@prisma/orm-mysql` declares `temporal-polyfill` as a peer dependency, so with Yarn, or with pnpm when its `autoInstallPeers` setting is `false`, add it to your dependencies yourself. With `defineConfig` from `@prisma/orm-mysql/config` in `prisma.config.ts`, `npx prisma contract emit`, `migration plan`, `db migrate`, `db verify` and `db sign` work against MySQL 8.4 for creating and dropping tables, columns, indexes, unique constraints and foreign keys. Any other schema change is refused with a message that it is not supported on MySQL yet. MySQL cannot roll back a schema change, so a failed migration leaves the operations that ran before the failure applied, as on MongoDB. When you run `db migrate` again, it skips each operation whose postcheck shows its change is already in the database. An operation without a postcheck runs again, and a precheck that still fails stops the run again.

**Coming soon.** There is no Prisma ORM 8 library for the database yet. Prisma ORM 7 supports it, and Prisma ORM 7 keeps receiving bug fixes and security updates for 18 months after Prisma ORM 8 reaches general availability. [How to stay on Prisma ORM 7](/orm/release-status#how-to-stay-on-prisma-orm-7) shows how to lock the version.

## What each database supports

The ORM client works the same on both databases. The lower-level query APIs follow the database's own query model.

| Feature | PostgreSQL | MongoDB |
| --- | --- | --- |
| [ORM client](/orm/reference/orm-client) | Yes | Yes |
| [SQL query builder](/orm/reference/sql-query-builder) | Yes | No |
| [Pipeline builder](/orm/reference/pipeline-builder) | No | Yes |
| [Raw queries](/orm/reference/raw-queries) | Raw SQL | Raw commands |
| [Transactions](/orm/fundamentals/transactions) | Yes | Not yet |
| [Migrations](/orm/migrations/how-migrations-work) | Yes | Yes |
| [Extensions](/orm/extensions) (pgvector, PostGIS, ParadeDB, and more) | Yes | Not yet |
| [Middleware](/orm/middleware/how-middleware-works) | Yes | Yes, except `beforeCompile` |

`db.transaction()` exists on the PostgreSQL client only, because Prisma ORM does not support MongoDB transactions yet. For multi-document writes on MongoDB, [use the MongoDB driver's session API](/orm/fundamentals/transactions#transactions-on-mongodb) alongside the client.

Middleware hooks are the same on both databases apart from `beforeCompile`, which rewrites the SQL query before it runs and so exists only on PostgreSQL. The built-in `lints` and `budgets` middleware inspect SQL and run on PostgreSQL. The `cache` middleware runs on both. See [which databases a middleware runs on](/orm/middleware/how-middleware-works#which-databases-a-middleware-runs-on).

Every extension in the [directory](https://www.prisma.io/extensions) lists the databases it targets. Today every extension that adds column types, operators, or index types targets PostgreSQL, and the only entries that list MongoDB are the database libraries and the `cache` middleware.

## Managed and hosted databases

Prisma ORM connects with a standard connection string, so any host that gives you one works.

| Provider | Database | Notes |
| --- | --- | --- |
| [Prisma Postgres](/postgres) | PostgreSQL | The default in `npm create prisma@latest`. Provisioned from the CLI, with connection pooling built in. |
| Supabase | PostgreSQL | The [Supabase extension](https://www.prisma.io/extensions/supabase) adds the auth and storage tables and role-bound clients. |
| Neon, Railway, Render, AWS RDS, Cloud SQL, self-hosted | PostgreSQL | Any PostgreSQL server. Extensions such as pgvector and PostGIS need the server-side extension to be installable, which most managed providers include. |
| MongoDB Atlas, self-hosted MongoDB | MongoDB | Any MongoDB deployment reachable with a `mongodb://` or `mongodb+srv://` URL. |

Need a database? [`npx create-db`](/postgres/npx-create-db) creates a temporary [Prisma Postgres](/postgres) database in seconds, without signing up. To host the app, you can deploy it on [Prisma Compute](/compute).

A `create-db` database is deleted after 24 hours unless you claim it, which needs a Prisma account. The Prisma CLI deploys apps to Prisma Compute with [Prisma Composer](/composer). Prisma Compute does not currently support WebSocket servers and has no multi-region deployments ([limitations](/compute/limitations)). Prisma Postgres has no point-in-time recovery yet; it is coming in November 2026 ([backups](/postgres/database/backups)).

## Databases that are coming

MySQL has an early preview that runs migrations and reads and writes data. MariaDB, Microsoft SQL Server, and CockroachDB have no Prisma ORM 8 library yet. To stay on a supported path for those databases today, use [Prisma ORM 7](/orm/v7/reference/supported-databases), which supports all of them.

Add a 👍 to the GitHub issue for the database you need, or open one if there is none, because the number of reactions is one of the inputs to what gets built next. Organizations that need a database sooner can talk to [Prisma enterprise support](https://www.prisma.io/enterprise).

Because a database library is an extension, a community package can add a database Prisma does not ship. If you publish one, [submit it to the directory](https://www.prisma.io/extensions/submit) and name the database it adds in the submission.
