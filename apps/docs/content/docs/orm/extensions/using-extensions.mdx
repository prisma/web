An extension is a package that teaches Prisma ORM a database feature it does not know out of the box. Installing one gives you new column types to declare in your schema, new query operations to call, and new index types, along with the migrations that install the feature in the database itself. Vector search, geospatial data, full-text search, typed JSON, and provider-specific integrations all reach your project this way.

Reach for an extension when your application needs one of those database features and you still want everything Prisma ORM gives you for the rest of your data: typed schema declarations, generated TypeScript, migration support, and query helpers.

Adding an extension means installing its package and then registering it in two places, your config file and your client. The steps here use pgvector, the vector search extension, as the example. Supabase is set up differently, so if that is the extension you are adding, read [the note under the catalog](#available-extensions) first.

## 1. Install the package

```npm title="Terminal"
npm install @prisma/orm-extension-pgvector
```

## 2. Register it in the config

Your config file is what the `prisma` command line tools read, so the registration here is the one they use: it is how `prisma contract emit` knows about the extension's types when it writes your contract, and how the migration commands know about the migrations the extension ships.

```ts title="prisma.config.ts"
import { definePrismaConfig } from 'prisma/config';
import pgvector from '@prisma/orm-extension-pgvector/control';
import { defineConfig as ormConfig } from '@prisma/orm-postgres/config';

export default definePrismaConfig({
  orm: ormConfig({
    contract: './src/prisma/contract.prisma',
    extensions: [pgvector],
    db: {
      connection: process.env['DATABASE_URL']!,
    },
  }),
});
```

## 3. Register it on the client

The second registration is the one your application uses while it is running: passing the extension to `postgres(...)` is what adds the extension's query operations and value types to the `db` client you write queries against.

```ts title="src/prisma/db.ts"
import pgvector from '@prisma/orm-extension-pgvector/runtime';
import postgres from '@prisma/orm-postgres/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  extensions: [pgvector],
});
```

## 4. Use the new type in your schema

Now that pgvector is registered in the config, its types are available in your contract, so you can give a column a vector type. A vector column needs an explicit number of dimensions, so name the type once under `types` and then use that name on the model:

```prisma title="src/prisma/contract.prisma"
types {
  Embedding1536 = pgvector.Vector(1536)
}

model Post {
  id        String         @id @default(uuid())
  title     String
  embedding Embedding1536?
}
```

## 5. Apply and query

Run `npx prisma contract emit` first, so that `contract.json` and `contract.d.ts` pick up the new column, and then run `npx prisma db init` on a new database, or `npx prisma db update` if the database already exists. You do not have to install the pgvector feature in PostgreSQL yourself, because the extension ships its own migration and this step runs `CREATE EXTENSION IF NOT EXISTS vector` for you. If `db init` reports a contract-space layout violation instead of succeeding, run `npx prisma migration plan` once. That writes the extension's baseline migration under `migrations/<extension>/`, and `db init` goes through after that. With the column in your database, you can query it with the operations the extension adds:

```ts title="src/prisma/similarity-search.ts"
const plan = db.sql.public.post
  .select('id', 'title')
  .select('distance', (f, fns) => fns.cosineDistance(f.embedding, queryVector))
  .orderBy((f, fns) => fns.cosineDistance(f.embedding, queryVector), { direction: 'asc' })
  .limit(10)
  .build();

const similar = await db.runtime().query(plan);
```

Alongside `fns.cosineDistance`, pgvector gives you `fns.cosineSimilarity`, and both take two vector expressions and return a `float8`. The difference is which way you sort: order ascending when you sort by distance, and descending when you sort by similarity.

## What an extension declares [#capabilities]

Every extension names the database features it adds under keys like `pgvector.cosine`, and you never write those keys by hand: registering the extension in the config is what records them in your contract, and registering it in `db.ts` is what makes them available while your app is running.

Keeping those two registrations in step is what lets Prisma ORM tell you something is missing before a query goes wrong. If your contract needs an extension that `db.ts` does not register, creating the client fails immediately, so a query never runs with the extension registered in only one of the two places. If the database itself cannot install the extension, `db init` or `db update` reports it before your app takes traffic.

Support for a database is itself an extension, which is why `@prisma/orm-postgres`, `@prisma/orm-sqlite`, and `@prisma/orm-mongo` are in the table: they connect SQL databases and document databases to the same core, and that is how a community package can add another database. The ones marked experimental work today, but the methods and options they give you are still changing, which is why ParadeDB supports only the `key_field` index option so far and SQLite is published without a quickstart to follow. Each name in the table links to that extension's directory page, and from there to the package README. Middleware wraps queries rather than adding a database feature, so it is listed on [How middleware works](/orm/middleware/how-middleware-works) instead.

:::note[Supabase does not follow the recipe above]

Supabase ships no `/control` subpath, so import its pack from `@prisma/orm-extension-supabase/pack` instead, and pass that to the same `ormConfig({ extensions: [supabasePack] })` call step 2 uses. The client is where the real difference is, because you build it with the `supabase()` factory from `@prisma/orm-extension-supabase/runtime` rather than with `postgres()`. That factory is built around roles: you pick the role you want with `asUser(jwt)`, `asAnon()`, or `asServiceRole()`, and the factory is what validates the JWT and binds the client to that role for row-level security. The [runnable example](https://github.com/prisma/orm/tree/main/examples/supabase) shows the whole setup in one project.

:::

If you would rather read a whole working project than a set of snippets, there is a runnable example for each of these extensions: [pgvector](https://github.com/prisma/orm/tree/main/examples/prisma-8-demo), [PostGIS](https://github.com/prisma/orm/tree/main/examples/prisma-8-postgis-demo), [ParadeDB](https://github.com/prisma/orm/tree/main/examples/paradedb-demo), and [Supabase](https://github.com/prisma/orm/tree/main/examples/supabase).

If the extension you need does not exist yet, you can build it. An extension pack is a versioned npm package with a documented layout, and the [call for extension authors](https://www.prisma.io/blog/prisma-next-call-for-extension-authors) explains how to write and publish one. Once yours is on npm, [submit it to the directory](https://www.prisma.io/extensions/submit), where the form validates your entry and opens the pull request for you.
