An extension is a package that teaches Prisma ORM a database feature it does not know out of the box. Installing one gives you new column types to declare, new query operations to call, and in some extensions new index types, along with the migrations that install the feature in the database itself. Vector search, geospatial data, full-text search, typed JSON, and provider-specific integrations all reach your project this way.

Reach for an extension when your application needs one of those database features and you still want everything Prisma ORM gives you for the rest of your data: typed schema declarations, generated TypeScript, migration support, and query helpers.

Your contract is the Prisma ORM 8 name for your schema: `contract.prisma` in a generated project, in place of `schema.prisma`. `npx prisma contract emit` writes `contract.json` and `contract.d.ts` from it, and those two files are what `db.ts` imports. [The data contract](/orm/contract-authoring/the-data-contract) covers what goes in it.

Adding an extension means installing its package and then registering it in two places, your config file and your client. These steps use pgvector, the vector search extension, as the example, and they assume a PostgreSQL project from the [quickstart](/prisma-orm/quickstart/postgresql), so `@prisma/orm-postgres` is already installed and the extension package is added next to it. Supabase is set up differently, so if that is the extension you are adding, read [the note under the catalog](#available-extensions) first.

## 1. Install the package

```npm title="Terminal"
npm install @prisma/orm-extension-pgvector
```

## 2. Register it in the config

Add the extension to the `extensions` array in your config file. The `prisma` command line tools read `prisma.config.ts` on every run, so listing the extension here is what lets `npx prisma contract emit` generate types for the extension's columns, and what lets the migration commands run the SQL the extension ships.

```ts title="prisma.config.ts"
import { definePrismaConfig } from 'prisma/config';
import pgvector from '@prisma/orm-extension-pgvector/control';
import { defineConfig as ormConfig } from '@prisma/orm-postgres/config';

export default definePrismaConfig({
  orm: ormConfig({
    contract: './src/prisma/contract.prisma',
    extensions: [pgvector],
    db: {
      connection: process.env['DATABASE_URL']!,
    },
  }),
});
```

The database package is the one you build on: `@prisma/orm-postgres` is what provides `ormConfig(...)` for the config and `postgres(...)` for the client. Every other extension, pgvector here, is passed to those two calls in their `extensions` array. Extensions publish separate entry points for the two, and `control` is the one the command line tools import, which is why the config file imports `@prisma/orm-extension-pgvector/control`.

## 3. Register it on the client

Add the extension to the `extensions` array on the client as well, which is what gives the `db` object you write queries against the extension's query operations and value types. Your application imports the `runtime` entry point rather than `control`.

```ts title="src/prisma/db.ts"
import pgvector from '@prisma/orm-extension-pgvector/runtime';
import postgres from '@prisma/orm-postgres/runtime';
import type { Contract } from './contract.d';
import contractJson from './contract.json' with { type: 'json' };

export const db = postgres<Contract>({
  contractJson,
  url: process.env['DATABASE_URL']!,
  extensions: [pgvector],
});
```

A project made with `npm create prisma@latest` already has `contract.json` and `contract.d.ts` from the scaffold, so these two imports resolve as soon as you write them. They describe your schema as it was before you edit it, and `npx prisma contract emit` in step 5 brings them up to date.

## 4. Use the new type in your schema

Now that pgvector is registered in the config, its types are available in your contract, so you can give a column a vector type. A vector column needs an explicit number of dimensions, so declare that dimension once as a named type in a `types` block, and then every column that uses the name gets the same dimension. The trailing `?` on `Embedding1536?` makes the column optional, exactly as `?` did in Prisma ORM 7. The `types` block is part of [PSL syntax](/orm/contract-authoring/psl-syntax).

```prisma title="src/prisma/contract.prisma"
types {
  Embedding1536 = pgvector.Vector(1536)
}

model Post {
  id        String         @id @default(uuid())
  title     String
  embedding Embedding1536?
}
```

## 5. Apply and query

Run `npx prisma contract emit` first, so that `contract.json` and `contract.d.ts` pick up the new column. Then run `npx prisma db init` on a new database, or `npx prisma db update` if the database already exists. Run `contract emit` again after every later edit to `contract.prisma`, because the migration commands read `contract.json` rather than the `.prisma` file.

`db init` reports a contract-space layout violation when the extension's own migration has not been written to disk yet. Run `npx prisma migration plan` once to write it under `migrations/pgvector/`, then run `npx prisma db init` again. That directory is part of your project's migrations, so commit it with the rest of `migrations/`.

The extension ships the migration that runs `CREATE EXTENSION IF NOT EXISTS vector`, so you do not write that yourself, but the PostgreSQL server has to have pgvector available for it to succeed. The local development server the quickstart sets up has it. A stock PostgreSQL image may not, and then the migration fails on that statement.

With the column in your database, write an embedding into it. A vector value is a plain `number[]` with as many entries as the column's dimension, so a column typed `Embedding1536` takes an array of 1536 numbers, which is what an embedding model gives you. Prisma ORM does not produce the numbers, and `embed` in this example stands for whichever model you call:

```ts title="src/prisma/write-post.ts"
const embedding: number[] = await embed('about cats');
await db.orm.public.Post.create({ title: 'about cats', embedding });
```

Searching for the rows closest to a query vector uses the operations the extension adds. The query vector is a `number[]` of the same length as the stored embeddings:

```ts title="src/prisma/similarity-search.ts"
export async function similaritySearch(queryVector: number[]) {
  const plan = db.sql.public.post
    .select('id', 'title')
    .select('distance', (f, fns) => fns.cosineDistance(f.embedding, queryVector))
    .orderBy((f, fns) => fns.cosineDistance(f.embedding, queryVector), { direction: 'asc' })
    .limit(10)
    .build();

  return db.runtime().query(plan);
}
```

`db.sql.public.post` is the `post` table in the PostgreSQL schema `public`, addressed through the SQL query builder described in [Advanced queries](/orm/fundamentals/advanced-queries). `.build()` returns the query as a plain object, and `db.runtime().query(plan)` runs it and returns the rows.

Alongside `fns.cosineDistance`, pgvector gives you `fns.cosineSimilarity`. Both take two vector expressions and return a `float8`, which you get as a `number`. The difference is which way you sort: order ascending when you sort by distance, because the closest row has the smallest distance, and descending when you sort by similarity.

## When a registration is missing [#capabilities]

If your contract uses an extension that `db.ts` does not register, creating the client throws an error whose `code` is `RUNTIME.MISSING_EXTENSION_PACK`, before any query runs. If the database cannot install the extension, `db init` or `db update` reports it.

The packages that add support for a database are extensions themselves, which is why `@prisma/orm-postgres`, `@prisma/orm-sqlite`, and `@prisma/orm-mongo` are in the table. The database package is the one you build on: it provides `ormConfig(...)` for the config and `postgres(...)` for the client. Every other extension is passed to those two calls in their `extensions` array, so a project has one database package and any number of extensions listed next to it.

The ones marked experimental work today, but their methods and options are still changing between releases. They are also incomplete in places: ParadeDB supports only the `key_field` index option so far, and SQLite is published without a quickstart to follow. Each name in the table links to that extension's directory page, and from there to the package README. Middleware wraps queries rather than adding a database feature, so it is listed on [How middleware works](/orm/middleware/how-middleware-works) instead.

:::note[Supabase does not follow the recipe above]

Supabase publishes no `/control` entry point. The bundle the command line tools need is published at `@prisma/orm-extension-supabase/pack` instead, so import that and pass it to the same `ormConfig({ extensions: [supabasePack] })` call step 2 uses. The client is where the real difference is, because you build it with the `supabase()` factory from `@prisma/orm-extension-supabase/runtime` rather than with `postgres()`. That factory is built around roles: you pick the role you want with `asUser(jwt)`, `asAnon()`, or `asServiceRole()`, and the factory is what validates the JWT and binds the client to that role for row-level security. The [runnable example](https://github.com/prisma/orm/tree/main/examples/supabase) shows the whole setup in one project.

:::

If you would rather read a whole working project than a set of snippets, there is a runnable example for each of these extensions: [pgvector](https://github.com/prisma/orm/tree/main/examples/prisma-8-demo), [PostGIS](https://github.com/prisma/orm/tree/main/examples/prisma-8-postgis-demo), [ParadeDB](https://github.com/prisma/orm/tree/main/examples/paradedb-demo), and [Supabase](https://github.com/prisma/orm/tree/main/examples/supabase).

If the extension you need does not exist yet, you can build it. An extension is a versioned npm package with a documented layout, and the [call for extension authors](https://www.prisma.io/blog/prisma-next-call-for-extension-authors) explains how to write and publish one. Once yours is on npm, [submit it to the directory](https://www.prisma.io/extensions/submit), where the form validates your entry and opens the pull request for you.
