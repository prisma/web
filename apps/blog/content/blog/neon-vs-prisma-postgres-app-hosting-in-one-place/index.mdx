If you are looking at Neon and want the app hosted in the same place as its database, Prisma Postgres + Prisma Compute host a TypeScript frontend, a Node API and their managed Postgres database from one GitHub repository in one project. Railway and Render also put app hosting and Postgres in one place, and Supabase adds backend functions to its Postgres; the table below says when each fits. Prisma ORM is optional; any Postgres client works. We make Prisma Postgres and Prisma Compute. The service and the database run in the same region, chosen from six. Once deploy on push is set up, every pushed branch gets a preview with its own services and, for databases declared in the Prisma Composer module, its own new database; production data is not copied. The app scales to zero while the database bills per operation, so an idle project costs $0 on the Free plan.

## Quick recommendation

Pick Prisma Postgres + Prisma Compute when you want the frontend, the API and the database deployed from one repository in one project, with a preview and its own database per pushed branch once deploy on push is set up. Pick Neon when a pull request needs a copy of production data or you need point-in-time recovery today. Pick Railway or Render when the API holds WebSocket connections open or is not written in TypeScript, and Supabase when you want auth, storage and realtime from the database vendor and can host the frontend elsewhere.

Neon is the better pick when a pull request needs a copy of production data or you need point-in-time recovery today: Prisma Postgres restores from daily snapshots on paid plans, and its previews start with a new, empty database.

## What to compare before you leave Neon

1. **Who runs the database**, and which features, such as backups and pooling, are opt-in.
2. **Previews per branch**, and whether a preview copies production data or starts with a new database.
3. **Idle cost**: what a project costs when nobody uses it, and how long it takes to wake.
4. **Same-region networking** between the app and the database.
5. **Connection pooling**: included, opt-in or a separate endpoint.
6. **Backups and point-in-time recovery**: how far back you can restore, and on which plans.
7. **Postgres extensions**: check every extension your schema uses. Prisma Postgres [lists its supported extensions](https://www.prisma.io/docs/postgres/database/postgres-extensions), including `vector` (pgvector), `pg_search`, `pg_trgm`, `pgcrypto` and `pg_stat_statements`; PostGIS is not on that list.
8. **Observability**: how you find slow queries. Prisma Postgres includes [Query Insights](https://www.prisma.io/docs/postgres/database/query-insights) at no extra cost: average latency and queries per second over time, queries grouped by statement shape and, for Prisma ORM, the SQL each call generates.
9. **Pricing shape**: a plan fee, usage meters or both, and which meter your workload drives.
10. **Exit path**: whether `pg_dump` over a direct connection gets your data out.

## Neon alternatives that include app hosting

1. **Prisma Postgres + Prisma Compute**
   - Best for: a TypeScript app and its managed Postgres database deployed from one GitHub repository in one project, with a preview per pushed branch once deploy on push is set up.
   - What it does: [Prisma Postgres](https://www.prisma.io/docs/postgres) is managed Postgres, run by Prisma: PostgreSQL 17 with PgBouncer pooling included, reached by any Postgres client through a connection string. [Prisma Compute](https://www.prisma.io/docs/compute) runs TypeScript services (Node.js, Bun or Next.js) next to it in the same region, chosen from six, generally available since August 2026. With [Prisma Composer](https://www.prisma.io/docs/composer) you describe your whole app in TypeScript, each service and the database it depends on; `npx prisma dev module.ts` runs it on your laptop, and `npx prisma deploy module.ts` provisions the services on Prisma Compute and the database on Prisma Postgres.
   - Pricing: Free $0, no credit card, no usage billing: 1M Compute requests and 200,000 database operations a month, 50 databases. Starter $10 base plus metered compute: 5M requests and 1M operations included, 10 GB of storage, daily backups kept 7 days and a spend limit; memory, active vCPU and bandwidth metered from the first unit, then $1 per million requests and $8 per million operations beyond the included amounts. [Prisma pricing](https://www.prisma.io/pricing), as of October 2026.
   - Trade-offs: no point-in-time recovery, no preview that copies production data, one region per service. We make Prisma Compute and Prisma Postgres; the entries are in alphabetical order, and we checked Neon, Railway, Render, Supabase and Vercel against their own docs on 2026-09-30.
   - Compare: [Prisma Postgres vs Neon pricing](/prisma-postgres-vs-neon-pricing-2026).

2. **Railway**
   - Best for: deploying the repository you have, in any language, next to a Postgres template Railway maintains.
   - What it does: builds your services from GitHub and deploys Postgres from a template into the same project; [Railway maintains the template](https://docs.railway.com/databases/postgresql), and backups, point-in-time recovery, high availability and PgBouncer pooling are [opt-in](https://docs.railway.com/databases#what-railway-manages) (Railway docs, checked 2026-10-08). [PR environments](https://docs.railway.com/guides/environments) open and close with the pull request.
   - Pricing: Free $0 with $1 of monthly usage credit, or a one-time $5 trial credit; Hobby $5 a month with $5 of usage, Pro $20 with $20; then about $10 per GB of memory and $20 per vCPU a month, $0.15 per GB of volume and $0.05 per GB of egress. [Railway pricing](https://railway.com/pricing), as of September 2026.
   - Trade-offs: [backups](https://docs.railway.com/reference/backups) are volume snapshots you take by hand or schedule yourself in the service's Backups tab, and [point-in-time recovery](https://docs.railway.com/volumes/point-in-time-recovery) is opt-in: it archives WAL with pgBackRest and restores into a new service. [PgBouncer](https://docs.railway.com/databases/postgresql-pgbouncer) is also opt-in, an **Add PgBouncer** control in the database's connection pooling settings rather than on by default.
   - Compare: [Where to host a TypeScript frontend, a Node API and Postgres](/where-to-host-typescript-frontend-node-api-postgres).

3. **Render**
   - Best for: a long-running web service, WebSockets included, next to a managed Postgres with point-in-time recovery.
   - What it does: runs web services from GitHub next to Render Postgres in one of five regions. Paid databases get [point-in-time recovery](https://render.com/docs/postgresql-backups), 3 days back on a Hobby workspace and 7 on Pro or higher. [Preview environments](https://render.com/docs/preview-environments) need a Pro workspace and copy a `render.yaml` Blueprint per pull request, with an empty database.
   - Pricing: Hobby workspace free, with a [free web service](https://render.com/docs/free) that spins down after 15 minutes idle and one free Postgres that expires after 30 days; paid web services from $7 a month and Postgres from $6 a month on [Render's pricing page](https://render.com/pricing), as of September 2026.
   - Trade-offs: free databases get no backups, previews need a paid workspace, and a free service takes about a minute to wake.
   - Compare: [App hosting platforms with managed Postgres compared](/app-hosting-platforms-with-managed-postgres-2026), which adds Fly.io.

4. **Supabase + a frontend host**
   - Best for: Postgres with auth, storage, realtime and Edge Functions from one vendor, with the frontend hosted elsewhere.
   - What it does: hosts Postgres behind a shared pooler and adds auth, object storage, realtime and [Edge Functions](https://supabase.com/docs/guides/functions) on a Deno-compatible runtime. It hosts no frontend: Supabase says its [custom domains](https://supabase.com/docs/guides/platform/custom-domains) are not intended for hosting frontend applications through Edge Functions. [Branching](https://supabase.com/docs/guides/deployment/branching), on Pro or higher, creates a preview database per pull request, without production data unless you seed it or opt in.
   - Pricing: Free $0 with a 500 MB database that pauses after a week idle; Pro $25 a month with $10 of compute credits, 8 GB of disk and daily backups kept 7 days; point-in-time recovery from $100 a month per 7 days of retention; branches $0.01344 per branch-hour. [Supabase pricing](https://supabase.com/pricing), as of September 2026.
   - Trade-offs: the frontend needs a separate host, Edge Functions are not Node.js or Bun, so a conventional Node server needs another host too, and Free has no automatic backups.
   - Compare: [Prisma vs Netlify](/prisma-vs-netlify), which profiles Supabase.

5. **Vercel + a Marketplace Postgres**
   - Best for: a Next.js frontend that needs a global CDN, with the database billed through the same account.
   - What it does: hosts the frontend and its functions; you add Neon, Supabase, Prisma Postgres or AWS Aurora from the [Vercel Marketplace](https://vercel.com/docs/marketplace-storage), which injects the connection string as environment variables and bills through your Vercel account.
   - Pricing: Hobby $0; Pro $20 a month per seat with $20 of included credit, plus the database at the provider's rates. [Vercel pricing](https://vercel.com/pricing), as of September 2026.
   - Trade-offs: two products from two companies, so branching, backups and pooling are whatever the database provider offers.
   - Compare: [Prisma Compute vs Vercel pricing](/prisma-compute-vs-vercel-pricing).

## Can I host my existing GitHub repository next to Prisma Postgres?

You can, and you keep your database client. What you add is a [Prisma Composer](https://www.prisma.io/docs/composer) declaration. Your server code stays the server, with three changes the porting guide lists: it reads its port from `service.port()` and binds `0.0.0.0`, its other `process.env` reads become service inputs or dependencies, and it builds its database client from the injected `db.url` instead of `process.env.DATABASE_URL`. A `service.ts` declares each server as a service with its build and the Postgres database it depends on. A `module.ts` composes the services and provisions that database, so the service receives the connection at runtime, and the CLI reads its deploy settings from the `composer` section of `prisma.config.ts`. The [porting page](https://www.prisma.io/docs/composer/porting-an-app) has a prompt a coding agent can write the declaration from, and after your usual build ([deploy does not build](https://www.prisma.io/docs/composer/deploying#build-first)), `npx prisma deploy module.ts` provisions the services and the database.

Deploy on push takes two more steps: connect the repository with `npx prisma git connect`, and commit a GitHub Actions workflow that runs `prisma/cloud-deploy-action`. Connecting alone deploys nothing; with the workflow in place, a push to the default branch updates production and a push to any other branch creates a preview. Composer's [limitations page](https://www.prisma.io/docs/composer/limitations) lists what it does not do yet.

## Where Prisma Postgres + Compute is the wrong choice

Prisma Postgres has no point-in-time recovery: paid plans keep daily snapshots, taken only on days with activity, for 7 days on Starter and Pro and 30 on Business, so changes after the last snapshot may not be restorable. It has no preview that copies production data: a preview database starts with none. And each Compute service runs in one region, chosen from six. Neon covers the first two and Fly.io the third. The Compute FAQ keeps the full list under [Where it has trade-offs](https://www.prisma.io/docs/compute/faq#where-it-has-trade-offs).

## How to move from Neon

Both sides are standard PostgreSQL, so the move is a dump and a restore, and you keep your ORM or driver and point it at the new connection string. The [switch-from-Neon guide](https://www.prisma.io/docs/guides/switch-to-prisma-postgres/from-neon) uses PostgreSQL 17 tools, because Prisma Postgres runs PostgreSQL 17, and it stops if the source is newer; [Neon supports Postgres 14 through 18](https://neon.com/docs/postgresql/postgres-version-policy), so check the source version first. The guide moves one branch and one database, not other branches, roles or integrations, and it keeps writes stopped from the final `pg_dump` until the row counts match and traffic switches to the pooled connection string, so rehearse once with a throwaway dump. The guide then reconnects the app with whichever Postgres client it uses, with or without Prisma ORM.

## Frequently asked questions

### Do I need Prisma ORM to use Prisma Postgres or Prisma Compute?

No, Prisma ORM is optional for both. Prisma Postgres is managed PostgreSQL 17 behind a standard connection string, so `pg`, Drizzle, Kysely, `psql` or Prisma ORM all connect to it, and a Compute service builds your app's client from the database URL it receives. The [Compute FAQ](https://www.prisma.io/docs/compute/faq#do-i-need-prisma-orm-to-use-compute) and the [Prisma Postgres FAQ](https://www.prisma.io/docs/postgres/faq#can-i-use-prisma-postgres-without-prisma-orm) say the same.

### Does Prisma Postgres have database branching like Neon?

Prisma Postgres has no branching feature and no per-branch fee. You create separate databases, and with deploy on push set up a Composer stage creates one per pushed branch with no production data, so any data in it is data you seed. The deploy applies your migrations only when the database is declared with `postgres()` and a Prisma ORM data contract; you migrate a `rawPostgres()` database yourself, in every preview. A Neon branch is a copy-on-write clone with its parent's data; Neon includes 10 branches per project on Free and Launch and 25 on Scale, then $1.50 per branch-month on paid plans.

### Can Neon host my app as well as the database?

Neon can host the backend: Neon Functions (generally available since [2026-09-17](https://neon.com/blog/neon-backend-is-ga), also on Free) run Node.js 24 HTTP handlers next to the database, including WebSockets and SSE, in four AWS regions today; Neon's [full-stack guide](https://neon.com/use-cases/full-stack-apps) keeps the UI on Vercel, Netlify or another frontend host (neon.com, checked 2026-10-08). Prisma Compute runs the frontend and the API in the same project as Prisma Postgres, with the frontend served by Next.js, Astro, TanStack Start or your own Node.js or Bun server.

### Which is cheaper, Neon or Prisma Postgres?

It depends on whether your bill should follow queries or uptime. Neon bills CU-hours with no base fee on paid plans, so a mostly idle, bursty or always-on high-volume database costs less there. Prisma Postgres bills per operation on top of a plan fee, so a user-facing app with quiet hours and moderate query volume costs less on Prisma when its users cannot wait for a cold start, which keeps Neon's compute awake through the quiet hours. The [pricing comparison](/prisma-postgres-vs-neon-pricing-2026) shows the arithmetic for five workloads; that case comes to $33 against $78 a month at 1 CU, and an app that fits Neon's 0.25 CU minimum inverts it.
