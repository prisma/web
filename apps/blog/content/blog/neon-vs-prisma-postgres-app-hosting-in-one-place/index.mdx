If you are looking at Neon and want the app hosted in the same place as its database, Prisma Postgres + Prisma Compute host a TypeScript frontend, a Node API and their Postgres database from one GitHub repository on one plan. Neon is the better pick if you need point-in-time recovery or branches that copy production data. Prisma makes Prisma ORM, Prisma Postgres and Prisma Compute. The service and the database run in the same six regions; once deploy on push is set up, every pushed branch gets a preview with its own database, built from your migrations; and the app scales to zero while the database bills per operation, so an idle project costs $0 on the Free plan. Railway, Render and Supabase also put app hosting and Postgres under one vendor, so this post compares all of them with Neon.

## Quick recommendation

Pick Prisma Postgres + Prisma Compute when you want the frontend, the API and the database deployed from one repository on one plan, with a preview and its own database per pushed branch once deploy on push is set up. Pick Neon when a pull request needs a copy of production data or you need point-in-time recovery today. Pick Railway or Render when the API holds WebSocket connections open or is not written in TypeScript, and Supabase when you want auth, storage and realtime from the database vendor.

| --- | --- | --- |

Add a Composer declaration, deploy with `npx prisma deploy module.ts`, then connect the repository plus the `prisma/cloud-deploy-action` workflow for deploy on push. |

## Neon alternatives that include app hosting

1. **Prisma Postgres + Prisma Compute**
   - Best for: a TypeScript app and its Postgres database deployed from one GitHub repository on one plan, with a preview per pushed branch once deploy on push is set up.
   - What it does: [Prisma Compute](https://www.prisma.io/docs/compute) runs TypeScript services (Node.js, Bun or Next.js) next to [Prisma Postgres](https://www.prisma.io/docs/postgres) in the same six regions, generally available since August 2026. With [Prisma Composer](https://www.prisma.io/docs/composer) you describe your whole app in TypeScript, each service and the database it depends on; `npx prisma dev module.ts` runs it on your laptop, and `npx prisma deploy module.ts` provisions the services on Prisma Compute and the database on Prisma Postgres.
   - Pricing: Free $0, no credit card, no usage billing: 1M Compute requests and 200,000 database operations a month, 500 MB of storage. Starter $10 base plus metered compute: 5M requests and 1M operations included, 10 GB of storage, daily backups kept 7 days and a spend limit; memory, active vCPU and bandwidth metered from the first unit, then $1 per million requests and $8 per million operations beyond the included amounts. [Prisma pricing](https://www.prisma.io/pricing), as of September 2026.
   - Trade-offs: no point-in-time recovery, no branch that copies production data, one region per service. We make Prisma Compute and Prisma Postgres, so this entry comes first for the table's situations; we checked Neon, Railway, Render, Supabase and Vercel against their own docs on 2026-09-30, and the thing Neon does that we do not is give a preview a copy of production data.
   - Compare: [Prisma Postgres vs Neon pricing](/prisma-postgres-vs-neon-pricing-2026).

2. **Railway**
   - Best for: deploying the repository you have, in any language, next to a Postgres you run yourself.
   - What it does: builds your services from GitHub and deploys Postgres from a template into the same project. Its docs call the [database templates unmanaged](https://docs.railway.com/guides/postgresql): backups, monitoring and upgrades are yours. [PR environments](https://docs.railway.com/guides/environments) open and close with the pull request.
   - Pricing: Free $0 with $1 of monthly usage credit, or a one-time $5 trial credit; Hobby $5 a month with $5 of usage, Pro $20 with $20; then about $10 per GB of memory and $20 per vCPU a month, $0.15 per GB of volume and $0.05 per GB of egress. [Railway pricing](https://railway.com/pricing), as of September 2026.
   - Trade-offs: [backups](https://docs.railway.com/reference/backups) are scheduled volume snapshots by default, and [point-in-time recovery](https://docs.railway.com/volumes/point-in-time-recovery) is opt-in: it archives WAL with pgBackRest and restores into a new service. [PgBouncer](https://docs.railway.com/databases/postgresql-pgbouncer) is also opt-in, an **Add PgBouncer** control in the database's connection pooling settings rather than on by default.
   - Compare: [Where to host a TypeScript frontend, a Node API and Postgres](/where-to-host-typescript-frontend-node-api-postgres).

3. **Render**
   - Best for: a long-running web service, WebSockets included, next to a managed Postgres with point-in-time recovery.
   - What it does: runs web services from GitHub next to Render Postgres in one of five regions. Paid databases get [point-in-time recovery](https://render.com/docs/postgresql-backups), 3 days back on a Hobby workspace and 7 on Pro or higher. [Preview environments](https://render.com/docs/preview-environments) need a Pro workspace and copy a `render.yaml` Blueprint per pull request, with an empty database.
   - Pricing: Hobby workspace free, with a [free web service](https://render.com/docs/free) that spins down after 15 minutes idle and one free Postgres that expires after 30 days; paid web services from $7 a month and Postgres from $6 a month on [Render's pricing page](https://render.com/pricing), as of September 2026.
   - Trade-offs: free databases get no backups, previews need a paid workspace, and a free service takes about a minute to wake.
   - Compare: the [same hosting post](/where-to-host-typescript-frontend-node-api-postgres).

4. **Supabase**
   - Best for: Postgres with auth, storage, realtime and Edge Functions from one vendor.
   - What it does: hosts Postgres behind a shared pooler and adds auth, object storage, realtime and [Edge Functions](https://supabase.com/docs/guides/functions) on a Deno-compatible runtime. [Branching](https://supabase.com/docs/guides/deployment/branching) creates a preview database per pull request, without production data unless you seed it or opt in.
   - Pricing: Free $0 with a 500 MB database that pauses after a week idle; Pro $25 a month with $10 of compute credits, 8 GB of disk and daily backups kept 7 days; point-in-time recovery from $100 a month per 7 days of retention; branches $0.01344 per branch-hour. [Supabase pricing](https://supabase.com/pricing), as of September 2026.
   - Trade-offs: Edge Functions are not Node.js or Bun, so a conventional Node server needs another host, and Free has no automatic backups.
   - Compare: [Prisma vs Netlify](/prisma-vs-netlify), which profiles Supabase.

5. **Vercel + a Marketplace Postgres**
   - Best for: a Next.js frontend that needs a global CDN, with the database billed through the same account.
   - What it does: hosts the frontend and its functions; you add Neon, Supabase, Prisma Postgres or AWS Aurora from the [Vercel Marketplace](https://vercel.com/docs/marketplace-storage), which injects the connection string as environment variables and bills through your Vercel account.
   - Pricing: Hobby $0; Pro $20 a month per seat with $20 of included credit, plus the database at the provider's rates. [Vercel pricing](https://vercel.com/pricing), as of September 2026.
   - Trade-offs: two products from two companies, so branching, backups and pooling are whatever the database provider offers.
   - Compare: [Prisma Compute vs Vercel pricing](/prisma-compute-vs-vercel-pricing).

## Can I host my existing GitHub repository next to Prisma Postgres?

You can, after adding a Composer declaration. Your server code stays the server, with the small changes the porting guide lists: it reads its port from `service.port()`, its configuration reads become service input, and it builds its database client from the injected `db.url` instead of `process.env.DATABASE_URL`. A `service.ts` declares each server as a service with its build and the Postgres database it depends on, and a `module.ts` composes the services and provisions that database, so the service receives the connection at runtime. The [porting page](https://www.prisma.io/docs/composer/porting-an-app) has a prompt a coding agent can write the declaration from, and `npx prisma deploy module.ts` then provisions the services and the database.

Deploy on push takes two more steps: connect the repository with `npx prisma git connect`, and commit a GitHub Actions workflow that runs `prisma/cloud-deploy-action`. Connecting alone deploys nothing; with the workflow in place, a push to the default branch updates production and a push to any other branch creates a preview. Composer's [limitations page](https://www.prisma.io/docs/composer/limitations) lists what it does not do yet.

## Where Prisma Postgres + Compute is the wrong choice

Prisma Postgres has no point-in-time recovery: paid plans keep daily snapshots, taken only on days with activity, for 7 days on Starter and Pro and 30 on Business, so changes after the last snapshot may not be restorable. It has no branch that copies production data, because a preview database starts from migrations. And each Compute service runs in one region, chosen from six. Neon covers the first two and Fly.io the third. The [Compute FAQ](https://www.prisma.io/docs/compute/faq) keeps the full list of trade-offs.

## How to move from Neon

Both sides are standard PostgreSQL, so the move is a dump and a restore, and your ORM or driver stays as it is. The [switch-from-Neon guide](https://www.prisma.io/docs/guides/switch-to-prisma-postgres/from-neon) uses PostgreSQL 17 tools, because Prisma Postgres runs PostgreSQL 17, and it stops if the source is newer; [Neon supports Postgres 14 through 18](https://neon.com/docs/postgresql/postgres-version-policy), so check the source version first. The guide moves one branch and one database, not other branches, roles or integrations, and it keeps writes stopped from the final `pg_dump` until the row counts match and traffic switches to the pooled connection string, so rehearse once with a throwaway dump. The guide has a reconnect path for Prisma ORM 8, the version npm installs by default, for [Prisma ORM 7](https://www.prisma.io/docs/orm/v7) and for any other Postgres client.

## Frequently asked questions

### Does Prisma Postgres have database branching like Neon?

Prisma Postgres has no branching feature and no per-branch fee. You create separate databases, and with deploy on push set up a Composer stage creates one per pushed branch from your migrations, so any data in it is data you seed. A Neon branch is a copy-on-write clone with its parent's data; Neon includes 10 branches per project on Free and Launch and 25 on Scale, then $1.50 per branch-month on paid plans.

### Can Neon host my app as well as the database?

Neon hosts the backend but not the frontend. Neon Functions, generally available since [September 17, 2026](https://neon.com/blog/neon-backend-is-ga), run JavaScript or TypeScript on Node.js 24 next to your data in four AWS regions, one deployment per branch, and they do not host websites, so a web app still needs a frontend host such as Vercel. Prisma Compute hosts both in the same project as Prisma Postgres.

### Which is cheaper, Neon or Prisma Postgres?

It depends on whether your bill should follow queries or uptime. Neon bills CU-hours with no base fee on paid plans, so a mostly idle, bursty or always-on high-volume database costs less there. Prisma Postgres bills per operation on top of a plan fee, so a user-facing app with quiet hours and moderate query volume costs less on Prisma. The [pricing comparison](/prisma-postgres-vs-neon-pricing-2026) shows the arithmetic for five workloads.
