A schema change is half the story, the data has to move too. Prisma Next puts that data step in TypeScript, in the same file as your schema, type-checked against the models as they were the day you wrote it.

Every schema change has a data step: filling in a new column, splitting a name into first and last, or cleaning up bad values before adding a constraint.

Today, that work usually lives in a one-off script you run by hand with `tsx`. Because the script sits outside your migration history, nothing prevents someone from running it twice and double-writing the column. If it fails halfway through, you fix the database by hand.

And the schema change that depends on the script lives in another folder entirely, with the link between the two left implicit.

Here is how Prisma Next handles it instead.

## You write data migrations in TypeScript

Here is a backfill, written as a Prisma Next migration:

```typescript
// examples/prisma-next-demo/migrations/20260422T0748_migration/migration.ts

this.dataTransform(endContract, "handle-nulls-user-displayName", {
  check: () =>
    db.sql.user
      .select("id")
      .where((f, fns) => fns.eq(f.displayName, null))
      .limit(1),
  run: () =>
    db.sql.user
      .update({ displayName: "Anonymous" })
      .where((f, fns) => fns.eq(f.displayName, null)),
}),
```

`dataTransform` takes a `check` (does this still need to run?) and a `run` (the change itself). Both use `db.sql.user.update(...)`, the same query builder you use in your application code, with the same autocomplete and type checking.

You used to drop into hand-written SQL for the data step. Without autocomplete or type checking, mistakes like a misspelled column name can slip through until the migration runs. Now you write a query in TypeScript, and the editor catches the typo before you commit.

A data migration is _just another migration_. It uses the same file shape and the same `migration plan` and `migration apply` commands. The only difference is that one step changes data instead of structure.

## Schema and data live in one file, in order

Adding a `NOT NULL` column to a table that already has rows usually takes three deploys. You ship the column as nullable, then ship and run the backfill, and finally ship the constraint. Three PRs, and three chances to get the order wrong.

In Prisma Next it is one file:

```typescript
// examples/prisma-next-demo/migrations/20260422T0748_migration/migration.ts

override get operations() {
  return [
    addColumn("public", "user", {
      name: "displayName",
      typeSql: "text",
      nullable: true,
    }),

    this.dataTransform(endContract, "handle-nulls-user-displayName", {
      check: () =>
        db.sql.user
          .select("id")
          .where((f, fns) => fns.eq(f.displayName, null))
          .limit(1),
      run: () =>
        db.sql.user
          .update({ displayName: "Anonymous" })
          .where((f, fns) => fns.eq(f.displayName, null)),
    }),

    setNotNull("public", "user", "displayName"),
  ];
}
```

Three operations, one PR, one `migration apply`. The order you wrote is the order they run.

The next reviewer sees the structure change and the data move in the same place, so questions like "which one runs first?" go away, along with the separate backfill script.

## How this fits in the TypeScript ecosystem

Other popular ORMs in the TypeScript ecosystem typically take one of two approaches to data migrations.

The first is raw SQL. When you need a data step, the tool generates an empty `.sql` file and you fill it in by hand:

```sql
-- migrations/0042_handle_nulls.sql
UPDATE "user" SET "displayName" = 'Anonymous' WHERE "displayName" IS NULL;
```

There is no autocomplete on column names, no type check on values, and no way to reuse query helpers from your application layer.

The second is a query builder typed against your live models. It looks closer to your application code, but the types follow your current model definitions:

```typescript
// migrations/0042_handle_nulls.ts (a typical TypeScript ORM)
await manager.update(User, { displayName: null }, { displayName: "Anonymous" });
```

When you wrote this, `User.displayName` existed. If you rename the field to `name` a few months later, the `User` model changes for every file that imports it, including this migration. Depending on the tool, the migration either stops compiling or points at a column that no longer exists when it runs.

Prisma Next addresses both gaps. The query builder lives inside the migration alongside schema operations like `addColumn` and `setNotNull`, and it is typed against the contract as it was when you wrote the migration, not the contract today.

## Old migrations don't break when you rename a field

Imagine you wrote the backfill above today. Six months from now, you rename `displayName` to `name` in your schema.

In most setups, the old migration breaks. The query that referenced `displayName` either fails to compile or runs against a column that no longer exists.

In Prisma Next, the old migration still compiles and still runs the same way it did the first time. The reason is straightforward: each migration folder includes a frozen copy of your models from the day you wrote the migration.

```text
examples/prisma-next-demo/migrations/20260422T0748_migration/
├── migration.ts            # the migration you wrote
├── ops.json                # the SQL the runner executes
├── start-contract.json     # your models before this migration
└── end-contract.json       # your models after this migration
```

When the migration runs `db.sql.user.update({ displayName: "Anonymous" })`, that query is checked against the frozen copy in this folder, not against your current schema. So `displayName` is still a real field as far as this migration is concerned, even after the rename.

You can keep old migrations in version control for years and trust them not to break.

## Data migrations also work in MongoDB

The same shape works on MongoDB today: each step is a `dataTransform` with a `check` and a `run`, bound to a frozen contract from the day you wrote it.

See [a full example here](https://github.com/prisma/prisma-next/blob/main/examples/retail-store/migrations/20260416_backfill-product-status/migration.ts).

## Try it yourself

Prisma Next is not production-ready yet, and Prisma 7 is still the right choice for production today. When Prisma Next is ready for general use, it becomes Prisma 8.

You can try it today, and your feedback helps shape what ships:

```bash
pnpx prisma-next init
```

Write a schema change with a data step in the same file, plan it, and apply it.
