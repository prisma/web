Prisma Postgres, Neon and Render each take a small Postgres database from your laptop online in three steps: create a database, run `pg_dump`, run `pg_restore`. Railway takes four and Supabase five. They differ on what a free database does when you leave it alone: Prisma Postgres and Neon keep it with no time limit and no credit card, Supabase pauses a free project after a week without activity, Render's free database expires 30 days after creation, and Railway's Free plan runs on $1 of credit a month after a one-time trial. We make Prisma Postgres.

Prisma Postgres is managed PostgreSQL 17 with connection pooling included. Its Free plan has 1.01 GB of storage and 200,000 operations a month, and the same free account can run the app that uses the database on Prisma Compute, for Node.js, Bun or Next.js apps. Any Postgres client connects; Prisma ORM is optional.

## Which service makes moving a laptop Postgres database online easiest?

Prisma Postgres, Neon and Render each take three steps from an empty account to a restored database, and of those, Prisma Postgres and Neon keep the free database with no time limit, while Render's expires 30 days after creation. Railway takes four steps, because `pg_restore` on your laptop needs a way in: its public TCP Proxy, or an SSH tunnel from [`railway connect postgres --tunnel-only`](https://docs.railway.com/cli/connect) that keeps the database private. Supabase takes five, because its guide runs the copy from a migration machine and leaves roles and row-level security to recreate afterwards.

## Pick by need

- **A free database with no time limit, plus the app on the same account:** Prisma Postgres with Prisma Compute.
- **Trying it before you sign up:** `npx create-db@latest` creates a temporary Prisma Postgres database that is deleted after 24 hours unless you claim it ([docs](https://www.prisma.io/docs/postgres/npx-create-db)).
- **Database branches, point-in-time restore or a PostgreSQL 18 source:** Neon.
- **Auth and file storage from the database vendor:** Supabase.
- **An app already on Render or Railway:** that platform's Postgres.

[Where Prisma Postgres is the wrong choice](#where-prisma-postgres-is-the-wrong-choice) has the details behind the Neon and Supabase lines.

Which Prisma Postgres path to follow depends on what you are moving:

| You are moving | Follow |
| --- | --- |

Prisma Composer needs Node.js 22.18 or newer ([prerequisites](https://www.prisma.io/docs/prisma-compute/deploy#prerequisites)). An app you already have gets a `service.ts` per server and one `module.ts`, plus three changes to the server itself: read the port from `service.port()` and bind `0.0.0.0`, turn its other `process.env` reads into service inputs or dependencies, and build the Postgres client from the injected `db.url` ([porting an app](https://www.prisma.io/docs/composer/porting-an-app)). The Free plan includes a Compute allowance with no usage billing, while paid plans meter Compute memory, CPU and bandwidth on top of the plan price ([pricing](https://www.prisma.io/pricing)).

## Migrate a local Postgres database to the cloud: create, pg_dump, pg_restore, swap DATABASE_URL

These steps work for any stack, because Prisma Postgres is standard PostgreSQL behind a connection string: Prisma ORM, Drizzle, Kysely, TypeORM, `node-postgres` and `psql` connect to it the same way they connect to the database on your laptop. You need the PostgreSQL 17 client tools, because Prisma Postgres runs PostgreSQL 17, so check that `pg_dump --version` prints `17.x` before you start. If the app uses Prisma ORM, follow the [checklist further down](#if-your-app-uses-prisma-orm) instead, because it does the same with the Prisma steps added.

1. **Create the database in the [Prisma Console](https://console.prisma.io).** Create a project with a Prisma Postgres database in the region closest to your users, open the database, click **Connect to your database** and then **Generate new connection string**. Copy both strings it shows: the pooled one (`pooled.db.prisma.io`) is for your app, and the direct one (`db.prisma.io`) is for `pg_restore`, `psql` and migrations.

2. **Dump the local database** into a compressed archive. Add `-h`, `-p` and `-U` if it does not run on the default socket, or pass a connection URL to `-d`:

   ```bash
   pg_dump -Fc -d mydb -f mydb.dump
   ```

3. **Restore the archive over the direct connection.** `--no-owner` and `--no-privileges` skip the ownership and grant statements that name roles from your laptop, which do not exist in Prisma Postgres:

   ```bash
   pg_restore --no-owner --no-privileges \
     -d 'postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require' \
     mydb.dump
   ```

4. **Swap `DATABASE_URL`** for the pooled string wherever the app runs, and restart the app.

Steps 1 to 3 are the three that the table counts. If you would rather stay in a terminal, step 1 becomes three commands, `npx prisma auth login`, `npx prisma project create my-app` and `npx prisma postgres create mydb`, so the import takes five commands in all. The docs page [Migrate a local Postgres database to a managed Postgres service](https://www.prisma.io/docs/postgres/import-from-existing-database) has both paths, and the checks to run first for extensions and row-level security policies.

## Where Prisma Postgres is the wrong choice

- You need point-in-time recovery or a branch that copies production data. Prisma Postgres has no backups on the Free plan; paid plans take a daily snapshot on days the database has activity, kept 7 days on Starter and Pro and 30 days on Business, and point-in-time recovery is not available yet ([backups](https://www.prisma.io/docs/postgres/database/backups)). Neon has point-in-time restore within a history window set by the plan, and 10 branches per project on Free ([instant restore](https://neon.com/docs/postgres/backup-restore/branch-restore), [pricing](https://neon.com/pricing), as of October 2026).
- You want auth and file storage from the database vendor. Supabase's Free plan includes Auth for 50,000 monthly active users and 1 GB of file storage ([pricing](https://supabase.com/pricing), as of October 2026).
- The source runs PostgreSQL 18. The PostgreSQL 17 tools that Prisma Postgres needs cannot dump it, and the [import guide](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql) says a source on 18 needs a separate downgrade-compatible process. Neon and Render offer PostgreSQL 18 databases ([Neon](https://neon.com/docs/postgresql/postgres-version-support), [Render](https://render.com/docs/postgresql-creating-connecting), as of October 2026).
- The database uses PostGIS or TimescaleDB. Neither is on the [supported extensions list](https://www.prisma.io/docs/postgres/database/postgres-extensions#supported-extensions).

## If your app uses Prisma ORM

For a Prisma ORM project, follow this checklist instead of the steps above. It covers the same ground, creating the database and copying the data, plus what a Prisma project needs on top: the Prisma CLI pointed at the hosted database, the migration history carried over, and a local database to keep developing against. The schema, the queries and Prisma Client keep working against the hosted database. Restore into it once: `pg_restore` does not roll back what it already loaded, so a second run on top of the first reports `already exists` errors, and the fix is a new, empty database.

The checklist takes an app on Docker Postgres or a local `prisma dev` instance to Prisma Postgres with schema, data and migration history intact:

1. Develop against a local database, with `prisma dev` or Docker.
2. Create the hosted Prisma Postgres database.
3. Point your config at it.
4. Replay the schema, and move the data if it matters.
5. Validate, deploy, and keep the local loop.

The commands below pin `prisma@7`, because the checklist follows the Prisma ORM 7 workflow (`migrate dev`, `prisma.config.ts`); Prisma ORM 8, the version npm installs by default, renames or drops them, and [Coming from Prisma ORM 7](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7) maps each one.

### Start local: `prisma dev` or Docker

The classic local setup is [Docker](https://www.docker.com): a `postgres:17` container on port 5432, a volume so data survives restarts, and `DATABASE_URL="postgresql://postgres:postgres@localhost:5432/postgres"` in `.env`. If you already have it, keep it: the rest of the checklist is identical.

The lighter route is `prisma dev`, which ships with the Prisma CLI:

```bash
npx prisma@7 dev
```

That starts a local Prisma Postgres instance on [PGlite](https://pglite.dev), an embedded Postgres engine, with no daemon or container, and prints connection strings ready to paste into `.env`:

```text
✔  Your local Prisma Postgres server default is now running

🔌 To connect with Prisma ORM use the following connection strings:

   DATABASE_URL="postgres://postgres:postgres@localhost:51214/template1?sslmode=disable&..."
```

`prisma dev` needs a Node.js version Prisma ORM 7 supports: 20.19 or later, 22.12 or later, or 24; if you plan to deploy on Prisma Compute as well, use 22.18 or newer, because Composer needs it. `npx prisma@7 dev --name myapp` gives every project its own named instance, `--detach` runs the server in the background, and `prisma dev ls`, `prisma dev stop <name>` and `prisma dev rm <name>` list, stop and delete instances.

It is a development tool that serves one connection at a time, not something you self-host; the [local development docs](https://www.prisma.io/docs/local-development/postgres) have the full reference.

Whichever route you chose, create the schema and, if your config defines a seed script, seed:

```bash
npx prisma@7 migrate dev
npx prisma@7 db seed
```

### Create the hosted database

Create the database in the [Prisma Console](https://console.prisma.io) and copy both connection strings, as in the first step of [Migrate a local Postgres database to the cloud](#migrate-a-local-postgres-database-to-the-cloud-create-pg_dump-pg_restore-swap-database_url). Every Prisma Postgres database has [two connection strings](https://www.prisma.io/docs/postgres/database/connecting-to-your-database): **pooled** (`pooled.db.prisma.io`) for application traffic and **direct** (`db.prisma.io`) for migrations and tools like `pg_restore`. You will use both.

Two CLI alternatives: for a brand-new project, `npx prisma@7.9.1 init --db` scaffolds the schema and provisions a Prisma Postgres database in one go, and [`npx create-db@latest`](https://www.prisma.io/docs/postgres/npx-create-db) creates a temporary database with no sign-up, deleted after 24 hours unless you claim it.

### Update env and config

Before you touch `.env`, check that it is gitignored, because production credentials are about to live in it, and keep your local URLs somewhere you can get them back; for a `prisma dev` instance, `npx prisma@7 dev ls` shows the connection string again.

Now point the app at the hosted database by swapping the connection strings:

```text
# .env (before)
DATABASE_URL="postgres://postgres:postgres@localhost:51214/template1?sslmode=disable&..."

# .env (after)
DATABASE_URL="postgres://USER:PASSWORD@pooled.db.prisma.io:5432/postgres?sslmode=require"
DIRECT_URL="postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require"
```

The app reads the pooled string through `DATABASE_URL` at runtime; the direct string is for the Prisma CLI, because migrations hold locks and session state across statements and fail through the PgBouncer transaction pooler, while an app on the direct string quietly exhausts connections under load. [Connecting to your database](https://www.prisma.io/docs/postgres/database/connecting-to-your-database) lists the other work that wants the direct string. Add `DIRECT_URL` and point the datasource in `prisma.config.ts` at it:

```ts
// prisma.config.ts
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  datasource: {
    url: env("DIRECT_URL"),
    // Set for local development with `prisma dev`; unset in production.
    shadowDatabaseUrl: process.env["SHADOW_DATABASE_URL"],
  },
});
```

The `url` line is the change production needs. That is the Prisma ORM 7 setup, where connection URLs live in `prisma.config.ts`; on Prisma ORM 6 the same job is done by `directUrl` in the schema's `datasource` block. For local development with `prisma dev`, set `DIRECT_URL` to the same value as `DATABASE_URL`, because the local server has no pooler, and copy the `SHADOW_DATABASE_URL` it prints into `.env` as well. Prisma Migrate uses that second database as its shadow database, and without it a later `migrate dev` fails with `relation "..." already exists`. `migrate deploy` in production does not use a shadow database, so the variable stays unset there.

Leave `.env` pointing at production for now: every Prisma CLI command in the rest of this checklist runs against the hosted database, and the last step switches local development back. Anything that loads `.env` in this window talks to production, including your test suite and any seed script that clears tables, and `migrate dev` and `migrate reset` will do to production exactly what their names say; the permanent home for these credentials is your hosting platform's environment settings.

### Move the schema and the data

**Starting fresh in production.** If your local data is disposable prototype data, replay the migration history against the hosted database and reseed.

This assumes a `prisma/migrations` folder, which you do not have if you prototyped with `npx prisma@7 db push`: `db push` never writes migration files, and `migrate dev` stops with `P3005, The database schema is not empty` against a database that already has your tables. Baseline instead, with `.env` pointing at your local database:

```bash
mkdir -p prisma/migrations/0_init

npx prisma@7 migrate diff \
  --from-empty \
  --to-schema prisma/schema.prisma \
  --script > prisma/migrations/0_init/migration.sql

npx prisma@7 migrate resolve --applied 0_init
```

That writes the migration your schema implies and records it as applied locally, without touching your data; the [baselining docs](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/baselining) cover the workflow in full. Point `.env` back at production before continuing. Do this before dumping, too, if you take the data path below, so the dump has a migration history to carry.

With `.env` on production, the CLI applies your migrations to the hosted database, over the direct connection:

```bash
npx prisma@7 migrate deploy
```

```text
2 migrations found in prisma/migrations

All migrations have been successfully applied.
```

`migrate deploy` applies the committed migration files in order, with no schema drafting, no prompts and no drift detection, which makes it safe for CI; the [workflows docs](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production) explain the split from `migrate dev`. If you have a seed script for production defaults, run it once now, while `.env` points at production.

**Bringing the data along.** If the local data matters, copy it with the standard Postgres tools. Both commands below take their database on the command line with `-d`, so neither reads `.env`.

The commands below are the Docker path. If your data lives in a local `prisma dev` instance, use the [Prisma VS Code extension](https://marketplace.visualstudio.com/items?itemName=Prisma.prisma), whose push-to-cloud action moves a local database to Prisma Postgres without a dump file; a PGlite instance serves a single connection, so anything else holding it blocks a dump, and `pg_dump` rejects Prisma's pool-tuning parameters unless you trim the printed URL back to `?sslmode=disable`.

Export from the Docker database:

```bash
pg_dump -Fc -v -n public --large-objects -f db_dump.bak \
  -d "postgresql://postgres:postgres@localhost:5432/postgres"
```

Import into Prisma Postgres using the direct connection string. `--no-owner` and `--no-privileges` skip the ownership and grant statements that name your local roles, which do not exist in Prisma Postgres:

```bash
pg_restore \
  --no-owner \
  --no-privileges \
  -d "postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require" \
  -v \
  ./db_dump.bak
```

`--no-owner` and `--no-privileges` leave row-level security policies in place. A policy that names a local role fails on restore, and `pg_restore` moves on to the next object, so list the policies before you dump with the query in the full guide's [inspect step](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql#1-inspect-the-source-database). Mark the ones that name local roles with `;` in the `pg_restore --list` manifest, as its [export step](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql#3-stop-source-writes-and-export-the-final-snapshot) shows, and pass that manifest to `pg_restore` with `--use-list`, as its [restore step](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql#4-restore-into-prisma-postgres) does; the manifest does nothing without that flag. Recreate those policies for your Prisma Postgres roles once the data is in.

Three details decide whether the restore lands cleanly. First, Prisma Postgres runs PostgreSQL 17, so `pg_dump` and `pg_restore` need to be version 17 (check with `pg_dump --version`); a PostgreSQL 17 `pg_dump` reads older servers but not an 18 one, as [noted above](#where-prisma-postgres-is-the-wrong-choice). Second, `-n public` dumps the `public` schema, where Prisma puts your tables by default, including `_prisma_migrations`, so your migration history travels with the data and the `migrate status` check below confirms it arrived; if you use `multiSchema` or keep tables outside `public`, add a `-n` flag per schema, or the restore looks clean while those tables are missing. `-n` also skips objects in other schemas that `public` depends on, so a `public` table that uses a type, function or sequence from another schema can fail to restore. Check for those dependencies before you dump; add a `-n` flag for each schema they live in, or drop `-n` and dump every schema, as the full guide's [export step](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql#3-stop-source-writes-and-export-the-final-snapshot) does. `-n` leaves large objects out of the dump as well, which is why the command carries `--large-objects`: without it, a table that stores files through PostgreSQL's large-object functions restores its rows but not the files. Third, the target database already has a `public` schema, so the restore reports `schema "public" already exists`. That is an error, not a warning: `pg_restore` continues past it by default and prints a count of errors at the end. Read every error above that count. On a fresh database the `public` schema error is the one to expect; treat any other error as something that did not load, and another `already exists` error in particular means you restored on top of a database you had already run `migrate deploy` against. Because `pg_restore` does not roll back what it already loaded, the fix is a new, empty database, not a second run. To stop at the first error and roll back everything the restore loaded instead, follow the full guide's [restore step](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql#4-restore-into-prisma-postgres), which runs `pg_restore` with `--single-transaction --exit-on-error` and a restore manifest; with this dump, prefix the `SCHEMA - public` and `COMMENT - SCHEMA public` lines with `;`, as the [Supabase guide](https://www.prisma.io/docs/guides/switch-to-prisma-postgres/from-supabase#5-restore-into-prisma-postgres) does, along with any policy lines you marked for local roles above, and leave every other line as it is. That keeps the `public` schema the target already has and still restores its tables, sequences and data.

### Validate, then deploy

Do not declare victory on a successful restore. Three checks, then the switch:

1. **Migration status.** Run `npx prisma@7 migrate status` against the hosted database. It compares your migration files against the `_prisma_migrations` table, so it confirms the history arrived intact, not that every column matches your schema:

   ```text
   Database schema is up to date!
   ```

2. **Row counts.** Open the **Studio** tab in the Console, or run a count against the direct connection:

   ```bash
   psql "postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require" \
     -c 'SELECT count(*) FROM "User";'
   ```

3. **Smoke test.** Start the app locally, with `.env` still on the hosted database, and click through the main flows. You are verifying config, not code, so the reads carry most of the signal; if you imported real data, keep the writes to records you can clean up afterwards, because cascades, sequence values and anything that sends mail do not come back with a `DELETE`.

4. **Deploy.** Set `DATABASE_URL` and `DIRECT_URL` in the hosting platform, add `npx prisma@7 migrate deploy` to the deploy pipeline so future migrations apply automatically, and ship.

Then put both local URLs back in `.env` in the same edit and keep the loop: `migrate dev` against `prisma dev` locally, commit the migration files, and let the pipeline replay them in production. A leftover `DIRECT_URL` points the CLI at production while your app runs local, and a leftover `DATABASE_URL` is worse: the app reads and writes production while everything looks local. Keep the old local database until production has run for a while, because `docker compose down -v` or `npx prisma@7 dev rm <name>` deletes the last live copy of that data.

## Frequently asked questions

### How do I move a local Postgres database to Prisma Postgres?

Create a database in the Prisma Console, run `pg_dump` against the laptop database and `pg_restore` into the new one over the direct connection string, then set `DATABASE_URL` to the pooled string. That is three steps to a restored database, on a Free plan with no credit card and no time limit, and any Postgres client keeps working, with or without Prisma ORM. [Five services compared](#five-services-compared) sets the same steps and free tiers side by side with Neon, Render, Railway and Supabase.

### Do I have to move my local data to production?

Move the data when it matters, and start fresh when it does not. For prototype data, run `npx prisma@7 migrate deploy` against the hosted database to recreate the schema from your committed migration files, then reseed. Copy it when it is real: content you authored, imported records, or anything users would miss.

### Does my application code change when I move to Prisma Postgres?

No, the schema, the generated client and the queries you wrote stay the same. The changes are two environment variables, the pooled `DATABASE_URL` and the direct `DIRECT_URL`, plus the one config line that points the Prisma CLI at the direct connection.

### Should I keep using prisma dev after production exists?

Yes, that is the intended workflow: production traffic hits hosted Prisma Postgres while daily development stays on a local `prisma dev` instance, and schema changes flow one way, from `migrate dev` locally, through git, to `migrate deploy` in your pipeline.
