[Prisma Postgres](https://www.prisma.io/docs/postgres), a managed PostgreSQL database, takes the Postgres database on your laptop in three commands, `npx prisma postgres create`, `pg_dump` and `pg_restore`, on a Free plan with no credit card, PostgreSQL 17 and connection pooling included, and every Postgres client you use today keeps working. Neon is the better pick if you need point-in-time recovery or a branch that copies production data, and Supabase if you want auth and file storage from the same vendor. Prisma makes Prisma ORM, Prisma Postgres and Prisma Compute.

Every managed Postgres service accepts a standard `pg_dump` archive; what differs is how you create the target, which PostgreSQL version it runs and what the free tier allows, and the [table below](#how-the-import-works) compares five services on those. The rest of the post is the checklist for a Prisma project: five steps that take an app on Docker Postgres or a local `prisma dev` instance to Prisma Postgres with schema, data and migration history intact.

## Quick recommendation

If the database runs PostgreSQL 17 or older, dump it and restore it into Prisma Postgres on the Free plan; the docs page [Migrate a local Postgres database to a managed Postgres service](https://www.prisma.io/docs/postgres/import-from-existing-database) has the three commands and the checks to run first. If your laptop already runs PostgreSQL 18, the PostgreSQL 17 tools cannot dump it: read the caveat in the [import guide](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql) first, or pick Neon or Render, which offer PostgreSQL 18. If you want the app hosted next to the database, [Prisma Compute](https://www.prisma.io/docs/compute) runs it on the same plan.

| Your situation | Pick | Why |
| --- | --- | --- |
| A laptop database on PostgreSQL 17 or older, standard tools, nothing else to move | Prisma Postgres | Three commands, Free plan with no credit card, PostgreSQL 17, connection pooling included, and any Postgres client keeps working |
| A Prisma ORM project whose migration history has to come along | Prisma Postgres | The `_prisma_migrations` table travels in the dump, and `npx prisma@7 migrate status` confirms it arrived |
| The app should run next to the database, on one plan | Prisma Compute + Prisma Postgres | Add a Composer declaration and deploy with `npx prisma deploy module.ts`; the Free plan covers app and database with no usage billing |
| A rehearsal of the restore with throwaway data, no account yet | `npx create-db@latest` | A temporary Prisma Postgres database, deleted after 24 hours unless you claim it; never for the real copy |
| You need point-in-time recovery or a branch that copies production data | Neon | Its plans carry a restore window (6 hours on Free, up to 7 days on Launch, up to 30 days on Scale) and 10 branches per project on Free ([pricing](https://neon.com/pricing), as of September 2026); Prisma Postgres has daily backups on paid plans and no point-in-time recovery yet |
| You want auth and file storage from the database vendor | Supabase | The Free plan includes Auth for 50,000 monthly active users and 1 GB of file storage ([pricing](https://supabase.com/pricing), as of September 2026) |
| The source already runs PostgreSQL 18 | Neon or Render | Both offer PostgreSQL 18 databases ([Neon](https://neon.com/docs/postgresql/postgres-version-policy), [Render](https://render.com/docs/postgresql-creating-connecting), as of September 2026); the PostgreSQL 17 tools Prisma Postgres needs cannot dump an 18 server |

## How the import works

:::note[How we compared]

We make Prisma Postgres and list it first for the situations in the table above. The other four rows rest on each vendor's own documentation as read on September 29, 2026, linked in the last column, on four criteria: the import tool, the steps between an empty account and a restored database (our count, following each vendor's guide), the free tier and the PostgreSQL versions offered. The one thing Neon does that Prisma Postgres does not: a restore window on every plan and branches that copy production data.

:::

| Service | Import tool | Steps | Free tier | PostgreSQL version | Source (as of September 2026) |
| --- | --- | --- | --- | --- | --- |
| **Prisma Postgres** | `pg_dump` and `pg_restore` with PostgreSQL 17 tools, over the direct connection | 3: `npx prisma postgres create`, `pg_dump -Fc`, `pg_restore --no-owner --no-privileges` | 200k operations a month, 500 MB, 50 databases, no credit card | 17 | [Import guide](https://www.prisma.io/docs/postgres/import-from-existing-database), [pricing](https://www.prisma.io/pricing) |
| **Neon** | Import Data Assistant: paste the source connection string, for databases under 10 GB on Postgres 14 to 17; over 10 GB, `pg_dump` and `pg_restore` | 4: open the assistant, paste the source connection string and run its checks, create the project, start the import (one-hour limit) | 100 CU-hours and 0.5 GB per project, 100 projects | 14, 15, 16, 17 or 18 | [Import Data Assistant](https://neon.com/docs/import/import-data-assistant), [versions](https://neon.com/docs/postgresql/postgres-version-policy), [pricing](https://neon.com/pricing) |
| **Supabase** | `pg_dump` with `--no-owner --no-privileges`, then `pg_restore` through the session pooler; roles and the row-level security status of tables are not migrated | 5: set up a migration machine, prepare the project, dump, restore, then recreate roles and re-enable RLS | 2 active projects, 500 MB each, paused after a week without activity | 15 or 17 | [Migration guide](https://supabase.com/docs/guides/platform/migrating-to-supabase/postgres), [pricing](https://supabase.com/pricing), [supabase/postgres](https://github.com/supabase/postgres) |
| **Railway** | Standard `pg_dump` and `pg_restore` over the database's public TCP proxy (`DATABASE_PUBLIC_URL`) | 4: add Postgres, enable public access, dump, restore | Free plan with $1 of monthly usage credit; Hobby is $5 a month with $5 of usage included | 16 on the `latest` tag of Railway's `postgres-ssl` image, with other major versions as tags | [Postgres guide](https://docs.railway.com/guides/postgresql), [template](https://github.com/railwayapp-templates/postgres-ssl), [pricing](https://railway.com/pricing) |
| **Render** | Standard `pg_dump` and `pg_restore` against the external database URL | 3: create a database, dump, restore | One free database per workspace, 1 GB, expires 30 days after creation | 13 to 18 | [Creating and connecting](https://render.com/docs/postgresql-creating-connecting), [backups and restores](https://render.com/docs/postgresql-backups), [free tier](https://render.com/docs/free) |

A `pg_dump` archive does not carry PostgreSQL roles, so on the four `pg_dump` paths the ownership and grant statements have to be skipped or rewritten; Supabase says so outright, and Neon's assistant does not document what it does with roles. The free tiers differ in what runs out: Render's free database expires after 30 days, Supabase pauses a free project after a week without activity, Railway's free plan is a $1 monthly usage credit, Neon's is 100 CU-hours per project, and Prisma Postgres counts operations, 200k a month, with no expiry and no credit card.

## Where Prisma Postgres is the wrong choice

- You need point-in-time recovery or a branch that copies production data. Prisma Postgres takes daily backups on paid plans, kept 7 days on Starter and Pro and 30 days on Business, and has no point-in-time recovery yet; Neon's plans carry a restore window and branches.
- The source runs PostgreSQL 18. The PostgreSQL 17 tools that Prisma Postgres needs cannot dump it, and the [import guide](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql) says a source on 18 needs a separate downgrade-compatible process; Neon and Render offer PostgreSQL 18 databases.
- The database uses PostGIS or TimescaleDB. Neither is on the [supported extensions list](https://www.prisma.io/docs/postgres/database/postgres-extensions#supported-extensions).

## The local-to-production gap

Three things move: where the database runs, the connection strings that point at it, and the schema and data that have to arrive there. The schema, the queries and Prisma Client stay as they are. As a checklist:

1. Develop against a local database, with `prisma dev` or Docker.
2. Create the hosted Prisma Postgres database.
3. Point your config at it.
4. Replay the schema, and move the data if it matters.
5. Validate, deploy, and keep the local loop.

The commands below pin `prisma@7`, because the post follows the Prisma ORM 7 workflow (`migrate dev`, `prisma.config.ts`); Prisma ORM 8, the version npm installs by default, renames or drops them, and [Coming from Prisma ORM 7](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7) maps each one.

## Start local: `prisma dev` or Docker

The classic local setup is [Docker](https://www.docker.com): a `postgres:17` container on port 5432, a volume so data survives restarts, and `DATABASE_URL="postgresql://postgres:postgres@localhost:5432/postgres"` in `.env`. If you already have it, keep it: the rest of the checklist is identical.

The lighter route is `prisma dev`, which ships with the Prisma CLI:

```bash
npx prisma@7 dev
```

That starts a local Prisma Postgres instance on [PGlite](https://pglite.dev), an embedded Postgres engine, with no daemon or container, and prints connection strings ready to paste into `.env`:

```text
✔  Your local Prisma Postgres server default is now running

🔌 To connect with Prisma ORM use the following connection strings:

   DATABASE_URL="postgres://postgres:postgres@localhost:51214/template1?sslmode=disable&..."
```

Node.js 20 or later is the only requirement. `npx prisma@7 dev --name myapp` gives every project its own named instance, `--detach` runs the server in the background, and `prisma dev ls`, `prisma dev stop <name>` and `prisma dev rm <name>` list, stop and delete instances.

It is a development tool that serves one connection at a time, not something you self-host; the [local development docs](https://www.prisma.io/docs/local-development/postgres) have the full reference.

Whichever route you chose, create the schema and, if your config defines a seed script, seed:

```bash
npx prisma@7 migrate dev
npx prisma@7 db seed
```

## Create the hosted database

Create the production database in the [Prisma Console](https://console.prisma.io):

1. Open the Console and click **New project** in your workspace.
2. Name the project, click **Get started** under Prisma Postgres, and pick the region closest to your users.
3. Click **Create project**, and wait for the database to finish provisioning.

Then copy the connection strings:

1. Select the database and click **Connect to your database**.
2. Click **Generate new connection string** and copy both strings it gives you.

Every Prisma Postgres database has [two connection strings](https://www.prisma.io/docs/postgres/database/connecting-to-your-database): **pooled** (`pooled.db.prisma.io`) for application traffic and **direct** (`db.prisma.io`) for migrations and tools like `pg_restore`. You will use both.

Two CLI alternatives: for a brand-new project, `npx prisma@7.9.1 init --db` scaffolds the schema and provisions a Prisma Postgres database in one go, and [`npx create-db@latest`](https://www.prisma.io/docs/postgres/npx-create-db) creates a temporary database with no sign-up, deleted after 24 hours unless you claim it.

## Update env and config

Before you touch `.env`, check that it is gitignored, because production credentials are about to live in it, and keep your local URLs somewhere you can get them back; for a `prisma dev` instance, `npx prisma@7 dev ls` shows the connection string again.

Now point the app at the hosted database by swapping the connection strings:

```text
# .env (before)
DATABASE_URL="postgres://postgres:postgres@localhost:51214/template1?sslmode=disable&..."

# .env (after)
DATABASE_URL="postgres://USER:PASSWORD@pooled.db.prisma.io:5432/postgres?sslmode=require"
DIRECT_URL="postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require"
```

The app reads the pooled string through `DATABASE_URL` at runtime; the direct string is for the Prisma CLI, because migrations hold locks and session state across statements and fail through the PgBouncer transaction pooler, while an app on the direct string quietly exhausts connections under load. [Connecting to your database](https://www.prisma.io/docs/postgres/database/connecting-to-your-database) lists the other work that wants the direct string. Add `DIRECT_URL` and point the datasource in `prisma.config.ts` at it:

```ts
// prisma.config.ts
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",
  datasource: {
    url: env("DIRECT_URL"),
  },
});
```

The `url` line is the only change. That is the Prisma ORM 7 setup, where connection URLs live in `prisma.config.ts`; on Prisma ORM 6 the same job is done by `directUrl` in the schema's `datasource` block. For local development, set `DIRECT_URL` to the same value as `DATABASE_URL`, because the local server has no pooler.

Leave `.env` pointing at production for now: every Prisma CLI command in the rest of this checklist runs against the hosted database, and the last step switches local development back. Anything that loads `.env` in this window talks to production, including your test suite and any seed script that clears tables, and `migrate dev` and `migrate reset` will do to production exactly what their names say; the permanent home for these credentials is your hosting platform's environment settings.

## Move the schema and the data

**Starting fresh in production.** If your local data is disposable prototype data, replay the migration history against the hosted database and reseed.

This assumes a `prisma/migrations` folder, which you do not have if you prototyped with `npx prisma@7 db push`: `db push` never writes migration files, and `migrate dev` stops with `P3005, The database schema is not empty` against a database that already has your tables. Baseline instead, with `.env` pointing at your local database:

```bash
mkdir -p prisma/migrations/0_init

npx prisma@7 migrate diff \
  --from-empty \
  --to-schema prisma/schema.prisma \
  --script > prisma/migrations/0_init/migration.sql

npx prisma@7 migrate resolve --applied 0_init
```

That writes the migration your schema implies and records it as applied locally, without touching your data; the [baselining docs](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/baselining) cover the workflow in full. Point `.env` back at production before continuing. Do this before dumping, too, if you take the data path below, so the dump has a migration history to carry.

With `.env` on production, the CLI applies your migrations to the hosted database, over the direct connection:

```bash
npx prisma@7 migrate deploy
```

```text
2 migrations found in prisma/migrations

All migrations have been successfully applied.
```

`migrate deploy` applies the committed migration files in order, with no schema drafting, no prompts and no drift detection, which makes it safe for CI; the [workflows docs](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production) explain the split from `migrate dev`. If you have a seed script for production defaults, run it once now, while `.env` points at production.

**Bringing the data along.** If the local data matters, copy it with the standard Postgres tools. Both commands below take their database on the command line with `-d`, so neither reads `.env`.

The commands below are the Docker path. If your data lives in a local `prisma dev` instance, use the [Prisma VS Code extension](https://marketplace.visualstudio.com/items?itemName=Prisma.prisma), whose push-to-cloud action moves a local database to Prisma Postgres without a dump file; a PGlite instance serves a single connection, so anything else holding it blocks a dump, and `pg_dump` rejects Prisma's pool-tuning parameters unless you trim the printed URL back to `?sslmode=disable`.

Export from the Docker database:

```bash
pg_dump -Fc -v -n public -f db_dump.bak \
  -d "postgresql://postgres:postgres@localhost:5432/postgres"
```

Import into Prisma Postgres using the direct connection string. `--no-owner` and `--no-privileges` skip the ownership and grant statements that name your local roles, which do not exist in Prisma Postgres:

```bash
pg_restore \
  --no-owner \
  --no-privileges \
  -d "postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require" \
  -v \
  ./db_dump.bak
```

Three details decide whether the restore lands cleanly. First, Prisma Postgres runs PostgreSQL 17, so `pg_dump` and `pg_restore` need to be version 17 (check with `pg_dump --version`); a PostgreSQL 17 `pg_dump` reads older servers but not an 18 one, as [noted above](#where-prisma-postgres-is-the-wrong-choice). Second, `-n public` dumps the `public` schema, where Prisma puts your tables by default, including `_prisma_migrations`, so your migration history travels with the data and the `migrate status` check below confirms it arrived; if you use `multiSchema` or keep tables outside `public`, add a `-n` flag per schema, or the restore looks clean while those tables are missing. Third, a restore prints a `schema "public" already exists` warning, which is safe to ignore; genuine `already exists` errors mean you restored on top of a database you had already run `migrate deploy` against.

## Validate, then deploy

Do not declare victory on a successful restore. Three checks, then the switch:

1. **Migration status.** Run `npx prisma@7 migrate status` against the hosted database. It compares your migration files against the `_prisma_migrations` table, so it confirms the history arrived intact, not that every column matches your schema:

   ```text
   Database schema is up to date!
   ```

2. **Row counts.** Open the **Studio** tab in the Console, or run a count against the direct connection:

   ```bash
   psql "postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require" \
     -c 'SELECT count(*) FROM "User";'
   ```

3. **Smoke test.** Start the app locally, with `.env` still on the hosted database, and click through the main flows. You are verifying config, not code, so the reads carry most of the signal; if you imported real data, keep the writes to records you can clean up afterwards, because cascades, sequence values and anything that sends mail do not come back with a `DELETE`.

4. **Deploy.** Set `DATABASE_URL` and `DIRECT_URL` in the hosting platform, add `npx prisma@7 migrate deploy` to the deploy pipeline so future migrations apply automatically, and ship.

Then put both local URLs back in `.env` in the same edit and keep the loop: `migrate dev` against `prisma dev` locally, commit the migration files, and let the pipeline replay them in production. A leftover `DIRECT_URL` points the CLI at production while your app runs local, and a leftover `DATABASE_URL` is worse: the app reads and writes production while everything looks local. Keep the old local database until production has run for a while, because `docker compose down -v` or `npx prisma@7 dev rm <name>` deletes the last live copy of that data.

## Frequently asked questions

### Do I have to move my local data to production?

Move it only if it matters. For prototype data, run `npx prisma@7 migrate deploy` against the hosted database to recreate the schema from your committed migration files, then reseed. Copy it when it is real: content you authored, imported records, or anything users would miss.

### Does my application code change when I move to Prisma Postgres?

No, the schema, the generated client and the queries you wrote stay the same. The changes are two environment variables, the pooled `DATABASE_URL` and the direct `DIRECT_URL`, plus the one config line that points the Prisma CLI at the direct connection.

### Should I keep using prisma dev after production exists?

Yes, that is the intended workflow: production traffic hits hosted Prisma Postgres while daily development stays on a local `prisma dev` instance, and schema changes flow one way, from `migrate dev` locally, through git, to `migrate deploy` in your pipeline.
