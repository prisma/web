Renaming a column is straightforward until there's data in it.

Say you have a `User` model with a `username` field, and you want to rename it to `handle`. You update your Prisma schema, fix the references in your application, and run your tests. Everything passes.

But when Prisma compares the old schema with the new one, it can't necessarily tell that you intended a rename. It sees a column that disappeared and another that appeared.

The resulting migration could drop `username` and add `handle`. Your schema would be correct, but the existing usernames would be gone.

Prisma ORM 8 changes how these situations are handled. It requires explicit decisions about potentially destructive operations, makes migrations easier to inspect, and checks that the database is in the expected state before applying changes.

These checks happen at different points in the migration process. Let's look at what each one does.

## Catching destructive changes before generating a migration

Consider this model:

```prisma
model User {
  id       Int    @id @default(autoincrement())
  email    String @unique
  username String
}
```

You rename `username` to `handle`:

```prisma
model User {
  id     Int    @id @default(autoincrement())
  email  String @unique
  handle String
}
```

Before applying the change to your development database, you can inspect it:

```bash
npx prisma db update --dry-run
```

Prisma reports two operations:

```text
├─ ⚠ Drop column "username" from "User"
└─ Add column handle to User

⚠ This migration contains destructive operations that may cause data loss.
```

Previously, you would have needed to recognize the problem and manually modify the generated SQL.

In Prisma ORM 8, the migration planner asks you to resolve the ambiguity before generating the migration. You can tell it that the change is a rename:

```bash
npx prisma migration plan \
  --name rename_username_to_handle \
  --rename User.username:User.handle
```

The generated operation now preserves the existing data:

```sql
ALTER TABLE "public"."User"
RENAME COLUMN "username" TO "handle";
```

You can also explicitly approve a deletion using `--delete` when removing data is intentional.

The important distinction is that Prisma doesn't infer your intent from the schema diff. When an operation could destroy data, you need to state what you want to happen.

This applies to automated workflows as well. Running `db update` with `--yes` won't approve a destructive operation. If the command needs a decision and the session isn't interactive, it fails with an explanation of how to resolve the change.

For coding agents, that means a potentially destructive schema change can't be approved simply by accepting every prompt.

## Making destructive operations visible during review

Suppose your application no longer needs the `bio` column. You've confirmed that its data can be removed, so you generate a migration:

```bash
npx prisma migration plan \
  --name remove_unused_bio \
  --delete User.bio
```

Prisma ORM 8 classifies migration operations according to the kind of change they make, including whether they are destructive.

You can inspect the migration by passing its directory to `migration show`:

```bash
npx prisma migration show migrations/app/<timestamp>_remove_unused_bio
```

For this example, the output includes:

```text
1 operation(s)
└─ ⚠ Drop column "bio" from "User"

⚠ This migration contains destructive operations that may cause data loss.
```

The migration can still be applied. Prisma isn't trying to prevent intentional deletions, but the operation is identified clearly enough that a reviewer doesn't need to discover it by reading the generated SQL.

This is particularly useful when a pull request includes several schema changes. Adding a field, changing a type, and deleting a column have different consequences, and the review should reflect that.

There is also a distinction between planning and applying migrations. The decision to delete `bio` is made when the migration is created. `db migrate` doesn't ask for that approval again when deploying it.

Reviewing the planned migration therefore matters, because deployment will execute the operation you've approved.

## Detecting modified migration files

Reviewing a migration is useful only if the migration being deployed matches what was reviewed.

Prisma ORM 8 records a hash of each migration's compiled operations and metadata. Before using those files, Prisma recomputes the hash and compares it with the recorded value.

If someone changes the compiled migration after it was generated, Prisma detects the mismatch.

You can check this before deployment:

```bash
npx prisma migration check
```

The command doesn't require a database connection, which makes it suitable for CI.

Prisma also performs the integrity check when running `db migrate`, so a modified compiled migration is rejected even if the separate CI check wasn't executed.

There is one limitation: the hash covers the compiled migration files, not the source `migration.ts` file. If you edit the source and recompile the migration, you should review the compiled result before merging it.

The hash tells Prisma whether the recorded compiled migration has changed. It doesn't replace code review.

## Keeping direct schema changes out of production

During development, `prisma db update` is useful because it applies schema changes without creating migration files. You can experiment with your database without maintaining a migration for every intermediate change.

Production databases usually need a different approach.

You want changes to go through migrations so they can be reviewed, tracked, and deployed consistently. Otherwise, someone could update the production schema directly and leave the application or migration history out of sync.

Prisma ORM 8 introduces database change policies to help enforce this distinction.

For example, you can declare that a production database should only accept migration-based changes. The declaration goes in the ref file for that environment, `migrations/app/refs/production.json`, next to the schema state the environment should be at:

```json
{
  "hash": "4948…c862",
  "invariants": [],
  "policies": {
    "change": ["migrate"]
  }
}
```

After the policy is explicitly applied, Prisma records it in the database.

If someone subsequently attempts a direct schema update:

```bash
npx prisma db update \
  --db "$PRODUCTION_DATABASE_URL"
```

Prisma refuses the operation because the database requires migrations.

The policy is stored in the database rather than relying solely on a configuration file in the repository. This means supported Prisma CLI versions can check the rule regardless of which checkout or environment is making the request.

Changing the policy also requires explicit authorization. Editing the ref file alone isn't enough to silently remove the restriction.

There are limits to what this protects.

The policy is enforced by Prisma's CLI, not by the underlying database permissions. Someone with direct SQL access can still modify the schema, and older CLI versions may not recognize the policy. Database access controls remain necessary.

Prisma ORM 8 also introduces data protection policies that describe whether data loss or changes to data access should be allowed. These are currently recorded and compared but not yet enforced. A database marked as forbidding data loss can therefore still accept an explicitly approved destructive migration.

For now, the enforceable protection is the change policy: it can require that schema changes go through the migration workflow.

## Checking the database before applying a migration

A migration is written against an expected database state and that state might change before deployment.

Suppose you generate a migration that renames `username` to `handle`, but someone manually renames the column to `user_name` in the meantime.

When the migration runs, the column it expects no longer exists.

Prisma ORM 8 checks the database's recorded schema state against the available migration history before starting. It also verifies the preconditions for individual operations.

In this example, Prisma stops because it cannot find the expected `username` column.

On PostgreSQL, the migration run is executed in a transaction, so a failed operation can roll back the changes made during that run. Prisma updates its recorded migration state only after verifying that the database matches the expected result.

This doesn't eliminate every possible migration failure. It does mean Prisma checks its assumptions before executing each operation rather than continuing against a database that differs from the planned state.

## How this is relevant for coding agents

These checks become particularly relevant when coding agents are generating migrations.

An agent can modify a schema, write a migration, and prepare a deployment without necessarily understanding why a column disappeared or whether existing data is still needed.

Prisma ORM 8 doesn't require the agent to make every decision correctly. Instead, potentially destructive changes require an explicit instruction, compiled migrations are checked for unexpected modifications, and production databases can reject changes that bypass the migration workflow.

The error messages also explain what needs to be resolved, so an agent can identify a failed operation without guessing at a workaround.

But there are boundaries.

An agent with production credentials can still execute raw SQL. An explicitly approved deletion will still delete data. And a migration that preserves the data can still break an application if older instances continue using the previous schema.

For example, renaming `username` to `handle` preserves the column's contents, but it doesn't account for application instances still querying `username`. In a production system with multiple application versions running during deployment, you may need to introduce the new column, migrate the data, update the application, and remove the old column in a later release.

Prisma's migration checks don't replace that rollout planning.

Keeping production credentials restricted, reviewing migrations, and maintaining backups are still part of operating a database safely.

## Putting the checks together

The protections in Prisma ORM 8 address different failure points.

| Stage               | What Prisma checks                                                         |
| ------------------- | -------------------------------------------------------------------------- |
| Planning            | Whether a potentially destructive change has been explicitly resolved      |
| Review              | Which migration operations could cause data loss                           |
| Before deployment   | Whether compiled migration files match their recorded hashes               |
| Database access     | Whether the requested schema-change method is permitted                    |
| Migration execution | Whether the database matches the expected state and operation requirements |

Returning to the original column rename, Prisma can identify the proposed deletion before a migration is generated. Once the rename is planned, reviewers can inspect the operation, and Prisma can verify the compiled migration before applying it.

If production is configured to accept only migrations, a direct schema update is rejected. And if the database has changed unexpectedly, the migration can stop before executing an operation whose assumptions are no longer valid.

None of these checks makes data loss impossible. What they do is reduce the number of ways an unintended destructive change can pass unnoticed from a schema edit to a production database.

For developers and coding agents alike, that means fewer assumptions left unchecked during the migration process.
