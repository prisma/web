You've probably seen posts like these. A coding agent [empties every table in a database](https://www.reddit.com/r/Anthropic/comments/1v9iurd/and_just_like_that_opus_5_ultracode_wipes_the/) ten minutes into its first session, [deletes a production database](https://www.reddit.com/r/ClaudeAI/comments/1uqhqlf/claude_code_wiped_my_entire_production_database/) that the team then has to restore from a backup, or [runs `drizzle-kit push --force` against production](https://github.com/anthropics/claude-code/issues/27063) and destroys months of data. The tools and the commands differ, but the pattern is the same each time: an agent hits an error and runs a command that deletes data before anyone has read what it's doing.

People made these mistakes long before agents did. One of the older open issues on the Prisma repository is titled ["Too EASY to DELETE ALL database"](https://github.com/prisma/orm/issues/9114). An agent makes the same mistakes faster, because it can edit a schema, generate a migration, and apply it before you've read the first diff.

Prisma ORM 8 removes the commands that could wipe a database and adds guardrails to the commands that remain, so that a change that would lose data needs your approval:

The sections below show each of these briefly and link to the docs for the details.

## The commands that wipe a database are gone

Most of these incidents come down to a few commands: a reset that drops every table, a schema push with a force flag, or a scratch database whose URL pointed at real data. Prisma ORM 8 has none of them, and no migration command resets or drops the database you connect to.

An agent that runs an old command out of habit gets an error, and the database stays as it was:

```text
$ npx prisma migrate reset --force

✘ [CLI.V7_COMMAND] `prisma migrate reset` is a Prisma 7 command and is not available in Prisma 8
  why: Prisma 8 has no reset: `db update` moves the database to the contract without a reset and asks before losing data […]
→ Use the replacement: prisma db update
```

A stuck agent tends to run whatever an error message offers, so no error in Prisma ORM 8 suggests a reset. The suggested fix is always a command that keeps your data.

<ResetAttempt />

The [command table in the upgrade guide](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7#commands) lists what replaces each Prisma ORM 7 command, and [Don't Let Your AI Agent Delete Your Production Database](/stop-your-ai-agent-dropping-your-database) explains the reasoning behind the design.

## Deleting data needs an approval that names the field

A renamed field is the change that most often loses data by accident. Prisma compares the old schema with the new one, and in that comparison renaming `username` to `handle` looks the same as dropping one column and adding another. A migration planned that way deletes every existing username.

<RenameWalkthrough />

Prisma ORM 8 stops and asks which one you meant. Passing `--yes` doesn't answer the question, so an agent can't approve the deletion by accepting every prompt:

```text
$ npx prisma db update --yes

✘ [CLI.CONSENT_REQUIRED] "User.username" needs a statement, which --yes cannot give.
  why: Drop column "username" from "User" would lose the values of field "User.username".
→ Run the command again with --rename User.username:User.handle
→ Run the command again with --delete User.username
```

`--rename` keeps the data and `--delete` drops it. In both cases the approval names the field, which gives you something specific to look for in review. An agent can still pass `--delete` itself, so the [agent instructions](#what-should-you-tell-your-coding-agent) below tell it to ask you first.

[Renames and data loss](https://www.prisma.io/docs/cli/migration-plan#renames-and-data-loss) in the docs covers the flags, and [Type changes and required fields](https://www.prisma.io/docs/cli/migration-plan#type-changes-and-required-fields) covers the other changes that need your input.

## A reviewer can see what a migration deletes

Prisma labels every operation it plans that deletes data, so a reviewer can find a dropped column without reading the generated SQL. [`prisma migration show`](https://www.prisma.io/docs/cli/migration-show) prints the operations in a migration:

```text
1 operation(s)
└─ ⚠ Drop column "bio" from "User"

⚠ This migration contains destructive operations that may cause data loss.
```

The label is a warning, and the migration still applies, because you approved the deletion when you planned it.

Prisma also records a hash of each generated migration and rejects one that was edited afterwards. `prisma db migrate` checks the hash before it applies anything, and `prisma migration check` runs the same check in CI without a database connection. The hash covers the compiled migration, so a migration that was recompiled from an edited `migration.ts` passes and needs a new review. [Applying a migration](https://www.prisma.io/docs/orm/migrations/applying-a-migration#check-before-preview-then-apply) shows the full sequence.

## Production can require migrations and forbid data loss

Everything so far works without setup. Without a policy, though, anyone who holds the production connection string can run a development command such as `prisma db update` against it, and that includes an agent. Database policies are opt-in and close that gap.

You declare a policy in the file that describes an environment, and the database's owner records it in the database with one deploy:

```json
{
  "policies": {
    "change": ["migrate"],
    "dataProtection": { "dataLoss": "data-loss-forbidden" }
  }
}
```

With `change: ["migrate"]`, Prisma refuses `db update` on that database and accepts only migrations. With `data-loss-forbidden`, it also refuses a migration that drops data, even one that was approved in review:

```text
$ npx prisma db migrate --db "$PRODUCTION_DATABASE_URL"

✘ [MIGRATION.DATA_PROTECTION_FORBIDS] This database's data protection policy forbids data loss
  why: The marker records dataLoss: data-loss-forbidden. Drop column "bio" from "User" (public.User.bio), in migration 20261120T1113_drop_bio of contract space "app".
→ […] To do it anyway, whoever owns the database must first change its data protection policy.
```

<PolicyOutcomes />

Loosening a policy takes a separate flag from the database's owner, and the refusal never names that flag, so a stuck agent doesn't find the override in the error message.

Policies need `prisma@8.0.0-rc.35` or later, and it's the Prisma CLI that enforces them, not the database's own permissions, so someone with direct SQL access can still change the schema. [Database policies](https://www.prisma.io/docs/orm/migrations/database-policies) in the docs has the setup steps and the full rules.

## Prisma checks the database before it changes anything

A migration is written for a particular database state, and that state can change before the migration deploys. Prisma checks the database before each operation and stops if it isn't in the state the migration expects:

```text
✘ [MIGRATION.PRECHECK_FAILED] Operation renameColumn.User.username failed during precheck: ensure column "username" exists
  why: […] the database has no column "username" on "User". The failed apply changed nothing.
```

On PostgreSQL the whole run is one transaction, so a failure partway through rolls back everything that run changed.

<ApplyRun />

[Rollbacks and recovery](https://www.prisma.io/docs/orm/migrations/rollbacks-and-recovery) covers what to do after a failed run.

## What should you tell your coding agent?

`prisma init` installs [agent skills](https://www.prisma.io/docs/cli/skills) that match the Prisma version in your project. They already tell an agent never to reset a database to fix a migration problem and never to loosen a policy to get its own deploy through.

The skills can't know which of your databases matter or when you want to be asked, so add those rules to your `AGENTS.md`, `CLAUDE.md`, or equivalent:

```md
## Database changes (Prisma ORM 8)

- Change the database only by editing the Prisma schema, then running
  `prisma contract emit`. Use `prisma db update` for the local development
  database. Use `prisma migration plan` for anything that will be deployed.
- Before applying, run `prisma db update --dry-run` or
  `prisma migration show <migration>` and list every operation marked
  destructive for me.
- If Prisma asks whether a change is a rename or a delete
  (`CLI.CONSENT_REQUIRED`), stop and ask me. Pass `--delete` or `--allow`
  only for a model or field I named in this conversation.
- Never reset, drop, or recreate a database to get past an error. Never run
  schema changes as raw SQL, and never use an older Prisma CLI to run a
  command that Prisma 8 refuses.
- Never pass `--permit-policy-change` or edit `policies` in
  `migrations/*/refs/*.json`. If a command fails with
  `MIGRATION.POLICY_MISMATCH`, `MIGRATION.CHANGE_POLICY_FORBIDS`, or
  `MIGRATION.DATA_PROTECTION_FORBIDS`, report it and stop.
- Connect only to the development database from `.env`. Never pass a
  staging or production URL to `--db`. Deployments apply migrations.
- Run `prisma migration check` before committing migrations. Don't edit
  `ops.json` or `migration.json` by hand.
```

Prisma catches an agent that breaks most of these rules. It can't catch raw SQL, an older CLI, or a production connection string in the agent's shell, and developers who relied on a rules file alone [report](https://forum.cursor.com/t/agent-decides-again-to-wipe-entire-db/123619) that agents forget it in long sessions.

## What doesn't Prisma ORM 8 protect against?

These guardrails apply only to schema changes made with the new Prisma commands, so they don't make data loss impossible:

- An agent that holds a production connection string can still run raw SQL or install the Prisma 7 CLI.
- A deletion that you approve still deletes the data. Commands whose purpose is deletion, such as `prisma dev --fresh` for local development services and `postgres delete` for a Prisma Postgres database, still exist.
- A hand-written SQL step in a migration carries whatever label its author gives it, so review it yourself.
- Nothing here looks at the queries your application runs, such as a `deleteMany` without a filter.
- A rename that keeps the data can still break running instances of your app that read the old column. Stage those changes as an [expand-and-contract migration](https://www.prisma.io/docs/guides/database/data-migration).

## What to set up on your own databases

Upgrading to Prisma ORM 8 gives you every guardrail above except policies. The rest depends on how you set up the databases you care about:

1. **Keep production credentials out of the agent's environment.** Most of these incidents started with a production connection string in a development shell. Let your deployment pipeline hold it.
2. **Record [policies](https://www.prisma.io/docs/orm/migrations/database-policies) on the databases that matter.** Declare `change: ["migrate"]` on production, and add `data-loss-forbidden` where no migration should ever remove data.
3. **Run `prisma migration check` in CI.** A migration that someone edited by hand then fails before it reaches a deploy.
4. **Make sure you can restore.** Prisma Postgres takes [daily backups](https://www.prisma.io/docs/postgres/database/backups) on paid plans. Whatever database you use, test a restore before you need one.
