Supabase protects your data with Postgres Row Level Security. But as an application grows, the authorization model tends to spread out: some of it lives in SQL migrations, some in RLS policies, some in dashboard settings, and some in application code.

The Supabase extension for [Prisma 8](https://www.prisma.io/docs/orm) puts those pieces in one place. Your tables, your relationships to `auth.users`, and your RLS policies live together in your Prisma schema. Prisma generates the migrations, and Postgres continues to enforce every policy.

Prisma 8 is available today as Release Candidate 1. Let's look at what changes, using a notes app where users can only read their own notes.

## Why Supabase authorization gets hard to track

Say every note in your app belongs to a user, and users must only ever see their own notes. Supabase gives you the right enforcement model for this: an RLS policy that checks `auth.uid()` is applied by Postgres on every query, no matter which code path issued it.

The hard part is keeping track of that model. To answer "who can read the `notes` table?", you may need to check:

- which columns `notes` has, after every migration that touched it
- whether `user_id` actually references `auth.users`, or just happens to hold UUIDs
- which RLS policies apply right now, after later migrations replaced earlier ones
- whether someone changed a policy in the dashboard, outside your migration history
- whether a server query still filters with `.eq('user_id', user.id)`, and which key its client uses

Each answer lives in a different place. Prisma 8 lets you describe all of them in one file.

## Define your schema and RLS together

Here is the notes app, complete:

```prisma
namespace public {
  model Note {
    id        Uuid        @id @default(uuid())
    title     String
    body      String?
    userId    Uuid
    user      supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
    createdAt Timestamptz @default(now())

    @@map("note")
    @@rls
  }

  // A signed-in user reads only their own notes.
  policy_select note_owner_read {
    target = Note
    roles  = [authenticated]
    using  = "\"userId\"::uuid = auth.uid()"
  }
}
```

Three things are happening here:

1. `user` is a real relation to Supabase's `auth.users` table.
2. `@@rls` enables Row Level Security, so no role sees any row unless a policy grants it.
3. `note_owner_read` says that signed-in users can read only their own notes.

There is deliberately no policy for anonymous visitors. With RLS enabled and no matching policy, they see zero rows.

Insert, update, and delete policies follow the same shape as `policy_select`, with the same `USING` and `WITH CHECK` conditions you would write in SQL. The full set for this app is four short blocks in the [Supabase extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase).

Declaring RLS in the Prisma schema is [the most-requested Supabase feature in Prisma's history](https://github.com/prisma/prisma/issues/12735), with over 400 reactions on the GitHub issue since 2022.

## Let Postgres filter rows for you

In a server route today, scoping a query to the signed-in user looks like this:

```ts
// supabase-js: the filter lives in application code
const supabase = createClient(url, key);

const { data: notes } = await supabase
  .from('notes')
  .select('id, title, body')
  .eq('user_id', user.id);
```

Whether that `.eq` is load-bearing depends on which key created the client. With the service role key, it is the only thing standing between one user and everyone's notes.

The Supabase extension removes that ambiguity. The client has no query methods until you bind a role, so you always choose the privilege level explicitly:

```ts
// Prisma 8: bind the verified user first, then query with no filter
const db = await getDb();
const bound = await db.asUser(jwt);

const notes = await bound.orm.public.Note
  .select('id', 'title', 'body')
  .all()
  .toArray();
```

`asUser()` verifies the JWT's signature against your project's public keys, then runs every query that follows as that user.

The query carries no user filter, and each user still sees only their own rows. The select policy is the filter, and Postgres applies it.

Writes get the same protection. Creating a note that belongs to someone else is rejected by the database's `WITH CHECK` condition:

```ts
await bound.orm.public.Note.select('id').create({ title, body, userId: someoneElse });
// => rejected by Postgres, not by an if-statement
```

For public traffic there is `db.asAnon()`. For admin jobs there is `db.asServiceRole()`, which bypasses RLS and is a separate, visible call in code review.

## Reference `auth.users` from your Prisma schema

Linking a table to Supabase Auth today means writing the constraint by hand:

```sql
-- a migration you write and maintain yourself
alter table public.notes
  add constraint notes_user_id_fkey
  foreign key (user_id) references auth.users (id) on delete cascade;
```

In the schema above, the same fact is one line:

```prisma
user supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
```

The extension knows the shape of everything Supabase owns, and it never generates DDL for Supabase's own tables. That rule makes it safe to reference `auth.users` from your models: the migration creates the foreign key, a note can never point at a user that doesn't exist, and deleting a user deletes their notes.

One boundary to know: the relation exists for the constraint. You cannot `include` the user from a note query, and trying is a compile-time error.

## Manage RLS through Prisma migrations

With SQL migrations, the current policy for a table is the sum of every migration that ever touched it. With Prisma 8, it is the policy block in your schema.

A policy change is an edit to that block. Then:

```npm
npx prisma@next migration plan --name add-notes
```

Prisma diffs your schema against the database and generates the DDL, policies included:

```sql
CREATE POLICY "note_owner_read_9f8e536e" ON "public"."note"
  AS PERMISSIVE FOR SELECT TO authenticated
  USING ("userId"::uuid = auth.uid())
```

`npx prisma@next migrate` applies it.

The workflow also runs in reverse. If your database already has policies, `npx prisma@next contract infer` reads them back into your schema, so adopting Prisma 8 doesn't mean rewriting your authorization from scratch.

RLS changes now appear next to the model they protect, which makes them easier to review in a pull request. The same property helps AI agents: one file describes your models, relationships, and policies.

## Keep using supabase-js for Auth, Storage, and Realtime

This doesn't replace `supabase-js`. Realtime subscriptions, Storage, and the Auth flows in your frontend stay where they are.

Prisma talks to Postgres directly and runs alongside them. Prisma 8 RC1 with the Supabase extension supports Node.js and Bun over your project's session pooler; the remaining boundaries are documented in the [extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase).

## Try Prisma 8 with your Supabase project

:::note[What is a Release Candidate?]
Prisma 8 is available today as Release Candidate 1 (RC1): the final preview before general availability. The API is stable, and we are collecting feedback before GA. [Share what you find in Discord](https://pris.ly/discord).
:::

Create a free Supabase project as a sandbox, then:

```npm
npx prisma@next orm init --yes --target postgres --authoring psl
npm install @prisma/orm-extension-supabase
```

Next:

1. Register the extension in `prisma.config.ts`: `extensions: [supabasePack]` inside the ORM config.
2. Set `DATABASE_URL` to your Supabase project's session pooler.
3. Add the schema and policies shown above.
4. Run:

```npm
npx prisma@next contract emit
npx prisma@next migration plan --name init
npx prisma@next migrate
```
