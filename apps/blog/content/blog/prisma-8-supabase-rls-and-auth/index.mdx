**Prisma 8 Release Candidate 1 lets you define your Supabase tables, auth relationships, and RLS policies in one Prisma schema. Prisma migrates all of it, Postgres enforces it, and we want your feedback before general availability.**

## Why Supabase projects end up with two sources of truth

Every Supabase app eventually splits its database schema across two homes. Your ORM holds the tables and relations and generates your types, while your Row Level Security policies and the foreign keys into `auth.users` live in handwritten SQL migrations, because no ORM could see the `auth` schema:

```sql
-- 20240301_rls.sql: written by hand, invisible to your ORM
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY "notes_owner" ON notes FOR SELECT
  TO authenticated USING (user_id = auth.uid());

ALTER TABLE notes
  ADD FOREIGN KEY (user_id) REFERENCES auth.users(id) ON DELETE CASCADE;
```

That split is where authorization bugs come from. When a production policy changes in the Supabase dashboard instead of your codebase, the update bypasses code review, and your ORM keeps generating queries with no awareness of the rules that now govern them. The most security-critical part of your data model is the one part no pull request ever shows.

Prisma 8 removes the split.

## One schema for models, auth, and RLS

Prisma 8, now in Release Candidate 1, extends the Prisma schema to cover the two things Supabase developers have always managed outside their ORM: RLS policies, declared next to the model they protect, and real foreign keys into Supabase's `auth.users` table. Prisma migrates both, so authorization changes travel through the same pull requests, diffs, and reviews as every other schema change.

## Define tables, auth relationships, and RLS together

Consider a notes application where every note belongs to a Supabase user:

```prisma
namespace public {
  model Note {
    id        Uuid        @id @default(uuid())
    title     String
    body      String?
    userId    Uuid
    user      supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
    createdAt Timestamptz @default(now())

    @@map("note")
    @@rls
  }
}
```

The `user` relation exists so that ownership is a fact the database guarantees rather than a convention your code follows. It becomes a real foreign key into `auth.users`, which means a note can never reference a user that doesn't exist, and deleting a user cascades to their notes without a cleanup script. Prisma understands the exact shape of `auth.users` because the Supabase extension ships a complete description of everything Supabase owns in your database, marked external so Prisma will reference it but never try to migrate or modify it.

`@@rls` enables Row Level Security on the table, which tells Postgres that no role sees any row unless a policy grants it. That is the foundation the next section builds on.

## Write RLS policies next to your models

Policies are named blocks in the same file, right below the model they protect:

```prisma
// A signed-in user reads only their own notes.
policy_select note_owner_read {
  target = Note
  roles  = [authenticated]
  using  = "\"userId\"::uuid = auth.uid()"
}
```

The insert, update, and delete policies follow the same shape, with a `withCheck` predicate so a user cannot write rows they don't own; the full set is four short blocks in the [Supabase extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase). There is deliberately no anon policy, because with RLS enabled and no matching policy, anonymous users see zero rows.

One command turns the schema and its policies into DDL and applies them:

```bash
npx prisma-next migrate
```

The generated migration enables RLS and creates each policy:

```sql
CREATE POLICY "note_owner_read_9f8e536e" ON "public"."note"
  AS PERMISSIVE FOR SELECT TO authenticated
  USING ("userId"::uuid = auth.uid())
```

You never write this SQL, and from now on every policy change appears in a schema diff. The workflow also runs in reverse: if you already have policies in a live database, `prisma-next contract infer` reads them back into your schema, so adopting Prisma 8 on an existing Supabase project doesn't mean rewriting your authorization from scratch.

## Let Postgres enforce access, not your application

Here is the route handler that lists a user's notes:

```ts
const notes = await bound.orm.public.Note
  .select('id', 'title', 'body', 'createdAt')
  .all()
  .toArray();
```

There is no `where userId = ...` filter, because the SELECT policy is the filter. Postgres runs the query as the signed-in user and returns only their rows, which means the forgotten-filter bug, the one where a single missing `where` clause leaks every user's data, stops being possible in application code.

The `bound` client carries the user's identity. You bind a role per request, and Prisma verifies the JWT from Supabase Auth before any query runs:

```ts
const db = await getDb();          // supabase({ contractJson, url, jwksUrl })

const bound = await db.asUser(jwt); // verified JWT, queries run as this user
// db.asAnon()                      // public traffic
// db.asServiceRole()               // admin jobs, bypasses RLS
```

![A request's JWT is verified by Prisma, the query runs as that user, and Postgres RLS filters the rows.](/prisma-8-supabase-rls-and-auth/imgs/request-flow.svg)

The client has no default query surface: until you choose `asUser`, `asAnon`, or `asServiceRole`, there is nothing to call. That design removes the classic footgun of running application queries as the connection's login role and silently bypassing RLS, because the compiler forces every query to name the identity it runs as.

Writes get the same protection. A request that tries to insert a note owned by someone else is rejected by the database's `WITH CHECK` predicate, regardless of what the application code says:

```ts
await bound.orm.public.Note.select('id').create({ title, body, userId: someoneElse });
// => rejected by Postgres, not by an if-statement
```

## What you gain from schema-defined authorization

Your authorization rules become part of the artifact you already review, so a policy change is a schema diff in a pull request instead of a surprise in the dashboard. Your auth relationships become real constraints that Postgres enforces, so referential integrity with Supabase Auth stops depending on cleanup scripts. And your security model becomes explicit in the types, so every query names the role it runs as and a reviewer can see who runs what at a glance.

The common thread is that schema and security evolve together. When a new model needs a policy, both land in the same commit, get reviewed by the same person, and ship in the same migration.

## Current limitations and supported scenarios

Prisma 8 RC1 with the Supabase extension supports Node.js and Bun, connecting through your project's session pooler (port 5432); the transaction pooler cannot carry the per-request role binding, and edge runtimes are not supported yet. Within that setup, a few boundaries to know:

- The `auth.users` relation is a constraint, not a navigable relation, so you cannot `include` the user from a note query. Traversal is a compile-time error rather than a runtime surprise.
- Policy predicates are strings, not a typed expression language.
- Realtime subscriptions and Storage are out of scope; keep using `supabase-js` for those. Prisma talks to Postgres directly and composes fine alongside it.

The [extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase) documents the remaining edge cases.

## Get started with Prisma 8 RC1 and Supabase

Spin up a free Supabase project as a sandbox and validate all of this yourself in a few minutes:

```bash
npx prisma-next init --yes --target postgres --authoring psl
npm install @prisma/orm-extension-supabase
```

Add the extension to `prisma-next.config.ts` with `extensions: [supabasePack]`, point `DATABASE_URL` at your project's session pooler, paste the schema and policies above, and run `npx prisma-next migrate`. One naming note: Prisma 8 installs as `prisma-next`, not `prisma@8`.
