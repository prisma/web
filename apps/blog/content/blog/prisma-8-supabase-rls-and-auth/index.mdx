**Prisma 8 Release Candidate 1 lets you define your Supabase tables, auth relationships, and RLS policies in one Prisma schema. Prisma migrates all of it, and Postgres enforces it on every query.**

## Why Supabase projects end up with two sources of truth

Row Level Security support is the most-requested Supabase-related feature in Prisma's history: [the GitHub issue asking for it](https://github.com/prisma/prisma/issues/12735) has collected over 400 reactions since 2022. Behind that demand is a split every Supabase app runs into.

Your ORM holds the tables and relations, and it generates your types. Your RLS policies and the foreign keys into `auth.users` live somewhere else, in SQL migrations written by hand:

```sql
-- 20240301_rls.sql: written by hand, invisible to your ORM
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY "notes_owner" ON notes FOR SELECT
  TO authenticated USING (user_id = auth.uid());

ALTER TABLE notes
  ADD FOREIGN KEY (user_id) REFERENCES auth.users(id) ON DELETE CASCADE;
```

When a production policy changes in the Supabase dashboard instead of your codebase, the change bypasses code review, and your ORM keeps generating queries with no awareness of the rules that govern them. The most security-critical part of your data model is the one part no pull request ever shows.

Prisma 8 removes the split.

## One schema for models, auth, and RLS

Prisma 8's Supabase extension brings both halves into your schema: RLS policies declared next to the model they protect, and real foreign keys into Supabase's `auth.users` table. One migration applies everything, and every change to your authorization rules shows up as a schema diff in a pull request.

## Write RLS policies next to your models

Consider a notes app where every note belongs to a Supabase user. The model and its read policy live in the same file:

```prisma
namespace public {
  model Note {
    id        Uuid        @id @default(uuid())
    title     String
    body      String?
    userId    Uuid
    user      supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
    createdAt Timestamptz @default(now())

    @@map("note")
    @@rls
  }

  // A signed-in user reads only their own notes.
  policy_select note_owner_read {
    target = Note
    roles  = [authenticated]
    using  = "\"userId\"::uuid = auth.uid()"
  }
}
```

`@@rls` turns on Row Level Security for the table, so no role sees any row unless a policy grants it. The policy block carries the same `USING` and `WITH CHECK` conditions you would otherwise write in SQL. The insert, update, and delete policies follow the same shape, with `withCheck` stopping users from writing rows they don't own; the full set is four short blocks in the [Supabase extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase). There is deliberately no anon policy, because with RLS enabled and no matching policy, anonymous visitors see zero rows.

The `user` field references your auth user table from your schema; we'll come back to what that unlocks below.

One command turns all of it into DDL and applies it:

```bash
npx prisma-next migrate
```

The generated migration enables RLS and creates each policy:

```sql
CREATE POLICY "note_owner_read_9f8e536e" ON "public"."note"
  AS PERMISSIVE FOR SELECT TO authenticated
  USING ("userId"::uuid = auth.uid())
```

You never write this SQL. And if your database already has policies, the workflow runs in reverse: `prisma-next contract infer` reads them back into your schema, so adopting Prisma 8 doesn't mean rewriting your authorization from scratch.

## Let Postgres enforce access, not your application

If you have wired Prisma to Supabase before, you know the trap: Prisma connects as the `postgres` role, which bypasses RLS, so the policies you wrote do nothing for queries that go through the ORM. Community workarounds involve client extensions and transaction wrappers that set the role by hand.

The part worth pausing on is step three. The query never filters by user, yet each user receives only their own notes, because the verified token decides what the database is willing to return. The forgotten `where` clause that leaks every user's data stops being a bug your code can have.

Writes get the same protection. Creating a note that belongs to someone else is rejected by the database's `WITH CHECK` condition, regardless of what the application code says:

```ts
await bound.orm.public.Note.select('id').create({ title, body, userId: someoneElse });
// => rejected by Postgres, not by an if-statement
```

For public traffic there is `db.asAnon()`, and for admin jobs `db.asServiceRole()`, which bypasses RLS and is deliberately a separate, visible choice in code review.

## Reference auth.users without fighting your migrations

The other half of the split has its own scar tissue. Point an ORM's migrations at a Supabase database and it either tries to drop `auth.users` or refuses to reference it across schemas, which is why most teams end up writing that foreign key in raw SQL too.

The extension fixes this with one rule: Prisma knows the exact shape of everything Supabase owns, and it will never generate DDL for any of it. That is what makes this line from the model safe:

```prisma
user supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
```

It becomes a real foreign key in the migration:

```sql
ALTER TABLE "public"."note"
  ADD CONSTRAINT "note_userId_fkey"
  FOREIGN KEY ("userId") REFERENCES "auth"."users"("id") ON DELETE CASCADE;
```

A note can never point at a user that doesn't exist, and deleting a user deletes their notes, guaranteed by Postgres rather than by a cleanup script. The relation exists for the constraint: you cannot `include` the user from a note query, and trying is a compile-time error rather than a runtime surprise.

## What you gain from schema-defined authorization

Your authorization rules become part of the artifact you already review. A policy change is a schema diff in a pull request, not a surprise in the dashboard.

Your auth relationships become real constraints, so referential integrity with Supabase Auth stops depending on application code remembering to clean up.

And your security model becomes explicit in the types. Every query names the role it runs as, so a reviewer can see who runs what at a glance, and schema and security evolve together in the same commit.

## Current limitations and supported scenarios

Prisma 8 RC1 with the Supabase extension supports Node.js and Bun, connecting through your project's session pooler (port 5432); the transaction pooler cannot carry the per-request role binding, and edge runtimes are not supported yet. Within that setup, a few boundaries to know:

- The `auth.users` relation is a constraint, not a navigable relation, so you cannot `include` the user from a note query.
- Policy predicates are strings, not a typed expression language.
- Realtime subscriptions and Storage are out of scope; keep using `supabase-js` for those. Prisma talks to Postgres directly and composes fine alongside it.

The [extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase) documents the remaining edge cases.

## Get started with Prisma 8 and Supabase

Create a free Supabase project as a sandbox, then test the workflow yourself in a few minutes:

```bash
npx prisma-next init --yes --target postgres --authoring psl
npm install @prisma/orm-extension-supabase
```

Next:

1. Add the extension to `prisma-next.config.ts`: `extensions: [supabasePack]`
2. Set `DATABASE_URL` to your Supabase project's session pooler.
3. Add the schema and policies shown above.
4. Run:

```bash
npx prisma-next migrate
```
