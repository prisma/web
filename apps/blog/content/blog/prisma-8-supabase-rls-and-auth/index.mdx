**Prisma 8 Release Candidate 1 lets you define your Supabase tables, auth relationships, and RLS policies next to each other in one Prisma schema. Prisma migrates all of it, and Postgres enforces it on every query.**

## Where is your current RLS policy?

Think about the last time you needed to know what the authorization policy for a table actually is. Not what it was when someone first wrote it. What it is right now, in production.

If you manage Row Level Security with SQL migrations, the answer lives somewhere in here:

```text
supabase/migrations/
├── 20250514093012_add_notes_policy.sql
├── 20250602141507_update_notes_policy.sql
├── 20250618102244_fix_notes_policy.sql
└── ...
```

Which one contains the current policy? You open the most likely file. It creates a policy, but a later migration replaced it. You open that one. Altered again, two weeks after. The current state of the most security-critical part of your data model is the sum of every migration that ever touched it, and the only way to read it is to replay them in your head. And if someone adjusted the policy in the Supabase dashboard along the way, it isn't in any of these files at all.

Imagine if you could define your RLS policy directly next to your model instead, and read the current state in one place.

Good news: now you can.

## Your schema is the source of truth

With Prisma 8's Supabase extension, your models, your auth relationships, and your RLS policies live in the same file. Here is a notes app where every note belongs to a Supabase user:

```prisma
namespace public {
  model Note {
    id        Uuid        @id @default(uuid())
    title     String
    body      String?
    userId    Uuid
    user      supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
    createdAt Timestamptz @default(now())

    @@map("note")
    @@rls
  }

  // A signed-in user reads only their own notes.
  policy_select note_owner_read {
    target = Note
    roles  = [authenticated]
    using  = "\"userId\"::uuid = auth.uid()"
  }
}
```

This one block answers every question you were hunting through the migrations directory for. `@@rls` turns on Row Level Security for the table, so no role sees any row unless a policy grants it. The policy block is the current read policy, carrying the same `USING` and `WITH CHECK` conditions you would otherwise write in SQL. Insert, update, and delete policies follow the same shape, with `withCheck` stopping users from writing rows they don't own; the full set is four short blocks in the [Supabase extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase). There is deliberately no anon policy, because with RLS enabled and no matching policy, anonymous visitors see zero rows. And the `user` field is a real reference to Supabase's `auth.users` table, which we'll come back to below.

This is where your application is defined. It is the file you edit, and the file you read. It is also [the most-requested Supabase feature in Prisma's history](https://github.com/prisma/prisma/issues/12735), with over 400 reactions on the GitHub issue since 2022.

## One command migrates everything

```bash
npx prisma-next migrate
```

Prisma diffs your schema against the database and generates the DDL, policies included:

```sql
CREATE POLICY "note_owner_read_9f8e536e" ON "public"."note"
  AS PERMISSIVE FOR SELECT TO authenticated
  USING ("userId"::uuid = auth.uid())
```

You never write this SQL, and you never need to read it to learn the current state; it is an implementation detail of the schema above. The workflow also runs in reverse: if your database already has policies, `prisma-next contract infer` reads them back into your schema, so adopting Prisma 8 doesn't mean rewriting your authorization from scratch.

## Every query names who is asking

A policy only protects queries that run under a role it applies to, so the Supabase client won't run anything until you say who is asking: it has no query methods until a role is bound. The part worth pausing on is step three. The query never filters by user, yet each user receives only their own notes, because the verified token decides what the database is willing to return. The forgotten `where` clause that leaks every user's data stops being a bug your code can have.

Writes get the same protection. Creating a note that belongs to someone else is rejected by the database's `WITH CHECK` condition, regardless of what the application code says:

```ts
await bound.orm.public.Note.select('id').create({ title, body, userId: someoneElse });
// => rejected by Postgres, not by an if-statement
```

For public traffic there is `db.asAnon()`, and for admin jobs `db.asServiceRole()`, which bypasses RLS and is deliberately a separate, visible choice in code review.

## A real foreign key into auth.users

The `user` field from the schema deserves a closer look:

```prisma
user supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
```

The extension ships with the exact shape of everything Supabase owns and follows one rule: Prisma never generates DDL for Supabase's own tables. That rule is what makes it safe to reference `auth.users` from your models. The migration turns the line into a real constraint:

```sql
ALTER TABLE "public"."note"
  ADD CONSTRAINT "note_userId_fkey"
  FOREIGN KEY ("userId") REFERENCES "auth"."users"("id") ON DELETE CASCADE;
```

A note can never point at a user that doesn't exist, and deleting a user deletes their notes, guaranteed by Postgres rather than by a cleanup script. The relation exists for the constraint: you cannot `include` the user from a note query, and trying is a compile-time error rather than a runtime surprise.

## Authorization your team and your AI agents can read

A policy change is now a schema diff in a pull request. The reviewer sees the old condition and the new one right next to the model they protect, and schema and security evolve together in the same commit.

The same property pays off in AI-assisted development. Supabase treats AI agents as a primary way people build applications, and an agent asked to reason about access control faces the exact hunt this post opened with: dozens of timestamped SQL files, each holding a partial truth. With authorization in the schema, the agent reads one file and gets models, relationships, and policies as structured metadata it can inspect, update, and reason about. Your authorization is no longer hidden inside migration history. It is part of your schema, and that makes your application easier to understand for developers and agents alike.

## Current limitations and supported scenarios

Prisma 8 RC1 with the Supabase extension supports Node.js and Bun, connecting through your project's session pooler (port 5432); the transaction pooler cannot carry the per-request role binding, and edge runtimes are not supported yet. Within that setup, a few boundaries to know:

- The `auth.users` relation is a constraint, not a navigable relation, so you cannot `include` the user from a note query.
- Policy predicates are strings, not a typed expression language.
- Realtime subscriptions and Storage are out of scope; keep using `supabase-js` for those. Prisma talks to Postgres directly and composes fine alongside it.

The [extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase) documents the remaining edge cases.

## Get started with Prisma 8 and Supabase

Prisma 8 is available today as Release Candidate 1 (RC1): the final preview before general availability. The API is stable, and we are collecting feedback before GA. [Share what you find in Discord](https://pris.ly/discord).

Create a free Supabase project as a sandbox, then test the workflow yourself in a few minutes:

```bash
npx prisma-next init --yes --target postgres --authoring psl
npm install @prisma/orm-extension-supabase
```

Next:

1. Add the extension to `prisma-next.config.ts`: `extensions: [supabasePack]`
2. Set `DATABASE_URL` to your Supabase project's session pooler.
3. Add the schema and policies shown above.
4. Run:

```bash
npx prisma-next migrate
```
