**You can now define your Supabase tables, auth relationships, and RLS policies in one Prisma schema. Prisma 8 migrates all of it, and Postgres enforces it.**

## Two versions of your schema

Every Supabase app eventually ends up with two versions of its database schema.

One lives in your ORM. It describes your tables and relations, and it generates your types.

The other lives in handwritten SQL migrations. That is where your Row Level Security policies go, and the foreign keys into `auth.users`, because your ORM cannot see the `auth` schema:

```sql
-- 20240301_rls.sql: written by hand, invisible to your ORM
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY "notes_owner" ON notes FOR SELECT
  TO authenticated USING (user_id = auth.uid());

ALTER TABLE notes
  ADD FOREIGN KEY (user_id) REFERENCES auth.users(id) ON DELETE CASCADE;
```

The two drift apart. The policy running in production is whatever the dashboard says, no pull request ever showed the change, and your ORM happily generates queries as if none of it exists.

Prisma 8 fixes that.

## What changed

Prisma 8 is the next major version of Prisma ORM, available now in Early Access. Its schema can declare two things no Prisma schema could before: RLS policies, written next to the model they protect, and real foreign keys into Supabase's `auth.users` table. Prisma migrates both, so SQL like the block above never gets written by hand again.

## The schema

Here is a notes app where every note belongs to a Supabase user:

```prisma
namespace public {
  model Note {
    id        Uuid        @id @default(uuid())
    title     String
    body      String?
    userId    Uuid
    user      supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
    createdAt Timestamptz @default(now())

    @@map("note")
    @@rls
  }
}
```

Two lines do the new work.

`user supabase:auth.AuthUser @relation(...)` references your auth user table from your Prisma schema. It becomes a real foreign key into `auth.users`, so deleting a user cascades to their notes and Postgres guarantees it. Prisma knows the exact shape of `auth.users` through the Supabase extension, and it will never try to migrate or modify anything Supabase owns.

`@@rls` enables Row Level Security on the table. The policies come next.

## The policy

Policies are named blocks in the same file, right below the model:

```prisma
// A signed-in user reads only their own notes.
policy_select note_owner_read {
  target = Note
  roles  = [authenticated]
  using  = "\"userId\"::uuid = auth.uid()"
}
```

The insert, update, and delete policies look the same: `policy_insert` and `policy_update` add a `withCheck` predicate so a user cannot write rows they don't own. The full set is four short blocks, shown in the [Supabase extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase). There is deliberately no anon policy: with RLS enabled and no matching policy, anonymous users see zero rows.

One command turns all of it into DDL and applies it:

```bash
npx prisma-next migrate
```

The generated migration enables RLS and creates each policy, for example:

```sql
CREATE POLICY "note_owner_read_9f8e536e" ON "public"."note"
  AS PERMISSIVE FOR SELECT TO authenticated
  USING ("userId"::uuid = auth.uid())
```

No SQL written by hand, and the policy now shows up in every schema diff. If you already have policies in a live database, it works in the other direction too: `prisma-next contract infer` reads existing policies back into your schema.

## Query without filters

This is the part that feels like magic. Here is the route handler that lists a user's notes:

```ts
const notes = await bound.orm.public.Note
  .select('id', 'title', 'body', 'createdAt')
  .all()
  .toArray();
```

There is no `where userId = ...` filter. The SELECT policy is the filter. Postgres runs the query as the signed-in user and returns only their rows, so an entire class of forgotten-filter bugs stops being possible in application code.

Where does `bound` come from? You bind a role per request. Prisma verifies the JWT from Supabase Auth and runs every query as that user:

```ts
const db = await getDb();          // supabase({ contractJson, url, jwksUrl })

const bound = await db.asUser(jwt); // verified JWT, queries run as this user
// db.asAnon()                      // public traffic
// db.asServiceRole()               // admin jobs, bypasses RLS
```

![A request's JWT is verified by Prisma, the query runs as that user, and Postgres RLS filters the rows.](/prisma-8-supabase-rls-and-auth/imgs/request-flow.svg)

The client has no default query surface. Until you choose `asUser`, `asAnon`, or `asServiceRole`, there is nothing to call. That removes the classic footgun of running app queries as the connection's login role and silently bypassing RLS.

Writes get the same treatment. A request that tries to insert a note owned by someone else is rejected by the database's `WITH CHECK` predicate, no matter what the application code says:

```ts
await bound.orm.public.Note.select('id').create({ title, body, userId: someoneElse });
// => rejected by Postgres, not by an if-statement
```

## Why this matters

Your authorization rules become part of the artifact you already review. A policy change is a schema diff in a pull request, not a surprise in the dashboard.

Your auth relationships become real constraints. Deleting a user cascades through `auth.users` foreign keys because the database enforces it, not a cleanup script.

Your security model becomes explicit in the types. Every query names the role it runs as, and the compiler won't let you skip that choice.

## Verified against a real project

Everything above ran against a hosted Supabase project, with two real users signed up through Supabase Auth and real JWTs verified against the project's JWKS endpoint. Each user sees only their own notes and anonymous requests see none. Forging another user's `userId` on insert or update is rejected by Postgres. Deleting a user cascade-deletes their notes. The example ships a full test suite covering every rule in both directions.

## Current limitations

Prisma 8 is in Early Access, and the Supabase extension has clear boundaries today:

- The `auth.users` relation is a constraint, not a navigable relation, so you cannot `include` the user from a note query. Traversal is a compile-time error rather than a runtime surprise.
- The runtime needs a real Postgres driver: Node.js and Bun today, no edge runtimes.
- Policy predicates are strings, not a typed expression language.
- Realtime subscriptions and Storage are out of scope; keep using `supabase-js` for those. Prisma talks to Postgres directly and composes fine alongside it.
- Use the session pooler (port 5432). The transaction pooler cannot carry the per-request role binding.

The [extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase) documents the remaining edge cases.

## Try it

Spin up a free Supabase project as a sandbox and validate all of this yourself in a few minutes:

```bash
npx prisma-next init --yes --target postgres --authoring psl
npm install @prisma/orm-extension-supabase
```

Add the extension to `prisma-next.config.ts` with `extensions: [supabasePack]`, point `DATABASE_URL` at your project's session pooler, paste the schema and policies above, and run `npx prisma-next migrate`. One naming note: Prisma 8 installs as `prisma-next`, not `prisma@8`.
