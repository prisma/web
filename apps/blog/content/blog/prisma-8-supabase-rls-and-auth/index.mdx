**Prisma 8 Release Candidate 1 gives Supabase developers one declarative, version-controlled source of truth: your tables, your `auth.users` relationships, and your Row Level Security policies live in one schema, Prisma generates the migrations, and Postgres still enforces every rule.**

## What it takes to answer "who can read this table?"

Say you run a notes app on Supabase. Every note belongs to a user, and users must only ever see their own notes. Supabase gives you the right enforcement model for this: Postgres Row Level Security, wired directly to Supabase Auth. A policy that checks `auth.uid()` is enforced by the database on every query, no matter which code path issued it.

Authoring and maintaining that model is the hard part. To be confident about one table, you end up reasoning about questions whose answers all live in different places:

- Which columns does `notes` have, after every migration that touched it?
- Does `user_id` actually reference `auth.users`, or does it just happen to hold UUIDs?
- Is RLS enabled, and which policies apply right now, after later migrations replaced earlier ones?
- Did someone adjust a policy in the dashboard, outside your migration history?
- Does that server query still need `.eq('user_id', user.id)`, and which client key does it run with?
- Will your generated TypeScript types tell you when any of this changes? They describe the shape of your data, not who is allowed to see it.

The schema lives in SQL migrations, the policies live in other migrations or the dashboard, the auth relationship is a convention, and the authorization checks are spread between Postgres and application filters.

The Supabase extension for [Prisma 8](https://www.prisma.io/docs/orm) moves all of that into one file. Models, `auth.users` relationships, and RLS policies are described together, reviewed in the same pull request, migrated by the same command, and read as one current state. Postgres remains the enforcement point. What changes is where the model is authored, and how it evolves.

## The whole model in one file

Here is the notes app, complete:

```prisma
namespace public {
  model Note {
    id        Uuid        @id @default(uuid())
    title     String
    body      String?
    userId    Uuid
    user      supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
    createdAt Timestamptz @default(now())

    @@map("note")
    @@rls
  }

  // A signed-in user reads only their own notes.
  policy_select note_owner_read {
    target = Note
    roles  = [authenticated]
    using  = "\"userId\"::uuid = auth.uid()"
  }
}
```

Every question from the list above is answered by this block. `@@rls` turns on Row Level Security, so no role sees any row unless a policy grants it. The policy block is the current read policy, carrying the same `USING` and `WITH CHECK` conditions you would otherwise write in SQL; insert, update, and delete policies follow the same shape, and the full set is four short blocks in the [Supabase extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase). There is deliberately no anon policy: with RLS enabled and no matching policy, anonymous visitors see zero rows. And `user` is a real reference to Supabase's `auth.users` table, covered below.

Declaring RLS in the Prisma schema is [the most-requested Supabase feature in Prisma's history](https://github.com/prisma/prisma/issues/12735), with over 400 reactions on the GitHub issue since 2022.

## Queries stop carrying the user filter

In a server route today, scoping a query to the signed-in user looks like this:

```ts
// supabase-js: the filter lives in application code
const supabase = createClient(url, key);

const { data: notes } = await supabase
  .from('notes')
  .select('id, title, body')
  .eq('user_id', user.id);
```

Whether that `.eq` is load-bearing depends on which key created the client. With the service role key, it is the only thing standing between one user and everyone's notes. With the user's forwarded token, RLS applies and the filter is redundant, but it stays in the code because nothing in the types marks which kind of client this is.

The Supabase extension removes the choice. The client has no query methods until you bind a role, so there is no client that silently runs with more privilege than you meant:

```ts
// Prisma 8: bind the verified user first, then query with no filter
const db = await getDb();
const bound = await db.asUser(jwt);

const notes = await bound.orm.public.Note
  .select('id', 'title', 'body')
  .all()
  .toArray();
```

`asUser` verifies the token's signature against your project's public keys before any connection is used, then runs everything that follows as that user. The query carries no user filter, and each user still receives only their own rows, because the select policy is the filter. The walkthrough below shows the request end to end:

Writes get the same protection. Creating a note that belongs to someone else is rejected by the database's `WITH CHECK` condition, regardless of what the application code says:

```ts
await bound.orm.public.Note.select('id').create({ title, body, userId: someoneElse });
// => rejected by Postgres, not by an if-statement
```

For public traffic there is `db.asAnon()`, and for admin jobs `db.asServiceRole()`, which bypasses RLS and is deliberately a separate, visible call in code review.

## A real foreign key into auth.users

Linking a table to Supabase Auth today means writing the constraint by hand and keeping it in your head afterwards:

```sql
-- a migration you write and maintain yourself
alter table public.notes
  add constraint notes_user_id_fkey
  foreign key (user_id) references auth.users (id) on delete cascade;
```

In the schema above, the same fact is one declared line:

```prisma
user supabase:auth.AuthUser @relation(fields: [userId], references: [id], onDelete: Cascade)
```

The extension ships with the exact shape of everything Supabase owns and follows one rule: Prisma never generates DDL for Supabase's own tables. That rule is what makes it safe to reference `auth.users` from your models. The migration turns the line into the same constraint, generated instead of hand-written. A note can never point at a user that doesn't exist, and deleting a user deletes their notes, guaranteed by Postgres rather than by a cleanup script. The relation exists for the constraint: you cannot `include` the user from a note query, and trying is a compile-time error rather than a runtime surprise.

## Migrations you review instead of SQL you reconstruct

If you have managed RLS with SQL migrations, you know the failure mode: the current policy for a table is the sum of every migration that ever touched it, plus whatever changed in the dashboard along the way. Reading it back means replaying history in your head.

Here, a policy change is an edit to the schema. Then:

```npm
npx prisma@next migration plan --name add-notes
```

Prisma diffs your schema against the database and generates the DDL, policies included:

```sql
CREATE POLICY "note_owner_read_9f8e536e" ON "public"."note"
  AS PERMISSIVE FOR SELECT TO authenticated
  USING ("userId"::uuid = auth.uid())
```

`npx prisma@next migrate` applies it. You never write this SQL, and you never need to read it to learn the current state. The workflow also runs in reverse: if your database already has policies, `npx prisma@next contract infer` reads them back into your schema, so adopting Prisma 8 doesn't mean rewriting your authorization from scratch.

The reviewer of a policy change now sees the old condition and the new one right next to the model they protect, and schema and security evolve in the same commit. The same property helps AI agents: instead of reconstructing your authorization model from dozens of timestamped SQL files, an agent reads one file and gets models, relationships, and policies as structured metadata.

## supabase-js stays for what it's good at

Realtime subscriptions, Storage, and the Auth flows in your frontend stay on `supabase-js`. Prisma talks to Postgres directly and runs alongside it; nothing about your Supabase project changes except where the data model is authored.

Prisma 8 RC1 with the Supabase extension supports Node.js and Bun over your project's session pooler; the remaining boundaries are being actively worked on and are documented in the [extension guide](https://www.prisma.io/docs/orm/next/extensions/supabase).

## Get started with Prisma 8 and Supabase

:::note[What is a Release Candidate?]
Prisma 8 is available today as Release Candidate 1 (RC1): the final preview before general availability. The API is stable, and we are collecting feedback before GA. [Share what you find in Discord](https://pris.ly/discord).
:::

Create a free Supabase project as a sandbox, then test the workflow yourself in a few minutes:

```npm
npx prisma@next orm init --yes --target postgres --authoring psl
npm install @prisma/orm-extension-supabase
```

Next:

1. Register the extension in `prisma.config.ts`: `extensions: [supabasePack]` inside the ORM config.
2. Set `DATABASE_URL` to your Supabase project's session pooler.
3. Add the schema and policies shown above.
4. Run:

```npm
npx prisma@next contract emit
npx prisma@next migration plan --name init
npx prisma@next migrate
```
