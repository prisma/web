Choose Prisma when your app is TypeScript services on Bun that call each other and share a Postgres database. Choose Vercel when you need Next.js platform features, WebSockets, Node.js, a non-TypeScript backend, or previews pre-filled with production data.

Both platforms host full-stack TypeScript apps with managed Postgres and preview every Git branch. The difference is what each one sets up for you. On Prisma, one deploy of a [Prisma Composer](https://www.prisma.io/docs/composer) app provisions your services on [Prisma Compute](https://www.prisma.io/docs/compute), their [Prisma Postgres](https://www.prisma.io/docs/postgres) databases, and the connections between them, all from TypeScript the compiler checks first. On Vercel, a push builds your framework code, the delivery network serves it, and a Marketplace integration connects a database.

The Prisma platform is four products: [Prisma ORM 8](https://www.prisma.io/docs/orm) (release candidate, general availability expected October 2026), Prisma Postgres, Prisma Compute, and Prisma Composer (early access).

## Choose Prisma when

- Several TypeScript services call each other. Each call's contract sits in the dependency declaration, so TypeScript checks the wiring. One service still deploys from a Git push; add Composer later.
- Your services run on Bun, or can, and one region with no edge runtime is enough.
- You want every Git branch to be its own environment, and you are fine creating its database with one command or a Composer stage deploy.
- You do not want to pay per seat or per deploy. Vercel charges $20 a month per extra team member; Prisma charges a plan fee plus usage.
- You can build on pre-release tooling. ORM 8 is a release candidate and Composer is in early access.

## Choose Vercel when

- You rely on Next.js features Vercel provides at the platform level, such as caching and on-demand image optimization. Compute runs Next.js, but you build [image routes](https://www.prisma.io/docs/compute/image-transformations) yourself.
- You need WebSocket servers. Compute does not support them; Vercel Functions serve them in public beta.
- Your app runs on Node.js and you do not want to move to Bun, or your backend is not TypeScript. Vercel Services runs a Next.js frontend beside a Python backend.
- You want preview databases that start as a copy of production. Vercel's Neon integration creates one per preview; on Prisma you provision and seed a branch database yourself.
- A request needs more than 60 seconds before it starts responding. Vercel Functions allow 300 seconds by default and 800 on Pro; Compute cancels a request that has sent nothing after 60.

## How do Prisma and Vercel compare?

Prisma's edge is typed service wiring and an environment per branch. Vercel's edge is framework delivery, runtime choice, and long-running requests.

| What you need | Prisma | Vercel |
| --- | --- | --- |
| Hosting | TypeScript services on Compute, running on Bun, one region each | Framework deployments and Functions; Services groups several apps |
| Managed Postgres | Prisma Postgres, any client | Marketplace providers, including Prisma Postgres and Neon |
| Typed data access | Prisma ORM 8, or any client | Any ORM or client, including Prisma ORM |
| Service wiring | Composer binds each dependency to its typed contract | Bindings (beta) inject a URL; types are yours to add |
| Previews | One environment per Git branch, torn down with the branch | One preview URL per Git branch |
| Preview databases | One per branch, provisioned by you or a stage deploy, no production data | Provider-specific; Neon copies production per branch |
| Long-running work | 60 seconds to first byte, then `waitUntil`; no WebSockets | 300 to 800 seconds, 30 minutes in beta; WebSockets in beta |
| Billing | Plan fee plus requests, memory, CPU, bandwidth | Plan fee plus compute, delivery, builds, and seats |

## How do you define the application?

On Prisma, the compiler checks how your services connect. On Vercel, you add that check yourself.

You describe services and dependencies in TypeScript, and a Composer deploy provisions them. On Vercel, you connect a repo, Vercel detects the framework, and `vercel.json` holds routing and Services config. Four Composer terms, used below:

- A **service** is one deployable unit, declared with `compute()`.
- A **service contract** is a service's API as schemas (arktype, zod, or any Standard Schema validator). It types the handlers and the client. The service that serves it is the **producer**.
- A **data contract** is ORM 8's schema file, `contract.prisma`, which replaces `schema.prisma`.
- A **root module** (`module.ts`) provisions every service and resource and wires them together. A **stage** is a preview copy of the whole app.

Here is a storefront that asks a catalog service for a price. The catalog publishes a contract, the storefront declares it as a dependency, and `service.load()` returns a typed client.

```ts tab="catalog/contract.ts"
import { contract, rpc } from "@prisma/composer/service-rpc";
import { type } from "arktype";

export const catalogContract = contract({
  getPrice: rpc({
    input: type({ productId: "string" }),
    output: type({ amount: "number", currency: "string" }),
  }),
});
```

```ts tab="storefront/service.ts"
import nextjs from "@prisma/composer/nextjs";
import { rpc } from "@prisma/composer/service-rpc";
import { compute } from "@prisma/composer-prisma-cloud";
import { catalogContract } from "../catalog/contract.ts";

export default compute({
  name: "storefront",
  deps: { catalog: rpc(catalogContract) }, // [!code highlight]
  build: nextjs({ module: import.meta.url, appDir: ".." }),
});
```

```ts tab="storefront/data.ts"
import service from "./service.ts";

export async function priceFor(productId: string) {
  const { catalog } = service.load();
  return catalog.getPrice({ productId }); // [!code highlight]
}
```

```ts tab="module.ts"
import { module } from "@prisma/composer";
import catalogModule from "./src/catalog/module.ts";
import storefrontService from "./src/storefront/service.ts";

export default module("store", ({ provision }) => {
  const catalog = provision(catalogModule);
  provision(storefrontService, { deps: { catalog: catalog.rpc } }); // [!code highlight]
});
```

Change `getPrice` from a plain number to an amount plus a currency, and every caller that still expects a number fails to compile. A shared-types package gives you that on any platform.

What Composer adds is the root module. It binds each dependency to its producer, and TypeScript checks the binding: a mismatched contract or a missing handler is a compile error, not a failed deploy. The deploy then provisions the services and the authenticated connections, so app code never reads a URL from `process.env`. The [store example](https://github.com/prisma/composer/tree/main/examples/store) shows the full version.

Databases work the same way: a service declares `deps: { db: postgres(catalogData) }`, and the module that owns the database provisions it with [`postgres({ name, contract, config })`](https://www.prisma.io/docs/composer/databases). The deploy applies migrations before the service starts and refuses to wire a service to a database whose schema does not match. Cron jobs, object storage, and event streams follow the same pattern.

Everything about the database comes from `contract.prisma`. Edit it, run `prisma contract emit`, and plan migrations from the same file. Coming from an older Prisma ORM? [This page](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7) maps each old command to its ORM 8 name.

Vercel's [Services](https://vercel.com/docs/services) also groups several apps into one deployment, including mixed languages. A [binding](https://vercel.com/docs/services/bindings), in beta, injects one service's URL into another as an environment variable. Type checking across that call is yours to add.

You do not need several services to start. One service runs on Compute from a Git push, without Composer.

## How do preview databases and migrations work?

Prisma gives every branch its own environment and plans migrations across databases at different versions. Vercel's Neon integration gives every preview a copy of production.

![Every Git branch is its own environment. The main branch runs the storefront and catalog services against the production database, which has id and email. The alice/phone branch runs its own copies against its own database with a phone column, and the bob/avatar branch does the same with an avatarUrl column.](/prisma-vs-vercel/imgs/branch-databases.svg)

### On Prisma

With [deploy on push](https://www.prisma.io/docs/compute/deploy-on-push) configured, each push deploys the branch to its own environment. A [branch](https://www.prisma.io/docs/compute/branching) owns its services and any databases created on it. Deleting the Git branch deletes all of it, databases included.

Environment variables have three scopes, which the CLI calls roles:

1. Production values.
2. Preview values, shared by every preview.
3. Branch overrides, which replace a preview value for one branch.

Set the first two once:

```bash
npx prisma@latest project env add DATABASE_URL=<production-url> --role production
npx prisma@latest project env add DATABASE_URL=<shared-preview-url> --role preview
```

For a database per branch, run the CLI from the feature branch, which it targets automatically, then add a branch override:

```bash
npx prisma@latest postgres create preview-db
npx prisma@latest project env add DATABASE_URL=<printed-url> --branch feature/search
```

For a Composer app, `npx prisma@latest deploy module.ts --stage <branch>` does both and applies migrations for any `postgres()` database. Either way, a preview pointed at production writes to production, and Prisma never copies production data into a branch database. Seed it if you need realistic rows. The [environment variables docs](https://www.prisma.io/docs/compute/environment-variables) cover the scopes.

Now suppose Alice adds `phone` on her branch, Bob adds `avatarUrl` on his, and both merge. Alice's database has one column, Bob's has the other, staging and production have neither, and all of them need the merged schema.

ORM 6 and 7 apply migrations in timestamp order. ORM 8 records, for each migration, the schema version it starts from and the one it ends at, so migrations form a [graph](https://www.prisma.io/docs/orm/migrations/the-migration-graph). After the merge, whoever merged runs `migration plan --name merge_alice --from <directory>` on `main`, using Alice's last migration directory as `migration graph` prints it, repeats it for Bob, and commits both. From then on `db migrate` takes any database, from wherever it is, to the merged version. Two migrations that change the same column still need a human to decide.

![The migration graph after the merge. State A is production with id and email. Alice's migration adds phone to reach state B, and Bob's migration adds avatarUrl to reach state C. Two merge migrations, one from B and one from C, both reach the merged state D. Each arrow is one migration, recorded as the state it starts from and the state it ends at.](/prisma-vs-vercel/imgs/migration-graph.svg)

The graph is an ORM 8 feature, so you get it on Vercel too. The platform adds the environment around it: a database per branch, a stage that migrates at deploy time, and a release step you run against production:

```bash
npx prisma@latest migration check
npx prisma@latest db migrate --show --db "$PRODUCTION_DATABASE_URL"
npx prisma@latest db migrate --db "$PRODUCTION_DATABASE_URL"
```

Check the compiled migration files, preview what would run, then run it.

### On Vercel

A push to a feature branch builds a preview URL, and a merge into the production branch deploys production, per Vercel's [environments docs](https://vercel.com/docs/deployments/environments).

The preview database comes from the integration you configured. The [Neon integration](https://vercel.com/marketplace/neon) creates a copy-on-write branch per preview with the parent's data and schema, as Vercel's [Ephemeral Environments guide](https://vercel.com/i/ephemeral-environments) describes. That beats Prisma's empty branch databases when you need production-shaped data. The [Prisma Postgres listing](https://vercel.com/marketplace/prisma) sets one `DATABASE_URL` for the project; you scope previews with Vercel's per-environment variables.

Schema changes travel the same way on both: migration files in Git, applied on deploy. If you run ORM 8 on Vercel, apply them with `npx prisma@latest db migrate --db "$DATABASE_URL"` in your build or release step.

## What can you run, and what does it cost?

Compute is Bun, one region, and 60 seconds to first byte, and it is cheaper per meter with no seat or deploy charges. Vercel runs Node.js, longer functions, and WebSockets, and charges per seat.

Prisma Compute runs TypeScript HTTP services on Bun, so a Node.js app must run on Bun. Builds detect Next.js, Nuxt, Astro, Hono, NestJS, TanStack Start, and plain Bun servers. Your app starts a server, scales to zero when idle, and has 60 seconds to start responding. Work after the response uses `waitUntil`, which does not retry or survive a redeploy. No edge runtime, no WebSockets. Compute does not require Prisma ORM, so an ORM 6 app runs as-is. The [limitations page](https://www.prisma.io/docs/compute/limitations) has the full list.

Vercel's [Next.js integration](https://vercel.com/docs/frameworks/full-stack/nextjs) handles caching and image optimization. Functions run 300 seconds by default, 800 on Pro, and 30 minutes in beta. WebSockets are in public beta.

Both bill memory while an instance runs and nothing once it scales to zero, and both bill CPU only while code executes. Vercel's rates below are Pro prices in its cheapest US regions; the [Fluid compute pricing](https://vercel.com/docs/functions/usage-and-pricing) page lists the rest.

| Meter | Prisma Compute | Vercel Pro (cheapest US regions) |
| --- | --- | --- |
| Plan | Free, or $10, $49, $129 a month with 5, 20, 100 million requests | $20 a month, including a $20 usage credit |
| Requests | $1 per million after the included amount | $0.60 per million |
| Memory | $0.006 per GB-hour | $0.0106 per GB-hour |
| Active CPU | $0.064 per vCPU-hour | $0.128 per CPU-hour |
| Bandwidth | $0.025 per GB | Regional; Pro includes 1 TB a month |
| Builds and previews | Not billed | $0.007 per build minute on paid teams |
| Seats | Not billed | $20 a month per extra seat |

Prisma Postgres is [priced separately](https://www.prisma.io/pricing), as is any Marketplace database on Vercel. Idle previews on Prisma cost nothing; the one exception is Composer's cron scheduler, which keeps one warm instance per deployed app or stage. The [Compute vs Vercel pricing](https://www.prisma.io/blog/prisma-compute-vs-vercel-pricing) post prices a full month.

## Can you use Prisma with Vercel?

Yes. Prisma ORM runs on Vercel, and [Prisma Postgres is in the Marketplace](https://vercel.com/marketplace/prisma). The [Vercel guide](https://www.prisma.io/docs/guides/postgres/vercel) covers Next.js, Nuxt, and SvelteKit. Keep Vercel for hosting, use ORM 8 and Prisma Postgres for queries and migrations, and run `db migrate` in your own release step.

## Frequently asked questions

<Accordions type="single">
  <Accordion title="Is Prisma a replacement for Vercel?">
For TypeScript apps, mostly. Prisma Compute hosts the app and Prisma Postgres holds the data. It does not replace Vercel's Next.js caching and image optimization, and Compute has no WebSockets, no multi-region, and a 60-second first-byte limit.
  </Accordion>
  <Accordion title="Does Prisma give each preview its own database?">
Yes, if you create it. Each Git branch is an isolated environment; you provision its database with the CLI or a Composer stage deploy, and it starts without production data. A preview-scoped or branch-scoped `DATABASE_URL` keeps it off production.
  </Accordion>
  <Accordion title="What is the migration graph in Prisma ORM 8?">
A record of which schema version each migration starts from and ends at. After two branches merge, the ORM plans a path from each database's current version to the merged schema. It works on any host, including Vercel.
  </Accordion>
  <Accordion title="Can I use Prisma ORM and Prisma Postgres on Vercel?">
Yes. The Prisma Postgres Marketplace integration provisions a database and sets `DATABASE_URL`, and Prisma ORM runs in any Vercel app. You run migrations in your own deployment step.
  </Accordion>
</Accordions>

## Try the Prisma workflow

Ship one change that touches a service contract and a schema, and see what the compiler and the deploy catch. The [Composer getting-started guide](https://www.prisma.io/docs/composer/getting-started) uses a quotes service and a gateway, the same roles as catalog and storefront above. Local runs need no account.

<Steps variant="vertical">

<Step variant="vertical">

### Run the two-service example

Follow the guide and run both services locally with `npx prisma@latest dev module.ts`.

</Step>

<Step variant="vertical">

### Change a service contract

Rename a method in the quotes contract and run your typecheck. The gateway fails to compile until you update it.

</Step>

<Step variant="vertical">

### Add a database and preview a schema change

Give the quotes service a `postgres()` database per the [databases page](https://www.prisma.io/docs/composer/databases). Add a field to `contract.prisma`, run `npx prisma@latest contract emit` and `npx prisma@latest migration plan --name <name>`, then `npx prisma@latest deploy module.ts --stage <branch>`. The stage gets its own migrated database.

</Step>

<Step variant="vertical">

### Merge and migrate production

Run `npx prisma@latest db migrate --show --db "$PRODUCTION_DATABASE_URL"` to preview, then drop `--show` to apply.

</Step>

</Steps>

If that loop fits your team, start with the [Composer getting-started guide](https://www.prisma.io/docs/composer/getting-started). If you need the Vercel-only features above, the [Vercel guide](https://www.prisma.io/docs/guides/postgres/vercel) gets Prisma ORM and Prisma Postgres running there instead.
