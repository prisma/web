The past few days have been difficult for Railway and the developers who rely on it.

Security incidents are stressful for everyone involved. For the engineers working to contain the problem, and for the developers who suddenly have to worry about their applications, credentials, and customer data.

On October 21, Railway disclosed a security incident involving customer environment variables. Since then, the team has been sharing updates, restoring services, and publishing recovery guides.

If you're running an application on Railway, you might be wondering what this means for you, what you should do next, and whether it's worth considering another platform.

This guide covers what happened, how to secure your application, and how to move a PostgreSQL database and TypeScript service to Prisma if you decide to.

**The priority is securing your application.** Whether you stay on Railway or move elsewhere is a decision you can make afterwards.

## What happened at Railway?

On October 21, Railway [disclosed a security incident](https://blog.railway.com/p/security-disclosure-wednesday-october-21st) involving the systems that store customer environment variables.

Environment variables often contain sensitive information, such as database passwords, API keys, and cloud credentials.

According to Railway, an unauthorized third party may have accessed encrypted environment variables and, in some cases, their decrypted values.

Railway believes the attack was part of a broader effort targeting infrastructure providers to obtain credentials for AI services. The team notified affected providers, temporarily paused deployments, and invalidated API and project tokens created before the incident.

By October 22, Railway had restored deployments across its plans and published several recovery guides to help developers rotate their credentials.

The team has continued sharing updates through its [status page](https://status.railway.com/).

Meanwhile, developers in a [Reddit discussion](https://www.reddit.com/r/devops/comments/1xc6bbp/railways_security_incident_is_more_serious_than_a/) reported unexpected usage of OpenAI, Anthropic, and OpenRouter API keys. Some said their providers had already revoked the affected credentials.

These are individual reports, so they don't tell us how widespread the incident was.

As of October 23, Railway hasn't published a complete root cause analysis or a confirmed number of affected accounts. The investigation is ongoing.

It's encouraging to see the team communicating openly and publishing practical guidance while working through the incident.

## What should you do now?

If your application runs on Railway, start by following its recovery guidance.

You don't need to change your infrastructure immediately. There are a few things you can do to reduce your risk regardless of where you host your application.

### 1. Rotate your secrets and API keys

Start with credentials that provide access to your infrastructure, data, or billing accounts.

This includes AI provider keys, cloud credentials, GitHub tokens, payment integrations, and database passwords.

One important detail: **updating an environment variable doesn't automatically invalidate the old credential.**

For example, replacing an OpenAI API key in Railway won't stop the old key from working. You also need to revoke it from OpenAI's dashboard.

If you suspect a credential is being actively misused, revoke it immediately, even if that means temporarily interrupting your application.

Railway has published [provider-specific recovery guides](https://blog.railway.com/) to help with this process.

### 2. Regenerate your database credentials

If you're using Railway PostgreSQL, follow its [credential rotation guide](https://blog.railway.com/p/security-disclosure-recommendation-rotate-postgresql-database-credentials).

The process involves disabling unnecessary public access, generating a new database password, restarting the database to close existing connections, and redeploying the applications that depend on it.

Remember to update any external services that connect to the same database.

### 3. Check for unusual activity

Changing your credentials prevents someone from continuing to use the old ones, but it doesn't tell you whether they've already been used.

Review your API usage, cloud audit logs, payment activity, and database access.

Look for requests you don't recognize, unexpected spending, unfamiliar database roles, or changes you didn't make.

If anything looks suspicious, preserve the relevant logs so you can investigate further.

### 4. Set spending limits where possible

An exposed API key can quickly become an expensive problem.

Where your provider supports them, set hard spending limits and usage alerts.

One developer in the Reddit discussion mentioned that a $50 spending cap helped limit the financial impact of unexpected API usage.

It's a useful safeguard to have regardless of which platform you're using.

### 5. Make sure you have a working backup

Backups are only useful if you can restore them.

For PostgreSQL, `pg_dump` lets you export your database into a file you control. Keep a copy outside your hosting provider and periodically restore it into a separate database to verify that it works.

Railway also has a [PostgreSQL backup and restore guide](https://docs.railway.com/guides/postgres-backups-restores).

One final thing worth keeping in mind: updating environment variables usually requires redeploying your application. If deployments are paused during an incident, applying replacement credentials may take longer. You can still revoke the original keys directly through their providers.

Keeping a record of where your secrets are used and how to revoke them makes incidents like this easier to manage.

## Considering a move? Here's how to migrate

Once your application is secure, you might want to explore other hosting options.

You don't have to move everything at once. In fact, testing a database migration independently is usually a better place to start.

For applications using PostgreSQL and TypeScript, one option is to use [Prisma Postgres](https://www.prisma.io/docs/postgres) for the database and [Prisma Compute](https://www.prisma.io/docs/compute) for hosting the application.

Prisma Postgres is a managed PostgreSQL service. You can use it with an existing application without adopting Prisma ORM or changing your deployment platform.

Prisma Compute runs supported TypeScript HTTP services, so you can also move your application if that makes sense for your setup.

Let's look at what the migration involves.

### Before you start

First, check that your application and database are compatible.

**For PostgreSQL:** Prisma Postgres currently runs PostgreSQL 17. The import process supports source databases running PostgreSQL 17 or earlier, and you'll need the PostgreSQL 17 client tools.

You should also check which extensions your database uses. Some extensions, including PostGIS and TimescaleDB, aren't currently supported. The [import guide](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql) explains how to check.

**For your application:** Prisma Compute supports TypeScript HTTP services running on Node.js or Bun, including supported frameworks such as Next.js.

It doesn't currently support every workload. If your application depends on WebSockets, persistent disks, or Docker-specific configuration, review the [Compute limitations](https://www.prisma.io/docs/compute/limitations) before proceeding.

If Compute isn't suitable for your application, you can still move the database and continue hosting your application elsewhere.

### Step 1: Move your PostgreSQL database

The migration uses standard PostgreSQL tools, so the process should look familiar.

You export your existing database with `pg_dump`, create a new Prisma Postgres database, and import the data using `pg_restore`.

I tested the import and restore process with PostgreSQL 17 using a sample database containing 500 users and 5,000 posts. The Railway-specific connection steps below follow Railway's documentation.

**Create a Prisma Postgres database**

You can create one through [Prisma Console](https://console.prisma.io/) or using the CLI:

```bash
npx prisma@latest auth login

npx prisma@latest project create my-db-project

npx prisma@latest postgres create my-db --region us-east-1
```

Save the connection string returned by the CLI.

Prisma Postgres provides a pooled connection for regular application queries and a direct connection for database operations such as imports and migrations.

For the restore, use the direct connection URL.

**Export your Railway database**

Set `DATABASE_PUBLIC_URL` to your Railway PostgreSQL connection string and `PRISMA_POSTGRES_DIRECT_URL` to your Prisma Postgres direct connection string.

Then export the database:

```bash
umask 077

pg_dump \
  --format=custom \
  --no-owner \
  --no-privileges \
  --dbname="$DATABASE_PUBLIC_URL" \
  --file=railway.dump
```

This creates a backup containing your database's schema and data.

Keep the file private, since it contains a copy of your application's data. If you're exporting through Railway's public TCP proxy, outbound data transfer may also incur egress charges.

**Restore the data into Prisma Postgres**

With the new database ready, import the backup:

```bash
pg_restore \
  --single-transaction \
  --exit-on-error \
  --no-owner \
  --no-privileges \
  --dbname="$PRISMA_POSTGRES_DIRECT_URL" \
  railway.dump

psql "$PRISMA_POSTGRES_DIRECT_URL" -c 'ANALYZE;'
```

Using `--single-transaction` ensures the restore succeeds or fails as a single operation rather than leaving an incomplete import.

In my local test, the restore took around eight seconds. The row counts, checksums, constraints, and sequences I compared matched the source database.

Actual migration times will depend on your database size and complexity.

If you use PostgreSQL row-level security, there's one additional detail to consider. `pg_dump` includes RLS policies but doesn't export the database roles they reference. The [Prisma Postgres import guide](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql) covers how to handle those roles.

**Verify the imported data**

Before changing your production connection string, test your application against the new database.

Check that your tables, records, constraints, and application queries behave as expected.

When you're ready for the actual cutover, pause writes to Railway, take a final backup, and restore it into a fresh Prisma Postgres database.

Verify the data again, then update your application to use the pooled Prisma Postgres connection string.

If you only wanted to migrate the database, that's all you need to do. Your application can continue running wherever it already runs.

### Step 2: Deploy your TypeScript application to Prisma Compute (optional)

If your application is a supported TypeScript HTTP service, you can also deploy it to Prisma Compute.

For an existing application, [Prisma Composer](https://www.prisma.io/docs/composer/porting-an-app) provides a way to describe your application's services, dependencies, and configuration.

Composer is currently in Early Access.

The idea is to keep your existing application code and add the configuration Compute needs to build and run it.

For a typical service, you'll add a `service.ts` declaration, a `module.ts` entry point, and Composer configuration in `prisma.config.ts`.

Your application then uses the port provided by Compute and receives its database connection through a configured secret.

The [Composer porting guide](https://www.prisma.io/docs/composer/porting-an-app) walks through those changes.

Once your application is configured, create a project for the service and add the database connection string as a secret.

```bash
npx prisma@latest project create my-api

# Enter the pooled connection string securely
read -r -s POSTGRES_URL
export POSTGRES_URL

npx prisma@latest project env add POSTGRES_URL --role production

npm run build

npx prisma@latest deploy module.ts
```

I used `POSTGRES_URL` for the connection string because Composer reserves names such as `DATABASE_URL` and `DATABASE_URL_POOLED` for databases it manages.

In my test, deploying the application into a separate project from the migrated database also avoided a Composer bootstrap error.

After deployment, Compute returned a public URL, and I verified that the application could read from and write to the migrated database.

There was one small issue with my Hono server: the first request returned a 502 because the database query exceeded Bun's default idle timeout during a cold start. Increasing the timeout resolved it.

These are useful things to test before sending production traffic to a new deployment.

### Step 3: Test the application and switch traffic

At this point, you should have a working copy of your application connected to the migrated database.

Before switching traffic, run your usual smoke tests. Check authentication, API endpoints, database reads and writes, and any services your application depends on.

Once everything works, you can attach your existing domain using the [Prisma Compute custom domains guide](https://www.prisma.io/docs/compute/domains).

Compute will provide the DNS record to configure and provision TLS for your domain.

Keep your original Railway database available in a read-only state during your rollback window, and document how you'd switch back if something goes wrong.

One detail worth planning for: if users create or modify data after the cutover, simply switching DNS back won't restore those changes to the original database. You'll need a way to move that data back safely.

A migration is much easier to manage when you've already tested both the cutover and the rollback.

## A few thoughts to close

Incidents like this are a reminder of how much trust goes into the infrastructure we use every day.

No platform is immune to security incidents, and moving to a different provider doesn't eliminate the need to manage credentials, monitor activity, and maintain reliable backups.

Railway has been communicating publicly and providing recovery guidance while working through a difficult situation. That's important for developers who depend on the platform.

If you're affected, focus on securing your application first.

And if the incident has prompted you to reconsider your infrastructure, take the opportunity to evaluate your options without rushing. You can test a database migration, verify that your application works, and decide what makes sense for your team.

If Prisma is one of the options you're considering, you can [try the migration with a test project](https://console.prisma.io/sign-up?utm_source=prisma_blog&utm_medium=organic&utm_campaign=railway_incident_migration&utm_content=article_footer).

Whatever you decide, the goal is the same: an application you can trust, with a recovery plan you're confident in.
