If you host on Railway, rotate every secret you keep there before you read the rest of this. I'd start with the keys that can spend money, and I'd revoke the old values at each provider, not just replace them in Railway. Your Railway Postgres password is an environment variable too, so regenerate it, and if nothing outside Railway talks to the database, switch off Public Access while you're there. Railway has a [guide for that](https://blog.railway.com/p/security-disclosure-recommendation-rotate-postgresql-database-credentials) and a dozen more [per provider](https://blog.railway.com/), and they're good. Further down I walk through moving a Postgres database and a TypeScript app off Railway, for anyone who wants that option once the rotation is done. I work at Prisma, so weigh that half accordingly.

## What happened

On October 21 Railway [disclosed](https://blog.railway.com/p/security-disclosure-wednesday-october-21st) unusual activity in the systems that store customer environment variables. Someone outside the company may have read encrypted variables and, for some of them, obtained the decrypted contents. Railway attributes it to a campaign against platform companies whose real target is AI inference providers, and it warned those providers so keys could be revoked early. Deployments stayed paused while the team contained the problem and came back one plan at a time on October 22, with Hobby and Free users waiting until late that evening UTC. Every API token was invalidated along the way, which broke CI for anyone holding one. Railway says a preliminary incident report is coming and will link it from the [status page](https://status.railway.com).

What sent me down this path was a [post on r/devops](https://www.reddit.com/r/devops/comments/1xc6bbp/railways_security_incident_is_more_serious_than_a/) from someone running a small marketplace backend on Railway. They had done the careful things and still hit the wall everyone hit. Railway was telling them to rotate everything, and the only way to ship new values was a deploy, which was paused. Others in the thread learned about the exposure from OpenAI, Anthropic or OpenRouter disabling a key before Railway's email arrived, and one person's fifty dollar spend limit was the only thing that capped the charge. Railway has posted status updates through both days, and nobody in that thread would wish the week on them.

## What I'm changing, wherever I host

The uncomfortable part is that the trap those developers fell into isn't a Railway trap. On almost every platform, [Prisma Compute](https://www.prisma.io/docs/compute) included, a new secret only takes effect after a redeploy, so a frozen deploy path freezes your rotation too. The real fix is an app that reads its secrets at runtime from a store you control. I'm not rebuilding mine for that this week, and I doubt you are either, so here are the smaller things I'm doing instead.

I'm writing down every secret I hold, what it can reach and where I'd go to revoke it, because revoking is the one move that never waits on a deploy. I'm putting hard spend limits on every LLM and cloud key. Where a provider lets me hold two live keys at once, I'll add the new one, redeploy, and only then kill the old. I'm keeping the canonical copy of each value in a secrets manager, since most platforms won't show a value back once it's set. And I'm taking a logical backup I own. Railway's [backups guide](https://docs.railway.com/guides/postgres-backups-restores) shows a scheduled dump and a restore drill alongside its snapshots, and that same dump is the first step of a migration.

## Moving the database and the app

Check whether this fits you before you touch anything. On the database side the question is extensions: [Prisma Postgres](https://www.prisma.io/docs/postgres) supports most of them, and PostGIS and TimescaleDB are the usual ones it [doesn't](https://www.prisma.io/docs/postgres/import-from-existing-database). On the app side, Prisma Compute runs TypeScript HTTP services on Node, Bun or Next.js, and it won't help you if you need WebSockets, a persistent disk, a Dockerfile or built-in cron; the [limitations](https://www.prisma.io/docs/compute/limitations) page has the full list. Prisma Postgres is the database, Prisma Compute is the hosting, and Composer is the small config layer that tells Compute how to run your app. They live together in a project, which has nothing to do with a Railway project.

I don't have a Railway account, so a local PostgreSQL 17 database with 500 users and 5,000 posts played the part of Railway, and the Railway-side commands come from Railway's docs rather than my terminal. Everything else ran on Prisma CLI 8.0.0-rc.27 and Composer 0.34.0. Run the CLI as `npx prisma@latest`, because if your project has an older `prisma` package installed, plain `npx prisma` runs that one and none of these commands exist in it.

### The database

Prisma Postgres gives you two hostnames for the same credentials: a pooled one for your app, which hands out a connection per transaction, and a direct one for tools like `pg_restore` that need a single session for the whole job. The create command prints the pooled string once and never again, so save it, and use the direct host `db.prisma.io` for the restore. I'd rehearse the whole thing before going anywhere near production: dump from Railway's public TCP proxy URL, or through a `railway connect postgres --tunnel-only` tunnel if you'd rather not pay egress, restore into the new database, check the counts. When you're ready to cut over, pause writes, take one more dump, and run the exact same restore on top of the rehearsal data.

```bash
npx prisma@latest auth login
npx prisma@latest project create my-db-project
npx prisma@latest postgres create my-db --region us-east-1    # prints the connection string once

pg_dump -Fc --no-owner --no-privileges -d "$DATABASE_PUBLIC_URL" -f railway.dump
pg_restore --clean --if-exists --no-owner --no-privileges --exit-on-error \
  -d 'postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require' railway.dump
```

Afterwards I compared row counts, a per-table checksum, foreign keys, indexes and sequence values against the source, and everything matched. The `--clean --if-exists` pair is what lets the same command run again at cutover without emptying the database by hand, and the PostgreSQL 17 client tools matter because `pg_restore` has to be at least as new as the server it restores into. If the database was all you wanted to move, that's it: point your Railway service at the pooled string in place of the `${{Postgres.DATABASE_URL}}` reference and redeploy.

### The app

Prisma Compute runs your service on Bun, and you describe the app to it with [Prisma Composer](https://www.prisma.io/docs/composer), which is in Early Access; everything below is what the versions above accept. The [porting guide](https://www.prisma.io/docs/composer/porting-an-app) assumes Composer creates the database for you, and mine already existed, so I passed its connection string in as a secret instead. I kept my Hono server and its build step exactly as they were, changed a few lines so the port and the database URL come from the `service.ts` file below instead of `process.env`, and added three small files:

```ts
// prisma.config.ts
import { defineConfig as composer } from "@prisma/composer/config";
import { nodeBuild } from "@prisma/composer/node/control";
import { prismaCloud, prismaState } from "@prisma/composer-prisma-cloud/control";
import { definePrismaConfig } from "prisma/config";

export default definePrismaConfig({
  composer: composer({
    extensions: [prismaCloud({ region: "us-east-1" }), nodeBuild()],
    state: prismaState(),
  }),
});

// src/service.ts
import node from "@prisma/composer/node";
import { secretString } from "@prisma/composer/arktype";
import { compute } from "@prisma/composer-prisma-cloud";
import { type } from "arktype";

export default compute({
  name: "api",
  deps: {},
  input: type({ databaseUrl: secretString() }),
  build: node({ module: import.meta.url, entry: "../dist/server.mjs" }),
});

// module.ts
import { module } from "@prisma/composer";
import { envSecret } from "@prisma/composer-prisma-cloud";
import api from "./src/service.ts";

export default module("my-api", ({ provision }) => {
  provision(api, { input: { databaseUrl: envSecret("POSTGRES_URL") } });
});
```

In the server, `service.port()` gives the port and `service.input().databaseUrl.expose()` the connection string; `.expose()` is Composer's deliberate step for turning a declared secret into a plain string. The first thing that tripped me up was the secret's name. I called it `DATABASE_URL`, and the deploy refused with `envSecret name "DATABASE_URL" is reserved`, because Prisma Cloud keeps that name, its pooled twin and anything starting with `COMPOSER_` for itself. The second snag came when I deployed into the same project my database lived in and got `HostedStateBootstrapError`. The docs point you at `--name` for that; what worked for me was giving the app its own project, created from its own directory, which also means the secret can go in before the first deploy:

```bash
npx prisma@latest project create my-api
POSTGRES_URL='<pooled connection string>' npx prisma@latest project env add POSTGRES_URL --role production
npm run build
npx prisma@latest deploy module.ts
```

I ran the deploy from inside the git checkout so the Prisma Console could file it under a commit. It printed a live URL in under 30 seconds, and reads and writes through it landed in the migrated database. My first request against that URL came back as a 502, though: the cold first query ran past the 10 second default `idleTimeout` on `Bun.serve`, which is what Hono's default export runs on, so raise that number if your app is served through `Bun.serve`. Keep Railway running until the new URL has earned your trust, then register your hostname with `prisma service domain add` and point a CNAME at the target it prints. Going back to Railway later is the same move in reverse, DNS back plus a dump of whatever was written since cutover, while a bad deploy on Compute is a different kind of problem that `prisma service version rollback` fixes.

## Try it with your coding agent

Paste this into Claude, Cursor or whichever agent you use, from inside your project:

```text
Migrate this app from Railway to Prisma Postgres (database) and Prisma Compute (hosting). I have not used Prisma before. Ask me before any step that touches production or deletes anything, and do not modify the Railway project, service or variables. Refer to secrets by variable name only; never print, log or commit values, and check that a variable is set with [ -n "$VAR" ] rather than echoing it. Always run the Prisma CLI as `npx prisma@latest`.

1. Inspect the app: framework, database client, env var names, railway.json or Dockerfile. Check the database for extensions Prisma Postgres does not support (PostGIS, TimescaleDB) and the app for WebSockets, cron, persistent disk, native Node addons or a non-TypeScript runtime. If any apply, stop and tell me.
2. Read https://www.prisma.io/docs/postgres/import-from-existing-database, https://www.prisma.io/docs/composer/porting-an-app and https://www.prisma.io/docs/compute/limitations. Ask me which region to use for both the database and the app.
3. These steps are mine, because they print or take secrets: `auth login`, `postgres create` (I will save the connection string), and `project env add POSTGRES_URL --role production` with the value read from my shell. Tell me when to run each.
4. Database: confirm pg_dump and pg_restore are 17.x. Dump with `pg_dump -Fc --no-owner --no-privileges` from $DATABASE_PUBLIC_URL, restore with `pg_restore --clean --if-exists --no-owner --no-privileges --exit-on-error` over the direct db.prisma.io host (same credentials, different host), then compare row counts and a per-table checksum.
5. App: add the Composer files per the porting guide, with the region and the matching build adapter (nodeBuild or nextjsBuild) in prisma.config.ts. Read the port from service.port() and the database URL from the declared input, named anything except DATABASE_URL, DATABASE_URL_POOLED or a name starting with COMPOSER_. From the app directory run `npx prisma@latest project create <app-name>` matching the module name, run the project's build (deploy does not build), then `npx prisma@latest deploy module.ts` from inside the git repository.
6. Test the deployed URL, then write me a cutover checklist (pause writes, final dump and restore, `prisma service domain add`, DNS CNAME) and a rollback checklist (DNS back, reverse dump of anything written since cutover).
```

Whatever you decide about hosting, pick one key this week and rotate it while nothing is broken. You'll find out what your deploy path does to you, with time to fix it.
