Early on Wednesday, a developer with a small marketplace backend on Railway noticed that builds had stopped. By evening they knew why. Railway had [disclosed](https://blog.railway.com/p/security-disclosure-wednesday-october-21st) that someone outside the company had reached the systems holding customer environment variables and, for some of them, read the decrypted values. The advice was to rotate everything. The developer did the careful things first, signing out old sessions and checking the dashboard, and then discovered that the only way to ship new values to a running app was a deploy, and deploys were paused. Their [post on r/devops](https://www.reddit.com/r/devops/comments/1xc6bbp/railways_security_incident_is_more_serious_than_a/) filled up with people in the same bind. Several found out about the exposure from OpenAI, Anthropic or OpenRouter disabling a key before Railway's email arrived. One wrote that a fifty dollar spend limit was the only thing standing between them and an open-ended bill.

If that's you, rotate first and read the rest later. Anything that can spend money goes first. Replacing a value in Railway doesn't kill the old key; revoking it at the provider does, so do that part. Your Railway Postgres password is on the list too, because a database URL is an environment variable like any other. Railway's [guide for the database](https://blog.railway.com/p/security-disclosure-recommendation-rotate-postgresql-database-credentials) and its [other recovery posts](https://blog.railway.com/) are clear and worth following to the letter. The team has been posting updates around the clock and builds came back plan by plan on Thursday. A preliminary incident report is promised on the [status page](https://status.railway.com). I wouldn't want their week.

I work at Prisma, so you should know that going in. Further down I walk through moving a Postgres database and a TypeScript app off Railway, because some people will want that option once the rotation is done, and I rehearsed it before writing it down. The part before that is what I'd want to read if I were still on Railway today.

## Every host has this trap

What stayed with me from that thread is how little of it was specific to Railway. On almost every platform I've used, a new secret only takes effect after a redeploy. [Prisma Compute](https://www.prisma.io/docs/compute) is no different. Most days nobody notices. The day your host freezes deploys to contain a breach, rotation and recovery are suddenly stuck behind the same broken thing, and you're choosing between a leaked key that still works and taking your own app down.

The real fix is an app that reads its secrets at runtime from a store you control, so a frozen deploy path never blocks a rotation. I'm not rebuilding mine for that this week, and I suspect you aren't either. So here is what I'm actually doing instead. The first thing was an inventory of every secret I hold, what it can reach and where I'd go to revoke it, because I can revoke a key at the provider whether or not my host is deploying. Every LLM and cloud key now has a hard spend limit, after watching a fifty dollar cap save someone in that thread. Where a provider lets me hold two live keys, I'll add the new one, redeploy, and only then kill the old. The canonical copy of each value lives in a secrets manager now, since most platforms won't show a value back once it's set. And I'm taking a logical backup I own. Railway's own [backups guide](https://docs.railway.com/guides/postgres-backups-restores) recommends a scheduled dump and a restore drill alongside its snapshots, and that same dump turns out to be the first step of a migration.

## Moving the database and the app

Extensions decide the database side. [Prisma Postgres](https://www.prisma.io/docs/postgres) covers most of them, with PostGIS and TimescaleDB the usual ones it [doesn't](https://www.prisma.io/docs/postgres/import-from-existing-database). The app side is where I'd expect most people to bounce. Compute runs one shape of thing, a TypeScript HTTP service on Node, Bun or Next.js, and my Hono server happens to be that shape. If yours ships as a Dockerfile, holds WebSockets open, writes to a disk or leans on Railway's cron, keep the database half of this post and skip the rest; the [limitations](https://www.prisma.io/docs/compute/limitations) page is honest about all of it. One more Prisma name is coming, Composer, and it's nothing grander than a few lines of TypeScript telling Compute how to run the app.

I don't have a Railway account, so a local PostgreSQL 17 database with 500 users and 5,000 posts played the part of Railway, and the two Railway-side commands below come from Railway's docs rather than my terminal. Everything else ran on Prisma CLI 8.0.0-rc.27 and Composer 0.34.0, as `npx prisma@latest`, and the `@latest` is doing work. If your project already has an older Prisma package installed, plain `npx prisma` runs that one, and none of these commands exist in it.

### The database

Prisma Postgres hands you two hostnames for the same credentials. The pooled hostname is the one the app talks to. It hands out a fresh connection per transaction, so anything you prepared on one request is gone by the next. `pg_restore` can't work like that; it needs one session for the whole job, and that's what the direct hostname is for. The create command prints the pooled string exactly once, so I pasted it into my password manager, and for the restore I swapped the hostname to the direct one.

My rehearsal was dull on purpose. I dumped from my stand-in database, restored into the empty Prisma one and counted rows on both sides. On Railway the dump comes from the public proxy URL, or through the CLI's tunnel on a big database so you're not paying egress just to rehearse. Cutover is the rehearsal again with writes paused: one last dump, then the same restore on top of what's already there.

```bash
npx prisma@latest auth login
npx prisma@latest project create my-db-project
npx prisma@latest postgres create my-db --region us-east-1    # prints the connection string once

pg_dump -Fc --no-owner --no-privileges -d "$DATABASE_PUBLIC_URL" -f railway.dump
pg_restore --clean --if-exists --no-owner --no-privileges --exit-on-error \
  -d 'postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require' railway.dump
```

When it finished I compared row counts, a per-table checksum, foreign keys, indexes and sequence values against the source, and everything matched. Telling `pg_restore` to clear existing tables first is what makes that same command safe to run again at cutover. I used the PostgreSQL 17 client tools throughout, and you'll want them too, because the restore tool has to be at least as new as the server it restores into. If the database was all you wanted to move, this is where you stop. Your Railway service gets the pooled string where the Railway one used to be, and a redeploy picks it up.

### The app

Prisma Compute runs your service on Bun, and you describe the app to it with [Prisma Composer](https://www.prisma.io/docs/composer). Composer is in Early Access, so what follows is what the versions above accept. Its [porting guide](https://www.prisma.io/docs/composer/porting-an-app) assumes Composer creates the database for you; mine already existed, so I handed it the connection string as a secret instead. I expected this to be the painful part, and mostly it wasn't. My Hono server and its build step stayed exactly as they were. A few lines changed so the port and the database URL come from the service file rather than `process.env`, and three small files appeared beside the code:

```ts
// prisma.config.ts
import { defineConfig as composer } from "@prisma/composer/config";
import { nodeBuild } from "@prisma/composer/node/control";
import { prismaCloud, prismaState } from "@prisma/composer-prisma-cloud/control";
import { definePrismaConfig } from "prisma/config";

export default definePrismaConfig({
  composer: composer({
    extensions: [prismaCloud({ region: "us-east-1" }), nodeBuild()],
    state: prismaState(),
  }),
});

// src/service.ts
import node from "@prisma/composer/node";
import { secretString } from "@prisma/composer/arktype";
import { compute } from "@prisma/composer-prisma-cloud";
import { type } from "arktype";

export default compute({
  name: "api",
  deps: {},
  input: type({ databaseUrl: secretString() }),
  build: node({ module: import.meta.url, entry: "../dist/server.mjs" }),
});

// module.ts
import { module } from "@prisma/composer";
import { envSecret } from "@prisma/composer-prisma-cloud";
import api from "./src/service.ts";

export default module("my-api", ({ provision }) => {
  provision(api, { input: { databaseUrl: envSecret("POSTGRES_URL") } });
});
```

In the server, `service.port()` gives you the port and `service.input().databaseUrl.expose()` the connection string; that `.expose()` call is Composer making you say out loud that you're turning a secret into a plain string. Two things tripped me up, and both were my fault. I first named the secret `DATABASE_URL`, and the deploy refused, because Prisma Cloud reserves that name, its pooled twin and anything starting with `COMPOSER_` for databases it provisions itself. Then I deployed into the same project my database lived in and got a `HostedStateBootstrapError`. The docs point you at a `--name` flag for that. What worked for me was giving the app its own project. I created it from the app's directory, which also meant the secret could go in before the first deploy:

```bash
npx prisma@latest project create my-api
POSTGRES_URL='<pooled connection string>' npx prisma@latest project env add POSTGRES_URL --role production
npm run build
npx prisma@latest deploy module.ts
```

I ran that from inside the git checkout so the Prisma Console could file the deployment under a commit. It printed a live URL in under thirty seconds, and reads and writes through it landed in the migrated database. My very first request came back as a 502, which gave me a moment. Hono's default export runs on `Bun.serve`, whose idle timeout defaults to ten seconds, and my cold first query ran past it. If yours is served the same way, that timeout is the one to raise. After that it behaved. I'd leave Railway up for a few days after this. The CLI registers your hostname and prints a CNAME target, and changing DNS to it is the actual cutover, so there's no reason to do it before the new URL has carried real traffic. Going back to Railway later is the same move in reverse, DNS back plus a dump of whatever was written since cutover. A broken deploy on Compute doesn't need any of that; you roll back to the previous version.

## Try it with your coding agent

Paste this into whatever coding agent you use, from inside your project:

```text
Migrate this app from Railway to Prisma Postgres (database) and Prisma Compute (hosting). I have not used Prisma before. Ask me before any step that touches production or deletes anything, and do not modify the Railway project, service or variables. Refer to secrets by variable name only; never print, log or commit values, and check that a variable is set with [ -n "$VAR" ] rather than echoing it. Always run the Prisma CLI as `npx prisma@latest`.

1. Inspect the app: framework, database client, env var names, railway.json or Dockerfile. Check the database for extensions Prisma Postgres does not support (PostGIS, TimescaleDB) and the app for WebSockets, cron, persistent disk, native Node addons or a non-TypeScript runtime. If any apply, stop and tell me.
2. Read https://www.prisma.io/docs/postgres/import-from-existing-database, https://www.prisma.io/docs/composer/porting-an-app and https://www.prisma.io/docs/compute/limitations. Ask me which region to use for both the database and the app.
3. These steps are mine, because they print or take secrets: `auth login`, `postgres create` (I will save the connection string), and `project env add POSTGRES_URL --role production` with the value read from my shell. Tell me when to run each.
4. Database: confirm pg_dump and pg_restore are 17.x. Dump with `pg_dump -Fc --no-owner --no-privileges` from $DATABASE_PUBLIC_URL, restore with `pg_restore --clean --if-exists --no-owner --no-privileges --exit-on-error` over the direct db.prisma.io host (same credentials, different host), then compare row counts and a per-table checksum.
5. App: add the Composer files per the porting guide, with the region and the matching build adapter (nodeBuild or nextjsBuild) in prisma.config.ts. Read the port from service.port() and the database URL from the declared input, named anything except DATABASE_URL, DATABASE_URL_POOLED or a name starting with COMPOSER_. From the app directory run `npx prisma@latest project create <app-name>` matching the module name, run the project's build (deploy does not build), then `npx prisma@latest deploy module.ts` from inside the git repository.
6. Test the deployed URL, then write me a cutover checklist (pause writes, final dump and restore, `prisma service domain add`, DNS CNAME) and a rollback checklist (DNS back, reverse dump of anything written since cutover).
```

Whatever you decide about hosting, I'd rotate one key this week, on a day when nothing is broken, mostly to find out what your own deploy path does when you try.
