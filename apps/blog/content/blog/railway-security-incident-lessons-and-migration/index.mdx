Rotate every secret you store in Railway, revoke the old values at each provider, and only then decide whether to stay or move. Railway disclosed on October 21 that an attacker may have read customer environment variables, including some decrypted values, and the recovery steps below follow Railway's own guidance and work on any host. The migration section at the end is for teams who want an alternative; it is not a security fix. I work at Prisma, so read that section knowing where I sit.

## What happened at Railway

Railway has handled the incident in public, with status updates through the night and thirteen recovery guides inside a day, and affected developers compared notes in a [thread on r/devops](https://www.reddit.com/r/devops/comments/1xc6bbp/railways_security_incident_is_more_serious_than_a/).

According to Railway's [disclosure](https://blog.railway.com/p/security-disclosure-wednesday-october-21st) and [status page](https://status.railway.com), on October 21 the team detected anomalous activity in the systems that store customer environment variables and concluded that an unauthorized third party may have read encrypted variables and, for some of them, their decrypted contents. Railway believes the attack belongs to a series targeting platform companies in order to reach AI inference providers, and it notified those providers so they could revoke keys early. Railway paused all deployments during containment, restored builds plan by plan on October 22, and invalidated every API and project token created before the incident, so any pipeline holding one needs a new token.

As of the morning of October 23, Railway had not published a root cause or a count of affected accounts, though it has promised a preliminary incident report and is emailing customers it believes were hit. Developers in the thread described OpenAI, Anthropic and OpenRouter keys used by someone else, and in several cases the provider had already disabled the key, which fits Railway's account of notifying providers first. Those are individual reports and say nothing about how many customers the incident reached.

## What to do now, on any host

1. **Rotate every secret stored in Railway, starting with the LLM, cloud and payment keys that can spend your money.** Replacing the value in Railway leaves the old key alive at the provider until you revoke it there. Railway's [recovery posts](https://blog.railway.com/) cover GCP, AWS, GitHub, Stripe, OpenAI, Anthropic, Grok and OpenRouter one by one.
2. **Regenerate database passwords.** Railway's [PostgreSQL guide](https://blog.railway.com/p/security-disclosure-recommendation-rotate-postgresql-database-credentials) has you remove Public Access first if nothing outside the project needs the TCP proxy, then regenerate the password from the database's Config tab and restart the database, which drops every open session, including any an attacker holds. Redeploy dependent services afterwards.
3. **Check the logs of every service a leaked key could reach.** That means provider dashboards, cloud audit logs, Stripe events, and your own database's role list and row counts.
4. **Put hard spend limits on every key that can bill you.** One developer in the thread credited a fifty dollar cap with turning an open-ended charge into an annoyance.
5. **Take a logical backup you own, and rehearse restoring it.** Railway's [backups guide](https://docs.railway.com/guides/postgres-backups-restores) recommends a scheduled `pg_dump` and a restore drill alongside its volume snapshots.

All five steps share one constraint. On most platforms, Prisma Compute included, a new secret takes effect only after a redeploy, so a host that pauses deploys to contain a breach also pauses your rotation. Keep an inventory of every secret and where to revoke it, because revocation never needs a deploy.

## If you are considering moving to Prisma

You can move the database on its own, which is one dump and one restore, or move a TypeScript service alongside it. [Prisma Postgres](https://www.prisma.io/docs/postgres) is managed PostgreSQL 17, and [Prisma Compute](https://www.prisma.io/docs/compute) hosts TypeScript services next to it in the same project.

I rehearsed the path below against a local PostgreSQL 17 database with 500 users and 5,000 posts standing in for Railway. I do not use Railway, so its two commands come from Railway's documentation and I did not run them. Everything else ran on Prisma CLI 8.0.0-rc.27 and Composer 0.34.0 through `npx prisma@latest`, which sidesteps any older Prisma package in your project.

### Check compatibility

Prisma Postgres supports most common extensions; PostGIS and TimescaleDB are not on its list, and the [import guide](https://www.prisma.io/docs/prisma-postgres/import-from-existing-database-postgresql) shows how to list what your source uses. Your source must be PostgreSQL 17 or older, and you need the version 17 client tools, since `pg_dump` must be at least as new as your source and `pg_restore` at least as new as the dump. Compute runs TypeScript HTTP services on Node, Bun or Next.js, not Dockerfiles or other languages, and its [limitations](https://www.prisma.io/docs/compute/limitations) page rules out WebSocket servers, persistent disks and built-in cron. If that describes your app, the database half of this guide still applies.

### Back up Railway Postgres and restore it to Prisma Postgres

Prisma Postgres gives you two hostnames for the same credentials, a pooled one for the application and a direct one, `db.prisma.io`, for `pg_restore`, `psql` and migrations, which need a single session. The create command prints the pooled string once, so save it and swap the hostname for the restore.

Rehearse against a copy first. Dump through Railway's public TCP proxy URL, which Railway bills as egress, or through the CLI's database tunnel, then restore into an empty Prisma Postgres database and compare row counts. The restore runs in a single transaction, so a failure leaves the target empty rather than half filled.

```bash
npx prisma@latest auth login
npx prisma@latest project create my-db-project
npx prisma@latest postgres create my-db --region us-east-1    # prints the connection string once

umask 077    # the dump is a full copy of your data; keep the file private
pg_dump --format=custom --no-owner --no-privileges \
  --dbname="$DATABASE_PUBLIC_URL" --file=railway.dump

pg_restore --single-transaction --exit-on-error --no-owner --no-privileges \
  --dbname='postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require' railway.dump

psql 'postgres://USER:PASSWORD@db.prisma.io:5432/postgres?sslmode=require' -c 'ANALYZE;'
```

In my rehearsal the restore took eight seconds, and every count, checksum, constraint and sequence I compared matched the source. `pg_dump` copies row-level security policies but not the roles they reference, so read the import guide's section on Railway-only roles if you use RLS.

For the real cutover, stop writes on Railway, take a final dump and restore it into a fresh Prisma Postgres database. Verify the counts again, point your application at the pooled string, and keep the Railway database read-only until your rollback window closes. If the database is all you wanted to move, you are done once you replace the `${{Postgres.DATABASE_URL}}` reference on your Railway service with the pooled string and redeploy.

### Deploy the TypeScript app to Prisma Compute

You describe the app to Compute with [Prisma Composer](https://www.prisma.io/docs/composer), which is in Early Access. The [porting guide](https://www.prisma.io/docs/composer/porting-an-app) leaves your server and build alone and has you add a `service.ts` and `module.ts` beside them, plus a `composer` section in `prisma.config.ts` that names the region. The guide expects Composer to create the database; for an existing one, pass its connection string in as a secret. The only changes inside my Hono server were reading the port from `service.port()` and the connection string from the declared input instead of `process.env`.

Composer refuses to bind that secret under the name `DATABASE_URL` or `DATABASE_URL_POOLED` (the deploy stops with `envSecret name "DATABASE_URL" is reserved`), because Prisma Cloud seeds those names for databases it provisions, so pick another. My first deploy into the project that already held the database stopped with `HostedStateBootstrapError`; the docs offer `--name` to target a different project, and what worked for me was creating an empty project from the app directory first, which also lets you store the secret before anything runs:

```bash
npx prisma@latest project create my-api
read -s POSTGRES_URL && export POSTGRES_URL     # paste the pooled string; it stays out of shell history
npx prisma@latest project env add POSTGRES_URL --role production
npm run build
npx prisma@latest deploy module.ts
```

The deploy printed a live URL, and reads and writes through it landed in the migrated database. The first request after the deploy returned a 502 because the cold query outlasted the ten second default idle timeout on `Bun.serve`; raise it if `Bun.serve` fronts your app too, which it does for Hono's default export.

### Validate, cut over, and keep a way back

Run your smoke tests against the new URL while Railway still serves production. When you are satisfied, register your hostname with `prisma service domain add`, create the CNAME it prints, run `add` again once the record resolves, and let `prisma service domain wait` confirm TLS before you move traffic; the [domains guide](https://www.prisma.io/docs/compute/domains) covers apex domains. Rolling back to Railway means moving DNS back and, if you need the writes made after cutover, restoring a full dump of the Prisma database into a fresh Railway Postgres; never restore over the original with destructive flags. Rotating the database credential later works the way it does everywhere else, by updating the production variable and redeploying.

Whether you stay on Railway or move, write down the rotation you just did while it is fresh. Those notes are the drill for next time.
