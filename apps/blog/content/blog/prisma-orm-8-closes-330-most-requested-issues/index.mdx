[Prisma ORM 8](https://www.prisma.io/docs/orm) resolves 330 open issues from the prisma/orm GitHub repository. Together they carry about 8,922 upvotes, and the oldest of them has been open since 2019.

Prisma 8 changed a lot at once: a pure TypeScript runtime with no Rust engine, [a data contract](https://www.prisma.io/docs/orm/contract-authoring/the-data-contract) instead of a schema plus a generated client, [TypeScript migrations](/typescript-migrations-in-prisma-next), and [an extension system](/prisma-next-call-for-extension-authors). Most of what we have written so far covers those headline changes. What has had less attention is that many of the requests you have been filing for years are answered by them.

We are publishing this list because we keep meeting developers who hit one of these issues on Prisma 5, 6 or 7, worked around it, and do not know it is fixed. 

_If you have ever upvoted an issue about JSON typing, polymorphism, partial unique indexes, `prisma generate` in a monorepo, or an engine binary that would not load, this post is for you._

:::info[Checked against 8.0.0-rc.16]
Prisma 8 is a release candidate and we expect it to be Generally Available later this year. Every item below was checked against 8.0.0-rc.16, released on October 7, 2026, using the reference docs in the prisma/orm repository and the published packages. Upvote counts are GitHub reactions as of October 8, 2026.
:::

Some issues are resolved because the feature now exists. Others are resolved because the part of Prisma that caused the problem, such as the engine binaries or the generated client, no longer exists.

## Before we dive in

_Every issue on this list started with a developer taking the time to share a problem or suggest an improvement._

Many of the changes in Prisma ORM 8, from TypeScript migrations to the new contract artifact, were shaped by your feedback and discussions on GitHub.

If you tried Prisma before and moved on because of one of these issues, [give Prisma 8 another try](https://www.prisma.io/docs/orm). If you're already on Prisma 7, our [upgrade guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/postgresql) will help you make the move.

And if something still doesn't work the way you'd like, [join us on Discord](https://pris.ly/discord), [open a GitHub issue](https://github.com/prisma/orm/issues/new/choose), or upvote an existing one. We use those votes to help prioritize what to build next, and this list shows why your feedback matters.

## The 10 most-upvoted issues we resolved

### [#3219](https://github.com/prisma/orm/issues/3219) Define type of content of Json field (799 upvotes)

**Before:** A `Json` field was typed as `JsonValue`. The shape of the data lived in your head and in a cast at every read site, and nothing stopped a write from storing something else.

**After:** Prisma 8 adds value objects. A `type Address { ... }` block in the contract becomes a typed field, stored as `jsonb` on PostgreSQL and as an embedded document on MongoDB, and it reads back as that exact TypeScript shape. For JSON that needs runtime validation, [`@prisma/orm-extension-arktype-json`](https://www.prisma.io/docs/orm/extensions/using-extensions) stores an arktype-validated column and rejects payloads that fail the schema on decode. See [value objects in PSL](https://www.prisma.io/docs/orm/contract-authoring/psl-syntax).

```prisma
type Address {
  street  String
  city    String
  zip     String?
  country String
}

model User {
  id      String   @id @default(uuid())
  email   String
  address Address?
}
```

### [#2789](https://github.com/prisma/orm/issues/2789) PostGIS/GIS support (669 upvotes)

**Before:** A geometry column had to be declared `Unsupported("geometry")`, which made it invisible to Prisma Client. Every spatial read, write and index went through raw SQL.

**After:** [`@prisma/orm-extension-postgis`](https://github.com/prisma/orm/tree/main/packages/3-extensions/postgis#readme) makes geometry a column type, `postgis.Geometry(srid)`, with GeoJSON values at runtime and seven typed operations: `distance`, `distanceSphere`, `dwithin`, `contains`, `within`, `intersects` and `intersectsBbox`. 

They work as predicates in the ORM and as projections in the SQL builder, and `prisma db init` enables the PostGIS server extension before the first migration runs. Even better, all this functionality is provided [by a small extension](https://www.prisma.io/extensions/postgis). 

If you have a feature you wish Prisma supported, ask your favorite agent to implement it as an extension, just like this one. 

See [using extensions](https://www.prisma.io/docs/orm/extensions/using-extensions) or the [guide to build one](/prisma-next-call-for-extension-authors).

```typescript
const plan = db.sql.public.cafe
  .select('id', 'name')
  .select('meters', (f, fns) => fns.distanceSphere(f.location, point))
  .orderBy((f, fns) => fns.distanceSphere(f.location, point), { direction: 'asc' })
  .limit(10)
  .build();
const nearby = await db.runtime().query(plan);
```

### [#2505](https://github.com/prisma/orm/issues/2505) Support for a Union type (462 upvotes)

**Before:** A feed of videos, photos and posts could not be modeled as one thing. You either kept separate models and merged the results in application code, or flattened everything into one model full of nullable columns.

**After:** A base model declares `@@discriminator(type)` and each variant declares `@@base(Content, "video")`. A variant without `@@map` shares the base table; a variant with its own `@@map` gets its own table joined by primary key. Querying the base returns every variant as a union type, and `.variant()` narrows to one. Polymorphism is in the experimental tier. See [relational data modeling](https://www.prisma.io/docs/orm/data-modeling/relational-databases).

```prisma
model Content {
  id    Int    @id @default(autoincrement())
  title String
  type  String

  @@discriminator(type)
}

model Video {
  videoUrl String
  duration Int

  @@base(Content, "video")
}

model Photo {
  imageUrl String
  caption  String?

  @@base(Content, "photo")
}

model Post {
  body String

  @@base(Content, "post")
}
```

### [#1644](https://github.com/prisma/orm/issues/1644) Support for Polymorphic Associations (373 upvotes)

**Before:** A `Vote` that could belong to a `Post` or a `Comment` meant two models, `PostVote` and `CommentVote`, or two nullable foreign keys and a hand-maintained type column.

**After:** Relate `Vote` to the base model. The relation is typed as the union of its variants, `.include()` returns whichever variant the row is, and `.variant()` narrows when you need one. It is the same `@@discriminator` / `@@base` mechanism as the union type above, so one feature answers both requests. See [relational data modeling](https://www.prisma.io/docs/orm/data-modeling/relational-databases).

### [#4228](https://github.com/prisma/orm/issues/4228) Support distinct in count() (313 upvotes)

**Before:** The `count()` method had no `distinct` option, so a paginated page of distinct rows needed raw SQL for its total.

**After:** Collections have `.distinct(...fields)` and `.distinctOn(...fields)`, and since rc.5 `.aggregate()` reduces over exactly the rows the chain describes, including `distinct`, `cursor`, `take` and `skip`. A distinct count is one query. See [`distinct()`](https://www.prisma.io/docs/orm/reference/orm-client) and the [rc.5 release notes](https://github.com/prisma/orm/releases/tag/v8.0.0-rc.5).

```typescript
const { authors } = await db.orm.public.Post
  .distinct('authorId')
  .aggregate((a) => ({ authors: a.count() }));
```

### [#18442](https://github.com/prisma/orm/issues/18442) Support for pg_vector (242 upvotes)

**Before:** Embeddings needed `Unsupported("vector")` in the schema and raw SQL for every similarity search.

**After:** [`@prisma/orm-extension-pgvector`](https://www.prisma.io/docs/orm/extensions/using-extensions) adds `pgvector.Vector(1536)` as a column type (a `number[]` at runtime, `Vector<1536>` in `contract.d.ts`), `fns.cosineDistance(f.embedding, queryVector)` in `select` and `orderBy`, and a baseline migration that runs `CREATE EXTENSION IF NOT EXISTS vector`.

```typescript
const plan = db.sql.public.document
  .select('id', 'title')
  .select('distance', (f, fns) => fns.cosineDistance(f.embedding, queryVector))
  .orderBy((f, fns) => fns.cosineDistance(f.embedding, queryVector), { direction: 'asc' })
  .limit(5)
  .build();
const matches = await db.runtime().query(plan);
```

### [#4688](https://github.com/prisma/orm/issues/4688) Imperative Migrations with a TypeScript DSL (214 upvotes)

**Before:** Migrations were SQL files that Prisma generated. Anything the schema could not express, such as a custom index or a data backfill, was hand-written SQL appended to a generated file, and data migrations lived in separate scripts with no transaction in common.

**After:** Every migration is a `migration.ts`. `prisma migration plan` renders one from the contract diff and `prisma migration new` scaffolds an empty one. Operations are typed methods such as `this.addColumn` and `this.createIndex`, `rawSql` is the escape hatch, and `this.dataTransform` runs typed queries as a data step inside the same transaction. See [how migrations work](https://www.prisma.io/docs/orm/migrations/how-migrations-work) and [editing a migration](https://www.prisma.io/docs/orm/migrations/editing-a-migration).

### [#15423](https://github.com/prisma/orm/issues/15423) Named aggregations allowing multiple aggregations per field in one query (205 upvotes)

**Before:** `_count` could appear once per relation, so "total posts and published posts" was two queries and a merge.

**After:** Inside `.include()`, a relation branch can be filtered and reduced with `count()`, `sum()`, `avg()`, `min()` or `max()`, and `combine()` returns several named sub-views of one relation in a single query. See [`include()`](https://www.prisma.io/docs/orm/reference/orm-client)[ and ](https://www.prisma.io/docs/orm/reference/orm-client)[`combine()`](https://www.prisma.io/docs/orm/reference/orm-client).

```typescript
const users = await db.orm.public.User
  .include('posts', (posts) =>
    posts.combine({
      total: posts.count(),
      published: posts.where((p) => p.publishedAt.isNotNull()).count(),
      recent: posts.orderBy((p) => p.createdAt.desc()).limit(3),
    }),
  )
  .all();
// users[0].posts → { total: number; published: number; recent: Post[] }
```

### [#3387](https://github.com/prisma/orm/issues/3387) Support @unique on nullable fields for databases that support it (199 upvotes)

**Before:** `@unique` on a nullable column was all or nothing. PostgreSQL can enforce uniqueness only among non-null rows with a partial unique index, but the schema had no way to say so, so the index lived outside Prisma and fought drift detection.

**After:** `@@index` takes `where:` and `unique:`, so a partial unique index is declared in the contract and planned like any other change. `contract infer` adopts partial indexes that already exist. See [PSL syntax](https://www.prisma.io/docs/orm/contract-authoring/psl-syntax).

```prisma
model User {
  id    Int     @id @default(autoincrement())
  email String?

  @@index([email], where: "email IS NOT NULL", unique: true, name: "users_email_unique")
}
```

### [#4954](https://github.com/prisma/orm/issues/4954) Allow arbitrary enum values (179 upvotes)

**Before:** Enum members had to be valid identifiers, so values like `1st` or `"Apt."` needed `@map`, and nothing exposed the mapped value at runtime.

**After:** Enum members are written `Name = "stored value"` with a declared codec, stored as a plain column that gets a generated `CHECK` constraint on every table Prisma ORM manages. The TypeScript type is the union of stored values, and `db.enums` exposes the members at runtime. See [enums in PSL](https://www.prisma.io/docs/orm/contract-authoring/psl-syntax#enums).

```prisma
enum Place {
  @@type("pg/text@1")
  First  = "1st"
  Second = "2nd"
  Third  = "3rd"
}
```

## The complete list of issues resolved

The remaining 320 issues, grouped by theme and ordered by upvotes. Each entry links to the GitHub issue and, where it helps, to the docs. That brings the total to 330 distinct issues.

### Querying and aggregation (51)

- **[#4246](https://github.com/prisma/orm/issues/4246) Add option to skip unnecessary SELECT after create() (165 upvotes):** A SQL builder `insert()` run through `execute()` resolves `{ affectedRows }` with no read-back, `.returning(...)` makes a single `INSERT ... RETURNING`, and the ORM has `createAndCount()`. See [the SQL query builder](https://www.prisma.io/docs/orm/reference/sql-query-builder).
- **[#13517](https://github.com/prisma/orm/issues/13517) SQL joins without relations/foreign keys/raw query (110 upvotes):** The SQL builder does explicit, typed `innerJoin(...)` on any predicate, with aliases and typed projections, no relation or foreign key required. See [advanced queries](https://www.prisma.io/docs/orm/fundamentals/advanced-queries).
- **[#3197](https://github.com/prisma/orm/issues/3197) Compound unique with a nullable field should allow null (104 upvotes):** There is no generated compound-unique input type; a lookup is a predicate, so `.where((t) => and(t.name.eq(x), t.label.isNull())).first()` treats a null member as an ordinary condition.
- **[#15594](https://github.com/prisma/orm/issues/15594) Support query cancellation with AbortController / AbortSignal (101 upvotes):** `runtime.execute(plan, { signal })` takes a per-query `AbortSignal`, and cancellation surfaces as `RUNTIME.ABORTED` with the phase it hit. See [transactions and runtime](https://www.prisma.io/docs/orm/reference/transactions-and-runtime).
- **[#5761](https://github.com/prisma/orm/issues/5761) Access to raw sql functions using Prisma APIs. (94 upvotes):** `fns.raw`...`.returns(codec)` embeds a native SQL function inside a typed query, decoded through the named codec. See [raw queries](https://www.prisma.io/docs/orm/reference/raw-queries).
- **[#6252](https://github.com/prisma/orm/issues/6252) Select none in update() (92 upvotes):** A SQL builder `update()` run through `execute()` resolves `{ affectedRows }` with no read-back, and the ORM `.select('id').update(...)` narrows what comes back.
- **[#6570](https://github.com/prisma/orm/issues/6570) Filtered relation count aggregate (62 upvotes):** An `include` branch composes `.where(...)` and then a reducer such as `count()`, so the filtered count lands as a typed field on each parent. - **[#3796](https://github.com/prisma/orm/issues/3796) More elegant select API by listing fields as array (61 upvotes):** `.select(...)` takes field names as variadic strings, and nested selection composes on `include` branches.
- **[#10866](https://github.com/prisma/orm/issues/10866) Select _avg from relation and also return the parent entity (49 upvotes):** An `include` reducer returns the parent row with the relation replaced by its `avg()`, and `count`, `sum`, `min`, `max` and `combine()` work the same way.
- **[#19159](https://github.com/prisma/orm/issues/19159) Improve cursor pagination to tolerate hard deletes and avoid looking up the row at the cursor (43 upvotes):** `.orderBy(...).cursor({ field: lastValue })` is a keyset comparison on the sort columns and never looks up the cursor row, so a deleted cursor row is fine. See [reading data](https://www.prisma.io/docs/orm/fundamentals/reading-data).
- **[#5683](https://github.com/prisma/orm/issues/5683) Support Unsupported Types inside Prisma Client (not just Prisma Migrate) (41 upvotes):** Extension-typed scalars such as `pgvector.Vector` and `postgis.Geometry` are first-class columns with typed reads and operators, and you can author your own codecs. See [using extensions](https://www.prisma.io/docs/orm/extensions/using-extensions).
- **[#22631](https://github.com/prisma/orm/issues/22631) Support aggregations _sum on nested relations (39 upvotes):** An `include` reducer returns the per-parent `sum()` in the same query; `count`, `avg`, `min`, `max` and the lossless bigint variants work the same way.
- **[#5617](https://github.com/prisma/orm/issues/5617) support subqueries (37 upvotes):** The example in the issue, the latest open start per todo, is a filtered `include` reducer in one query, and `fns.raw` covers other scalar subselects.
- **[#13596](https://github.com/prisma/orm/issues/13596) Return affected rows from deleteMany() operation (33 upvotes):** A SQL builder `.delete().where(...).returning(...)` yields the removed rows in one statement, and a non-returning delete resolves `{ affectedRows }`. See [the SQL query builder](https://www.prisma.io/docs/orm/reference/sql-query-builder).
- **[#12279](https://github.com/prisma/orm/issues/12279) raw SQL expressions (31 upvotes):** `fns.raw` fragments typed by codec work inside `.select(...)` and `.where(...)`, and `db.raw.sql` runs a whole statement with a declared row shape. See [raw queries](https://www.prisma.io/docs/orm/reference/raw-queries).
- **[#1984](https://github.com/prisma/orm/issues/1984) Optimize SQL queries for "fluent API" (28 upvotes):** The fluent API is gone; relation loading is `.include()`, which the Postgres adapter lowers to one `LATERAL` + `json_agg` statement instead of one query per traversal.
- **[#26546](https://github.com/prisma/orm/issues/26546) First class Vector support (28 upvotes):** `pgvector.Vector(n)` is a column type with `cosineDistance` on the field proxy and in the SQL builder, and PostGIS `distanceSphere` covers the geo part of the request. See [using extensions](https://www.prisma.io/docs/orm/extensions/using-extensions).
- **[#7181](https://github.com/prisma/orm/issues/7181) Concat 2 columns while searching (24 upvotes):** A `fns.raw` fragment typed `pg/bool@1` is a valid `where()` predicate, so `CONCAT(...) ILIKE ...` runs inside the typed builder. See [raw queries](https://www.prisma.io/docs/orm/reference/raw-queries).
- **[#24241](https://github.com/prisma/orm/issues/24241) Runtime error that occurs in findUnique() when unique constraint is composed of one field (24 upvotes):** There is no generated `WhereUniqueInput` or compound-unique naming; a lookup is `.first({ pk })` or `.where({ field }).first()`, typed from the contract.
- **[#23564](https://github.com/prisma/orm/issues/23564) Support cursor with relationLoadStrategy: join (23 upvotes):** `.cursor()` and `.include()` are methods on the same immutable collection, and includes are single-statement `LATERAL` joins, so cursor pagination never falls back to N+1.
- **[#13024](https://github.com/prisma/orm/issues/13024) Using RANK() OVER(...) (21 upvotes):** Window functions belong to the SQL builder lane: a typed `fns.raw` projection with `.returns(codec)` sits next to model fields. See [the SQL query builder](https://www.prisma.io/docs/orm/reference/sql-query-builder).
- **[#5044](https://github.com/prisma/orm/issues/5044) Pass falsy values to disconnect a relation (20 upvotes):** ORM writes take foreign-key scalars directly, so `update({ personalTeamId: null })` clears an optional relation with no checked/unchecked split and no `P2017`.

- **[#13017](https://github.com/prisma/orm/issues/13017) SQL Query Builder (19 upvotes):** A typed SQL builder lane, `db.sql.<ns>.<table>`, ships beside the ORM with explicit joins, aliases, computed projections, window functions and `RETURNING`. See [the SQL query builder](https://www.prisma.io/docs/orm/reference/sql-query-builder).
- **[#19030](https://github.com/prisma/orm/issues/19030) Add support for SQL functions in filter conditions (19 upvotes):** SQL builder `where()` callbacks receive `fns`, and a `fns.raw` fragment with `.returns('pg/bool@1')` expresses any SQL function such as `TRIM`. See [raw queries](https://www.prisma.io/docs/orm/reference/raw-queries).
- **[#2652](https://github.com/prisma/orm/issues/2652) Get column name from field name (for @map) + referenced table and column name from relation field (via @relation and then field) (17 upvotes):** `db.sql.<ns>.<table>` is a typed builder over the physical table, and `contract.json` carries every field's column name under `storage`. See [the contract artifact](https://www.prisma.io/docs/orm/contract-authoring/the-contract-artifact).
- **[#27047](https://github.com/prisma/orm/issues/27047) Expected object, got object error with queryCompiler selecting relations (17 upvotes):** Fixed in 6.9, and Prisma 8 has no `queryCompiler` preview: nested includes lower to one `LATERAL` + `json_agg` query.
- **[#13004](https://github.com/prisma/orm/issues/13004) @Transactions decorator, Expose and accept a transaction object (16 upvotes):** `db.transaction(async (tx) => ...)` hands you a `tx` context with the same `orm` and `sql` surfaces, which you can pass to any helper. See [transactions](https://www.prisma.io/docs/orm/fundamentals/transactions).
- **[#14978](https://github.com/prisma/orm/issues/14978) Type error in IN clause in postgreSQL using $queryRaw when upgrading to v4 (13 upvotes):** The cast in 4.x was intentional; in Prisma 8 the ORM `.in([...])` and the SQL builder are typed by the column codec, and the raw lane binds parameters through declared codecs.
- **[#21648](https://github.com/prisma/orm/issues/21648) Postgres: too many bind variables in prepared statement on findMany() (13 upvotes):** Relations load via `LATERAL` + `json_agg` in one query; parent ids are never expanded into an `IN` list, so the 32,767 bind-variable cap is never reached.
- **[#8417](https://github.com/prisma/orm/issues/8417) Being able to do a create() query for Unsupported types (11 upvotes):** Extension-typed scalars are first-class typed fields you pass to `create()`; there is no `Unsupported()` escape hatch to work around.
- **[#16979](https://github.com/prisma/orm/issues/16979) Allow use of multiple compound ids in deleteMany() or findMany() (11 upvotes):** Writes are predicate-driven, so `.where(or(and(...), and(...))).delete()` runs one `DELETE` over every compound key, and `.all()` with the same predicate reads them.
- **[#20721](https://github.com/prisma/orm/issues/20721) Unclear error: Cannot select both '$scalars: true' and a specific scalar field (11 upvotes):** There is no engine-side query validation; `include()` takes only relation names typed from `contract.d.ts`, so an unknown name is a TypeScript error.
- **[#15263](https://github.com/prisma/orm/issues/15263) $queryRaw's unknown return type is too broad (7 upvotes):** `db.raw.sql` declares a codec per column in its row spec, so raw rows come back typed instead of `unknown`. See [raw queries](https://www.prisma.io/docs/orm/reference/raw-queries).
- **[#15708](https://github.com/prisma/orm/issues/15708) Nested Queries: Filter fields of 1-to-1 relations with where (4 upvotes):** `include('profilePicture', (p) => p.where(...))` works on to-one relations, and a refined to-one include is typed nullable because the refinement can exclude the row.
- **[#8560](https://github.com/prisma/orm/issues/8560) Cursor-based pagination not working as expected (only works if cursor actually exists) (3 upvotes):** `cursor({ field: value })` is value-based keyset pagination, so the cursor row does not need to exist.
- **[#17276](https://github.com/prisma/orm/issues/17276) groupBy() typings seem to be broken when inlined into a $transaction (3 upvotes):** There is no array-form `$transaction`; `groupBy` is a fluent chain typed from the contract and runs inside `db.transaction` like any other call.
- **[#17297](https://github.com/prisma/orm/issues/17297) Prisma.GroupByArgs not matching the arguments of the groupBy method (3 upvotes):** There is no `Prisma.XGroupByArgs`; grouping is a fluent chain, and a reusable predicate is typed with `ShorthandWhereFilter`.
- **[#14918](https://github.com/prisma/orm/issues/14918) Triggers not working properly with Prisma: [ERROR] Query '' is required to return data, but found no record(s). (2 upvotes):** `create` runs `INSERT ... RETURNING` and hands back the inserted row, so a trigger that rewrites the key does not break a follow-up `SELECT` by the original id.
- **[#15710](https://github.com/prisma/orm/issues/15710) Prisma is not using LIMIT for cursor based pagination. (2 upvotes):** Keyset pagination is `.orderBy(...).cursor({ field: lastValue }).limit(n)`: a value predicate plus `LIMIT`, with no `order_cmp` subquery.
- **[#18153](https://github.com/prisma/orm/issues/18153) Setting to Change Cursor Behavior when Cursor Record Doesn't Exist (2 upvotes):** `cursor({ field: value })` is value-based, so a missing cursor record simply yields the next rows after that value.

- **[#15197](https://github.com/prisma/orm/issues/15197) Command failed (AtlasError): Pipeline length greater than 50 not supported) (0 upvotes):** The Rust engine emitted one `$set` pipeline stage per field; Prisma 8 Mongo updates go through the MongoDB driver as a plain `$set` document or typed field operations.
- **[#17287](https://github.com/prisma/orm/issues/17287) Error in migration engine. Reason: [psl/builtin-connectors/src/mongodb.rs:125:9] not yet implemented (0 upvotes):** There is no Rust migration engine to panic; the Mongo interpreter rejects `@db.*` attributes with a diagnostic instead.
