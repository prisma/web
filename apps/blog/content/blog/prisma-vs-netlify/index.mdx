Prisma and Netlify both host full-stack TypeScript applications with managed Postgres, and both deploy every Git branch as a preview you can review before merging. They differ in what each platform sets up for you. On Prisma, one deploy of a [Prisma Composer](https://www.prisma.io/docs/composer) app provisions your services on [Prisma Compute](https://www.prisma.io/docs/compute), their [Prisma Postgres](https://www.prisma.io/docs/postgres) databases, and the authenticated connections between them, all from TypeScript definitions in your repository that the compiler type-checks first. Netlify builds and publishes a site's frontend and its functions together and connects a database branch to each Deploy Preview.

Choose Prisma when your app is TypeScript on Bun with a Postgres database, one region per service is enough, you can build on pre-release tooling today, and especially when several services call each other. Choose Netlify when you need its edge network and Image CDN for web delivery, Node.js rather than Bun, background work that runs for minutes, or preview databases pre-filled with production data.

The Prisma platform is four products: [Prisma ORM 8](https://www.prisma.io/docs/orm), a release candidate with general availability expected in October 2026, for typed data access; Prisma Postgres for the database; Prisma Compute for running TypeScript services; and Prisma Composer, in early access, for declaring how those services connect.

## Choose Prisma when

- Several TypeScript services call each other, and you want each call's contract in the dependency declaration so TypeScript checks the wiring. One service still deploys from a Git push, and you can add Composer later.
- Your services run on Bun, or can be made to, and one region per service with no edge runtime is enough.
- You want every Git branch to be an isolated environment with its own services and environment variables, and you are fine creating its database with one command or a Composer stage deploy.
- You can build on pre-release tooling. Prisma ORM 8 is a release candidate and Composer is in early access; Prisma Compute and Prisma Postgres are the hosting and database underneath them.

## Choose Netlify when

- Most of what you serve is pages and assets delivered worldwide, and you want caching and an Image CDN built in. Prisma Compute serves your app from one region with no edge runtime, and image resizing is a route you build with `Bun.Image`, as the [image transformations guide](https://www.prisma.io/docs/compute/image-transformations) shows.
- Your app runs on Node.js and you do not want to move it to Bun.
- You want preview databases that start as a copy of production. Netlify Database creates a branch per Deploy Preview with production data; on Prisma you provision a branch database and seed it yourself.
- You have background work that runs for minutes. Netlify Background Functions run for up to 15 minutes and Async Workloads add retries and multi-step jobs. A Prisma Compute request has 60 seconds to start responding, and work after the response relies on `waitUntil`, which does not retry failures or survive a redeploy.

## How do Prisma and Netlify compare?

| What you need | Prisma | Netlify |
| --- | --- | --- |
| Application hosting | TypeScript HTTP services on Prisma Compute, running on Bun, one region per service | Serverless Functions and Edge Functions deployed with the site on Netlify's edge network |
| Managed PostgreSQL | Prisma Postgres, which any PostgreSQL client can use | Netlify Database, [built on Neon](https://www.netlify.com/blog/netlify-database/) and managed through Netlify |
| Typed data access | Prisma ORM 8, or the PostgreSQL client you prefer | Drizzle ORM, or any PostgreSQL driver or ORM including Prisma ORM |
| Service-to-service wiring | Composer declares each dependency with its typed contract and provisions the connection | Site and functions build together and share types through imports |
| Application previews | Each Git branch deploys to its own environment, torn down when the branch is deleted | Each pull request gets a Deploy Preview; branches get branch deploys |
| Preview databases | A separate database per Git branch, provisioned by you or by a Composer stage deploy, with no production data copied | A Neon-backed database branch with a copy of production data for each Deploy Preview |
| Long-running work | 60 seconds to start responding, then `waitUntil` for work after the response; scheduled jobs through Composer; no WebSockets | Background Functions up to 15 minutes; Async Workloads for retries and multi-step jobs |
| Billing model | Plan fee plus requests, provisioned memory, active CPU, and outbound bandwidth; nothing for deploys or seats | A credit allowance per plan; compute, requests, bandwidth, and production deploys consume credits |

## How do you define the application?

On Prisma you describe services and their dependencies in TypeScript, and a Composer deploy provisions what you described. On Netlify you connect a repository and a build command, and a push builds and publishes the site and its functions together. A site and its functions in one repository already share types through imports, so the difference only matters once you have separately deployed services that call each other.

A few Composer terms, since the rest of this section uses them:

- A **service** is one deployable unit, such as a Next.js app or a Bun HTTP server, declared with `compute()`.
- A **service contract** is a service's API written as schemas, using any validator that implements the Standard Schema spec, such as arktype or zod. It types both the handlers on the serving side and the client on the calling side. The service that serves a contract is its **producer**.
- A **data contract** is Prisma ORM 8's description of your database: the `contract.prisma` file that replaces `schema.prisma`.
- A **root module**, conventionally `module.ts`, is the file that provisions every service and resource and wires their dependencies together.
- A **stage** is Composer's name for a Prisma Compute preview branch: a complete, isolated copy of the app with its own services and databases. This post says "branch" for the Git branch and the environment it maps to, and "stage" when the deploy command or Composer is the subject.

Take a storefront that calls a catalog service for a product's price. The catalog publishes its API as a service contract, the storefront declares that contract as a dependency, and at runtime `service.load()` returns a typed client for it, built from the connection details the deploy injected.

```ts tab="catalog/contract.ts"
import { contract, rpc } from "@prisma/composer/service-rpc";
import { type } from "arktype";

export const catalogContract = contract({
  getPrice: rpc({
    input: type({ productId: "string" }),
    output: type({ amount: "number", currency: "string" }),
  }),
});
```

```ts tab="storefront/service.ts"
import nextjs from "@prisma/composer/nextjs";
import { rpc } from "@prisma/composer/service-rpc";
import { compute } from "@prisma/composer-prisma-cloud";
import { catalogContract } from "../catalog/contract.ts";

export default compute({
  name: "storefront",
  deps: { catalog: rpc(catalogContract) }, // [!code highlight]
  build: nextjs({ module: import.meta.url, appDir: ".." }),
});
```

```ts tab="storefront/data.ts"
import service from "./service.ts";

export async function priceFor(productId: string) {
  const { catalog } = service.load();
  return catalog.getPrice({ productId }); // [!code highlight]
}
```

```ts tab="module.ts"
import { module } from "@prisma/composer";
import catalogModule from "./src/catalog/module.ts";
import storefrontService from "./src/storefront/service.ts";

export default module("store", ({ provision }) => {
  const catalog = provision(catalogModule);
  provision(storefrontService, { deps: { catalog: catalog.rpc } }); // [!code highlight]
});
```

Suppose `getPrice` used to return a plain number and the catalog team changes it to an amount plus a currency, as the contract above shows. Every caller that still treats the result as a number fails to compile, because the storefront's client is typed from the same contract the catalog serves. A shared-types package in a monorepo gives you that compile-time check on any platform. What Composer adds is the root module in the last tab. It binds each dependency to the service that produces it, TypeScript checks that wiring, and a dependency bound to a service with a different contract or a producer missing a handler is a compile error, not a failed deploy. At deploy time Composer provisions the services and the authenticated connections that wiring describes, so application code never reads a URL from `process.env`. The contract above is a simplified illustration; the [Composer store example](https://github.com/prisma/composer/tree/main/examples/store) shows the real catalog and orders services built the same way.

The database follows the same pattern, and in the store example `catalogModule` packages the catalog service with its own database this way. A service declares `deps: { db: postgres(catalogData) }`, where `catalogData` wraps the emitted contract, and the module that owns the database provisions it with [`postgres({ name, contract: catalogData, config: "./prisma.config.ts" })`](https://www.prisma.io/docs/composer/databases). The deploy applies the database's migrations before the service starts, and because both ends share the contract value, it refuses to wire a service to a database whose schema does not match. Composer ships modules that work the same way for scheduled jobs, object storage, and event streams. Composer ships modules that work the same way for scheduled jobs, object storage, and event streams.

Everything about the database derives from `contract.prisma`. You edit it, run `prisma contract emit` to regenerate `contract.json` and `contract.d.ts`, and plan migrations from the same file. If you are coming from an earlier Prisma ORM, [Coming from Prisma ORM 7](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7) maps each old command to its ORM 8 name: `prisma generate` is now `prisma contract emit`, and `migrate dev` is `migration plan` followed by `db migrate`.

Netlify also supports typed database access with [Drizzle ORM](https://docs.netlify.com/build/data-and-storage/netlify-database/tooling/) against Netlify Database, and its [functions](https://docs.netlify.com/build/functions/overview/) are built and versioned with the site. What Composer adds is the contract between separately deployed services, checked at the dependency declaration.

You do not need several services to start. A single service can run on Prisma Compute with Prisma Postgres directly, deployed from a Git push without Composer, and you can adopt Composer when the app grows a second service or a scheduled job.

## How do preview databases and migrations work?

Both platforms build every branch and give you a running preview. On Prisma, each branch is its own environment where you provision a database, and Prisma ORM 8 can plan a migration path for databases that are at different schema versions. On Netlify, each Deploy Preview gets a database branch that arrives pre-filled with production data.

![Every Git branch is its own environment. The main branch runs the storefront and catalog services against the production database, which has id and email. The alice/phone branch runs its own copies against its own database with a phone column, and the bob/avatar branch does the same with an avatarUrl column.](/prisma-vs-netlify/imgs/branch-databases.svg)

### On Prisma

With the GitHub integration and [deploy on push](https://www.prisma.io/docs/compute/deploy-on-push) configured, each push to a feature branch deploys the application to that branch's preview environment. A [branch](https://www.prisma.io/docs/compute/branching) owns its own services, deployments, and any databases created on it, and deleting the Git branch tears all of that down, databases included, so treat a branch database as disposable.

Environment variables have three scopes, which the CLI calls roles: production values, preview values that every preview deploy gets, and branch overrides that replace a preview value for one branch. Set production's connection string once, and give previews their own:

```bash
npx prisma@latest project env add DATABASE_URL=<production-url> --role production
npx prisma@latest project env add DATABASE_URL=<shared-preview-url> --role preview
```

With only those two, every preview shares one preview database. For a database per branch, run the CLI from the feature branch, which it targets automatically, create a database there, and set a branch override, where `--branch` names the branch the override belongs to:

```bash
npx prisma@latest postgres create preview-db
npx prisma@latest project env add DATABASE_URL=<printed-url> --branch feature/search
```

For a Composer app, `npx prisma@latest deploy module.ts --stage <branch>` replaces both steps: it creates the stage's own databases, wires the services to them, and applies the migrations of any `postgres()` database typed by a data contract. Either way, a database reached through `DATABASE_URL` is only as isolated as the URL you set, and a preview pointed at production writes to production. Prisma does not copy production data into a branch database, so seed it yourself if the feature needs realistic rows. The [environment variables docs](https://www.prisma.io/docs/compute/environment-variables) cover all three scopes.

Now suppose Alice adds a `phone` field on her branch and Bob adds an `avatarUrl` field on his, each testing against their own database, and both branches merge the same afternoon. Alice's laptop database has `phone`, Bob's has `avatarUrl`, staging and production have neither, and every one of them needs the merged schema. Prisma ORM 6 and 7 apply migrations in timestamp order, so a migration's place in history comes from its name. In Prisma ORM 8, each migration records the contract version it starts from and the one it ends at, so the migrations form a graph of schema versions, which the docs call the [migration graph](https://www.prisma.io/docs/orm/migrations/the-migration-graph). After the merge, whoever merged runs `migration plan --name merge_alice --from <directory>` on `main`, where the directory is Alice's last migration as `migration graph` prints it, does the same for Bob, and commits the two merge migrations. It is the same `migration plan --name` command you use for a fresh migration, with `--from` telling it which state to start from. From then on `db migrate` takes any database, a laptop, staging, or production, from wherever it is to the merged version. Two migrations that change the same column still need a human to decide the result, as they would anywhere.

![The migration graph after the merge. State A is production with id and email. Alice's migration adds phone to reach state B, and Bob's migration adds avatarUrl to reach state C. Two merge migrations, one from B and one from C, both reach the merged state D. Each arrow is one migration, recorded as the state it starts from and the state it ends at.](/prisma-vs-netlify/imgs/migration-graph.svg)

The migration graph is a Prisma ORM 8 feature, so you get it on Netlify too. What the Prisma platform adds is the environment around it: a database per branch, a Composer stage that applies migrations at deploy time, and a release step you run against production's connection string:

```bash
npx prisma@latest migration check
npx prisma@latest db migrate --show --db "$PRODUCTION_DATABASE_URL"
npx prisma@latest db migrate --db "$PRODUCTION_DATABASE_URL"
```

The first checks that no compiled migration file or ref was edited by hand, the second prints what would run, and the third runs it.

### On Netlify

You connect a Git repository and configure a build command. With continuous deployment enabled, a push builds the site and its functions, a pull request gets a Deploy Preview URL for the team to review, and a merge into the production branch triggers a production deploy. Because the functions are versioned with the site, the preview runs the backend code that belongs to that branch.

Netlify Database gives each Deploy Preview a database branch containing a copy of production data from when the preview was first created, and Netlify's own migrations feature applies [migration files committed to Git](https://docs.netlify.com/build/data-and-storage/netlify-database/migrations/) as part of production and preview deploys. Changes made in the preview database stay separate from production, as its [database documentation](https://docs.netlify.com/build/data-and-storage/netlify-database/) describes. That pre-filled branch is an advantage over Prisma's empty branch databases when a feature needs production-shaped data to test.

Schema changes travel the same way on both platforms: as migration files in Git that your deployment applies. The preview branch's data stays out of production, and what reaches production is the migration. If you run Prisma ORM 8 on Netlify, the migration graph plans those migrations there as well, and you apply them with `npx prisma@latest db migrate --db "$NETLIFY_DB_URL"` in your build command or a release step, since Netlify exposes each Deploy Preview's branch through that variable.

## What can you run, and what does it cost?

Prisma Compute runs TypeScript HTTP services on Bun next to Prisma Postgres, so an existing Node.js app needs to run on Bun. Push-triggered builds detect Next.js, Nuxt, Astro, Hono, NestJS, TanStack Start, and plain Bun servers. Your application starts a server and handles requests, scales to zero when idle, and has 60 seconds to start responding to each request before Compute cancels it. Work that outlives the response, such as processing a webhook after returning `202`, uses `waitUntil` to keep the instance awake, which is best-effort: it does not retry failures or survive a redeploy. Compute does not require Prisma ORM, so a Prisma ORM 6 app runs there as-is; the migration workflow above assumes ORM 8. Each service runs in one region, there is no edge runtime, and WebSocket servers are not supported. The [limitations page](https://www.prisma.io/docs/compute/limitations) lists the runtime limits.

Netlify provides an edge network, caching, and an Image CDN for web delivery. For asynchronous work, its [Background Functions](https://docs.netlify.com/build/functions/background-functions/) run for up to 15 minutes, and [Async Workloads](https://docs.netlify.com/build/async-workloads/overview/) add retries and multi-step jobs.

Prisma Compute bills a plan fee plus four meters at [published rates](https://www.prisma.io/docs/compute/pricing). On both, memory is billed while an instance is running, whether it is busy or waiting on a database, and nothing is billed once the instance has scaled to zero. Netlify bills metered usage in credits: a plan includes a monthly allowance, and each metered feature consumes credits at a [published rate](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/). The dollar column below converts credits at Netlify's Pro rate of $20 for 3,000 credits, which is the same per-credit price as its Pro add-on of 1,500 credits for $10.

| Meter | Prisma Compute | Netlify (credits, and in dollars at the Pro rate) |
| --- | --- | --- |
| Plan | Free, or $10, $49, or $129 a month with 5, 20, or 100 million requests included | Pro from $20 a month for 3,000 credits |
| Requests | $1 per million after the plan's included requests | 2 credits per 10,000, about $1.33 per million |
| Compute | $0.006 per GB-hour of memory while an instance is running, plus $0.064 per vCPU-hour of active CPU | 10 credits per GB-hour of function compute, about $0.067; CPU is not metered separately |
| Outbound bandwidth | $0.025 per GB | 20 credits per GB, about $0.13 |
| Database compute | Prisma Postgres, metered separately | 10 credits per GB-hour, about $0.067 |
| Production deployments | Not billed | 15 credits each, about $0.10 |
| Preview and branch deploys | Not billed; a running preview bills its usage | Not metered by credits |

Prisma Postgres has [its own pricing](https://www.prisma.io/pricing), and Netlify Database compute and bandwidth are metered in the same credits as the rest of the site. Idle preview branches on Prisma cost nothing, because a preview scales to zero when it has no traffic and bills only while an instance is running. The one exception is Composer's cron scheduler, which stays awake as one warm instance per deployed app so that it can fire jobs on time, and a stage is a deployed copy, so a stage that includes the scheduler holds one too.

## Can you use Prisma with Netlify?

Yes, Prisma ORM runs in a Netlify-hosted application, and using the ORM does not require Prisma Compute or Prisma Postgres. Netlify Database is Postgres, so Prisma ORM connects to it like any other PostgreSQL database, and the [Netlify Database tooling page](https://docs.netlify.com/build/data-and-storage/netlify-database/tooling/) says any Postgres-compatible driver or ORM works. You run `db migrate` in your build command or release step and leave Netlify's migrations feature unused for that database. Prisma Postgres is also available through the official Netlify extension, which the [Netlify guide](https://www.prisma.io/docs/guides/postgres/netlify) walks through; that guide is written for Prisma ORM 7 today.

Prisma Postgres works with any PostgreSQL client, and Prisma Compute does not require Prisma ORM, so you can adopt one product without replacing everything at once.

## Try the Prisma workflow

The quickest way to judge the Prisma side is to ship one change that touches a service contract and a schema, and see what the compiler and the deploy catch. The [Composer getting-started guide](https://www.prisma.io/docs/composer/getting-started) uses a quotes service and a gateway that calls it, which play the same roles as the catalog and storefront above. Local runs need no Prisma account; you need one when you deploy in step 3.

<Steps variant="vertical">

<Step variant="vertical">

### Run the two-service example

Follow the getting-started guide to run the quotes service and the gateway locally with `npx prisma@latest dev module.ts`.

</Step>

<Step variant="vertical">

### Change a service contract

Rename or reshape a method in the quotes contract, then run your typecheck. The gateway's call site fails to compile until you update it.

</Step>

<Step variant="vertical">

### Add a database, change its schema, and preview it

The example ships without a database, so follow the [Composer databases page](https://www.prisma.io/docs/composer/databases) to give the quotes service a `postgres()` database typed by a `contract.prisma` file. Then add a field to that file, run `npx prisma@latest contract emit` and `npx prisma@latest migration plan --name <name>`, and deploy the branch as a stage with `npx prisma@latest deploy module.ts --stage <branch>`. The stage gets its own database with the migration applied.

</Step>

<Step variant="vertical">

### Merge and migrate production

Merge the branch, then run `npx prisma@latest db migrate --show --db "$PRODUCTION_DATABASE_URL"`, where the variable holds your production database's connection string, to see what would run. Drop `--show` to apply it.

</Step>

</Steps>

If that loop fits how your team ships, start with the [Composer getting-started guide](https://www.prisma.io/docs/composer/getting-started). If you need the Netlify-only features above, the [Netlify guide](https://www.prisma.io/docs/guides/postgres/netlify) gets Prisma ORM and Prisma Postgres running there instead.
