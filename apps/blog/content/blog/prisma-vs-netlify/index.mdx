Choose Prisma when your app is TypeScript services on Bun that call each other and share a Postgres database. Choose Netlify when you need its edge network and Image CDN, Node.js, background work that runs for minutes, or previews pre-filled with production data.

Both platforms host full-stack TypeScript apps with managed Postgres and preview every Git branch. The difference is what each one sets up for you. On Prisma, one deploy of a [Prisma Composer](https://www.prisma.io/docs/composer) app provisions your services on [Prisma Compute](https://www.prisma.io/docs/compute), their [Prisma Postgres](https://www.prisma.io/docs/postgres) databases, and the connections between them, all from TypeScript the compiler checks first. On Netlify, a push builds and publishes your site and its functions, and Netlify Database gives each Deploy Preview its own database branch.

The Prisma platform is four products: [Prisma ORM 8](https://www.prisma.io/docs/orm) (release candidate, general availability expected October 2026), Prisma Postgres, Prisma Compute, and Prisma Composer (early access).

## Choose Prisma when

- Several TypeScript services call each other. Each call's contract sits in the dependency declaration, so TypeScript checks the wiring. One service still deploys from a Git push; add Composer later.
- Your services run on Bun, or can, and one region with no edge runtime is enough.
- You want every Git branch to be its own environment, and you are fine creating its database with one command or a Composer stage deploy.
- You can build on pre-release tooling. ORM 8 is a release candidate and Composer is in early access.

## Choose Netlify when

- You mostly serve pages and assets worldwide and want caching and an Image CDN built in. Compute serves from one region, and you build [image routes](https://www.prisma.io/docs/compute/image-transformations) yourself.
- Your app runs on Node.js and you do not want to move to Bun.
- You want preview databases that start as a copy of production. Netlify Database creates one per Deploy Preview; on Prisma you provision and seed a branch database yourself.
- You have background work that runs for minutes. Netlify Background Functions run up to 15 minutes and Async Workloads add retries. A Compute request has 60 seconds to start responding, and `waitUntil` after that does not retry or survive a redeploy.

## How do Prisma and Netlify compare?

Prisma's edge is typed service wiring and an environment per branch. Netlify's edge is web delivery, runtime choice, long background jobs, and pre-filled preview databases.

| What you need | Prisma | Netlify |
| --- | --- | --- |
| Hosting | TypeScript services on Compute, running on Bun, one region each | Serverless and Edge Functions deployed with the site |
| Managed Postgres | Prisma Postgres, any client | Netlify Database, [built on Neon](https://www.netlify.com/blog/netlify-database/) |
| Typed data access | Prisma ORM 8, or any client | Drizzle, or any driver or ORM, including Prisma ORM |
| Service wiring | Composer binds each dependency to its typed contract | Site and functions build together and share types by import |
| Previews | One environment per Git branch, torn down with the branch | A Deploy Preview per pull request; branch deploys for branches |
| Preview databases | One per branch, provisioned by you or a stage deploy, no production data | A Neon branch per Deploy Preview with a copy of production |
| Long-running work | 60 seconds to first byte, then `waitUntil`; no WebSockets | Background Functions up to 15 minutes; Async Workloads |
| Billing | Plan fee plus requests, memory, CPU, bandwidth | Credits for compute, requests, bandwidth, and production deploys |

## How do you define the application?

On Prisma, the compiler checks how your services connect. On Netlify, a site and its functions share types by import, and anything beyond that is yours to add.

You describe services and dependencies in TypeScript, and a Composer deploy provisions them. On Netlify, you connect a repo and a build command, and a push publishes the site and its functions together. Four Composer terms, used below:

- A **service** is one deployable unit, declared with `compute()`.
- A **service contract** is a service's API as schemas (arktype, zod, or any Standard Schema validator). It types the handlers and the client. The service that serves it is the **producer**.
- A **data contract** is ORM 8's schema file, `contract.prisma`, which replaces `schema.prisma`.
- A **root module** (`module.ts`) provisions every service and resource and wires them together. A **stage** is a preview copy of the whole app.

Here is a storefront that asks a catalog service for a price. The catalog publishes a contract, the storefront declares it as a dependency, and `service.load()` returns a typed client.

```ts tab="catalog/contract.ts"
import { contract, rpc } from "@prisma/composer/service-rpc";
import { type } from "arktype";

export const catalogContract = contract({
  getPrice: rpc({
    input: type({ productId: "string" }),
    output: type({ amount: "number", currency: "string" }),
  }),
});
```

```ts tab="storefront/service.ts"
import nextjs from "@prisma/composer/nextjs";
import { rpc } from "@prisma/composer/service-rpc";
import { compute } from "@prisma/composer-prisma-cloud";
import { catalogContract } from "../catalog/contract.ts";

export default compute({
  name: "storefront",
  deps: { catalog: rpc(catalogContract) }, // [!code highlight]
  build: nextjs({ module: import.meta.url, appDir: ".." }),
});
```

```ts tab="storefront/data.ts"
import service from "./service.ts";

export async function priceFor(productId: string) {
  const { catalog } = service.load();
  return catalog.getPrice({ productId }); // [!code highlight]
}
```

```ts tab="module.ts"
import { module } from "@prisma/composer";
import catalogModule from "./src/catalog/module.ts";
import storefrontService from "./src/storefront/service.ts";

export default module("store", ({ provision }) => {
  const catalog = provision(catalogModule);
  provision(storefrontService, { deps: { catalog: catalog.rpc } }); // [!code highlight]
});
```

Change `getPrice` from a plain number to an amount plus a currency, and every caller that still expects a number fails to compile. A shared-types package gives you that on any platform.

What Composer adds is the root module. It binds each dependency to its producer, and TypeScript checks the binding: a mismatched contract or a missing handler is a compile error, not a failed deploy. The deploy then provisions the services and the authenticated connections, so app code never reads a URL from `process.env`. The [store example](https://github.com/prisma/composer/tree/main/examples/store) shows the full version.

Databases work the same way: a service declares `deps: { db: postgres(catalogData) }`, and the module that owns the database provisions it with [`postgres({ name, contract, config })`](https://www.prisma.io/docs/composer/databases). The deploy applies migrations before the service starts and refuses to wire a service to a database whose schema does not match. Cron jobs, object storage, and event streams follow the same pattern.

Everything about the database comes from `contract.prisma`. Edit it, run `prisma contract emit`, and plan migrations from the same file. Coming from an older Prisma ORM? [This page](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7) maps each old command to its ORM 8 name.

Netlify supports typed database access with [Drizzle](https://docs.netlify.com/build/data-and-storage/netlify-database/tooling/) against Netlify Database, and its [functions](https://docs.netlify.com/build/functions/overview/) build and version with the site. What Composer adds is the checked contract between separately deployed services.

You do not need several services to start. One service runs on Compute from a Git push, without Composer.

## How do preview databases and migrations work?

Prisma gives every branch its own environment and plans migrations across databases at different versions. Netlify gives every Deploy Preview a copy of production.

![Every Git branch is its own environment. The main branch runs the storefront and catalog services against the production database, which has id and email. The alice/phone branch runs its own copies against its own database with a phone column, and the bob/avatar branch does the same with an avatarUrl column.](/prisma-vs-netlify/imgs/branch-databases.svg)

### On Prisma

With [deploy on push](https://www.prisma.io/docs/compute/deploy-on-push) configured, each push deploys the branch to its own environment. A [branch](https://www.prisma.io/docs/compute/branching) owns its services and any databases created on it. Deleting the Git branch deletes all of it, databases included.

Environment variables have three scopes, which the CLI calls roles:

1. Production values.
2. Preview values, shared by every preview.
3. Branch overrides, which replace a preview value for one branch.

Set the first two once:

```bash
npx prisma@latest project env add DATABASE_URL=<production-url> --role production
npx prisma@latest project env add DATABASE_URL=<shared-preview-url> --role preview
```

For a database per branch, run the CLI from the feature branch, which it targets automatically, then add a branch override:

```bash
npx prisma@latest postgres create preview-db
npx prisma@latest project env add DATABASE_URL=<printed-url> --branch feature/search
```

For a Composer app, `npx prisma@latest deploy module.ts --stage <branch>` does both and applies migrations for any `postgres()` database. Either way, a preview pointed at production writes to production, and Prisma never copies production data into a branch database. Seed it if you need realistic rows. The [environment variables docs](https://www.prisma.io/docs/compute/environment-variables) cover the scopes.

Now suppose Alice adds `phone` on her branch, Bob adds `avatarUrl` on his, and both merge. Alice's database has one column, Bob's has the other, staging and production have neither, and all of them need the merged schema.

ORM 6 and 7 apply migrations in timestamp order. ORM 8 records, for each migration, the schema version it starts from and the one it ends at, so migrations form a [graph](https://www.prisma.io/docs/orm/migrations/the-migration-graph). After the merge, whoever merged runs `migration plan --name merge_alice --from <directory>` on `main`, using Alice's last migration directory as `migration graph` prints it, repeats it for Bob, and commits both. From then on `db migrate` takes any database, from wherever it is, to the merged version. Two migrations that change the same column still need a human to decide.

![The migration graph after the merge. State A is production with id and email. Alice's migration adds phone to reach state B, and Bob's migration adds avatarUrl to reach state C. Two merge migrations, one from B and one from C, both reach the merged state D. Each arrow is one migration, recorded as the state it starts from and the state it ends at.](/prisma-vs-netlify/imgs/migration-graph.svg)

The graph is an ORM 8 feature, so you get it on Netlify too. The platform adds the environment around it: a database per branch, a stage that migrates at deploy time, and a release step you run against production:

```bash
npx prisma@latest migration check
npx prisma@latest db migrate --show --db "$PRODUCTION_DATABASE_URL"
npx prisma@latest db migrate --db "$PRODUCTION_DATABASE_URL"
```

Check the compiled migration files, preview what would run, then run it.

### On Netlify

A push builds the site and its functions, a pull request gets a Deploy Preview URL, and a merge into the production branch deploys production. The functions are versioned with the site, so a preview runs the backend that belongs to that branch.

Each Deploy Preview gets a database branch with a copy of production data from when the preview was created, and Netlify applies [migration files committed to Git](https://docs.netlify.com/build/data-and-storage/netlify-database/migrations/) on production and preview deploys. Changes in the preview database stay out of production, per the [database docs](https://docs.netlify.com/build/data-and-storage/netlify-database/). That pre-filled branch beats Prisma's empty branch databases when you need production-shaped data.

Schema changes travel the same way on both: migration files in Git, applied on deploy. If you run ORM 8 on Netlify, apply them with `npx prisma@latest db migrate --db "$NETLIFY_DB_URL"` in your build or release step; Netlify exposes each preview's branch through that variable.

## What can you run, and what does it cost?

Compute is Bun, one region, and 60 seconds to first byte, with no seat or deploy charges. Netlify runs Node.js, long background jobs, and a global edge, and meters production deploys in credits.

Prisma Compute runs TypeScript HTTP services on Bun, so a Node.js app must run on Bun. Builds detect Next.js, Nuxt, Astro, Hono, NestJS, TanStack Start, and plain Bun servers. Your app starts a server, scales to zero when idle, and has 60 seconds to start responding. Work after the response uses `waitUntil`, which does not retry or survive a redeploy. No edge runtime, no WebSockets. Compute does not require Prisma ORM, so an ORM 6 app runs as-is. The [limitations page](https://www.prisma.io/docs/compute/limitations) has the full list.

Netlify provides an edge network, caching, and an Image CDN. [Background Functions](https://docs.netlify.com/build/functions/background-functions/) run up to 15 minutes, and [Async Workloads](https://docs.netlify.com/build/async-workloads/overview/) add retries and multi-step jobs.

Prisma bills a plan fee plus four meters; memory counts while an instance runs and nothing once it scales to zero. Netlify bills metered usage in [credits](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/) from a monthly allowance. The dollar column converts credits at the Pro rate of $20 for 3,000, the same per-credit price as the Pro add-on.

| Meter | Prisma Compute | Netlify (credits, in dollars at the Pro rate) |
| --- | --- | --- |
| Plan | Free, or $10, $49, $129 a month with 5, 20, 100 million requests | Pro from $20 a month for 3,000 credits |
| Requests | $1 per million after the included amount | 2 credits per 10,000, about $1.33 per million |
| Compute | $0.006 per GB-hour memory plus $0.064 per vCPU-hour CPU | 10 credits per GB-hour, about $0.067; no separate CPU meter |
| Bandwidth | $0.025 per GB | 20 credits per GB, about $0.13 |
| Database compute | Prisma Postgres, priced separately | 10 credits per GB-hour, about $0.067 |
| Production deploys | Not billed | 15 credits each, about $0.10 |
| Preview and branch deploys | Not billed | Not metered |

Prisma Postgres is [priced separately](https://www.prisma.io/pricing); Netlify Database compute and bandwidth use the same credits as the site. Idle previews on Prisma cost nothing; the one exception is Composer's cron scheduler, which keeps one warm instance per deployed app or stage.

## Can you use Prisma with Netlify?

Yes. Netlify Database is Postgres, so Prisma ORM connects to it like any other database; the [tooling page](https://docs.netlify.com/build/data-and-storage/netlify-database/tooling/) says any driver or ORM works. Run `db migrate` in your build or release step and leave Netlify's migrations feature unused for that database. Prisma Postgres is also available through the official Netlify extension; the [Netlify guide](https://www.prisma.io/docs/guides/postgres/netlify) covers it, written for ORM 7 today.

## Frequently asked questions

<Accordions type="single">
  <Accordion title="Is Prisma a replacement for Netlify?">
For TypeScript apps, mostly. Prisma Compute hosts the app and Prisma Postgres holds the data. It does not replace Netlify's edge network, caching, and Image CDN, and Compute has no WebSockets, no multi-region, and a 60-second first-byte limit.
  </Accordion>
  <Accordion title="Does Prisma give each preview its own database?">
Yes, if you create it. Each Git branch is an isolated environment; you provision its database with the CLI or a Composer stage deploy, and it starts without production data. A preview-scoped or branch-scoped `DATABASE_URL` keeps it off production.
  </Accordion>
  <Accordion title="What is the migration graph in Prisma ORM 8?">
A record of which schema version each migration starts from and ends at. After two branches merge, the ORM plans a path from each database's current version to the merged schema. It works on any host, including Netlify.
  </Accordion>
  <Accordion title="Can I use Prisma ORM with Netlify Database?">
Yes. Netlify Database is PostgreSQL built on Neon, and Prisma ORM connects to it like any other PostgreSQL database. Run migrations in your own build or release step. Prisma Postgres is also available through the official Netlify extension.
  </Accordion>
</Accordions>

## Try the Prisma workflow

Ship one change that touches a service contract and a schema, and see what the compiler and the deploy catch. The [Composer getting-started guide](https://www.prisma.io/docs/composer/getting-started) uses a quotes service and a gateway, the same roles as catalog and storefront above. Local runs need no account.

<Steps variant="vertical">

<Step variant="vertical">

### Run the two-service example

Follow the guide and run both services locally with `npx prisma@latest dev module.ts`.

</Step>

<Step variant="vertical">

### Change a service contract

Rename a method in the quotes contract and run your typecheck. The gateway fails to compile until you update it.

</Step>

<Step variant="vertical">

### Add a database and preview a schema change

Give the quotes service a `postgres()` database per the [databases page](https://www.prisma.io/docs/composer/databases). Add a field to `contract.prisma`, run `npx prisma@latest contract emit` and `npx prisma@latest migration plan --name <name>`, then `npx prisma@latest deploy module.ts --stage <branch>`. The stage gets its own migrated database.

</Step>

<Step variant="vertical">

### Merge and migrate production

Run `npx prisma@latest db migrate --show --db "$PRODUCTION_DATABASE_URL"` to preview, then drop `--show` to apply.

</Step>

</Steps>

If that loop fits your team, start with the [Composer getting-started guide](https://www.prisma.io/docs/composer/getting-started). If you need the Netlify-only features above, the [Netlify guide](https://www.prisma.io/docs/guides/postgres/netlify) gets Prisma ORM and Prisma Postgres running there instead.
