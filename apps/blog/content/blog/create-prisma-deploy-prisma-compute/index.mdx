Starting a new app should not turn into a stack assembly project.

New Prisma apps still have a lot of setup surface: framework scaffold, schema, Prisma Client, env, migrations, seed data, and a place to run the app.

`create-prisma` turns that setup into one interactive flow.

Now it can keep going. For Compute-ready templates, `create-prisma` can scaffold the app, generate Prisma Compute defaults in a TypeScript config file, set up Prisma Postgres, and deploy to Prisma Compute. The generated project can be redeployed later with the script it includes.

```bash
bun create prisma@latest
```

## From scaffold to deployed app

`create-prisma` already scaffolds framework starters with Prisma wired in: schema, client helper, seed file, database scripts, and an env file.

For Compute-ready templates, it also drops in `prisma.compute.ts`.

When you choose to deploy during setup, the flow can provision Prisma Postgres, wire the connection string into the project, run the Prisma setup, and ship the app to Prisma Compute in the same run.

## Add-ons for the rest of the workflow

`create-prisma` can also set up the tools around the app. During setup, you can choose add-ons for Prisma Skills, the Prisma MCP server, and the Prisma extension for supported editors.

Choose the Skills add-on when an agent will keep working in the repo after setup. It installs Prisma Agent Skills from [`prisma/skills`](https://github.com/prisma/skills), including the `prisma-compute` skill for deploys, logs, domains, and the Compute workflow.

That gives agents Prisma-specific context for changing and redeploying the app without moving those instructions into the prompt.

## Why deploy belongs in the starter

Deployment in `create-prisma` is about preserving the decisions the scaffold just made: framework, app name, port, env file, database connection, and generated scripts.

That is what the deploy step in `create-prisma` adds: a generated `prisma.compute.ts` that captures how your app deploys.

For a Hono app, the config looks like this:

```typescript
import { defineComputeConfig } from "@prisma/compute-sdk/config";

export default defineComputeConfig({
  app: {
    name: "my-api",
    framework: "hono",
    httpPort: 8080,
    env: ".env",
  },
});
```

The result is a project with aligned build, runtime, and redeploy defaults, not just an ORM dependency added to a starter.

For a closer look at the TypeScript deploy config it generates, including how it scales to monorepos, see [Configure Prisma Compute deploys in TypeScript](/prisma-compute-config-file).

Those same conventions make agent work more reliable: schema, env, deployment, and generated scripts all point at the same setup.

## Redeploying after setup

When you deploy through `create-prisma`, the generated project includes `prisma.compute.ts` and a `compute:deploy` script.

After making changes, redeploy from the project:

```bash
cd my-api
bun run compute:deploy
```

It redeploys your app code using the defaults in `prisma.compute.ts`. Database provisioning and migrations stay outside that redeploy script.

If you need to deploy an existing app that was not created with `create-prisma`, use the Prisma CLI directly:

```bash
bunx @prisma/cli@latest app deploy
```

## Start from one command

`create-prisma` is the new-project path: a Prisma-ready app and, for supported templates, its first Compute deploy, from one command.

Start interactively:

```bash
bun create prisma@latest
```

After that, changes redeploy through the generated config and scripts.
