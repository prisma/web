[Prisma Compute](https://www.prisma.io/docs/compute) is generally available today. It hosts TypeScript apps (Node.js, Bun, or Next.js) next to [Prisma Postgres](https://www.prisma.io/docs/postgres) on one plan and runs them on the Bun runtime. By default, your app runs in the same region as its databases, and once you set up deploy on push, every Git branch deploys as its own environment, with its own database when your app declares one. Usage is now billed, and Prisma's uptime SLA applies to Compute serving traffic on the Pro, Business, and Enterprise plans.

We opened the [public beta](/launching-prisma-compute-public-beta) on June 8, and Compute was free for the eleven weeks it ran.

## What GA means

With general availability:

- Usage is billed at the rates in the table below, unchanged since we published them in June.
- Prisma's [SLA](https://www.prisma.io/legal/sla) commits to 99.95% monthly uptime on the Pro, Business, and Enterprise plans and excludes pre-GA features. With GA, Compute serving your app's traffic is no longer excluded, subject to the other exclusions the SLA page lists. The Free and Starter plans are not covered.
- Every paid plan has a hard spend limit, on by default, which you can change in the Console.
- During the beta, Prisma built your app on its own servers when you pushed. Those Prisma-hosted builds are deprecated, and builds now run in your repository's GitHub Actions. A beta project still on Prisma-hosted builds shows a notice in the Console with its cutoff date and a button that opens the setup pull request; merge it before the cutoff.

Compute bills for requests, memory, CPU, and bandwidth:

| Meter              | Price                                                   |
| ------------------ | ------------------------------------------------------- |
| Requests           | $1 per million, after the plan's included requests      |
| Provisioned memory | $0.006 per GB-hour, while an instance is running         |
| Active CPU         | $0.064 per vCPU-hour of CPU time your code uses          |
| Outbound bandwidth | $0.025 per GB sent to the internet                      |

Every plan covers Compute and Prisma Postgres together, so the app and its database share one bill:

| Plan     | Price a month | Compute requests | Prisma Postgres operations | Memory, CPU, and bandwidth                                   |
| -------- | ------------- | ---------------- | -------------------------- | ------------------------------------------------------------ |
| Free     | $0            | 1 million        | 200,000                    | 360 GB-hours, 4 vCPU-hours, and 10 GB included; never billed |
| Starter  | $10           | 5 million        | 1 million                  | Billed from the first unit                                   |
| Pro      | $49           | 20 million       | 10 million                 | Billed from the first unit                                   |
| Business | $129          | 100 million      | 50 million                 | Billed from the first unit                                   |

The Free plan needs no credit card. When a workspace passes one of its limits, its apps pause until the next month or until you upgrade, so on the Free plan the cost of a traffic spike is downtime. The 360 GB-hours equal 512 MB of memory held for 30 days. Moving to a paid plan drops the free memory, CPU, and bandwidth, so the same memory costs $2.16 a month on Starter, plus its CPU time and the $10 fee. The fee pays for the larger request and database-operation allowances and daily backups, and on Pro and Business, the SLA. Enterprise plans are priced on request and include the SLA. The [pricing page](https://www.prisma.io/pricing) lists Prisma Postgres storage and overage rates.

Deployments, preview branch creation, and seats are not billed. An idle instance is snapshotted and stops billing memory until the next request resumes it, which is what scaling to zero means on Compute, so a preview that nobody is using costs only its database's storage, unless the app declares a `cron` schedule, whose scheduler stays awake in every environment. Builds run in your own GitHub Actions, so on a private repository they count against your GitHub plan's minutes. We explained the reasoning in [Price the Work, Not the Workflow](/price-the-work-not-the-workflow): when an agent deploys a preview ten times while it fixes a bug, the bill should count what those previews ran, not how many times they deployed.

The Usage page in the [Console](https://console.prisma.io/?utm_source=blog&utm_medium=blog&utm_campaign=compute-ga&utm_content=ga-post) breaks requests, memory, CPU, and bandwidth down by day, by app, and by response status. The [Compute pricing docs](https://www.prisma.io/docs/compute/pricing) work through example bills for a preview, an agent workload, and a bandwidth-heavy app.

## Where Compute fits in the Prisma stack

Compute is one part of the stack described in [Prisma Is Building the Stack for the Next Million Products](/building-the-stack-for-the-next-million-products), which we published today. An agent that has written a feature still needs a copy of the database it can change without touching production, a place to run the app, and logs to read, and each extra vendor adds credentials and an API to learn.

Prisma Postgres can give each branch its own database, and Compute runs the app on that branch, first as a preview and then, once you merge, in production. You, or an agent working for you, deploy, read runtime logs, roll back, and redeploy a fix through one CLI and one REST API. Builds run in GitHub Actions, so GitHub is the only other account involved, and build output appears there.

## What changed since the beta

The beta launched with deploys from the CLI and on push from GitHub, immutable versions with preview URLs and rollback, branch databases, per-branch environment variables, and custom domains. The sections below cover what changed between the beta launch and GA.

### A preview environment for every pushed branch

Deploys on push now build and run in your repository's GitHub Actions through [`prisma/cloud-deploy-action`](https://github.com/prisma/cloud-deploy-action). The default branch deploys to production, and every other branch deploys to a preview with its own services, environment variables, and the Prisma Postgres databases your app declares. Preview databases start without production data, and deleting the branch deletes the preview and its databases. GitHub is the only supported Git provider; from other CI systems, `npx prisma deploy module.ts --stage <name>` creates the same kind of environment once `PRISMA_SERVICE_TOKEN` and `PRISMA_WORKSPACE_ID` are set.

The workflow authenticates with GitHub's OIDC token, so there are no deploy secrets to store. Every Prisma deploy path, from the CLI and the GitHub Action to the Console's repository import and the Deploy Button, deploys a Prisma Composer module, which the next section describes. Once the repository has one and a build script, setting up deploy on push in the Console is one pull request: pick the repository, merge the pull request the Console opens, and push. As in the beta, environment variables have separate production and preview values, so a preview can run with its own credentials.

### Your app and its infrastructure, declared in TypeScript

The Prisma CLI deploys through [Prisma Composer](https://www.prisma.io/docs/composer), which describes a whole app in TypeScript: Compute services, Prisma Postgres databases, [Object Store](https://www.prisma.io/docs/storage) buckets, scheduled jobs, and secrets. A service declares what it depends on, the root module provisions it and wires it in, the server reads it at runtime, and the `composer` section of `prisma.config.ts` configures the deploy:

```ts tab="module.ts"
import { module } from "@prisma/composer";
import { rawPostgres } from "@prisma/composer-prisma-cloud";
import apiService from "./src/api/service.ts";

export default module("my-app", ({ provision }) => {
  const db = provision(rawPostgres({ name: "database" }));
  provision(apiService, { deps: { db } });
});
```

```ts tab="src/api/service.ts"
import node from "@prisma/composer/node";
import { compute, rawPostgres } from "@prisma/composer-prisma-cloud";

export default compute({
  name: "api",
  deps: { db: rawPostgres() },
  build: node({ module: import.meta.url, entry: "../../dist/api/server.mjs" }),
});
```

```ts tab="src/api/server.ts"
import { SQL } from "bun";
import service from "./service.ts";

const { db } = service.load();
const sql = new SQL({ url: db.url, idleTimeout: 10, prepare: false });

Bun.serve({
  port: service.port(),
  hostname: "0.0.0.0",
  fetch: async () => Response.json(await sql`select now()`),
});
```

```ts tab="prisma.config.ts"
import { defineConfig as composer } from "@prisma/composer/config";
import { nodeBuild } from "@prisma/composer/node/control";
import { prismaCloud, prismaState } from "@prisma/composer-prisma-cloud/control";
import { definePrismaConfig } from "prisma/config";

export default definePrismaConfig({
  composer: composer({
    extensions: [prismaCloud({ region: "us-east-1" }), nodeBuild()],
    state: prismaState(),
  }),
});
```

A build script such as `bun build src/api/server.ts --target=bun --outfile dist/api/server.mjs` produces the file that `entry` points at, and Compute runs that file on Bun. This example uses Bun's built-in server and SQL client, so building it needs Bun installed. An Express or other Node.js server is declared the same way and runs through Bun's Node.js compatibility. After a build, `npx prisma dev module.ts` runs the app on your laptop against a local Postgres, and `npx prisma deploy module.ts` provisions the real service and database and connects them. Running `deploy` again applies only what changed.

The server reads its database URL from `service.load()`, which Composer fills in for each environment from what the module provisioned. You never copy a connection string into a preview's or production's settings, because each deploy writes that environment's own URL for `service.load()` to read, and a missing dependency is a type error. When an idle instance is snapshotted, its database connections are closed. A pool that still held them would hand a dead connection to the first query after a resume, so the example sets a short `idleTimeout`: the pool drops idle connections on its own and opens fresh ones when traffic returns. `prepare: false` turns off named prepared statements, which collide on the single-session local database that `prisma dev` runs.

A `rawPostgres()` database hands the server a connection URL for the client you already use, and its migrations are yours to run, so a preview database for an app on Drizzle or another client starts empty until the app migrates it. A `postgres(contract)` database, from `@prisma/composer-prisma-cloud/orm`, takes the data contract that Prisma ORM 8 compiles from your schema, adds a client typed by it, and the deploy applies your Prisma migrations before the service starts, so each preview database begins with your schema. Prisma ORM's settings then go in an `orm` section of the same `prisma.config.ts`. Services that call each other can share [typed contracts](https://www.prisma.io/docs/composer/core-concepts), so a breaking change to one service's API fails the other's type check (`npx tsc --noEmit`), which you can run in CI before the deploy step.

Compute has no built-in cron, so scheduled jobs come from Composer's `cron` building block. It adds a scheduler service to the app that never scales to zero and calls your code on the schedule you set, which means a schedule costs one always-on instance.

To port an existing app, add a `service.ts` per server, one `module.ts`, and the `composer` section of `prisma.config.ts`, and change the server to read its port and dependencies from `service.port()` and `service.load()`. The [porting guide](https://www.prisma.io/docs/composer/porting-an-app) includes a prompt your coding agent can follow.

### Import a GitHub repository, or share a Deploy Button

Any workspace can now import a GitHub repository from the Console. The [framework guides](https://www.prisma.io/docs/guides) cover deploying Next.js, Nuxt, Astro, Hono, NestJS, TanStack Start, and Elysia apps.

A [Deploy Button](https://www.prisma.io/docs/compute/deploy-button) in a README gives whoever clicks it a running copy of your app, with its own database, in their own workspace. The [Prisma apps directory](https://www.prisma.io/apps) lists open-source starters that deploy the same way.

### Build pages, boot errors, and rollbacks

Every build has a page in the Console naming the deployment and database it touched, and a build that has not reported back after 30 minutes is flagged. If your app is unreachable after a deploy, the boot log says why in the two common cases: the server bound to `localhost`, or it listens on the wrong port. If a deploy breaks production, you can now roll it back to an earlier version from the Console, as well as with `npx prisma service version rollback api --project my-app`, which reuses that version's build. Rolling back asks you to confirm by typing the version id, so an agent without a terminal passes it with `--to <version-id> --confirm <version-id>`.

### A REST API for the deploy loop

The Management API was renamed the [REST API](https://www.prisma.io/docs/rest-api), and its [OpenAPI spec](https://api.prisma.io/v1/swagger-editor) now covers Compute services, deployments, builds, and paginated logs, along with buckets and service tokens. CI can swap a GitHub Actions OIDC token for a 30-minute workspace token, so it stores no long-lived secret, and a deploy tool of your own can report its builds so they appear in the Console. Every platform command in the CLI takes `--json`, so an agent reads the same runtime logs you do and can act on them. Compute usage is on the Console's Usage page; the API does not report it yet.

### Storage and regions

Every project can create S3-compatible Object Store buckets next to its databases and apps. Bucket pricing is not published yet, and the billing and SLA terms above cover Compute, not buckets. Compute runs in six regions: `us-east-1`, `us-west-1`, `eu-west-3`, `eu-central-1`, `ap-northeast-1`, and `ap-southeast-1`. A new project's region comes from your choice in the Console, or on a first CLI deploy from `prismaCloud({ region })` in `prisma.config.ts` or the `PRISMA_REGION` variable, and a service takes that region unless you choose another.

## How the Prisma stack compares with Vercel, Netlify, Cloudflare, and AWS

Vercel and Netlify serve frontends from a global network, Cloudflare runs code in hundreds of cities, and AWS has a service for almost any workload. Prisma's case is narrower and rests on integration. Prisma ORM, Prisma Postgres, and Prisma Compute are built to work together, so the app and its database run in the same region on one plan, and each branch can get its own instance of both. On Cloudflare, Postgres comes from another provider, on Vercel with a Marketplace database the host and the database come from different companies, and on AWS they are separate services you wire together. Netlify now sells Postgres as part of its platform (Netlify Database, built on Neon), and there the differences are in previews and in the runtime.

| Platform | Where the app runs | Where Postgres comes from | A database per preview | Request time limit |
| --- | --- | --- | --- | --- |
| Prisma Compute | A Bun process in a Firecracker microVM, in one region | Prisma Postgres, on the same plan | One per declared database, without production data | 60 seconds to the first byte; a started stream keeps going |
| Vercel | Functions on Fluid compute | A Marketplace provider, such as Neon, Supabase, Prisma Postgres, or AWS Aurora | Depends on the provider | 300 seconds by default, up to 800 on Pro, 30 minutes in beta |
| Netlify | Functions on Node.js | Netlify Database, on credit-based plans | A branch per deploy preview, copied from production | 60 seconds for a synchronous function; 15 minutes for a background function |
| Cloudflare | Workers in V8 isolates across Cloudflare's network | D1 (SQLite), or Postgres from another provider through Hyperdrive | Yours to set up | No wall-clock limit; on Workers Paid, 30 seconds of CPU time by default and up to 5 minutes |
| AWS | Lambda, or containers on ECS | RDS or Aurora, with RDS Proxy to pool connections | Yours to set up | 15 minutes per invocation on standard Lambda |

Vendor details come from each vendor's own documentation, including Vercel's [pricing](https://vercel.com/docs/pricing), [Fluid compute pricing](https://vercel.com/docs/functions/usage-and-pricing), [function duration](https://vercel.com/docs/functions/configuring-functions/duration), [Postgres](https://vercel.com/docs/postgres), and [Marketplace storage](https://vercel.com/docs/marketplace-storage) pages; Netlify's [credit-based plans](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/), [function limits](https://docs.netlify.com/build/functions/configuration/), [background functions](https://docs.netlify.com/build/functions/background-functions/), [Netlify Database docs](https://docs.netlify.com/build/data-and-storage/netlify-database/), [Netlify Database page](https://www.netlify.com/platform/database/), and [Netlify Database GA changelog](https://www.netlify.com/changelog/2026-04-28-netlify-database/); Cloudflare's [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [placement](https://developers.cloudflare.com/workers/configuration/placement/), [Hyperdrive](https://developers.cloudflare.com/hyperdrive/), and [database billing changelog](https://developers.cloudflare.com/changelog/post/2026-06-18-planetscale-databases-cloudflare-billing/) pages; and AWS's [Lambda pricing](https://aws.amazon.com/lambda/pricing/), [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html), [Lambda with RDS](https://docs.aws.amazon.com/lambda/latest/dg/services-rds.html), and [Aurora auto-pause](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2-auto-pause.html) pages.

Railway, Render, and Fly.io are closer to Compute, because they run long-lived servers. They also run WebSocket servers and persistent disks, which Compute does not, and Railway and Render have built-in cron jobs. The [Compute FAQ](https://www.prisma.io/docs/compute/faq) compares them with Compute in a table.

### Vercel and Netlify: functions next to a frontend

Vercel and Netlify started as frontend platforms, and their backends are functions deployed alongside the frontend. Vercel moved Vercel Postgres databases to Neon in December 2024, so a Vercel app gets Postgres from a Marketplace provider, and a preview database comes from that provider's integration, if it offers one. Marketplace databases can be billed on the Vercel invoice, but each is another company's product, with its own plan and limits. Prisma Postgres is one of those providers, so a frontend that needs a global CDN can stay on Vercel and use it.

Netlify made Netlify Database generally available in April 2026 on its credit-based plans, and each deploy preview gets a database branch with a copy of production data, which suits previews that must test against real data. A Compute preview database starts without production data, which keeps production data out of previews and leaves seeding test data to you.

Request limits and process lifetimes differ as well. A synchronous Netlify Function has 60 seconds to finish, and a Vercel Function runs for up to 300 seconds by default and 800 on Pro, with a 30-minute maximum in beta. A Compute request has 60 seconds to start responding, and a streamed response can keep going after that, so long work on Compute moves into a stream or into background work under `waitUntil`, which keeps the instance awake on a best-effort basis: work in progress does not survive a restart or a new deployment, and failures are not retried. Netlify's background functions run for up to 15 minutes and retry on failure. Like Fluid compute, Compute keeps a process alive between requests. When a Compute instance goes idle, it is snapshotted, and the next request resumes it in milliseconds with its memory intact.

Vercel and Netlify also bill for activity around the app. Vercel Pro includes one seat that can deploy, charges $20 a month for each additional one, and bills build time per CPU-minute. Netlify Pro has unlimited seats, but every production deploy costs 15 credits, so an agent that merges ten changes a day spends 4,500 credits a month on deploys alone, more than the 3,000 credits the $20 Pro plan includes, before any request, bandwidth, or compute credits. Prisma does not bill for seats or deploys, and it does not run your builds: they run in your GitHub Actions, free on public repositories and counted against your plan's minutes on private ones.

Comparing the hosting meters alone, against Vercel Functions in Vercel's cheapest regions, Compute costs less for memory ($0.006 against $0.0106 per GB-hour) and for CPU ($0.064 per vCPU-hour against $0.128 per CPU-hour). Per request, Vercel is cheaper: $0.60 per million function invocations against Compute's $1, though each Vercel invocation also counts as a CDN request, which Vercel bills by region or covers under its Flat Rate CDN tier. Compute has no CDN, so its $1 per million also applies to every static file the app serves, which is why an asset-heavy frontend costs less on Vercel. The larger difference is that on Prisma the database is on the same plan and bill. Vercel Pro's $20 fee also includes $20 of usage credit, while Prisma's paid plans include requests but no memory or CPU.

### Cloudflare: global code, regional data

Cloudflare Workers run in V8 isolates across Cloudflare's network, so they start quickly and run close to whoever sent the request. A database lives in one region, though, so a Worker running near a user in Sydney that reads from Postgres in Virginia makes that round trip for every query Hyperdrive cannot answer from its cache. Cloudflare's Smart Placement addresses this by running the Worker in a location closer to its backend.

Compute puts the app next to its database by default, the placement Smart Placement aims for. The app runs in one region, next to its Prisma Postgres database, so a user far from that region pays the distance once per request while the app's queries stay local. Cloudflare does not run Postgres itself, though it can provision another provider's Postgres and bill it on your Cloudflare invoice. D1 is SQLite, Hyperdrive connects Workers to Postgres that another provider runs, and a database per preview depends on what that provider offers. Each isolate gets 128 MB of memory and a subset of the Node.js APIs. A Compute instance runs your server as a Bun process, whose Node.js compatibility is also partial.

### AWS: every part exists, and you assemble them

On AWS, a TypeScript app with Postgres means Lambda or ECS for the code, API Gateway, a load balancer, or a Lambda function URL in front of it, RDS or Aurora for the data, RDS Proxy to pool connections, IAM roles for each piece, and usually a VPC around all of it. Each is a separate service with its own API and its own line on the bill. Frameworks such as SST and Amplify generate much of this wiring, but the services and their IAM permissions are still there for an agent to work through. AWS has no built-in database per Git branch: you script one yourself, for example with Aurora clones, or use a framework that provisions one per stage.

AWS recommends RDS Proxy for Lambda in production, but an Aurora cluster with an RDS Proxy attached cannot auto-pause, so the recommended setup gives up scale to zero for the database. Prisma Postgres bills per operation and per GB stored, so an idle database costs only its storage.

Lambda in its default mode runs one request at a time in each execution environment and bills that environment's allocated memory for the whole invocation, including time spent waiting on a model API, at $0.0000166667 per GB-second, which is $0.06 per GB-hour with CPU included. Compute also bills memory for as long as an instance runs, waiting included, but at $0.006 per GB-hour, and bills CPU separately, only while code runs. For the [agent workload](https://www.prisma.io/docs/compute/pricing#agent-workflow) in the pricing docs, 10,000 tasks that each hold 1 GB for 30 seconds and use 3 seconds of CPU while waiting on a model API, both platforms bill about 83 GB-hours. Leaving bandwidth out, the usage meters come to about $5.00 on Lambda (about $4.00 on Arm) and about $1.04 on Compute ($0.50 of memory, $0.53 of CPU, and $0.01 of requests). Free tiers change the result at that size: the workload fits inside Lambda's monthly free allowance, while its 8.3 vCPU-hours exceed the Compute Free plan's 4, so on Compute it needs at least the $10 Starter plan, which also covers the database. At 100 times the volume, after free allowances and Starter's fee, it comes to about $493 on Lambda (about $395 on Arm) and about $113 on Compute, and the Lambda figures leave out the database, which on Prisma is part of the same plan. These are estimates from list prices, not benchmarks, and they give every task its own gigabyte, which is how Lambda runs them; a Compute instance can serve concurrent requests from the same memory.

## When another platform is the better choice

Compute is not the right host for every app yet. Choose something else if you need:

- **WebSocket servers.** Streaming responses and server-sent events work, but Compute does not accept the WebSocket upgrade, so a server cannot hold a two-way socket open.
- **More than one region, an edge runtime, or a built-in CDN for static files.** Each service runs in one region. An asset-heavy frontend can stay on Vercel or Netlify and use Prisma Postgres.
- **More than 60 seconds before the first byte.** A response that has started streaming is not cut off, but a request that has sent nothing after 60 seconds gets a `504`.
- **A backend in another language, a Docker image, or Node.js behavior that Bun does not implement.** Compute runs TypeScript services on Bun.
- **Background jobs that must finish or retry.** Work under `waitUntil` is best-effort: a restart or a new deployment ends it, and failures are not retried.
- **A persistent filesystem.** Files you need to keep go to the database, or to Object Store, whose pricing is not published yet.
- **Point-in-time recovery for the database.** Paid Prisma Postgres plans take daily backups, but restoring to an arbitrary moment is not available yet.

The [Compute FAQ](https://www.prisma.io/docs/compute/faq) covers each of these in more detail, along with the platforms that handle them.

[Deploy your first app](https://www.prisma.io/docs/prisma-compute/deploy) and the [Composer getting-started guide](https://www.prisma.io/docs/composer/getting-started) walk through the project setup, from `package.json` to `module.ts` and `prisma.config.ts`. A new project also needs a region, which `prismaCloud({ region })` in the config above sets; the `PRISMA_REGION` variable works too. For the example above, install the Composer packages, plus `prisma` as a dev dependency because `prisma.config.ts` imports `prisma/config`, mark the package as an ES module, add the build script, then sign in once, build, and deploy:

```bash
npm install @prisma/composer @prisma/composer-prisma-cloud
npm install -D prisma typescript @types/bun
npm pkg set type=module
npm pkg set scripts.build="bun build src/api/server.ts --target=bun --outfile dist/api/server.mjs"
npx prisma auth login
npm run build
npx prisma deploy module.ts
```

`typescript` and `@types/bun` let `npx tsc --noEmit` check the wiring, with the `tsconfig.json` from the Composer getting-started guide.

If a coding agent does your deploying, run `npx prisma init` once after installing `@prisma/composer`. It syncs the agent skill that ships with Composer and adds a `postinstall` script that re-syncs it when you install dependencies.
