TypeScript 7 is [out](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/). The compiler and language service have been rewritten in Go, and Microsoft measures the native compiler at roughly 10x faster than the old JavaScript one. We moved a large TypeScript monorepo onto it the day it shipped. Whole-repo type checking dropped from about 74 seconds to about 24 seconds, and we deleted the memory flags CI needed to finish the check.

Here are the numbers, exactly what we changed, what broke, and how to decide whether to migrate now.

## The numbers

One monorepo, dozens of packages and apps, same machine, same command, median of several runs on GitHub Actions.

| Metric                | Before (TS 5.x)     | After (TS 7)  | Change        |
| --------------------- | ------------------- | ------------- | ------------- |
| Whole-repo type check | ~74s                | ~24s          | ~3x faster    |
| Node heap flag        | up to 8 GB          | none          | removed       |
| Command               | `pnpm typecheck`    | same          | same          |
| CI runner             | GitHub Actions      | same          | same          |

Two honest caveats before you read on. Microsoft's own [benchmarks](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) land between roughly 8x and 12x on projects like VS Code and Playwright. We got 3x, not 10x, because only part of our CI time was ever spent in `tsc`; the rest is bundling, tests, and code generation, none of which the new compiler touches. And your own number will differ based on how type-heavy your code is. The multiplier is real, but it is not universal.

## What TypeScript 7 actually is

It is the same TypeScript, running on a faster engine. Same syntax, same type rules, same error messages. What changed is the implementation: the compiler used to run as JavaScript on a single thread, and now it runs as native, parallelized Go. That is where the speed comes from, and it is why the migration is about tooling and config rather than your application code.

## What we had to change

Almost none of it was application code. Here is the checklist we followed, worst surprises last.

1. Run your existing type check on the classic compiler first, so a later failure means a real problem, not a migration artifact.
2. Move to a single compiler version across the repo.
3. Update `tsconfig` path resolution (remove `baseUrl`).
4. Replace any code that imports `typescript` as a library.
5. Fix the handful of type-level differences.
6. Lock the version and compare timings.

The two that produce real diffs are worth showing.

### Remove `baseUrl` from tsconfig

TypeScript 7 resolves `paths` relative to the config file, so `baseUrl` goes away and each alias becomes an explicit relative path. Same resolution, less magic.

```diff
{
  "compilerOptions": {
-   "baseUrl": ".",
    "paths": {
-     "@/*": ["src/*"]
+     "@/*": ["./src/*"]
    }
  }
}
```

If you use `vite-tsconfig-paths`, upgrade it to v5 at the same time. Older versions relied on `baseUrl` to anchor aliases and will break the production build without it.

### Stop importing the compiler as a library

This is the caveat that matters most, and it is the one people miss. TypeScript 7 does **not** ship the programmatic compiler API yet. Microsoft expects it to arrive in 7.1, and recommends keeping classic TypeScript installed side by side for tools that still need it. So any script that did `import ts from "typescript"` to walk the AST needs a plan.

We had one script that read component props out of `.tsx` files with the compiler API:

```ts
// Before: uses the TypeScript compiler API (unavailable in TS 7)
import ts from "typescript";

const source = ts.createSourceFile(file, src, ts.ScriptTarget.Latest, true);
for (const node of source.statements) {
  if (ts.isInterfaceDeclaration(node)) {
    // ...read members
  }
}
```

We moved it to a standalone parser that has no dependency on the compiler:

```ts
// After: uses oxc-parser, which emits a plain ESTree AST
import { parseSync } from "oxc-parser";

const { program } = parseSync(file, src);
for (const node of program.body) {
  if (node.type === "TSInterfaceDeclaration") {
    // ...read members
  }
}
```

The regenerated output was byte-for-byte identical. If you cannot drop the compiler API, the side-by-side option is a pin in the one package that needs it:

```jsonc
// repo default: the native compiler
"typescript": "7.0.2"

// only in the package that still needs the compiler API:
"typescript": "5.8.2"
```

## Sharp edges

A short punch list of type-level differences the native compiler surfaced. All were type-only; nothing changed at runtime.

- **Typed-array generics are stricter.** WebCrypto and `node:crypto` call sites now want an explicit `ArrayBuffer` type argument.

  ```diff
  - crypto.subtle.importKey("raw", rawKey, { name: "AES-GCM" }, true, ["encrypt"]);
  + crypto.subtle.importKey("raw", rawKey as Uint8Array<ArrayBuffer>, { name: "AES-GCM" }, true, ["encrypt"]);
  ```

- **`Buffer` no longer satisfies a `Uint8Array` type.** Test fixtures that leaned on `Buffer` had to be built as real typed arrays.

  ```diff
  - const bytes = Buffer.from([1, 2, 3]);
  + const bytes = new Uint8Array([1, 2, 3]);
  ```

- **Deep recursive mapped types can hit a recursion limit** the old compiler did not enforce. We rewrote one to an equivalent non-recursive form.

- **The memory flags are gone.** The native compiler holds far less in memory, so the heap tuning we had accumulated to keep CI green is no longer needed.

  ```diff
  - "typecheck": "NODE_OPTIONS=--max-old-space-size=8192 tsc --noEmit",
  + "typecheck": "tsc --noEmit",
  ```

## What improved, and what did not

The type check got faster and lighter. Editors stay responsive on large projects because the language service is part of the same native port. That is the whole win, and it is worth having.

It is just as important to say what TypeScript 7 did **not** change:

- It did not make bundling or the production build faster. Those go through Vite and esbuild, and `tsc` emits nothing in our setup.
- It did not change anything at runtime. Every fix above was type-level.
- It did not remove type-level bottlenecks. A pathological type is still slow, just slow in Go.
- It did not make compiler-API tooling compatible. That is still on you, until the 7.1 API lands.
- It did not make generated types smaller.

## Should you migrate now?

**Try it now if:**

- Type checking is a meaningful slice of your CI time.
- Your editor slows down on a large project.
- Your repo does not depend on the compiler API.
- You can run it in CI before making it the default.

**Wait a bit if:**

- Your tooling imports `typescript` as a library.
- You rely on custom AST transforms or compiler-API scripts.
- Your build time is dominated by bundling, tests, or code generation, not type checking.

The move is low-risk to trial: TypeScript 7 installs as the normal package, so you can point one CI job at it and keep the old compiler a command away.

```bash
npm install -D typescript@latest
```

## Why this matters to us

We care about compiler speed because our users live in exactly these codebases. [Prisma ORM](https://www.prisma.io/docs/orm) generates types that land directly in your editor and CI feedback loop, so we work hard to [keep type checking fast](/why-prisma-orm-checks-types-faster-than-drizzle) as schemas and monorepos grow. A faster compiler makes those generated types cheaper to live with, which is why we moved the moment the native compiler was ready. If your TypeScript app also runs on [Prisma Postgres](https://www.prisma.io/docs/postgres) or [Prisma Compute](https://www.prisma.io/docs/compute) (in public beta), the same feedback loop gets quicker across the board.

TypeScript 7 is out, the speedup is real, and for most large projects the migration is mostly config. Point your existing type check at it and compare the timing before you commit.
