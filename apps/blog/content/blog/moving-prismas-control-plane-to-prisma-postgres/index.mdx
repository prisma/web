Seven minutes after we merged the pull request that moved Prisma's control plane to [Prisma Postgres](https://www.prisma.io/docs/postgres), the last statement ran on the old database. Fifty-two minutes after the cutover, a colleague merged a migration that quietly broke our rollback. Nobody outside the team noticed either event. This is the story of how 83 tables and 74 GB moved from Amazon RDS with logical replication, with no maintenance window and a week in which we could still have gone back.

The replication itself turned out to be the easy part. What made the move safe were two decisions about its edges: cutting over in a single merge so every service switched together, and keeping the old database as a live replica so that changing our minds would cost a config revert rather than a restore. The thing that did bite us is something logical replication does not carry: schema changes. That is the lesson we most want you to take away.

## Why we could not pause writes

The control plane is everything in Prisma that is not the database engine: the Console, authentication, the Management API, the marketplace integrations, the MCP server, and the GitHub webhook pipeline, all running on Cloudflare Workers. These six services share one Postgres database that had lived on RDS since before Prisma Postgres existed.

We sell a managed Postgres and ask customers to run production on it, so our own production belonged there too. The catch was that the Console cannot take a maintenance window. People deploy from it around the clock, and the API keys it issues sit in the request path of every customer application. That ruled out the [dump and restore path](https://www.prisma.io/docs/postgres/import-from-existing-database) in our docs, which needs writes paused.

Postgres logical replication is built for the other case. The source publishes row changes, the target subscribes, copies each table once, and then follows along in near real time for as long as you need. Our plan was to let Prisma Postgres follow RDS for a few days, switch every service over in one go, and then turn the stream around so RDS followed Prisma Postgres until we were sure.

## Publish 82 of the 83 tables

We had rehearsed the whole recipe on our preview environment, and production used the same commands with one change. The rehearsal had published every table, whereas production used an explicit list that left out `_prisma_migrations`, the table where Prisma records which migrations have run.

That one line mattered because CI was already applying every migration to the new database on each deploy, so the target had the full schema and a populated migration history before replication started. Copying that table would have failed on the first duplicate key, and a failed table copy retries forever with its sync error count climbing until someone notices. Before creating anything we also checked `wal_level` on the source, primary keys on every table, the same 204 migrations on both sides, and that every other table on the target was empty.

## 74 GB, most of it webhook logs

The migration spec had been written against a smaller database than the one we found. Two tables held most of the 74 GB, and the largest was a log of every GitHub webhook delivery we had ever received, stored as raw JSON with no retention policy. Nobody had decided to keep nine million payloads forever; on RDS the disk had simply grown quietly, and the bill with it.

The copy, which Postgres runs two tables at a time by default, still finished the same day with the two wide tables last. The new database then reported 79 GB rather than 74, which puzzled us until we compared TOAST compression settings: `pglz` on the new side and `lz4` on the old, so the same rows simply took more space. We shipped a 30-day retention job for the webhook log the following week. Measure the thing before you move it, and look at what the bytes are made of.

## Three things that delayed the first row

Each of these cost us real time before a single row had moved.

**Our SQL client was in manual-commit mode.** The production connection profile in DBeaver defaults to manual commit, so the publication we had just created existed only inside an uncommitted transaction, and the target could not see it. If you create replication objects from a GUI client, check the commit mode before you start wondering whether the grants are wrong.

**The new instance went to sleep.** Prisma Postgres scales an idle instance to zero with a memory snapshot and [resumes it in single-digit milliseconds](/cloudflare-unikernels-and-bare-metal-life-of-a-prisma-postgres-query) on the next connection, so an application sees only a few milliseconds on its first connection. A logical replication apply worker is different, because it runs inside the instance without any client connecting to it. Before application traffic pointed at the target, nothing woke it and the subscription stalled. We kept the target awake through the copy with a tiny service on [Prisma Compute](https://www.prisma.io/docs/compute) that held one connection open and ran `SELECT 1` every few seconds, and deleted it the day before cutover.

**The network path needed proving.** The target had to reach RDS through a security group that did not allow its egress address. We added a separate group so it could be removed cleanly afterwards, then verified the path from the target side with a `dblink` probe before creating the subscription, because a subscription that cannot connect fails late and quietly.

Two details repay attention. And the rollback slot is created minutes before the cutover rather than days before, because a slot pins WAL from the moment it exists until a consumer reads it, at roughly a gigabyte an hour in our case. ## Schema changes do not replicate

The property that shaped both the cutover and the rollback is this: row changes flow from publisher to subscriber, and `ALTER TABLE` does not. If a migration adds a column on the source and the subscriber has not applied the same migration, the apply worker fails on the first transaction that needs the new column and retries it in a loop, and nothing behind it moves until someone fixes the schema by hand. Sequence values are not replicated either, so check whether any of your keys depend on one.

We knew this going in. Before the copy started, the CI job that applies migrations to the new database stopped being allowed to fail, and every production deploy was made to depend on it, so a migration that failed on Prisma Postgres would hold the whole deploy the way a failure on RDS always had. That guard held, but what we had not thought through was the rollback week.

## One merge moves everything

Before the rollback week, the cutover itself. Each of our services talks to the database on two paths. The classic Prisma Client goes through [Accelerate](https://www.prisma.io/docs/accelerate), and the [Prisma 8](https://www.prisma.io/docs/orm) client connects [directly over TCP](https://www.prisma.io/docs/postgres/database/connecting-to-your-database) through a [Cloudflare Hyperdrive](https://developers.cloudflare.com/hyperdrive/) binding, because every one of these services is a Worker. If one path switched to the new database and the other did not, a service could write a row on one side and fail to read it back on the other, so both paths had to change in the same deployment of each service.

The Hyperdrive binding lives in a config file in the repository, and the connection strings live in our secrets manager. The cutover branch changed one line in three config files, and the new secrets were added under new names minutes before the merge. The client code already read the new names first and fell back to the old ones, but a Worker only picks up new secrets when it is deployed, and any push to `main` deploys every service. So the merge was the switch, and deleting the new values before a redeploy was the rollback. The old Accelerate values were never touched. The one old value we did edit was the plain direct connection string that the migration job reads, because that job reads a fixed name with no fallback. That edit is what broke the rollback later.

That gave us a single merge to `main` as the cutover, with each service's deploy publishing the new binding and the new secrets together. Between services there was a skew of a few minutes while six deploy jobs ran, and during that window some services wrote to RDS while others wrote to Prisma Postgres. The forward subscription stayed up the whole time, so writes that still landed on RDS kept flowing across. The failure we could detect in that window was a key collision, where a row created on the new side meets a row with the same key arriving from the old side. That shows up as an apply error, so the one number we watched during the rollout was the apply error counter, and it stayed at zero. Updates to the same row from both sides would have overwritten each other silently, which is why the window had to be minutes and not hours.

## Cutover day

Three minutes before the merge we created the rollback slot. The merge went in, every migrate job and every service deploy went green, and seven minutes after the merge the last statement from any service ran on RDS. A sixty-second sample of the RDS write counters twenty minutes later showed zero inserts, updates, and deletes, and our tracing showed no new class of error on any service.

We then dropped the forward subscription and publication and created the reverse subscription on RDS. Within half an hour the reverse slot was active with a few kilobytes of lag, zero apply errors, and the newest project row identical on both databases. A straggler check over every table with an `updatedAt` column found no table where RDS had more recent rows than Prisma Postgres.

One detail made the reverse direction work. The rollback slot had been retaining every write on the new side since before the merge, including the rows that forward replication had applied there, and the first thing a naive reverse stream would do is try to insert rows that RDS already had. Both databases run Postgres 17, so we could create the reverse subscription with `origin = none`, available since Postgres 16, which skips rows that arrived through replication and sends back only what the application itself wrote.

## Fifty-two minutes later, a migration

Fifty-two minutes after the cutover, a colleague merged a pull request that included a database migration. In principle that was fine: the migration applied cleanly to Prisma Postgres, which was now production, but nothing applied it to RDS.

The reason was the one old value we had edited. We had pointed the migration job's direct connection string at the new database as part of the switch, so both migrate jobs now ran against the same database and nothing pointed at RDS. The old database never heard about the new column. The reverse apply worker on RDS errored on the first change to the affected table and retried it in a loop, and nothing behind it moved. It did not fail loudly; the apply error counter climbed, and we noticed only because we were still watching it.

We applied the same SQL by hand on RDS, along with a copy of the migration history row, and the reverse stream caught up. Then we changed CI so that for the rest of the rollback week every migration applied to both databases, with the old one treated as production for schema purposes even though no service was reading it.

The lesson is that during a rollback window, the database you have left is still production. Every schema change that reaches the new side has to reach the old side too, or the rollback you are paying to keep alive silently stops being one. We had guarded the forward direction and forgotten that the reverse direction has the same property.

## Shutting down RDS

A week after the cutover we ran a final parity check on the key tables, comparing row counts and the newest `updatedAt` on each, and they matched. We dropped the reverse subscription on RDS, which also dropped the slot on the new side, and dropped the reverse publication. One last gotcha: `DROP SUBSCRIPTION` cannot run inside a transaction block while a slot is attached, so the same client that had tripped us on manual commit at the start had to be switched to auto-commit at the end.

We took a final snapshot and stopped both RDS instances rather than deleting them, knowing that RDS restarts a stopped instance after seven days. Then we spent a day on the cleanup a migration leaves behind: the extra security group, the replication role, the old Hyperdrive resource, the old Accelerate keys, and ten environment variable names that had existed only to make the switch possible, collapsed back down to four.

## A checklist for your own migration

**Make the cutover one merge.** Every piece of connection config goes into the same deployment, shaped so that adding new values is the switch and removing them is the rollback.

**Make the rollback a running replica.** Create the slot on the new database minutes before cutover, and once the old side is quiet, subscribe it to the new side with `copy_data = false` and `origin = none`. After you drop that subscription there is no rollback that keeps data.

**Verify with a query that returns only mismatches.** Compare every table's count on both sides through `dblink`, then hash the slow-moving tables, and expect hashes to differ on tables written on every login.

**Treat schema changes as the dangerous part.** Logical replication carries rows, not DDL or sequence values. Make the new database's migration job a hard dependency of every deploy before the copy starts, and apply every migration to both databases for as long as the rollback is open.

**Measure before you move.** Know which tables hold the bytes and why. A retention policy written before the copy is a copy you do not have to wait for.

## What the work actually was

There was no status page entry, no error spike, and no support ticket. The control plane that issues every Prisma Postgres connection now runs on Prisma Postgres. The replication itself is plain Postgres, and the two Prisma-specific parts were leaving out the migrations table and keeping a scale-to-zero instance awake during the copy. Postgres did what the documentation says it does. The work was in packaging the switch and in keeping the way back open, and the second of those needs the same care as the first.
