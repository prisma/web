# Regional performance investigation — 24 October 2026

The current Compute deployment is not yet at Vercel parity for all visitors. Warm landing HTML can beat Vercel, but articles, documentation, public media, cookie-bearing visits and campaign URLs frequently contact the US origin. Faster HTML alone also changes the mobile resource schedule.

## Reproduced mobile regression

Three interleaved cached/bypass pairs against the identical deployment in Bangkok. HTML bytes match (a dummy cookie bypasses the old HTML rule); both variants use the same static assets. Lighthouse 13.5.0 / Chrome 155, applied 150 ms latency, 1,600/750 Kbps down/up, CPU ×4. Browser profiles/storage reset each audit. No local builds ran alongside these audits.

| Median | Cached HTML | Cookie bypass |
| --- | ---: | ---: |
| FCP | 3.454 s | 2.719 s |
| LCP | 4.887 s | 3.651 s |
| Blocking time | 596 ms | 609 ms |

Both load about 830 KB of fonts and select the same featured hero SVG as LCP. Its actual transfer starts earlier or similarly with cached HTML, but completes later. All four font faces are preloaded; Inter italics alone costs about 388 KB and is preloaded even though it is not critical to the archive’s first paint. Later traces confirm it is still requested through CSS after removing its preload; this is a scheduling change, not a 388 KB transfer elimination. Many full-size author avatars also compete with the lead image. This reproduces the resource-scheduling problem; it does not prove how much each resource contributes. The cookie applies to asset requests too, so this is a practical paired bypass comparison, not a browser-scheduler microbenchmark.

## Changes under verification

- Keep the critical Sora preload; let CSS request the Inter faces actually needed and the code font when used. Prioritize the featured image at parser discovery; lazy-load author avatars. The generated archive now contains one font preload and an explicit high-priority hero. Fonts, visual styling, original assets and content are retained.
- Give actual public files bounded edge freshness instead of forcing an origin revalidation for every image. Generate a 2,708-file inventory with sizes/content hashes (about 442 KB) from the five public directories. Do not cache an image-shaped API merely by suffix. Preserve positive application file TTLs and explicit CDN policies.
- Allow public prerendered/explicitly public MDX HTML with cookies and distinct query keys, and expand the eligibility rule across websites. Private/dynamic pages, authorization, Set-Cookie, unsupported Vary and Next/RSC variants remain excluded. Keep the complete query key; do not merge filters with campaign URLs.
- Add 300 seconds of background revalidation after the 60-second edge lifetime. Browser HTML still revalidates; no bodies are buffered. This can leave old public content visible for up to six minutes without a deployment purge.
- Add origin no-transform to already-compressed public media so CDN transport can retain Content-Length/range semantics. This is a candidate fix until the deployed Cloudflare range checks pass.

## Additional structural findings

Composer intentionally omits article static-params generation in docs/blog to fit
the file budget. Those pages return Next’s default private SSR headers, even
though their repository MDX is public and independent of cookies or request data.
A wider Cloudflare rule alone cannot cache them. The follow-up marks just these
content routes as public in Composer builds and applies the same status/variant/
Set-Cookie/Vary checks at the gateway. It does not write every article’s HTML/RSC
to runtime disk. Other request-rendered pages remain private; Vercel is unchanged.

Live file validators such as `W/"2974ee1-3e8"` encode the byte size and a fixed
one-second timestamp. This cannot distinguish same-size edits between deployments.
The exact archive/restore layer responsible for normalization has not been
isolated. The public-file inventory now carries SHA-256 digests, and the gateway
uses content-based conditional validators, retaining raw streams, HEAD and ranges.
A regression test covers equal-size edits, weak/strong comparison and If-Range.
Unreliable Last-Modified dates are removed for these normalized file validators.
Compute should supply correct content validators natively for static artifacts.

The same-source Vercel preview is protected by Vercel SSO; it was not benchmarked
as a public page. The public production comparison still has different content
and analytics configuration, so it is not an isolated hosting-only experiment.

## Remaining parity requirements

1. **Global delivery and cold misses:** a single EWR origin cannot match local edge delivery on every miss. Evaluate [Smart Tiered Cache](https://developers.cloudflare.com/cache/how-to/tiered-cache/) for shared fills, then measure cold/warm and post-expiry behavior from the same regions. Do not infer that it is currently enabled. Rare pages, evicted entries and first-ever requests still need an origin.
2. **Navigation and request variants:** the initial rule intentionally bypasses Next RSC/prefetch. Test client navigation separately. Broadly caching RSC without a correct key is unsafe because Cloudflare does not honor arbitrary Vary by default. A Next-aware edge adapter or a validated versioned data key is needed for this path.
3. **Unique campaign identifiers:** retaining query strings is correct but fragments the cache for gclid/other unique click IDs. Audited query normalization requires a supported custom cache key/edge adapter; dropping every query string would break filter redirects and other route semantics.
4. **Deployment invalidation:** bounded six-minute staleness is not Vercel’s deployment-aware cache. Composer/Compute should expose deployment-scoped asset caches, atomic promotion/invalidation (including old hashed chunks referenced by stale HTML), safe Next HTML/RSC variation, conditional requests and byte ranges without hand-maintained Cloudflare rules.
5. **Whole-page acceptance:** compare equivalent homepage, docs, blog archive and article content on desktop and mobile, at cold/warm edge and browser states. Include returning visitors, campaign URLs, navigation, post-expiry requests and regions outside Asia. Use repeated paired samples and eventually field p75 LCP/INP/CLS per region/device; a tiny lab median cannot certify all-user parity.
6. **Observability:** expose per-hop timing and cache reason (edge, gateway, upstream, instance scheduling/startup) so a slow first response can be attributed without guessing. Add a standard geographic regression benchmark to the Compute/Composer release process.

## Stream framing diagnosis

The range problem was reproduced without Cloudflare or Compute: Bun 1.4.3
serves a `Bun.file` with Content-Length but discards a supplied length when the
body is a fetched/ReadableStream response, using chunked transfer instead. This
also explains why a HEAD and a short direct range looked correct while a full
streamed GET lacked its length. Standard/CDN no-transform headers cannot repair
a length already removed by the HTTP server.

The same stream through `node:http` on Bun preserves Content-Length. The proxy
package now exports `createHttpServer` via `@prisma/proxy/node`; the gateway uses
it without changing runtime, adding dependencies or buffering large files.
Tests on Node and Bun cover a 2 MiB multi-chunk response, HEAD, 304 without a
false zero length, raw gzip, separate cookies, streamed POST and disconnect
cancellation. A deliberately slow client against a 128 MiB stream caused only
1,966,080 bytes to be produced before cancellation, demonstrating backpressure.
The complete local stack also checks full streamed GET lengths, including the
43,470,561-byte GIF. Sampled gateway RSS is 187.7 MB, within the 1 GB allowance.

The content-validator namespace changes to `asset-v1` so CDN entries created
without a length receive one fresh complete response instead of revalidating
forever with their old metadata. Deployed Cloudflare verification is still
required before claiming the range problem is resolved.
