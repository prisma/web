## Breaks copy-paste

- `guides/deployment/docker.mdx:567` — "Change the schema …, run `npm run contract:emit`, then `npx prisma migration plan --name <change>`; the next `docker compose up --build` applies it." — After the guide's own step 2.3 (`migration plan --name init`, then plain `npx prisma db migrate`), no `db` ref exists, so that next `migration plan` refuses with `MIGRATION.PLAN_ORIGIN_UNKNOWN`. Step 2.3 needs `db migrate --advance-ref db` (as the Vercel, Turborepo and GitHub Actions guides do), or the next step needs `--from`. — evidence: in `scratch/audit-deploy-integrations/docker-test`, after the step 2.3 commands, adding a field, `contract emit`, then `npx prisma migration plan --name add-bio` printed "Migrations exist on disk, but there is no `db` ref and no --from was given …" with `MIGRATION.PLAN_ORIGIN_UNKNOWN`; `migrations/app/refs/` did not exist.
- `guides/deployment/bun-workspaces.mdx:383` — step 5 shows the `User` model to edit with `createdAt TimestamptzString @default(now())` and `updatedAt DateTime(as: string) @onCreate(now()) @onUpdate(now())`, and says `db update` then prints "Applied 1 operation(s)" (line 404). The starter `orm init` wrote in step 2.1 has `createdAt DateTime @default(now()) @onCreate(now())` and `updatedAt temporal.UpdatedAt`, so pasting the block also changes both column types. — evidence: `scratch/audit-deploy-integrations/bun-mono`, after `bun run db:init` on the real starter and pasting the step 5 block, `bunx prisma db update` printed "Applied 3 operation(s)": add column `bio`, "Alter type of "User"."createdAt" to timestamptz", "Alter type of "User"."updatedAt" to timestamptz". Starter source: `orm/.../packages/1-framework/3-tooling/cli/src/commands/init/templates/code-templates.ts:179-200`.
- `guides/deployment/turborepo.mdx:497` — the same mismatch in step 7: the `User` block to paste uses the old `TimestamptzString` / `DateTime(as: string) @onUpdate(now())` fields while step 2.5 told the reader to keep the real starter, so the planned migration also alters `createdAt` and `updatedAt`, not just "Add column "bio"" as the printed output at line 525 shows. — evidence: same starter source; the Bun run above shows the extra operations for the identical change.

## Misleading

- `guides/deployment/turborepo.mdx:165-188`, `guides/integrations/github-actions.mdx:77-101` — each page presents the block as the starter contract `orm init` wrote ("leave it as it is for now"; "`orm init` starts you with `User` and `Post` models. Add a `published` flag"). The real starter uses `DateTime @default(now()) @onCreate(now())` and `temporal.UpdatedAt`, not `TimestamptzString` and `DateTime(as: string) @onCreate(now()) @onUpdate(now())`. The shown block still emits (checked), but readers compare it with a file that differs and, on the GitHub Actions page, change two column types without being told. — evidence: `code-templates.ts:179-200`; `cat src/prisma/contract.prisma` after `npx -y prisma@latest orm init --yes --target postgres --authoring psl`.
- `guides/deployment/pnpm-workspaces.mdx:111`, `guides/deployment/turborepo.mdx:142`, `guides/deployment/bun-workspaces.mdx:95`, `guides/integrations/github-actions.mdx:64` — the "generated `db.ts`" block imports `'./contract.d'`; the file `orm init` writes imports `'./contract.d.js'`. Four pages, same line. — evidence: `code-templates.ts:356-375` (`dbFile`); the generated `src/prisma/db.ts` in `scratch/audit-deploy-integrations/docker-test`.
- `guides/deployment/cloudflare-workers.mdx:149`, `guides/deployment/bun-workspaces.mdx:139` and `:404`, `guides/integrations/ai-sdk.mdx:98`, `guides/authentication/clerk/nextjs.mdx:108` and `:120` — six output blocks show a JSON fragment (`"summary": "Applied 5 operation(s) across 1 space(s), database signed"`, `"dir": "migrations/app/…_init"`). The CLI now prints human output with or without a terminal: `✔ Applied 5 operation(s) across 1 contract space`, then the operation tree and `✔ Advanced ref "db" → …`. The Docker and pnpm pages already show the current form, so the area disagrees with itself. — evidence: `npx prisma db init` and `npx prisma migration plan --name init` run without a terminal in `scratch/audit-deploy-integrations/vercel-flow` and `bun-mono`.
- `guides/deployment/bun-workspaces.mdx:142` — "The command is safe to repeat and reports `Applied 0 operation(s)` when there is nothing left to do." — A second `db init` prints `✔ Database already matches contract across 1 contract space`, as `pnpm-workspaces.mdx:153` says. — evidence: second `bunx prisma db init` in `scratch/audit-deploy-integrations/bun-mono`; `control-api/operations/db-run.ts:563`.
- `guides/deployment/bun-workspaces.mdx:24` — "Bun 1.1 or later". `orm/supported-versions.mdx:16` says Bun 1.3 or newer (the C18 decision). — evidence: `orm/supported-versions.mdx:16`; `changes.md` C18 decision.
- `guides/deployment/bun-workspaces.mdx:413` — says a missing `DATABASE_URL` fails with `CONTRACT.MARKER_READ_FAILED` and "Postgres driver not connected". `guides/deployment/vercel.mdx:117` and `:156` say the same situation is `DRIVER.NOT_CONNECTED`. Running a query from the generated `db.ts` with no `DATABASE_URL`, under both Bun and Node.js, throws `DRIVER.NOT_CONNECTED` ("Postgres driver not connected. Call connect(binding) …"). — evidence: `bun q.ts` in `scratch/audit-deploy-integrations/bun-mono` and `node ../docker-test/q2.ts` from an empty folder, both with `DATABASE_URL` unset.
- `guides/deployment/vercel.mdx:25` — "If yours is a TypeScript contract, `contract.ts`, `contract emit` writes its files to `src/prisma/generated/`" for a project set up by `npm create prisma` or `npx prisma orm init` (line 15). Only the create-prisma template sets `output: …/generated`; the config `orm init` writes sets no `output`, so `contract emit` writes `src/prisma/contract.json` next to `contract.ts`. — evidence: `create-prisma/templates/create/_shared/prisma.config.ts.hbs:10,34`; `orm/.../commands/init/templates/code-templates.ts:306-323` (`configFile`, no `output`); `packages/1-framework/1-core/config/src/default-contract-output-path.ts:18-25`.
- `guides/deployment/cloudflare-workers.mdx:152`, `guides/integrations/ai-sdk.mdx:101` — "creates the `user` and `post` tables" / "creates the `session` and `message` tables". The tables are named after the models, `"User"`, `"Post"`, `"Session"`, `"Message"`, as the Docker page's output and the Vercel page's `relation "public.User" does not exist` show. — evidence: `db init` output "Create table "User"", "Create table "Post"" in `scratch/audit-deploy-integrations/bun-mono`.
- `guides/integrations/pgfence.mdx:11` — the reason given for having no Prisma ORM 8 version: "Prisma ORM 8 migrations are TypeScript and JSON files with no SQL output to scan." Each migration's `ops.json` holds the SQL of every operation, and `prisma migration show <dir>` and `prisma migration plan` print a "DDL preview" of the statements. pgfence may still not read these, but "no SQL output" is not true. — evidence: `migrations/app/20261120T0743_init/ops.json` (`"sql": "CREATE SCHEMA IF NOT EXISTS \"public\""`) and `npx prisma migration show 20261120T0743_init` output in `scratch/audit-deploy-integrations/docker-test`.
- `guides/postgres/vscode.mdx:43-47` and `:137` — in the unversioned tree, the page says the extension "can support both version 6 and version 7 of Prisma ORM" and that agent mode can "generate the Prisma Client". It never mentions Prisma ORM 8 or says it documents Prisma ORM 6 and 7, while `orm/contract-authoring/editor-support.mdx:9` tells Prisma ORM 8 users to install the same extension for `contract.prisma`. — evidence: `orm/contract-authoring/editor-support.mdx:9-24`; Prisma ORM 8 has no `prisma generate` (`vercel.mdx:31`).

## Unverified

- `guides/compute/deploy-existing-app.mdx:38` — says an app that keeps reading the placeholder `DATABASE_URL` (`-`) "deploys and then fails every query with `P1001` and `host: "base"`". `P1001` is a Prisma ORM 7 engine code; no source in prisma/orm rc.24 emits it. On rc.24, `postgres({ contract, url: "-" })` throws `RUNTIME.BINDING_INVALID` ("Postgres URL must be a valid URL") at import, so the app would not start. The page pins `@prisma/orm-postgres` 8.0.0-rc.20 on purpose, which I did not install. — checked: `rg P1001` over `packages/` (no hits); `DATABASE_URL="-" node ../docker-test/q2.ts`.
- `guides/authentication/clerk/nextjs.mdx:528` — "Deploy fails with `MIGRATION_PATH_NOT_FOUND`." The ORM's own skill says Composer releases older than it print that name, and current ORM code uses `MIGRATION.MARKER_MISMATCH`/`MIGRATION.PATH_UNREACHABLE`; the Composer skill shipped with `@prisma/composer` (installed by `prisma` rc.34) still names `MIGRATION_PATH_NOT_FOUND`. Which one a deploy prints today depends on the Composer version; not run (no deploy). — checked: `node_modules/@prisma/orm-postgres/skills/prisma-8/references/migrations.md:467`, `node_modules/@prisma/composer/skills/prisma-composer-core-concepts/SKILL.md:370,759`.
- `guides/deployment/cloudflare-workers.mdx:191,301` — a module-level client hangs the second request in `workerd`. Not run; `wrangler` was not used.
- `guides/deployment/pnpm-workspaces.mdx:25,97,397` — the pnpm 12.0 to 12.4.0 link defect and the 12.7.0 output. Only pnpm 12.3.4 was available, and a stray `pnpm-lock.yaml` in the home directory made package-manager detection unreliable in the scratch tree; not run.
- `guides/deployment/docker.mdx:342-347,537` — the `@emnapi/runtime` lockfile failure inside the Linux image and the 2.1 GB image size. The image was not built.
