## Breaks copy-paste

- `orm/migrations/editing-a-migration.mdx:256` — says to enable an extension "with `createExtension('pgcrypto')` from the same module" (`@prisma/orm-postgres/migration`) — the free function was removed in rc.24; an import of it fails with "does not provide an export named". The call is `this.createExtension({ extension: 'pgcrypto' })`. `orm/reference/migration-api.mdx:315` already says this, so the two pages also disagree — evidence: `docs/releases/v8.0.0-rc.24.md` ("no longer exports the free functions `createExtension` and `dataTransform`"), `pg-target/exports/migration.ts` (exports `rawSql`, `col`, … but no `createExtension`)
- `orm/reference/migration-api.mdx:341-345` ("copied as they are"), `orm/migrations/editing-a-migration.mdx:74` and `:217`, `guides/database/data-migration.mdx:181` — each tells the reader to add `import { sql } from '@prisma/orm-postgres/builder/runtime'` to the planned `migration.ts`. Whenever the planned file holds a SQL value (a default, a check, an index expression, or the CHECK of any PSL `enum`), the planner already imports `sql` from `@prisma/orm-postgres/migration`, so the file fails to load with `SyntaxError: Identifier 'sql' has already been declared`. The guide hides this because its listing at `data-migration.mdx:179` shows the planner's import as `{ Migration, MigrationCLI, col, lit }` and line 214 shows the check as a plain string; the planner writes `{ Migration, MigrationCLI, col, lit, sql }` and ``expression: sql`"status" IN (...)` ``. The builder import needs an alias such as `import { sql as sqlBuilder }` — evidence: `migration plan --name add_status` on the guide's contract, then adding the guide's import line and running `node migrations/app/20261120T0753_add_status/migration.ts` prints the SyntaxError; `migration-api.mdx:21` itself says the planner imports `sql` from the migration module
- `cli/db-schema.mdx:43` — `jq '... | .envelope.result.schema.tables[].columns[].typeText'` — on PostgreSQL the result has no `schema.tables`; tables sit under `schema.namespaces.<schema>.tables.<table>.columns.<column>`, so the command fails with `jq: error: Cannot iterate over null`. A working path is `.envelope.result.schema.namespaces[].tables[].columns[].typeText` — evidence: `npx prisma db schema --json` on the scratch database; `result.schema` keys are `nodeKind, namespaces, roles, extensions, existingSchemas, pgVersion`
- `guides/database/data-migration.mdx:467` — "If `db migrate` reports `MIGRATION.HASH_MISMATCH`" — `db migrate` reports a hand-edited `ops.json` as `MIGRATION.CONTRACT_SPACE_VIOLATION` (and `migration check` as `MIGRATION.CHECK_HASH_MISMATCH`), as `orm/migrations/applying-a-migration.mdx:169` says. A reader searching the output for the guide's code finds nothing — evidence: editing one label in `ops.json` in the scratch `guide/` project, then `npx prisma db migrate` prints `✘ [MIGRATION.CONTRACT_SPACE_VIOLATION] Contract-space integrity failure for "app"`
- `cli/migration-show.mdx:23` — `<target>` is "a directory name, a hash or hash prefix, a ref, or a path" — a ref name is refused (`✘ [MIGRATION.REF_WRONG_GRAMMAR] "db" is a ref name, not a migration`), and "a hash" means only the migration's own `migrationHash`: a contract hash prefix is refused (`Hash matched a contract but not a migration`). `orm/migrations/how-migrations-work.mdx:157` lists the forms correctly, so the two pages disagree. (The CLI's own help text also says "ref".) — evidence: `npx prisma migration show db` and `npx prisma migration show 5ab63e` (a contract hash) both exit with `MIGRATION.REF_WRONG_GRAMMAR`; `migration show c4a68c` (a `migrationHash` prefix) works

## Misleading

- `orm/migrations/applying-a-migration.mdx:27,30,33` — the sample output marks `⚠ Set NOT NULL on "user"."displayName"` and prints "This migration contains destructive operations that may cause data loss.", and line 33 says setting `NOT NULL` "deletes no rows but still counts" as destructive — since rc.17 `setNotNull` is `widening`, so the real output has no `⚠` on that line and no warning. The page contradicts `how-migrations-work.mdx:132`, `migration-api.mdx:133` and `migration-plan.mdx:70`, which call it widening — evidence: `docs/releases/v8.0.0-rc.17.md:23`, `pg-target/core/migrations/operations/columns.ts:362`, `op-factory-call.ts` (`SetNotNullCall … 'widening'`); applying the same migration printed `├─ Set NOT NULL on "user"."displayName"` with no warning
- `orm/reference/migration-api.mdx:202` ("There is no method that renames a column. Raw SQL shows a column rename") and `:380` (use `rawSql` "such as a column rename … replace the `dropColumn` and `addColumn` it writes with one `rawSql`") — `this.renameColumn({ schema?, table, column, to })` exists, returns a list to spread, and is what `migration plan --rename User.name:User.fullName` writes. The page itself mentions "later `renameTable` and `renameColumn` calls" at line 124 — evidence: `pg-target/core/migrations/postgres-migration.ts:724`; the scratch plan with `--rename User.name:User.fullName` wrote `...this.renameColumn({ schema: 'public', table: 'user', column: 'name', to: 'fullName' })` and `ALTER TABLE "public"."user" RENAME COLUMN "name" TO "fullName"`
- `guides/database/schema-changes.mdx:623` — "Renaming a field plans as a destructive drop column plus add column, because the planner has no rename hint yet … replace the pair with a `rawSql` `ALTER TABLE ... RENAME COLUMN`" — `migration plan` asks before it drops a field that holds data and takes `--rename User.name:User.fullName`, as `cli/migration-plan.mdx:61` and `generating-a-migration.mdx:227` say — evidence: same scratch run as above
- `orm/migrations/editing-a-migration.mdx:45-60` (the "as planned" listing) and `orm/reference/migration-api.mdx:372` — the planner names the slots after the field, `placeholder('User.displayName:check')` and `placeholder('User.displayName:run')`, not `'backfill-user-displayName:check'` / `'<name>:check'`, and it also writes `backfillsColumn: { schema: 'public', table: 'user', column: 'displayName' }`. The filled-in listing at lines 97-107 drops `backfillsColumn`, although line 116 says everything else "stays exactly as `migration plan` wrote it"; without it a failing check no longer counts the NULL rows — evidence: `migrations/app/20261120T0744_add_display_name/migration.ts` as planned in the scratch `app/`; `pg-target/core/migrations/operations/data-transform.ts:105-109`; `skills/prisma-8/references/migrations.md:229`
- `orm/migrations/generating-a-migration.mdx:201`, `orm/migrations/editing-a-migration.mdx:36` — the placeholder plan prints `⚠ Planned migration with placeholder(s) — edit migration.ts then run \`node migration.ts\` to self-emit` and nothing else above `from:` — rc.34 prints `… — edit migration.ts, then run \`node migrations/app/<dir>/migration.ts\` to self-emit`, then the operation tree (`Add column`, `Set NOT NULL`) and a `Statements applied` block. Editing-a-migration line 43 explains the old sentence — evidence: scratch `migration plan --name add_display_name --backfill User.displayName`

## Missing

- Nine of the methods `migration plan` writes into a PostgreSQL `migration.ts` are not in the Migration API reference, which says it lists "everything `migration.ts` can call": `renameColumn`, `addColumnWithTemporaryDefault` (written for every new required field planned without `--backfill`), `addRequiredColumnToEmptyTable`, `deleteRows`, `renameStoredKey`, `removeStoredKey`, `fillStoredKey` (named on `cli/migration-plan.mdx:100`), `dropExtension`, `setExtensionSchema` — evidence: `pg-target/core/migrations/postgres-migration.ts:381-560,724,991,1001`; every one is rendered by `pg-target/core/migrations/op-factory-call.ts`; the scratch plan for a new required `age Int` wrote `this.addColumnWithTemporaryDefault({ …, temporaryDefault: sql\`0\` })` — belongs on `orm/reference/migration-api.mdx` (Columns, Stored enum values, Extensions)
- Seven MongoDB migration functions are exported and planned since rc.24 but not listed: `renameCollection`, `renameField`, `unsetField`, `castField`, `fillField`, `rawAggregate`, `rawUpdateMany`. `rawAggregate` and `rawUpdateMany` build the query objects that `migration-api.mdx:495-528` and `editing-a-migration.mdx:280-300` assemble by hand (collection, command, `meta` with `lane`), and `rawUpdateMany(..., { bypassDocumentValidation: true })` is how a data transform skips validation, which `how-migrations-work.mdx:195` recommends without showing. What `migration plan --convert` / `--backfill` writes on MongoDB (`dataTransform` with `placeholder('User.age:update')`) gets one sentence on `cli/migration-plan.mdx:110` and no example — evidence: `packages/3-targets/mongo/1-target/src/exports/migration.ts`, `…/core/migrations/migration-factories.ts:123-142,271,306,408,468,806`, `docs/releases/v8.0.0-rc.24.md` ("MongoDB plans rewrite the documents a schema change touches"), `skills/prisma-8/references/migrations.md` (Type changes, the MongoDB bullet) — belongs on `orm/reference/migration-api.mdx#mongodb-operations` and `orm/migrations/editing-a-migration.mdx#the-same-pattern-on-mongodb`
