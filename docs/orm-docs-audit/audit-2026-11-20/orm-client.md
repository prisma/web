# Audit: orm-client

Pages read: orm/index.mdx, orm/core-concepts.mdx, orm/coming-from-prisma-orm-7.mdx, orm/fundamentals/advanced-queries.mdx, orm/fundamentals/reading-data.mdx, orm/fundamentals/relations-and-joins.mdx, orm/fundamentals/transactions.mdx, orm/fundamentals/types.mdx, orm/fundamentals/writing-data.mdx, orm/reference/index.mdx, orm/reference/orm-client.mdx, orm/reference/transactions-and-runtime.mdx, orm/release-status.mdx, orm/supported-databases.mdx, orm/supported-versions.mdx

The September findings in this area (row reads through `execute()`, `upsert` without `conflictOn`, streaming, the raw lane, many-to-many include, `verifyMarker`, the lossless aggregates, `firstOrThrow`, `query` versus `execute`) are all fixed on `main`. The pages already describe most of what rc.10 to rc.24 changed in the client: `contractFromJson`, `@onCreate`, `whereUnique`, `firstOrThrow`, row locks, fragments, `using`, `db.query`/`db.execute`/`db.toSql`, `cursor`, `transactionOptions` and `IsolationLevel`, MongoDB `prepare`, `connect()` being safe to call again, and `RUNTIME.BINDING_INVALID`. Every import path, export, and error code I checked on these pages exists at rc.24 except the one below.

## Breaks copy-paste

None found. Every client import path, exported name, and option checked on these pages exists in `@prisma/orm-postgres` and `@prisma/orm-mongo` 8.0.0-rc.24.

## Misleading

- `orm/fundamentals/relations-and-joins.mdx:242` — a second `connect` of the same tag "fails with an error whose code is `ORM.RELATION_LINK_DUPLICATE`. Catch that code" — the code was removed when nested writes moved to the write graph in rc.24. When the join table has a key over exactly its two link columns, as `PostTag @@id([postId, tagId])` on this page does, the junction insert now carries a skip-on-conflict clause, so the second `connect` succeeds and writes nothing. The `catch` the page tells readers to write never runs — evidence: `packages/3-extensions/sql-orm-client/src/mutation-graph/nested-mutations.ts:350-376,574-590` (`linkKeyConflict`), `projects/nested-mutations/spec.md:217` ("`ORM.RELATION_LINK_DUPLICATE` is removed"), no occurrence of `RELATION_LINK_DUPLICATE` anywhere under `packages/`
- `orm/fundamentals/writing-data.mdx:175` — "`connectOrCreate`, the relation `set`, and nested updates, upserts, and deletes do not exist" — since rc.24 a relation callback inside `update()` can run `where(...).updateAll(...)` and `where(...).deleteAll()` on to-many relations, and a relation callback can return an array of operations. `orm/reference/orm-client.mdx:1329-1330` and `orm/coming-from-prisma-orm-7.mdx:422` already say so, so the task page contradicts both. `writing-data.mdx:165-173` and `relations-and-joins.mdx:207-225` show only `create`, `connect`, and `disconnect` — evidence: `docs/releases/v8.0.0-rc.24.md:83-84` (#31013, #31014, #31016)
- `orm/core-concepts.mdx:89` — "Your app checks the signature on its first query too, but it only logs a warning" — the warning goes to the client's `log` option, which defaults to a sink that drops everything, and neither `orm init` nor `create-prisma` passes `log` in `db.ts`, so with the generated client nothing is printed. `orm/reference/transactions-and-runtime.mdx:41` says the same ("logs a warning on a mismatch") while line 60 of the same page says "Without `log`, these are not printed". Line 41 also tells the reader to run `npx prisma db update` on a mismatch, which is wrong for a database that changes only through migrations (the other pages say `db migrate` there) — evidence: `packages/2-sql-family/5-runtime/src/sql-runtime.ts:258-259,336` (`noopLog`), `:1717,1733` (marker codes), `create-prisma/templates/create/_shared/src/prisma/db.ts.hbs:16,37` (no `log`)
- `orm/reference/orm-client.mdx:398` and `:434` — on MongoDB, a related document loaded by `include()` has an `id` that "comes back as an `ObjectId` object", so wrap it in `String(...)` — since rc.14 included documents are decoded through their codecs, and since rc.19 the field keeps its schema name, so `posts[0].author.id` is a hex string, like the parent's `id`. The `String(...)` advice is harmless but the stated reason is wrong — evidence: `docs/releases/v8.0.0-rc.14.md` ("Mongo reads decode documents from `include()` ... so an `ObjectId` in them reads as a hex string"), `test/integration/test/mongo/stored-names.e2e.test.ts:194-204` (included `author` equals `rowOf(id)` with `id` a string)
- `orm/index.mdx:42` — "MySQL, SQL Server, and CockroachDB come later, and until then Prisma ORM 7 supports them" — `@prisma/orm-mysql` (reads, writes, transactions, migrations) and `@prisma/orm-mariadb` (migrations) are published at 8.0.0-rc.24, and `orm/supported-databases.mdx:15-16,31-33` and `orm/supported-versions.mdx:42` list them. The ORM landing page disagrees with both — evidence: `npm view @prisma/orm-mysql dist-tags` → `latest: 8.0.0-rc.24`, `packages/9-public/@prisma/orm-mysql/README.md`, `docs/releases/v8.0.0-rc.24.md:78`
- `orm/fundamentals/transactions.mdx:11` — "MySQL is an early preview that reads data, and its `db.transaction(...)` runs reads and raw SQL" — ORM `create`, `update`, `upsert` and `delete` work on MySQL since rc.23, and `orm/supported-databases.mdx:31` says so — evidence: `docs/releases/v8.0.0-rc.23.md:187` (#30927), `packages/9-public/@prisma/orm-mysql/README.md` ("runs ORM and SQL builder reads and writes, raw SQL and transactions")
- `orm/reference/index.mdx:12` — the SQL query builder "is PostgreSQL only" — `orm/fundamentals/advanced-queries.mdx:9` says it is "for PostgreSQL and SQLite", and MySQL has it too (rc.22 reads, rc.23 writes). The two pages disagree, and both leave out MySQL — evidence: `docs/releases/v8.0.0-rc.22.md:278`, `packages/9-public/@prisma/orm-sqlite/package.json` and `orm-mysql` export `./runtime` with `sql`, `packages/3-targets/mysql/1-mysql/9-facade/src/runtime/mysql.ts:95-103`
- `orm/release-status.mdx:23` and `:25` (and `metaDescription` on `:6`) — "Prisma ORM 6 receives security patches until 19 November 2026", in the present tense — that date passed on the day of this audit; Prisma ORM 7.0.0 was published 2025-11-19, so the 12-month window has ended — evidence: `npm view prisma time` → `"7.0.0": "2025-11-19T12:06:18.817Z"`
- `orm/fundamentals/writing-data.mdx:144` — MongoDB: type a timestamp `temporal.CreatedAt` or `temporal.UpdatedAt`, and "Pass any other value yourself" — MongoDB contracts accept `@onCreate(...)` and `@onUpdate(...)` generators on any field (only a database `@default` is refused), so a `uuid()` or `nanoid()` id or `@onCreate(now())` is filled by the client too — evidence: `packages/2-mongo-family/2-authoring/contract-psl/src/type-aliases.ts:302` ("MongoDB has no database defaults, so an alias's `@default` is refused"), `refusal-diagnostics.ts:356-364` (generated values on MongoDB fields), `skills/prisma-8/references/contract.md:164-166`
- `orm/fundamentals/reading-data.mdx:49-50` and `:56` — `findUnique` maps to `.where({ email }).first()` — `orm/coming-from-prisma-orm-7.mdx:261` and `orm/reference/orm-client.mdx:956-957` map it to `.whereUnique({ email }).first()`. Three pages, two answers for the same mapping — evidence: the three pages; `whereUnique` exists since rc.18 (`docs/releases/v8.0.0-rc.18.md:231`)
- `orm/reference/orm-client.mdx:250`, `orm/reference/transactions-and-runtime.mdx:392`, `:405`, `:416`, `:503` — MongoDB examples read `process.env.MONGODB_URL` — `orm init` and `create-prisma` write `DATABASE_URL` for MongoDB too, and `orm/fundamentals/transactions.mdx:175` uses `DATABASE_URL`; the plan records that the MongoDB quickstart was corrected for the same mismatch in prisma/web#8863. A reader pasting the reference example into a generated project gets an undefined URL — evidence: `packages/1-framework/3-tooling/cli/src/commands/init/output.ts:123,170` ("Set DATABASE_URL"), `changes.md:46`

## Unverified

- `orm/fundamentals/advanced-queries.mdx:335-340` — the `$group` output shows `_id` as a cuid-like string, but `authorId` is an `ObjectId` field and the pipeline builder sends and returns values without codec conversion (`orm/reference/orm-client.mdx:2187` says so for `match()`), so `_id` is probably a driver `ObjectId`. I checked `packages/2-mongo-family/5-query-builders/query-builder/src/builder.ts:396` (`group`) but did not trace whether `runtime.query` decodes a grouped `_id`.
- `orm/reference/orm-client.mdx:1331`, `:1485` and `orm/fundamentals/writing-data.mdx:316` — after `limit(0)`, `update()` and `delete()` "change nothing and return `null`". rc.24 (#31026) sends `update()` and `delete()` alone, without first selecting the row, when the condition names one row by primary key or unique constraint. I did not check whether a `limit(0)` on such a chain still stops the write. Checked `docs/releases/v8.0.0-rc.24.md:85` and `packages/3-extensions/sql-orm-client/src/write-guards.ts`, which guards only the bulk writes and relation updates.
