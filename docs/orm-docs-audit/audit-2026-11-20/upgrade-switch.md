# Audit: upgrade-switch

Pages read: `guides/upgrade-prisma-orm/index.mdx`, `guides/upgrade-prisma-orm/postgresql.mdx`, `guides/upgrade-prisma-orm/postgresql-incremental.mdx`, `guides/upgrade-prisma-orm/mongodb.mdx`, `guides/switch-to-prisma-orm/from-sql-orms.mdx`, `guides/switch-to-prisma-orm/from-drizzle.mdx`, `guides/switch-to-prisma-orm/from-mongoose.mdx`, `guides/database/multiple-databases.mdx`

How this was checked: besides reading the source, I ran the flows in `/Users/wmadden/Projects/prisma/scratch/audit-upgrade-switch/` against throwaway PostgreSQL 17 and MongoDB 8.0 replica-set containers (removed afterwards). On `prisma` 8.0.0-rc.34 with `@prisma/orm-postgres` and `@prisma/orm-mongo` 8.0.0-rc.24: `orm init` for PostgreSQL and MongoDB, `contract infer` on TypeORM-shaped and Drizzle-shaped databases, the Prisma 7 handoff with `prisma7Schema` (sign, baseline, `add_user_bio`, `contract print`), both multiple-database configs, and the Mongoose adoption with `db update`. On the pinned `prisma` 8.0.0-rc.27 with `@prisma/orm-postgres` 8.0.0-rc.20: the whole one-pass PostgreSQL guide against a Prisma 6-shaped database. Every code sample on the eight pages was type-checked with TypeScript 5.9 against those packages, and the samples compile.

The one-pass PostgreSQL guide (`postgresql.mdx`) holds at its pinned versions: `prisma generate` fails with `CLI.UNKNOWN_COMMAND` and exit 2, `db sign` prints `Database signed` and `Advanced ref "db"`, the baseline and `(no operations)` outputs match, `DateTime` reads as `"2026-11-20 07:53:50.742"`, `.cursor()` leaves the cursor row out, and the queries compile as CommonJS under `nodenext`. Its only finding is the pack list it shares with the route-by-route guide.

## Breaks copy-paste

- `guides/upgrade-prisma-orm/mongodb.mdx:134` — the table maps the Prisma 6 `Int`, `Float` and `Boolean` to `Int64Number`, `Double` and `Bool`, then says "The v6 names `Int`, `Float` and `Boolean` still work, with a `PSL_DEPRECATED_SCALAR_NAME` warning", which reads as if keeping `Int` keeps the BSON long. In Prisma 8 PSL, `Int` is `Int32`: the warning says `Scalar type "Int" is deprecated and will be removed; use "Int32"`, the codec is `mongo/int32@1`, and the validator requires `bsonType: "int"`. A reader who keeps `Int` gets a validator that refuses every document Prisma 6 wrote, because Prisma 6 stored `Int` as a BSON long. — evidence: `contract emit` of a model with `k Int` and `a Int64Number` on rc.24 gives `k` → `mongo/int32@1` / `{"bsonType":"int"}`, `a` → `mongo/int64Number@1` / `{"bsonType":"long"}`; `packages/2-mongo-family/2-authoring/contract-prisma6/README.md:20` (a plain Prisma 6 `Int` is a BSON long).
- `guides/database/multiple-databases.mdx:452` — says `npx prisma contract emit` with no `./prisma.config.ts` stops with `[CONFIG.FILE_NOT_FOUND]`. — It stops with `[CLI.CONFIG_SECTION_INVALID] The 'orm' section is missing: no config file was found.`, followed by `[CLI.CONFIG_FIELD_INVALID]`. — evidence: `npx prisma contract emit` in a project whose only configs are `prisma.users.config.ts` and `prisma.posts.config.ts`, `prisma` 8.0.0-rc.34.

## Misleading

- `guides/upgrade-prisma-orm/index.mdx:20` — "The route-by-route guide infers a new `contract.prisma` from the live database." — The route-by-route guide reads `prisma/schema.prisma` through `prisma7Schema(...)`, the same as the one-pass guide (`postgresql-incremental.mdx:252-268`, `:281`). Only its "Optional" section later converts the file with `contract print`, and nothing in it runs `contract infer`. The two pages disagree. — evidence: `guides/upgrade-prisma-orm/postgresql-incremental.mdx:252`.
- `guides/upgrade-prisma-orm/postgresql-incremental.mdx:289` — "Three of them need an extension pack" lists `citext`, `vector` and `postgis`. Line 60 says the one-command `orm init` path is refused for the same three, and `postgresql.mdx:141` names the same three. — A fourth extension also needs a pack: `pg_search`, through `@prisma/orm-extension-paradedb/control`. A schema that lists `pg_search` fails `contract emit` with `PSL.PRISMA7_EXTENSION_PACK_MISSING` and is refused by `orm init --from-prisma7-schema`, and none of the three passages mentions it. — evidence: `packages/3-targets/postgres/1-target/src/core/prisma7-binding.ts:99-118` (packs for `vector`, `postgis`, `pg_search`, `citext`); `packages/2-sql-family/2-authoring/contract-prisma7/README.md:36`.
- `guides/upgrade-prisma-orm/postgresql-incremental.mdx:508` — "`migration status` ends with `Up to date`" right after `db sign`. — Before the first `migration plan` there is no migration, and `migration status` prints `(no migrations)` and `✔ No migrations found`. — evidence: `npx prisma db sign` then `npx prisma migration status` against a Prisma 7-shaped database with the guide's `prisma.config.ts`, `prisma` 8.0.0-rc.34.
- `guides/upgrade-prisma-orm/postgresql-incremental.mdx:58` — after the one-command path the reader is told to "continue with step 2.5". That step and everything after it assume the contract is in `generated/prisma8`: line 339 gives the import `../generated/prisma8/contract.json`, and lines 351-362 add `generated/prisma8/**/*.d.ts` to `include`. — `orm init --from-prisma7-schema` writes the contract and `db.ts` to `src/prisma`, not `generated/prisma8`. — evidence: `packages/1-framework/3-tooling/cli/src/orm/init-scaffold.ts:221-222` (Prisma 7 source → `DEFAULT_CONTRACT_SOURCE_DIR`); `packages/1-framework/1-core/config/src/config-types.ts:45` (`'src/prisma'`).
- `guides/upgrade-prisma-orm/postgresql-incremental.mdx:40` — the example repository `prisma/prisma8-and-7-example` is said to show "the finished result of each phase". — Its `package.json` pins `@prisma/orm-postgres` 8.0.0-rc.11, `prisma` 8.0.0-rc.15, `@prisma/cli-engine` 0.3.0 and Prisma 7 `7.10.0-dev.58`, which is thirteen ORM releases behind the guide. The plan records only that the repository uses a separate contract file. — evidence: `gh api repos/prisma/prisma8-and-7-example/contents/package.json`.
- `guides/upgrade-prisma-orm/mongodb.mdx:43` — step 1 runs `npx prisma@latest orm init --yes --target mongodb --authoring psl` in the Prisma 6 project. — With `--target` and `--authoring`, `orm init` writes a starter contract and a `prisma.config.ts`, and installs `prisma@latest` over the Prisma 6 CLI. Its own warning says this "breaks the Prisma 6 CLI": every Prisma 6 command fails until Prisma 6 has its own config file. Steps 5 and 6 of the same guide ask the reader to keep the Prisma 6 app deployable and to run Prisma ORM 8 beside it. Without the two flags, `orm init` stops with `CLI.INIT_PRISMA6_SCHEMA_FOUND` and prints a side-by-side setup. — evidence: `packages/1-framework/3-tooling/cli/src/orm/init-inputs.ts:664-671` and `:700-715`; `packages/1-framework/3-tooling/cli/src/commands/init/errors.ts:525-545`.
- `guides/upgrade-prisma-orm/mongodb.mdx:46` — "`init` writes a `prisma.config.ts`" and then shows one that imports `definePrismaConfig` from `'prisma/config'`. — `orm init` writes `import { definePrismaConfig } from '@prisma/cli-engine'`, as `from-mongoose.mdx:173`, `from-drizzle.mdx:185` and `multiple-databases.mdx:71` show. Both imports work, but the pages give two forms of the file `init` writes. — evidence: `packages/1-framework/3-tooling/cli/src/commands/init/templates/code-templates.ts:313`; the scaffolded `prisma.config.ts` on rc.34.
- `guides/upgrade-prisma-orm/mongodb.mdx:425` — "on a populated database it refuses the validator changes this migration needs, because adding a validator to a collection with existing documents is classed destructive. `db update` applies them after a confirmation prompt." — `db init` refuses them as widening operations (`widening operation disallowed: Add validator on users`), not destructive ones. `db update` applies them without asking: it asks only about operations that would lose data. `from-mongoose.mdx:538` says "applies it without asking", so the two pages also disagree. — evidence: `npx prisma db init` then `npx prisma db update` with no TTY on a populated collection, rc.34; `packages/1-framework/3-tooling/cli/src/control-api/operations/db-update.ts:19-25`.
- `guides/switch-to-prisma-orm/from-mongoose.mdx:538` — "MongoDB does not check the documents already in a collection when it adds a validator. A document the validator would refuse stays as it is, and the next write to it fails." `mongodb.mdx:442` says the same thing more briefly. — Since rc.24, `db update`, `db migrate` and `migration plan` check every document before they add a validator. They stop with `MIGRATION.PRECHECK_FAILED`, naming one `_id`, the field it does not fit, and the `mongosh` `$nor` query that finds the rest. The manual `$nor` check on lines 538-544 is now what the CLI does. — evidence: `docs/releases/v8.0.0-rc.24.md` ("MongoDB plans rewrite the documents a schema change touches"); `npx prisma db update` with `__v` still on the documents prints `[MIGRATION.PRECHECK_FAILED] Operation validator.categories.add stopped: 2 documents in collection categories do not fit the new validator`; `skills/prisma-8/references/migrations.md:389`.
- `guides/switch-to-prisma-orm/from-mongoose.mdx:351` — "Optional fields such as `profile` are required in the `create` input, so pass `null` when there is no value." `from-drizzle.mdx:643` says the same thing for PostgreSQL: "pass `null` for a nullable column you do not set". — An optional field can be left out of `create(...)` on both databases. It type-checks, and the row comes back with the field as `null`. — evidence: `db.orm.users.create({ email, name })` on the Mongoose contract and `db.orm.public.Post.create({ title, authorId })` on the Drizzle contract both compile, and both return `profile: null` / `content: null` when run, rc.24.
- `guides/switch-to-prisma-orm/from-sql-orms.mdx:324` — the sample output prints every `createdAt` as a string, such as `'2026-09-10 21:57:22.667511+06'`, which contradicts line 184 and line 394 on the same page (a `Date`). — `DateTime(precision: 6)` reads a JavaScript `Date`, and the script prints `createdAt: 2026-11-20T07:50:45.235Z`. All nine rows of the block (lines 324-339) show the old form. — evidence: `node src/prisma-queries.ts` against the inferred TypeORM contract, rc.24.
- `guides/switch-to-prisma-orm/from-sql-orms.mdx:206` — the `db sign` result is shown as `"summary": "Database signed (marker created)"`, `"target": {...}` and `"marker": { "created": true, "updated": false }`. `from-drizzle.mdx:417-425` shows `from: none` / `to: <hash>`. — rc.34 prints `"summary": "Database signed"` with `spaces[]` and `advancedRefs[]` in JSON. The human output is `✔ app: signed <hash> (no marker before)`, `✔ Database signed` and `✔ Advanced ref "db" → <hash>`. Neither page says that `db sign` also sets the `db` ref and writes `migrations/`. — evidence: `npx prisma db sign --json` and `npx prisma db sign`, rc.34.
- `guides/switch-to-prisma-orm/from-sql-orms.mdx:128`, `from-drizzle.mdx:204`, `from-mongoose.mdx:192` (3 places) — the `db.ts` that "`orm init` writes" imports `type { Contract } from './contract.d'`. — Since rc.24, `orm init` writes `'./contract.d.js'`. — evidence: `packages/1-framework/3-tooling/cli/src/commands/init/templates/code-templates.ts` (`dbFile`); the scaffolded `src/prisma/db.ts` and `prisma/users/db.ts` on rc.34; `docs/releases/v8.0.0-rc.24.md` (#30360).
- `guides/switch-to-prisma-orm/from-drizzle.mdx:279` — the inferred contract shows `post Posts @relation(..., index: false)` on the join model. — rc.24 `contract infer` writes `index: "posts_to_categories_post_id_category_id_pk"` there. The step 3 contract copies `index: false` (line 374), which gives a different storage hash from what `infer` produces. `db sign` still accepts it. — evidence: `npx prisma contract infer` on the Drizzle-shaped database, then `contract emit` of both forms: `619ae802…` against `83b73a7b…`.
- `guides/switch-to-prisma-orm/from-mongoose.mdx:130`, `:155` and `:485` — the printed `orm init` output shows `npm add @prisma/orm-mongo dotenv`, line 155 says the app reuses "the same" driver Mongoose depends on, and step 4.1 says to make `mongodb` a direct dependency because it was only a transitive one. — `orm init` installs `mongodb` itself (`add @prisma/orm-mongo dotenv mongodb`, `"mongodb": "^7.9.0"`), so step 4.1's `npm install mongodb` does nothing. `@prisma/orm-mongo` needs `mongodb ^7.0.0`, while Mongoose 8 depends on `mongodb ~6.20.0`, so on Mongoose 8 the app runs two drivers. The `mongodb@^7` AWS-credentials warning on `mongodb.mdx:34` is not on this page. — evidence: `orm init --target mongodb` on rc.34; `@prisma/orm-mongo@8.0.0-rc.24` `peerDependencies`; `npm view mongoose@8 dependencies.mongodb`.

## Missing

- The side-by-side setup for a Prisma 6 MongoDB app: Prisma 6 installed as `"prisma6": "npm:prisma@6"` with a `prisma6` script and `prisma6.config.ts`, Prisma 8 reading the Prisma 6 schema through `prisma6Schema(...)`, and Prisma 6's `db push`, then `contract emit` and `db sign`, after each schema change. `orm init` prints these steps under `CLI.INIT_PRISMA6_SCHEMA_FOUND`. The site has only one paragraph on `prisma6Schema`, and the index offers MongoDB only "all at once". — evidence it exists: `packages/1-framework/3-tooling/cli/src/commands/init/prisma6-side-by-side.ts`; `packages/2-mongo-family/2-authoring/contract-prisma6/README.md` ("Using the source in a Prisma 6 project"); `packages/3-targets/mongo/9-facade/README.md` — belongs on `guides/upgrade-prisma-orm/mongodb.mdx` step 1 and as a row in `guides/upgrade-prisma-orm/index.mdx`.
- What to do when the validator check stops an apply on MongoDB: the `MIGRATION.PRECHECK_FAILED` output and its `mongosh` query, and the way to apply a validator over documents that do not fit, `checkDocuments: false` on the `collMod` in `migration.ts`. — evidence it exists: `skills/prisma-8/references/migrations.md:388-389`; `docs/releases/v8.0.0-rc.24.md` — belongs on `guides/upgrade-prisma-orm/mongodb.mdx` step 4 and `guides/switch-to-prisma-orm/from-mongoose.mdx` step 4.3.
- `temporal-polyfill` is a required peer dependency of `@prisma/orm-mongo` since rc.24, so a Yarn project, or npm with `legacy-peer-deps`, must add it itself. The prerequisites name only the `mongodb` peer. — evidence it exists: `@prisma/orm-mongo@8.0.0-rc.24` `peerDependencies` (`temporal-polyfill: ^1.0.4`); `docs/releases/v8.0.0-rc.24.md` — belongs in the prerequisites of `guides/upgrade-prisma-orm/mongodb.mdx` and `guides/switch-to-prisma-orm/from-mongoose.mdx`.
- After step 2.1 of the route-by-route guide, an old `prisma migrate dev`, `prisma generate` or `prisma db push` in a script or CI job fails with `CLI.V7_COMMAND`. The error names the Prisma 8 command to run instead and how to keep Prisma 7 as `@prisma/prisma7`. The guide says to update scripts but not what the reader sees if one is missed. — evidence it exists: `docs/releases/v8.0.0-rc.24.md` ("Prisma 7 commands fail with `CLI.V7_COMMAND`"); `skills/prisma-8/references/migrations.md:596` — belongs on `guides/upgrade-prisma-orm/postgresql-incremental.mdx` step 1.4 or 2.1.
- MongoDB 8.0 as the minimum server version. `mongodb.mdx:22` states it, and `from-mongoose.mdx` prerequisites do not. — evidence it exists: `orm/supported-versions.mdx` (MongoDB 8.0); `guides/upgrade-prisma-orm/mongodb.mdx:22` — belongs in `guides/switch-to-prisma-orm/from-mongoose.mdx` prerequisites.

- `guides/upgrade-prisma-orm/index.mdx:26` and `postgresql-incremental.mdx:12` — which Prisma 8 versions Prisma Compute deploys. These are platform facts outside the four checkouts, and I did not check them.
