# Conventions for the orm/contract-authoring pages (in addition to conventions.md)

- These are explanation and how-to pages, not reference pages: The data contract (what it is), Author in PSL, Author in TypeScript, The emitted artifacts, Capabilities. Each one answers "what is this and what do I write". Keep the heading order. Do not renumber, rename, or reorder headings; if a heading must change because it contains a banned term, pin the old anchor with `[#old-anchor]`.
- No commentary about the docs inside the docs. Cut sentences such as "This page explains", "This page covers the basics briefly", "the examples throughout these docs", "to give a sense of the granularity". Write the thing itself.
- Never interleave PostgreSQL and MongoDB sentence by sentence. Where both databases matter, give PostgreSQL its own sentences or block and then MongoDB its own. Tabs already on a page stay.
- The word "contract" is the subject of this section. On first use on a page: "your contract, the `contract.prisma` file that replaced `schema.prisma`" (or `contract.ts` when the page is about TypeScript authoring). After that, "contract" alone. "Data contract" is allowed in the page title and once in the first sentence of the-data-contract; elsewhere say "contract".
- `prisma contract emit` "writes `contract.json` and `contract.d.ts` beside the source". Say this once per page where the command first appears. Never a bare "emit" as a noun ("the emit", "emission", "emitted artifacts"). "The artifacts" is allowed after the page has named the two files.
- "Hashes" and the marker: "when you run `prisma db sign`, Prisma ORM records which contract the database matches in a small table it creates in the database; the client checks that record before its first query" (verify against source; use the wording the check confirms). Do not write "signature" or "marker" without that definition on the same page.
- Banned on these pages in addition to the list: gate / gated / gates (write "checks", "requires", "is only available when"); capability in prose (write "a database feature the contract needs", "what your database supports"; the code identifier `capabilities` for the section of `contract.json`, and the key names such as `sql.lateral`, are code and stay); codec (write "how the value is stored and read", or name the type id such as `pg/text@1`); canonical / canonicalizes (write "in a fixed key order"); deterministic (write "the same source always produces the same files"); pure (as in "the contract file must stay pure": write "must not read the environment, the clock, or random values"); artifact when the two files can be named instead; "source of truth" (write "the one file the config points at"); "escape hatch"; "purpose-built"; "first-class"; "wiring" / "wired"; "hangs off"; "consult"; "authoritative"; "physical name" (write "column name in the database"); "value object" only with its definition on the same page ("a `type` block: a structured value stored inside its parent row, with no table of its own").
- Type ids such as `pg/text@1`: "the PostgreSQL type plus a version, always `@1` today". Do not explain the format twice on one page.
- "Prompt your coding agent" sections: keep, but the first sentence reads "Projects created with `npm create prisma@latest` include the Prisma ORM skills for your coding agent. In an existing project, run `npx prisma skills sync`." Keep the example prompts.
- Scaffold command: `npm create prisma@latest -- my-app`. Emit command in prose and code: `npx prisma contract emit` (not `prisma@latest`, once the page has shown installation; the pages assume an existing project).
- The source of truth is prisma/orm at 8.0.0-rc.10 (`cfccb09be2`), checked out at `wip/prisma-src/`. Where a page names an rc.9 behaviour that rc.10 changed, rc.10 wins.
- The CLI pages under `/cli/` (`contract-emit`, `contract-infer`, `db-sign`, `db-verify`, `db-init`, `migration-plan`, `configuration`) are out of scope; link to them, do not restate their flags.
