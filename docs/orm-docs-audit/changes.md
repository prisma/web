# Prisma ORM 8 docs: what to change, and in what order

This is the working list of changes to the Prisma ORM 8 documentation, built from a page-by-page audit against `@prisma/orm-postgres@8.0.0-rc.9` (the audit files are under `audit/`, with a source citation for every finding). Four kinds of change: restructure the site (A), correct existing pages (B), write new pages (C), change the ORM or its tooling where the docs are hard because the tool is (D). Section E lists small gaps found after the audit.

Item numbers (A1, B11, C9, D4) are stable identifiers used in the audit files and the PRs; some are out of sequence because items were added as they were found. "J1" to "J12" are the reader jobs defined in `journeys.md`. Source paths are in `prisma/orm` at rc.9 unless they start with `create-prisma`.

Status as of 2026-09-30.

## D. Change the ORM and its tooling

Places where the docs are hard because the tool is. Grouped by who owns the fix.

### ORM behaviour

- **D1. Make adoption one step.** Today: `contract infer`, edit, `contract emit`, `db sign`, `migration plan`, `migration ref set db <hash>`. Either `db sign` sets the `db` ref when none exists, or a `db adopt` command does sign plus ref. Removes the recreate-everything trap in J2 and halves C3. Landed as prisma/orm#30251: `db sign` sets the `db` ref, with or without `--db`; `--advance-ref <name>` redirects and `--no-advance-ref` skips. Documented in #8291. Brief in `brief-db-ref-on-adoption.md`.
- **D2. `migration plan` with no origin and no migrations on disk plans from empty silently.** With migrations on disk it refuses (`MIGRATION.PLAN_ORIGIN_UNKNOWN`). For a signed database with no ref the silent case is the wrong default; it should warn or refuse the same way. Landed with D1: the plan prints a notice and `--json` carries `fromDefaulted: true`.
- **D9. `--db` suppresses `db` ref advancement.** `db init` and `db update` advance the ref only when the URL comes from config; with `--db` they do not unless `--advance-ref` is also passed. Surprising, and every example passes `--db`. Advance regardless, or warn when `--db` is used without `--advance-ref` and no ref exists. Source: `cli/src/control-api/operations/ref-advancement.ts:19-28`. Decided 2026-09-22 and filed as prisma/orm#30370: `db migrate` should advance `db` when the connection comes from `prisma.config.ts` and `CI` is unset, never with `--db`, with `--no-advance-ref` to opt out and a failed ref write downgraded to a warning. Still open on 2026-09-28.
- **D13. `migration ref set … @db` fails** with `MIGRATION.HASH_NOT_IN_GRAPH` instead of reading the marker. Support it when a connection is available, or reject it with a message that says why. Source: `cli/src/control-api/operations/ref.ts:104-118`. Still open on 2026-09-28: `@db` resolves to an empty hash and fails as `errorRefSetHashNotInGraph('')` (`migration/src/refs/contract-ref.ts:50-56`, `cli/src/control-api/operations/ref.ts:98-112`).
- **D15. `db update` never plans data operations.** A change that needs a backfill fails and the user must switch to `migration plan`; nothing says so. Allow it, or print the hint. Source: `cli/src/control-api/operations/db-update.ts:17`. Still open on 2026-09-28: `db update` plans only the additive, widening, and destructive classes and prints no pointer to `migration plan`.
- **D16. `migration status` exits 0 on warnings.** CI has to parse `--json`. A `--strict` flag or a non-zero exit on warn-level findings makes C11 one line. Source: `cli/src/orm/migration/status-findings.ts`. No longer needed: the CI job is `db migrate --to <ref>`, which refuses a database whose marker is outside the history before it runs anything (prisma/web #8310; the skill says the same since prisma/orm#30382). `migration status` exiting 0 on its `warn` findings is deliberate.
- **D8. Streaming does not stream on `postgres()`.** The facade creates its driver with `cursor: { disabled: true }`, so `for await` iterates an already-fetched result; only the serverless facade exposes cursor batches. Measured: breaking after the first row of a 400,000-row table still grew the heap by 64 MB. Expose `cursor` on `postgres()` or keep the docs' new wording. Source: `packages/3-extensions/postgres/src/runtime/postgres.ts:245-247`.
- **D12. Permissive mode is unreachable on Postgres.** `postgres()` never forwards `mode`, so every "warn in permissive mode" branch in lints and budgets is dead on Postgres; only `mongo()` accepts it. Expose it or remove the branches. Source: `postgres.ts:86-94,276-282`, `sql-runtime.ts:187`. Still open on 2026-09-28: `postgres()` takes no `mode`, so the runtime is always strict; at `main` only budgets read `ctx.mode`, not lints.
- **D7. `db.connect()` vs `db.runtime()`, `db.close()` vs `db.runtime().close()`.** Two names for adjacent things, a Mongo-only `await`, and `db.prepare` then `db.connect()` throwing `DRIVER.ALREADY_CONNECTED`. One call on both targets would simplify every page that shows a script. Still open on 2026-09-28: on PostgreSQL `runtime()` returns a `Runtime` and `prepare` exists; on MongoDB `runtime()` returns a promise and there is no `prepare`; `prepare` followed by `connect()` still throws `DRIVER.ALREADY_CONNECTED`.
- **D10. Inferred contracts fail at read time without the Temporal polyfill.** `contract infer` maps timestamp columns to Temporal-backed types; on Node.js 25 and earlier every read throws (official Node.js 26 ships `globalThis.Temporal`; Homebrew's Node.js 26 build omits it) `RUNTIME.TEMPORAL_UNAVAILABLE` unless `temporal-polyfill/full/global` is imported. `create-prisma` installs the polyfill; `orm init` does not. Options: infer to `TimestamptzString` by default, have `orm init` install and import the polyfill, or fail at emit with a clear message. Source: `packages/3-targets/3-targets/postgres/src/core/psl-infer/postgres-type-map.ts:30-33`. Still open on 2026-09-28: `contract infer` still maps `timestamptz` to the Temporal-backed `Timestamptz` (the map moved to `psl-build/postgres-type-map.ts:32-33`), the Prisma 7 route in `orm init` maps `DateTime` to the Temporal-backed `Timestamp(3)`, and `orm init` neither installs nor imports `temporal-polyfill`. prisma/orm#30301 and #30308 (infer `timestamptz` as `TimestamptzString`) are open. Update 2026-09-30: prisma/orm#30520 (open) fixes the control-plane half: `contract emit`, `db init`, `db update`, `contract infer`, and `node migration.ts` stop needing a global `Temporal` for date and time defaults. The application runtime is deliberately unchanged, so an app on Node.js 24 still needs `temporal-polyfill` for its first date read, and the docs keep telling readers to import it in `db.ts`.

The canonical error-reference intros are written for the maintainers, not the reader.** Found 2026-09-30 by a cold reader round on the generated pages (prisma/web#8353 fixes the site's own sentences). In `docs/reference/error-reference.md` of prisma/prisma: "structured envelope", links to ADR 239 and Error Handling as the definition, "your facade package's `utils/structured-error` subpath" without saying which package is yours, the `structuredError` versus `runtimeError` rule for `error.meta` and `error.details` (the reader needs `error.meta ?? error.details`), "a bad answer is still an answer", "diagnostics on a successful envelope", the `4`-`99` band paragraph that repeats the exit-`4` paragraph, the `PN-DOMAIN-NNNN` rename note (readers know `P2002`, and nothing says where those went), and `TESTKIT` with no description. In prisma-cli's file: "unified Prisma CLI", "warn-severity diagnostics that ride a successful run", "No boundary invents a code", the exit-code contract only by link, and "Engine-level invocation" as the `CLI` description. Both intros should say what the reader does: match on `error.code`, read `error.meta ?? error.details`, follow the printed `docsUrl`.

### Product decisions

- **D4. Missing client API.** Verified absent: `firstOrThrow` on the collection (it exists on the result, so `.all().firstOrThrow()` works), atomic `increment`/`decrement`, case-insensitive string filters, insert with on-conflict-do-nothing (`skipDuplicates`), JSON path or containment filters (the `jsonb` codec has only the `equality` trait). Also not supported: soft delete, validations, lifecycle callbacks, custom `Collection` subclasses, read replicas, MongoDB referential actions. Each needs a decision: build it, or document the workaround and say it is not planned. The types work has shipped: the where filter types (#30158) in rc.9; `Models`, `Scalars<>`, and `Shape<>` (#30231, #30236) in rc.10. Status on 2026-09-28: insert-and-skip-conflicts landed as `createAll(rows, { onConflict: 'skip', conflictOn? })` and `createAndCount` (prisma/orm#30365, rc.12); the field filters have `.ilike(pattern)` and, since rc.12, full-text search operations. Still absent on SQL: atomic increment and decrement, `firstOrThrow` on a collection, case-insensitive equality, JSON path or containment filters, soft delete, validations, lifecycle callbacks, read replicas. MongoDB has `inc` and `mul`; MongoDB referential actions are still unsupported, and the Prisma 6 schema reader now rejects `onDelete` and `onUpdate` explicitly (prisma/orm#30405). Suggested on 2026-09-28, for the ORM team to schedule: build atomic increment and decrement and a collection-level `firstOrThrow` before GA; JSON path and containment filters and list filters after GA; document case-insensitive matching with `.ilike` and its escaping, and nested writes through `db.transaction`; soft delete, validations, callbacks, and read replicas are not planned (Prisma ORM 7 had none built in); MongoDB referential actions not for GA, with `docs/reference/mongodb-user-promise.md` corrected.
- **D6. The npm `latest` tag.** `prisma@latest` is the Prisma ORM 8 CLI (8.0.0-rc.15 on 2026-09-21) while `@prisma/client@latest` is 7.10.0, so a Prisma 7 project's routine `npx prisma` picks up the 8 CLI against a 7 client. Move the release candidate to `next` until GA, or state the policy on C4. Resolved: the tag stays; #8194 pins the Prisma ORM 6 pages to 6.19.3 and the Prisma ORM 7 CLI commands to `prisma@prev`.

## Naming

The product is "Prisma ORM". A version number appears only when two versions are contrasted ("Prisma ORM 7 to 8"). Never "Prisma 8" as a product name. Rule, counts, and exceptions in `naming.md`. Applies to every item above and to the proposed nodes in `ia.md`. Landed as #8246 and #8275.
