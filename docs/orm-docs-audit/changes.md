**B11. `execute()` to `query()` for every row-returning plan.** The largest defect the audit found. Since rc.2, `runtime.execute(plan)` returns `{ affectedRows }` and rows come from `runtime.query(plan)` (an `AsyncIterableResult`, awaitable to an array or iterated with `for await`). The MongoDB client's `db.execute(plan)` facade method was removed in the same release; rows come from `(await db.runtime()).query(plan)`. Prepared statements split the same way: `ps.query(runtime, params)` for rows, `execute` only for `.affectedCount()` plans. Roughly 200 lines on 14 pages: `orm/reference/sql-query-builder.mdx` (about 31), `orm/reference/pipeline-builder.mdx` (about 50), `orm/reference/raw-queries.mdx` (about 20), `orm/fundamentals/advanced-queries.mdx` (10), `orm/reference/transactions-and-runtime.mdx` (about 12, including `withTransaction`'s `tx` surface and `executePrepared`, which does not exist), `orm/core-concepts.mdx`, `orm/fundamentals/reading-data.mdx`, `orm/fundamentals/relations-and-joins.mdx`, `orm/extensions/using-extensions.mdx`, `orm/middleware/built-in-cache.mdx`, both `add-to-existing-project` pages, `guides/upgrade-prisma-orm/mongodb.mdx` (5). Non-returning writes such as `orm/fundamentals/transactions.mdx:60` are correct and stay on `execute`. The shipped skill has the same defect (D14). Evidence: `packages/2-sql/5-runtime/src/sql-runtime.ts:309-322`, `packages/3-extensions/mongo/src/runtime/mongo.ts:28-39`, `docs/releases/v8.0.0-rc.2.md`. Audit: `orm-client`, `builders`, `start-guides`.

**B12. Evidence: `docs/releases/v0.17.0.md:45`, `packages/1-framework/3-tooling/migration/src/refs/contract-ref.ts:14-24`. Audit: `contract`, `migrations-cli`.

**B13. `extensionPacks` to `extensions`.** Renamed in 0.17 and the old key fails loudly. `orm/contract-authoring/typescript-schema-builder.mdx` (5 sites in `defineContract`; the PostgreSQL contract on that page does not build) and `orm/contract-authoring/the-contract-artifact.mdx` (2 sites as the `contract.json` top-level key). Evidence: `docs/releases/v0.17.0.md:73`, `packages/3-extensions/postgres/src/contract/define-contract.ts`. Audit: `contract`.

**B14. Migration directory layout and imports.** The site shows `start-contract.json` / `end-contract.json` inside each migration directory and `migration.ts` importing `./end-contract`. ### Page rewrites

**B15. Existing-project pages: the default path is `src/prisma/`, not `prisma/`.** Both `add-to-existing-project` pages tell the reader to keep the default schema path `prisma/contract.prisma` and build every later command on it (`contract infer --output ./prisma/contract.prisma`, `import "./prisma/db"`). `orm init` defaults to `src/prisma/contract.prisma` and writes `db.ts` beside it, so a reader who accepts the default gets a file `prisma.config.ts` never reads and an import that does not resolve. **B16. The `db` ref and plan-origin story on the migrations pages.** Three connected errors. (a) The pages say `migration plan` without `--from` or a `db` ref plans a full CREATE migration; since rc.8 it refuses with `MIGRATION.PLAN_ORIGIN_UNKNOWN` when migrations exist on disk, and names the exits (`migration ref set db <hash>`, `--from <ref>`, `--from @empty`). The upgrade guide tells readers to look for the CREATE TABLE symptom that no longer appears. (b) `db init` and `db update` advance the `db` ref automatically only when `--db` is omitted; every example on the site passes `--db "$DATABASE_URL"`, which suppresses that unless `--advance-ref` is also given, so a reader following the site's loop hits (a) on the second plan. No page says this. (c) Retracted after PR 2: the audit said `MIGRATION.NO_TARGET` never comes from `migration plan`, but `plan-resolution.ts` calls `findLatestMigration`, which calls `findLeaf`, which throws it on a cyclic graph, and the monorepo's `gotchas.md:83-110` reproduces exactly the rollback case `rollbacks-and-recovery.mdx` describes. That page was right. Also `the-migration-graph.mdx` says there is no baseline mechanism; the planner writes an automatic baseline when the graph is empty and the `db` ref names a snapshot, and `--from @empty` is the supported retrofit. Pages: all six `orm/migrations/*`, `cli/migration-plan.mdx`, `cli/db-init.mdx`, `cli/db-update.mdx`, `cli/migration-ref.mdx`, `cli/index.mdx`, `guides/upgrade-prisma-orm/postgresql.mdx`. Evidence: `packages/1-framework/3-tooling/cli/src/utils/cli-errors.ts:428-475`, `cli/src/control-api/operations/ref-advancement.ts:19-28`, `cli/src/control-api/operations/migration-plan.ts:369,505-545`. Audit: `migrations-cli`, `start-guides`. Ties to D1, D2, D9.

**B17. Middleware pages: the hook model is wrong.** The pages document five hooks with `intercept` and `beforeExecute` for reads. Since rc.2 there are two lifecycles: `beforeQuery` / `interceptQuery` / `onRow` / `afterQuery` for row queries, and `beforeExecute` / `interceptExecute` / `afterExecute` for non-returning writes. There is no `intercept`, no compatibility alias, and `afterExecute` carries `stats.affectedRows`, not `rowCount`. The authoring guide's flagship query logger implements only `afterExecute` and reads `result.rowCount`, so it is a type error and would never log the SELECT the page shows it logging. Also: `unindexedPredicate` is not a lint severity key; `severities.latency` on budgets is read (page says it is not); "permissive mode" is unreachable from the Postgres client (D12); the cache runs on the query lifecycle. Pages: all five `orm/middleware/*`. Evidence: `packages/2-sql/5-runtime/src/middleware/sql-middleware.ts`, `packages/2-sql/5-runtime/src/middleware/lints.ts:13-23`, `budgets.ts:97-125`, `examples/prisma-8-demo/src/prisma/slow-query-warning.ts`. Audit: `builders`.

**B18. Raw SQL page says the opposite of what ships.** `orm/reference/raw-queries.mdx` and `advanced-queries.mdx` say there is no way to run a standalone raw statement. Since rc.2 there is: `db.raw.sql\`…\`.returnsRow(spec).build()` for rows and `.affectedCount().build()` for writes; raw row queries compose as subqueries and CTEs. The page also calls `db.raw` as a template tag; it is a lane object and the tag is `db.raw.sql`. The "bare scalar interpolation is broken because the inferer emits unversioned ids" callout is contradicted by the adapter source, which emits versioned ids. Evidence: `packages/2-sql/4-lanes/sql-builder/src/types/raw-query.ts:117-170`, `packages/3-targets/6-adapters/postgres/src/core/adapter.ts:112-140`, `examples/prisma-8-demo/src/queries/raw-query-demo.ts`. Audit: `builders`, `orm-client`.

**B19. Relations and data-modeling pages say things are unsupported that work.** (a) The 1:1 mirror field `profile Profile?` "is not supported yet": it is accepted (rejected only when the foreign key is not unique) and `include('profile')` type-checks as a to-one include. (b) Implicit many-to-many `include` "not supported yet": the ORM resolves `through` relations and the demo includes `Post.tags`; nested `create` / `connect` / `disconnect` through the junction also work, and `orm-client.mdx` already documents `disconnect` through the junction. (c) Referential actions "as it lands": `onDelete` / `onUpdate` with `Cascade` / `Restrict` / `SetNull` / `NoAction` are lowered today. (d) The discriminator "is not filled in automatically": `.variant('Bug').create()` injects it; the page never mentions `.variant()`. Both pages send users to the SQL builder for things the ORM does. Pages: `orm/fundamentals/relations-and-joins.mdx`, `orm/data-modeling/relational-databases.mdx`. Evidence: `packages/2-sql/2-authoring/contract-psl/test/interpreter.relations.test.ts:78`, `packages/3-extensions/sql-orm-client/src/collection-contract.ts:356-379`, `mutation-executor.ts:836-926`, `collection.ts:406`, `psl-relation-resolution.ts:19-22`. Audit: `contract`, `orm-client`.

**B20. Aggregates decode as numbers, not strings.** `sql-query-builder.mdx` and `advanced-queries.mdx` tell users `COUNT` / `SUM` / `AVG` come back as strings and to call `Number(...)`. Since rc.2 `count()`, integer `sum()`, and `avg()` return `number` (throwing `RUNTIME.DECODE_FAILED` outside the safe range), with `countBigInt()`, `sumBigInt()`, `avgDecimal()` beside them. The "fixed" function list on `sql-query-builder.mdx` omits these; `min` / `max` are not numeric-only. Correction after PR 2: the audit said the `DateTime` column (`pg/timestamptz@1`) is still excluded from `min`/`max`; no such codec exists at rc.9. `DateTime` maps to `pg/timestamptz-temporal@1`, which is in `MIN_MAX_PRESERVING_CODECS`, so `min('createdAt')` type-checks; the compile error the page should show is `sum`/`avg` over a timestamp column. Evidence: `packages/3-targets/3-targets/postgres/src/core/aggregates.ts:126-213`, `docs/releases/v8.0.0-rc.2.md:32-53`. Audit: `builders`, `orm-client`.

Stale CLI names, flags, codes, and output.** One pass over `cli/*` and `orm/migrations/*`: `--skip-skills` and `CLI.INIT_SKILL_INSTALL_FAILED` on `orm-init.mdx` (removed rc.6; also cited on `(index)/index.mdx` and `getting-started.mdx`); `ref set` / `ref list` bare group (rc.5: `migration ref set`) and `ref set prod @db` (fails, `@db` is not accepted by the offline command); `prisma-cli migrate` hint text and the sentence explaining it (rc.5: hints print `prisma db migrate`); `(PN-RUN-3000)` (0.17: dotted codes, `MIGRATION.RUNNER_FAILED` and siblings); `from: null` (prints `from: (baseline)`); the "Applied 1 migration(s)…" summary line (no migration count); `git clone …/orm` then `cd prisma`; `npx prisma@latest migrate` on `create-prisma.mdx` (the command is `db migrate`); hyphenated `--name add-users-table` shown as the directory name (slugs become `add_users_table`); `contract infer` presents `--db` as required (falls back to config); `orm-init.mdx` says the scaffolded `db.ts` does not load `.env` (it starts with `import 'dotenv/config'`) and that `contract:emit` calls `prisma-cli`. Audit: `migrations-cli`, `start-guides`, `contract`.

## D. Change the ORM

These are places where the docs are hard because the tool is. Each is a candidate for the product backlog, not a docs fix. D1 and D3 have briefs (`brief-db-ref-on-adoption.md`, `brief-skills-opt-out.md`) and are handed off.

**D1. Make adoption one step.** Today: `contract infer`, edit, `contract emit`, `db sign`, `migration plan --name baseline` (or equivalent), `migration ref set db <hash>`. Two options: have `db sign` also set the `db` ref when no ref exists, or add a `db adopt` command that runs sign plus ref. Either removes the recreate-everything trap in J2 and cuts C3 in half. Handed off.

**D2. `migration plan` with no origin and no migrations on disk.** The CLI refuses when migrations exist on disk with no ref (`MIGRATION.PLAN_ORIGIN_UNKNOWN`). When no migrations exist it silently plans from empty. For a signed database with no ref that is the wrong default; it should warn or refuse the same way. Related to D1.

**D3. Opt out of agent files at scaffold time.** `create-prisma` has no flag and always writes all four agents plus a `postinstall`. Add a prompt and a `--skills none` flag, and have `orm init` ask. Five users in one week; the circulating workaround is wrong. Handed off.

**D4. Missing client API.** Verified absent from the SQL ORM client source: `firstOrThrow` on the collection (it exists on `AsyncIterableResult`, so `.all().firstOrThrow()` works and could be documented as the workaround), atomic `increment`/`decrement` on update, case-insensitive string filters, insert with on-conflict-do-nothing (`skipDuplicates`), and filtering on JSON columns by path or containment (the `jsonb` codec declares only the `equality` trait and the SQL builder has no `->>` or `@>` functions; the workaround is `db.raw.sql`). Also confirmed not supported, for C1's "not yet" list: soft delete, model validations, lifecycle callbacks, custom `Collection` subclasses (`CollectionImpl` has private clone methods), read replicas and multi-database routing, MongoDB referential actions. Each needs a decision: build it, or document the workaround (SQL builder or raw) and say it is not planned. The types work (`Models`, `Shape<>`, where types) is already in PRs.

**D5. `contract infer` output on Prisma 7 databases.** Users report the inferred contract failing to emit: `@db.*` attributes, `Decimal` defaults, non-`public` schemas. Check whether infer on rc.9 still emits removed syntax, and whether the `Decimal @default(0.00)` failure is a bug. Infer should produce a contract that emits. See also D10.

**D6. The npm `latest` tag.** `prisma@latest` is 8.0.0-rc.13 while `@prisma/client@latest` is 7.10.0, so a Prisma 7 project's routine `npx prisma` picks up the 8 CLI against a 7 client. Either move the RC to a `next` tag until GA or state the policy on C4. Serhii said he would find out why; no update.

**D7. `db.connect()` versus `db.runtime()`, and `db.close()` versus `db.runtime().close()`.** Two names for adjacent things, used interchangeably across pages, with a Mongo-only `await`, and now a third pair for teardown. `db.prepare` followed by `db.connect()` throws `DRIVER.ALREADY_CONNECTED` because `prepare` connects in the background. If the API can be one call on both targets, the docs get simpler on every page that shows a script.

**D8. Streaming does not stream.** `postgres()` builds its driver with `cursor: { disabled: true }`, so `for await` over a result iterates an already-buffered array; only the serverless facade exposes cursor batches. The reading-data page promises the opposite. Either expose `cursor` / `batchSize` on `postgres()` or drop the promise (B25). Evidence: `packages/3-extensions/postgres/src/runtime/postgres.ts:245-247`, `packages/3-targets/7-drivers/postgres/src/postgres-driver.ts:39-53`.

**D9. `--db` suppresses `db` ref advancement.** `db init` and `db update` advance the `db` ref only when `--db` is omitted; with `--db` they do not unless `--advance-ref` is also passed. Every doc example passes `--db`, and the result is `MIGRATION.PLAN_ORIGIN_UNKNOWN` on the second plan. The rule is surprising and undocumented. Consider advancing regardless of how the URL was supplied, or warning when `--db` is used without `--advance-ref` and no `db` ref exists. Related to D1 and D2. Evidence: `cli/src/control-api/operations/ref-advancement.ts:19-28`.

**D10. Inferred contracts fail at read time without the Temporal polyfill.** `contract infer` maps `timestamp` / `timestamptz` columns to Temporal-backed `Timestamp` / `Timestamptz`; on Node.js before 26.8.2 (checked: 26.8.1, 24.16, and 22.22 have no `globalThis.Temporal`; 26.8.2 does) every read of such a column throws `RUNTIME.TEMPORAL_UNAVAILABLE` unless `temporal-polyfill/full/global` is imported first. `create-prisma` installs the polyfill; `orm init` does not, and neither the existing-project page nor the upgrade guide mentions it, so real upgrades with `DateTime` columns break after step 3. Options: infer to `TimestamptzString` by default, have `orm init` install and import the polyfill, or fail at emit time with a clear message. Evidence: `packages/3-targets/3-targets/postgres/src/core/psl-infer/postgres-type-map.ts:30-33`, `packages/3-targets/3-targets/postgres/src/core/errors.ts:74-86`.

**D11. create-prisma pins rc.8.** `create-prisma@0.11.7` pins `@prisma/orm-postgres` and `@prisma/orm-mongo` to `8.0.0-rc.8` (to match a Composer peer dependency), so a fresh scaffold does not get the rc.9 behaviour the site documents. Either bump on every RC or document the lag. Evidence: `wip/create-prisma-src/src/constants/dependencies.ts:8-10`.

**D12. Permissive mode is unreachable on Postgres.** `postgres(...)` never forwards a `mode`, so the runtime is always strict and every "warn in permissive mode" path on the lints and budgets pages cannot happen; only `mongo(...)` accepts `mode`. Either expose `mode` on `postgres()` or remove the branches and the docs. Evidence: `packages/3-extensions/postgres/src/runtime/postgres.ts:86-94,276-282`, `sql-runtime.ts:187`.

**D13. `migration ref set … @db` fails.** `@db` parses to the empty sentinel for the offline command and fails with `MIGRATION.HASH_NOT_IN_GRAPH` instead of reading the database marker. Either support it (read the marker when a `--db` is available) or reject it with a message that says so. Evidence: `cli/src/control-api/operations/ref.ts:104-118`.

**D14. The shipped skill is stale in the same places as the site, and a few more.** (Also: `cipherstash.EncryptedString` as the canonical extension example although that package was dropped, `createTelemetryMiddleware` from a package that does not exist, and no mention of the cache middleware.) Will said skills are not the focus, but every audit found the skill wrong where the site is wrong, and it is what agents read. Verified stale in `skills/prisma-8/references/`: `execute` for row reads (should be `query`), `PN-CLI-*` / `PN-MIG-*` / `PN-RUN-*` codes (dotted since 0.17), the flat `defineConfig` config file (envelope since rc.4), `orm init --skip-skills` and the `prisma/contract.prisma` default (`src/prisma/`), "N:M include and nested mutations unsupported" (they work), `pn_meta_marker` (it is `prisma_contract.marker`), `createTelemetryMiddleware` from a package that does not exist, `@@discriminator` / `@@base` "SQL-only" (Mongo has them), scalar lists "rejected" (Postgres accepts them), `-y` for destructive consent (it is `--confirm <database>`), free-function migration factories (they are `this.` methods), `migration show` with no argument (positional required). One ticket to the skills owner with this list; the audit files have the line numbers.

**D15. `db update` never plans data operations.** Its allowed classes are additive, widening, destructive; a change that needs a backfill fails and the user must switch to `migration plan`. Undocumented. Either allow it or print the switch hint. Evidence: `cli/src/control-api/operations/db-update.ts:17`.

**D16. `migration status` exits 0 on warnings.** CI must parse `--json` `diagnostics[]` to catch `MIGRATION.DIVERGED`, `MARKER_NOT_IN_HISTORY`, `CONTRACT.AHEAD`, `NO_MARKER`. A `--strict` flag or a non-zero exit on warn-level findings would make C11 one line. Evidence: `cli/src/orm/migration/status-findings.ts`.

**D17. `docs/reference/` and `docs/Supported Versions.md` disagree with the site and partly with the source.** `reference/capabilities.md` and the site's capabilities page disagree on key namespacing (`sql.lateral` vs `postgres.lateral`), pack key nesting, the error code spelling, and whether capabilities are negotiated at connect time or fixed at emit time. `Supported Versions.md` says Node 24 and documents `--merge-tsconfig`; the scaffold says 22.18 and the flag does not exist. `Telemetry.md` says no exit code is sent; rc.9 sends one. `docs/reference/error-reference.md` (from which the site's ORM error reference is generated word for word) still writes `ref set`, `ref list`, and `prisma ref set <name> <hash>` in eight entries; the mounted command has been `migration ref set` since rc.5, so the fix belongs in the error definitions' `fix` text. `mongodb-user-promise.md` promises MongoDB referential actions that are not implemented. Whoever owns `docs/` in the monorepo should reconcile these before the site is written from them; until then the audit treats `packages/` and `docs/releases/` as the only truth.

**D18. create-prisma's MongoDB scaffold writes a `.env` nothing reads.** For MongoDB the scaffold writes `.env` with `DATABASE_URL`, but the generated `prisma.config.ts` reads `MONGODB_URL` and loads no dotenv file, so the file is dead and the CLI's own next-step text says to set `MONGODB_URL` in the environment. Found during the PR 3 review. Evidence: `wip/create-prisma-src/templates/create/_shared/prisma.config.ts.hbs:13,31`, `src/tasks/prisma-setup/project-files.ts:22-26`, `src/tasks/prisma-setup/presentation.ts:46`.
