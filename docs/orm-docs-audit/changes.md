# Prisma ORM 8 docs: what to change, and in what order

This is the working list of changes to the Prisma ORM 8 documentation, built from a page-by-page audit against `@prisma/orm-postgres@8.0.0-rc.9` (the audit files are under `audit/`, with a source citation for every finding). Four kinds of change: restructure the site (A), correct existing pages (B), write new pages (C), change the ORM or its tooling where the docs are hard because the tool is (D). Section E lists small gaps found after the audit.

Item numbers (A1, B11, C9, D4) are stable identifiers used in the audit files and the PRs; some are out of sequence because items were added as they were found. "J1" to "J12" are the reader jobs defined in `journeys.md`. Source paths are in `prisma/orm` at rc.9 unless they start with `create-prisma`.

Status as of 2026-11-20. The per-item notes below carry the history; this section is the summary, checked against `main` on that date.

The site was audited in full a second time on 2026-11-20, against `prisma` 8.0.0-rc.34, the ORM packages at 8.0.0-rc.24 and `create-prisma` 0.14.8. Sections A to E record the first audit (2026-09-11, against rc.9) and what became of it. Section F is the second audit's list, and it is the open work now.

## D. Change the ORM and its tooling

Places where the docs are hard because the tool is. Grouped by who owns the fix.

### ORM behaviour

- **D1. Make adoption one step.** Today: `contract infer`, edit, `contract emit`, `db sign`, `migration plan`, `migration ref set db <hash>`. Either `db sign` sets the `db` ref when none exists, or a `db adopt` command does sign plus ref. Removes the recreate-everything trap in J2 and halves C3. Landed as prisma/orm#30251: `db sign` sets the `db` ref, with or without `--db`; `--advance-ref <name>` redirects and `--no-advance-ref` skips. Documented in #8291. Brief in `brief-db-ref-on-adoption.md`.
- **D2. `migration plan` with no origin and no migrations on disk plans from empty silently.** With migrations on disk it refuses (`MIGRATION.PLAN_ORIGIN_UNKNOWN`). For a signed database with no ref the silent case is the wrong default; it should warn or refuse the same way. Landed with D1: the plan prints a notice and `--json` carries `fromDefaulted: true`.
- **D9. `--db` suppresses `db` ref advancement.** `db init` and `db update` advance the ref only when the URL comes from config; with `--db` they do not unless `--advance-ref` is also passed. Surprising, and every example passes `--db`. Advance regardless, or warn when `--db` is used without `--advance-ref` and no ref exists. Source: `cli/src/control-api/operations/ref-advancement.ts:19-28`. Decided 2026-09-22 and filed as prisma/orm#30370: `db migrate` should advance `db` when the connection comes from `prisma.config.ts` and `CI` is unset, never with `--db`, with `--no-advance-ref` to opt out and a failed ref write downgraded to a warning. Still open on 2026-09-28.
- **D13. `migration ref set … @db` fails** with `MIGRATION.HASH_NOT_IN_GRAPH` instead of reading the marker. Support it when a connection is available, or reject it with a message that says why. Source: `cli/src/control-api/operations/ref.ts:104-118`. Still open on 2026-09-28: `@db` resolves to an empty hash and fails as `errorRefSetHashNotInGraph('')` (`migration/src/refs/contract-ref.ts:50-56`, `cli/src/control-api/operations/ref.ts:98-112`).
- **D15. `db update` never plans data operations.** A change that needs a backfill fails and the user must switch to `migration plan`; nothing says so. Allow it, or print the hint. Source: `cli/src/control-api/operations/db-update.ts:17`. Still open on 2026-09-28: `db update` plans only the additive, widening, and destructive classes and prints no pointer to `migration plan`.
- **D16. `migration status` exits 0 on warnings.** CI has to parse `--json`. A `--strict` flag or a non-zero exit on warn-level findings makes C11 one line. Source: `cli/src/orm/migration/status-findings.ts`. ### Product decisions

- **D4. Missing client API.** Verified absent: `firstOrThrow` on the collection (it exists on the result, so `.all().firstOrThrow()` works), atomic `increment`/`decrement`, case-insensitive string filters, insert with on-conflict-do-nothing (`skipDuplicates`), JSON path or containment filters (the `jsonb` codec has only the `equality` trait). Also not supported: soft delete, validations, lifecycle callbacks, custom `Collection` subclasses, read replicas, MongoDB referential actions. Each needs a decision: build it, or document the workaround and say it is not planned. The types work has shipped: the where filter types (#30158) in rc.9; `Models`, `Scalars<>`, and `Shape<>` (#30231, #30236) in rc.10. Status on 2026-09-28: insert-and-skip-conflicts landed as `createAll(rows, { onConflict: 'skip', conflictOn? })` and `createAndCount` (prisma/orm#30365, rc.12); the field filters have `.ilike(pattern)` and, since rc.12, full-text search operations. Still absent on SQL: atomic increment and decrement, `firstOrThrow` on a collection, case-insensitive equality, JSON path or containment filters, soft delete, validations, lifecycle callbacks, read replicas. MongoDB has `inc` and `mul`; MongoDB referential actions are still unsupported, and the Prisma 6 schema reader now rejects `onDelete` and `onUpdate` explicitly (prisma/orm#30405). Suggested on 2026-09-28, for the ORM team to schedule: build atomic increment and decrement and a collection-level `firstOrThrow` before GA; JSON path and containment filters and list filters after GA; document case-insensitive matching with `.ilike` and its escaping, and nested writes through `db.transaction`; soft delete, validations, callbacks, and read replicas are not planned (Prisma ORM 7 had none built in); MongoDB referential actions not for GA, with `docs/reference/mongodb-user-promise.md` corrected.

### Found while fixing the slices, for other repositories

None of these is fixed. Each was reproduced by an implementer or a reviewer on `prisma` 8.0.0-rc.34, the ORM packages at rc.24, or `create-prisma` 0.14.8.

**create-prisma**

- 0.14.8 pins `prisma` 8.0.0-rc.33, `@prisma/orm-postgres` 8.0.0-rc.23 and `@prisma/composer` 0.38.0, not the current releases. `@prisma/composer-prisma-cloud` pins `@prisma/orm-postgres` to exactly rc.23, so no scaffold can install an rc.24 extension pack; a plain `npm install @prisma/orm-extension-paradedb` fails with `ERESOLVE`.
- The scaffold commits a first migration but no `db` ref. In a checkout where `db:init` never ran, the first `migration:plan` fails with `MIGRATION.PLAN_ORIGIN_UNKNOWN`. It could write `migrations/app/refs/db.json` pointing at the first migration. `dev:composer` never writes the ref either.
- The generated `db.ts` takes Composer's client with `.client` and catches every error. With an extension configured, Composer's client throws `RUNTIME.MISSING_EXTENSION_PACK`, `db.ts` falls back to a client with no `DATABASE_URL`, and the first query fails with `DRIVER.NOT_CONNECTED`, which names neither cause. `service.load().database.clientWith({ extensions })` works.
- With `DATABASE_URL` unset, the first query fails with "Postgres driver not connected", which does not mention `DATABASE_URL`.
- The Next.js template pins `next` 16.4.2, a version with published advisories. In an agent shell its `npm run build` stops with a `SecurityFatalError` that prints instructions addressed to AI agents.
- The MongoDB README tells users to set `MONGODB_URL`; the generated `db.ts` reads `DATABASE_URL`.
- The svelte template's `tsconfig.json` makes SvelteKit warn that `types` must include `$app/types`.

**prisma/orm**

- A `--backfill` plan passes the raw JSON import `endContract` to `this.dataTransform(...)`. Once the placeholders are filled in, that fails the type check and fails at run time with `RUNTIME.NAMESPACE_UNKNOWN`.
- `migration status` suggests `prisma migration plan --name <name>` when there is no `db` ref; that command refuses with `MIGRATION.PLAN_ORIGIN_UNKNOWN`.
- On MongoDB, a new required `DateTime` field planned without `--backfill` gets no fill and no warning; `db migrate` then stops with `MIGRATION.PRECHECK_FAILED`. The planner already warns for an `Int` field.
- The cache middleware registers on a MongoDB client, but no public API lets a MongoDB read carry the cache annotation, so it caches nothing there. Its README still lists MongoDB.
- No supported way exists to remove the Supabase extension from a project: the `supabase` row stays in `prisma_contract.marker` and `migrations/supabase/` stays in the project, so `db verify`, `db init` and `db update` fail with contract-space violations.
- The arktype-json README passes the pack as `{ arktypeJson: pack }`, a key that fails with `RUNTIME.MISSING_EXTENSION_PACK`.
- `@onCreate(nanoid())` and `@onCreate(uuid())` are refused on a MongoDB `String` field.
- The TypeScript starter that `orm init` writes has a `belongsTo` with no foreign key, so `prisma contract print` refuses it. `orm init` also writes `contract.ts` into a `"type": "commonjs"` project, where the first `contract emit` fails.
- `contract infer` without `--output` overwrites the contract source in a PSL project with only a warning.
- A valid Prisma 6 MongoDB self-relation cannot be read through `prisma6Schema` without removing its relation fields: Prisma 6 requires `onDelete: NoAction` and `onUpdate: NoAction` there, and Prisma 8 refuses any referential action.
- The `MIGRATION.PRECHECK_FAILED` advice to keep a field optional leaves out `contract emit` before `migration plan`. Error `docs:` links are printed in two forms, `#CODE` for some codes and `/CODE` for others.
- The `prisma6Schema` README says a document written without an optional field reads with the field absent; at rc.24 it reads as `null`. The side-by-side steps `orm init` prints do not say that a fresh install stops generating the Prisma 6 client.
- `docs/reference/error-reference.md` at `v8.0.0-rc.24` has entries for three codes nothing raises: `CLI.INIT_REINIT_NEEDS_FORCE`, `RUNTIME.EXECUTION_RESULT_MISSING`, `RUNTIME.MIDDLEWARE_RESULT_MISMATCH`.
- The Vite plugin prints `Failed to load config module graph root` at startup on TanStack Start, and still emits the contract.
- `db migrate` prints "across 1 contract space(s)"; `db init` and `db update` print "across 1 contract space".

**prisma/prisma-cli**

- `docs/reference/error-reference.md` lacks 13 codes that `@prisma/composer-cli` 0.39.0 raises: `CONFIG.SECTION_MISSING`, `DEV.ATTACH_FAILED`, `DEV.CONTAINER_FAILED`, `DEV.CONVERGE_FAILED`, `DEV.DEV_SERVER_UNAVAILABLE`, `DEV.DEV_SERVER_UNSUPPORTED`, `DEV.ENVIRONMENT_NAME_MISMATCH`, `DEV.PLATFORM_UNSUPPORTED`, `DEV.PREFLIGHT_FAILED`, `DEV.SERVICE_START_FAILED`, `DEV.STACK_WRITE_FAILED`, `DEV.TARGET_UNSUPPORTED`, `DEV.TEARDOWN_FAILED`.
